Grundsätze des Moduls

Eine Brücke, kein Durchgriff. Eine App sieht vom Rahmen nur den AppContext, nie eine Klasse des Wirts und kein statisches Singleton. Wer den Kontext umsetzt (Mehr-App-Wirt, Einzelstart, Probe), bestimmt, was die App kann.
Entdeckt über den ServiceLoader. Je App eine Datei META-INF/services/envisionz.api.App; der Konstruktor ist parameterlos und baut weder Oberfläche noch Ein-/Ausgabe.
Keine Reflexion, kein JAXB. Der Sitzungszustand ist ein flaches Modell aus Zeichenketten. native-image braucht dafür keine Reflexionskonfiguration, und Formatänderungen lassen sich ohne Codeänderung wandeln.
Kopien, wo herumgereicht wird. AppDescriptor.fileExtensions wird mit List.copyOf übernommen, sonst könnte eine App das Menü des Wirts nachträglich ändern. PersistableState.tabs() bleibt dagegen die lebende Liste, die der Wirt beim Laden füllt.
Reihenfolge bleibt stehen. Eigenschaften und Abschnitte liegen in LinkedHashMap; die Reihenfolge landet so in der XML-Datei, und zwei gesicherte Stände lassen sich vergleichen.
Klein, aber das riskanteste Modul. Wer AppDescriptor anfasst, ändert alle Apps zugleich, und der Bruch fällt erst beim Start des fertigen Programms auf.

Der App-Vertrag envisionz.api

Jede App ist ein eigenständiges Modul, das der Rahmen als Reiter zeigt oder ein Einzelstarter als alleinige Anwendung. Eine Instanz steht für einen geöffneten Reiter, nicht für den App-Typ. Hintergrund, Formeln und Pseudocode →

App, AppView, AppDescriptor – Lebenszyklus und Metadaten

Lebenszyklus: Konstruktor (nur Felder), descriptor() beim Entdecken, createView(ctx) baut die Oberfläche, captureState() vor dem Sichern, restoreState(tab) nach dem Laden, dispose() beim Schließen. AppView trennt die Swing-Komponente vom Vertrag. AppDescriptor ist ein Record mit Kennung, Anzeigename, Menüeintrag, Symbol, Dateiendungen (klein, ohne Punkt) und Tastenkürzel; Name und Menüeintrag werden aus envisionz/api/apps.properties bzw. apps_en.properties übersetzt, sonst gilt der Text des Beschreibers.

Methoden

  • App: descriptor(), createView(AppContext), captureState(), restoreState(PersistableTab), dispose()
  • AppView: component(); mit Vorgabe onShown(), canClose() (Veto beim Schließen)
  • new AppDescriptor(id, displayName, menuLabel, iconResource, fileExtensions, acceleratorKey)

Eingesetzt in

alle 21 Appsframework-core: AppRegistryframework-swing: SwingHost, TabManager, Menü, Leistelauncher-multi

Wofür

Neue Werkzeuge ohne Änderung am Rahmen einhängen; dieselbe App im Mehr-App-Programm und als Einzelprogramm. canClose() nutzen acft, learn, machieve und matrix, onShown() acft, chiffre, hello und matrix.

Beispiel – eine vollständige, minimale App (beispielhaft)

public final class BeispielApp implements App {
    private static final AppDescriptor D = new AppDescriptor(
            "beispiel", "Beispiel", "Beispiel öffnen …", null, List.of("csv"), null);

    public BeispielApp() { }                              // für den ServiceLoader: kein Swing, kein IO
    @Override public AppDescriptor descriptor() { return D; }
    @Override public AppView createView(AppContext ctx) { JPanel p = new JPanel(); return () -> p; }
    @Override public PersistableTab captureState() { return new PersistableTab(D.id(), "Beispiel"); }
    @Override public void restoreState(PersistableTab state) { }
    @Override public void dispose() { }
}
// dazu: src/META-INF/services/envisionz.api.App  mit dem Klassennamen

AppContext – alles, was eine App vom Rahmen bekommt

Der Wirt übergibt den Kontext in createView. Protokoll, Ereignisbus, Dienstverzeichnis, ein eigenes Arbeitsverzeichnis je Instanz (vom Wirt angelegt und beim Schließen aufgeräumt), Reitertitel und Selbstschließen.

Methoden

  • workDirectory() → Path
  • setTitle(String) (null = Name aus dem Beschreiber), closeTab()

Gesicherter Sitzungszustand envisionz.api.persistence

PersistableState, PersistableTab, PersistableTab.Section

Reine Datenträger ohne Logik. PersistableState ist die Wurzel (Formatversion CURRENT_VERSION = "1.0", Sicherungszeitpunkt ISO, Reiterliste, sichtbarer Reiter). Ein PersistableTab trägt flache Eigenschaften und benannte Abschnitte; ein Abschnitt hat eigene Eigenschaften und wiederholte Einträge. section(name) liefert beim zweiten Aufruf denselben Abschnitt. Geschrieben und gelesen wird in framework-core. Hintergrund, Formeln und Pseudocode →

Methoden

  • new PersistableTab(appId, title), set(key, value), get(key, default), section(name), properties(), sections()
  • Section: set, get, addItem() → Map<String,String>, items()
  • PersistableState: version(), savedAt(), tabs(), activeTabIndex() mit Settern

Eingesetzt in

alle 21 Apps: captureState / restoreStateframework-core: StAX-Leser und -Schreiber, PersistenceManagerframework-swing: Arbeitsbereich sichern/laden

Wofür

Arbeitsbereich mit allen offenen Reitern sichern und auf einem anderen Rechner wieder öffnen (Pfade unter path:… legt framework-core relativ ab).

Beispiel – Zustand eines Reiters festhalten und zurückholen

t.set("path:datei", datei.toString());                  // "path:" → relativ zur XML-Datei gesichert

String pfad = state.get("path:datei", null);

Ereignisse zwischen Apps envisionz.api.events

EventBus, FocusAppEvent, EinstellungZeigenEvent

Synchroner Bus für lose Kopplung: Empfänger laufen auf dem veröffentlichenden Faden, in Reihenfolge der Anmeldung; der konkrete Typ des Ereignisses bestimmt die Empfänger. FocusAppEvent(appId) bittet den Wirt, eine App nach vorn zu holen oder zu öffnen, synchron auf dem EDT, damit ein folgendes Datenereignis die frische Instanz schon erreicht. EinstellungZeigenEvent(bereich) lässt die Einstellungs-App einen Bereich zeigen, ohne dass der Rahmen die App kennt.

Methoden

  • publish(E event), subscribe(Class<E>, Consumer<E>) → Subscription
  • Subscription.unsubscribe() – mehrfach unschädlich, typisch in dispose()
  • record FocusAppEvent(String appId), record EinstellungZeigenEvent(String bereich)

Eingesetzt in

umgesetzt in framework-core: SimpleEventBusFocusAppEvent: prelimdesign, matrix; swing: SwingHost, MenuBuilderEinstellungZeigenEvent: settings; swing: MenuBuilder („Über“)Bus genutzt: charts, prelimdesign, hdf5reader, maps, matrix, neural, settings

Wofür

Daten von PrelimDesign oder dem HDF5-Leser an Charts und Maps übergeben, ohne dass sich die Apps kennen; Einstellungen und „Über N-VISIONZ“ aus dem Menü öffnen.

Beispiel – Tabelle an Charts übergeben (so in app-prelimdesign)

ctx.eventBus().publish(new FocusAppEvent("charts"));                        // erst Empfänger nach vorn
ctx.eventBus().publish(new TableAvailableEvent(tabelle, "PrelimDesign: …", "charts")); // dann die Daten (framework-data)

Beispiel – abonnieren und wieder abmelden

EventBus.Subscription s = ctx.eventBus().subscribe(TableAvailableEvent.class, e -> zeige(e.table()));
// in dispose():
s.unsubscribe();
Zugestellt wird nach dem exakten Laufzeittyp: wer einen Obertyp abonniert, bekommt nichts. Die Ereignis-Records sind deshalb endgültig.

ServiceRegistry – Dienste über Typen, nicht über Apps

Eine App meldet eine Umsetzung unter einer Schnittstelle an, eine andere fragt danach. Ist nichts angemeldet, liefert get ein leeres Optional: keine Fehlersituation, sondern eine Auskunft.

Methoden

  • register(Class<T>, T) – ersetzt eine frühere Anmeldung
  • get(Class<T>) → Optional<T>, unregister(Class<T>)

Eingesetzt in

umgesetzt in framework-core: SimpleServiceRegistryfileanalysis: meldet den Dateibetrachter anhdf5reader: fragt ihn abneural: meldet SurrogateService an

Wofür

Eine Datei aus dem Katalog des HDF5-Lesers im Hex-Betrachter der Dateianalyse zeigen, ohne Abhängigkeit von App zu App.

Beispiel – so in app-hdf5reader

Optional<Dateibetrachter> dienst = ctx.services().get(Dateibetrachter.class);   // Schnittstelle aus framework-core
if (dienst.isEmpty()) { status.setText("Hex-Betrachter nicht geöffnet"); return; }
dienst.get().zeige(datei);

FrameworkLogger – schmales Protokoll

Sechs Stufenmethoden und Unterprotokolle. Die Regel dazu: kein System.out.println in App- oder Rahmencode; Diagnose geht über das Protokoll, das der Wirt einrichtet (Konsole und Datei mit Rotation).

Methoden

  • trace, debug, info, warn, error(msg), error(msg, Throwable)
  • forClass(Class), forName(String)

Eingesetzt in

umgesetzt in framework-core: JulFrameworkLogger18 Apps über ctx.logger()framework-swing

Wofür

Fehlersuche in der EXE ohne Konsolenfenster; die Meldungen landen auch in der Protokollkonsole des Hauptfensters.

Gehärtete XML-Leser envisionz.api.xml

SichereXml – die eine Stelle, an der XML-Fabriken entstehen

DOCTYPE verboten, äußere Entitäten, DTD, Schema und XInclude aus, sichere Verarbeitung an. Das schließt beide Angriffe auf einmal: das Nachladen fremder Dateien über <!ENTITY … SYSTEM> und die „Milliarde Lacher“ aus verschachtelten Entitäten. Die Dateien des Arbeitsbereichs tragen keine DOCTYPE-Deklaration und verlieren nichts. Hintergrund, Formeln und Pseudocode →

Methoden

  • domFabrik() → DocumentBuilderFactory
  • domLeser() → DocumentBuilder
  • staxFabrik() → XMLInputFactory

Eingesetzt in

Achse mit gedrehter Beschriftung envisionz.api.chart

AngledTickAxis – Fähigkeit einer Wertachse

Winkel der Achsenzahlen von 0 bis 90 Grad (außerhalb gekappt), Ankerpunkt des Textes ("AUTO" oder ein Name wie "TOP_RIGHT") und Abstand des Achsentitels über den gedrehten Zahlen. Die Schnittstelle selbst ist frei von JFreeChart; so können die Optionskarten in framework-swing sie bedienen, ohne von framework-chart abzuhängen.

Methoden

  • setLabelAngleDeg(double), getLabelAngleDeg()
  • setLabelAnchorCode(String), getLabelAnchorCode()
  • setLabelGap(double), getLabelGap()

Eingesetzt in

umgesetzt in framework-chart: AngledNumberAxisframework-swing: LegendOptionsPanelacft, charts: ChartOptions

Wofür

Lange Achsenzahlen schräg stellen, ohne dass der Achsentitel in die Zahlen läuft.

Beispiel

if (plot.getDomainAxis() instanceof AngledTickAxis a) { a.setLabelAngleDeg(45); a.setLabelAnchorCode("AUTO"); }
