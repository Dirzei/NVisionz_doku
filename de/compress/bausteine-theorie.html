Bausteine – Bitleser, längenbegrenzte Huffman-Codes, Lauflänge

Die Teile unter den Formaten: wie Bits vom niederwertigen oder vom höchstwertigen Ende gelesen und geschrieben werden, warum Huffman-Codes beim Schreiben umgedreht werden, wie die Paketverschmelzung den optimalen Code unter einer Längengrenze findet, wie kanonische Codes entstehen und bitweise gelesen werden, und PackBits als Lauflängenkodierung. Mit Pseudocode nach BitLeser, BitSchreiber, BitLeserMsb, HuffmanCode, HuffmanDekoder und Rle.

Bitreihenfolgen

Ein Bitstrom ist eine Folge von Bits, die in Bytes abgelegt wird. Offen ist, in welcher Reihenfolge die Bits eines Bytes belegt werden, und in welcher Reihenfolge die Bits einer mehrbittigen Zahl im Strom stehen. Die Formate im Modul benutzen drei Kombinationen:

Lesererstes Bit eines Bytesmehrbittige ZahlFormate
BitLeserBit 0 (niederwertig)niederwertiges Bit zuerstDeflate, Brotli
BitLeserMsbBit 7 (höchstwertig)höchstwertiges Bit zuerstbzip2
Zstdbitsrückwärts vom Stromendehöchstwertiges Bit zuerstzstd (siehe FSE)

Rechenbeispiel LSB. BitSchreiber schreibt nacheinander 5 in 3 Bit, 0 in 1 Bit, ABCD in 16 Bit und 1 in 1 Bit. Heraus kommen die Bytes D5 BC 1A: Byte 0 = 1101010121101\,0\,101_2 (unten die 5, darüber die 0, oben die unteren vier Bit von ABCD), Byte 1 = BC, Byte 2 = 0001101020001\,1010_2 (die oberen vier Bit A und darüber die 1).

Rechenbeispiel MSB. BitLeserMsb über A5 0F liest mit bits(4), bits(8), bits(4) die Werte 10, 80 (= 0x50) und 15 – Bits laufen über die Bytegrenze hinweg von oben nach unten.

Huffman-Codes in einem LSB-Strom

Ein Huffman-Code ist eine Folge von Entscheidungen im Baum, gelesen vom ersten Bit an; kanonisch geschrieben ist das erste Bit das höchstwertige des Codewerts. Ein LSB-Strom legt aber das zuerst geschriebene Bit nach unten. Damit der Leser die Bits in Baumreihenfolge bekommt, schreibt BitSchreiber.huffman(code, l) die ll Bits einzeln, höchstwertiges zuerst. Beispiel: die Codes 110, 0, 1110 ergeben das eine Byte 73 = 0111001120111\,0011_2: von unten gelesen 1, 1, 0 | 0 | 1, 1, 1, 0.

Pseudocode – BitLeser.bits(n) und BitSchreiber.bits(w, n)

funktion lies(n):                           0 ≤ n ≤ 32
    solange haldeBits < n:
        wenn pos ≥ ende: Fehler (nennt die Stelle)
        halde ← halde oder (daten[pos++] << haldeBits);  haldeBits += 8
    w ← halde und (2^n − 1);  halde ← halde >>> n;  haldeBits −= n
    gib w

funktion schreibe(w, n):
    halde ← halde oder ((w und (2^n − 1)) << haldeBits);  haldeBits += n
    solange haldeBits ≥ 8:  gib das unterste Byte aus;  halde ← halde >>> 8;  haldeBits −= 8

funktion huffman(code, l):  für i ← l−1 abwärts bis 0:  schreibe((code >>> i) und 1, 1)

Quelle: envisionz-framework-compress/src/envisionz/compress/bits/BitLeser.java, BitSchreiber.java. aufBytegrenze() verwirft beim Lesen die angebrochenen Bits und füllt beim Schreiben mit Nullen; bytes(...) schreibt ganze Bytes nur an einer Bytegrenze.

Festlegung im Framework: Ein Lesen über das Ende hinaus wirft eine Ausnahme mit der Stelle, statt Nullbits zu liefern – sonst würde aus einem abgeschnittenen Strom ein Dekodierfehler an ganz anderer Stelle. (Ausnahmen mit Absicht: der LZMA-Bereichsleser und die zstd-Ströme, wo das Format das Lesen über das Ende vorsieht.) BitLeser lädt nur so viele Bytes nach, wie er braucht, und hält danach immer weniger als acht Bits in der Halde. BitLeserMsb führt die Position in Bits und prüft vor einem Mehrbitzugriff, ob genug da ist; ein gescheiterter Zugriff verbraucht nichts.

Huffman-Codes und ihre Längengrenze

Für Symbole mit den Häufigkeiten hih_i sucht man Codelängen lil_i, die die Kraft-Ungleichung ∑2−li≤1\sum 2^{-l_i} \le 1 erfüllen und die Gesamtlänge ∑hili\sum h_i l_i minimieren. Huffmans Verfahren (die beiden seltensten Knoten wiederholt zusammenfassen) liefert das Optimum. Die mittlere Länge liegt zwischen der Entropie und einem Bit darüber:

H≤l<H+1,H=−∑ipilog2⁡pi,pi=hi∑jhjH \le \bar{l} < H + 1, \qquad H = -\sum_i p_i \log_2 p_i, \quad p_i = \frac{h_i}{\sum_j h_j}

Huffmans Baum kennt aber keine Längengrenze. Bei stark ungleichen Häufigkeiten wird er tief: Fibonacci-Häufigkeiten ergeben einen Baum, in dem jedes Symbol eine Stufe tiefer liegt als das nächsthäufigere. Deflate erlaubt höchstens 15 Bit, die Codelängen-Tabelle höchstens 7. Ein Code über der Grenze ist nicht „etwas zu lang“, sondern für jeden fremden Leser unlesbar.

Paketverschmelzung

Die Paketverschmelzung (Larmore und Hirschberg, 1990) findet den optimalen Code unter einer Längengrenze LL. Sie beruht auf einem Münzsammlerproblem: jedes Symbol ist auf jeder der Stufen 1…L1 \dots L als „Münze“ vorhanden, mit dem Gewicht hih_i und dem Nennwert 2−k2^{-k} auf Stufe kk. Gesucht ist eine Auswahl vom Gesamtnennwert n−1n - 1 (bei nn Symbolen) mit kleinstem Gesamtgewicht; wie oft ein Symbol in dieser Auswahl vorkommt, ist seine Codelänge.

Praktisch rechnet man von der tiefsten Stufe nach oben: die nach Gewicht sortierte Münzliste wird in Paare zusammengefasst („packen“), und die Pakete werden in die Münzliste der nächsten Stufe einsortiert („verschmelzen“). Nach L−1L - 1 Runden nimmt man von der obersten Liste die 2n−22n - 2 leichtesten Einträge; jedes Symbol erhält als Länge die Zahl seiner Vorkommen darin.

Pseudocode – HuffmanCode.laengen(h, L)

benutzt ← Symbole mit h > 0
wenn keine: gib alle Längen 0
wenn genau eines: gib diesem die Länge 1               Deflate verlangt einen Ein-Bit-Code
grund ← je Symbol ein Posten (h, {s}), nach Gewicht sortiert
pakete ← leer
wiederhole L − 1 mal:
    zusammen ← verschmelze(grund, pakete)              sortiert nach Gewicht
    pakete ← je zwei aufeinanderfolgende Posten zu einem (Gewichte addiert, Symbole vereinigt)
letzte ← verschmelze(grund, pakete)
für die ersten 2·|benutzt| − 2 Posten von letzte:
    für jedes Symbol s darin:  länge[s] ← länge[s] + 1

Quelle: envisionz-framework-compress/src/envisionz/compress/huffman/HuffmanCode.java. Bei gleichem Gewicht wird der Posten aus der Grundliste zuerst genommen.

Rechenbeispiele

Das Lehrbuchbeispiel mit den Häufigkeiten 5, 9, 12, 13, 16, 45 (Summe 100) ergibt die Längen 4, 4, 3, 3, 3, 1 und die kanonischen Codes 1110, 1111, 100, 101, 110, 0. Die mittlere Länge ist 2,24 Bit, die Entropie 2,22 Bit.

Kanonische Codes

Übertragen werden nur die Längen; Schreiber und Leser bilden daraus dieselben Codes. Mit nln_l Codes der Länge ll ist der erste Code der Länge ll

c1=0,cl=2(cl−1+nl−1)c_1 = 0, \qquad c_l = 2\,(c_{l-1} + n_{l-1})

und innerhalb einer Länge wird nach Symbolnummer hochgezählt. HuffmanCode.vollstaendig prüft die Kraft-Summe ∑i2Lmax⁡−li=2Lmax⁡\sum_i 2^{L_{\max} - l_i} = 2^{L_{\max}} (mit dem Sonderfall eines einzelnen Symbols). Deflate und Brotli vergeben so; zstd vergibt die längsten Codes zuerst (siehe FSE und Huffman).

Bitweise dekodieren

Der HuffmanDekoder baut keine Sprungtabelle, sondern hält nur zwei Felder: die Zahl der Codes je Länge und die Symbole, sortiert nach Länge und Nummer. Beim Lesen wird der Code Bit für Bit von oben aufgebaut. Nach ll Bits ist erster der kleinste Code der Länge ll; liegt der gelesene Wert unter erster + (Zahl der Codes dieser Länge), ist das Symbol gefunden. Das ist das Verfahren aus puff.c der zlib-Beispiele.

code ← 0;  erster ← 0;  index ← 0
für ℓ ← 1 bis größte Länge:
    code ← code oder leser.bit()
    anzahl ← zaehl[ℓ]
    wenn code − erster < anzahl:  gib symbol[index + code − erster]
    index ← index + anzahl
    erster ← (erster + anzahl) · 2
    code ← code · 2
Fehler "kein gültiger Huffman-Code"

Quelle: envisionz-framework-compress/src/envisionz/compress/huffman/HuffmanDekoder.java. Der Aufbau kostet einen Durchlauf über die Längen; gegenüber einer Tabelle mit neun Bit Vorschau entfällt der Tabellenaufbau, dafür kostet das Lesen einen Schritt je Bit.

Lauflänge nach PackBits

Rle kodiert nach dem Muster von PackBits: ein Steuerbyte ss, dann Daten.

  • 0≤s≤1270 \le s \le 127: die nächsten s+1s + 1 Bytes stehen einzeln da.
  • 129≤s≤255129 \le s \le 255: das folgende Byte gilt 257−s257 - s-mal (2 bis 128).
  • s=128s = 128 ist nicht vergeben und ein Fehler.

Der Packer nimmt einen Lauf ab drei gleichen Bytes (höchstens 128), sonst sammelt er Einzelbytes (höchstens 128) und bricht vor dem nächsten Dreierlauf ab. Der schlechteste Fall ist begrenzt: ein Steuerbyte je 128 Einzelbytes, also

naus≤n+⌈n128⌉n_{\text{aus}} \le n + \left\lceil \frac{n}{128} \right\rceil

Der beste Fall ist ebenfalls begrenzt: zwei Byte je 128, also höchstens 64 : 1.

Rechenbeispiele (mit Rle.packe): AAAAABCDEEE ergibt FC 41 02 42 43 44 FE 45 – 257−252=5257 - 252 = 5-mal A, dann 2+1=32 + 1 = 3 Einzelbytes BCD, dann 257−254=3257 - 254 = 3-mal E. 3000 gleiche Bytes ergeben 48 Byte: 23 Läufe zu 128 und einer zu 56, je zwei Byte.

solange i < n:
    lauf ← Zahl gleicher Bytes ab i, höchstens 128
    wenn lauf ≥ 3:  gib (257 − lauf), daten[i];  i ← i + lauf
    sonst:
        anfang ← i;  einzeln ← 0
        solange i < n und einzeln < 128:
            wenn daten[i] = daten[i+1] = daten[i+2]: abbrechen
            i ← i + 1;  einzeln ← einzeln + 1
        gib (einzeln − 1), daten[anfang .. anfang + einzeln − 1]

Quelle: envisionz-framework-compress/src/envisionz/compress/rle/Rle.java.

Festlegung im Framework: Rle ist als Vorstufe gedacht, nicht als Ersatz für Deflate: auf Masken, Segmentierungsbildern und dünn besetzten Feldern verkürzt sie den Eingang, sodass das 32-KiB-Fenster von LZ77 danach über ein vielfach größeres Gebiet blickt. Für sich allein ist sie unterlegen.

Wie geprüft wird

  • CompressSelfTest: Bitstrom hin und zurück, umgedrehte Huffman-Codes kommen in Baumreihenfolge zurück, Lesen über das Ende meldet sich; Huffman: das häufigste Symbol hat den kürzesten Code, Kraft-Summe vollständig, mittlere Länge 2,24 Bit im Lehrbuchbeispiel (Toleranz 0,005), bei Fibonacci-Häufigkeiten keine Länge über 15 bzw. 7, eine Symbolfolge kommt über den Dekoder unverändert zurück, ein einzelnes Symbol bekommt ein Bit; RLE hin und zurück für fünf Proben, schlechtester Fall unter n+n/128+1n + n/128 + 1, 3000 gleiche Bytes ergeben genau 48.
  • Msbleserprobe (23 Prüfungen): der MSB-Leser gegen die Ausschnitte einer BigInteger (400 Fälle), fortlaufendes Lesen mit Breiten 1 bis 32, bitsLang(64) gegen ByteBuffer.getLong (50 Fälle), Grenzen und Ausnahmen, ein gescheiterter Zugriff verbraucht nichts.

Eine Lehre aus dem Bau steht in der Moduldoku: die Prüfung „langer Lauf schrumpft stark“ verlangte für 3000 gleiche Bytes weniger als 40 Byte. Richtig sind 48, weil PackBits einen Lauf bei 128 deckelt – die Prüfung lag falsch, nicht der Code.

Grenzen

  • BitLeser und BitSchreiber lesen und schreiben höchstens 32 Bit auf einmal, BitLeserMsb mit bitsLang bis 64. Keiner ist nebenläufig benutzbar.
  • Die Paketverschmelzung legt für jede Stufe neue Listen mit Symbolmengen an; für die Alphabete des Moduls (bis 286 Symbole, Grenze 15) ist das unerheblich, für sehr große Alphabete wäre eine sparsamere Fassung angebracht.
  • Der bitweise Huffman-Dekoder ist langsamer als ein tabellengestützter; gemessen wurde der Unterschied nicht.
  • Die Packer (Rle.packe, Huffman-Längen außerhalb von Deflate) haben außerhalb der Proben noch keinen Aufrufer.
