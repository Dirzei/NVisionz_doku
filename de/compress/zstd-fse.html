Zstandard – FSE, Huffman über Gewichte und der rückwärts gelesene Bitstrom

Die Entropiekodierung von zstd (RFC 8878): wie ein Zustandsautomat nach der Art von tANS Symbole mit gebrochener Bitzahl liest, wie die Zustandstabelle aus einer normierten Verteilung entsteht und wie diese Verteilung im Strom steht, warum der Bitstrom rückwärts läuft, und wie Huffman-Codes aus Gewichten gebaut werden. Mit Pseudocode nach Zstdbits, Zstdfse und Zstdhuff. Rahmen, Literale und Sequenzen stehen auf einer eigenen Seite.

Worum es geht

Huffman gibt jedem Symbol eine ganze Zahl von Bits. Ein Symbol mit der Wahrscheinlichkeit 0,7 trüge eigentlich −log2⁡0,7≈0,51-\log_2 0{,}7 \approx 0{,}51 Bit Information, kostet aber mindestens ein ganzes. Ein Bereichskodierer wie in LZMA vermeidet das, rechnet aber je Bit mit Multiplikationen. FSE (Finite State Entropy, eine Form von tabellierten asymmetrischen Zahlensystemen, tANS) erreicht die gebrochene Bitzahl mit einer Tabelle: je Symbol ein Zugriff, eine Addition und wenige gelesene Bits.

Die Idee hinter tANS

Der Kodierer führt einen Zustand xx aus einem festen Bereich von N=2AN = 2^A Werten (AA = Genauigkeit). Jeder Zustand ist genau einem Symbol zugeordnet; ein Symbol ss mit der normierten Häufigkeit nsn_s besitzt nsn_s Zustände, mit ∑sns=N\sum_s n_s = N. Seine Wahrscheinlichkeit ist also ns/Nn_s / N.

Der Leser sieht im Zustand xx das Symbol s(x)s(x) und kommt zum nächsten Zustand, indem er b(x)b(x) Bits liest und sie zu einer Grundzahl g(x)g(x) addiert:

x'=g(x)+lies(b(x))x' = g(x) + \text{lies}\big(b(x)\big)

Die nsn_s Zustände eines Symbols teilen den ganzen Zustandsraum [0,N)[0, N) lückenlos unter sich auf: der kk-te von ihnen (k=ns,…,2ns−1k = n_s, \dots, 2n_s - 1 gezählt) deckt einen Bereich der Breite 2b2^{b} mit

b=A−⌊log2⁡k⌋,g=k⋅2b−Nb = A - \lfloor \log_2 k \rfloor, \qquad g = k \cdot 2^{b} - N

Ein Symbol mit ns=N/2n_s = N/2 liest so immer genau 1 Bit, eines mit ns=1n_s = 1 immer AA Bits. Liegt nsn_s zwischen zwei Zweierpotenzen, lesen manche seiner Zustände ⌊A−log2⁡ns⌋\lfloor A - \log_2 n_s \rfloor und manche ein Bit mehr – im Mittel ergibt sich ≈−log2⁡(ns/N)\approx -\log_2(n_s/N).

Der Kodierer arbeitet genau umgekehrt: er kennt zu jedem Symbol und dem Folgezustand den Vorzustand und schreibt die Bits, die der Leser lesen wird. Weil der Zustand vom nächsten Symbol abhängt, kodiert er die Symbole von hinten nach vorn – und schreibt den Bitstrom rückwärts, damit der Leser vorwärts dekodieren kann.

Die Zustandstabelle aus einer Verteilung

Welcher Zustand zu welchem Symbol gehört, legt RFC 8878 genau fest, damit Schreiber und Leser dieselbe Tabelle bauen:

  1. Symbole mit der Häufigkeit −1-1 („kommt vor, aber seltener als 1/N1/N“) bekommen je einen Zustand vom Ende her: N−1,N−2,…N-1, N-2, \dots. Sie zählen wie Häufigkeit 1 und lesen stets AA Bits.
  2. Die übrigen Symbole werden der Reihe nach, jedes nsn_s-mal, mit der Schrittweite σ=N/2+N/8+3\sigma = N/2 + N/8 + 3 im Kreis verteilt, wobei die schon belegten Endplätze übersprungen werden. σ\sigma ist ungerade und damit teilerfremd zu NN, trifft also jeden Platz genau einmal.
  3. Dann werden die Zustände jedes Symbols in aufsteigender Folge durchnummeriert, k=ns,ns+1,…k = n_s, n_s + 1, \dots, und bb und gg nach der Formel oben berechnet.

Pseudocode – Zstdfse.ausVerteilung(verteilung, hoechstes, A)

N ← 2^A
wenn Σ (v = −1 ? 1 : v) ≠ N: Fehler "Verteilung geht nicht auf"
hoch ← N − 1
für s ← 0 bis hoechstes:
    wenn v[s] = −1: symbol[hoch--] ← s;  nächster[s] ← 1
    sonst:          nächster[s] ← v[s]
σ ← N/2 + N/8 + 3;  stelle ← 0
für s ← 0 bis hoechstes:
    wiederhole v[s]-mal:
        symbol[stelle] ← s
        stelle ← (stelle + σ) mod N
        solange stelle > hoch:  stelle ← (stelle + σ) mod N     Endplätze überspringen
wenn stelle ≠ 0: Fehler
für i ← 0 bis N−1:
    s ← symbol[i];  k ← nächster[s]++
    bits[i] ← A − ⌊log2 k⌋;  grund[i] ← k · 2^bits[i] − N

Quelle: envisionz-framework-compress/src/envisionz/compress/zstd/Zstdfse.java. Lesen: anfang liest AA Bits als ersten Zustand, symbol(x) schlägt nach, weiter(x) liest bits[x] Bits und addiert grund[x].

Genauigkeit A=5A = 5, N=32N = 32, Verteilung für die Symbole 0 bis 3: (−1,6,16,9)(-1, 6, 16, 9), Summe 1+6+16+9=321 + 6 + 16 + 9 = 32. Die Schrittweite ist σ=16+4+3=23\sigma = 16 + 4 + 3 = 23. Die Tabelle, mit Zstdfse.ausVerteilung über Reflexion berechnet, nach Symbolen geordnet:

Jede Zeile deckt die Folgezustände 0 bis 31 genau einmal ab. Symbol 2 (Wahrscheinlichkeit 1/21/2) kostet immer 1 Bit; Symbol 3 (9/329/32, Information −log2⁡(9/32)≈1,83-\log_2(9/32) \approx 1{,}83 Bit) kostet in zwei Zuständen 1 Bit und in sieben Zuständen 2 Bit; Symbol 0 kostet 5 Bit.

Wie die Verteilung im Strom steht

Eine Verteilung wird vorwärts gelesen, Bits vom niederwertigen Ende jedes Bytes an – im Gegensatz zum Bitstrom, der danach folgt. Die ersten 4 Bit sind A−5A - 5. Dann folgen die Häufigkeiten mit einer schrumpfenden Bitbreite: je weniger vom Zustandsraum noch zu vergeben ist, desto weniger Bits braucht die nächste Zahl. Innerhalb einer Breite gibt es zusätzlich einen Sonderbereich kleiner Werte, die mit einem Bit weniger auskommen. Gespeichert wird die Häufigkeit plus eins (so wird −1-1 zu 0). Nach einer Häufigkeit 0 folgt eine Wiederholungszahl in Zwei-Bit-Gruppen für weitere Nullen; der Wert 3 heißt „drei weitere, und es geht weiter“.

A ← bits(4) + 5;  N ← 2^A
rest ← N + 1;  schwelle ← N;  breite ← A + 1;  s ← 0
solange rest > 1 und s ≤ hoechstesSymbol:
    wenn vorige Häufigkeit war 0:
        weitere ← 0
        solange schau(2) = 3:  weitere ← weitere + 3;  nimm(2)
        weitere ← weitere + bits(2);  setze so viele Symbole auf 0;  weiter
    grenze ← 2·schwelle − 1 − rest
    w ← schau(breite);  klein ← w mod schwelle
    wenn klein < grenze:  zahl ← klein;  nimm(breite − 1)          Sonderbereich
    sonst:  zahl ← w mod (2·schwelle);  wenn zahl ≥ schwelle: zahl ← zahl − grenze
            nimm(breite)
    zahl ← zahl − 1                                                 −1 ist erlaubt
    rest ← rest − |zahl|;  v[s++] ← zahl
    solange rest < schwelle:  breite ← breite − 1;  schwelle ← schwelle / 2
wenn rest ≠ 1: Fehler "summiert sich nicht auf N"
Tabelle ← ausVerteilung(v, s − 1, A);  verbraucht ← aufgerundete Bytes

Quelle: envisionz-framework-compress/src/envisionz/compress/zstd/Zstdfse.java (liesVerteilung, innere Klasse Vorwaerts). Fehlende Bits hinter dem Abschnitt zählen beim Vorausschauen als 0; wer mehr als vier Byte darüber hinaus verbrauchen will, wird abgewiesen.

Der rückwärts gelesene Bitstrom

Innerhalb eines Bytes laufen die Bits vom niederwertigen Ende, der Strom als Ganzes aber vom letzten Byte zum ersten. Im letzten Byte steht deshalb kein Datenbit zuoberst, sondern eine Marke: das höchste gesetzte Bit sagt, wo die Nutzbits aufhören; es und die Nullen darüber sind Füllung. Mit λ\lambda führenden Nullen im letzten Byte hat ein Strom aus mm Byte

8m−(λ+1)8m - (\lambda + 1)

Nutzbits. Beispiel aus der Zstdbausteinprobe: das einzelne Byte 0x05 = 0000 0101 hat die Marke auf Bit 2 und darunter zwei Nutzbits mit dem Wert 01. Ein letztes Byte 0 ist ein Fehler.

anfang(daten, ab, m):
    wenn m ≤ 0 oder daten[ab+m−1] = 0: Fehler
    stelle ← 8m − (führende Nullen des letzten Bytes + 1)
funktion bits(n):   das oberste zuerst
    wenn stelle − n < 0: Fehler "Bitstrom zu Ende"
    wiederhole n-mal: stelle ← stelle − 1;  w ← 2w + Bit (stelle mod 8) von Byte (stelle div 8)
funktion schau(n):  wie bits, aber ohne zu verbrauchen; Bits unter Stelle 0 zählen als 0
funktion bitsMitNullen(n): w ← schau(n); stelle ← stelle − n   darf negativ werden

Quelle: envisionz-framework-compress/src/envisionz/compress/zstd/Zstdbits.java.

Festlegung im Framework: Im Sequenzstrom wird streng gelesen – ein Zugriff unter Stelle 0 ist ein Fehler. Bei den FSE-kodierten Huffman-Gewichten und beim Lesen von Huffman-Codes mit der größten Codelänge auf einmal zählen fehlende Bits dagegen als 0: der Kodierer hat dafür gesorgt, dass die aufgefüllten Nullen dasselbe ergeben. Geprüft wird bei den Literalen danach, und schärfer: nach dem letzten Symbol eines Stroms müssen genau null Bits übrig sein.

Huffman über Gewichte

zstd überträgt für die Literale nicht die Codelängen, sondern Gewichte wsw_s. Ein Gewicht w>0w > 0 belegt 2w−12^{w-1} Anteile des Coderaums, w=0w = 0 heißt „kommt nicht vor“. Aus der Summe der übertragenen Gewichte folgen die größte Codelänge und das letzte Gewicht, das nicht im Strom steht:

S=∑s2ws−1,Lmax⁡=⌊log2⁡S⌋+1,2wletzt−1=2Lmax⁡−SS = \sum_{s} 2^{w_s - 1}, \qquad L_{\max} = \lfloor \log_2 S \rfloor + 1, \qquad 2^{w_{\text{letzt}} - 1} = 2^{L_{\max}} - S

Der Rest 2Lmax⁡−S2^{L_{\max}} - S muss eine Zweierpotenz sein. Die Codelänge eines Symbols ist dann ls=Lmax⁡+1−wsl_s = L_{\max} + 1 - w_s.

Rechenbeispiel (das Beispiel aus RFC 8878, nachgerechnet mit Zstdhuff.ausGewichten): die Gewichte (4,3,2,0,1)(4, 3, 2, 0, 1) der Symbole 0 bis 4 ergeben S=8+4+2+0+1=15S = 8 + 4 + 2 + 0 + 1 = 15, Lmax⁡=4L_{\max} = 4, Rest 16−15=116 - 15 = 1, also w5=1w_5 = 1. Die Codelängen sind 1, 2, 3, –, 4, 4.

Die kanonische Zuweisung läuft andersherum als bei Deflate: zstd vergibt die längsten Codes zuerst, also an die Symbole mit dem kleinsten Gewicht, innerhalb eines Gewichts nach Symbolnummer. Mit der Deflate-Reihenfolge entstünde eine vollständige Tabelle, die andere Symbole liefert.

Gelesen wird mit einer Tabelle über 2Lmax⁡2^{L_{\max}} Einträge: man sieht Lmax⁡L_{\max} Bits an, schlägt Symbol und wahre Codelänge nach und verbraucht nur so viele Bits.

Pseudocode – Zstdhuff.ausGewichten und symbol

S ← Σ 2^(w−1) über w > 0;  wenn S = 0: Fehler
L ← Bitlänge(S);  voll ← 2^L;  rest ← voll − S
wenn rest keine Zweierpotenz: Fehler
w[letztes] ← Bitlänge(rest)
für ℓ ← L abwärts bis 1:                          längste Codes zuerst
    anfang[ℓ] ← stelle;  stelle ← stelle + (Zahl der Symbole mit Länge ℓ) · 2^(L−ℓ)
für jedes Symbol s mit w[s] > 0:
    ℓ ← L + 1 − w[s]
    fülle 2^(L−ℓ) Einträge ab anfang[ℓ] mit (s, ℓ);  anfang[ℓ] += 2^(L−ℓ)

funktion symbol(strom):  v ← strom.schau(L);  strom.nimm(länge[v]);  gib sym[v]

Quelle: envisionz-framework-compress/src/envisionz/compress/zstd/Zstdhuff.java.

Wie die Gewichte im Strom stehen

  • Kopfbyte h≥128h \ge 128: h−127h - 127 Gewichte folgen direkt, je 4 Bit, das erste im oberen Halbbyte.
  • Kopfbyte h<128h < 128: die nächsten hh Byte sind FSE-kodiert, mit einer Verteilung der Genauigkeit höchstens 6. Gelesen wird mit zwei abwechselnden Zuständen. Das Ende steht nirgends als Zahl: es ist erreicht, wenn eine Fortschaltung über den Stromanfang hinausgreift; das dann noch anstehende Symbol des anderen Zustands gehört dazu.
za ← anfang();  zb ← anfang();  n ← 0
wiederhole:
    w[n++] ← sym(za);  za ← weiterNachsichtig(za)
    wenn übrig < 0:  w[n++] ← sym(zb);  abbrechen
    w[n++] ← sym(zb);  zb ← weiterNachsichtig(zb)
    wenn übrig < 0:  w[n++] ← sym(za);  abbrechen

Quelle: envisionz-framework-compress/src/envisionz/compress/zstd/Zstdblock.java (liesBaum).

Wie geprüft wird

  • Zstdbausteinprobe (52 Prüfungen): die Endmarke des rückwärts gelesenen Stroms an Einzelbytes, 400 rückwärts eingebettete Felder zu 0 bis 32 Bit; die drei vorgegebenen Verteilungen (LL, ML, OF) summieren sich richtig, haben die −1-1-Symbole oben und stimmen mit einer Konstruktion nach dem Wortlaut von RFC 8878 4.1.1 überein; ANS-Eigenschaften über 40 gerechnete Verteilungen der Genauigkeit 5 bis 9; Verteilungsköpfe, von einem eigenen Schreiber erzeugt und zurückgelesen (60 Verteilungen, Nullläufe der Längen 1, 3, 4, 7, 18); 500 Symbole gegen einen eigenen FSE-Kodierer; das Huffman-Beispiel der RFC mit elf Symbolen; 60 gerechnete Huffman-Bäume zu je 200 Symbolen; Fehlerfälle (Summe falsch, alle Gewichte null, Rest keine Zweierpotenz).
  • Drei Fehler, die die Formatprobe beim Bau gefunden hat und die als Gegenproben stehen: eine vorgegebene ML-Verteilung mit den −1-1-Symbolen an falscher Stelle (Summe stimmte, Zustand 57 lieferte 32 statt 52), die umgekehrte kanonische Reihenfolge, und ein zu strenger Gewichtsstrom.

Nicht einzeln an Handblöcken prüfbar sind FSE-kodierte Gewichte und FSE-gepackte Sequenztabellen; sie deckt die Zstdprobe über die Anker aus libzstd (siehe Rahmen und Sequenzen).

Grenzen

  • Nur lesend: es gibt keine FSE-Normierung, keine Gewichtssuche und keinen Kodierer im Hauptcode.
  • Die Tabellen werden je Block neu gebaut (bis 292^9 Zustände); schnellere Leser mit mehreren Symbolen je Zugriff gibt es nicht.
  • Genauigkeiten: LL und ML höchstens 9, OF höchstens 8, Huffman-Gewichte höchstens 6 – größere Angaben werden abgewiesen.
