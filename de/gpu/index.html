Die Grafikeinheit aus Java – OpenCL und Vulkan ohne Fremdbibliothek

Wie das Framework die Grafikeinheit anspricht: ohne JNI, ohne Bindungsbibliothek, ohne fremden Übersetzer, allein mit der Schnittstelle für Fremdfunktionen des JDK (FFM, java.lang.foreign) und dem Treiber, der ohnehin auf dem Rechner liegt. Zwei Rückenden – OpenCL und Vulkan Compute – rechnen denselben Kernquelltext; die CPU bleibt Maßstab und Rückfall. Diese Übersicht ordnet die Teile ein; die Vertiefungsseiten erklären jeden Schritt mit Pseudocode.

0Fremdbibliotheken: nur das JDK und der Treiber des Rechners
2Rückenden, OpenCL und Vulkan Compute, mit denselben Begriffen Warteschlange, Puffer, Kern
22Kerne für den ganzen CFD-Schritt, ein Quelltext für beide Rückenden
bitgleichzur CPU auf den Nachbildungen (OpenCL und Vulkan auf der CPU) in allen Fällen der Proben
3,7×ganzer CFD-Schritt über Vulkan auf einer integrierten Notebook-Grafikeinheit gegen acht CPU-Fäden (320 000 Zellen, 2. Ordnung: 55,4 gegen 202,4 ms)
110Gegenproben über die fünf Module, alle rot

Grundsätze

Kein Fremdcode. Kein JOCL, kein LWJGL, kein glslang, kein clspv. Der Zugang ist FFM aus dem JDK; gebraucht wird nur die Bibliothek, die der Grafiktreiber ohnehin mitbringt (OpenCL.dll, vulkan-1.dll). Was sonst eine Bibliothek leistet – Funktionsgriffe, Strukturen, Übersetzer –, steht in wenigen Klassen im Framework.
Die CPU ist der Maßstab. Jeder Kern rechnet dieselben Schritte in derselben Reihenfolge wie der Java-Code. Auf einer Nachbildung (OpenCL bzw. Vulkan auf der CPU) wird Bitgleichheit verlangt; auf einer Karte ist sie der Normalfall, eine Toleranz nur dort, wo die Hardware anders runden darf.
Kein stilles Versagen, aber stiller Rückfall. Fehlt der Treiber, fehlt double oder passt das Verfahren nicht (implizit, viskos, Turbulenz …), rechnet die CPU – und grafikeinheit() sagt, warum. Ein Schritt, der auf dem Gerät keinen physikalischen Zustand ergibt, wird auf der CPU wiederholt und dort gemeldet.
Ein Quelltext. Die Kerne stehen einmal, in OpenCL C. Vulkan bekommt sie über einen eigenen Übersetzer. Eine Berichtigung wirkt so auf beiden Wegen, und keine zweite Fassung kann still auseinanderlaufen.
Optional und austauschbar. Der Löser kennt nur die Schnittstelle Schrittkern. Die Umsetzungen liegen in eigenen Modulen und werden über den ServiceLoader gefunden. Der Löser bleibt reines JDK; fehlt jede Umsetzung, rechnet er auf der CPU.
Jede Probe hat eine rote Gegenprobe. Für jede wichtige Stelle gibt es einen absichtlich verdorbenen Fall (fma zugelassen, Reihenfolge vertauscht, Puffer verwechselt …), und die zuständige Probe muss ihn fangen.

Der Weg: FFM statt Bindungsbibliothek envisionz.opencl · envisionz.vulkan

Eine C-Schnittstelle aus Java ansprechen heißt: Bibliothek laden, für jede Funktion einen Griff mit ihrer Signatur bauen, Strukturen Byte für Byte in Speicher legen, Rückgabewerte prüfen. Bei OpenCL sind es rund 25 Funktionen, bei Vulkan rund 50. Hintergrund und Pseudocode: Gerät öffnen, Puffer, Kerne, Pipeline →

OpenCl, Vulkan – das Gerät, einmal je JVM

Öffnet beim ersten Aufruf Bibliothek, Gerät und (bei OpenCL) Kontext bzw. (bei Vulkan) Instanz, logisches Gerät und Rechenwarteschlange. Ohne Gerät kommt null, und grund() nennt die Ursache.

Methoden

  • OpenCl.oeffne(), Vulkan.oeffne() → Geraet oder null
  • grund(), abgeschaltet()
  • Geraet.programm(quelle, optionen) (OpenCL), Geraet.text()

Schalter

  • -Denvisionz.opencl=aus, -Denvisionz.vulkan=aus
  • ….alle=ja: auch CPU-Geräte (für die Proben)
  • ….bibliothek=PFAD: eine andere Treiberbibliothek
  • dazu im Programm: Einstellungen, Bereich Grafikeinheit

Warteschlange, Puffer, Kern – je Faden

Beide Rückenden haben dieselben drei Begriffe. Eine Warteschlange gehört einem Faden und besitzt ihre Puffer und Kerne; close() gibt alles frei.

Beispiel – y = a x + y in double auf der Grafikeinheit (Vulkan)

String quelle = """
    __kernel void axpy(const int n, const double a, __global const double* x, __global double* y) {
        int i = get_global_id(0);
        if (i < n) y[i] = a * x[i] + y[i];
    }""";
Geraet g = Vulkan.oeffne();                                  // null: Vulkan.grund() sagt warum
Kernbau.Beschreibung b = Uebersetzer.uebersetze(quelle, 64).get("axpy");
try (Warteschlange q = new Warteschlange(g)) {
    Puffer px = q.puffer(8L * n), py = q.puffer(8L * n);
    q.schreibe(px, x);  q.schreibe(py, y);
    Kern k = q.kern(b).arg(0, n).arg(1, 2.5).arg(2, px).arg(3, py);
    q.starte(k, n);                                          // aufgezeichnet, noch nicht abgeschickt
    q.lies(py, y);                                           // schickt ab, wartet, liest
}

Bitgleich zur CPU

Gleitkommarechnung ist nicht assoziativ, und eine Grafikeinheit darf vieles anders machen als Java: a·b + c zu einem fma zusammenziehen, Summen umordnen, Minimum und Maximum ohne Rücksicht auf NaN und das Vorzeichen der Null bilden. Bitgleichheit entsteht nur, wenn jede dieser Freiheiten ausdrücklich genommen wird. Hintergrund, Regeln, das Abweichungsmaß und eine Lehre →

Freiheit des GerätsOpenCLVulkan (SPIR-V)
a*b+c zu fma verschmelzen#pragma OPENCL FP_CONTRACT OFFNoContraction an jeder Gleitkommarechnung
Summen umordnenSummen je Zelle in der Reihenfolge der Flächenliste; die Norm summiert die CPU der Reihe nach
Minimum, Maximumjmin/jmax wie Math.min/Math.max: NaN setzt sich durch, +0 > −0
Division, Wurzeldouble nach IEEE gerundetSache des Treibers – gemessen in ULP
Optimierung des Treiberswahlweise je Kern (-Denvisionz.cfd.gpu.optimiert)immer; NoContraction hält sie vom fma ab

Der Übersetzer OpenCL C → SPIR-V envisionz.vulkan.clc

Vulkan nimmt keine Quelltexte, sondern SPIR-V, einen Binärcode aus 32-Bit-Wörtern. Statt einen fremden Übersetzer mitzuliefern, übersetzt das Framework die benutzte Teilmenge von OpenCL C selbst: Präprozessor, Zerleger, Syntaxbaum, Erzeuger – rund 1 900 Zeilen Java. Aufbau, Sprachumfang und Pseudocode der Erzeugung →

Uebersetzer.uebersetze(quelle, lokal)

Liefert je __kernel eine Kernbau.Beschreibung: die SPIR-V-Wörter, die Arbeitsgruppe, die Parameter (Puffer als Bindungen, Zahlen als Push-Konstanten) und die Größe des Push-Blocks. Alles außerhalb der Teilmenge wird mit Zeilennummer abgewiesen.

Sprachumfang

  • Makros, auch mit Parametern; int, double, bool
  • if, for, while, do, break, continue, return; &&, ||, ?: mit echter Verzweigung
  • Hilfsfunktionen mit Wert- und Zeigerparametern, private und __local-Felder, barrier
  • sqrt, fabs, fmin/fmax, isnan, isinf, signbit, atomic_min/max/add

Geprüft

Alle 22 Kerne des CFD-Schritts und die zwei des Residuums ergeben gültiges SPIR-V (Validierer der Spezifikation als Schiedsrichter); Sprachmittel über 5 000 Werte bitgleich zu Java.

Der ganze CFD-Schritt auf der Karte envisionz.cfd.opencl · envisionz.cfd.vulkan

Nur das Residuum auf der Karte war langsamer als die CPU: Gradienten, Begrenzer und Ränder blieben auf der CPU, und jeder Aufruf kopierte hin und her. Seither bleibt der Zustand während des ganzen Schritts auf dem Gerät; nur Ränder, die das Gerät nicht kennt, rechnet je Stufe die CPU mit ihrem eigenen Code. Abstimmung je Grafikeinheit envisionz.gpu.abstimmung

Welche Arbeitsgruppe, wie viele Ergebnisse je Faden und welche Kachel ein Kern auf einer Karte braucht, lässt sich nicht vorhersagen. Das Framework probiert es auf dem Rechner aus – jeden Kandidaten erst gegen die CPU geprüft – und merkt sich den schnellsten je Gerät und Treiber; bedienbar in den Einstellungen oder auf der Kommandozeile.
