Ein eigener Übersetzer von OpenCL C nach SPIR-V

Warum Vulkan-Kerne im Framework aus demselben OpenCL-C-Text entstehen wie die OpenCL-Kerne, wie der Übersetzer aufgebaut ist (Präprozessor, Zerleger, Syntaxbaum, Erzeuger), wie ein SPIR-V-Modul aussieht, und wie die drei schwierigen Stellen gelöst sind: strukturierter Kontrollfluss, Kurzschlussoperatoren und Puffer als Argumente von Hilfsfunktionen – mit Pseudocode nach dem Quelltext.

Worum es geht

Ein OpenCL-Treiber übersetzt Kernquelltext selbst. Ein Vulkan-Treiber nimmt nur SPIR-V: eine Zwischensprache aus 32-Bit-Wörtern, in der jeder Wert eine Nummer hat, jede Rechnung eine Anweisung ist und jede Verzweigung einen ausdrücklichen Zusammenführungspunkt nennt. Die üblichen Wege dorthin sind fremde Übersetzer – glslang für GLSL, clspv für OpenCL C – mit eigenem Bau, eigenen Fassungen und eigenem nativen Code.

Das Framework geht einen anderen Weg. Die Kerne des CFD-Schritts sind schon in OpenCL C geschrieben und gegen die CPU bitgleich geprüft. Ein zweiter Satz in einer anderen Sprache wäre eine zweite Stelle, an der sich Fehler einschleichen, und eine, die bei jeder Berichtigung mitgezogen werden muss. Also übersetzt das Framework die Teilmenge von OpenCL C, die seine Kerne benutzen, selbst nach SPIR-V. Was außerhalb liegt, wird mit Zeilennummer abgewiesen statt halb übersetzt. Rund 1 900 Zeilen Java, ohne Abhängigkeit.

Wie ein SPIR-V-Modul aussieht

Ein Modul ist eine Folge von 32-Bit-Wörtern: fünf Wörter Kopf (die magische Zahl 0x07230203, die Fassung 1.3 für Vulkan 1.1, der Erzeuger, die höchste vergebene Nummer plus eins, null), dann Anweisungen. Jede Anweisung beginnt mit einem Wort, das Länge und Befehlsnummer trägt. Die Reihenfolge der Abschnitte ist vorgeschrieben:

OpCapability Shader, Float64                    was das Modul braucht
OpExtInstImport "GLSL.std.450"                  Wurzel, Betrag, NMin, NMax
OpMemoryModel Logical GLSL450
OpEntryPoint GLCompute %kern "axpy" %gid …      Einstieg: Name wie im Quelltext
OpExecutionMode %kern LocalSize 64 1 1          die Arbeitsgruppe
OpName …                                        Namen für Fehlermeldungen des Treibers
OpDecorate …                                    Bindungen, Versätze, Builtins, NoContraction
Typen, Konstanten, globale Variablen            Puffer, Push-Block, __local-Felder
OpFunction … OpFunctionEnd                      Hilfsfunktionen und der Kern

Der Erzeuger sammelt die Abschnitte in getrennten Listen und fügt sie am Ende in dieser Reihenfolge zusammen. Typen und Konstanten werden zwischengespeichert, damit jeder genau einmal erklärt ist – SPIR-V verlangt das für Typen.

Parameter: Puffer als Bindungen, Zahlen im Push-Block

In OpenCL C sind Puffer Zeiger. In SPIR-V für Vulkan gibt es keine Zeiger, die von außen kommen; ein Puffer ist eine globale Variable in der Speicherklasse StorageBuffer, ein Block mit einem Feld unbestimmter Länge, dekoriert mit Satz 0 und einer Bindung. Zahlen liegen in einem gemeinsamen Push-Block mit Versätzen nach std430: int auf 4, double auf 8 Byte ausgerichtet.

für jeden Parameter p des Kerns, in Reihenfolge:
    wenn p ist Puffer:
        typ ← Block { Feld[] von double bzw. int }     ArrayStride 8 bzw. 4
        v ← globale Variable StorageBuffer;  DescriptorSet 0, Binding = nächste Nummer
        wenn p const:  NonWritable
    sonst:
        versatz ← aufrunden(pushGröße, Größe(p.typ));  pushGröße ← versatz + Größe(p.typ)
        Mitglied im Push-Block an versatz
im Kern: jede Zahl einmal aus dem Push-Block laden und in eine eigene Variable legen –
so darf der Kern sie wie in C verändern

Der Puffer an Bindung k und die Zahl an Versatz v sind genau das, was Kern.arg(i, …) auf der Java-Seite befüllt. Die Reihenfolge der Kernparameter bleibt dieselbe wie unter OpenCL, sodass derselbe Aufrufcode beide Rückenden bedienen kann.

Strukturierter Kontrollfluss

SPIR-V für Vulkan verlangt strukturierte Verzweigungen: vor jeder bedingten Verzweigung steht, wo die Wege wieder zusammenlaufen (OpSelectionMerge), und jede Schleife nennt im Kopf ihren Ausgang und ihren Fortsetzungsblock (OpLoopMerge). break springt zum Ausgang, continue zur Fortsetzung. Der Erzeuger bildet die C-Anweisungen genau darauf ab.

Pseudocode – if und Schleifen (nach Erzeuger.anweisung, Erzeuger.schleife)

wenn(bed, dann, sonst):
    c ← ausdruck(bed)
    merge, bDann, bSonst ← neue Blöcke   (ohne sonst: bSonst = merge)
    OpSelectionMerge merge;  OpBranchConditional c, bDann, bSonst
    Block bDann:   anweisung(dann);   wenn nicht beendet: springe merge
    Block bSonst:  anweisung(sonst);  wenn nicht beendet: springe merge
    Block merge

schleife(init; bed; schritt) rumpf:
    anweisung(init)
    kopf, prüfung, körper, weiter, aus ← neue Blöcke
    springe kopf
    Block kopf:     OpLoopMerge aus, weiter;  springe prüfung
    Block prüfung:  c ← ausdruck(bed);  OpBranchConditional c, körper, aus
    Block körper:   (break → aus, continue → weiter)  anweisung(rumpf);  springe weiter
    Block weiter:   ausdruck(schritt);  springe kopf
    Block aus
do … while: der Kopf springt gleich in den Körper, geprüft wird im Fortsetzungsblock

Code hinter return, break oder continue im selben Block ist tot und wird nicht erzeugt – SPIR-V erlaubt nach einer Sprunganweisung keine weitere im Block.

Kurzschluss: &&, || und ?:

In C wertet a && b den rechten Teil nur aus, wenn der linke wahr ist. Das ist nicht nur Geschwindigkeit, sondern oft Bedingung: i < n && x[i] > 0 liest x[i] nur innerhalb des Puffers. Eine einfache Übersetzung in OpLogicalAnd würde beide Seiten rechnen. Der Erzeuger verzweigt deshalb wirklich und führt das Ergebnis mit OpPhi zusammen, das je nach Herkunftsblock einen Wert wählt:

und(a, b):
    ca ← ausdruck(a);  vonA ← aktueller Block
    rechts, merge ← neue Blöcke
    OpSelectionMerge merge
    OpBranchConditional ca, rechts, merge          falsch: rechts gar nicht rechnen
    Block rechts:  cb ← ausdruck(b);  vonB ← aktueller Block;  springe merge
    Block merge:   r ← OpPhi(false aus vonA, cb aus vonB)
    gib zurück r
oder(a, b): ebenso, nur verzweigt wahr direkt zu merge und der Phi-Wert von dort ist true

Wichtig ist vonB: der rechte Teil kann selbst verzweigen, und dann ist der Block, aus dem es zu merge geht, nicht mehr rechts. Eine Gegenprobe vertauscht die Herkunftsblöcke im OpPhi und muss rot werden.

Hilfsfunktionen und Puffer als Argumente

Die CFD-Kerne rufen Hilfsfunktionen, die Zeiger nehmen: einen Zustand aus einem Puffer lesen, einen Geist in ein privates Feld schreiben, einen Fluss rechnen. In SPIR-V hat ein Zeiger eine Speicherklasse als Teil seines Typs; eine Funktion mit „Zeiger auf double“ müsste wissen, ob er auf ein privates Feld, ein __local-Feld oder einen Puffer zeigt. Zeiger auf Puffer als Funktionsargument verlangen zudem die Fähigkeit VariablePointers, die nicht jedes Gerät hat.

Der Erzeuger löst beides durch Spezialisierung: für jede Form, in der eine Hilfsfunktion gerufen wird, entsteht eine eigene SPIR-V-Funktion. Ein Argument, das ein privates oder lokales Feld ist, wird ein Zeiger der passenden Speicherklasse. Ein Argument, das ein Puffer ist, wird gar nicht übergeben: die Fassung spricht die globale Variable dieser Bindung direkt an.

rufe(f, argumente):
    form ← für jedes Zeigerargument: (privat, Länge) | (lokal, Länge) | (Puffer, Bindung)
    wenn (f, form) schon erzeugt:  fn ← diese Fassung
    sonst:
        wenn f steht im Aufrufstapel:  wirf Fehler(Zeile, "Rekursion")
        fn ← neue Funktion;  Parameter nur für Werte und Feld-Zeiger
        im Rumpf: Puffer-Parameter p ↦ globale Variable der Bindung
        merke (f, form) ↦ fn;  erzeuge den Rumpf
    OpFunctionCall fn(Werte, Feld-Zeiger)

Ein Modul enthält nur die Funktionen, die sein Kern erreicht, und je Kern entsteht ein eigenes Modul. Die Rekursionsprüfung steht vor dem Nachschlagen im Zwischenspeicher – sonst würde eine Funktion, die sich selbst ruft, ihre halb erzeugte Fassung finden und still eine Endlosschleife bilden. Diese Reihenfolge sichert eine Gegenprobe.

Einzelheiten, die zählen

  • Variablen im ersten Block: SPIR-V verlangt alle OpVariable einer Funktion am Anfang ihres ersten Blocks. Der Erzeuger sammelt sie in einer eigenen Liste und setzt sie beim Zusammenfügen vor den Code; deklariert werden darf in C trotzdem überall.
  • Rest wie in C: % wird OpSRem (Vorzeichen des Dividenden, wie Java), nicht OpSMod (Vorzeichen des Divisors). Gegenprobe vorhanden.
  • Umwandlung: int nach double mit Vorzeichen (OpConvertSToF), double nach int abschneidend; Mischrechnungen nach den Regeln von C.
  • signbit liest das Vorzeichenbit aus dem oberen 32-Bit-Wort des double – eine Gegenprobe nimmt das untere.
  • Kennungen: get_global_id(0) ist das Builtin GlobalInvocationId, get_local_id LocalInvocationId, get_group_id WorkgroupId.
  • barrier wird OpControlBarrier mit Arbeitsgruppen-Gültigkeit und Speichersemantik für lokalen Speicher; __local-Felder sind globale Variablen der Speicherklasse Workgroup.
  • Kein fma: jede Gleitkommarechnung erhält NoContraction (siehe Bitgleich zur CPU).
