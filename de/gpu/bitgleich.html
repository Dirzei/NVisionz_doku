Bitgleich zur CPU – welche Freiheiten eine Grafikeinheit hat und wie man sie ihr nimmt

Warum ein Kern auf der Grafikeinheit dieselben Bits liefern kann wie der Java-Code, welche vier Stellen dafür sorgfältig gebaut sein müssen (fma, Summenreihenfolge, Minimum und Maximum, Division und Wurzel), wie Reduktionen trotzdem parallel laufen, wie man eine Abweichung richtig misst – und wie ein falsches Maß einen Übersetzerfehler vortäuschte.

Worum es geht

Eine Probe, die „ungefähr gleich“ verlangt, findet keinen Fehler, der kleiner ist als ihre Toleranz – und in einem Strömungslöser wächst ein kleiner Fehler über tausend Schritte oft zu einem großen. Das Framework verlangt deshalb, wo immer es geht, Bitgleichheit: der Kern auf dem Gerät liefert für jede Zelle dieselben 64 Bit wie der Java-Code. Dann ist jeder Unterschied ein Befund, und die Probe kann ihn bis auf die Zelle eingrenzen.

Möglich ist das, weil Java und die Grafikeinheit beide nach IEEE 754 rechnen: Addition, Subtraktion, Multiplikation, Division und Wurzel in double sind korrekt gerundet, das Ergebnis ist der exakte Wert, auf die nächste darstellbare Zahl gerundet. Wer dieselben Rechnungen in derselben Reihenfolge ausführt, erhält dieselben Bits. Die Kunst liegt darin, dem Gerät jede Gelegenheit zu nehmen, davon abzuweichen.

Erste Freiheit: fma

Ein fused multiply-add rechnet a⋅b+ca\cdot b + c mit einer einzigen Rundung statt zweien:

getrennt: rd⁡(rd⁡(a⋅b)+c)fma: rd⁡(a⋅b+c)\text{getrennt: } \operatorname{rd}\big(\operatorname{rd}(a\cdot b) + c\big) \qquad\qquad \text{fma: } \operatorname{rd}(a\cdot b + c)

Das fma ist genauer – aber eben anders. Java zieht nie selbsttätig zusammen. C-Übersetzer für Grafikeinheiten tun es gern, denn ein fma ist eine Anweisung statt zwei. Dagegen hilft auf jedem Rückende genau eine Zeile:

  • OpenCL: #pragma OPENCL FP_CONTRACT OFF am Kopf des Quelltexts.
  • Vulkan: SPIR-V kennt kein Pragma, sondern eine Dekoration je Ergebnis. Der Baukasten und der Übersetzer setzen NoContraction an jede Gleitkomma-Addition, -Subtraktion, -Multiplikation und -Division. Die Probe CL-01 zählt nach, dass keine fehlt; eine Gegenprobe nimmt die Dekoration weg und muss rot werden.

Zweite Freiheit: Reihenfolge der Summen

Gleitkomma-Addition ist nicht assoziativ: (a+b)+c(a+b)+c und a+(b+c)a+(b+c) können sich im letzten Bit unterscheiden. Eine parallele Summe über viele Fäden ordnet die Summanden zwangsläufig anders als eine Schleife. Das Framework löst das auf drei Wegen:

  • Summen je Zelle rechnet ein Faden je Zelle, in genau der Reihenfolge der Flächenliste der Zelle – der Reihenfolge, in der auch EulerLoeser summiert. Parallel ist nur, welche Zelle ein Faden nimmt, nicht die Reihenfolge innerhalb.
  • Summen über das ganze Netz (die Norm des Residuums) rechnet das Gerät nicht. Es legt die Quadrate je Zelle in einen Puffer, die CPU holt sie und summiert der Reihe nach wie EulerLoeser.norm. Das kostet eine Übertragung von 8 Byte je Zelle und Schritt – und erspart jede Diskussion über die Reihenfolge.
  • Minimum und Maximum über das ganze Netz (der globale Zeitschritt, die Bezugsgrößen des Begrenzers) dürfen parallel laufen: ein Maximum hängt nicht von der Reihenfolge ab. Gerechnet wird zweistufig, wie unten gezeigt.

Pseudocode – Summe je Zelle (Kern zellen)

c ← Kennung des Fadens;  wenn c ≥ zz:  ende
r ← (0, 0, 0, 0, 0)
für q = anfang[c] … anfang[c+1] − 1:            dieselbe Reihenfolge wie die CPU
    f ← zf[q]
    s ← +1, wenn c Eigner von f ist, sonst −1
    r ← r + s · fluss[f]                         komponentenweise, ohne fma
res[c] ← r

Pseudocode – Maximum in zwei Stufen (Kerne bezugTeil, bezugEnde)

Stufe 1: TEILE = 1024 Fäden, jeder nimmt jede 1024. Zelle
i ← Kennung;  m ← 0
für c = i, i + 1024, … < zz:   m ← jmax(m, wert(c))
teil[i] ← m

Stufe 2: eine Arbeitsgruppe von ENDE = 256 Fäden
j ← lokale Kennung;  m ← 0
für i = j, j + 256, … < 1024:   m ← jmax(m, teil[i])
l[j] ← m;  Sperre
für h = 128, 64, …, 1:                         Baum im lokalen Speicher
    wenn j < h:  l[j] ← jmax(l[j], l[j + h])
    Sperre
wenn j = 0:  ergebnis ← l[0]

Ein ähnlicher Fall ist die Prüfung auf physikalischen Zustand: jeder Faden, der eine Zelle mit nicht positiver Dichte oder innerer Energie findet, ruft atomic_min(schlecht, c). Welcher Faden zuerst kommt, ist gleich – am Ende steht die kleinste Zellnummer, dieselbe, die die CPU-Schleife zuerst gefunden hätte.

Dritte Freiheit: Minimum und Maximum

fmin und fmax in OpenCL C – und NMin/NMax in SPIR-V – geben bei einem NaN den anderen Wert zurück und dürfen −0 und +0 als gleich behandeln. Math.max in Java gibt NaN zurück, wenn ein Argument NaN ist, und hält +0 für größer als −0. Die Kerne rufen deshalb nie fmax direkt, sondern zwei kleine Hilfsfunktionen:

jmax(a, b):
    wenn isnan(a) oder isnan(b):  gib zurück a + b      NaN setzt sich durch
    wenn a = 0 und b = 0:  gib zurück (signbit(a) ? b : a)    +0 > −0
    gib zurück (a ≥ b ? a : b)

jmin(a, b):  ebenso, mit (signbit(a) ? a : b) und (a ≤ b ? a : b)

Das NaN-Verhalten ist kein Zierrat: ein NaN in einer Zelle soll den Zeitschritt vergiften und damit auffallen, nicht still durch ein „Minimum“ verschwinden.

Vierte Freiheit: Division und Wurzel

OpenCL verlangt für double eine korrekt gerundete Division und Wurzel. Bei Vulkan hängt die Genauigkeit von OpFDiv und der Wurzel aus GLSL.std.450 am Treiber; das Framework verlässt sich deshalb nicht darauf, sondern misst. Auf der CPU-Nachbildung von Vulkan sind beide korrekt gerundet – dort verlangt die Uebersetzerprobe (CL-04) Bitgleichheit; auf einer Karte meldet sie die größte Abweichung in ULP und lässt höchstens 4 zu. Deshalb prüfen die Proben des CFD-Schritts über Vulkan auf einer Karte gegen eine Toleranz, auf der Nachbildung bitgleich.

Die Optimierung des Treibers

Auch mit allen vier Regeln bleibt ein Rest: der optimierende Übersetzer des Treibers darf Rechnungen umstellen, solange er die Regeln von OpenCL einhält – und was die Regeln genau erlauben, legt jeder Treiber ein wenig anders aus. Gemessen am ganzen CFD-Schritt auf einer integrierten Grafikeinheit:

OpenCL, 80 000 Zellen, 2. Ordnungms je Schrittgegen CPU
alle Kerne mit -cl-opt-disable37,0bitgleich
alle außer dem Flächenkern optimiert (-Denvisionz.cfd.gpu.optimiert=bitgleich)21,6bitgleich
alle optimiert (Vorgabe)16,11,9·10−15 bezogen

Nur der Flächenkern – Rekonstruktion und Roe-Fluss, der längste Kern – rechnet optimiert anders, und das um Rundung. Weil 10−1510^{-15} weit unter jeder physikalisch relevanten Genauigkeit liegt, ist „alle optimiert“ die Vorgabe; der bitgleiche Weg bleibt mit einem Schalter erreichbar, und die strengste Probe nimmt ihn ausdrücklich. Unter Vulkan optimiert der Treiber immer; die Abweichung lag dort in derselben Größe.

Wie man eine Abweichung misst

Wenn nicht bitgleich, dann wie weit daneben? Die naheliegende Antwort – die Abweichung je Wert durch den Wert – ist falsch für Felder, deren Werte durch null gehen. Das Framework misst je Variable bezogen auf den größten Betrag dieser Variable, und bei den fünf Erhaltungsgrößen teilen sich die drei Impulskomponenten einen Bezug:

ev=maxc⁡|ac,v−bc,v|sv,sv=maxc⁡|ac,v|,sρu=sρv=sρw=max⁡(sρu,sρv,sρw)e_v = \frac{\max_c |a_{c,v} - b_{c,v}|}{s_v}, \qquad s_v = \max_c |a_{c,v}|, \qquad s_{\rho u} = s_{\rho v} = s_{\rho w} = \max(s_{\rho u}, s_{\rho v}, s_{\rho w})

und meldet maxv⁡ev\max_v e_v. Umgesetzt in Abweichung.bezogen; alle Proben und das Messwerkzeug nehmen dieselbe Stelle.

Eine Lehre: Zuerst hatte jede Variable ihren eigenen Bezug. In einem zweidimensionalen Fall ist der Impuls senkrecht zur Ebene aber nur Rundungsrauschen um 10−1810^{-18}. Ein anderes letztes Bit dort ergab „Abweichung“ 10−2 bis 1, und es sah aus, als rechne der optimierende Übersetzer der Karte falsch. Erst die Gegenprüfung auf unserer Seite – alle Flüsse jeder Stufe Fläche für Fläche gleich bis aufs letzte Bit, der Schritt trotzdem „35 % daneben“ – zeigte, dass das Maß falsch war, nicht die Karte. Seither gilt der gemeinsame Bezug für den Impuls.

Die Regel der Proben

Gerätverlangt
Nachbildung auf der CPU (OpenCL- oder Vulkan-Software-Treiber)bitgleich: Zustand, Residuum jedes Schritts, Zeit
KarteZustand bezogen < 10−10, Residuen relativ < 10−8, gleiche Zahl der Schritte
Karte, strengster Fall (OpenCL, Ordnung 1, bitgleicher Weg)Normen bitgleich

Die Toleranz auf der Karte ist fünf Größenordnungen weiter als die gemessenen 10−15: sie soll Fehler fangen, nicht Rundung. Die Gegenproben verderben gezielt – die Norm rückwärts summiert, NoContraction weggelassen, die Reduktion nur über eine Hälfte der Gruppe, das Abweichungsmaß mit eigenem Bezug je Impulskomponente – und müssen auf der Nachbildung rot werden.
