SQL über jeder Datenquelle – Hintergrund

Wie eine SELECT-Abfrage über dBASE, SQLite, Parquet und die übrigen Formate ausgewertet wird: Vorrang der Operatoren, dreiwertige Logik mit NULL, LIKE, ganzzahlige Rechnung wie SQLite, Zusammenfassen mit Aggregaten und das Überspringen von Zeilengruppen.

Worum es geht: eine Abfragesprache ohne Datenbank

Jedes lesbare Format liefert dieselbe Sicht: Tabellen aus Feldern und einen Kursor über die Sätze. Darüber wertet envisionz.fileformats.sql eine Teilmenge von SQL aus – SELECT mit WHERE, GROUP BY, HAVING, ORDER BY, LIMIT –, ohne die Datei anzufassen. Bei SQLite ist ausdrücklich nicht die eingebaute Maschine gemeint: gelesen wird mit dem eigenen Leser, ausgewertet mit eigenem Code. Weil die Ergebnisse mit denen von SQLite verglichen werden, gelten dessen Regeln, auch dort, wo sie überraschen.

Vorrang

Der Zerleger ist ein absteigender Parser mit einer Stufe je Vorrang, von schwach nach stark:

OR≺AND≺NOT≺Vergleich, LIKE, IN, BETWEEN, IS NULL≺+,−≺×,/,%≺Vorzeichen.\text{OR} \ \prec\ \text{AND} \ \prec\ \text{NOT} \ \prec\ \text{Vergleich, LIKE, IN, BETWEEN, IS NULL} \ \prec\ +,\,- \ \prec\ \times,\,/,\,\% \ \prec\ \text{Vorzeichen} .

Damit ist a OR b AND c dasselbe wie a OR (b AND c), und NOT a AND b dasselbe wie (NOT a) AND b. Ein Vorrangfehler liefert keine Fehlermeldung, sondern Zeilen – nur die falschen; deshalb wird er am Baum geprüft, nicht am Ergebnis.

Drei Wahrheitswerte

SQL kennt wahr (W), falsch (F) und unbekannt (U). Jeder Vergleich mit NULL ist U, auch NULL = NULL. Die Verknüpfungen folgen Kleenes starker Logik:

ppqqp∧qp \wedge qp∨qp \vee q¬p\neg p
WUUWF
FUFUW
UUUUU

Kurz: p∧q=min⁡(p,q)p \wedge q = \min(p, q), p∨q=max⁡(p,q)p \vee q = \max(p, q), ¬p=1−p\neg p = 1 - p mit F = 0, U = ½, W = 1. WHERE behält nur Zeilen mit W. Darum holt NOT (wert > 0) eine Zeile mit wert NULL nicht zurück: ¬U=U\neg U = U. Wer NULL-Vergleiche als falsch rechnet, bekommt bei jeder Tabelle mit Lücken zu viele oder zu wenige Zeilen.

LIKE

% passt auf beliebig viele Zeichen (auch keine), _ auf genau eines. Groß- und Kleinschreibung zählen nur im ASCII-Bereich nicht, wie bei SQLite: 'ABC' LIKE 'abc' ist wahr, 'ä' LIKE 'Ä' nicht. Mehrere % hintereinander wirken wie eines. Verglichen wird gierig mit zwei Zeigern: gemerkt wird nur das letzte % und die Textstelle dazu; passt ein Zeichen nicht, springt der Musterzeiger hinter dieses % zurück, und das % schluckt ein Zeichen mehr. Ein späteres % macht alle früheren Rücksprungstellen überflüssig – was es vor sich gefunden hat, kann ein anderer Schnitt nicht besser machen. Damit endet der Vergleich nach höchstens

(|t|+1)(|m|+1)(|t| + 1)\,(|m| + 1)

Schritten für Text t und Muster m, ohne Rekursion. Bis 2026-10-25 wurde an jedem % jede Fortsetzung rekursiv versucht; 30-mal %a gegen 40-mal a und ein b lief damit praktisch nicht zu Ende.

Rechnen wie SQLite

Zwei ganze Zahlen ergeben eine ganze Zahl: 7 / 2 ist 3, zur Null hin abgeschnitten, −7/2=−3-7 / 2 = -3; der Rest hat das Vorzeichen des Dividenden, −7mod2=−1-7 \bmod 2 = -1. Sobald eine Gleitkommazahl beteiligt ist, wird gleitend gerechnet: 5.0 / 2 ist 2,5. Ein Überlauf (auch −263/−1-2^{63} / -1) wird zur Gleitkommazahl statt still umzuschlagen; Teilen durch null gibt NULL.

Zusammenfassen

Eine Abfrage fasst zusammen, wenn sie GROUP BY hat oder irgendwo in der Auswahl oder im HAVING ein Aggregat steht – COUNT, SUM, AVG, MIN, MAX. „Irgendwo“ heißt in jedem Teilausdruck, auch in den Grenzen von BETWEEN, in der Liste von IN und im Muster von LIKE: SELECT 5 BETWEEN MIN(w) AND MAX(w) ist eine Zeile, nicht eine je Satz. COUNT(*) zählt alle Zeilen, COUNT(spalte) nur die ohne NULL; SUM, AVG, MIN, MAX übergehen NULL.

Zeilengruppen überspringen

Aus einer WHERE-Bedingung, die aus AND-verknüpften Vergleichen einer Spalte mit einer Zahl oder einem BETWEEN zwischen zwei Zahlen besteht (andere Teile übergeht sie), wird eine Vorauswahl: ein Bereich je Spalte. Ein Leser mit Statistik je Block (Parquet: kleinster und größter Wert je Zeilengruppe) darf Blöcke überspringen, deren Bereich die Bedingung nicht schneiden kann. Das ist ein Angebot, keine Bedingung: ausgewertet wird WHERE an jeder gelieferten Zeile trotzdem, und LIMIT zählt nach dem Überspringen.

Was daraus folgt

  • Annahmen. Eine Tabelle, eine Abfrage; keine Verbindungen, Unterabfragen oder Fensterfunktionen – sie werden benannt abgewiesen.
  • Dieselbe Abfrage über dBASE, SQLite und Parquet liefert dasselbe; das ist die stärkste Prüfung des Auswerters.
  • Ohne ORDER BY, GROUP BY und DISTINCT läuft die Abfrage strömend und bricht bei LIMIT ab; mit einer der drei wird die Auswahl im Speicher gehalten.
  • Ein Aggregat kann überall in einem Ausdruck stehen; das Zusammenfassen hängt nicht daran, wo.

Wie geprüft wird

  • Sqlprobe (Zerlegen, Vorrang am Baum, dreiwertige Logik, Rechnen, Zusammenfassen, Ordnen, drei Formate, ein Ergebnis) und sql.Auswerterprobe mit Erwartungen aus der Beschreibung von SQLite.
  • TheorieFDprobe prüft Aggregate in BETWEEN, IN, LIKE und HAVING sowie die LIKE-Regeln; Gegenproben verschieben Vorrang, NULL-Vergleich, AND mit falsch, ganzzahlige Teilung und die Aggregatsuche.
  • TheorieG2probe misst LIKE mit 30-mal %a gegen eine Zeitgrenze von drei Sekunden und vergleicht 20 000 Zufallsfälle mit einer Tafelrechnung (dynamische Programmierung); die Gegenprobe setzt das rekursive Rücksetzen wieder ein.
  • sql.TheorieG2probe stellt 59 Abfragen, deren Ergebnis SQLite auf derselben Tafel gerechnet hat: Gruppen über zwei Spalten, LIMIT a, b und OFFSET, Aliasse, verneinte Prädikate, Vorauswahl mit vertauschten Seiten, Aggregate in HAVING unter NOT, IS NULL, Funktionen und Rechnung, SUBSTR mit negativen Angaben, Zahlenschreibweisen, Fehler im Satz.

Grenzen

  • Keine Verbindungen mehrerer Tabellen, keine Unterabfragen, kein UNION, keine Fensterfunktionen, nichts Schreibendes.
  • LIKE kennt keine ESCAPE-Klausel; % und _ lassen sich im Muster nicht maskieren.
  • Die Vorauswahl nutzt nur Vergleiche und BETWEEN mit Zahlen; OR, NOT und Texte bleiben ohne Vorauswahl.
  • Wo die Teilmenge bewusst von SQLite abweicht: ORDER BY sortiert nur nach Spalten der Auswahl (sonst wird die Abfrage mit Grund abgewiesen, statt still falsch zu sortieren), OFFSET ohne LIMIT wird angenommen, DISTINCT in einer Aggregatfunktion wird abgewiesen. Die nachgestellte Form x NOT NULL gilt wie in SQLite als x IS NOT NULL.
