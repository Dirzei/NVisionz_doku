Limit against decompression bombs – background

Why packed data may grow by orders of magnitude, how far each format can grow at most, and how Entpackgrenze pushes back at two points: at the announced size and at the size actually produced. With pseudocode following the source, worked examples and the probes.

What it is about

A compression method replaces repetitions with short references. The more uniform the data, the shorter the packed stream – with nothing but zeros, a gigabyte shrinks to about a megabyte. That is the purpose. A decompression bomb turns it around: a small file that demands so much memory when unpacked that the application aborts with an OutOfMemoryError. In Java that is not a clean error but a state after which the runtime no longer works reliably.

There are two kinds, and both must be caught:

  • The honest bomb: the stream really produces huge amounts, for instance Deflate back-references with distance 1 and length 258 in a row.
  • The lying bomb: a header claims a huge size – a zstd frame header of a few bytes can announce 2 GB, a Snappy varint of five bytes 4 GB. A reader that takes the announcement as array size without looking allocates the memory before it has read a single payload byte.

Entpackgrenze is the common answer of all decoders in the module: an upper limit GG on the output of one call, checked against what is announced and against what is actually produced.

How far a format can grow at most

The expansion ratio is q=nout/ninq = n_{\text{out}} / n_{\text{in}}. For the defence its maximum counts: how many output bytes a single input byte produces in the most favourable case. It follows from the shortest command that produces the most bytes.

Deflate. The longest back-reference is 258 bytes (length code 285, no extra bits). If a dynamic block contains only two literal/length symbols and one distance symbol, length code 285 has one bit and distance code 0 (distance 1) has one as well. A back-reference then costs 2 bits:

qmax⁡=258⋅8bit2bit=1032q_{\max} = \frac{258 \cdot 8\ \text{bit}}{2\ \text{bit}} = 1032

The block header and the end-of-block symbol count against it but do not matter for large amounts. Recomputed with the module's own encoder: 4 MiB of zeros give 4080 bytes with Deflate.packe, i.e. q≈1028q \approx 1028. A raw stream of one megabyte of zeros gives 1032 bytes.

zstd. An RLE block consists of three bytes of block header and a single byte that is repeated; the block size sits in 21 bits of the header, and the format limits a block to 128 KiB. Four bytes therefore yield up to 131,072 bytes, qmax⁡=32768q_{\max} = 32\,768. This is the case the Bombenprobe builds as “2 GB from 64 KB”.

LZ4. A length above 15 is continued with extra bytes; every byte 0xFF extends the back-reference by 255. At most about 255 output bytes arise per input byte. Lz4Block.entpacke(block, groesse) therefore rejects any announcement above 255⋅nin+64255 \cdot n_{\text{in}} + 64.

Snappy. The most productive command is the copy of kind 10: three bytes (tag byte plus two bytes of offset) for up to 64 bytes, i.e. qmax⁡=64/3≈21.3q_{\max} = 64/3 \approx 21.3. Snappy.entpacke rejects a target size above 32⋅nin+6432 \cdot n_{\text{in}} + 64 – with headroom above the true maximum.

LZMA, bzip2, Brotli, LZO. No fixed formula bound is in the code here. In LZMA a repeated back-reference with well-trained models costs clearly less than one bit; bzip2 stacks two run-length stages. For these formats GG alone applies.

Checked twice: announcement and growth

A decoder needs an output buffer. If it knows the final size from the header, it is tempting to allocate it at once – and that is exactly the door for the lying bomb. If it does not know it, the buffer grows along. Both paths go through the limit:

  • vorab(angekündigt, vorab, verfahren) checks the announcement against GG and allocates at most vorab bytes. Throughout the module vorab is 16 MiB. A file that announces 2 GB but delivers only 64 KB therefore never occupies more than 16 MiB.
  • wachse(jetzt, gebraucht, verfahren) checks the size actually needed against GG and names the new buffer size.
  • pruefe(groesse, verfahren) is the core of both: negative or above GG means Grenzueberschreitung.

The new buffer size when growing is

Lnew=min⁡(max⁡(2max⁡(L,16),b),max⁡(b,G))L_{\text{new}} = \min\Big(\max\big(2\max(L,\,16),\ b\big),\ \max(b,\ G)\Big)

with the current length LL and the demand b≤Gb \le G. The buffer doubles because then the sum of all copy operations stays bounded: if a buffer grows from L0L_0 to NN by doubling, in total

L0+2L0+4L0+…+N2<NL_0 + 2L_0 + 4L_0 + \dots + \frac{N}{2} < N

bytes are copied – the effort per output byte is constant. Capping at GG makes sure the last doubling step does not request memory beyond the limit merely because it “happens” to double.

Where the limit comes from

The applicable limit GG is determined anew on every call, in a fixed order of precedence:

  1. a limit for a section of the current thread, set with Entpackgrenze.mit(grenze, arbeit);
  2. the system property envisionz.entpacken.max (bytes) – an explicit start option for this run;
  3. the user's setting in the system property envisionz.entpacken.eingestellt, which Rahmeneinstellungen from framework-swing sets at start-up;
  4. the default VORGABE = 2302^{30} bytes = 1 GiB.

The setting comes in via a system property and not via a method call. That way framework-swing needs no compile-time dependency on compress, and applications without compress on the class path still start.

Pseudocode – Entpackgrenze.grenze() and lies(name)

function grenze():
    a ← ABWEICHEND.get()                         thread limit from mit(...)
    if a ≠ null: return min(a, FELD_MAX)
    s ← lies(EIGENSCHAFT)                         "envisionz.entpacken.max"
    if s > 0: return s
    e ← lies(EINGESTELLT)                         "envisionz.entpacken.eingestellt"
    if e > 0: return e
    return min(VORGABE, FELD_MAX)

function lies(name):
    t ← System.getProperty(name)
    if t ≠ null and t parses as an integer:
        v ← number(t)
        if v > 0: return min(v, FELD_MAX)
    return 0                                     0 or negative: not set or unusable

Source: envisionz-framework-compress/src/envisionz/compress/Entpackgrenze.java. eingestellteGrenze() combines the last two steps; mit(...) restores the previous thread limit in finally, also for nested calls.

Pseudocode – the three check points

function pruefe(groesse, verfahren):
    g ← grenze()
    if groesse < 0 or groesse > g: throw Grenzueberschreitung
    return groesse as int

function wachse(jetzt, gebraucht, verfahren):
    pruefe(gebraucht, verfahren)
    neu ← max(2 · max(jetzt, 16), gebraucht)
    return min(neu, max(gebraucht, grenze()))

function vorab(angekuendigt, vorab, verfahren):
    pruefe(angekuendigt, verfahren)                the announcement itself
    return min(angekuendigt, max(1, vorab))     at most vorab is allocated

Source: envisionz-framework-compress/src/envisionz/compress/Entpackgrenze.java. Callers: Inflate (initially vorab(4·input, 16 MiB)), Lzma, Zstd, Lz4, Lzo1x (16 MiB up front each), wachse in all growing buffers; pruefe over the sum of all members, streams and frames in gzip, bzip2, zstd and LZ4.

Sums over members, streams and frames

gzip, bzip2, zstd, LZ4 and XZ may contain several members, streams or frames in a row. Each piece on its own may stay below GG, the sum may not: 128 gzip members of 4 MiB each add up to 512 MiB. The running sum is therefore checked against GG while reading, after each piece – not only at the end, when a thousand pieces are already in memory:

summe ← 0
while another member is present:
    g ← liesGlied(...)                       unpacks this member
    summe ← summe + length(g.daten)
    pruefe(summe, "gzip")                     aborts at the first member above G
    append g

Source: envisionz-framework-compress/src/envisionz/compress/gzip/Gzip.java (glieder); likewise Bzip2.liesStrom per block, Zstd.rahmen and Lz4.rahmen per frame.

Conventions in the framework

Convention in the framework: The default is VORGABE = 1 GiB. The largest possible limit is FELD_MAX = Integer.MAX_VALUE − 8, the largest length a Java array safely accepts. In the settings app the limit can be chosen between 16 and 2047 MiB (section Security, stored as sicherheit.entpackenMaxMb in rahmen.properties).
Convention in the framework: The limit applies to the output of one call, not to the process. Ten calls side by side may each occupy up to GG. At most 16 MiB are allocated up front, whatever a header announces; the rest grows along if it really comes.
Convention in the framework: A system property that cannot be read as an integer counts as not set. A readable number ≤0\le 0 likewise counts as not set; a larger one is clamped to at most FELD_MAX. The same holds for setzeGrenze(b): with b≤0b \le 0 it clears the setting; then the default applies again. (Until 2026-09-28, -Denvisionz.entpacken.max=0 was clamped to 1 byte; unified with WT20.)

Worked example

Limit G=64G = 64 MiB (this is how the Bombenprobe runs). A gzip member holding 4 MiB of zeros is 4098 bytes long. A file of 128 such members is 512 KiB in size and would yield 512 MiB.

  • Members 1 to 16: the sum reaches 16⋅4=6416 \cdot 4 = 64 MiB – exactly GG, allowed.
  • Member 17: sum 68 MiB > GG → Grenzueberschreitung before member 18 is read.

The probe measures how much memory the thread requested in total: 283 MB. That is more than GG, because each member is built in a growing buffer that doubles, and the finished members sit in a list until the abort. Before the limit existed, the same bombs ran to 1 to 2 GB. The probe demands that a bomb requests less than five times the limit.

A growth example following the formula above, with G=64G = 64 MiB = 67,108,864 bytes: a buffer of 48 MiB needs 49 MiB. 2⋅48=962 \cdot 48 = 96 MiB would be the doubling step; it is capped at max⁡(49,64)=64\max(49, 64) = 64 MiB. If it then needs 65 MiB, b>Gb > G, and the call aborts.

How it is checked

  • Entpackgrenzeprobe (10 checks): each level of precedence in both directions against the next – a setting smaller and larger than the default, a start option smaller and larger than the setting, the thread limit smaller and larger than everything. Only then does a wrong rule such as “the smallest wins” show up. In addition: an unusable start option lets the setting apply, 0 means “nothing set” – for setzeGrenze as well as for the start option.
  • Bombenprobe (9 checks): one bomb each for zstd (RLE, 2 GB from 64 KB; frame header claims 2 GB), gzip (128 members of 4 MiB), LZ4 (frame header claims 2 GB), LZMA (header claims 2 GB) and Snappy (header claims 4 GB). Each must abort under a 64 MiB limit and request less than five times that. Two harmless counter-cases (zstd RLE with 1 MiB, one gzip member with 4 MiB) must unpack completely – the limit is not a lock. And the default must be 1 GiB.
  • Counter-probes to the Entpackgrenzeprobe: “setting overlooked” and “smallest instead of precedence” turn red.

Limits

  • The limit bounds the output, not the peak demand. Gzip.entpacke holds all members and then their concatenation, briefly about twice the output; Lzma2 keeps the entire previous output as dictionary.
  • Beyond about 2 GiB nothing works: the output is a Java array. Larger entries need a streaming reader, which the module does not have.
  • Computing time is not limited. A file just below GG is unpacked completely, however long that takes.
  • The plausibility bounds of LZ4 and Snappy only apply to the calls with a known target size; the frame formats rely on GG.
