Deflate – the module's own encoder

How Deflate.packe produces a stream: search for back-references via hash chains, lazy matching, block formation, length-limited Huffman codes, run-length coded code lengths and the cost comparison with the stored block. The format itself is on the page format and decoder.

What it is about

The format specifies what a reader must understand – not how a writer finds its back-references. An encoder has two tasks of very different character:

  1. Parsing: splitting the input into literals and back-references. That is a search: for every position, the longest earlier match within the 32 KiB window. Done exhaustively this would be quadratic; in practice one searches via hash chains and stops after a number of candidates.
  2. Coding: counting the resulting symbols, building the best Huffman codes under the length limit and writing everything into a block – or finding that a stored block is shorter.

Deflate.packe does both in one pass: symbols are collected, and every 16,384 symbols a block is written.

Search via hash chains

A back-reference is at least three bytes long. It is therefore enough to know earlier positions with the same three leading bytes. From the three bytes b0,b1,b2b_0, b_1, b_2 at a position a 15-bit value is formed:

h=((b0⋅210)xor⁡(b1⋅25)xor⁡b2)mod⁡215h = \big( (b_0 \cdot 2^{10}) \operatorname{xor} (b_1 \cdot 2^{5}) \operatorname{xor} b_2 \big) \operatorname{mod} 2^{15}

Two arrays hold the chains: kopf[h] is the most recent position with this value, vorher[p mod 32768] the previous position with the same value as position pp. A search walks the chain backwards from the most recent position, compares byte by byte at each candidate (at most 258) and remembers the longest match. It ends when

  • the chain leaves the window (candidate <p−32767< p - 32767),
  • the chain depth of the level is used up,
  • a match of 258 bytes has been found (it cannot be longer), or
  • the next chain link is no longer smaller than the current one – then the chain runs in a circle, because vorher is a ring buffer and the slot was overwritten.

Lazy matching

Greedy parsing takes the longest match at every position and jumps behind it. That is not always best: one position later a longer match may begin which the greedy step skips. Lazy parsing therefore also checks the next position after each find. If a longer back-reference is possible there, the current byte is written as a literal and the longer find is kept pending – it may in turn be beaten from the position after that.

An example, traced with the module's own encoder: Verdichter, Verdichtung, dichter Verdichter (43 bytes).

Levelparse (end)packed
SCHNELL (greedy)… <22,7> <21,9> er38 bytes
NORMAL (lazy)… <22,7> ␣ <33,10>39 bytes

Greedily, at the position of the space before the last word, “␣Verdicht” (9 bytes, distance 21) is taken, leaving “er” as literals. Lazily, one position later the whole of “Verdichter” is seen (10 bytes, distance 33); the space is written as a literal and the longer find is taken. Here the result is nevertheless one byte longer – the larger distance needs more extra bits, and in such a short block every new symbol also costs space in the code header. On longer text the gain prevails; the module documentation states “regularly a few per cent”.

Writing a block

A block collects up to 16,384 symbols – one pair of length and distance per symbol, distance 0 meaning a literal. When writing, in turn:

  1. Counting. Frequencies of the 286 literal/length symbols (lengths via their length code) and of the 30 distance codes; end of block 256 counts once.
  2. Code lengths. HuffmanCode.laengen(frequency, 15) for both alphabets – optimal lengths under the limit 15 by package-merge (see building blocks).
  3. Distance tree never empty. If the block has no back-reference, distance code 0 gets length 1; an empty distance tree is not provided for in the format.
  4. Trimming. HLIT and HDIST are chosen as small as possible (at least 257 and 1): trailing zeros drop out.
  5. Code-length sequence. Both length sequences one after the other are run-length coded with symbols 16, 17 and 18, their frequencies counted and a code of at most 7 bits built for them; HCLEN is trimmed as long as the length at the last place of the fixed order is zero (at least 4).
  6. Comparing costs and writing the cheaper block.

Pseudocode – run lengths of the code lengths (clFolge)

alle ← litLänge[0..hlit−1] ++ distLänge[0..hdist−1]
i ← 0
while i < length(alle):
    wert ← alle[i];  lauf ← number of equal values from i
    if wert = 0:
        while lauf ≥ 11: wie ← min(lauf, 138); emit (18, wie); i += wie; lauf −= wie
        while lauf ≥ 3:  wie ← min(lauf, 10);  emit (17, wie); i += wie; lauf −= wie
    otherwise:
        emit (wert, 0); i += 1; lauf −= 1           the value itself appears once

Source: envisionz-framework-compress/src/envisionz/compress/deflate/Deflate.java (clFolge). The repeat counts are written minus 3 (for 16 and 17, 2 and 3 bits) or minus 11 (for 18, 7 bits).

The cost comparison

With data that cannot be packed – random data, already packed files – Huffman costs more than it saves: the symbols are nearly uniformly distributed, and the code header comes on top. schreibeBlock therefore computes both paths in bits before writing. For the dynamic block:

Kdyn=3+5+5+4+3HCLEN+∑CL sequence(lcl(s)+z(s))+∑shs(l(s)+z(s))+∑dhd(l(d)+z(d))K_{\text{dyn}} = 3 + 5 + 5 + 4 + 3\,\text{HCLEN} + \sum_{\text{CL sequence}} \big(l_{\text{cl}}(s) + z(s)\big) + \sum_{s} h_s\,\big(l(s) + z(s)\big) + \sum_{d} h_d\,\big(l(d) + z(d)\big)

with the code lengths ll, the extra bits zz (2, 3 and 7 for the code-length symbols 16, 17, 18) and the frequencies hh. For the stored path with rr raw bytes, split into ⌈r/65535⌉\lceil r/65535 \rceil blocks:

Kstored=3+((8−(B+3)mod⁡8)mod⁡8)+8(t−1)+32t+8r,t=max⁡(1,⌈r65535⌉)K_{\text{stored}} = 3 + \Big(\big(8 - (B + 3) \operatorname{mod} 8\big) \operatorname{mod} 8\Big) + 8\,(t - 1) + 32\,t + 8r, \qquad t = \max\!\left(1, \left\lceil \frac{r}{65535} \right\rceil\right)

where BB is the number of bits written so far: the first partial block has three header bits and pads to the byte boundary (0 to 7 bits), every further one starts on a byte boundary and needs three header and five padding bits; plus LEN and NLEN per partial block. Example: B=5B = 5, r=10r = 10 gives 3+0+0+32+80=1153 + 0 + 0 + 32 + 80 = 115 bits; B=0B = 0, r=65,536r = 65{,}536 gives 3+5+8+64+524,288=524,3683 + 5 + 8 + 64 + 524{,}288 = 524{,}368 bits (Deflate.kostenGespeichert). The block is stored if Kstored<KdynK_{\text{stored}} < K_{\text{dyn}} and r≤4⋅65535r \le 4 \cdot 65535. This way a random stream grows by less than one per cent; without the comparison it would be several per cent.

Convention in the framework: The encoder produces no blocks with fixed codes (block type 1). The decoder reads them because foreign streams contain them; producing them oneself only pays in cases that the comparison with the stored block catches anyway.
Convention in the framework: Since 2026-09-28 KstoredK_{\text{stored}} is the exact bit count of the stored partial blocks. Before, the code computed 3+8−(B+3)mod⁡83 + 8 - (B + 3) \operatorname{mod} 8: if the header ended exactly on a byte boundary, that counted 8 padding bits instead of 0, and with more than one partial block their header and padding bits were missing. Both shifted the decision by a few bits only in borderline cases.

Conventions in the framework

Convention in the framework: window 32,768 bytes, minimum length 3, maximum length 258, hash table 2152^{15} entries, 16,384 symbols per block, literal/length and distance codes at most 15 bits, code-length code at most 7 bits. Chain depths 16, 128 and 2048 for SCHNELL, NORMAL, GRUENDLICH; packe(daten) uses NORMAL.

How it is checked

  • Round trip at all three levels over eight samples (CompressSelfTest).
  • Cross check: every stream of our own is read by the JDK Inflater – this proves format conformance independently of our own decoder.
  • Size: on a repeated text at most 10 % larger than JDK level 9 (the run prints the ratio); 50,000 random bytes grow by less than 1 %.
  • Cost of the stored block: kostenGespeichert against the examples above (115, 120 and 524,368 bits), and 10,000 random bytes come out at exactly the computed length. Counter-probes deflate-gespeichert-fuellbits and deflate-gespeichert-teilbloecke red.
  • Edge cases: lengths 257 to 260, distance 1, block change after 16,384 symbols, stored blocks above 65,535 bytes, repetition across 35,000 bytes.
  • Huffman: no length above 15 or 7 with Fibonacci frequencies, the code stays complete.

Limits

  • No optimal parsing: the search is greedy or lazy by one position; methods weighing costs over many positions do not exist.
  • The block boundary is fixed at 16,384 symbols, not where the statistics change.
  • No streaming mode: the whole input is present as an array.
  • No preset dictionary when packing (only when unpacking).
  • The encoders have no caller outside the probes yet; PdfWriter still uses java.util.zip.
