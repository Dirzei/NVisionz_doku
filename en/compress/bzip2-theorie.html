bzip2 – Burrows-Wheeler and the layers above it

bzip2 does not pack with back-references but reorders until packing pays off. This page explains the Burrows-Wheeler transform and its inversion in linear time, move-to-front, the run lengths RUNA/RUNB as a bijective numeral system, the Huffman tables with selector list, the RLE1 pre-stage, the checksums and the old randomisation – with pseudocode following Bzip2.

What it is about

Deflate and LZMA look for repetitions and refer to them. bzip2 takes another route: it reorders the block so that equal characters stand together in runs, turns the runs into small numbers and encodes those with Huffman. When unpacking, the layers run backwards:

The Burrows-Wheeler transform

Write all nn cyclic rotations of a block one below the other, sort them and take the last column LL together with the number zz of the row holding the original block. Example banana:

Rowsorted rotationfirst column FFlast column LL
0abananan
1anabanan
2ananabab
3banana ← z=3z = 3ba
4nabanana
5nanabana

Result: L=L = nnbaaa, z=3z = 3. The last column contains the same characters as the block, only reordered: every character stands before the remaining text by which its row is sorted. In a text, almost always the same letters precede “he ” – which is why LL forms runs although the block itself has none.

Inversion in linear time

The illustrative inversion – repeatedly prepending columns and sorting – takes hours for a 900 KB block. The practical one uses two facts:

  1. The first column FF is LL sorted; it therefore follows from the character counts of LL.
  2. The kk-th occurrence of a character cc in LL and the kk-th occurrence of cc in FF are the same character of the text. (The rows beginning with cc are sorted by their remainder; the rows ending with cc by the same remainder, only rotated by one – so the order is the same.)

If row rr begins at text position tt, then F[r]=T[t]F[r] = T[t]. The same character appears in LL in the row that begins at t+1t + 1. The table weiter therefore assigns to each row rr the row that begins one text position later. With the cumulative counts C[c]C[c] (number of characters smaller than cc) it is built in one pass over LL:

weiter[C[Li]+ranki(Li)]=i\text{weiter}\big[C[L_i] + \text{rank}_i(L_i)\big] = i

with the rank ranki(c)\text{rank}_i(c) = number of cc in L0…Li−1L_0 \dots L_{i-1}. From row zz (text position 0), p=weiter[z]p = \text{weiter}[z] gives the row beginning at position 1; its last character L[p]L[p] is T[0]T[0]. And so on, nn times.

Worked example (recomputed with Bzip2.rueckBwt via reflection): L=L = nnbaaa gives C[a]=0,C[b]=3,C[n]=4C[a] = 0, C[b] = 3, C[n] = 4 and weiter = [3, 4, 5, 2, 0, 1]. From z=3z = 3: p=2→p = 2 \to b, p=5→p = 5 \to a, p=1→p = 1 \to n, p=4→p = 4 \to a, p=0→p = 0 \to n, p=3→p = 3 \to a – i.e. banana.

Pseudocode – Bzip2.rueckBwt(bwt, n, zeiger)

anfang[0..256] ← 0
for i ← 0 to n−1:  anfang[bwt[i] + 1] ← anfang[bwt[i] + 1] + 1
for c ← 1 to 256:  anfang[c] ← anfang[c] + anfang[c−1]       cumulative: C[c]
for i ← 0 to n−1:  weiter[anfang[bwt[i]]++] ← i
p ← weiter[zeiger]
for k ← 0 to n−1:  aus[k] ← bwt[p];  p ← weiter[p]

Source: envisionz-framework-compress/src/envisionz/compress/bzip2/Bzip2.java. Cost O(n+256)O(n + 256) time and one int array of block length.

Move-to-front

Move-to-front replaces every character by its position in a list and then moves it to the front. Runs of equal characters thus become runs of zeros, frequent characters small numbers. The initial list is the bytes occurring in the block in ascending order. Example, list (a, b, n):

Characternnbaaa
position202200
list aftern a bn a bb n aa b na b na b n

RUNA and RUNB

Zeros from move-to-front are not encoded one by one but as a run length with two symbols of their own. The run length r≥1r \ge 1 is written in the bijective base-2 numeral system, with digits 1 (RUNA) and 2 (RUNB), lowest position first:

r=∑k=0m−1dk2k,dk∈{1,2}r = \sum_{k=0}^{m-1} d_k \, 2^k, \qquad d_k ∈ \{1, 2\}

There is no digit 0; hence every length has exactly one representation, and length 0 needs no symbol.

rr12345678
sequenceABA AB AA BB BA A AB A A

Whoever reads the sequence as an ordinary binary number (A = 0, B = 1) gets almost right lengths – and thus silently shifted data. The remaining move-to-front values j≥1j \ge 1 are written as symbol j+1j + 1; the last symbol of the alphabet, number of characters+1\text{number of characters} + 1, is the end of block (EOB). The example above, MTF sequence 2 0 2 2 0 0, becomes the symbols 3, A, 3, 3, B, EOB.

Huffman tables with selector list

A block carries two to six Huffman tables over the same alphabet. Every 50 symbols the table may change; which one applies is given by the selector list. It is itself move-to-front coded and each entry written in unary (as many ones as the value, then a zero). The code lengths of each table are delta coded: a start value of 5 bits, then per symbol a sequence of steps “10” (+1) and “11” (−1), closed by “0”. Lengths from 1 to 20 are allowed. The canonical code is read from the most significant bit, using two tables per length: grenze[ℓ] (largest code value of length ℓ) and basis[ℓ] (offset into the symbol sequence sorted by length).

Convention in the framework: The code lengths need not form a complete tree – the Kraft sum ∑s2−ℓs\sum_s 2^{-\ell_s} is not checked when the tables are built, neither for =1= 1 nor for ≤1\le 1. That is how libbzip2 1.0.8 does it (BZ2_hbCreateDecodeTables checks nothing), and the reader follows it. A stream is rejected only when it actually reads into a gap: if a code does not fit even at the tree's largest length, symbol reports “the code lengths do not form a complete tree” (keinen vollstaendigen Baum). Example: lengths 2, 2, 2 (Kraft sum 3/43/4) occupy 00, 01, 10; a stream containing 11 is rejected, one without it is read – both as in libbzip2 (cross-checked with Python's bz2). Until 2026-09-28 there was a check here that only counted the symbols and never fired; the gap was only noticed after 23 bits had been read.

Which bytes occur in the block at all is stated in two stages: 16 bits say which groups of sixteen are in use, and only for those follow 16 bits each with the individual bytes.

Pseudocode – Bzip2.liesBlock (abridged)

crc ← 32 bits;  randomised ← 1 bit;  zeiger ← 24 bits

                                          check 1 ≤ ℓ ≤ 20
for each tree: grenze, basis, folge from the lengths (canonical);  ℓmax ← largest length
mtf ← zeichen;  lauf ← 0;  stelle ← 1

    every 50 symbols: tree ← next selector
    s ← Huffman symbol(tree)                value does not fit up to ℓmax: error “no complete tree”

RLE1 and the block size

Before the reordering lies a first run-length stage: after exactly four equal bytes a count byte follows with the number of further repetitions, 0 to 255 – even when it is 0. A run thus holds at most 4+255=2594 + 255 = 259 bytes.

while i < n:
    gleich ← number of equal bytes from i, at most 4
    if gleich < 4: write them;  i ← i + gleich
    otherwise: if i + 4 ≥ n: error "count byte missing"
               write the byte (4 + roh[i+4]) times;  i ← i + 5

Source: Bzip2.rueckRle1.

The block size 100,000⋅level100{,}000 \cdot \text{level} counts the bytes after RLE1. libbzip2 leaves 19 bytes of headroom per block (nblockMAX = 100000·level − 19); the multi-block anchor b4 has blocks of 99,981, 99,981 and 50,038 bytes. The level digit only fixes the upper limit: the same content at level 1 and level 9 gives files that differ in exactly one byte – the digit.

Checksums, markers, randomisation

  • Every block begins with the 48-bit marker 314159265359 (the digits of π), the stream ends with 177245385090 (π\sqrt{\pi}). Blocks do not begin on byte boundaries; only the signature BZh and the level digit are aligned. Several streams in a row each begin on a byte boundary again.
  • The block checksum is a CRC-32 with the polynomial 04C11DB7, but unreflected (Crc32Bzip2, see checksums).
  • The combined checksum at the end of the stream is not a checksum over the data but a chaining: G←rotl1⁡(G)xor⁡cblockG \leftarrow \operatorname{rotl}_1(G) \operatorname{xor} c_{\text{block}}, starting from 0. It depends on the order of the blocks.
  • Up to bzip2 0.9.0 a block could be randomised: before sorting, the lowest bit was flipped at certain positions so that very uniform blocks would not slow down the sort. The distances between the positions are in a table of 512 numbers (BZ2_rNums). entwuerfle flips the same bits back after the inverse BWT.
Convention in the framework: Bits are read from the most significant end (BitLeserMsb, position kept in bits). With the Deflate reader not even the block marker would match. The reader throws on an access beyond the end before consuming a bit.

How it is checked

  • Bzip2probe (60 checks): the CRC variant (123456789 → FC891918, different from CBF43926; empty text, zero byte, all byte values; the chaining is not commutative); six anchors from libbzip2: b1/b2 the same content at levels 9 and 1 (same length, exactly one byte different), b3 for RLE1 (300 × A, four C with count byte 0, five D, 259 E in one run, 260 F in two), b4 three blocks in one stream (the combined checksum is the chaining, not the checksum over everything), b5 two streams in one file, b6 the empty content without a single block; damage (signature, level digit, block marker, block and combined checksum, flipped byte, truncated, too short, randomised bit set), and the message names the right stream; two hand-set streams with an incomplete tree (lengths 2, 2, 2): read when the gap is not hit, rejected with “no complete tree” when it is.
  • Bzip2verwuerfeltprobe (4 checks): randomised blocks are recognised and read correctly; without derandomising, the block checksum fails.
  • Msbleserprobe (23 checks): the MSB bit reader against slices of a BigInteger over the same byte array (400 cases), against ByteBuffer.getLong (50 cases), the 48-bit marker, and a failed access at the end consumes nothing.
  • Counter-probes, all red: RUNA/RUNB binary instead of bijective, move-to-front left out, jump table swapped, RLE1 count byte ignored, CRC reflected, combined checksum without rotation; the gap reported only after 23 bits (bzip2-luecke).

Limits

  • Read-only. An encoder would need suffix sorting over up to 900 KB per block.
  • As in libbzip2, an incomplete tree is rejected only when an unassigned code is read, not when the tables are built. An over-subscribed tree (Kraft sum >1> 1) is read with the same tables as in libbzip2; some symbols are then unreachable.
  • bzip2 inside a ZIP container (method 12) is not read, only named.
  • All blocks and streams are held in memory at once; capped by the decompression limit.
