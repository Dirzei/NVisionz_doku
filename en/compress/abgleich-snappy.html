Snappy — comparison against the format description and python-snappy

As of: 2026-09-07
Our implementation: envisionz.compress.snappy.Snappy and SnappyRahmen — read-only
Specification: Snappy format description (Google), public
Compared against: google/snappy 1.1 (über python-snappy)
Test bench: envisionz.compress.SnappySelfTest — 40 checks

The reference implementation. snappy by Google is the reference implementation and at the same time the only one defining the format.

Why this one. Because Snappy is the default in Parquet and in Hadoop stores, and both are built against Google's implementation.

Coverage, computed from the rows below: of 9 features we have 8 present, 0 partial and 1 absent; the reference implementation has 9 / 0 / 0.

● present · ● absent · ● partial · – not applicable

The Note column points into section 5 of this document — not into the workspace item list. The word in front says what kind of thing it is: gap is something we lack and that is open; decided is something we deliberately do not do; property is a trait of the format affecting both implementations; open there is a gap of the reference product. Only the gaps are work — they are collected in section 5.1 and appear as one item in OFFENE-PUNKTE.md.

Snappy is deliberately dumb. No Huffman, no entropy coding, only literals and back-references in four command types — it compresses worse than everything else and is many times faster for it. In Parquet it was the default for a long time.

The one place where it bites: the length for command type 01 starts at four, not at one. A copy shorter than four bytes does not pay, and the spare room is used otherwise. Assuming one reads every copy three bytes short — and because short copies are frequent, the result looks almost right.

Deliberate decisions

SN1 (decided) — No writing

This module reads. A writer would be many times the work of the reader — it must not only know the format but choose well — and nobody here needs one: nothing is compressed, everything is decompressed.
