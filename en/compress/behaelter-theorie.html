gzip and ZIP – reading containers

Two containers around the same Deflate stream, with very different layouts: gzip as a sequence of members read from the front, ZIP as an archive whose table of contents sits at the end and has to be searched for from the end. Layout, checks, pseudocode following the source and the traps where a reader silently goes wrong.

What it is about

A raw Deflate stream does not say what the file was called, when it was made, whether it arrived intact, and in the case of an archive not even which files it contains. The containers provide this. They themselves contain no mathematics beyond a checksum – but they contain places where a reader that is “right in the normal case” delivers wrong results on valid files without reporting an error. This page is about those places.

gzip (RFC 1952)

A gzip file is a sequence of members. Each member is laid out as

Fieldlengthcontent
ID1 ID221F 8B
CM1method, only 8 = Deflate assigned
FLG1bit 0 FTEXT, 1 FHCRC, 2 FEXTRA, 3 FNAME, 4 FCOMMENT; bits 5–7 must be zero
MTIME4Unix time in seconds, 0 = not set
XFL, OS1 + 1hint about the level, operating system of the writer
[FEXTRA]2 + nlength, then n bytes
[FNAME]up to 0file name, ISO-8859-1, terminated by a zero byte
[FCOMMENT]up to 0comment, likewise
[FHCRC]2lower 16 bits of the CRC-32 over all header bytes before it
data…raw Deflate stream
CRC324CRC-32 of the unpacked data
ISIZE4length of the unpacked data modulo 2322^{32}

All multi-byte fields are least significant byte first. The optional fields, if present, appear in a fixed order; whoever skips one that is not there starts the Deflate stream at the wrong place.

The traps

  • Several members. Two gzip files in a row are a valid gzip file, gunzip delivers both parts. A reader that stops after the first member silently returns only part. The end of a member is stored nowhere as a number – it follows only from the Deflate stream, which carries its end within itself. For this, Inflate.entpackeMitEnde returns the position behind the stream.
  • ISIZE is a remainder. Above 4 GiB it holds nmod⁡232n \operatorname{mod} 2^{32}. Therefore nand⁡(232−1)n \operatorname{and} (2^{32}-1) is compared with ISIZE.
  • FHCRC checks only the header, and only with 16 bits. The checksum of the data is CRC32 at the end of the member.
  • Padding at the end. Some writers pad to a block size with zero bytes. If only zeros follow a member, that is not another member.

Pseudocode – Gzip.glieder(gz) and liesGlied

if length(gz) < 18: error                     10 header + 8 trailer
p ← 0;  summe ← 0
while p < length(gz):
    if only zero bytes from p on: break
    g ← liesGlied(gz, p)
    summe ← summe + length(g.daten);  Entpackgrenze.pruefe(summe)
    if g.ende ≤ p: error "does not advance"
    p ← g.ende
if no members: error

function liesGlied(gz, ab):
    check ID 1F 8B, CM = 8, no unknown flag bits
    zeit ← 4 bytes;  system ← gz[ab+9];  p ← ab + 10
    if FEXTRA:   len ← 2 bytes;  zusatz ← len bytes
    if FNAME:    name ← up to the zero byte (ISO-8859-1)
    if FCOMMENT: kommentar ← up to the zero byte
    if FHCRC:    if (CRC32(gz[ab..p−1]) and 0xFFFF) ≠ 2 bytes: error
    (daten, nach) ← Inflate.entpackeMitEnde(gz, p, rest)
    if nach + 8 > length(gz): error "trailer bytes missing"
    if CRC32(daten) ≠ 4 bytes at nach: error
    if (length(daten) and 0xFFFFFFFF) ≠ 4 bytes at nach+4: error
    return member(…, ende = nach + 8)

Source: envisionz-framework-compress/src/envisionz/compress/gzip/Gzip.java. Gzip.entpacke concatenates the data of all members.

Convention in the framework: Name and comment are read as ISO-8859-1, as RFC 1952 prescribes – even though today's writers put UTF-8 in them. There is no guessing. The timestamp is reported, not interpreted. No gzip is written; in the framework, packing is done with Zlib.packe.

ZIP

ZIP is an archive with many entries. Each entry sits in the file as a local header (signature PK\003\004, 30 bytes plus name and extra field) with its packed data. At the end is the central directory: one record per entry (signature PK\001\002, 46 bytes plus name, extra field, comment) with method, CRC-32, both sizes and the offset of the local header. At the very end the end of central directory (PK\005\006, 22 bytes plus comment) with count, size and offset of the directory.

Finding the end of central directory

After the end record a comment of up to 65,535 bytes may follow – with arbitrary content, including the signature PK\005\006 itself. So it is not enough to search backwards for the first signature. In the last min⁡(file size,22+65535)\min(\text{file size}, 22 + 65535) bytes the reader looks for the last position ii at which the fields are consistent with each other:

i+22+ki=file sizeandvi+si≤file size(or vi=FFFFFFFF16)i + 22 + k_i = \text{file size} \qquad\text{and}\qquad v_i + s_i \le \text{file size}\ \ (\text{or } v_i = \text{FFFFFFFF}_{16})

with the comment length kik_i, the directory offset viv_i and the directory size sis_i at this position.

suchweite ← min(file size, 22 + 65535)
schluss ← the last suchweite bytes
for i ← suchweite − 22 down to 0:
    if 4 bytes at i ≠ 06054b50: continue
    passt ← basis + i + 22 + comment length(i) = file size
    liegtDrin ← offset(i) = FFFFFFFF or offset(i) + size(i) ≤ file size
    if passt and liegtDrin: return i
return −1                                  "end signature not in the last … bytes"

Source: envisionz-framework-compress/src/envisionz/compress/zip/Zipdatei.java (sucheEnde).

Zip64

The end record has 16- and 32-bit fields. More than 65,535 entries or sizes and offsets above 4 GiB do not fit. Zip64 then sets the small fields to their maximum (FFFF or FFFFFFFF) and stores the true values elsewhere:

  • 20 bytes before the end record is the Zip64 locator (PK\006\007) with the 64-bit offset of the Zip64 end record (PK\006\006); it holds count, size and offset of the directory with 64 bits (from bytes 32, 40, 48).
  • Per entry, the extra field with ID 1 carries the 64-bit values – only for the fields that are FFFFFFFF in the record, in the order uncompressed, compressed, header offset.

Reading an entry

function bytes(e):
    if e encrypted: error
    if e.methode ∉ {0, 8}: error (names the method)
    kopf ← 30 bytes at e.kopfVersatz;  check signature 04034b50
    daten ← e.kopfVersatz + 30 + name length + extra length   from the local header
    roh ← e.gepackt bytes from daten
    aus ← (methode = 0) ? roh : Inflate.entpacke(roh)
          errors from Inflate become ZipException with the entry name
    if e.ungepackt > 0 and length(aus) ≠ e.ungepackt: error
    if (CRC32(aus) and 0xFFFFFFFF) ≠ e.pruefsumme: error
    return aus

Source: envisionz-framework-compress/src/envisionz/compress/zip/Zipdatei.java (bytes, liesVerzeichnis, zip64, zusatzfeld).

Convention in the framework: The central directory is authoritative, not the sequence of local headers. From the local header only the name and extra field lengths are taken to find the start of the data – both may differ from the directory. Sizes and checksum come from the directory. A reader that only walks the local headers can show a different file list for a manipulated container.
Convention in the framework: If general-purpose bit 11 is set, the name is read as UTF-8, otherwise as CP437 (the code page of the original PKZIP) – not as ISO-8859-1: there 0xFC is ü, in CP437 it is ³. The archive comment at the end of the directory has no bit 11 of its own (APPNOTE 4.4.4 names it only for the name and comment of an entry); per APPNOTE appendix D the original code page applies without bit 11, so it is read as CP437 as well (since 2026-09-28; before, always UTF-8). Encrypted entries and the methods Deflate64 (9), bzip2 (12), LZMA (14), zstd (93), XZ (95) and PPMd (98) are named, reported as findings and not read.

The MS-DOS time

Every entry carries date and time as two 16-bit words:

year=1980+⌊d/29⌋,month=⌊d/25⌋mod⁡16,day=dmod⁡32\text{year} = 1980 + \lfloor d / 2^9 \rfloor, \quad \text{month} = \lfloor d / 2^5 \rfloor \operatorname{mod} 16, \quad \text{day} = d \operatorname{mod} 32

hour=⌊t/211⌋,minute=⌊t/25⌋mod⁡64,second=2(tmod⁡32)\text{hour} = \lfloor t / 2^{11} \rfloor, \quad \text{minute} = \lfloor t / 2^5 \rfloor \operatorname{mod} 64, \quad \text{second} = 2\,(t \operatorname{mod} 32)

The seconds thus have a resolution of two. Date 0 means “no time”; invalid values (month 0 or 13) are set to at least 1 or yield no timestamp. The probe reads 2000-12-01T00:00 from a generated container.

How it is checked

  • Gzipprobe (46 checks): three foreign anchors from Python's gzip (including the two-member one with timestamps 1 and 2); three members give three parts; zero bytes at the end are not a member; all sixteen combinations of the four optional fields, because an error in skipping only shows up with certain combinations; an empty name is a zero byte and not a missing field; eleven sizes from 1 to 200,000 bytes; incompressible data; nine kinds of damage (signature, method 9, unassigned flag bit, header checksum, missing trailer, data checksum, length, too short) – and the message names the right member.
  • Zipprobe (41 checks): generated containers (stored and Deflate, subfolder, 50 entries, MS-DOS time), a real container from Python's zipfile with umlauts in the name, a container with the end signature in the comment that Python's zipfile no longer opens, an archive comment with the byte 0x81 that must come out as “ü” (CP437), five broken containers (wrong checksum, lying size, truncated, not a ZIP, two bytes) and the proof that the reader does not modify the file (size, modification time, content).
  • Zip64probe (12 checks): Zip64 with compressed and stored entries, a container from Python with sizes and header offset from the extra field; counter-probes without Zip64 locator and without extra field.

A lesson from building it is recorded in the module documentation: the first counter-probe for the comment trap stayed green, because the wrong signature sat ten bytes before the end of the file – the search does not even start there, since no complete end record fits before it. Only a longer comment hit the spot that was to be secured.

Limits

  • gzip and ZIP are only read, not written.
  • ZIP entries must fit into a Java array; a compressed entry above Integer.MAX_VALUE bytes is rejected with a message.
  • No encryption, no multi-part archives, no evaluation of data descriptors (the sizes come from the directory anyway).
  • An archive comment that a writer stored as UTF-8 comes out as CP437 – the format offers no marker for it, and nothing is guessed.
  • Gzip.entpacke holds all members and their concatenation in memory at the same time.
