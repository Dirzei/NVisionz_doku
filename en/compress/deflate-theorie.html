Deflate and zlib – format and decoder

What a Deflate stream contains (RFC 1951) and how Inflate reads it: LZ77 back-references, length and distance codes with extra bits, canonical Huffman codes, the three block types, the code-length codes of the dynamic block, plus the zlib frame (RFC 1950) with Adler-32 and dictionary. The module's own encoder has a page of its own.

What it is about

Deflate combines two ideas. The first comes from Lempel and Ziv (1977): text repeats itself, so a passage that occurred before is not written again but referenced – “take 24 bytes starting 13 bytes further back”. The second comes from Huffman (1952): what occurs often gets a short code, what occurs rarely a long one. Deflate thus writes a sequence of literals (single bytes) and back-references (length, distance) and encodes these symbols with Huffman codes.

An example from the module's own encoder (traced with a small program against Deflate.packe): the text abrakadabra, abrakadabra, abrakadabra! (38 bytes) becomes

a b r a k a d <7,4> , ␣ <13,24> !

The back-reference ⟨7,4⟩\langle 7,4\rangle delivers abra. The second one, ⟨13,24⟩\langle 13,24\rangle, is longer than its distance: it reads bytes it has only just written itself and so repeats “abrakadabra, ” almost twice. That is allowed and intended. Packed, it is 29 bytes.

The alphabet: literals, lengths, distances

Literals and lengths share one alphabet of 286 symbols (288 in the fixed code):

  • 0 to 255: the byte itself;
  • 256: end of block;
  • 257 to 285: a length class; the exact length 3 to 258 follows from base plus extra bits.

A length symbol is followed by a symbol from the second alphabet, the 30 distance codes, again with extra bits, for distances 1 to 32,768. The classes grow roughly geometrically: every two classes double the range, and one more extra bit covers it. For a distance code c≥4c \ge 4

z(c)=⌊c2⌋−1,base(c)=2z(c)+1+(cmod⁡2)2z(c)+1z(c) = \left\lfloor \frac{c}{2} \right\rfloor - 1, \qquad \text{base}(c) = 2^{z(c)+1} + (c \operatorname{mod} 2)\, 2^{z(c)} + 1

so for instance code 10: z=4z = 4, base 32+0+1=3332 + 0 + 1 = 33, distances 33 to 48. The lengths follow the same pattern from code 265 on, with two exceptions: code 285 alone stands for 258 without extra bits, and code 284 with all five extra bits set would arithmetically give 227+31=258227 + 31 = 258. The table in RFC 1951 lists only 227 to 257 for code 284; the combination is not provided for by the specification, but widespread decoders and our Inflate accept it. Our compressor always writes 258 as code 285.

Canonical Huffman codes

A prefix code assigns each symbol a bit sequence none of which is the beginning of another; the stream can then be read without separators. A code with lengths lil_i exists exactly when the Kraft inequality holds:

∑i2−li≤1\sum_i 2^{-l_i} \le 1

A complete code satisfies the inequality with equality. RFC 1951 does not state this requirement explicitly; zlib demands it (apart from the special case of a single distance code), our HuffmanDekoder also accepts incomplete codes. The optimal code for frequencies hih_i minimises the mean length l=∑hili/∑hi\bar{l} = \sum h_i l_i / \sum h_i, which lies at most one bit above the entropy H=−∑pilog2⁡piH = -\sum p_i \log_2 p_i.

Only the lengths are transmitted. The codes themselves follow from them by a fixed rule that writer and reader apply alike: shorter codes come first, equal lengths in order of symbol number, and within a length the code counts up. With nln_l codes of length ll, the first code of length ll is

c1=0,cl=2(cl−1+nl−1)c_1 = 0, \qquad c_l = 2\,(c_{l-1} + n_{l-1})

Example: lengths (2,1,3,3)(2, 1, 3, 3) for the symbols A, B, C, D give B = 0, A = 10, C = 110, D = 111.

Convention in the framework: Huffman codes are read from the most significant bit, but the Deflate bit stream fills each byte from the least significant bit. The BitLeser delivers bits in stream order; the HuffmanDekoder builds up the code bit by bit from the top. When writing, BitSchreiber.huffman() reverses the codes. All other fields (block header, extra bits, lengths) are read as ordinary numbers starting at the least significant bit.

The three block types

A stream consists of blocks. Each begins with three bits: BFINAL (last block) and BTYPE.

  • BTYPE 0 – stored. The remaining bits up to the byte boundary are discarded, then follow LEN and NLEN (16 bits each, NLEN being the ones' complement) and LEN bytes unchanged. At most 65,535 bytes per block.
  • BTYPE 1 – fixed codes. The lengths are given by the standard: literals 0–143 have 8 bits, 144–255 have 9, symbols 256–279 have 7, 280–287 have 8; all 30 distance codes have 5 bits.
  • BTYPE 2 – transmitted codes. The block carries its own code lengths, in two stages (see below).
  • BTYPE 3 is not assigned and is an error.

The dynamic block in detail

The header holds HLIT − 257 (5 bits), HDIST − 1 (5 bits) and HCLEN − 4 (4 bits). Then come HCLEN lengths of 3 bits each for the code-length code, in the order

16 17 18 0 8 7 9 6 10 5 11 4 12 3 13 2 14 1 15

The order is chosen so that the rarely used lengths are at the end and can be left out with a small HCLEN. With this code, HLIT+HDIST\text{HLIT} + \text{HDIST} code lengths are then read – both alphabets one after the other as a single sequence. Symbols 0 to 15 are the length itself; three symbols abbreviate runs:

Symbolmeaningextra bitsrepetitions

18zeros711 … 138

In the abrakadabra… example this gives HLIT = 271 (the highest symbol used is length code 270), HDIST = 8, HCLEN = 18, and literal lengths a = 2 bits, the other letters, comma, space, exclamation mark and 256 with 4 bits each, length codes 258 and 270 with 3 bits each; the two distance codes used, 5 and 7, with 1 bit each.

The decoder

Pseudocode – Inflate.lauf(daten, ab, laenge)

leser ← BitLeser(daten, ab, laenge)         bits from the least significant end
repeat:
    letzter ← leser.bit() = 1
    art ← leser.bits(2)
    case art = 0:                               stored
        leser.aufBytegrenze()
        len ← 16 bits;  nlen ← 16 bits
        if len xor 0xFFFF ≠ nlen: error "LEN/NLEN do not match"
        copy len bytes;  jump behind them
    case art = 1:  block(fixed(literals), fixed(distances))
    case art = 2:
        hlit ← bits(5)+257;  hdist ← bits(5)+1;  hclen ← bits(4)+4
        for i ← 0 to hclen−1:  cl[ORDER[i]] ← bits(3)
        c ← HuffmanDekoder(cl)
        i ← 0
        while i < hlit+hdist:
            s ← c.lies(leser)
            if s < 16:   L[i++] ← s
            if s = 16:   if i = 0: error;  repeat L[i−1] (3+bits(2)) times
            if s = 17:   i ← i + 3 + bits(3)          the zeros are already there
            if s = 18:   i ← i + 11 + bits(7)
        if i > hlit+hdist: error "code lengths overflow"
        block(HuffmanDekoder(L[0..hlit−1]), HuffmanDekoder(L[hlit..]))
    case art = 3: error "block type 3 is not assigned"
until letzter
ende ← leser.byteStelle()                      first byte behind the stream

function block(lit, dist):
    repeat:
        s ← lit.lies(leser)
        if s < 256: write byte s
        if s = 256: return
        otherwise:
            len ← LAENGE_BASIS[s−257] + bits(LAENGE_ZUSATZ[s−257])
            d ← dist.lies(leser)
            abstand ← ABSTAND_BASIS[d] + bits(ABSTAND_ZUSATZ[d])
            if abstand > n: error "points before the start"
            for k ← 0 to len−1:  aus[n+k] ← aus[n−abstand+k]   byte by byte
            n ← n + len

Source: envisionz-framework-compress/src/envisionz/compress/deflate/Inflate.java. The tables LAENGE_BASIS, LAENGE_ZUSATZ, ABSTAND_BASIS, ABSTAND_ZUSATZ and CL_ORDNUNG are constants there and are shared with the encoder.

Convention in the framework: Back-references are copied byte by byte, never with System.arraycopy. With a distance smaller than the length, source and destination overlap on purpose: distance 1, length 258 means “the same byte 258 times”. arraycopy treats source and destination as separate and would deliver the right length with the wrong content.

The HuffmanDekoder builds no lookup table but compares bit by bit with two counters per length – the method from puff.c among the zlib examples (details on the building blocks page).

Where the stream ends

A Deflate stream carries its end within itself: the BFINAL bit and then the end-of-block symbol. Inflate.entpackeMitEnde additionally returns the first byte behind the stream. The bits after the last block are padding up to the byte boundary. This is needed for gzip, where eight trailer bytes and possibly another member follow the stream.

Convention in the framework: ende is leser.byteStelle() without a preceding aufBytegrenze(). With today's BitLeser the two are equivalent, because bits(n) loads only as many bytes as it needs and afterwards always keeps fewer than eight bits in its reservoir. The counter-probe swapping the two forms therefore stayed green and was discarded.

The zlib frame

zlib (RFC 1950) puts two header bytes around a Deflate stream and four bytes of checksum behind it:

  • CMF: lower four bits the method (8 = Deflate), upper four bits log2⁡\log_2 of the window size minus 8.
  • FLG: bit 5 is FDICT; the lower five bits are chosen so that (256⋅CMF+FLG)mod⁡31=0(256\cdot\text{CMF} + \text{FLG}) \operatorname{mod} 31 = 0.
  • If FDICT is set, four bytes follow: the Adler-32 of the agreed dictionary.
  • At the end the Adler-32 of the unpacked data, most significant byte first – like the dictionary ID, but unlike every field inside the Deflate stream itself.

Adler-32 consists of two sums modulo 65,521, the largest prime below 2162^{16}:

a=1+∑ixi,b=∑kak,Adler32=216(bmod⁡65521)+(amod⁡65521)a = 1 + \sum_{i} x_i, \qquad b = \sum_{k} a_k, \qquad \text{Adler32} = 2^{16}\, (b \operatorname{mod} 65521) + (a \operatorname{mod} 65521)

The derivation and the overflow trap are on the checksums page.

Worked example. Zlib.packe("abc") gives 14 bytes:

78 01 | 01 03 00 FC FF 61 62 63 | 02 4D 01 27

Header 78 01: 0x7801=30721=31⋅9910x7801 = 30721 = 31 \cdot 991, so divisible by 31. Then a stored block: byte 01 carries BFINAL = 1 and BTYPE = 0, then LEN = 3, NLEN = FFFC, then abc. The encoder computed that a dynamic block would be more expensive for three bytes. At the end the Adler-32 024D0127: a=1+97+98+99=295=0x127a = 1 + 97 + 98 + 99 = 295 = \text{0x127}, b=98+196+295=589=0x24Db = 98 + 196 + 295 = 589 = \text{0x24D}.

Pseudocode – Zlib.entpacke(daten, woerterbuch)

if length < 6: error
cmf ← daten[0];  flg ← daten[1]
if cmf and 0x0F ≠ 8: error "method instead of 8"
if (cmf·256 + flg) mod 31 ≠ 0: error "header check"
anfang ← 2
if flg and 0x20:                               FDICT
    kennung ← 4 bytes, most significant first
    if woerterbuch = null: error (names the ID)
    if Adler32(woerterbuch) ≠ kennung: error "dictionary does not match"
    anfang ← 6
roh ← Inflate.entpacke(daten, anfang, length − anfang − 4, woerterbuch)
if Adler32(roh) ≠ last 4 bytes (most significant first): error
return roh

Source: envisionz-framework-compress/src/envisionz/compress/deflate/Zlib.java. In Inflate the dictionary is placed in front of the output, at most its last 32 KiB; back-references may point into it, and only what is produced after it is returned.

Convention in the framework: Zlib.packe always writes CMF = 0x78 (Deflate, 32 KiB window) and the smallest fitting FLG, i.e. 0x01, without level information and without dictionary. If a stream being read carries no FDICT, a dictionary passed in stays unused, as in zlib.

How it is checked

CompressSelfTest (103 checks) does not check the format by round trip alone, since the module's own encoder and decoder could be wrong in the same way. Every stream takes both cross paths:

  • Our stream through java.util.zip.Inflater for eight samples (empty, one byte, two bytes, a run of 5000 bytes, 20,000 random bytes, text, periodic, all 256 byte values).
  • The streams of the JDK Deflater at levels 1, 6 and 9 through our Inflate – for the same eight samples; this covers all three block types and the codes produced by the JDK.
  • Edge cases: distance 1 with length 258, lengths 257 to 260, several blocks, stored blocks above 65,535 bytes, a repetition across 35,000 bytes.
  • zlib: header byte 0x78, header check divisible by 31, a falsified Adler-32 is noticed.

Woerterbuchprobe (8 checks) checks the path with a preset dictionary: zlib and raw with dictionary, a dictionary above 32 KiB (its end counts), a stream without FDICT leaves a dictionary unused; as counter-probes a missing and a wrong dictionary, a raw stream without dictionary (back-reference before the start) and the beginning instead of the end of a large dictionary.

Limits

  • The window is 32 KiB; a longer dictionary counts only with its end.
  • Inflate unpacks entirely into memory; there is no streaming mode. The output is capped by the decompression limit.
  • Deflate64 (ZIP method 9) is not read.
  • The Huffman decoder reads bit by bit; for large amounts of data a table with several bits of look-ahead is faster. This has not been measured.
  • zlib streams with a method other than 8 are rejected; the window field in CMF is not evaluated.
