envisionz-framework-compress

Every compression format decoded in-house – without java.util.zip

Function overview for the presentation of the envisionz framework, as of 28 Sep 2026. Deflate and zlib both ways, gzip and ZIP, XZ and LZMA, bzip2, Zstandard, LZ4, Snappy, LZO, Brotli and LZW for reading, plus seven checksums and a limit against decompression bombs. For each method: purpose, API, use in the framework, applications, examples. The examples are shortened. Many API names are German (e.g. entpacke = decompress, packe = compress, Entpackgrenze = decompression limit, Pruefsumme = checksum); they are shown unchanged.

Principles of the module

No java.util.zip. Own code instead of a wrapper around Deflater. java.util.zip serves only in the probes, as a counter-reference; the only thing taken from the JDK is SHA-256 for XZ (java.security).
Cross-check instead of round trip. An own encoder and an own decoder can be wrong in the same way. So the own stream goes through the JDK's Inflater and the JDK's streams through the own Inflate; for the other formats there are foreign anchors from libzstd, libbzip2, lz4 and Python.
Reading is the rule. Only Deflate/zlib and PackBits are compressed. gzip, ZIP, bzip2, XZ, zstd, LZ4, Snappy, LZO, Brotli and LZW are read only – an encoder would be a project of its own each.
Back-references byte by byte. Distance 1 and length 258 means “the same byte 258 times”. System.arraycopy would give the right length with the wrong content; Deflate, LZ4, Snappy and LZO therefore copy byte by byte.
Every checksum is recomputed. ZIP entries against their CRC-32, XZ in all four check types, gzip over every member. A file that decompresses but has the wrong content is caught this way.
Limit against decompression bombs. No header may allocate more memory than the Entpackgrenze allows (default 1 GiB), and the actual output is checked against it as well.

Limit against decompression bombs envisionz.compress

Entpackgrenze – no more than allowed

Four bytes of zstd can yield a 128 KB block, a few hundred kilobytes of gzip a gigabyte of zeros. The limit applies to the output of one call, twice over: to what a header announces and to what is actually produced. Precedence: limit for a section of a thread, then the system property envisionz.entpacken.max, then the user setting, then the default. The setting arrives through a system property so that framework-swing need not know compress. Background, formulas and pseudocode →

Methods

  • grenze(), mit(grenze, arbeit) – limit for one section
  • setzeGrenze(bytes), eingestellteGrenze(), ausEigenschaft()
  • pruefe(groesse, verfahren), wachse(jetzt, gebraucht, verfahren), vorab(angekuendigt, vorab, verfahren)
  • Constants VORGABE (1 GiB), EIGENSCHAFT, EINGESTELLT; exception Grenzueberschreitung

Used in

Deflate and zlib, both ways envisionz.compress.deflate

Deflate, Inflate, Zlib – RFC 1951 and 1950

The encoder: LZ77 with dynamic Huffman, three search levels, lazy matching, and before every block a comparison with the stored block (random data thus grows by less than one per cent). The decoder reads all three block types. Measured on files from the workspace: consistently within a few per cent of the JDK, on a WAV file even below it (4,575,536 against 4,583,829 bytes); 5 MB in 0.7 s at level NORMAL. gzip and ZIP envisionz.compress.gzip · envisionz.compress.zip

Gzip – RFC 1952, all members

Two concatenated gzip files are a valid gzip. A reader that stops after the first member silently returns half – here every member is read. The length at the end is modulo 232, the extra fields come in a fixed order, FHCRC covers only the header. Checked against three anchors from Python's gzip and all sixteen combinations of extra fields. Background, formulas and pseudocode →

Comparison against specification and reference implementation: gzip · ZIP

Methods

  • Gzip.entpacke(gz) – all members in sequence
  • Gzip.glieder(gz) → Glied: name, kommentar, zeit, daten, crc, laenge, systemname()

Used in

fileformats: FITS (GZIP_1, GZIP_2)

What for

.gz files and gzip-compressed image tiles in FITS.

Zipdatei, Zipeintrag – ZIP, read only

The directory sits at the end, and after it may come a comment of up to 65,535 bytes – even one containing the end signature. So the reader searches backwards for the first position where the figures agree with each other. Stored and Deflate entries, Zip64, names as UTF-8 or CP437; every entry is checked against its CRC-32. Encrypted entries and bzip2, LZMA, zstd, XZ and PPMd inside ZIP are named, not read. A probe anchor that Python's zipfile can no longer open is read.

Methods

  • Zipdatei.oeffne(pfad) (AutoCloseable), eintraege(), finde(name)
  • bytes(eintrag), bytes(name), kommentar(), befunde()
  • Zipeintrag: name, methode, gepackt, ungepackt, pruefsumme, verschluesselt, verfahren(), istVerzeichnis()

Used in

fileformats: XLSX, PPTX, Folienplan, NPZfileformats: ZipQuelle, Formaterkennung

What for

Opening Office files, NumPy archives, JARs and plain ZIP containers without a manipulated file showing a different file list.

Example – contents of an XLSX file

try (Zipdatei zip = Zipdatei.oeffne(Path.of("tabelle.xlsx"))) {
    for (Zipeintrag e : zip.eintraege()) System.out.println(e.name() + "  " + e.verfahren());
    byte[] xml = zip.bytes("xl/workbook.xml");
    zip.befunde().forEach(System.out::println);
}

XZ, LZMA, LZMA2 envisionz.compress.lzma

Xz, Lzma, Lzma2 – the range coder and its container

The LZMA core decides every bit through a range decoder with adaptive models, twelve states and four remembered distances. LZMA2 adds chunks on top, XZ the container: multi-byte integers, padding to multiples of four (the padding bytes must be zero), check type none, CRC32, CRC64 or SHA-256. Checked are all four CRC32 of the frame, the sizes in the index and the check value of the data. The Delta and BCJ pre-filters (x86, PowerPC, IA-64, ARM, ARM-Thumb, SPARC, ARM64) are reversed; RISC-V is named, not applied. bzip2 envisionz.compress.bzip2

Bzip2 – four layers on top of each other

From bits to data: Huffman (up to six trees per block) → RLE2 with RUNA/RUNB → move-to-front → Burrows-Wheeler, with RLE1 underneath. RUNA/RUNB is a bijective base-two numeral system; the BWT inversion uses a jump table built in one pass, not sorting. Bits are read from the most significant end (BitLeserMsb), the checksum is the unreflected CRC-32 (Crc32Bzip2). Checked against six anchors from libbzip2, including several blocks and several streams in one file. Background, formulas and pseudocode →

Zstandard envisionz.compress.zstd

Zstd and Zstdwoerterbuch – RFC 8878

Backward-read bit stream, FSE tables, Huffman from weights instead of code lengths, three remembered offsets and state carried across block boundaries – without it no file above 128 KB could be read. Dictionaries in formatted or raw form. Checked against fourteen anchors from libzstd 1.5.7 and, outside the probe, 120 random cases against python-zstandard, all identical byte for byte. Fast codecs of the data formats envisionz.compress.lz4 · .snappy · .lzo

Lz4Block, Lz4, Snappy, SnappyRahmen, Lzo1x

The codecs inside Parquet, Arrow and Avro. LZ4 in two forms: the bare block format and the .lz4 frame format with linked blocks, skippable foreign frames and xxHash32 checksums. Snappy raw and in the framing format with masked CRC-32C. LZO1X reads no bits but command bytes; the follow-up state sits in the low bits of the second-to-last byte. Brotli envisionz.compress.brotli

Brotli, Brotlibaum, Brotliwoerterbuch

Brotli brings 122,784 bytes of text with it and refers to them as if already written; without this dictionary a reader would output nonsense on the first real text. Three independent block partitions (literals, commands, distances), context from the two previous bytes, four remembered distances. The JDK has not a single class for it. LZW for PDF, TIFF and GIF envisionz.compress.lzw

Lzw – one decoder for three formats

Replaces three earlier decoders (PdfFilters.lzw, Giflzw, Tifflzw) and knows their differences as switches: bit order, when the code width grows, initial width, and how strictly a broken stream is treated. The core produces no messages; it reports in the result how the stream ended, and the callers report themselves. The probe checks it against the old wording of all three decoders and the example from PDF 32000-1. Background, formulas and pseudocode →

Methods

Checksums envisionz.compress.pruef

Adler32, Crc32, Crc32c, Crc32Bzip2, Crc64, XxHash32, XxHash64

Seven checksums whose confusion silently gives wrong results: CRC-32C (Castagnoli) is not CRC-32 (IEEE), the bzip2 variant is unreflected, zstd stores the lower 32 bits of an XXH64, LZ4 uses the second byte of an xxHash32 as header checksum. Adler-32 overflows Java's int – found only when comparing with the JDK over 300 kB. Background, formulas and pseudocode →

Methods

  • Crc32.von(daten), incremental new Crc32(), nimm(...), wert(); likewise Adler32, Crc64
  • Crc32c.von(daten[, ab, laenge]), maskiere(c), entmaskiere(m) (Snappy)
  • Crc32Bzip2.von(...), verbinde(bisher, block)
  • XxHash32.von(daten[, ab, laenge, saat]), XxHash64.von(daten[, ab, laenge, saat])

Used in

fileformats: PNG, Avrointernal: gzip, ZIP, XZ, zlib, Snappy, LZ4, zstd, bzip2

What for

Bits, Huffman, run length envisionz.compress.bits · .huffman · .rle

BitLeser, BitLeserMsb, BitSchreiber, HuffmanCode, HuffmanDekoder, Rle

The building blocks underneath. Huffman lengths by package-merge (Larmore/Hirschberg): the optimal code under a length limit – Deflate allows at most 15 bits, the code-length table 7. BitSchreiber.huffman() reverses the codes, because Deflate fills bytes from the bottom while Huffman codes are read from the top. Rle is PackBits, meant as a pre-stage.
