Zstandard – frame, literals and sequences

How a zstd stream (RFC 8878) is built and how Zstd and Zstdblock read it: frame header with window and content size, the three block types, the literals section with one or four Huffman streams, the sequences section with three FSE tables, the three repeat offsets with their exception, the state carried across blocks, checksum and dictionaries. The entropy coding itself is on the page FSE and Huffman.

What it is about

Like Deflate, zstd belongs to the LZ77 family: literals and back-references. The difference is the arrangement. Deflate writes literals and back-references interleaved into one stream with a common code. zstd separates them: every block has a section with all literals one after the other and a section of sequences, each a triple

(literal length,offset,match length)(\text{literal length},\ \text{offset},\ \text{match length})

“take this many literals, then copy this many bytes from this far back”. Literals are text, lengths are numbers; separated, each can be encoded better – literals with Huffman, the three kinds of numbers with one FSE table each.

The frame

A file is a sequence of frames. A frame begins with the magic number 28 B5 2F FD, then the descriptor byte:

Bitsfieldmeaning
7–6size flaglength of the content size: 0 → 0 bytes (1 with single segment), 1 → 2, 2 → 4, 3 → 8
5single segmentno window byte; the window is the content size
3reservedmust be 0
2checksum4 bytes of checksum at the end of the frame
1–0dictionary flaglength of the dictionary ID: 0, 1, 2 or 4 bytes

The window byte ww gives the window size with exponent e=⌊w/8⌋e = \lfloor w/8 \rfloor and mantissa m=wmod⁡8m = w \operatorname{mod} 8:

F=210+e+210+e8⋅mF = 2^{10+e} + \frac{2^{10+e}}{8} \cdot m

The content size is least significant byte first; with two bytes, 256 is added (the values 0 to 255 already fit in one byte). This exception is in the specification, not in the header. After the blocks follow, if announced, the lower 32 bits of an XXH64 over the content (seed 0).

Between frames there may be skippable frames (magic 184D2A50 to 184D2A5F, then a 32-bit length); they are skipped. If only zero bytes follow the last frame, the file has ended.

Blocks

Every block has a 3-byte header (least significant first): bit 0 “last block”, bits 1–2 the type, bits 3–23 the size.

  • Type 0, raw: size bytes unchanged.
  • Type 1, RLE: a single byte, repeated size times.
  • Type 2, compressed: literals and sequences section, together size bytes.
  • Type 3: reserved, error.

The literals section

The first byte carries the literal type in bits 0–1 (0 raw, 1 RLE, 2 Huffman with tree, 3 Huffman without tree – the tree of the previous block) and the size format in bits 2–3. The sizes are spread over the following bytes:

Example from the Zstdblockprobe: 300 raw literals have the header C4 12: 0xC4=110001002\text{0xC4} = 1100\,0100_2, type 0, format 1, size ⌊0xC4/16⌋+16⋅0x12=12+288=300\lfloor \text{0xC4}/16 \rfloor + 16 \cdot \text{0x12} = 12 + 288 = 300.

With four streams, three lengths of 2 bytes each follow the tree description; the fourth follows from the remainder. The output is split into four equal pieces of ⌈n/4⌉\lceil n/4 \rceil literals, only the last may be shorter. Each stream is a backward bit stream of its own with end marker, and after the last literal of each stream it must be exhausted exactly.

The sequences section

The number of sequences takes 1 to 3 bytes: b0=0b_0 = 0 means none (then the literals are the whole block); b0<128b_0 < 128 is the number; b0<255b_0 < 255 means 256(b0−128)+b1256\,(b_0 - 128) + b_1; b0=255b_0 = 255 means b1+256b2+0x7F00b_1 + 256\,b_2 + \text{0x7F00}. Then comes the modes byte: 2 bits each for the LL, OF and ML table (bits 7–6, 5–4, 3–2); the lower two bits must be 0.

Modetablebytes in the stream
0predefined distribution from the specification (LL, ML accuracy 6, OF 5)0
1RLE: a single symbol, accuracy 01
2FSE distribution in the streamits length
3the table of the previous block0

The tables appear in the order LL, OF, ML. Behind them, up to the end of the block, the backward sequence bit stream.

The orders

Three orders are specified and differ – any swap gives well-formed, wrong numbers:

  • Initial states: LL, then OF, then ML.
  • Extra bits per sequence: offset, then match length, then literal length.
  • State update after every sequence except the last: LL, then ML, then OF.

Pseudocode – executing sequences (Zstdblock.entpacke)

ll ← anfang(LL);  of ← anfang(OF);  ml ← anfang(ML)
for i ← 1 to anzahl:
    cl ← symLL(ll);  cm ← symML(ml);  co ← symOF(of)
    ov  ← 2^co + bits(co)                          offset first
    bez ← ML_GRUND[cm] + bits(ML_ZUSATZ[cm])
    lit ← LL_GRUND[cl] + bits(LL_ZUSATZ[cl])
    d ← abstandAusfuehren(gemerkt, ov, lit)
    if litStelle + lit > number of literals: error
    copy lit literals to the end of the output
    if d > n: error "back-reference before the start"
    copy bez bytes from n − d, byte by byte      overlap allowed
    if i < anzahl:  ll ← weiter(ll);  ml ← weiter(ml);  of ← weiter(of)
append the remaining literals

The repeat offsets

zstd keeps the three most recently used offsets (r1,r2,r3)(r_1, r_2, r_3), (1,4,8)(1, 4, 8) at the start of the frame. The rule for OV ≤ 3 has an exception within the exception: if the sequence has no literals, the meaning shifts by one, since a sequence without literals repeating the same offset as its predecessor practically never happens.

OVwith literalswithout literals
1r1r_1, nothing changesr2r_2, r1r_1 and r2r_2 swap
2r2r_2, r1r_1 and r2r_2 swapr3r_3, moves to the front
3r3r_3, moves to the frontr1−1r_1 - 1, moves to the front
≥ 4OV−3\text{OV} - 3, new at the front, the others move down

Worked example following abstandAusfuehren, start (1,4,8)(1, 4, 8):

  1. 2 literals, OV = 5 → offset 2, remembered (2,1,4)(2, 1, 4).
  2. 0 literals, OV = 1 → meant is r2=1r_2 = 1; swap → (1,2,4)(1, 2, 4).
  3. 3 literals, OV = 3 → r3=4r_3 = 4, moves to the front → (4,1,2)(4, 1, 2).
  4. 0 literals, OV = 3 → r1−1=3r_1 - 1 = 3 → (3,4,1)(3, 4, 1).

If r1−1r_1 - 1 gave the value 0, that is an error: 0 is not an offset.

What a block leaves to the next

Within a frame the following carry across block boundaries: the most recently read Huffman tree (for literal type 3), the three most recently used sequence tables (for mode 3) and the three repeat offsets. Zstdblock.Vortrag carries them. As soon as a file exceeds the largest block size of 128 KiB, practically all blocks from the second on refer to them; without this carry-over no such file would be readable. Nothing is carried between frames.

Dictionaries

A zstd dictionary (Zstdwoerterbuch.lies) is either raw content (ID 0, repeat offsets 1, 4, 8) or formatted: magic 37 A4 30 EC, 32-bit dictionary ID, a Huffman description, the FSE distributions for OF, ML and LL, three repeat offsets (4 bytes each, each 1 to content length) and the content. When unpacking, the content stands before the output, back-references may reach into it, and at the end it is cut off; tree, tables and offsets count as those “of the previous block”.

Convention in the framework: If a frame names a dictionary ID, the dictionary passed in must carry exactly that ID; without a dictionary the call aborts with the ID in the message. A frame without ID (--no-dict-id) gets a dictionary passed in; there the caller decides. At most 16 MiB are allocated up front, whatever the content size says.

Pseudocode – Zstd.liesRahmen (abridged)

fhd ← descriptor byte;  check bit 3 = 0

wb ← dictionary ID (0/1/2/4 bytes);  size ← content size (0/1/2/4/8 bytes, +256 for 2)
if single segment: F ← size

    header ← 3 bytes;  last ← bit 0;  type ← bits 1–2;  n ← bits 3–23
    type = raw: append n bytes;  type = RLE: append one byte n times
    type = compressed: Zstdblock.entpacke(n bytes, vortrag);  type = 3: error
until last
content ← aus without the dictionary content

if checksum: compare 4 bytes with (XXH64(content) and 0xFFFFFFFF)

How it is checked

  • Zstdprobe (82 checks): XXH64 against python-xxhash across the loop boundaries (31, 32, 33, 63, 64, 65 bytes) and with seeds; fourteen anchors from libzstd 1.5.7 – Huffman in four streams, single segment with content size and checksum, raw block, predefined tables, two frames, the empty content, a skippable frame, three blocks with offsets across block boundaries, literals without sequence, mixed modes, RLE blocks, RLE tables, all three tables repeated, literals without tree; the back-reference with offset 1 and length 99,998 (100,000 × Q); self-built frames for paths libzstd does not take (RLE literals, skippable frame in the middle); eleven kinds of damage.
  • Zstdblockprobe (41 checks): hand-built blocks: all literal header formats, RLE literals, an overlapping back-reference, the table values LL17 = 18 + 1 bit and ML38 = 51 + 3 bits, the order of the extra bits (with counter-probe), three consecutive blocks with repeat offsets (“without literals, 1 means the second remembered”), seven blocks against a reference model of the RFC rules of its own, all limits of the sequence count (127, 128, 32,511, 32,512), four Huffman streams, literal type 3.
  • Zstdwoerterbuchprobe (18 checks): two dictionaries and six streams from python-zstandard 0.25.0 with libzstd 1.5.7, each compared via SHA-256; raw content, frame without ID, wrong and missing dictionary, broken tables.
  • Outside the probes: 120 random cases (levels 1 to 22, with and without checksum, 0 to 200,000 bytes) against python-zstandard, all identical byte for byte.

Limits

  • Read-only.
  • The window size is read and reported but not enforced as a limit for back-references; the limit is the output so far and the decompression limit.
  • The repeat offsets of a dictionary are read and applied; on real data this is not distinguishable, because libzstd writes the default 1, 4, 8.
  • The output lies completely in memory; no streaming mode.
