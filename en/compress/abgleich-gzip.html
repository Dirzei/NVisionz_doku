gzip — comparison against RFC 1952 and Python's gzip

As of: 2026-09-07
Our implementation: envisionz.compress.gzip.Gzip — read-only, no third-party library
Specification: RFC 1952, public, unchanged since 1996
Compared against: Pythons gzip über zlib 1.3
Test bench: envisionz.compress.Gzipprobe — 46 checks, three foreign anchors

The reference implementation. Python's gzip module builds on zlib, i.e. the very implementation that spread the format.

Why this one. Because gzip's wrapper is so small that a mistake in it only shows on a real file — and because nearly every gzip file in the world comes from zlib.

The Note column points into section 5 of this document — not into the workspace item list. The word in front says what kind of thing it is: gap is something we lack and that is open; decided is something we deliberately do not do; property is a trait of the format affecting both implementations; open there is a gap of the reference product. Only the gaps are work — they are collected in section 5.1 and appear as one item in OFFENE-PUNKTE.md.

Almost nothing, and that is exactly the trap. The payload is a raw DEFLATE stream; around it sit ten header bytes, a few optional fields and eight trailing bytes. Reading the header correctly and skipping the rest gets you through nine files out of ten — and on the tenth you notice nothing.

The most dangerous case is the multi-member container: several complete gzip streams one after another in one file. A reader that stops after the first trailer delivers half the data without a single error message.

The items

Deliberate decisions

GZ3 (decided) — No writing

This module reads. A gzip writer would be ten lines on top of the DEFLATE writer, but nobody here needs one: only test fixtures are written, and the raw stream suffices for that.

Findings against the reference implementation

GZ1 (open there) — The JDK reads only the first member

java.util.zip.GZIPInputStream does not reliably read a multi-member container to the end — it depends on how the calling code drives the stream. That is not a JDK defect but a property of its interface; whoever does not know it gets half the data and no message. Our reader reads all members and reports their count.

GZ2 (open there) — The JDK does not hand out the optional fields

File name, comment and extra fields are read by the JDK and discarded: its interface offers no way to ask for them. For a tool meant to explain a foreign file, that is the most interesting part of the header.
