LZ4, Snappy and LZO1X – fast codecs without entropy coding

Three methods built for speed: back-references and literals sit in the stream as whole bytes, without Huffman and without probabilities. Layout of the commands, frame formats with xxHash32 and masked CRC-32C, the state of LZO, pseudocode following Lz4Block, Lz4, Snappy, SnappyRahmen and Lzo1x, worked examples and probes.

What it is about

Deflate, zstd and LZMA gain a large part of their compression from entropy coding: frequent symbols get short codes. That costs work per bit when reading. LZ4, Snappy and LZO do without it. A command consists of whole bytes: a tag byte whose bits carry type, length and part of the offset, then possibly further length or offset bytes, then the literals. Unpacking is essentially a sequence of copy operations. These methods sit inside Parquet, Arrow, Avro, ORC, LevelDB and Hadoop data.

All three have one thing in common: the back-reference may overlap itself. If the offset dd is smaller than the length ll, the copy reads bytes it has just written itself; the result is a pattern of period dd:

yn+k=yn+k−d,k=0,1,…,l−1y_{n+k} = y_{n+k-d}, \qquad k = 0, 1, \dots, l - 1

That is why all three classes copy byte by byte. System.arraycopy would treat source and destination as separate and deliver the right length with the wrong content.

LZ4

The block format

An LZ4 block is a sequence of sequences. Each begins with a token: the upper four bits are the number of literals, the lower four the length of the back-reference minus 4. If a field is 15, extra bytes follow and are added until one is smaller than 255:

length=15+∑ibi,b1=…=bk−1=255,bk<255\text{length} = 15 + \sum_{i} b_i, \qquad b_1 = \dots = b_{k-1} = 255,\ b_k < 255

After the token (and its literal extra bytes) come the literals, then the offset as 2 bytes (least significant first, 1 to 65,535), then the extra bytes of the match length. The last sequence of a block has no back-reference: it ends after its literals.

Worked example. 6000 bytes abcabc… can be written as a single sequence: three literals, then offset 3, length 5997. The match length is 5997−4=5993=15+23⋅255+1135997 - 4 = 5993 = 15 + 23 \cdot 255 + 113:

3F | 61 62 63 | 03 00 | FF × 23 | 71

That is 30 bytes; Lz4Block.entpacke(block, 6000) returns the 6000 bytes from it (recomputed). The foreign anchor f4 from lz4 1.9.4 packs the same content as a frame into 63 bytes.

Pseudocode – Lz4Block.entpacke(quelle, ab, laenge, ziel, zielAb, hoechstens)

p ← ab;  n ← zielAb;  grenze ← zielAb + hoechstens
while p < ende:
    t ← quelle[p++]
    lit ← t >>> 4
    if lit = 15: repeat b ← quelle[p++]; lit ← lit + b while b = 255
    if p + lit > ende or n + lit > grenze: error
    copy lit literals;  p ← p + lit;  n ← n + lit
    if p ≥ ende: break                           last sequence: no back-reference
    d ← 2 bytes, least significant first
    if d = 0 or d > n: error
    ℓ ← (t and 15) + 4
    if (t and 15) = 15: repeat b ← quelle[p++]; ℓ ← ℓ + b while b = 255
    if n + ℓ > grenze: error
    for i ← 1 to ℓ: ziel[n] ← ziel[n − d];  n ← n + 1      byte by byte
return n − zielAb

Source: envisionz-framework-compress/src/envisionz/compress/lz4/Lz4Block.java. The offset is checked against the write position in the whole buffer, not against the start of the block: with linked blocks a back-reference may point into the previous block.

Convention in the framework: The rules that the last five bytes of a block are literals and that the last back-reference ends at least twelve bytes before the end only bind a writer; the reader does not rely on them. The length fields are unbounded; the computation is therefore done against the known target size, and entpacke(block, groesse) rejects a target size above 255⋅block length+64255 \cdot \text{block length} + 64.

If the blocks are linked (bit 5 = 0, the default of lz4), a back-reference may reach into previous blocks; Lz4 therefore unpacks all blocks into one continuous buffer. A file may consist of several frames, and skippable foreign frames (184D2A50 to 184D2A5F) are skipped. A preset dictionary (at most its last 64 KiB) stands before the output; with independent blocks before each block.

Snappy

A raw Snappy stream begins with the uncompressed length as a varint (7 bits per byte, least significant group first – the other way round from SQLite). Then elements follow; the lower two bits of the tag byte tt say which:

Bitskindlengthoffsetbytes
00literal⌊t/4⌋+1\lfloor t/4 \rfloor + 1; for 60…63 the length − 1 is in ⌊t/4⌋−59\lfloor t/4 \rfloor - 59 following bytes–1 + (0…4) + length
01copy4+(⌊t/4⌋mod⁡8)4 + (\lfloor t/4 \rfloor \operatorname{mod} 8), i.e. 4…11256⌊t/32⌋+b1256 \lfloor t/32 \rfloor + b_1, 11 bits2
10copy⌊t/4⌋+1\lfloor t/4 \rfloor + 1, 1…642 bytes3

Worked example. The stream 0C 08 61 62 63 15 03 (recomputed with Snappy.entpacke): varint 0C = 12 bytes target. 08 = literal, length 2+1=32 + 1 = 3: abc. 15 = 0001010120001\,0101_2: kind 01, length 4+5=94 + 5 = 9, offset 256⋅0+3=3256 \cdot 0 + 3 = 3. Result abcabcabcabc.

Pseudocode – Snappy.entpacke

ziel ← varint;  if ziel > 32·input + 64: error;  check against the decompression limit
while p < ende:
    t ← daten[p];  art ← t and 3
    if art = 0:
        len ← t >>> 2;  p ← p + 1
        if len ≥ 60: len ← (len − 59) bytes, least significant first
        len ← len + 1;  copy len literals
    otherwise:
        kind 1: len ← 4 + ((t >>> 2) and 7);  d ← ((t >>> 5) << 8) + daten[p+1];  p ← p + 2
        kind 2: len ← (t >>> 2) + 1;  d ← 2 bytes;  p ← p + 3
        kind 3: len ← (t >>> 2) + 1;  d ← 4 bytes;  p ← p + 5
        if d ≤ 0 or d > n: error
        copy len bytes from n − d, byte by byte
if n ≠ ziel: error

Source: envisionz-framework-compress/src/envisionz/compress/snappy/Snappy.java.

The framing format

The framing format splits a stream into chunks with 1 byte type and 3 bytes length. The first is the stream identifier (type 0xFF, content sNaPpY). Type 0x00 is a compressed chunk, 0x01 an uncompressed one, each preceded by 4 bytes of masked CRC-32C of the uncompressed data; 0x02 to 0x7F are reserved and must not be skipped; 0x80 to 0xFE are skipped and reported as a finding. The masking is

m=(rotr15⁡(c)+0xA282EAD8)mod⁡232m = \Big(\operatorname{rotr}_{15}(c) + \text{0xA282EAD8}\Big) \operatorname{mod} 2^{32}

with the rotation by 15 bits to the right. It prevents a CRC over data containing its own CRC from falling onto a fixed value. Details on CRC-32C are on the checksums page.

LZO1X

LZO1X reads no bits but command bytes. Which command is meant follows from the value tt of the byte and from what came before.

Here a,ba, b are the following bytes. In M4, bit 3 of tt is the top offset bit (contribution 16,384); M4 with a zero offset part is the end marker 11 00 00. A long length field counts zero bytes of 255 each and then adds the base value (15, 31 or 7) and the first non-zero byte.

The real trick is the state: after every back-reference the lower two bits of the second-to-last byte read say how many literals (0 to 3) follow without a command of their own. If the very first byte is greater than 17, it is itself a literal run of t−17t - 17 bytes.

Worked examples (recomputed with Lzo1x.entpacke): 15 61 62 63 64 11 00 00 gives abcd – first byte 21−17=421 - 17 = 4 literals, then the end marker. 15 61 62 63 64 6C 00 11 00 00 gives abcdabcd: 0x6C=108\text{0x6C} = 108 is M2 with length ⌊108/32⌋+1=4\lfloor 108/32 \rfloor + 1 = 4 and offset 1+(27mod⁡8)+0=41 + (27 \operatorname{mod} 8) + 0 = 4; the lower two bits of 6C are 0, so no trailing literals.

Source: envisionz-framework-compress/src/envisionz/compress/lzo/Lzo1x.java. A long length field above 2242^{24} is rejected as damaged. If an expected size is given, the output must end up exactly that long, otherwise an error (“erwartet waren …”).

Convention in the framework: LZO has no checksum. The Lzoprobe records this as a finding: a flipped byte does not change the length, but it does change the content, and nobody notices. The expected size allocates the output buffer up front (at most 16 MiB) and since 2026-09-28 is compared at the end – it is the only thing by which a caller recognises a wrong block, if the length changes along with it.

How it is checked

  • Lz4probe (67 checks): xxHash32 against python-xxhash (empty, 1, 3, 4, 16, 31, 32, 100, 1000 bytes, seeds 0 and 1, slices); a bare block; five frame anchors from lz4 1.9.4 (independent blocks, with size and content checksum, with block checksums, f4 with offset 3 and length 5997, f5 three linked blocks over 139,122 bytes); two frames in a row; uncompressed blocks from a writer of its own; skippable foreign frames; twelve kinds of damage; an uncompressed block exactly at the block limit (64 KiB) is read, one above it rejected. The probe proved two of its author's own assumptions wrong: f1 had independent instead of linked blocks, and no anchor contained an uncompressed block.
  • Lz4woerterbuchprobe (9 checks): dictionary with linked and independent blocks, with and without ID, long dictionary, counter-probes.
  • SnappySelfTest (40 checks): CRC-32C (“123456789” = E3069283, tabled against bitwise over 200 random blocks, in pieces), masking there and back; literals of 60, 61, 300 and 70,000 bytes (zero to three length bytes); all copy kinds; overlapping copies with offset 1, 2, 3; broken streams; the framing format with repeated stream identifier, skippable and reserved chunks, wrong checksum.
  • Lzoprobe (25 checks): twelve anchors from liblzo2 via python-lzo – a pure literal run, dense short back-references, long ones with large offset, overlapping throughout, random data (compressed larger than raw), long length fields, a single byte, all four command kinds, 30,000 equal bytes, the short back-reference directly after a literal run, more than 20,000 and more than 40,000 bytes back (top offset bit); plus three error cases, an expected size too large and one too small (both reported) and the finding about the missing checksum.

Limits

  • All three are read-only.
  • The Snappy bound 32⋅n+6432 \cdot n + 64 has headroom above the true maximum ratio (kind 10: 3 bytes → 64 bytes, about 21.3). Since 2026-09-28 the source comment says so (before, it read “a copy command of two bytes yields up to 64”; a two-byte command of kind 01 yields at most 11).
  • LZ4: with independent blocks without dictionary, a back-reference into the previous block is not prevented. (Since 2026-09-28, uncompressed blocks are checked against the block limit from the header like compressed ones.)
  • LZO: without a given expected size (0) the length remains unchecked.
