LZW for PDF, TIFF and GIF – background

The method of Lempel, Ziv and Welch: a dictionary that writer and reader build up in the same way while working, codes of growing width, the special case of the code that refers to itself, and the three differences between PDF, TIFF and GIF that appear as switches in Lzw.Einstellung. With the worked example from PDF 32000-1 and pseudocode following Lzw.

What it is about

LZW (Welch, 1984, after Ziv and Lempel 1978) does not write back-references with length and distance but numbers of dictionary entries. The dictionary starts with all single characters. Every time the writer outputs an entry, it creates a new one: the output entry plus the next character. The entries thus grow with the repetitions in the text. The reader does not need to be sent the dictionary – it builds it from the codes read in exactly the same way, just one step later.

Today LZW is mainly still read in three formats: in the PDF filter LZWDecode, in TIFF (compression 5) and in GIF. All three use the same method with codes at most 12 bits wide, but differ in details that make a stream of one format unreadable for the reader of another.

The method

With bb bits per character (PDF and TIFF: 8, GIF: 2 to 8, from the file) the codes are:

Codemeaning
0…2b−10 \dots 2^b - 1the character itself
2b2^bclear code: reset the dictionary, width back to b+1b+1
2b+12^b + 1end code
2b+2…40952^b + 2 \dots 4095created entries

An entry is stored as a pair (predecessor, last character); its string arises by walking the predecessor chain down to a single character – backwards, hence via a stack. After every code read (except the first after a clear code) the reader creates an entry:

Enew=E(old)+first character of E(code)E_{\text{new}} = E(\text{old}) + \text{first character of } E(\text{code})

The self-reference. The writer can output a code it has only just created and which the reader does not yet know – when the pattern xSxSxxSxSx occurs in the text. The missing entry is then E(old)+first character of E(old)E(\text{old}) + \text{first character of } E(\text{old}), since the first character of the new entry is the first character of E(old)E(\text{old}).

The code width

The codes start with b+1b + 1 bits and become wider when the entries no longer fit. Exactly when is the most important difference between the formats. With the next free entry nn and the switch ff (frueh), the width ww grows after an entry has been created as soon as

n+f≥2wandw<12n + f \ge 2^{w} \quad \text{and} \quad w < 12

PDF (with the default EarlyChange = 1) and TIFF grow one position earlier (f=1f = 1): after creating entry 510, n=511n = 511, and code 511 is already read with 10 bits. GIF, with f=0f = 0, grows only at n=512n = 512. If a TIFF reader reads a GIF stream, it slips by one bit at the first width change, and the rest is nonsense.

The core produces no messages. It states in its result how the stream ended – ENDCODE, DATENENDE (the bits did not suffice for another code) or UNGUELTIG (with the code and the next free entry) – and the callers report in their own language.

Pseudocode – Lzw.entpacke(d, ab, laenge, e)

clear ← 2^b;  end ← clear + 1;  n ← end + 1;  w ← b + 1;  old ← −1
for i ← 0 to clear−1:  predecessor[i] ← −1;  last[i] ← i
repeat:
    fill the reservoir with whole bytes until it holds w bits (LSB or MSB order)
    if not enough bits: how ← DATENENDE;  break
    code ← next w bits
    if code = clear:  n ← end + 1;  w ← b + 1;  old ← −1;  continue
    if code = end:  how ← ENDCODE;  break
    if code < n:                                   entry ← code
    else if old ≥ 0 and (not strict or code = n): entry ← SELF-REFERENCE
    else if skipInvalid:                           continue
    otherwise:  how ← UNGUELTIG;  break
    base ← (entry = SELF-REFERENCE) ? old : entry
    stack ← characters of the chain from base (last first);  first ← bottom character
    if SELF-REFERENCE: append first at the end
    output the stack in the right order (with hoechstens: cap, keep counting)
    if old ≥ 0 and n < 4096:
        predecessor[n] ← old;  last[n] ← first;  n ← n + 1
        if n + frueh ≥ 2^w and w < 12:  w ← w + 1
    old ← (entry = SELF-REFERENCE) ? n − 1 : entry

Source: envisionz-framework-compress/src/envisionz/compress/lzw/Lzw.java. The reservoir is a long; for GIF bytes are added at the top and codes taken from the bottom, for PDF and TIFF the other way round.

Convention in the framework: Without streng, every code from nn upwards counts as a self-reference as long as there is a previous code – that is what the replaced PDF and TIFF decoders did, and the probe demands that nothing changes about it. ungueltigUeberspringen therefore only takes effect when there is no previous code yet (at the start or after a clear code). With streng (GIF) only exactly nn is a valid self-reference. When the dictionary is full with 4096 entries, nothing more is created, and the width stays 12 until a clear code comes.

How it is checked

Lzwprobe (40 checks) sets the core against the old wording of all three replaced decoders (PdfFilters.lzw, Giflzw, Tifflzw), whose source is contained in the probe:

  • the example from PDF 32000-1 as a foreign anchor;
  • six valid inputs from a probe encoder that tracks the decoder's state, across all width changes from 9 to 12 bits, with a full dictionary and clear code – each in six settings (PDF with frueh 0 and 1, TIFF, GIF with 2, 5 and 8 bits): the core returns the input, and so does the old version;
  • 1600 broken streams of random bytes (800 PDF, 400 TIFF, 400 GIF, 362 of them invalid): the core equals the old version everywhere, including the error marker.

Seven counter-experiments turned red: early width fixed to 1, bit order fixed to MSB, self-reference not strict, invalid codes not skipped, the appended character of a self-reference at the front instead of the back, capping off, initial width fixed to eight.

Limits

  • Unpacking only; there is no LZW encoder in the module (the probe encoder only serves the probe).
  • Codes at most 12 bits wide (4096 entries), as in all three formats.
  • A given maximum length (hoechstens, often from a TIFF or PDF header) is checked against the decompression limit; without it the output grows along.
  • The core does not check the output for plausibility; a wrongly chosen setting gives a valid but meaningless stream or an early UNGUELTIG.
