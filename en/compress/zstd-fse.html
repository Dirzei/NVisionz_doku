Zstandard – FSE, Huffman from weights and the backward bit stream

The entropy coding of zstd (RFC 8878): how a state machine in the manner of tANS reads symbols with a fractional bit count, how the state table arises from a normalised distribution and how that distribution sits in the stream, why the bit stream runs backwards, and how Huffman codes are built from weights. With pseudocode following Zstdbits, Zstdfse and Zstdhuff. Frame, literals and sequences are on a page of their own.

What it is about

Huffman gives every symbol a whole number of bits. A symbol with probability 0.7 actually carries −log2⁡0.7≈0.51-\log_2 0.7 \approx 0.51 bits of information but costs at least a whole one. A range coder as in LZMA avoids this but computes with multiplications per bit. FSE (Finite State Entropy, a form of tabled asymmetric numeral systems, tANS) reaches the fractional bit count with a table: per symbol one lookup, one addition and a few bits read.

The idea behind tANS

The encoder keeps a state xx from a fixed range of N=2AN = 2^A values (AA = accuracy). Every state is assigned to exactly one symbol; a symbol ss with normalised count nsn_s owns nsn_s states, with ∑sns=N\sum_s n_s = N. Its probability is therefore ns/Nn_s / N.

In state xx the reader sees the symbol s(x)s(x) and reaches the next state by reading b(x)b(x) bits and adding them to a baseline g(x)g(x):

x'=g(x)+read(b(x))x' = g(x) + \text{read}\big(b(x)\big)

The nsn_s states of a symbol share the whole state space [0,N)[0, N) among themselves without gaps: the kk-th of them (counted k=ns,…,2ns−1k = n_s, \dots, 2n_s - 1) covers a range of width 2b2^{b} with

b=A−⌊log2⁡k⌋,g=k⋅2b−Nb = A - \lfloor \log_2 k \rfloor, \qquad g = k \cdot 2^{b} - N

A symbol with ns=N/2n_s = N/2 thus always reads exactly 1 bit, one with ns=1n_s = 1 always AA bits. If nsn_s lies between two powers of two, some of its states read ⌊A−log2⁡ns⌋\lfloor A - \log_2 n_s \rfloor bits and some one bit more – on average ≈−log2⁡(ns/N)\approx -\log_2(n_s/N) results.

The encoder works exactly the other way round: for every symbol and following state it knows the preceding state and writes the bits the reader will read. Because the state depends on the next symbol, it encodes the symbols from back to front – and writes the bit stream backwards so that the reader can decode forwards.

The state table from a distribution

Which state belongs to which symbol is specified exactly by RFC 8878, so that writer and reader build the same table:

  1. Symbols with count −1-1 (“occurs, but less often than 1/N1/N”) get one state each from the end: N−1,N−2,…N-1, N-2, \dots. They count as count 1 and always read AA bits.
  2. The other symbols are distributed in order, each nsn_s times, around the circle with step σ=N/2+N/8+3\sigma = N/2 + N/8 + 3, skipping the end places already taken. σ\sigma is odd and hence coprime to NN, so it hits every place exactly once.
  3. Then the states of each symbol are numbered in ascending order, k=ns,ns+1,…k = n_s, n_s + 1, \dots, and bb and gg are computed with the formula above.

Pseudocode – Zstdfse.ausVerteilung(verteilung, hoechstes, A)

N ← 2^A
if Σ (v = −1 ? 1 : v) ≠ N: error "distribution does not add up"
hoch ← N − 1
for s ← 0 to hoechstes:
    if v[s] = −1: symbol[hoch--] ← s;  naechster[s] ← 1
    otherwise:    naechster[s] ← v[s]
σ ← N/2 + N/8 + 3;  stelle ← 0
for s ← 0 to hoechstes:
    repeat v[s] times:
        symbol[stelle] ← s
        stelle ← (stelle + σ) mod N
        while stelle > hoch:  stelle ← (stelle + σ) mod N      skip end places
if stelle ≠ 0: error
for i ← 0 to N−1:
    s ← symbol[i];  k ← naechster[s]++
    bits[i] ← A − ⌊log2 k⌋;  grund[i] ← k · 2^bits[i] − N

Worked example

Accuracy A=5A = 5, N=32N = 32, distribution for symbols 0 to 3: (−1,6,16,9)(-1, 6, 16, 9), sum 1+6+16+9=321 + 6 + 16 + 9 = 32. The step is σ=16+4+3=23\sigma = 16 + 4 + 3 = 23. The table, computed with Zstdfse.ausVerteilung via reflection, arranged by symbol:

Each row covers the following states 0 to 31 exactly once. Symbol 2 (probability 1/21/2) always costs 1 bit; symbol 3 (9/329/32, information −log2⁡(9/32)≈1.83-\log_2(9/32) \approx 1.83 bits) costs 1 bit in two states and 2 bits in seven states; symbol 0 costs 5 bits.

How the distribution sits in the stream

A distribution is read forwards, bits from the least significant end of each byte – unlike the bit stream that follows it. The first 4 bits are A−5A - 5. Then come the counts with a shrinking bit width: the less of the state space remains to be assigned, the fewer bits the next number needs. Within one width there is additionally a special range of small values that make do with one bit less. The count is stored plus one (so −1-1 becomes 0). After a count of 0 a repeat count follows in two-bit groups for further zeros; the value 3 means “three more, and it continues”.

A ← bits(4) + 5;  N ← 2^A
rest ← N + 1;  schwelle ← N;  breite ← A + 1;  s ← 0
while rest > 1 and s ≤ highestSymbol:
    if previous count was 0:
        weitere ← 0
        while peek(2) = 3:  weitere ← weitere + 3;  take(2)
        weitere ← weitere + bits(2);  set that many symbols to 0;  continue
    grenze ← 2·schwelle − 1 − rest
    w ← peek(breite);  klein ← w mod schwelle
    if klein < grenze:  zahl ← klein;  take(breite − 1)          special range
    otherwise:  zahl ← w mod (2·schwelle);  if zahl ≥ schwelle: zahl ← zahl − grenze
                take(breite)
    zahl ← zahl − 1                                                −1 is allowed
    rest ← rest − |zahl|;  v[s++] ← zahl
    while rest < schwelle:  breite ← breite − 1;  schwelle ← schwelle / 2
if rest ≠ 1: error "does not add up to N"
table ← ausVerteilung(v, s − 1, A);  consumed ← bytes rounded up

Source: envisionz-framework-compress/src/envisionz/compress/zstd/Zstdfse.java (liesVerteilung, inner class Vorwaerts). Missing bits behind the section count as 0 when peeking; whoever wants to consume more than four bytes beyond it is rejected.

The backward bit stream

Within a byte the bits run from the least significant end, but the stream as a whole runs from the last byte to the first. The last byte therefore holds no data bit at the top but a marker: the highest set bit says where the payload bits end; it and the zeros above it are padding. With λ\lambda leading zeros in the last byte, a stream of mm bytes has

8m−(λ+1)8m - (\lambda + 1)

payload bits. Example from the Zstdbausteinprobe: the single byte 0x05 = 0000 0101 has the marker at bit 2 and below it two payload bits with value 01. A last byte of 0 is an error.

start(daten, ab, m):
    if m ≤ 0 or daten[ab+m−1] = 0: error
    stelle ← 8m − (leading zeros of the last byte + 1)
function bits(n):   top bit first
    if stelle − n < 0: error "bit stream exhausted"
    repeat n times: stelle ← stelle − 1;  w ← 2w + bit (stelle mod 8) of byte (stelle div 8)
function schau(n):  like bits, but without consuming; bits below position 0 count as 0
function bitsMitNullen(n): w ← schau(n); stelle ← stelle − n   may become negative

Source: envisionz-framework-compress/src/envisionz/compress/zstd/Zstdbits.java.

Convention in the framework: In the sequence stream reading is strict – an access below position 0 is an error. For the FSE-coded Huffman weights and when reading Huffman codes with the largest code length at once, missing bits count as 0 instead: the encoder made sure that the padded zeros give the same result. For the literals the check comes afterwards, and more strictly: after the last symbol of a stream exactly zero bits must be left.

Huffman from weights

For the literals zstd does not transmit code lengths but weights wsw_s. A weight w>0w > 0 occupies 2w−12^{w-1} shares of the code space, w=0w = 0 means “does not occur”. From the sum of the transmitted weights follow the largest code length and the last weight, which is not in the stream:

S=∑s2ws−1,Lmax⁡=⌊log2⁡S⌋+1,2wlast−1=2Lmax⁡−SS = \sum_{s} 2^{w_s - 1}, \qquad L_{\max} = \lfloor \log_2 S \rfloor + 1, \qquad 2^{w_{\text{last}} - 1} = 2^{L_{\max}} - S

The remainder 2Lmax⁡−S2^{L_{\max}} - S must be a power of two. The code length of a symbol is then ls=Lmax⁡+1−wsl_s = L_{\max} + 1 - w_s.

Worked example (the example from RFC 8878, recomputed with Zstdhuff.ausGewichten): the weights (4,3,2,0,1)(4, 3, 2, 0, 1) of symbols 0 to 4 give S=8+4+2+0+1=15S = 8 + 4 + 2 + 0 + 1 = 15, Lmax⁡=4L_{\max} = 4, remainder 16−15=116 - 15 = 1, hence w5=1w_5 = 1. The code lengths are 1, 2, 3, –, 4, 4.

The canonical assignment runs the other way round compared with Deflate: zstd assigns the longest codes first, i.e. to the symbols with the smallest weight, within one weight by symbol number. With the Deflate order a complete table would arise that delivers different symbols.

Reading uses a table of 2Lmax⁡2^{L_{\max}} entries: peek at Lmax⁡L_{\max} bits, look up symbol and true code length, and consume only that many bits.

Pseudocode – Zstdhuff.ausGewichten and symbol

S ← Σ 2^(w−1) over w > 0;  if S = 0: error
L ← bit length(S);  voll ← 2^L;  rest ← voll − S
if rest is not a power of two: error
w[last] ← bit length(rest)
for ℓ ← L down to 1:                           longest codes first
    anfang[ℓ] ← stelle;  stelle ← stelle + (number of symbols with length ℓ) · 2^(L−ℓ)
for each symbol s with w[s] > 0:
    ℓ ← L + 1 − w[s]
    fill 2^(L−ℓ) entries from anfang[ℓ] with (s, ℓ);  anfang[ℓ] += 2^(L−ℓ)

function symbol(stream):  v ← stream.schau(L);  stream.nimm(length[v]);  return sym[v]

Source: envisionz-framework-compress/src/envisionz/compress/zstd/Zstdhuff.java.

How the weights sit in the stream

  • Header byte h≥128h \ge 128: h−127h - 127 weights follow directly, 4 bits each, the first in the upper nibble.
  • Header byte h<128h < 128: the next hh bytes are FSE-coded, with a distribution of accuracy at most 6. Reading uses two alternating states. The end is stored nowhere as a number: it is reached when an update reaches beyond the start of the stream; the symbol still pending in the other state belongs to it.
za ← anfang();  zb ← anfang();  n ← 0
repeat:
    w[n++] ← sym(za);  za ← weiterNachsichtig(za)
    if remaining < 0:  w[n++] ← sym(zb);  break
    w[n++] ← sym(zb);  zb ← weiterNachsichtig(zb)
    if remaining < 0:  w[n++] ← sym(za);  break

Source: envisionz-framework-compress/src/envisionz/compress/zstd/Zstdblock.java (liesBaum).

How it is checked

  • Zstdbausteinprobe (52 checks): the end marker of the backward stream on single bytes, 400 fields of 0 to 32 bits embedded backwards; the three predefined distributions (LL, ML, OF) add up correctly, have the −1-1 symbols at the top and agree with a construction following the wording of RFC 8878 4.1.1; ANS properties over 40 computed distributions of accuracy 5 to 9; distribution headers produced by a writer of its own and read back (60 distributions, zero runs of lengths 1, 3, 4, 7, 18); 500 symbols against an FSE encoder of its own; the Huffman example of the RFC with eleven symbols; 60 computed Huffman trees of 200 symbols each; error cases (wrong sum, all weights zero, remainder not a power of two).
  • Three errors found by the format probe during construction, kept as counter-probes: a predefined ML distribution with the −1-1 symbols in the wrong place (the sum was right, state 57 delivered 32 instead of 52), the reversed canonical order, and a weight stream read too strictly.

FSE-coded weights and FSE-compressed sequence tables cannot be checked individually on hand-built blocks; they are covered by the Zstdprobe via the anchors from libzstd (see frame and sequences).

Limits

  • Read-only: there is no FSE normalisation, no weight search and no encoder in the main code.
  • The tables are rebuilt per block (up to 292^9 states); faster readers with several symbols per lookup do not exist.
  • Accuracies: LL and ML at most 9, OF at most 8, Huffman weights at most 6 – larger values are rejected.
