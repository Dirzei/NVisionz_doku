Building blocks – bit readers, length-limited Huffman codes, run length

The parts underneath the formats: how bits are read and written from the least or the most significant end, why Huffman codes are reversed when written, how package-merge finds the optimal code under a length limit, how canonical codes arise and are read bit by bit, and PackBits as run-length coding. With pseudocode following BitLeser, BitSchreiber, BitLeserMsb, HuffmanCode, HuffmanDekoder and Rle.

Bit orders

A bit stream is a sequence of bits stored in bytes. Open questions are in which order the bits of a byte are filled, and in which order the bits of a multi-bit number appear in the stream. The formats in the module use three combinations:

Readerfirst bit of a bytemulti-bit numberformats
BitLeserbit 0 (least significant)least significant bit firstDeflate, Brotli
BitLeserMsbbit 7 (most significant)most significant bit firstbzip2
Zstdbitsbackwards from the end of the streammost significant bit firstzstd (see FSE)

Worked example LSB. BitSchreiber writes in turn 5 in 3 bits, 0 in 1 bit, ABCD in 16 bits and 1 in 1 bit. The result is the bytes D5 BC 1A: byte 0 = 1101010121101\,0\,101_2 (the 5 at the bottom, above it the 0, at the top the lower four bits of ABCD), byte 1 = BC, byte 2 = 0001101020001\,1010_2 (the upper four bits A and above them the 1).

Worked example MSB. BitLeserMsb over A5 0F reads, with bits(4), bits(8), bits(4), the values 10, 80 (= 0x50) and 15 – bits run across the byte boundary from top to bottom.

Huffman codes in an LSB stream

A Huffman code is a sequence of decisions in the tree, read from the first bit on; written canonically, the first bit is the most significant one of the code value. An LSB stream, however, puts the bit written first at the bottom. So that the reader gets the bits in tree order, BitSchreiber.huffman(code, l) writes the ll bits one at a time, most significant first. Example: the codes 110, 0, 1110 give the single byte 73 = 0111001120111\,0011_2: read from the bottom 1, 1, 0 | 0 | 1, 1, 1, 0.

Pseudocode – BitLeser.bits(n) and BitSchreiber.bits(w, n)

function read(n):                            0 ≤ n ≤ 32
    while haldeBits < n:
        if pos ≥ ende: error (names the position)
        halde ← halde or (daten[pos++] << haldeBits);  haldeBits += 8
    w ← halde and (2^n − 1);  halde ← halde >>> n;  haldeBits −= n
    return w

function write(w, n):
    halde ← halde or ((w and (2^n − 1)) << haldeBits);  haldeBits += n
    while haldeBits ≥ 8:  output the lowest byte;  halde ← halde >>> 8;  haldeBits −= 8

function huffman(code, l):  for i ← l−1 down to 0:  write((code >>> i) and 1, 1)

Source: envisionz-framework-compress/src/envisionz/compress/bits/BitLeser.java, BitSchreiber.java. aufBytegrenze() discards the partial bits when reading and pads with zeros when writing; bytes(...) writes whole bytes only at a byte boundary.

Convention in the framework: Reading past the end throws an exception naming the position instead of delivering zero bits – otherwise a truncated stream would turn into a decoding error at a completely different place. (Intentional exceptions: the LZMA range reader and the zstd streams, where the format provides for reading past the end.) BitLeser loads only as many bytes as it needs and afterwards always keeps fewer than eight bits in its reservoir. BitLeserMsb keeps the position in bits and checks before a multi-bit access whether enough is there; a failed access consumes nothing.

Huffman codes and their length limit

For symbols with frequencies hih_i one looks for code lengths lil_i that satisfy the Kraft inequality ∑2−li≤1\sum 2^{-l_i} \le 1 and minimise the total length ∑hili\sum h_i l_i. Huffman's method (repeatedly merging the two rarest nodes) delivers the optimum. The mean length lies between the entropy and one bit above it:

H≤l<H+1,H=−∑ipilog2⁡pi,pi=hi∑jhjH \le \bar{l} < H + 1, \qquad H = -\sum_i p_i \log_2 p_i, \quad p_i = \frac{h_i}{\sum_j h_j}

Huffman's tree, however, knows no length limit. With very uneven frequencies it becomes deep: Fibonacci frequencies give a tree in which every symbol lies one level deeper than the next more frequent one. Deflate allows at most 15 bits, the code-length table at most 7. A code above the limit is not “a bit too long” but unreadable for any foreign reader.

Package-merge

Package-merge (Larmore and Hirschberg, 1990) finds the optimal code under a length limit LL. It rests on a coin collector's problem: every symbol is available on each of the levels 1…L1 \dots L as a “coin” with weight hih_i and face value 2−k2^{-k} on level kk. Sought is a selection of total face value n−1n - 1 (for nn symbols) with the smallest total weight; how often a symbol appears in this selection is its code length.

In practice one computes from the deepest level upwards: the coin list sorted by weight is combined into pairs (“package”), and the packages are sorted into the coin list of the next level (“merge”). After L−1L - 1 rounds one takes the 2n−22n - 2 lightest entries of the top list; every symbol gets as length the number of its occurrences in them.

Pseudocode – HuffmanCode.laengen(h, L)

benutzt ← symbols with h > 0
if none: return all lengths 0
if exactly one: return length 1 for it                Deflate requires a one-bit code
grund ← one item (h, {s}) per symbol, sorted by weight
pakete ← empty
repeat L − 1 times:
    zusammen ← merge(grund, pakete)                  sorted by weight
    pakete ← every two consecutive items into one (weights added, symbols united)
letzte ← merge(grund, pakete)
for the first 2·|benutzt| − 2 items of letzte:
    for each symbol s in it:  length[s] ← length[s] + 1

Source: envisionz-framework-compress/src/envisionz/compress/huffman/HuffmanCode.java. With equal weight the item from the base list is taken first.

Worked examples

The textbook example with frequencies 5, 9, 12, 13, 16, 45 (sum 100) gives the lengths 4, 4, 3, 3, 3, 1 and the canonical codes 1110, 1111, 100, 101, 110, 0. The mean length is 2.24 bits, the entropy 2.22 bits.

Canonical codes

Only the lengths are transmitted; writer and reader form the same codes from them. With nln_l codes of length ll, the first code of length ll is

c1=0,cl=2(cl−1+nl−1)c_1 = 0, \qquad c_l = 2\,(c_{l-1} + n_{l-1})

and within one length the code counts up by symbol number. HuffmanCode.vollstaendig checks the Kraft sum ∑i2Lmax⁡−li=2Lmax⁡\sum_i 2^{L_{\max} - l_i} = 2^{L_{\max}} (with the special case of a single symbol). Deflate and Brotli assign codes this way; zstd assigns the longest codes first (see FSE and Huffman).

Decoding bit by bit

The HuffmanDekoder builds no lookup table but keeps only two arrays: the number of codes per length and the symbols sorted by length and number. When reading, the code is built up bit by bit from the top. After ll bits, erster is the smallest code of length ll; if the value read lies below erster + (number of codes of this length), the symbol has been found. This is the method from puff.c among the zlib examples.

code ← 0;  erster ← 0;  index ← 0
for ℓ ← 1 to largest length:
    code ← code or leser.bit()
    anzahl ← zaehl[ℓ]
    if code − erster < anzahl:  return symbol[index + code − erster]
    index ← index + anzahl
    erster ← (erster + anzahl) · 2
    code ← code · 2
error "no valid Huffman code"

Source: envisionz-framework-compress/src/envisionz/compress/huffman/HuffmanDekoder.java. Construction costs one pass over the lengths; compared with a table with nine bits of look-ahead there is no table to build, but reading costs one step per bit.

Run length after PackBits

Rle encodes after the pattern of PackBits: a control byte ss, then data.

  • 0≤s≤1270 \le s \le 127: the next s+1s + 1 bytes stand singly.
  • 129≤s≤255129 \le s \le 255: the following byte applies 257−s257 - s times (2 to 128).
  • s=128s = 128 is not assigned and is an error.

The encoder takes a run from three equal bytes on (at most 128), otherwise it collects single bytes (at most 128) and stops before the next run of three. The worst case is bounded: one control byte per 128 single bytes, i.e.

nout≤n+⌈n128⌉n_{\text{out}} \le n + \left\lceil \frac{n}{128} \right\rceil

The best case is bounded too: two bytes per 128, i.e. at most 64 : 1.

Worked examples (with Rle.packe): AAAAABCDEEE gives FC 41 02 42 43 44 FE 45 – 257−252=5257 - 252 = 5 times A, then 2+1=32 + 1 = 3 single bytes BCD, then 257−254=3257 - 254 = 3 times E. 3000 equal bytes give 48 bytes: 23 runs of 128 and one of 56, two bytes each.

while i < n:
    lauf ← number of equal bytes from i, at most 128
    if lauf ≥ 3:  emit (257 − lauf), daten[i];  i ← i + lauf
    otherwise:
        anfang ← i;  einzeln ← 0
        while i < n and einzeln < 128:
            if daten[i] = daten[i+1] = daten[i+2]: break
            i ← i + 1;  einzeln ← einzeln + 1
        emit (einzeln − 1), daten[anfang .. anfang + einzeln − 1]

Source: envisionz-framework-compress/src/envisionz/compress/rle/Rle.java.

Convention in the framework: Rle is meant as a pre-stage, not as a replacement for Deflate: on masks, segmentation images and sparse fields it shortens the input so that the 32 KiB window of LZ77 afterwards covers a much larger area. On its own it is inferior.

How it is checked

  • CompressSelfTest: bit stream there and back, reversed Huffman codes come back in tree order, reading past the end reports itself; Huffman: the most frequent symbol has the shortest code, Kraft sum complete, mean length 2.24 bits in the textbook example (tolerance 0.005), with Fibonacci frequencies no length above 15 or 7, a symbol sequence comes back unchanged through the decoder, a single symbol gets one bit; RLE there and back for five samples, worst case below n+n/128+1n + n/128 + 1, 3000 equal bytes give exactly 48.
  • Msbleserprobe (23 checks): the MSB reader against slices of a BigInteger (400 cases), continuous reading with widths 1 to 32, bitsLang(64) against ByteBuffer.getLong (50 cases), limits and exceptions, a failed access consumes nothing.

A lesson from building it is recorded in the module documentation: the check “a long run shrinks a lot” demanded fewer than 40 bytes for 3000 equal bytes. Correct is 48, because PackBits caps a run at 128 – the check was wrong, not the code.

Limits

  • BitLeser and BitSchreiber read and write at most 32 bits at once, BitLeserMsb with bitsLang up to 64. None is usable concurrently.
  • Package-merge creates new lists with symbol sets for every level; for the module's alphabets (up to 286 symbols, limit 15) this does not matter, for very large alphabets a more economical version would be appropriate.
  • The bitwise Huffman decoder is slower than a table-driven one; the difference has not been measured.
  • The encoders (Rle.packe, Huffman lengths outside Deflate) have no caller outside the probes yet.
