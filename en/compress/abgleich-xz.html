XZ and LZMA — comparison against the format description and xz-utils

As of: 2026-09-07
Our implementation: envisionz.compress.lzma — read-only
Specification: The .xz File Format (public) and the LZMA description from the SDK
Compared against: xz-utils 5.4 (über Pythons lzma)
Test bench: envisionz.compress.Xzprobe — 53 checks, 17 foreign anchors, 27 mutation tests; envisionz.compress.Xzfilterprobe — 21 checks, 10 foreign anchors

The reference implementation. xz-utils by Lasse Collin is the reference; LZMA itself comes from Igor Pavlov (7-Zip).

Why this one. Because it is the only widespread implementation, and the range coder has no tolerance: a single bit read wrongly turns everything after it into noise.

Coverage, computed from the rows below: of 13 features we have 12 present, 0 partial and 1 absent; the reference implementation has 13 / 0 / 0.

The Note column points into section 5 of this document — not into the workspace item list. The word in front says what kind of thing it is: gap is something we lack and that is open; decided is something we deliberately do not do; property is a trait of the format affecting both implementations; open there is a gap of the reference product. Only the gaps are work — they are collected in section 5.1 and appear as one item in OFFENE-PUNKTE.md.

The most expensive of the six, for a reason found nowhere else. Deflate, bzip2, zstd and LZ4 write symbols: a Huffman word, an FSE state, a length — they can be extracted and checked one by one. LZMA does not. It carries an interval and narrows it with every bit in proportion to the probability it currently assigns that bit — and that probability is not in the file but learned while reading.

From that follows the whole difficulty: there is no place to enter, and no error that shows locally. A single bit read wrongly skews all following probabilities, and the output does not go wrong at a point but from a point onwards.

The items

Our open gaps

None.

Deliberate decisions

XZ3 (decided) — No writing

This module reads. A writer would be many times the work of the reader — it must not only know the format but choose well — and nobody here needs one: nothing is compressed, everything is decompressed.

Features

XZ2 (property) — The additional filters — applied since 2026-09-25

A chain of up to three filters may precede LZMA2: Delta for measurement series, BCJ for machine code. Applied are Delta and BCJ for x86, PowerPC, IA-64, ARM, ARM-Thumb, SPARC and ARM64, also with a start offset and chained (envisionz.compress.lzma.Vorfilter, after liblzma's public-domain filters). RISC-V (since liblzma 5.6) is rejected by name — there was no writer for it.

Measured against ten streams from liblzma 5.4.5 (docs/xz/xz2_erzeuge.py, ARM64 via ctypes). Each mutation test removes the filter from the block header: the block's CRC64 then reports the difference — so the fixtures give every filter something to convert.

XZ1 (property) — SHA-256 as check type — verified

XZ allows CRC-32, CRC-64, SHA-256 or no check at all. All four are verified; SHA-256 via java.security.MessageDigest, which every Java runtime must provide — no third-party library. Until 2026-09-25 the line was listed as a gap although the reader already did it (Xzprobe, anchor c_sha256); since then with a counter-check: a flipped byte of the checksum is reported. xz itself does not use SHA-256 by default.
