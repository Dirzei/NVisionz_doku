LZMA2, XZ and pre-filters

What lies above the LZMA core: the LZMA2 chunking with its reset levels, the XZ container with multi-byte integers, padding, four check types and index, and the pre-filters Delta and BCJ, which transform data before packing. With pseudocode following Lzma2, Xz and Vorfilter.

What it is about

A raw LZMA stream is indivisible: it cannot be picked up in the middle, and with incompressible data it becomes larger than the input. LZMA2 therefore adds chunks on top, which may be compressed or raw and each specify what carries over from the previous chunk. XZ puts the container around it: signature, blocks, check values, an index. And pre-filters transform the data so that LZMA finds more repetitions.

LZMA2: chunks and reset levels

Every chunk begins with a control byte:

Control bytemeaningfollowed by
0x00end of stream–
0x01raw chunk, reset dictionarysize − 1 (16 bits), bytes
0x02raw chunk, keep dictionarysize − 1 (16 bits), bytes
0x03 … 0x7Fnot assignederror
0x80 … 0xFFcompressed chunkoutput − 1 (16 bits), compressed − 1 (16 bits), properties byte if any

For a compressed chunk the lower five bits of the control byte are the upper five bits of the output size (21 bits in total, up to 2 MiB). Bits 5 and 6 are the reset level:

Levelstate and modelsproperties bytedictionary
0carry on–carries on
1resetkeep oldcarries on
2resetread newcarries on
3resetread newreset

Level 0 is not a special case: liblzma writes it already at the second chunk of a 120 kB file. A reader that starts every chunk afresh reads noise from the second chunk on. Every compressed chunk brings its own range stream (five initial bytes); but what was learned before is kept depending on the level.

Pseudocode – Lzma2.lies(daten, ab, ende)

kern ← null;  brauchtEigenschaften ← true
repeat:
    if p ≥ ende: error "without end byte"
    s ← daten[p++]
    if s = 0x00: break
    if 0x02 < s < 0x80: error "unknown control byte"
    if s = 0x01 or s ≥ 0xE0: brauchtEigenschaften ← true      dictionary is reset
    else if kern = null: error "first chunk must reset the dictionary"
    if s ∈ {0x01, 0x02}:                                       raw
        m ← 16 bits + 1
        if kern = null: kern ← Lzma(0, 0, 0)
        if s = 0x01: kern.woerterbuchZuruecksetzen()           before copying
        kern.roheBytes(m bytes)                                     state and models remain
        continue
    m ← ((s and 0x1F) << 16 | 16 bits) + 1;  g ← 16 bits + 1
    stufe ← (s >>> 5) and 3
    if stufe ≥ 2: eig ← next byte;  brauchtEigenschaften ← false
    else if brauchtEigenschaften: error "properties byte missing"
    if kern = null: kern ← Lzma(lc, lp, pb from eig)
    else if stufe ≥ 1: kern.modelleZuruecksetzen(lc, lp, pb from eig)
    if stufe = 3: kern.woerterbuchZuruecksetzen()
    kern.stueck(daten, p, p + g, m)                new range reader, m bytes of output
    p ← p + g
return (output, p)                                p lies behind the end byte

Source: envisionz-framework-compress/src/envisionz/compress/lzma/Lzma2.java. The rules for the first chunk, the properties byte after a dictionary reset and the behaviour of raw chunks were cross-read on 2026-09-15 against xz-java (LZMA2InputStream.decodeChunkHeader) and liblzma (lzma2_decoder.c).

Convention in the framework: “Resetting the dictionary” does not discard the output buffer – those bytes are the output – but only moves the limit wbAb to the current position. A back-reference across this limit is an error, and the first literal after it sees 0 as its previous byte. The dictionary is the entire output so far; the dictionary size from the filter header is checked (at most 40) but not needed.

The XZ container

  • Stream header: signature FD 37 7A 58 5A 00, two flag bytes (the first zero, the check type in the lower four bits of the second), CRC32 over the flags.
  • Block header: size (b0+1)⋅4(b_0 + 1) \cdot 4 bytes; block flags (number of filters − 1 in bits 0–1, bit 6 compressed size present, bit 7 uncompressed size present, bits 2–5 reserved); per filter ID and length of the properties as multi-byte integers, then the properties; zero padding; CRC32 over the header.
  • Block data, padded to a multiple of four, then the check value of the unpacked data.
  • Index: indicator 00, number of blocks, two sizes per block – the compressed one without block padding (“unpadded size”: block header + compressed data + check value) and the uncompressed one –, padding, CRC32.
  • Stream footer: CRC32, index size 4⋅(w+1)4 \cdot (w + 1) from the stored value ww (“backward size”), the stream flags again, 59 5A (“YZ”).

Multi-byte integers

All sizes are stored with seven payload bits per byte, least significant group first; a set top bit means “another byte follows”:

x=∑i=0k−1(biand⁡127)⋅27i,k≤9x = \sum_{i=0}^{k-1} (b_i \operatorname{and} 127) \cdot 2^{7i}, \qquad k \le 9

Example: 300 = 2⋅128+442 \cdot 128 + 44 is stored as AC 02 (44+128=172=0xAC44 + 128 = 172 = \text{0xAC}, then 2). A zero byte in the last place of a multi-byte number is rejected, otherwise the same number would have two representations.

Check types

The check types are arranged in groups of three; the length depends only on the group:

l(0)=0,l(c)=4⋅2⌊(c−1)/3⌋(1≤c≤15)l(0) = 0, \qquad l(c) = 4 \cdot 2^{\lfloor (c-1)/3 \rfloor} \quad (1 \le c \le 15)

i.e. 4, 8, 16, 32 and 64 bytes. Recomputed are 0x00 none, 0x01 CRC32, 0x04 CRC64 (the default of xz) and 0x0A SHA-256. For an unknown check type its length is still skipped so that the next block begins at the right place, and the result reports geprueft = false.

Pseudocode – one block in Xz

kopfLänge ← (roh[ab] + 1) · 4;  check CRC32 over kopfLänge − 4 bytes
flaggen ← roh[ab+1];  filter ← (flaggen and 3) + 1
if flaggen and 0x3C: error "reserved bits"
if flaggen and 0x40: gepackt ← vielfach()
if flaggen and 0x80: entpackt ← vielfach()
for each filter f:
    kennung ← vielfach();  eigLänge ← vielfach()
    if f is the last: require LZMA2 (0x21), eigLänge = 1, dictionary value ≤ 40
    else if kennung = Delta (0x03): distance ← property + 1
    else if 0x04 ≤ kennung ≤ 0x0A: BCJ, start offset from 0 or 4 property bytes
    otherwise: error (RISC-V 0x0B and others by name)
check that the padding up to the CRC is zero
(teil, datenEnde) ← Lzma2.lies(roh, datenAb, gepackt known ? datenAb + gepackt : end of file)

remember unpadded ← headerLength + (dataEnd − dataStart) + length(check value)

in the index, for each block i:
compare compressed(i) with unpadded(i) and uncompressed(i) with length(teil(i))
in the stream footer:

Source: envisionz-framework-compress/src/envisionz/compress/lzma/Xz.java (lies, einStrom, einBlock, verzeichnisLesen, vielfach, pruefLaenge).

Convention in the framework: The compressed size in the block header may be missing, and liblzma omits it as a rule. Then only the LZMA2 stream says where the block data end – which is why Lzma2.lies returns the position behind the end byte. Whoever reads to the end of the file instead no longer finds the check value and the index; all fifteen anchors failed on this on 2026-09-06.
Convention in the framework: The stream flags are two bytes; the check type is in the second. In the stream footer it is compared at byte 9 of the footer with the one from the header. SHA-256 comes from java.security.MessageDigest – the only place in the module's main code that uses a JDK computation.

Pre-filters

A pre-filter changes no length; it transforms bytes so that equal content looks equal. When packing it runs before LZMA2, when unpacking after it in reverse order.

Delta (ID 0x03) stores every byte as the difference to the byte aa positions earlier (a=a = properties byte + 1). It is undone by

xi=(yi+xi−a)mod⁡256,i≥ax_i = (y_i + x_{i-a}) \operatorname{mod} 256, \qquad i \ge a

This helps with measurement series and images with evenly growing values: 10, 12, 14, 16 becomes 10, 2, 2, 2.

BCJ (Branch/Call/Jump, IDs 0x04–0x0A) looks for branch instructions with a relative target in machine code and, when packing, replaces the relative target by the absolute one. If a program calls the same function from many places, the same bytes then appear everywhere and LZMA finds repetitions. When unpacking, the conversion is reversed. For x86 (E8 call, E9 jmp with 32-bit offset) at position pp with start offset ss:

relative=absolute−(s+p+5)\text{relative} = \text{absolute} - (s + p + 5)

The conversion is only done if the top byte of the offset is 00 or FF, i.e. a plausible nearby jump; a mask over the E8/E9 bytes seen recently excludes further false hits. Example from the Vorfilterprobe: E8 10 00 00 00 at position 0 becomes E8 0B 00 00 00, since 0x10−5=0x0B\text{0x10} - 5 = \text{0x0B}; with start offset 0x1000 and target 0x2000 the result is 0x2000−0x1005=0xFFB\text{0x2000} - \text{0x1005} = \text{0xFFB}.

For ARM (instruction word with top byte EB, BL) the field is 24 bits in units of four bytes:

f'=4f−(s+p+8)4mod⁡224f' = \frac{4f - (s + p + 8)}{4} \operatorname{mod} 2^{24}

Field 0x100 at position 0 becomes 0xFE, at position 4 0xFD. PowerPC, IA-64, ARM-Thumb, SPARC and ARM64 follow the public-domain filters of liblzma (src/liblzma/simple/*.c) with their own instruction formats.

Pseudocode – Vorfilter.delta and arm

function delta(b, a):
    for i ← a to length(b)−1:  b[i] ← b[i] + b[i−a]          modulo 256

function arm(b, s):
    for i ← 0, 4, 8, … while i + 4 ≤ length(b):
        if b[i+3] = 0xEB:
            q ← (b[i+2]·2^16 + b[i+1]·2^8 + b[i]) · 4
            z ← (q − (s + i + 8)) >>> 2
            b[i..i+2] ← lower 24 bits of z, least significant first

Source: envisionz-framework-compress/src/envisionz/compress/lzma/Vorfilter.java. The x86 filter with its mask follows x86.c from liblzma line by line.

How it is checked

  • Xzprobe (55 checks): anchors from liblzma: text, all 256 byte values, empty, 70,000 equal bytes, a raw chunk of 4000 random bytes, eight symbols, unusual properties, 3 MB with reset level 0 across the chunk boundary; all four check types; two streams in a row (both halves come out); five blocks in one stream; CRC64 of “123456789” = 995DC9BBDF1939FA and not the one of ISO 3309; damage (flipped byte, 104 single-bit flips, truncated, non-zero padding, wrong index with and without new CRC, wrong compressed size in the index and wrong index size in the stream footer, both with recomputed CRC); the multi-byte integers 127 and 128; a flipped SHA-256.
  • Lzmabausteinprobe (58 checks): all LZMA2 control bytes and error paths, the four reset levels on hand-built streams (level 0 lets models and dictionary carry on, level 3 in mid-stream forgets the dictionary), raw chunks between compressed ones, and three liblzma streams whose end lies behind the end byte.
  • Xzfilterprobe (21 checks): Delta with distance 4, all seven BCJ filters (x86 also with start offset 0x1000) and Delta with x86 in a row, each against a stream from liblzma 5.4.5 and with a counter-probe without the filter; RISC-V and LZMA2 in the wrong place are rejected.
  • Vorfilterprobe (20 checks): the names of the IDs, Delta with distances 1, 4, 7 against a separately written forward direction, x86 and ARM with hand-computed expected values (positive and negative targets, start offset, E9, no jump without 00/FF, shorter than five bytes).

Limits

  • Read-only; the BCJ filter for RISC-V (since liblzma 5.6) is named, not applied.
  • Only LZMA2 is read as the last filter; at most three pre-filters before it.
  • The entire output lies in memory (dictionary = output); capped by the decompression limit.
  • A level-3 dictionary reset in mid-stream does not occur in liblzma files; it is checked only on hand-built streams.
