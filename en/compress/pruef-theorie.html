Checksums – CRC, Adler-32 and xxHash

The computation behind the module's seven checksums: CRC as polynomial division over GF(2), reflected and unreflected, the 256-entry table, the variants CRC-32, CRC-32C, bzip2 and CRC-64, the chaining and the masking; Adler-32 with its overflow bound; xxHash32 and xxHash64 as in the code. With check values recomputed against the classes.

What it is about

A checksum is meant to detect random corruption: a flipped bit, a burst of spoiled bits, a truncated end. It is no protection against deliberate manipulation. Seven methods sit in the module, and each is prescribed by a particular format – a mix-up gives a checksum that is always wrong although the data are right.

CRC as polynomial division

A bit sequence mk−1…m1m0m_{k-1} \dots m_1 m_0 is read as a polynomial M(x)=∑imixiM(x) = \sum_i m_i x^i with coefficients in GF(2) – addition is xor, there are no carries. With a generator polynomial G(x)G(x) of degree rr, the CRC is the remainder

R(x)=M(x)⋅xrmod⁡G(x)R(x) = M(x) \cdot x^{r} \operatorname{mod} G(x)

If RR is appended to the message, M(x)xr+R(x)M(x)\,x^r + R(x) is divisible by GG. An error pattern E(x)E(x) stays undetected exactly when GG divides it. The properties follow from this: every polynomial with more than one term detects all single-bit errors, and a polynomial of degree rr with a constant term detects all error bursts up to length rr.

Worked example with a small generator G=x3+x+1G = x^3 + x + 1 (1011) and the message 1101: 1011 is subtracted (xor) from 1101000 step by step wherever the leading digit is 1:

1101000
1011       → 0110
 1100      → 0111
  1110     → 0101
   1010    → 0001    remainder 001

Checked via powers: x3≡x+1x^3 \equiv x + 1, so x6+x5+x3≡(x2+1)+(x2+x+1)+(x+1)=1x^6 + x^5 + x^3 \equiv (x^2 + 1) + (x^2 + x + 1) + (x + 1) = 1.

The conventions of a practical CRC

Besides the polynomial the formats fix three things:

  • Initial value of all ones: otherwise leading zero bytes would not change the CRC.
  • Final inversion (xor⁡\operatorname{xor} with all ones).
  • Bit direction. “Reflected” means: the least significant bit of each byte is the highest coefficient; the register shifts right, and the polynomial is written bit-reversed – 04C11DB7 becomes EDB88320. Unreflected (bzip2) shifts left with the polynomial as it stands.

The table

Bitwise, every byte costs eight shift steps. Because the division is linear, the eight steps can be precomputed for every possible value of the lowest register byte. For the reflected CRC, per byte xx:

c←T[(cxor⁡x)and⁡255]xor⁡⌊c28⌋c \leftarrow T\big[(c \operatorname{xor} x) \operatorname{and} 255\big] \operatorname{xor} \left\lfloor \frac{c}{2^8} \right\rfloor

with T[i]T[i] = the result of eight bitwise steps starting from ii. For CRC-32: T[1]=T[1] = 77073096, T[128]=T[128] = EDB88320 – for i=128i = 128 the only set bit drops out only in the eighth step, and exactly the polynomial remains.

Pseudocode – Crc32 (likewise Crc32c, Crc64)

// table, computed once instead of typed in
for i ← 0 to 255:
    c ← i
    repeat 8 times:  c ← (c and 1) ? (POLYNOM xor (c >>> 1)) : (c >>> 1)
    T[i] ← c

stand ← FFFFFFFF
for each byte x:  stand ← T[(stand xor x) and 0xFF] xor (stand >>> 8)
wert ← stand xor FFFFFFFF

Source: envisionz-framework-compress/src/envisionz/compress/pruef/Crc32.java (polynomial EDB88320), Crc32c.java (82F63B78), Crc64.java (C96C5795D7870F42, 64-bit register). The classes compute incrementally: nimm(...) any number of times, then wert().

Convention in the framework: Every table is computed from the polynomial when the class is loaded, not copied: a typed-in table is a source of error with no benefit. Crc32.wert() returns a Java int; whoever compares with an unsigned value from the file masks with 0xFFFFFFFFL (as in Zipdatei and Xz).

CRC-32C

CRC-32C uses Castagnoli's polynomial 1EDC6F41 (reflected 82F63B78). It detects burst errors better and is available as a dedicated instruction in current processors; that is why Snappy, iSCSI, ext4 and Btrfs use it. Structure and initial value are the same as for CRC-32, the values entirely different.

The Snappy framing format does not store the CRC-32C raw but masked:

m=(rotr15⁡(c)+0xA282EAD8)mod⁡232,c=rotl15⁡((m−0xA282EAD8)mod⁡232)m = \Big(\operatorname{rotr}_{15}(c) + \text{0xA282EAD8}\Big) \operatorname{mod} 2^{32}, \qquad c = \operatorname{rotl}_{15}\Big((m - \text{0xA282EAD8}) \operatorname{mod} 2^{32}\Big)

The reason: the CRC of a message with its own CRC appended is a constant (the “residue” of the polynomial). If a format stores CRC values in data over which a CRC runs again, a class of errors goes unnoticed; the rotation and the addition break this up. Example: “123456789” → raw E3069283, masked C78AB0E5.

The bzip2 variant and the chaining

Crc32Bzip2 uses the same polynomial 04C11DB7 as CRC-32, but unreflected: the register shifts left, the byte enters at the top:

c←(c⋅28mod⁡232)xor⁡T[(⌊c/224⌋xor⁡x)and⁡255]c \leftarrow \big(c \cdot 2^8 \operatorname{mod} 2^{32}\big) \operatorname{xor} T\Big[\big(\lfloor c/2^{24} \rfloor \operatorname{xor} x\big) \operatorname{and} 255\Big]

Initial value and final inversion are the same, which makes the mix-up likely; “123456789” gives FC891918 instead of CBF43926.

At the end of a bzip2 stream there is a combined checksum formed from the block checksums, not from the data:

G0=0,Gk=rotl1⁡(Gk−1)xor⁡ckG_0 = 0, \qquad G_{k} = \operatorname{rotl}_1(G_{k-1}) \operatorname{xor} c_k

Because the rotation precedes every block, GG depends on the order: two swapped blocks are noticed although each is correct on its own. Example with Crc32Bzip2.verbinde(0x12345678, 0x0F0F0F0F): rotl1⁡(12345678)=2468ACF0\operatorname{rotl}_1(\text{12345678}) = \text{2468ACF0}, xor⁡0F0F0F0F=2B67A3FF\operatorname{xor}\ \text{0F0F0F0F} = \text{2B67A3FF}.

CRC-64

By default XZ writes CRC-64 following ECMA-182: polynomial 42F0E1EBA9EA3693, reflected C96C5795D7870F42, initial value and final inversion with 64 ones. There are at least four common CRC-64s with different polynomials; the Xzprobe checks explicitly that the value is not the one of ISO 3309.

Adler-32

Adler-32 (zlib) consists of two sums modulo P=65521P = 65521, the largest prime below 2162^{16}:

ak=1+∑i=1kxi,bn=∑k=1nak,Adler32=216(bnmod⁡P)+(anmod⁡P)a_k = 1 + \sum_{i=1}^{k} x_i, \qquad b_n = \sum_{k=1}^{n} a_k, \qquad \text{Adler32} = 2^{16}\,(b_n \operatorname{mod} P) + (a_n \operatorname{mod} P)

aa alone would be blind to permutations; bb weights every byte with the number of steps to the end, bn=n+∑i(n−i+1)xib_n = n + \sum_i (n - i + 1)\,x_i, and so captures the order. Adler-32 is faster than a CRC but weaker for short messages, because aa and bb hardly use the value range there.

Worked example “Wikipedia”: the running values of aa are 88, 193, 300, 405, 517, 618, 718, 823, 920; a=920=0x398a = 920 = \text{0x398}, b=4582=0x11E6b = 4582 = \text{0x11E6}, hence 11E60398 – the value checked by CompressSelfTest.

When the reduction is needed. If one computes in unsigned 32 bits and reduces only every nn steps, bb must not overflow within nn steps. In the worst case (all bytes 255, aa and bb just below PP beforehand) bb grows by

255⋅n(n+1)2+(n+1)(P−1)≤232−1255 \cdot \frac{n(n+1)}{2} + (n + 1)(P - 1) \le 2^{32} - 1

The largest integer solution is n=5552n = 5552 (giving 4,294,690,2004{,}294{,}690{,}200); for n=5553n = 5553 it would be 4,296,171,735>232−14{,}296{,}171{,}735 > 2^{32} - 1.

a ← 1;  b ← 0                           long, not int
while bytes remain:
    block ← min(rest, 5552)
    repeat block times:  a ← a + x;  b ← b + a
    a ← a mod 65521;  b ← b mod 65521
wert ← (b << 16) or a

Source: envisionz-framework-compress/src/envisionz/compress/pruef/Adler32.java.

Convention in the framework: aa and bb are long. The bound 5552 holds for unsigned 32 bits; in Java's signed int (largest value 231−12^{31} - 1) bb would overflow earlier, and the remainder of a negative number is negative. This was only found in the comparison with the JDK over 300 kB; the standard example “Wikipedia” is too short for it.

xxHash32 and xxHash64

xxHash is not a CRC but a fast hash function made of multiplications by large odd constants, rotations and a final mixing. It detects random corruption but is not cryptographic.

xxHash32 with the primes P1…P5P_1 \dots P_5 (9E3779B1, 85EBCA77, C2B2AE3D, 27D4EB2F, 165667B1) and the round

ρ(v,w)=rotl13⁡(v+wP2)⋅P1(mod⁡232)\rho(v, w) = \operatorname{rotl}_{13}(v + w\,P_2) \cdot P_1 \quad (\operatorname{mod} 2^{32})

  1. From 16 bytes on: four accumulators v1=s+P1+P2v_1 = s + P_1 + P_2, v2=s+P2v_2 = s + P_2, v3=sv_3 = s, v4=s−P1v_4 = s - P_1 (seed ss) each process one 4-byte word of a 16-byte stripe; afterwards h=rotl1⁡v1+rotl7⁡v2+rotl12⁡v3+rotl18⁡v4h = \operatorname{rotl}_1 v_1 + \operatorname{rotl}_7 v_2 + \operatorname{rotl}_{12} v_3 + \operatorname{rotl}_{18} v_4. Below 16 bytes: h=s+P5h = s + P_5.
  2. h←h+nh \leftarrow h + n with the whole length nn.
  3. Remaining 4-byte words: h←rotl17⁡(h+wP3)⋅P4h \leftarrow \operatorname{rotl}_{17}(h + w P_3) \cdot P_4; remaining bytes: h←rotl11⁡(h+xP5)⋅P1h \leftarrow \operatorname{rotl}_{11}(h + x P_5) \cdot P_1.
  4. Final mixing: h←hxor⁡⌊h/215⌋h \leftarrow h \operatorname{xor} \lfloor h / 2^{15} \rfloor, h←hP2h \leftarrow h P_2, h←hxor⁡⌊h/213⌋h \leftarrow h \operatorname{xor} \lfloor h / 2^{13} \rfloor, h←hP3h \leftarrow h P_3, h←hxor⁡⌊h/216⌋h \leftarrow h \operatorname{xor} \lfloor h / 2^{16} \rfloor.

xxHash64 has the same structure but different constants (only the rotation widths 1, 7, 12, 18 in the merge and 11 for the byte-wise remainder are shared): 64-bit primes, 32-byte stripes of four 8-byte words, a round with rotl31⁡\operatorname{rotl}_{31}, and after merging every accumulator is mixed in once more: h←(hxor⁡ρ(0,vi))⋅P1+P4h \leftarrow (h \operatorname{xor} \rho(0, v_i)) \cdot P_1 + P_4. The remainders are processed in steps of 8, 4 and 1 bytes, the final mixing shifts by 33, 29 and 32. Whoever “extends xxHash32 to 64 bits” gets a different function.

Convention in the framework: Words are read little-endian regardless of the machine. All right shifts are unsigned (>>>); with >> about every second value would be wrong because the sign bit is dragged along. Multiplication and addition in Java's two's complement are the same as unsigned. LZ4 stores only the second byte of an xxHash32 in the frame header, zstd only the lower 32 bits of an xxHash64.

How it is checked

  • CompressSelfTest: Adler-32 of “Wikipedia” = 11E60398, CRC-32 of “123456789” = CBF43926, both against java.util.zip.Adler32 and CRC32 over 300,000 random bytes (far beyond 5552 steps), Adler-32 of the empty array = 1.
  • SnappySelfTest: CRC-32C of “123456789” = E3069283, the table against a bitwise computation over 200 random blocks, computed in three pieces, masking there and back, CRC-32C ≠ CRC-32.
  • Bzip2probe: FC891918 and CBF43926 differ, empty text, zero byte, a, all 256 byte values; verbinde rotates and is not commutative.
  • Xzprobe: CRC-64 of “123456789” = 995DC9BBDF1939FA, not the value according to ISO 3309, empty CRC-64 = 0.
  • Lz4probe: twelve checks of xxHash32, ten of them values against python-xxhash, with lengths around the boundaries 4 and 16, seeds 0 and 1, slices.
  • Zstdprobe: 22 values of xxHash64 against python-xxhash, lengths around the boundaries 8 and 32 (31, 32, 33, 63, 64, 65), three seeds.

Limits

  • None of the seven functions protects against deliberate manipulation; for the module it is enough that they find random errors.
  • The CRCs compute byte by byte with one table; faster methods (several tables, processor instructions) do not exist.
  • Crc32Bzip2, XxHash32 and XxHash64 compute only over a whole array or a slice; Crc32, Crc32c, Crc64 and Adler32 also incrementally.
  • SHA-256 for XZ comes from java.security, not from this package.
