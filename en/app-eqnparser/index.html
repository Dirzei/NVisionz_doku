envisionz-app-eqnparser

Set up, solve and evaluate systems of equations

Overview of the app, as of 29 September 2026. The user interface to the equation solver: edit models in the CAS and NFML formats, solve them with Newton, Broyden, Levenberg-Marquardt and homotopy methods, follow the run, calculate operating points in batches, sweep performance maps and look at the model as a flowsheet.

What the app is for

A compressor, a combustor or a whole engine can be described as a system of equations: many equations in which mass flows, pressures, temperatures and efficiencies are so entangled that none can be worked out on its own. Such systems are solved numerically, and they are delicate: a poor starting value, the root of a negative number or a stiff transition, and the method goes nowhere.

The app gives the solver a user interface. You write or load a model, see its variables with units, choose method and options, start the run and watch live how the residuals fall. The main use so far is meanline models of axial compressors, up to the complete performance map with efficiency islands.

What it can do

Editing the model

The CAS tab is the editor; the rest of the interface hangs on the model.

  • Editor with syntax colouring for CAS models; the structure of the model as a tree.
  • Load models in the NFML format, including INCLUDE and map lines, which are resolved relative to the file.
  • Variables tab: values, starting values and units, using the framework's common unit registry.
  • Derivatives sub-tab: for each equation the residual and all partial derivatives in the real variable names, fixed variables marked.
  • C export sub-tab: header and source file of a C output of the system. What cannot be translated (calls without a C counterpart) appears as a comment and in the status line; nothing disappears silently.

Solving and following

A run in the background, visible live.

  • Eleven solvers: Newton with Armijo search (dense and with sparse LU), a plain sparse-LU solver, Broyden (dense and sparse), Levenberg-Marquardt, homotopy, arc-length homotopy, adaptive lambda, smoothed Newton and two-phase Newton.
  • Options for scaling (equilibration), residual normalisation, condition estimation and physical projection, 31 settings in all.
  • Run tab with a configuration card, Convergence tab with a history chart and a log. The result reports convergence, convergence with violated bounds, or non-convergence.
  • Converged results can be stored as a table in H2.

Batch, map and starting values

Many calculations, not just one.

  • Batch: a CSV of operating points is worked through, and the result goes to a CSV of solutions.
  • Map: the performance map is swept point by point, in the background and with a progress display.
  • Starting-value search: the framework's evolutionary search is offered as a scorer and can be used in the search workbench to find usable starting values.

Diagnosis and flowsheet

Understanding why a model does not converge, and how it is connected.

  • Diagnosis: model check at the starting point (condition, residuals, guard rails) and decomposition into strongly connected components, with an HTML report.
  • Flowsheet: the connections taken from the model on four levels: units, streams, couplings, equations. The diagnosis lies as a layer on the picture without anything having to be solved.
  • Info boxes at the units compare any number of calculation states (starting point, solution, stored runs) with a deviation column; without a fixed selection they show the quantities with the largest deviation. Export as SVG including the boxes.
  • The flowsheet follows a change of model and resolves INCLUDE.

Translating models of another simulation system

A card in the tool rail, not a window.

  • The working-directory tree recognises control decks of the other system and offers them.
  • The card shows inputs, run script, library and maps, proposes the target deck and picks up a target-value file from nearby.
  • Buttons to translate, to calculate the design point and to recalculate; the result appears in the card's log, and the deck loads like any other model.

Data and formats

  • Reads: CAS models (.cas) and NFML models (.nfml), operating points as CSV, map sets and target-value files.
  • Writes: solutions as an H2 table (variable and value), batch results as CSV, C sources, the flowsheet as SVG and HTML reports of the diagnosis.
  • Session: the model path and all 31 solver options are remembered.
  • Numbers: the solver writes numbers without a locale, so the log stays readable under a German locale.

What it builds on

  • envisionz-commandline-eqnparser: parser, solvers, diagnosis, derivatives, C export and the translation of foreign decks. The app calls it only through SolverAPI and BatchRunner; the core knows no class of the framework and also runs on its own as a command-line tool.
  • framework-flowsheet: the graph model and its display; the app supplies the adapter from the model.
  • framework-thermo: material properties and combustion for the models.
  • framework-data: H2 storage, loaded tables, unit registry.
  • framework-swing: background runner, log field, icons, help field, cards in the tool rail.
  • framework-viewer: display of the help pages.
  • framework-evolve: the search for starting values.
  • framework-core and framework-api: registration as an app, session.

State and limits

All tabs are in operation: model, variables, run, batch, convergence, diagnosis, map, derivatives, C export, flowsheet and help with twenty topics in both languages (getting started, syntax, solvers, examples, references). The app is the largest module among the applications.

The interface is tested headless in seven programs: wiring with loading, variables, run, results and the tabs for derivatives and C export; model view; storage of runs; starting-value search; log reader under a German locale; translation card and flowsheet switching. The counter-tests are kept in a list of their own. In addition there are acceptance checks of the flowsheet on two complete models with a real solution run.

Limits: A run cannot be stopped midway; on cancel the solver runs to the end and the result is discarded. The Variables and Map tabs so far read only CAS models. A switch to the framework's common cards and sidebars is postponed.
