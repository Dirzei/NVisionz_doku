Units and Numbers from Text – Background

The mathematics behind UnitRegistry, UnitProfile and Zahlenleser: why a unit needs two numbers, how absolute values and differences are converted, where a column gets its unit from, and what becomes of "1,500".

Linear-affine units

A quantity such as temperature is given in units whose zero points do not coincide: 0 °C is 273.15 K, 0 °F is about 255.37 K. A converter that only knows a factor returns 0 K for 0 °C. The framework therefore describes every unit by two numbers relative to the SI base unit of its quantity kind, the factor ff and the offset oo:

b=fv+o,v=b−ofb = f\,v + o, \qquad v = \frac{b - o}{f}

Here vv is the value in the unit and bb the value in the base unit (K, Pa, J/kg, …). Between two units AA and BB of the same kind the conversion always goes through the base; with nn units that needs nn entries instead of n2n^2 conversions:

vB=(fAvA+oA)−oBfBv_B = \frac{(f_A v_A + o_A) - o_B}{f_B}

Absolute value and difference

In a difference of two values the zero point cancels:

(fa+o)−(fb+o)=f(a−b)(f\,a + o) - (f\,b + o) = f\,(a - b)

A temperature span of 10 °C is therefore a span of 10 K, and 9 °F is 5 K. Converting a span with convert gives 283.15 K – the 273.15 belongs to the absolute value only. The framework therefore keeps two methods apart: convert for values with a zero point, convertDelta for everything that comes from a subtraction (temperature spans, tolerances, pressure drops, slopes, standard deviations).

Pseudocode – UnitRegistry.convert and convertDelta

convert(value, from, to):
    if from = null or to = null:  return value
    if key(from) = key(to):  return value  spelling, case-insensitive
    A ← get(from);  B ← get(to)
    if A = null or B = null:  return value  unknown: do not guess
    if not sameBase(A, B):  return value  other quantity kind: do not convert
    return B.fromBase( A.toBase(value) )  toBase: f·v + o, fromBase: (b − o)/f

convertDelta(delta, from, to):
    the same four pre-checks
    return A.factor · delta / B.factor  without offset

Source: envisionz-framework-data/src/envisionz/data/units/UnitRegistry.java. For duplicate names in different kinds, get returns the first entry registered.

Decision in the framework: An unknown or non-convertible unit returns the value unchanged; no exception is thrown and nothing is guessed. To find out whether a conversion is possible, ask isConvertible(a, b) – there, speed and airspeed also count as convertible.

Quantity kinds and profiles

A QuantityKind says what a unit belongs to and what its base is (baseUnit()); QuantityKind.byId finds it by an identifier that matches the one in the standalone equation-parser registry. A UnitProfile assigns a display unit to each kind. There are three ready-made profiles:

  • SI – the base units.
  • Imperial – imperial units.
  • RR – the historical mixed system of cycle calculation: temperature in K, pressure in psia, specific enthalpy in CHU/lb. Special units such as lb·√K/(s·psia) for the flow function come with it.

Profiles are immutable; withUnit(kind, unit) returns a changed copy.

Where a column gets its unit from

When a table is loaded, the unit of a column can come from three sources. They are applied in this order, the most explicit statement winning:

  1. Header: UnitHeaders.applyHeaderConvention reads column headers of the form NAME [unit]. If the unit is known, the name is shortened to NAME and source unit and quantity kind are set; an unknown unit leaves the header untouched.
  2. Sidecar file: UnitAssignmentStore reads <name>.units.properties next to the CSV – quantity kind, unit and alias per column, plus the options of the load dialog.
  3. Name heuristic: QuantityNameDefaults recognises station identifiers of cycle calculation by regular expressions (case-insensitive) and sets only the quantity kind, never the unit. Columns that already have a kind or a unit are skipped.

The last step is LoadedTable.withSiValues(registry): a copy in which every numeric column with a known source unit is converted to the SI base of its kind. The source unit stays as metadata, the column is marked as converted, and a column so marked is not converted a second time. Unknown units, text columns and empty or unreadable cells stay unchanged; an integer column becomes a decimal column if the conversion is not the identity.

Numbers from text

The same string can mean different things: "1,500" is the number 1.5 in a German file and fifteen hundred in an English one. The module therefore has one place where text becomes a number – Zahlenleser for file data (CSV, H2 cells, table cells, envelope files) and Eingabezahl for typed text. Both have two faces.

The current rule – heute ("today")

heute(raw):
    if raw = null:  return null
    s ← raw without leading and trailing white space
    if s is empty:  return null
    try parseDouble( s with every ',' replaced by '.' )
    on format error:  return null

This rule reproduces word for word the line replace(',', '.') that used to be scattered everywhere – including its weakness: "1,500" becomes 1.5, "1.234,5" is an error. heuteEndlich additionally admits only finite values, istZahlHeute requires at most one dot after the replacement.

The house rule – lies(raw, Schreibweise)

The future rule requires the caller to name the notation explicitly. What does not fit returns null instead of a silent interpretation:

  • STRENG (strict): no group separator, and the comma is not a numeric character.
  • DEUTSCH (German): dot groups, comma is decimal. ENGLISCH (English): the other way round.
entgruppiere(core, group, decimal):
    if the decimal character occurs more than once:  return null
    whole ← part before the decimal character;  fraction ← part after it
    if fraction contains a group character:  return null
    if whole contains a group character:
        parts ← whole split at the group characters
        if the first part is empty, longer than 3, or starts with '0':  return null
        if any further part does not have exactly 3 digits:  return null
        whole ← parts joined
    return whole [ "." fraction ]

Source: envisionz-framework-data/src/envisionz/data/zahl/Zahlenleser.java. Before entgruppiere a leading sign is split off; afterwards the result is read with parseDouble and must be finite.

Decision in the framework: lies has no caller yet. The switch was built in two steps: first pull all places together on heute without any result changing, then replace the rule at this one place. The tests therefore record what heute does, even where it misses.

How it is checked

  • Einheitenprobe has all reference values derived by hand and written as numbers in the code, not copied from the running program. Examples: 9 °F as a difference is 5 K (tolerance 10−1210^{-12}), 1 lb is 0.45359237 kg (10−1510^{-15}), 1 CHU/lb is 4186.8 J/kg (10−910^{-9}).
  • Its sharpest anchor is a pass over a real body of data from the equation parser: 7169 unit statements in 29 spellings, each of which must yield a quantity kind or be on the list of known exceptions. If the holdings are missing the test says so loudly and counts the item as skipped.
  • Two traps are pinned down that would both deliver a plausible number: the prefix "kilo" in KG*SQRT(K)/(S*KPA) (factor 10−310^{-3}, not 1) and the area of the flow function, which cannot be converted into the flow function.
  • Beipackprobe (35 checks): round trips save/load and write/read, RFC 4180 with CRLF and quotation marks; the header beats the sidecar file.
  • Zahlprobe (292 checks) sets each heute form against the old expression over 35 cases; lies is checked separately against hand-computed expectations.

Limits

  • All units are linear-affine. Logarithmic units (dB) and non-linear scales do not exist.
  • A unit that is not recognised leads to no message but to the unchanged value; whoever needs certainty checks beforehand with isConvertible.
  • The name heuristic knows only the station identifiers of cycle calculation; it never sets a unit.
  • heute reads "1,500" as 1.5 and does not read thousands separators.
