Event bus, app catalog and session storage – background

The procedures behind SimpleEventBus, AppRegistry, PersistenceManager and StaxStateWriter: by which rule events are delivered, how apps are discovered and how a session is saved so that the file also works on another machine.

App catalog

AppRegistry is the catalog of all apps the host can open. discover() lets the ServiceLoader resolve all entries under META-INF/services/envisionz.api.App on the class path (more on the contract on the page of the api module). For each app found, the catalog remembers two things: the AppDescriptor and a factory that creates a fresh instance through the no-argument constructor of the class found. The instance delivered by the loader serves only to read the descriptor.

Queries: all() returns the entries sorted by identifier (not in discovery order), findById an Optional, newInstance(id) a new app – with IllegalArgumentException for an unknown identifier. If a class cannot be created, the error message names the missing no-argument constructor as the likely cause. For starters without reflection there is register(descriptor, supplier). If discovery finds two app classes with the same identifier, the one found later wins; every such case is logged as a warning and listed in doppelteKennungen() as a line kennung: KlasseAlt ersetzt durch KlasseNeu.

Event bus and service registry

Two apps should be able to talk to each other without knowing each other: one reports “file loaded”, the other reacts. The bus is the simplest form of this that holds up.

Delivery rule

Listeners are kept in a table event class → list of listeners. publish(e) looks up the exact run-time class of e (listeners.get(event.getClass())); whoever subscribes to a superclass or an interface receives nothing. This is a deliberate simplification: matching is a single table lookup, and inheritance causes no surprises. Events are usually records without subclasses, so the restriction costs nothing.

Three properties of delivery are fixed:

  • Synchronous on the calling thread. When publish returns, all listeners have worked. If the call comes from Swing, that is the event dispatch thread (EDT). A worker thread that wants to publish has to go through SwingUtilities.invokeLater itself.
  • Snapshot. The list is copied before delivery. A listener may unsubscribe during delivery without breaking the iteration.
  • Fault isolation. If a listener throws a RuntimeException, it is written to the log (a warning with the event class) and the remaining listeners are served anyway. Otherwise all later apps would miss the event without anyone noticing.
publish(e):
    list ← listeners[ e.getClass() ]
    if list missing or empty: return
    copy ← synchronized(list) { array from list }          snapshot
    for each c in copy (subscription order):
        try c.accept(e)
        catch RuntimeException x: log a warning                 continue with the next

subscribe(cls, c):
    list ← listeners.getOrCreate(cls)
    synchronized(list) { list.append(c) }
    return handle that removes c again                      unsubscribing twice is harmless

Source: envisionz-framework-core/src/envisionz/core/events/SimpleEventBus.java. An Error (such as out of memory) is not caught, only RuntimeException.

SimpleServiceRegistry is a ConcurrentHashMap from interface type to implementation: register replaces an earlier implementation of the same type, get returns an Optional, unregister removes. There is exactly one service per type and no ranking.

Saving and loading the workspace

A saved session is an XML file with the open tabs (for the model see framework-api). Three problems must be solved for it to hold up in daily use: paths should be right on another machine too, a crash while writing must not destroy the old file, and a file from a foreign hand must not get the application into trouble.

Paths: save relative, load absolute

Properties whose key begins with path: count as file paths. When saving, the value is made relative to the folder of the XML file; when loading it is made absolute again. This allows a whole working folder with its session file to be copied to another machine. Two exceptions leave the value absolute: if the target is on another drive (relativize then throws IllegalArgumentException), or if the relative path would begin with ../../../.., i.e. lead four or more levels up – such chains are brittle and unreadable. Separators are normalised to / before this check, because relativize returns backslashes on Windows.

save(state, file):
    state.version ← "1.0";  state.savedAt ← now
    dir ← parent(absolute(file));  undo ← []
    try
        for each tab:  search tab properties, every section, every entry:
            for each (key, value) with key starts with "path:" and value not empty:
                abs ← absolute(value)
                rel ← dir.relativize(abs), separators to "/"
                if rel starts with "../../../.." or other drive: value ← abs   ("/" form)
                else value ← rel
                undo.remember(key ← original value)
        StaxStateWriter.write(state, file)
    finally  run all undo steps                          also on error

load(file):
    state ← StaxStateReader.read(file);  StateMigrator.migrate(state)
    for each path: value: if not absolute: value ← normalise(dir.resolve(value))

Source: envisionz-framework-core/src/envisionz/core/persistence/PersistenceManager.java. Resetting in finally lets the caller keep working with absolute paths after saving.

Writing through a temporary file

Writing directly into the target file would leave half a file after a crash in mid-write – the session would be gone. StaxStateWriter.write(state, file) therefore creates a temporary file in the target's folder (name starts with the file name, suffix .tmp), writes there and moves it onto the target with REPLACE_EXISTING and ATOMIC_MOVE. If the file system does not support an atomic move (AtomicMoveNotSupportedException, as on some network drives), the move is done without ATOMIC_MOVE – still better than overwriting directly. In finally the temporary file is deleted if it still exists; after an error none is left behind.

The writer produces the file by hand with XMLStreamWriter: UTF-8, two spaces per level, the system's line break. Its own indentation is needed because StAX supplies none. A null value is written as empty text; special characters are escaped by StAX.

Reading, versions and foreign files

The reader (StaxStateReader) switches off DTDs and external entities and skips unknown properties instead of failing – an older application can thus read a newer file without understanding the additional keys. StateMigrator.migrate is the place for future format changes: today "1.0" applies; an empty or missing version is read as "1.0"; any other version throws IllegalStateException. Guessing what an unknown version contains would be more dangerous than refusing.

Decision in the framework: Event delivery follows the exact class, synchronously, on a snapshot and with fault isolation. The session file is never overwritten directly, path: values are changed only while writing and reset afterwards, and an unknown format version aborts loading.

How it is checked

  • Kernprobe (62 checks; class coverage 16 of 16) checks against the promised behaviour of the interfaces: that the concrete event type determines the recipients – in both directions –, subscription order, harmless double unsubscribing, fault isolation and snapshot, the round trip of the session with XML special characters, path relativisation including its limit (more than three levels up stay absolute), that the passed state is not changed permanently, and that an unknown version throws; also that discover reports two apps with the same identifier. Ten counter-tests – from “no fault isolation” to “wave an unknown version through” – each turned it red.
  • Ablageprobe checks writer and reader: round trip field by field through stream and through file (the latter additionally passes the temporary file and the move step), angle brackets, ampersand, quotation marks, line breaks, umlauts and characters outside the basic plane in values, a value of eighty thousand characters, and a file with an external entity as an attacker would present it. After a failed write attempt no temporary file may remain.
  • A crash in mid-write cannot be provoked from a probe; the indivisibility of the move is therefore not measured, only the error path.

Limits

  • The bus is neither asynchronous nor hierarchical; a listener that computes for long holds up all others and – under Swing – the user interface.
  • An event with a subclass reaches only listeners subscribed to exactly that subclass.
  • Duplicate app identifiers during discovery remain allowed: the one found later replaces the earlier one. This is, however, logged as a warning and can be queried via doppelteKennungen(); which class wins still depends on the order on the class path.
  • Relativisation knows only values under keys with the prefix path:; paths in other properties stay as the app stores them.
  • On file systems without an atomic move the storage is not indivisible, only better than overwriting directly.
