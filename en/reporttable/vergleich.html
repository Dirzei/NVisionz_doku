Units, Differences and Expressions – Background

The mathematics behind Einheitenschicht, Formel and the validity rules of Grid: why values are converted first and subtracted afterwards, when no difference arises at all, and how an arithmetic expression for a free comparison column is read. What is described is what the source code of this module contains.

Convert first, then subtract

An operating-point report sets calculation states side by side and computes difference columns: new value minus reference value, or the deviation in percent. The values come from different sources and are not necessarily in the same unit. The unit layer therefore sits between source and report builder, and thus before the difference columns are formed – that is not a question of arrangement but the core.

A unit has a factor ff and an offset oo relative to the base, b=fv+ob = f\,v + o (see Units and Numbers). Converting two absolute values individually and subtracting afterwards is correct, because the offset cancels. Subtracting first and converting the difference like an absolute value is wrong as soon as an offset is involved: a temperature difference of 10 °C is 10 K, not 283.15 K.

The layer reads target unit and source unit per parameter: Zieleinheiten.fuer(key, ausQuelle) returns the target unit set in the dictionary or by the user, or else the unit of the source. The source data are never overwritten; when switching (SI, imperial, RR) the calculation starts again from the original, never from an already converted value.

When no difference arises

Every conversion returns a Ergebnis(wert, befund, hinweis) (result: value, finding, note). The Befund is one of five states: UNVERAENDERT (unchanged), UMGERECHNET (converted), EINHEIT_UNBEKANNT (unit unknown), NICHT_VERGLEICHBAR (not comparable) and KEIN_WERT (no value). The source code insists that a number that would look like a result but is none does not come into being at all:

angleichen(key, value):  adjust
    if value missing or not a number:  return (value, KEIN_WERT)
    from ← unit of the value;  to ← targets.fuer(key, from)
    if from = null:  return (value, EINHEIT_UNBEKANNT, "the source names no unit")
    if to = null or to = from:  return (value, UNVERAENDERT)
    if not converter.vergleichbar(from, to):  return (value, NICHT_VERGLEICHBAR, note)
    return (converter.umrechnen(number, from, to), UMGERECHNET)

delta(key, new, reference):
    a ← angleichen(key, new);  b ← angleichen(key, reference)
    if a value is missing:  return KEIN_WERT
    if a or b NICHT_VERGLEICHBAR:  return NICHT_VERGLEICHBAR
    if a unit is unknown for one of them:  return EINHEIT_UNBEKANNT   otherwise not safe
    if the units differ after adjusting:  return NICHT_VERGLEICHBAR
    return (a − b, in the common unit)

prozent(key, new, reference):
    the same obstacles as for delta
    if reference = 0:  return (KEIN_WERT, "reference value is zero")
    return ((a − b) / b · 100, unit "%")

Source: envisionz-framework-reporttable/src/envisionz/reporttable/units/Einheitenschicht.java. Two examples of "not comparable": kg·√K/(s·Pa) and s·√K/m look alike and differ by an area; subtracting two such numbers would give a number that looks like a result.

Decision in the framework: Without a unit converter nothing is guessed: OhneUmrechnung leaves every value as it is and regards only literally equal units as comparable. The RegistryRechner – the only package of the module with a dependency (on framework-data) – fills the target units through a profile with SI, imperial or RR. A percentage column with reference value zero returns KEIN_WERT with a reason instead of NaN or infinity: passing a NaN on to the output would mean printing "NaN" into the report.

Expressions for free comparison columns

Besides delta and prozent a comparison column can carry a freely written arithmetic expression, for example (wert - ref) / ref * 1000 for the deviation in per mille. Formel is a small reader of its own (recursive descent) and depends on nothing: the draft first named the reader of the command-line layer, but a framework module may not depend on the layer above it, and the CAS library would come along. The language:

  • Numbers with a dot, also 1e-3. No comma – the template is an interchange format and does not depend on the language of the computer.
  • + - * / ^, parentheses, signs. wert (value) is the value of this row in the calculation state of the cell, ref the same in the reference state; any other name is a parameter of the same case, ref(NAME) the same in the reference.
  • Functions: abs sqrt exp ln log10 min max.
// grammar of the reader (recursive descent, binding from the bottom up)
summe     ::= produkt  ( ('+' | '-') produkt )*
produkt   ::= vorzeichen ( ('*' | '/') vorzeichen )*
vorzeichen ::= ('-' | '+') vorzeichen  |  potenz
potenz    ::= atom ( '^' vorzeichen )?  right-associative
atom      ::= '(' summe ')'  |  zahl  |  name  |  'ref' '(' name ')'
           |  ('abs'|'sqrt'|'exp'|'ln'|'log10') '(' summe ')'  exactly one argument
           |  ('min'|'max') '(' summe (',' summe)* ')'  at least one

Source: envisionz-framework-reporttable/src/envisionz/reporttable/formel/Formel.java. The expression is read once into a tree of calculation nodes and then evaluated per cell with an assignment (Belegung); an error while reading reports expression, position and reason (FormelException).

Because ^ in potenz is followed by a vorzeichen, which in turn can be a potenz, the power is right-associative: 232=29=5122^{3^2} = 2^9 = 512. And because the sign sits one level above the power, −22=−(22)=−4-2^2 = -(2^2) = -4, as in mathematics. If a value is missing there is no result – the cell stays empty, as with every other comparison column (Formel.Luecke); that is different from a result that is not finite, which the caller decides.

Example: (wert - ref) / ref * 1000 with wert=0.866wert = 0.866 and ref=0.861ref = 0.861 gives (0.005)/0.861⋅1000=5.807(0.005)/0.861 \cdot 1000 = 5.807 per mille.

What makes a grid valid

The result of the build is a Grid, the seam between core and output paths (Word, Swing, command line). An invalid grid cannot even be created; the constructor checks:

  • Every value row has exactly as many cells as the grid has columns (group rows excepted).
  • The reference of a comparison column is an index, not a label. It must point to an existing column, also via detours, and must not run in a circle (the chain is followed for at most nn steps, after which it must have repeated).
  • The decimal places of a cell are never negative; a negative zero is normalised to 0.0, otherwise "-0.00" would appear in the report.

The messages name row, column and label. alsText(Locale) only fixes the rounding; the placeholder for an empty cell is set by the output path.

How it is checked

  • Einheitenschichtprobe (95 checks) computes the wrong way as well – subtract first, then convert like an absolute value – and demands that it does not come out. In addition the finding states, reference zero and non-comparable units.
  • Formelprobe (45 checks): precedence, right-associativity of the power, gaps, error messages with position.
  • Gridprobe (125 checks): valid grids get through, invalid ones are rejected with a message that names the row, column or name.
  • The tests measure not only that valid cases get through but that invalid ones are rejected; the extensions come with counter-experiments in which the old fault is built back in and must turn red (15 for the expressions).

Limits

  • The percentage refers to the chosen target unit: for temperatures in °C and in K the same pair of values gives different percentages.
  • After adjusting, the difference requires literally equal units; what the converter cannot convert yields a finding, not a number.
  • Formel knows only the operators and functions named and only numbers with a dot; a result that is not finite is for the caller to decide.
  • The report build (package build) belongs to the module but is not present in this source snapshot and is therefore not described here.
