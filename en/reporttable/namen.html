Names, Parameter Dictionary and Cases – Background

The mathematics behind NameNormalizer, Namensabbildung, DictParser, Fallspalte and Designaufteilung: how station designations from different programs and vintages become one unambiguous key, and how a calculation state falls apart into cases. What is described is what the source code of this module contains.

One name, one key

The same quantity has different names in different calculation states: E30Q26, E030Q026, e030_q026. If a report is to set values from several sources side by side, all three must map to one key. NameNormalizer turns a raw name deterministically into a ParameterKey in three steps, in this order:

  1. Remove separators: _ - . / and any white space.
  2. Bring every digit group to a minimum width (default 3): drop leading zeros, then pad with zeros on the left.
  3. Upper-case, using Locale.ROOT.
text(rawName):
    if rawName missing or empty after trimming:  exception
    out ← empty;  i ← 0
    while i < length:
        c ← raw[i]
        if c is white space or in "_-./":          i ← i + 1  step 1
        else if c is a digit:
            end ← end of the digit group from i
            out ← out + group( raw[i … end) );  i ← end
        else:                                    out ← out + c;  i ← i + 1
    if out is empty:  exception  only separators
    return UPPER(out, Locale.ROOT)  step 3

group(digits):  step 2
    core ← digits without leading zeros, at least one digit stays
    if length(core) ≥ width:  return core  never truncate
    return zeros padded to width + core

Source: envisionz-framework-reporttable/src/envisionz/reporttable/dict/NameNormalizer.java. Instances are immutable and stateless; the width must be at least 1.

Decision in the framework: Three subtleties are expressly decided. Leading zeros are removed first, then padding is added – otherwise E0030 would stay as it is at width 3, and two spellings of the same station would give different keys. A longer group stays longer: E1234 does not become E234; truncating would make one quantity out of two different ones. Upper-casing uses Locale.ROOT: under a Turkish system language i would otherwise become İ, and the same raw name would give different keys on two computers. A key must be the same everywhere.

Collision only within one source

Namensabbildung collects the raw names of one source and watches that no two different ones fall on the same key. Across sources the same key is the purpose of the normalisation; within a source it is an error, because two columns would pretend to mean the same quantity. Taking up the same raw name several times is harmless (comparison is on the trimmed raw name); only a different raw name on the same key raises NamenskollisionException, with source, key and both names. The order of intake is kept so that messages and outputs are reproducible. Whoever uses one mapping for two sources would be told about collisions that are none.

The parameter dictionary

The .pdict is a line-oriented text format (UTF-8) with sections [gruppe …] (group) and [parameter …]. For each key it fixes display name, group, unit, decimal places, aliases (alternative raw names) and quantity kind. The reading decisions:

  • # comments out whole lines only. Otherwise a label such as Druckverhaeltnis #2 could not be written without half of it vanishing – and nobody would notice when reading the file.
  • einheit : - means dimensionless. If the key is missing altogether, the dictionary says nothing about the unit (null versus "") – the two remain distinguishable.
  • Keywords are case-insensitive, values are not: a label stands as it was written; the group identifier likewise stays as it is.
  • art : case marks the column that names the cases; without a statement art : wert applies.
  • An unknown key aborts: overlooking it would be more convenient, but a typo in stelen : 4 would then silently mean that the precision does not apply – and a wrongly rounded number cannot be seen in the finished report.

Errors come as DictParseException with file, line number and line content; every entry remembers its line number so that a contradiction can name both lines involved. A missing dictionary entry, by contrast, is not an error: unassigned names keep their original spelling and are reported.

Cases and designs

A source (.src) describes how its file is to be read – nothing about the report. Every calculation state consists of cases; which column names them is decided by Fallspalte in four steps, in one place for all kinds of source:

  1. the statement casespalte, if present;
  2. a column marked art : case in the dictionary;
  3. the first column whose name cannot be assigned to any entry;
  4. failing that, the running row number.

Step 3 is the makeshift solution and is not taken if the dictionary is empty: then every column would be unknown and the first would become the case identifier although it is a measured value. Without a dictionary step 4 applies directly.

If a file contains several calculation states, Designaufteilung splits it by a design column: every distinct value becomes a calculation state of its own, with this value as label – so it is called that in [zuordnung Design A] and referenz : Design A. The cases are counted anew per calculation state, in the order in which the values first appear: if design B started at row 5, its design point would otherwise be "case 5", and a template written for two separate files would run into nothing with the same data in one piece. A case is numbered locally to its source and has no meaning across calculation states; CaseRef therefore carries the calculation state with it. The split is done after opening, the same for every kind; the values are copied and the whole source is closed.

How it is checked

  • Namensprobe (85 checks) and Verzeichnisprobe (140): spellings with the same key, minimum width, the locale trap, collisions with both names, dictionary errors with line number. The tests measure not only that valid cases get through but that invalid ones are rejected – with a message that says which line, column or name is meant.
  • Quellenprobe (89 checks) measures the case-column rule on the CSV path, Designaufteilungsprobe (35, 13 counter-experiments red) the design column, Anbieterprobe (10) the provider lookup.

Limits

  • The normalisation knows only the separators named and the digit groups; it does not recognise synonyms. Two quantities named differently are linked only by an alias in the dictionary.
  • The digit width is a single number for the whole dictionary; it should match the station nomenclature.
  • Case numbers count from 1 and are valid only within their calculation state.
