Damage in the video stream – background

The computation behind Bitfehler: how the slice start codes show, without decoding, where a decoder had to guess, and why this is the most delicate point of the chain for a verifiable restoration.

Why concealment is invisible

If a scratch on the disc destroys bits, every decoder fills the affected place with a guess – from the neighbouring blocks or the previous picture. The result looks like picture content. Neither a viewer nor any later processing can tell that it is guessed. Anyone presenting a restoration as verifiable must know where concealment took place. Bitfehler answers that without decoding the stream.

Slices and macroblock rows

An MPEG picture is divided into slices, on DVD one per row of macroblocks. A macroblock row is 16 picture lines high. The start code of a slice carries its row number in the last byte: 00 00 01 01 is the first row, 00 00 01 24 the thirty-sixth. A picture of height hh needs

R=⌈h16⌉rows, numbered without gaps 1,…,RR = \left\lceil \frac{h}{16} \right\rceil \quad\text{rows, numbered without gaps } 1,\dots,R

At 576 lines that is 36, at 480 lines 30. If a number is missing, a macroblock row is missing, and the decoder has to invent it. A missing row rr concerns picture lines 16(r−1)16(r-1) to 16r−116r-1; in general for rows vv to bb:

zfrom⁡=16(v−1),zto⁡=16b−1z_{\mathrm{from}} = 16\,(v-1), \qquad z_{\mathrm{to}} = 16\,b - 1

Pseudocode – Bitfehler

// input: an ELEMENTARY video stream
R ← max(1, (height + 15) div 16)                    rows of a frame
R½ ← max(1, ((height + 1) div 2 + 15) div 16)       rows of a field
pictures ← 0;  intact ← 0;  multiple ← 0;  fields ← 0
examine(d):
    seen ← empty;  duplicate ← 0;  inPicture ← false;  field ← false
    for each start code 00 00 01 cc:
        if cc = 00:                                      new picture
            if inPicture: evaluate(seen, duplicate, field)
            seen ← empty;  duplicate ← 0;  field ← false;  inPicture ← true;  pictures ← pictures + 1
        else if cc = B5 and inPicture and extension id = 8:     picture coding extension
            field ← (picture_structure = 1 or 2)
        else if 01 ≤ cc ≤ AF:                             slice
            if cc already in seen: duplicate ← duplicate + 1
            add cc to seen
    if inPicture: evaluate(seen, duplicate, field)

evaluate(seen, duplicate, field):
    n ← if field: R½ else R;   if field: fields ← fields + 1
    if seen empty: damage(rows 1..n, "kein einziger Slice — Bild verloren");  done
    for r ← 1 to n:  merge contiguous missing rows into one damage "Slices fehlen"
    if highest number > n: damage(n+1..highest, "Slice-Nummer über der erwarteten Bildhöhe")
    multiple ← multiple + duplicate                    several slices per row: allowed, no damage
    if no damage: intact ← intact + 1

intactShare ← intact / max(1, pictures)

Source: envisionz-framework-media/src/envisionz/media/ps/Bitfehler.java.

Convention in the framework: Contiguous gaps are merged into one damage, because one message per scratch is more useful than sixteen per missing row. The finding (level FALLE) names the number of damages and the share of affected pictures and recommends marking the places in the confidence picture as “replaced” and excluding them from fusion. The first twelve damages are listed, the rest is counted.
Convention in the framework: MPEG-2 allows several slices per macroblock row. A row number that starts again within the same picture is therefore no damage; it is only counted (mehrfacheSlices()) and named as a note in the finding. The class recognises field pictures by the picture coding extension (picture_structure 1 or 2); for them half the picture height applies, i.e. 18 instead of 36 rows at 576 lines. halbbilder() returns the number of fields.
Convention in the framework: The check belongs on the elementary stream. On a program stream it gives wrong results, because its PES headers contain byte sequences that look like start codes; only Elementarstrom makes it reliable.

How it is checked

The probe (Medienprobe, section “Bitfehler – fehlende Slices, und der heile Fall”) builds pictures from start codes laid out by hand and checks both directions: a stream with a gap reports the kind “Slices fehlen” and the right rows, a picture without any slice reports “kein einziger Slice”, numbers above the picture height are named – and an intact stream reports no damage. Two slices on the same row, and a stream in which every row is split into two slices, give no damage; the extra slice is counted and named in the finding. Fields with 18 rows (576 lines) are intact, a field without row 18 reports exactly that row, a frame with picture coding extension still needs 36 rows. After the elementary-stream extract of a program stream the result agrees (one damage, rows 15 to 16, second picture).

Limits

  • Only the slice start is visible. A bit error inside a slice that spares the start code is not found; the decoder conceals it all the same.
  • Codes 01 to AF count as slices; pictures taller than 175 rows are thus not covered.
  • The expected row count comes from the picture height given by the caller. Without a picture coding extension (MPEG-1) every picture counts as a frame.
  • Several slices on the same row always count as allowed; a slice that carries a wrong but already present row number because of a bit error therefore goes unnoticed.
  • The class says where concealment was necessary, not what originally stood there.
