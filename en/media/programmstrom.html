MPEG program stream and elementary stream – background

The computation behind Programmstrom and Elementarstrom: how a program stream is split at start codes, why MPEG-1 and MPEG-2 have to be read differently, and how the pure video stream is pulled out with a sliding window.

Packets and start codes

An MPEG program stream carries picture, sound and auxiliary data interleaved in a sequence of packets. Every packet begins with the start code 00 00 01; the fourth byte names the kind:

BytePacketNote
BAPack headerdifferent length in MPEG-1 and MPEG-2
BB, BESystem header, padding packetskipped
BFprivate 2on DVD the navigation packets
BDprivate 1AC-3, LPCM, DTS, subtitles; substream in the first payload byte
C0–DFMPEG audio
E0–EFVideo

After the start code come two bytes of packet length LL (most significant byte first); the packet ends at p+6+Lp + 6 + L. The substream of a private packet is in the first payload byte: 80–87 AC-3, 88–8F DTS, A0–A7 LPCM, 20–3F subtitles.

The navigation packets look like payload and lie in the middle of the stream. Passing them into the video stream produces breakage at exactly the places where the DVD has its jump marks.

Splitting, and the difference between MPEG-1 and MPEG-2

The pack header reveals the version in the upper two bits of the byte after the start code: 01 means MPEG-2 (header 14 bytes, plus 0–7 stuffing bytes whose number is in the lower three bits of the header), 0010 means MPEG-1 (header 12 bytes). Behind it the PES header of every packet differs as well:

  • MPEG-2: a byte with marker 10, a flags byte, then the header length in the third byte. The payload starts after 3+header length3 + \text{header length} bytes.
  • MPEG-1: any number of stuffing bytes FF, optionally a buffer marker (01 in the upper bits, two bytes), then optionally time stamps – recognisable only by the upper four bits: 0010 = five-byte presentation stamp, 0011 = ten bytes with decoding stamp, otherwise a single byte 0F.

An extractor that knows only MPEG-2 fails on a video CD. Programmstrom therefore evaluates both.

Pseudocode – Programmstrom.zerlege

p ← 0
while p + 4 ≤ length(data):
    if not 00 00 01 at p: p ← p + 1;  continue
    code ← data[p + 3]
    if code = BA:                                    pack header
        if upper 2 bits of data[p+4] = 01: mpeg2 ← true;  p ← p + 14;  p ← p + (data[p−1] and 7)
        else: p ← p + 12
        continue
    if code = B9: end                                  program end
    if code < BB: p ← p + 4;  continue
    L ← 16-bit length at p + 4;  end ← min(length(data), p + 6 + L)
    if code ∈ {BB, BE}: p ← end;  continue
    if mpeg2 and upper 2 bits of data[p+6] = 10:
        pts ← presentation stamp, if flag bit 7 set;  content ← p + 6 + 3 + header length
    else: skip FF, buffer marker, stamps by the upper 4 bits → content
    count packet and payload bytes per code
    if code = BF: count navigation packet
    if code = BD: count substream data[content]
    if code ∈ E0..EF: follow pts (first, last, jumps > 5 s);  search video headers in the payload
    p ← end

Source: envisionz-framework-media/src/envisionz/media/ps/Programmstrom.java. From the payload of video packets Videokopf reads the sequence header (B3), extensions (B5, identifiers 1 and 8) and the picture type (00).

Convention in the framework: The playing time is given as (last−first video stamp)/90000(\text{last} - \text{first video stamp}) / 90000 seconds, not estimated from the bit rate. A jump of the video stamps over 5⋅900005 \cdot 90000 ticks, i.e. five seconds, is reported as ACHTUNG; image fusion must not average across such a jump.

The pure video stream with a sliding window

Elementarstrom places the payloads of the video packets (E0–EF, or only a requested identifier) one after another. A title set of eighty minutes measures almost three gibibytes; a byte[] holds at most 2 GiB. So a window of 1 MiB slides over the stream.

Cutting is allowed only at packet borders. Unlike in an elementary stream, start codes also occur inside the payload here, because the payload is itself a video stream. A cut at the last start code found would hit the middle of a payload. The scanner therefore processes what is completely present and reports where the first incomplete packet begins; its beginning moves to the head of the next window.

Pseudocode – Elementarstrom.videoAus(ein, aus)

window ← buffer of 1 MiB;  fill ← 0
while not finished:
    fill window from fill on from the input;  if input empty: last ← true
    if fill = 0: end
    consumed ← section(window, fill, out, last)
    if last: end
    if consumed = 0:                      a packet larger than the window
        double the window;  continue
    move window[consumed .. fill] to the start;  fill ← fill − consumed

section: like split, but
    if the packet reaches beyond the window end and not last:  return p
    BB, BE: skip;  BF: count navigation packet, skip
    if video and requested: write payload from header end to out

Source: envisionz-framework-media/src/envisionz/media/ps/Elementarstrom.java. The header skipping is word for word the same as in Zeitmarken.nachDemKopf.

Convention in the framework: The packet length is a 16-bit value; a packet over 1 MiB is not foreseen in the stream. A damaged stream can claim it; without the doubling the scanner would stand still. A packet cut off in the last window is taken as it is and belongs in the finding.

How it is checked

Medienprobe lays out packets byte by byte itself; ps.Videokopfprobe checks the video header against ISO/IEC 11172-1 and 13818-1 and -2.

  • Elementarstrom: the extract is byte for byte the same stream as the source stream, exactly one navigation packet is skipped, and the extracts from byte[] and from the data stream agree.
  • Programmstrom: width 720, height 576 and frame rate 25 from the sequence header; variable bit rate and navigation packets are reported.
  • Window: the same method, cutting only at packet borders, is checked by ps.Tonauszugprobe with a stream of 3.1 MiB and with an MPEG-1 pack header that begins 8 bytes before the 1 MiB border; byte[] and data stream must deliver the same.

Limits

  • Programmstrom works on a byte[]; for long files Vobs and Elementarstrom with the window are intended.
  • Packets are only split, not decoded: the module says what is in the stream, not what the picture looks like.
  • The time axis rests on 33-bit time stamps at 90 kHz; an overflow is not handled, it would be reported as a jump.
