envisionz-app-report

Build reports from tables and export them as Word or PDF

Overview of the app, as of 29 September 2026. The app builds a report as a tree of a title, named nodes and embedded, editable tables. It saves the report as one XML file and exports it as an editable Word document or as a PDF. A second tab assembles an operating-point report from calculation results.

What the app is for

Results of calculations often end up in a Word document by hand: copy tables, add units, colour cells, set headings. With every new calculation it starts again. The app keeps the structure of a report as a template. It consists of a title, named sections and tables with row names, units and value columns. The template can be saved, loaded and output again and again.

The output is neither an image nor a rigid page. The Word document contains real headings that a table of contents can pick up, and real tables that can be edited further in Word.

What it can do

Report tree

The report is a tree: a root (the title), named nodes below it, and the tables inside the nodes. The tables are editable directly in the tree; one click into a cell is enough. The context menu adds, renames and removes nodes and moves them up or down. Renaming the report, saving, loading and exporting are in the menu of the root.

Structured tables

Each table has a vertical label on the left (the descriptor), rows with a name and a unit, any number of value columns and an optional header row. Row names can be merged into groups. Every cell carries its own formatting: bold, italic, text colour and background. Structure and cell format are set in dedicated editors.

Word export

The document is written as .docx in own code, without a third-party library: the title and node names become headings (levels 1 and 2), the descriptor becomes a vertical column merged over all rows, merged name groups become merged cells, and the header row becomes a repeating row. The format is A4 portrait with 2 cm margins. The export reads the values live from the tables in the user interface.

PDF export

The same report is written as a PDF through the framework's PDF writer. Nodes follow one another; a table whose header no longer fits on the page starts on the next one. Cell formatting (font style, text colour, background) is carried over. The PDF does not carry the vertical descriptor, which moves into the table heading, or merged cells, which appear with an empty name.

Operating-point report

The second tab builds a report of operating points from a template and result files. A vertical rail with six cards selects files, cases, calculation states and units. The result appears as a grid table: row headers on the left, groups that collapse on a click, empty cells shown as a dash. The unit of a row is distinguishable as named, deliberately dimensionless (-) or unknown (?, cell in italics). The build runs in the background, and errors appear in the status line. The template can be loaded and saved, and the report goes to Word or PDF.

Workspace state

Closing and reopening the workspace keeps the whole report tree, together with the selection in the operating-point report (template, file, selection, units).

Data and formats

  • Report file: one XML file with the title, nodes, table structure and cell formats. When reading, a DOCTYPE declaration is rejected, and a broken document is reported rather than thrown.
  • Word: .docx, editable, with heading styles.
  • PDF: output of the report only, no reading.
  • Operating-point report: reads a template and result files that are described in the framework module for report tables.

What it builds on

  • reporttable: the grid of the operating-point report, with units and calculation states. The app turns the grid into a report and writes it out.
  • pdf: the PDF writer for the PDF output.
  • api: the app interface, registration through the ServiceLoader and the workspace state.
  • data: events and data access of the framework; the connection to the table events of other apps is not made yet (see limits).
  • swing: user interface, side rail, background runner and icons.

The report core (tree, tables, XML, Word) is self-contained: it needs only the JDK and imports nothing from the framework. Only the thin adapter to the host knows the framework.

State and limits

  • Reports can be built, filled in the user interface, saved as XML and exported as Word or PDF. The operating-point report works with a template, files and both output paths.
  • The values of the report tree are entered by hand. A connection to the tables of other apps through the framework's event channel is still missing.
  • Two-line column headers of the operating-point report appear in Word and PDF on one line, the two parts joined by a middle dot. Rows with the same label are not merged automatically.
  • The PDF has no vertical descriptor and no merged cells.
  • There is no help page yet; the hints are in the toolbar.
