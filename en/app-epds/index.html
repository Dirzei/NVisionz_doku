envisionz-app-epds

Read, compare and merge result folders of engine simulation runs

Overview of the app, as of 29 September 2026. The app scans the result folders of EPDS runs, shows each run in detail, compares all runs with one another, merges the results of the converged runs into one table and hands it on to the charts app.

14Java source files
7result files per run that are read
196checks in 7 test programs
3help pages, German and English
5framework modules underneath, plus app-charts

What the app is for

An engine design study with EPDS produces many runs, often dozens to hundreds, each in a folder of its own with several result files: cycle calculation, weights, turbine cooling, fan, design point, geometry. What matters is the comparison across runs: how do the characteristic values change when one input is varied, and which runs converged at all?

The app takes these folders and turns them into one table with one row per run. From there the data goes into charts, into an H2 database or into the map app. It replaces a tool of the 2020 predecessor program and removes its weaknesses: shifted columns when files are missing, error values instead of empty cells, and a fixed folder layout.

What it can do

Reading folders

One folder is enough, at whatever level.

  • You may pick the project folder containing FullOutput, that folder itself, or a single multirun_* or singlerun_* folder.
  • A run counts as converged if its marker file is present; only such runs enter the analysis. The results of an aborted run are numbers without meaning.
  • Problems while reading are collected as warnings rather than treated as an abort.
  • Files in UTF-8 or Windows-1252 are read; characters such as ° and µ do not abort the import.

One run in detail

Tree on the left, cards on the right.

  • At the top the meridional-cut geometry, true to scale (the same unit per pixel on both axes), below it tabs for cycle, weights, design point, fan information, input file and overrides.
  • A run that did not converge shows only an empty "invalid" card; no details are loaded.

Comparison across all runs

The import node shows overview tables: quantities in the rows, runs in the columns.

  • Tabs for design points, weights, outputs, geometry and data.
  • The rows are the union of all quantities that occur. A quantity missing in one run appears there as an empty cell; nothing moves up. An intersection would have let quantities disappear silently.

Merging and passing on

The "Main Data" node is the central place for charts.

  • The merged table has one row per converged run; columns are named NAME(i) per station. Unreadable values (NaN, #NAME?) become empty cells.
  • The "Diagrams" tab embeds the chart interface of app-charts: the same roles, the types 1D, 2D and 3D, and the same options as there.
  • Buttons: "Hand over to charts", "Hand over to maps" (the runs as an operating line in the map tool) and "Save as H2".
  • The physical quantity of a column is preset from its name; the unit is deliberately left empty and set in the chart dialog.

Cache

What has been read is not read again.

  • A fingerprint is formed from file size and modification time of all files involved. If it matches, the overview comes from an H2 file, and the status line says so.
  • If only new runs are added at the end of the import, only those are read; any other change rebuilds everything.
  • A damaged cache is reported and rebuilt; the cache is never the source.
  • Runs are read in parallel, and the result is always in run order.

Data and formats

  • Reads: result folders with the cycle calculation (EngineCycle.dat), weights (EN52Output.csv), cooling (CF_RRD_output.csv), fan (ReynoldsCorrection.csv), design point (MarsCaseSetInput.dat), geometry (EPDS_Active.kasm) and Overrides.csv.
  • Writes: an H2 database with the table EPDS_<folder name>; the cache file lives in the program folder.
  • Session: the scanned root folders are remembered and read again at start.

What it builds on

  • framework-api: registration as an app, session, events for changing focus.
  • framework-core: the program folder used for the cache.
  • framework-data: loaded tables, H2 store, quantity kinds, the "table available" event.
  • framework-swing: background runner and cards.
  • framework-chart and app-charts: the embedded chart interface. This is the only app-on-app dependency in the workspace, decided that way by the owner.

State and limits

Finished are reading, single runs, comparison, merging, the geometry view, hand-over to charts and maps, H2 export, the cache with appending of new runs, and three help pages in both languages.

Testing runs headless on generated result folders in which every fourth run has not converged, some files are missing and some are written in Windows-1252. Seven test programs with 196 checks cover scan, runs, overview, geometry, cache, registration and interface.

Limits: The file formats are derived from the predecessor program and from generated folders. A temperature-entropy diagram and the definition of geometry lines are postponed. The app reads and arranges; it does not recalculate.
