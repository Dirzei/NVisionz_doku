Text, tokeniser, language model – training examples for commands from templates

The computation behind IntentDataGenerator: templates with slots, the chain of variations with their probabilities, protection of the inserted values from synonym replacement, four kinds of typos, uniqueness, and splitting by template instead of by example – with pseudocode following the source, examples generated with the module, the probes and the limits.

What this is about

A model that understands commands to an application of one's own – "load compressor map 3", "show me the turbine" – needs thousands of labelled example sentences: text, intent and the extracted values. For the commands of one's own application no ready corpus exists. Written by hand there would be too few, and they would be uniform, because one unconsciously reuses the same turns of phrase.

The generator therefore multiplies a manageable number of templates – about 50 to 100 – by systematic variation: values for slots, synonyms, politeness forms, filler words, capitalisation, punctuation and deliberate typos. It invents nothing: whoever writes ten templates and generates ten thousand examples has ten phrasings a thousand times.

Templates and slots

A template is a line "intent | pattern text", the pattern contains slots in curly braces (the examples are German, as is the generator):

KENNFELD_LADEN | Lade das {komponente} Kennfeld {index}
KENNFELD_LADEN | Zeig mir Kennfeld {index}

For each slot, slot(name, values…) gives the possible values; synonym(word, alternatives…) words that may be replaced in the finished sentence; prefix(…) and suffix(…) filler words for beginning and end. readTemplates reads templates from a text file and skips empty lines and lines starting with #; a line without the separator bar throws.

The chain of variations

  1. Fill slots. Every slot gets a random value from its list; the value is recorded in the label (slots). A slot without values throws.
  2. Replace synonyms – word-wise, i.e. only if no letter adjoins on the left or right ("Kennfeld" does not hit "Kennfeldern"), and not at positions belonging to an inserted value. Per synonym group one alternative is drawn (the original word included).
  3. Filler in front ("Bitte ", "Kannst du "): the start of the sentence is then lower-cased – unless the second character is already upper case, because then it is an abbreviation like "FNPR".
  4. Suffix at the end (" bitte", " danke").
  5. Punctuation with probability 1−0.301 - 0.30: a question mark if the sentence starts with "Kannst", "Koennt", "Wie" or "Was", otherwise a full stop.
  6. Lower case for the whole sentence.
  7. Typo at a position i∈[1,n−2]i \in [1, n-2] (never at the first or last character, only with at least four characters), with equal frequency one of four kinds: swapping two neighbouring characters, omission, doubling, neighbouring key on a QWERTZ keyboard (keeping upper case).

Typos are included on purpose. A model that has only seen error-free input fails on the first mistyped one; the byte-level tokeniser carries typos without trouble (see Byte pair encoding), and the model only has to learn to read past them.

Pseudocode – IntentDataGenerator.generate(templates, perTemplate)

out ← [];  seen ← {}
for each template t:
    made ← 0;  attempts ← 0
    while made < perTemplate and attempts < 30 · perTemplate:
        attempts += 1
        s ← oneExample(t)
        if (intent, text) of s not in seen:  add;  out += s;  made += 1
return out

oneExample(t):
    text ← t.pattern;  slots ← {}
    while text contains "{name}":  w ← random value(name);  slots[name] ← w;  replace
    for each synonym group (word → all):  e ← random(all)
        if e ≠ word: replace word word-wise by e, except within slot value ranges
    with P = 0.25: text ← filler + decapitalise(text)
    with P = 0.15: text ← text + suffix
    with P = 0.70: text ← text + ("?" for a question start, else ".")
    with P = 0.20: text ← lower(text)
    with P = 0.12: text ← typo(text)
    return Sample(trim(text), t.intent, slots)

Source: envisionz-framework-autograd/src/envisionz/autograd/text/IntentDataGenerator.java, methods generate, einBeispiel, ersetzeWortAusserhalb, entkapitalisiere, tippfehler. Every stage draws from the same generator created with the seed; same seed, same examples.

Decision in the framework: the inserted slot values are protected from synonym replacement. According to the module documentation replacement first also hit them – the value "Kennfeld" became "Kennlinienfeld" in the text, and label and text no longer matched. The fault showed neither during generation nor during training, only when inspecting the output by eye; since then there is a check for it. Default rates: typo 0.12, filler 0.25, suffix 0.15, lower case 0.20, missing punctuation 0.30.

Splitting by template

Evaluating a model needs examples it has not seen in training. If the examples were split, variants of the same template would end up on both sides: what would be measured is whether the model reads past typos and filler words, not whether it understands new phrasings. The evaluation would be worthlessly flattering – 99 % hits that mean nothing. generateSplit therefore splits the templates and generates each subset anew from its own templates; after generation an example no longer shows which template it came from.

check shareTrain > 0, shareValid ≥ 0, shareTrain + shareValid < 1
mixed ← templates, shuffled with Random(splitSeed)
nT ← round(n · shareTrain);   nT ← max(1, min(nT, n − 2))
nV ← round(n · shareValid);   nV ← max(1, min(nV, n − nT − 1))
return [ generate(mixed[0 … nT)), generate(mixed[nT … nT+nV)), generate(mixed[nT+nV … n)) ]

Each subset thus gets at least one template. With few templates per intent an intent can nevertheless end up entirely in one subset; missingIntents(parts) names the intents that do not occur in all three parts. writeSamples writes the examples as a tab-separated file (intent, text, slots as name=value separated by commas) with a header line.

Worked examples

Generated with the module. Seed 1, template "KENNFELD_LADEN | Lade das {komponente} Kennfeld {index}", values Verdichter/Turbine and 1/2/3, synonyms "Lade" → "Öffne", "Zeige", fillers "Bitte ", "Kannst du ", suffixes " bitte", " danke", twelve examples requested – twelve unique ones result, among them:

  • "Zeige das Verdichter Kennfeld 3" – synonym, no punctuation, slots komponente=Verdichter, index=3;
  • "Kannst du lade das Verdichter Kennfeld 1?" – filler with lower-case sentence start and question mark;
  • "zeige das turbine kennfeld 2." – all lower case, with full stop; the label keeps "Turbine".

One also sees what the generator cannot do: "Kannst du lade …" is grammatically skewed. Templates and fillers must fit together; the generator does not check grammar.

Split. Ten templates with shares 0.8 and 0.1: eight for training, one for evaluation, one for test. Five templates with the same shares: round⁡(4)=4\mathrm{round}(4) = 4 is limited to 5−2=35 - 2 = 3, then one for evaluation and one for test.

How often what happens. With the defaults about every eighth example carries a typo, every fifth is entirely lower case, and three in ten end without punctuation.

Why tolerance 2. The Levenshtein distance counts insertion, deletion and substitution of one character each; it has no transposition. The swap at position 2 turns "Verdichter" into "Vredichter". Undoing that takes two substitutions (r → e, e → r), so the distance is 2. Omission ("Vrdichter"), doubling ("Veerdichter") and neighbouring key ("Vetdichter"), by contrast, have distance 1. A tolerance of 1 would have reported every swap inside a slot value as a label error although the label is correct.

How it is checked

  • GeneratorTest (14 checks): no duplicates; yield at least 55 % of what was requested (short templates without slots simply do not have enough variants – the generator then delivers fewer instead of repeating itself); every slot value occurs in the text, compared tolerantly; strict: every slot value appears literally in the text unless a typo changed it (tolerance Levenshtein distance 2, because a swap counts as two changes); all five intents present; punctuation and capitalisation vary; vocabulary wider than 60 forms; no text in both training and test; the check for missing intents runs; all examples round-trip losslessly through the tokeniser and are at most 64 tokens long; template file read, example file written.
  • According to the module documentation a first tolerance of one character reported intended swaps as label errors – a false alarm that would have masked the real finding.

Limits

  • Multiplying, not inventing. Coverage depends entirely on the variety of the templates.
  • Typos and lower case may also change slot values in the text; the label keeps the original value. A model that is to extract values must learn this deviation.
  • Synonyms are replaced case-sensitively and only as whole words; the neighbouring keys know only lower-case letters a–z (no umlauts as starting key).
  • Questions are recognised only at four fixed sentence starts; the generator is tailored to German.
  • If the number of possible variants is small, a template falls short of the requested number after 30⋅30\cdotperTemplate attempts.
