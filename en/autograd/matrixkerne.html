Single-precision matrix kernels and Vector API – blocking, kernel selection and vector loops

The computation behind FloatKernels, Kernels and VectorKernel: why the loop order i, k, j makes the result independent of blocking and vector width, how the kernel is selected, how the vector loops handle the tail, and why the four-column version without fma stays bit-identical – with pseudocode following the source, measurements, the probes and the limits.

What this is about

The autograd core computes in double. The gradient check needs that (see Gradient check), and so do the bit-exact comparisons between serial and parallel computation (see Matrix product). For a training run, however, double precision is ballast: double moves twice as many bytes as float, and for matrix products of this size memory is often the bottleneck.

The package envisionz.autograd.fast therefore offers a second computational path in float. It is connected at exactly one place: the forward step of Ops.matmul, when the switch Ops.schnellesMatmul is set (default off) and the amount of work batch⋅M⋅K⋅N\text{batch}\cdot M\cdot K\cdot N is at least Ops.schnellesMatmulAb = 1,000,000. The backward pass always stays in double.

Precision of float

float has a 24-bit mantissa; the unit roundoff is u=2−24≈6⋅10−8u = 2^{-24} \approx 6\cdot 10^{-8} – about seven decimal digits instead of sixteen. A sum of KK products accumulates rounding errors; with random signs the error typically grows like K\sqrt{K}, in the worst case like KK. The probe KernelTest therefore measures the largest distance to the double computation, relative to the typical size of the result values (their root mean square), and requires

maxij⁡|cij−c˜ij|rms⁡(c)<6⋅10−8⋅K⋅40.\frac{\max_{ij} |c_{ij} - \tilde{c}_{ij}|}{\operatorname{rms}(c)} < 6\cdot 10^{-8}\cdot\sqrt{K}\cdot 40.

The factor 40 is headroom. Measured was about 2.1⋅10−62.1\cdot 10^{-6} at 100×128×512 (bound 2.7⋅10−52.7\cdot 10^{-5}).

Why relative to the size of the result and not to each entry: a product of normally distributed numbers has entries close to zero. There the denominator of a per-entry error is tiny, and what comes out as relative error is cancellation at a single entry. According to the module documentation such a comparison once gave 1.7·10−4 per entry – but 5·10−8 relative to the size of the result, i.e. within float.

Blocking and loop order

For C←C+ABC \leftarrow C + A B with A∈RM×KA \in \mathbb{R}^{M\times K}, B∈RK×NB \in \mathbb{R}^{K\times N}, all stored row by row, FloatKernels.matmul runs in the order i, k, j with j innermost. Only then are BB and CC both contiguous in the innermost pass while aika_{ik} stays fixed. The usual order i, j, k would have a stride of NN elements through BB innermost.

Above that lie three block loops with the adjustable block sizes blockM = 64, blockK = 128 and blockN = 256. A block of BB thus covers 128⋅256⋅4128 \cdot 256 \cdot 4 bytes = 128 KiB, a block of AA 32 KiB and one of CC 64 KiB. The aim is to use a section of BB once loaded for several rows of AA before it is evicted from the cache.

Pseudocode – FloatKernels.matmul(a, b, c, M, K, N)

for i0 = 0, 64, … < M:
    for k0 = 0, 128, … < K:
        for j0 = 0, 256, … < N:
            for i = i0 … min(i0+64, M) − 1:
                for k = k0 … min(k0+128, K) − 1:
                    av ← a[i, k];  if av = 0:  continue
                    for j = j0 … min(j0+256, N) − 1:
                        c[i, j] ← c[i, j] + av · b[k, j]

Source: envisionz-framework-autograd/src/envisionz/autograd/fast/FloatKernels.java. The kernels add to c and do not overwrite it.

One consequence of this order matters for testing: every entry cijc_{ij} receives its terms aikbkja_{ik} b_{kj} in ascending kk, however the blocks are cut. Since Java does not contract multiplication and addition into an fma on its own, the naive, the blocked and the vectorised kernel are bit-identical for matmul. The Schnellpfadprobe measures that: blocked against naive 0.0 for five shapes, among them 65×129×257.

For C←C+ABTC \leftarrow C + A B^{\mathsf T} with BTB^{\mathsf T} stored as [N,K][N, K] – the shape of QKTQ K^{\mathsf T} in attention – matmulNT computes per entry a dot product of two contiguous rows and adds it. The transpose is avoided.

Kernel selection

The interface MatmulKernel has name(), priority(), isAvailable() (default true), matmul and matmulNT. The built-in BlockedKernel calls FloatKernels and has priority 0 so that any extension overtakes it.

Pseudocode – Kernels.waehle()

all ← [BlockedKernel]
try:
    for each implementation k found by the ServiceLoader:
        if k is not a BlockedKernel:  all ← all + [k]
catch Throwable:  print a note                      core stays usable
best ← all[0]
for each k in all:
    avail ← k.isAvailable()  (a Throwable counts as unavailable)
    if avail and k.priority() > best.priority():  best ← k
return best

Source: envisionz-framework-autograd/src/envisionz/autograd/fast/Kernels.java. The choice is made on the first call of kernel(); setKernel(k) overrides it, setKernel(null) restores the automatic choice.

Decision in the framework: the Vector API is an incubator module in OpenJDK and requires --add-modules jdk.incubator.vector at compile time and at start-up. The core is not to carry that dependency. The vector kernel therefore lives in the separate project envisionz-framework-autograd-vector and is registered via META-INF/services. If the project or the module is missing, the ServiceLoader finds nothing and the built-in kernel runs. The fast path stays off until someone switches it on: a switch that turns itself on would make the gradient check and the bit-exact comparisons useless.

The vector kernel

VectorKernel takes the machine's preferred vector width (FloatVector.SPECIES_PREFERRED): 16 floats with 512-bit registers, 8 with 256 bits. It reports priority 100 and is available when the width is greater than 1. Its name states the width, for example "Vector API (8 float)", because a speed-up factor cannot be placed without the width.

matmul: vector over j, scalar tail

The order is i, k, j as in the built-in kernel, but without blocking. The innermost loop runs in steps of the vector width WW up to ⌊N/W⌋⋅W\lfloor N/W \rfloor \cdot W (loopBound), the at most W−1W-1 remaining columns as scalars.

A masked tail instead of the scalar loop was measured and not adopted: it gained 6 to 16 % for shapes with a tail, but also 1 to 7 % at 256×256×256, where there is no tail and both paths do the same computation. The gain was thus within what the order of measurement alone accounts for.

matmulNT: four output columns at once

In the dot product a vector loaded from AA is used for four rows of BTB^{\mathsf T} instead of one. Each of the four columns has its own vector accumulator:

W ← vector width;  G ← ⌊K / W⌋ · W
for i = 0 … M−1:
    j ← 0
    while j + 3 < N:                                       four columns
        s0, s1, s2, s3 ← zero vectors
        for k = 0, W, … < G:
            va ← a[i, k … k+W)
            sq ← sq + va · bT[j+q, k … k+W)    for q = 0 … 3     mul, then add
        rq ← sum of the lanes of sq
        for k = G … K−1:  rq ← rq + a[i, k] · bT[j+q, k]
        c[i, j+q] ← c[i, j+q] + rq;  j ← j + 4
    for the remaining up to three columns:  the same computation with one accumulator

Source: envisionz-framework-autograd-vector/src/envisionz/autograd/fast/vector/VectorKernel.java.

Every column sums in the same order as in the single-column version: vector part, lane reduction, scalar tail. The result is therefore bit-identical to the single-column version. An fma rounds only once after multiplication and addition instead of twice; it would have broken this bit identity, and on the target machine it gave 0.76 to 1.01 times the speed on its own, i.e. no gain. Implemented are four columns without fma. Compared with FloatKernels.matmulNT, however, the result is not bit-identical: there the values are added one after another, here first per lane.

Measurements

All factors are single-threaded and depend on the machine; without the vector width they cannot be placed. According to the module documentation, measured in the build environment with 512-bit registers (16 floats), against the double path:

Shape M×K×Ndoubleblocked floatVector API
256×256×25611.07 ms1.13×5.17×
512×512×51287.51 ms1.06×4.19×
100×128×5124.52 ms1.09×5.02×

Blocking alone buys almost nothing; the gain comes from explicit vectorisation. 128×128×128 is too short at about 1.6 ms for a reliable measurement and swung between 0.5× and 6.3×. A new run of KernelTest in the build environment for this page gave 7.3×, 5.5× and 5.9× for the Vector API and 1.9×, 1.4× and 1.5× for the blocked kernel – the same order of magnitude, but clearly different individual values.

On the target machine with 256-bit registers (8 floats) the vector width is half as large; the module documentation expects a factor of 2 to 3 there instead of 4 to 5. What was measured there is the four-column version of matmulNT: per shape alternating in 41 pairs after warm-up, median, two runs, for shapes from 128×64×128 to 512×512×512. Four columns alone gave 1.44 to 1.79 times the speed of the single-column version.

Worked examples

Vector loop. With N=20N = 20 and W=8W = 8, loopBound is 16: two full vectors, then four values one by one (figure). With W=16W = 16 it is also 16: one vector, then four values. With N=7N = 7 and W=8W = 8 everything runs as scalars.

Threshold. The product QKTQ K^{\mathsf T} of one head with 25 positions and head width 64 has 25⋅64⋅25=40,00025 \cdot 64 \cdot 25 = 40{,}000 multiplications and stays far below the threshold of 1,000,000. A weight matrix [256,1024][256, 1024] applied to a batch [8,128,256][8, 128, 256] comes to 8⋅128⋅256⋅1024≈2.7⋅1088 \cdot 128 \cdot 256 \cdot 1024 \approx 2.7\cdot 10^{8} and takes the fast path if it is switched on. The threshold is higher than the parallel threshold of 250,000 because all three matrices are additionally converted to float and back.

Error bound. With K=128K = 128 the bound of KernelTest is 6⋅10−8⋅128⋅40≈2.7⋅10−56\cdot 10^{-8}\cdot\sqrt{128}\cdot 40 \approx 2.7\cdot 10^{-5}. The Schnellpfadprobe measured 2.3·10−7 to 2.6·10−7 between the fast and the slow path of Ops.matmul at K=40K = 40 and 70.

How it is checked

  • KernelTest (in the source tree): every available kernel against a double reference at 1×1×1, 3×5×7, 64×64×64, 100×128×512 and 257×33×129, matmulNT at 64×96×48, and that the kernel adds to c. Without the vector project 7 checks, with it 13. Plus a measuring part without verdict.
  • Schnellpfadprobe, 29 checks: selection (priority, setKernel, reset), accumulation, blocked against naive, matmulNT against matmul with a hand-transposed BB, every kernel against the built-in one, 16 edge shapes with no full vector, exactly one and one plus tail, the fast against the slow path of Ops.matmul for three shapes (tolerance 10−510^{-5}, and explicitly not bit-identical), a bit-identical double result below the threshold, and the backward pass against a closed formula at double precision. Comparisons of two float paths use the tolerance 2⋅10−52\cdot 10^{-5}, relative to the size of the result.
  • Kernprobe in the vector project, 44 checks: design (name states the width, priority 100 against 0, width a power of two, available exactly when more than one float), 10 shapes of matmul and 6 shapes of matmulNT against the built-in kernel, accumulation and zero matrices, and the four-column version bit-identical to the single-column one at 1, 2, 3, 4, 5, 7, 8, 9 and 31 columns. According to the module documentation six deliberately planted faults are caught, among them fma instead of mul+add, the wrong row of BTB^{\mathsf T} and = instead of +=.

Limits

  • Only the forward step of Ops.matmul is connected. matmulNT is not used by production code; attention still transposes.
  • The fast path makes one kernel call per batch entry on one thread. The double path, by contrast, spreads the rows over all cores above the parallel threshold. On a machine with many cores the gain from vectorisation can therefore be partly eaten up; this has not been measured.
  • For every call AA and BB are copied completely to float and the result back to double.
  • The Vector API remains an incubator module; --add-modules jdk.incubator.vector is needed at compile time and at start-up. Whether the vector path takes effect in a native image, and which switches it needs, is according to the module documentation still to be checked on the target machine.
  • float is not suitable for the gradient check or for bit-exact comparisons; both stay on the double path.
