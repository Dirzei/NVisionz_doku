Optimiser and weight storage – weight file, provenance and checkpoint

The computation behind WeightIO and Checkpoint: the layout of the weight file byte by byte, the FNV-1a checksum, the order of checks when loading, the provenance record for later merging of models, and the optimiser state file – with pseudocode following the source, recounted file sizes, the probes and the limits.

What this is about

A trained model is an ordered list of number arrays. To store it, writing out the numbers is not enough. On loading it must be certain that the file fits exactly this model – same number of tensors, same shapes –, that it is undamaged, and that after loading bit for bit the same values are in the parameters. Only then can an interrupted and resumed training run be compared with an uninterrupted one, and only then is a shipped model the same as the tested one.

Two further things are needed only later and cannot be added afterwards: where a weight state comes from (for merging models) and the optimiser's state (for resuming).

Layout of the weight file

The format is flat and little-endian throughout. The tensors appear in the order of Module.parameters() (see Building blocks).

The file size is thus

8+4+4+P+4+∑i=1nT(4+4ri)+8N+8bytes.8 + 4 + 4 + P + 4 + \sum_{i=1}^{n_T} (4 + 4 r_i) + 8N + 8 \ \text{bytes}.

Decision in the framework: values are stored as double, not as float. The file is therefore twice as large (8 instead of 4 MB for 10610^6 parameters), but saving and loading is bit-exact – the precondition for comparing a resumed run with an uninterrupted one at all. The class description of WeightIO still shows the layout of version 1 without the two provenance fields; version 2 is written as in the table.

The FNV-1a checksum

FNV-1a (Fowler, Noll, Vo) is a simple, fast hash function over bytes. With 64 bits it starts at the offset basis h0h_0 and processes every byte bb with an exclusive or and a multiplication modulo 2642^{64}:

h0=cbf29ce48422232516,h←(h⊕b)⋅100000001b316mod264.h_0 = \mathtt{cbf29ce484222325}_{16}, \qquad h \leftarrow (h \oplus b) \cdot \mathtt{100000001b3}_{16} \bmod 2^{64}.

A single flipped bit changes hh for certain, because ⊕\oplus with a different byte and multiplication by the odd prime are each invertible; over many bytes the change spreads to all digits. FNV does not protect against deliberate modification – that is not its purpose. What it is after are aborted writes and damaged files.

h ← 0xcbf29ce484222325
for each byte b in the value range:
    h ← h xor (b and 0xFF)
    h ← h · 0x100000001b3                 64-bit multiplication with overflow
return h

Source: envisionz-framework-autograd/src/envisionz/autograd/WeightIO.java, method fnv; Checkpoint uses the same function for the state file.

Writing and loading

Writing first puts the whole header into a buffer, writes it, and then streams the values through a buffer of at most 1 MiB; every time the buffer is flushed, the checksum is continued over its content. The 8 bytes of the checksum follow at the end. The file is re-created with TRUNCATE_EXISTING.

Loading checks in a fixed order before anything is changed – a half-loaded model is worse than one that was not loaded at all:

Pseudocode – WeightIO.load(path, params)

open file;  map it in an arena (read only)
header ← parseHeader:
    check length ≥ 16, magic = EVZAGW01, 1 ≤ version ≤ 2
    if version ≥ 2: read P (check 0 ≤ P ≤ 1 MiB), read provenance
    read n_T (check 0 ≤ n_T ≤ 1,000,000)
    for each tensor: rank (check 1 ≤ r ≤ 8), axis lengths
check n_T = |params|                           otherwise: a different model
check shape of each tensor = shape of the parameter
check remaining length = 8·N + 8               truncated file
check FNV-1a(value range) = stored sum          damaged file
only now: copy all values in order into params[i].data
close arena                                       releases the mapping at once

Source: envisionz-framework-autograd/src/envisionz/autograd/WeightIO.java, methods save, load, readHeader, parseHeader, abbilden.

Decision in the framework: reading uses a file mapping – it saves the copy step and works in native-image without extra runtime support. The mapping is created in a confined java.lang.foreign.Arena, whose closing releases it deterministically. An ordinary mapping would keep the file locked on Windows until the buffer is garbage-collected, and the sequence "write checkpoint, load, continue, write again" failed when reopening with TRUNCATE_EXISTING.

Provenance

From version 2 on every file carries a Provenance with five fields: model id, id of the ancestor (empty for a run from scratch), architecture (for example "enc:MODERN,L4,d128,h4,ff256"), step count and a note. It is stored as text with the separator U+001F, so that it stays readable in an editor if something goes wrong.

The reason is the later merging of models. Two networks trained independently from scratch cannot be averaged: every permutation of the neurons of a layer (with a matching permutation of the next) gives the same network, so the weights of two runs live in different coordinate systems, and their mean is noise. Only models that started from the same state can be combined via task vectors – the difference to the common ancestor. This record must exist before the first real run; afterwards the ancestor cannot be reconstructed.

sharesAncestorWith(o) is true if both have an ancestor recorded and either the ancestors are equal or one state is the ancestor of the other. Without a recorded ancestor nothing is faked.

Checkpoint: two files

Checkpoint.save writes two files side by side: name.evzw (the weights, format as above) and name.evzo (the optimiser state). The weights are the result and are passed on and compared; the optimiser state is about twice as large, is of interest only to a resuming run, and would be ballast when shipping.

Field of the state fileSize
magic EVZAGO018 bytes
version (1), step count tt, group count GG4 bytes each
length of each group4G4G bytes
all first moments mm, then all second moments vv2⋅8N2\cdot 8N bytes
FNV-1a over mm and vv8 bytes
Decision in the framework: the weights are written first. If the process aborts afterwards, the model survives and only resumability is lost – the less bad half. On loading a missing state file is not an error (a model that has been passed on has none; Loaded.optimizerRestored() reports it); an existing but unsuitable one throws, because if ignored silently the run would quietly start estimating from scratch. The path of the state file is formed by replacing the extension of the weight file with .evzo.

Worked example: file sizes

A layer Linear(2, 3) has two tensors, [2,3][2, 3] and [3][3], together N=9N = 9 values.

  • Without provenance the five empty fields with step count 0 are encoded as "␟␟␟0␟", P=5P = 5: 8+4+4+5+4+(4+8)+(4+4)+72+8=1258+4+4+5+4+(4+8)+(4+4)+72+8 = 125 bytes.
  • With provenance "tiny-01", no ancestor, "d64-L2", 120 steps, "Probelauf": P=7+1+0+1+6+1+3+1+9=29P = 7+1+0+1+6+1+3+1+9 = 29, file 125−5+29=149125 - 5 + 29 = 149 bytes (figure).
  • State file for it: 8+4+4+4+4⋅2+2⋅8⋅9+8=1808 + 4 + 4 + 4 + 4\cdot 2 + 2\cdot 8\cdot 9 + 8 = 180 bytes.

All three sizes were measured with the module's classes. For a model with one million parameters that is about 8 MB of weights and 16 MB of optimiser state.

How it is checked

  • EncoderTest: header read, parameter count correct; round trip save and load bit-exact; a different shape is rejected; a file with a single flipped bit is caught by the checksum.
  • ModernTest: provenance is written and read; without a record it stays empty; a common ancestor is recognised, a missing one is not faked; the values stay bit-exact despite the provenance field.
  • TrainerTest: two files written; provenance and optimiser state read; weights and state bit-exact; a missing state file is reported, not thrown; an unsuitable state is rejected.
  • Gewichtsdateiprobe (6 checks): write, read – with the built-in counter-check that reading really happened –, write the same file again afterwards, also after readHeader; the file can be deleted (a held file could not be removed on Windows); the round trip stays bit-exact.

Limits

  • The value range is addressed internally with int offsets: at most just under 2 GiB of values, i.e. about 268 million parameters per file.
  • The checksum covers only the values. Header and provenance are checked via plausibility limits, shapes and length, but not via a checksum; a damaged character in the note goes unnoticed.
  • FNV-1a detects damage, not manipulation.
  • No names: assignment works by order and shapes alone. Two models of equal shape but with the registration of two equally sized tensors swapped would load into each other.
  • The state file is still read via an ordinary file mapping, not via the arena; on Windows it may therefore stay locked for a while after loading.
