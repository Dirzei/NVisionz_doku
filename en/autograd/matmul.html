Matrix product – three forms, backward path and distribution over the cores

The computation behind Ops.matmul: definition for single matrices, batches with a shared matrix and batch times batch, the gradients with respect to both factors, the loop order, the distribution over all cores without races and with the same summation order as the serial run, and the optional forward step in single precision – with pseudocode following the source, figures for the thresholds, the probes and the limits.

What this is about

In a transformer almost all of the computing time goes into the matrix product: every linear layer is one, attention consists of two more per head, and the backward pass needs another two for each product. How the loops are arranged, whether memory is read contiguously and whether several cores take part decides between hours and days of training.

At the same time the matrix product is where parallelisation most easily goes wrong: on the way back many rows write into the same row of a gradient. A race there does not crash – it only occasionally corrupts a gradient, and the model learns a little worse.

Definition and the three forms

Ops.matmul(a, b) multiplies over the last two axes. aa has the shape […,M,K][\dots, M, K]; all axes before that together form a batch of size SS. Two cases are allowed for bb:

Shape of aShape of bResultUse
[M,K][M, K][K,N][K, N][M,N][M, N]a vector or a sequence through a layer
[…,M,K][\dots, M, K][K,N][K, N] – shared[…,M,N][\dots, M, N]the same weight matrix for all batch entries
[…,M,K][\dots, M, K][…,K,N][\dots, K, N], equal batch axes[…,M,N][\dots, M, N]attention: QKTQK^T and weights times VV per head

With the batch index ss the product is

Cs,m,n=∑k=0K−1As,m,kB(s),k,n,C_{s,m,n} = \sum_{k=0}^{K-1} A_{s,m,k}\, B_{(s),k,n},

where B(s)B_{(s)} is the same for all ss in the shared case. If the inner axes, the rank or a batch axis do not match, the operation throws.

The gradients with respect to both factors

With G=gC=∂L/∂CG = g_C = \partial L/\partial C, the chain rule gives for every entry of AA, which enters all NN entries of its result row:

∂L∂As,m,k=∑nGs,m,nB(s),k,nin shortgA=GBT.\frac{\partial L}{\partial A_{s,m,k}} = \sum_{n} G_{s,m,n}\, B_{(s),k,n} \qquad\text{in short}\qquad g_A = G\,B^T.

An entry of BB enters all MM rows – and with a shared matrix additionally all batch entries:

∂L∂Bk,n=∑s∑mAs,m,kGs,m,n(shared),∂L∂Bs,k,n=∑mAs,m,kGs,m,n(per batch),\frac{\partial L}{\partial B_{k,n}} = \sum_{s}\sum_{m} A_{s,m,k}\, G_{s,m,n} \quad\text{(shared)}, \qquad \frac{\partial L}{\partial B_{s,k,n}} = \sum_{m} A_{s,m,k}\, G_{s,m,n} \quad\text{(per batch)},

in short gB=ATGg_B = A^T G, summed over the batch for a shared matrix. Exactly this sum over ss and mm is the critical point of parallelisation.

Loop order

Forwards, the outer loop runs over the result rows (s,m)(s, m), inside that over kk, innermost over nn:

Cs,m,⋅+=As,m,kB(s),k,⋅for k=0,…,K−1.C_{s,m,\cdot} += A_{s,m,k}\; B_{(s),k,\cdot} \qquad \text{for } k = 0,\dots,K-1.

In the innermost loop one row of BB and one row of CC are read and written contiguously, and As,m,kA_{s,m,k} is a constant. If it is zero, the whole inner loop is skipped – a noticeable saving for masks, ReLU activations and the selection matrix of the spectral fit. The usual order m,n,km, n, k would jump by NN entries through BB in the innermost loop.

Distribution over the cores

Above a threshold the product runs in parallel. The axis distributed is always one whose work items write into separate memory regions:

  • Forward and gradient with respect to A: over the result rows (s,m)(s, m). Each row of CC or gAg_A belongs to exactly one work item.
  • Gradient with respect to B: over kk (shared matrix) or over (s,k)(s, k) (per batch). The obvious distribution over mm would be a race: all rows mm – and with a shared matrix all batch entries – write into the same row gB,k,⋅g_{B,k,\cdot}.

The choice has a second effect: every work item sums its row in the same order as the serial run. The result is therefore bit-identical, not merely "almost equal". If it deviated even in the last digit, there would be either a race or a changed summation order – both would be a finding.

According to the module documentation, making kk the outer loop of the gradient with respect to BB also nearly halved the serial case (training part of acceptance M2 from 57.1 s to 31.7 s on one core): the row gB,k,⋅g_{B,k,\cdot} stays in cache across all ss and mm instead of changing constantly in the innermost loop.

Distribution uses IntStream.range(0, count).parallel(), i.e. the common fork-join pool with work stealing. A hand-made even split would make every step wait for the slowest cores on a processor with fast and efficient cores; with work stealing the fast cores simply take more items.

Pseudocode – Ops.matmul(a, b)

M, K ← last axes of a;  K2, N ← last axes of b
check K = K2, rank ≥ 2;  shared ← (rank(b) = 2)
if not shared: check equal batch axes
S ← product of batch axes of a;  work ← S·M·K·N

// forward
if schnellesMatmul and work ≥ schnellesMatmulAb:
    schnellVorwaerts(…)                          float kernel, see below
else:
    for each row (s, m) — parallel if work ≥ threshold:
        for k ← 0 to K−1:
            av ← A[s,m,k];  if av = 0: continue
            for n ← 0 to N−1:  C[s,m,n] += av · B[(s),k,n]

backward (G = C.grad):
    if A.grad ≠ null:
        for each row (s, m) — parallel:
            for k:  A.grad[s,m,k] += Σ_n G[s,m,n] · B[(s),k,n]
    if B.grad ≠ null and shared:
        for each k — parallel:                  own row B.grad[k,·]
            for s, for m:
                av ← A[s,m,k];  if av = 0: continue
                for n:  B.grad[k,n] += av · G[s,m,n]
    if B.grad ≠ null and not shared:
        for each (s, k) — parallel:  for m, n:  B.grad[s,k,n] += A[s,m,k] · G[s,m,n]

// "parallel" means: work ≥ parallelMatmulThreshold and more than one item

Source: envisionz-framework-autograd/src/envisionz/autograd/Ops.java, methods matmul, rows and schnellVorwaerts.

Decision in the framework: the threshold Ops.parallelMatmulThreshold is 250,000 multiplications (S⋅M⋅K⋅NS\cdot M\cdot K\cdot N) and is mutable – the acceptance test uses it to compare the parallel with the serial path, and it can be re-measured on the target machine. Without a threshold it would not work: in the build environment the parallel path was 2.4 times slower than the serial one at 13,824 multiplications (module documentation). The small products of attention would only become more expensive when distributed.

The optional forward step in single precision

With Ops.schnellesMatmul = true the forward step of large products runs through the selected kernel from envisionz.autograd.fast (see Matrix kernels). Both factors are converted to float once, the kernel is called per batch entry, and the result is written back as double.

kernel ← Kernels.kernel()
af ← toFloat(A);  bf ← toFloat(B)
for s ← 0 to S−1:
    cf ← zeros[M·N]
    as ← slice s of af;  bs ← shared ? bf : slice s of bf
    kernel.matmul(as, bs, cf, M, K, N)        kernels add into cf
    C[s] ← cf                                 set, not added
Decision in the framework: the switch is off by default, and the threshold Ops.schnellesMatmulAb is 1,000,000 multiplications – below that, converting there and back costs more than the kernel saves. Only the forward step is connected; the backward path always computes in double with the factors' double values. Gradient checking and bit-exact comparisons thus remain possible even with the switch on.

The same count applies on the way back, since both gradients cost one product of the same size each. According to the module documentation, the measured training step at this size (528,898 parameters, four layers) took 124 ms.

How it is checked

  • AutogradTest, part 1: all three forms against central differences (tolerance 10−610^{-6}).
  • AutogradTest, part 3: parallel against serial path, forward value and both gradients, compared via bit patterns (doubleToRawLongBits). Three cases – 1×64×96×1281\times 64\times 96\times 128 (2D), 6×40×64×646\times 40\times 64\times 64 with a shared matrix and the same size batch times batch –, 25 repetitions each, because a race does not show up in every run. Plus the chained computation QKTQK^T as it occurs in the encoder. Switching is done via the threshold: Long.MAX_VALUE for serial, 0 for parallel.
  • Gradientenprobe: gradient with respect to AA and BB against the hand-derived formulas GBTG B^T and ATGA^T G.
  • Schnellpfadprobe (26 checks): the switch defaults to off; below the threshold the computation is bit-identical; above it, fast and slow path agree to 10−510^{-5} and explicitly not bit-identically (it is float); the gradient with the switch on matches the closed formula ∂∑C/∂Am,k=∑nBk,n\partial\sum C/\partial A_{m,k} = \sum_n B_{k,n} to 10−1210^{-12} – a guard against someone connecting the backward path to the float kernel as well.

Limits

  • Indexing uses int: S⋅M⋅NS\cdot M\cdot N and S⋅M⋅KS\cdot M\cdot K must stay below 2312^{31}.
  • No stretching of batch axes: bb is either a matrix or has exactly the batch axes of aa.
  • transposeLast is a real permutation with a copy; a product with a transposed factor therefore costs an extra copy. The form ABTA B^T without a copy exists only in the float kernel (matmulNT).
  • Skipping zeros makes the run time data-dependent; measurements with sparse inputs do not carry over to dense ones.
  • Parallel means: the common fork-join pool. If the application computes other things on this pool at the same time, both share the cores.
