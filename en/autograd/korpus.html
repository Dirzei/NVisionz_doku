Loading and vetting a speech corpus in advance – WAV chunks, metadata and phoneme coverage

The computation behind CorpusLoader and G2pCoverage: a WAV file as a sequence of chunks, the conversion of samples per bit depth, the corpus duration extrapolated from a sample, and the figure "phonemes per character" – with pseudocode following the source, worked examples, the probes and the limits.

What this is about

A speech corpus consists of text lines and the matching recordings. Learning targets are later derived from it – for example the formant trajectories of the second stage (see Frame sequences) or phoneme sequences for speech output. A training run on it takes hours. Faults in the corpus – a missing file, an unexpected sample rate, characters the phoneme converter does not know – do not necessarily show up during training, because a model learns something even from wrong targets.

The package therefore settles three questions beforehand: Are all clips present and readable? How large is the corpus, and does it have a usable sample rate? Does the phoneme conversion cope with the text?

Layout of the corpus directory

The HUI layout is read: a directory with a file metadata.csv and a subdirectory wavs/. Every line of the metadata has the form

id|raw text|normalised text

The separator is the pipe, not the comma – despite the extension .csv. A comma reader would get a single column. The id belongs to the file wavs/id.wav.

The third column is the normalised text: numbers written out, abbreviations expanded. That is exactly what a grapheme-to-phoneme converter needs. Entry.text() therefore returns the third column, and the second only if the third is missing or blank.

Lines whose audio file is missing are skipped and counted; the count is printed. A missing clip would otherwise only surface in the middle of a training run. The loader keeps only references to the files, not the audio data itself: 22 hours at 44.1 kHz are about 3.5 billion samples, i.e. about 14 GB as float. Audio data is read file by file with readWav.

The WAV file as a sequence of chunks

A WAV file is a RIFF file: after a 12-byte header (RIFF, total length, WAVE) come chunks. Every chunk starts with a four-character id and a length ℓ\ell as a 32-bit little-endian number, followed by ℓ\ell bytes of content. Chunks start at even positions; an odd length is followed by a pad byte. The next chunk therefore starts at

p'=p+8+ℓ+(ℓmod2).p' = p + 8 + \ell + (\ell \bmod 2).

Two chunks are needed: fmt with format tag, channel count, sample rate and bit depth (at offsets 0, 2, 4 and 14 of the content), and data with the samples. Many files have exactly these two chunks, and then the samples always start at byte 44. Some tools, however, insert further chunks, such as LIST with recording information. A reader with a fixed offset of 44 then reads metadata as samples. readWav therefore walks the chunks.

Conversion of the samples

The values are mapped to the interval [−1,1)[-1, 1). With the raw value bb read, per bit depth:

Bit depthRaw valueSample
8 bitunsigned, 0≤b≤2550 \le b \le 255(b−128)/128(b - 128)/128
16 bitsignedb/215b / 2^{15}
24 bitsigned, top byte sign-extendedb/223b / 2^{23}
32 bit, format tag 3IEEE 754 floatbb unchanged
32 bit, otherwisesignedb/231b / 2^{31}

8 bit is the only unsigned depth – its centre is 128. Multichannel files stay interleaved (left, right, left, …); the duration is n/(fs⋅c)n / (f_s \cdot c) with nn samples, sample rate fsf_s and cc channels.

Pseudocode – CorpusLoader.readWav(file)

d ← all bytes of the file
check |d| ≥ 44, d[0..4) = "RIFF", d[8..12) = "WAVE"
rate ← 0;  channels ← 1;  bits ← 16;  format ← 1;  dataFrom ← −1
p ← 12
while p + 8 ≤ |d|:
    id ← d[p..p+4);  ℓ ← le32(d, p+4);  content ← p + 8
    if ℓ < 0 or content + ℓ > |d|:  ℓ ← |d| − content       truncated file
    if id = "fmt " and ℓ ≥ 16:
        format ← le16(content);  channels ← max(1, le16(content+2))
        rate ← le32(content+4);  bits ← le16(content+14)
    else if id = "data":  dataFrom ← content;  dataLength ← ℓ
    p ← content + ℓ + (ℓ mod 2)                                 pad byte
check dataFrom ≥ 0
w ← max(1, bits / 8);  n ← ⌊dataLength / w⌋
for i = 0 … n−1:  s[i] ← conversion as in the table, other depths 0
return (s, rate, channels)

Source: envisionz-framework-autograd/src/envisionz/autograd/corpus/CorpusLoader.java, method readWav.

Decision in the framework: an own WAV reader instead of javax.sound.sampled. The JDK package is awkward to include in a native image and adds nothing for uncompressed PCM files. Supported are 8, 16, 24 and 32 bit integer and 32 bit floating point. The loader holds only references; audio data is read per file on request.

Short report on the corpus

summary(eintraege, stichprobe) counts the entries and the characters of the texts and then reads m=min⁡(stichprobe,nE)m = \min(\text{stichprobe}, n_E) audio files. The sample is spread evenly over the corpus – entry ⌊inE/m⌋\lfloor i\, n_E / m \rfloor for i=0,…,m−1i = 0, \dots, m-1 – rather than the first mm: corpora are often ordered by chapter, and the first clips are not representative. From the mean duration t\bar{t} of the clips read follows the extrapolated total duration

T≈t⋅nE3600h.T \approx \frac{\bar{t} \cdot n_E}{3600}\ \text{h}.

The report lists all sample rates that occur and warns in two cases: when more than one rate occurs and when a rate is below 22,050 Hz. The reason for the second threshold: the Nyquist frequency is half the sample rate. A corpus at 16 kHz only reaches 8 kHz, and the centre of the /s/ lies at 6 to 8 kHz – right at the edge. Unreadable files in the sample are skipped so that a single broken file does not prevent the report.

Phoneme coverage before training

A grapheme-to-phoneme converter developed on short dialogue lines meets proper names, French and Latin fragments, old spelling and typographic characters in an audiobook. An unknown character is silently skipped, so the word is mispronounced. G2pCoverage.check(texte, bekannt, conv) checks three things:

  1. Character coverage: every character of the lower-cased text that is not whitespace and not in bekannt is counted with its frequency.
  2. Yield: the ratio a=L/Za = L / Z of the number LL of phonemes produced to the number ZZ of characters.
  3. Empty conversions: lines from which the converter produces not a single phoneme. In training they would be silent targets.

The denominator counts all characters of the lower-cased text including spaces and punctuation. According to the class description German text yields 0.8 to 1.0 phonemes per character. Below a=0.6a = 0.6 the report warns: text is probably being swallowed. ok() is true if neither unknown characters nor empty conversions occurred; the yield does not enter ok().

Pseudocode – G2pCoverage.check(texte, bekannt, conv)

unknown ← empty count;  empty ← [];  Z ← 0;  L ← 0
for each line t in texte:
    if t blank:  continue
    k ← lowercase(t);  Z ← Z + |k|
    for each character c in k:
        if c not whitespace and c ∉ bekannt:  unknown[c] += 1
    n ← conv.countPhonemes(t);  L ← L + n
    if n = 0:  empty ← empty + [t]
return Report(|texte|, Z, L, unknown, empty, L / Z  (0 if Z = 0))

Source: envisionz-framework-autograd/src/envisionz/autograd/corpus/G2pCoverage.java.

Decision in the framework: the converter is passed as the functional interface Converter (countPhonemes(text)) so that the package does not depend on the speech output. The supplied base set GERMAN_BASE contains the lower-case letters a–z with ä, ö, ü, ß, the digits, common punctuation including the typographic quotation marks „ “ ” ‘ ’ and the dashes – —, plus é, è, ê, à, ç, ñ, á, í, ó, ú. The typographic forms are included on purpose: they occur constantly in book text, and a set with only the typewriter forms would report them as unknown by the dozen.

Worked examples

File size. The file in the figure has 4410 samples of 2 bytes, i.e. 8820 bytes of data. With 12 bytes of RIFF header, 8 + 16 bytes of fmt, 8 + 21 + 1 bytes of LIST and 8 bytes of data chunk header this gives 12+24+30+8+8820=889412 + 24 + 30 + 8 + 8820 = 8894 bytes; the samples start at byte 74, not 44.

Extrapolation. In the probe every clip has 22,050 samples at 44,100 Hz, i.e. t=0.5\bar{t} = 0.5 s. With four entries that gives 0.5⋅4/3600≈0.00060.5 \cdot 4 / 3600 \approx 0.0006 h; the report shows a mean of 0.5 s and an extrapolated 0.0 h.

Yield. The probe converter simply counts letters. "Der Verdichter läuft rund." has 26 characters and 22 letters, "Die Turbine erreicht ihre Drehzahl." 35 characters and 30 letters. Together a=52/61≈0.85a = 52/61 \approx 0.85 – within the expected range. A converter that returns nothing gives a=0a = 0, two empty conversions and the warning in the report.

Book-typical characters. In "»Das ist ein Zitat«, sagte er — nachdenklich…" and "Der Coup d'État war ein Fiasko." the check finds three unknown characters: the two guillemets and the ellipsis as a single character. The É becomes é by lower-casing and is known.

How it is checked

  • CorpusTest rebuilds a corpus in memory – metadata and WAV files are generated by the probe – so that the expected result is known. 18 checks:
    • WAV round trip of a 440 Hz sine at 8, 16, 24 and 32 bit with tolerances 0.02 / 0.001 / 10−5 / 10−5; measured largest deviations were 1.17·10−2, 4.57·10−5, 1.49·10−7 and 0;
    • an inserted odd-length LIST chunk with pad byte is skipped; a file without the RIFF id is rejected;
    • of five metadata lines with four existing files, four are read; separator and preference for the normalised text; the report names the sample rate and extrapolates the duration; a missing metadata.csv raises an exception;
    • coverage: clean text without unknown characters, plausible yield, book-typical characters are flagged, empty conversions are reported, too low a yield is warned about, ok() distinguishes correctly.
  • With a directory as argument the probe additionally measures a real corpus (number of entries, mean duration, sample rates).

Limits

  • The format tag is only evaluated to distinguish "32-bit float or integer". A file in the extensible format (tag 0xFFFE) with floating-point samples is read as integer – a probe with the values 0.5 / −0.25 / 0.1 gave 0.49 / −0.51 / 0.48. Compressed formats are not rejected.
  • Bit depths other than 8, 16, 24 and 32 (for example 20 bit) silently yield all zeros.
  • The whole file is read into memory at once; for individual corpus clips that is harmless, for recordings lasting hours it is not.
  • Channels are not separated; anyone needing mono samples must de-interleave themselves.
  • Metadata lines with fewer than two fields are skipped without being counted; only missing audio files are reported.
  • The yield is a rough indicator: it tells whether text is being swallowed, not whether the phonemes are right.
