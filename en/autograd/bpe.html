Text, tokeniser, language model – byte pair encoding

The computation behind BytePairEncoder: why subwords, why bytes as the base, how pre-tokenisation protects word boundaries, how learning counts and merges pairs, how encoding finds the same segmentation again, and what the text storage looks like – with pseudocode following the source, an example recomputed with the module, the probes and the limits.

What this is about

A language model works on a fixed vocabulary of symbols. How a text is split into symbols decides the size and usefulness of the model:

  • Whole words fail in German. Compounds are unboundedly productive – "Verdichterkennfeldinterpolation" (compressor map interpolation) is in no dictionary –, and this holds even more for technical vocabulary. Every unknown word would become a placeholder, and the information would be lost.
  • Single characters do not have this problem but make sequences about five times longer. Attention costs quadratically in the length (see Attention): five times the length means twenty-five times the effort.
  • Subwords lie in between. Frequent words become one symbol, rare ones stay split into pieces, and in the worst case a word falls back to single bytes – it is never lost.

Byte pair encoding (Sennrich, Haddow, Birch, after a compression method by Gage) determines the subwords from the data: start with the smallest units and repeatedly merge the most frequent adjacent pair into a new symbol.

Bytes as the base

The first 256 ids are fixed as the byte values 0 to 255 of the UTF-8 encoding. Umlauts, ß and all other characters are thus covered without special handling: a character outside ASCII is a sequence of two to four bytes, which the method merges back together by itself when frequent enough. Encoding traps – a character the tokeniser does not know – cannot arise at all.

The ids are assigned like this:

RangeMeaning
0 … 255the byte values
256 … 256 + SS − 1the SS special symbols in the order given (for example <s>, <pad>); they have no byte sequence
from 256 + SSthe merges in learning order; rank ii gets id 256+S+i256 + S + i

Pre-tokenisation at word boundaries

Before merging, the text is split into word forms so that no symbols arise across word boundaries ("der Verdichter" must not become one symbol). The walk is over code points, not over char:

  • A leading space stays with the following word. The model thus distinguishes "Feld" at the start of a sentence from " Feld" in the middle, without spaces using up symbols of their own.
  • A run of letters forms a word, and so does a run of digits – separately, so that no symbols like "feld3" arise.
  • Every other character (punctuation, line break, anything else) stands alone.
Decision in the framework: pre-tokenisation walks over code points. Characters outside the basic plane (emoji, for example) consist of a surrogate pair in Java; walking char by char would tear the pair apart, and Java's UTF-8 encoder would turn each half into a question mark. According to the module documentation exactly this happened first – Greek, Cyrillic and Japanese passed without error because they lie in the basic plane; only an emoji in the test text revealed the fault.

Learning

Counting is done not on the raw text but on the unique word forms with their frequencies: a word that occurs ten thousand times is split once and carried with weight 10,000. That gives the same pair counts at a fraction of the effort.

Pseudocode – BytePairEncoder.lerne(texts, targetVocab, minFrequency, specials)

check targetVocab > 256 + |specials|
freq ← empty ordered map word form → count
for each text:  for each word form w in pretokenise(text): freq[w] += 1
words ← per word form the list of its UTF-8 bytes;  count ← per word form its frequency
next ← 256 + |specials|;  merges ← []
repeat (targetVocab − next) times:
    pairs ← empty
    for each word form w:  for each adjacent pair (a, b) in w: pairs[(a,b)] += count[w]
    (a, b) ← pair with the largest count;  on ties the one with the smaller key a·2³² + b
    if count < minFrequency: break
    append (a, b) to merges;  new ← next;  next += 1
    for each word form w: replace each occurrence of (a, b), left to right, by new
return BytePairEncoder(specials, merges)

Source: envisionz-framework-autograd/src/envisionz/autograd/text/BytePairEncoder.java, methods lerne, verschmelze, vorzerlege.

Decision in the framework: on a tie in pair count the pair with the smaller key a⋅232+ba\cdot 2^{32} + b wins. Otherwise the result would depend on the order of the hash table, and two learning runs on the same data would produce different vocabularies. minFrequency ends learning as soon as the best pair is rarer – this prevents random sequences from typos becoming symbols at the end; the vocabulary may then stay smaller than requested.

Encoding and decoding

Encoding must produce the same segmentation as learning. Therefore, per word form, the adjacent pair with the smallest rank – the one learned first – is always merged, until none of the pairs is in the list of merges any more.

Pseudocode – BytePairEncoder.kodiere(text)

out ← []
for each word form w in pretokenise(text):
    ids ← UTF-8 bytes of w
    while |ids| ≥ 2:
        find the adjacent pair (ids[i], ids[i+1]) with the smallest rank
        if none is known: break
        replace all occurrences of this pair by its id
    append ids to out
return out

Decoding concatenates the byte sequences of the ids and reads the result as UTF-8; special symbols are skipped, unknown ids throw. Because every byte has its own id, every input is representable and the round trip is lossless – even for text the tokeniser has never seen.

Storage is text in UTF-8: magic EVZBPE1, number of special symbols, one special symbol per line, number of merges, one pair "a b" per line. The merges are plain number pairs; the file stays readable and can be checked by hand if something goes wrong.

Worked example

Learned on three sentences – "der Verdichter verdichtet", "die Verdichter verdichten", "der Verdichter" – with target vocabulary 268 (i.e. twelve merges), minimum frequency 2, no special symbols. The word forms are "der", " Verdichter" (three times), " verdichtet", "die", " verdichten". The module learns in this order:

Encoded, "der Verdichter" gives two symbols: [266, 264] = "der", " Verdichter". The never-seen "Verdichterkennfeld" – at the start of a sentence, without a leading space – becomes [86, 263, 107, 101, 110, 110, 102, 101, 108, 100]: "V", "erdichter" and the bytes of "kennfeld", which were not frequent enough in this small set. " verdichtet" becomes " v", "erdichte", "t". All three decode losslessly to the original text.

The corresponding file has 15 lines: EVZBPE1, 0, 12 and the twelve pairs from "101 114" to "261 101".

How it is checked

  • TokenizerTest (7 checks): lossless round trip over the whole training set; lossless round trip for completely unknown text (including Greek, Cyrillic, Japanese and emoji); no id outside the vocabulary; a second learning run gives the same vocabulary; saving and loading changes nothing, special symbols are preserved; sequences are at least two times shorter than byte-wise. According to the module documentation the compression factor on known text was 6.65.
  • TextKorpusTest and GeneratorTest use the tokeniser as well: umlauts survive odd block sizes; all generated command examples round-trip losslessly.

Limits

  • Learning cost. Every merge recounts all pairs of all word forms. For a target vocabulary of a few thousand entries on a large corpus this is noticeable; an incremental pair count would be faster but does not exist here.
  • Special symbols are not recognised in the text: "<s>" in the input text is encoded byte by byte. The caller inserts special symbols as ids (specialId).
  • Only the space attaches to the following word. Tab and line break are symbols of their own.
  • No symbols across word boundaries. Fixed phrases of several words never become one symbol; digit runs stay separate from letters.
  • The vocabulary may stay smaller than requested if the minimum frequency takes effect earlier.
