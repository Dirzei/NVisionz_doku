Sequence training and sampling – training on sequences, resumable bit for bit

The computation behind lm.SequenceTrainer: splitting into training and evaluation by sequence, batches via accumulated gradients without padding, the learning-rate schedule over the whole run, checkpoints, and resuming an interrupted run so that it is bit-identical to the uninterrupted one – with pseudocode following the source, recomputed figures, the probes and the limits.

What this is about

A training run takes hours. It must therefore be possible to run it without a user interface, to watch it, to cancel it and – after a crash or on purpose – to resume it. "Resume" is meant more strictly than it sounds: the resumed run should deliver the same numbers as a run that was never interrupted. Only then can one later tell whether a bad result is due to the model or to the interruption.

For that the trainer knows neither tokeniser nor text files. It receives ready-made sequences of ids, the matching target sequences and a recipe LossFunction(ids, targets, training) that turns them into a scalar loss. The same loop thus serves a language model, an intent recogniser or a parameter model for speech output – the three differ only in model and loss.

Batches via accumulated gradients

Sequences have different lengths. The usual solution – padding to a common length and masking the padded positions – is a classic source of errors: the mask must act at every place, in attention, in the loss, in every normalisation over positions, and a forgotten place silently falsifies the result. The trainer avoids this entirely. Because differentiation is linear,

∇θ∑j=1BLj(θ)=∑j=1B∇θLj(θ),\nabla_\theta \sum_{j=1}^{B} L_j(\theta) = \sum_{j=1}^{B} \nabla_\theta L_j(\theta),

it is enough to run forward and backward for each sequence of the batch separately, without resetting the gradients in between – they accumulate in the parameters (see Reverse mode). Afterwards they are divided by the batch size:

g=1B∑j=1B∇θLj.g = \frac{1}{B}\sum_{j=1}^{B} \nabla_\theta L_j.

Without this division the effective learning rate would depend on the batch size: a batch twice as large would give a gradient twice as large. With Adam that would largely cancel in the step, but not in the norm clipping, which acts on the absolute norm.

Split, schedule and checkpoints

  • Split by sequence. The sequence indices are shuffled with Random(shuffleSeed); the first round⁡(n⋅fvalid⁡)\mathrm{round}(n\cdot f_{\mathrm{valid}}) are evaluation sequences (at least one if the fraction is above zero, at most n−1n-1). The split is by sequence, not by position – otherwise neighbours of the same sequence would end up on both sides, and evaluation would measure memorisation.
  • Steps. ⌈ntrain⁡/B⌉\lceil n_{\mathrm{train}}/B\rceil optimiser steps per epoch; the last batch may be smaller and is divided by its actual size.
  • Schedule. Before every step the trainer sets the learning rate per Adam.schedule (see Adam), computed over the total number of steps of the whole run.
  • Evaluation. After every epoch the mean loss over the evaluation sequences, with training = false (no dropout); the best value is tracked.
  • Checkpoints. Every checkpointEvery steps and in any case at the end the trainer writes weights and optimiser state (see Checkpoint); the provenance receives the current step count.
  • Watching and cancelling. A Listener is called after every step, epoch and checkpoint – from the training thread; a user interface must wrap its calls itself. Cancellation is cooperative: before every batch the trainer asks a BooleanSupplier.

Resuming bit for bit

For a run interrupted after EdE_d epochs to continue exactly like the uninterrupted one, three things must be right:

  1. Optimiser state. mm, vv and the step counter come from the checkpoint instead of being created anew. Without them Adam estimates from scratch and makes a jump exactly at the seam.
  2. Learning-rate schedule. The schedule depends on the total number of steps. If the continuation were started as "three more epochs", it would get a schedule for three epochs – with a new warm-up and a new decay. Therefore trainResume explicitly takes the completed epochs EdE_d and the total EE; the step counter starts at EdE_d times steps per epoch. Whoever wants to interrupt a run must fix its full length in advance.
  3. Shuffle order. The sequences are reshuffled per epoch with their own generator. The continuation replays the shuffles of the EdE_d completed epochs without computing and then sees the same batches as the uninterrupted run.

Pseudocode – SequenceTrainer.trainResume(…, opt, E_d, E)

check |inputs| = |targets| > 0 and equal length per sequence
ord ← 0 … n−1, shuffled with Random(shuffleSeed)
nV ← round(n · validFraction);  if validFraction > 0 and nV = 0: nV ← 1
nV ← min(nV, n − 1);   valid ← ord[0 … nV);   train ← ord[nV … n)
if opt = null: opt ← new Adam(params, peakLr)
opt.weightDecay ← cfg.weightDecay;  opt.maxGradNorm ← cfg.maxGradNorm
perEpoch ← ⌈|train| / B⌉;   total ← perEpoch · max(E, cfg.epochs)
step ← perEpoch · E_d
shuffler ← Random(shuffleSeed xor 0x5DEECE66D)
repeat E_d times: shuffle train with shuffler      replay completed epochs
for epoch ← 1 to cfg.epochs:
    shuffle train with shuffler
    for each batch S of train (size ≤ B):
        if cancelled: stop
        opt.learningRate ← Adam.schedule(step, warmup, total, peakLr, minLr)
        opt.zeroGrad()
        for each sequence j in S:  L ← lossFn(in_j, target_j, true);  L.backward()
        if |S| > 1: all gradients ← gradients / |S|
        norm ← opt.step();  step += 1
        listener.onStep(…);  if step mod checkpointEvery = 0: checkpoint
    evaluation loss over valid with training = false;  listener.onEpoch(…)
if checkpoint path set: write checkpoint
return Result(step, …)

Source: envisionz-framework-autograd/src/envisionz/autograd/lm/SequenceTrainer.java. train(…) is trainResume with opt = null, Ed=0E_d = 0 and EE = cfg.epochs.

Decision in the framework: defaults in SequenceTrainer.Config: 10 epochs, batch size 8, peak learning rate 3⋅10−43\cdot 10^{-4}, final value 10−510^{-5}, 200 warm-up steps, weight decay 0.01, norm bound 1.0, shuffle seed 42, checkpoint only at the end (checkpointEvery = 0), evaluation fraction 5 %. The trainer has no user interface of its own and no dependency on Swing; a user interface only watches it.

Cutting a long sequence

For a language model chunk(ids, L, …) cuts a long id sequence into non-overlapping sections of length LL. The target is always the input shifted by exactly one:

ink=(xkL,…,xkL+L−1),targetk=(xkL+1,…,xkL+L),k=0,1,…while kL+L+1≤n.\text{in}_k = (x_{kL}, \dots, x_{kL+L-1}), \qquad \text{target}_k = (x_{kL+1}, \dots, x_{kL+L}), \qquad k = 0, 1, \dots \ \text{while } kL + L + 1 \le n.

At every position the model learns to guess the next token from everything before; the causal mask prevents it from looking ahead (see Masks). A remainder too short for a full section plus target is discarded. L<2L \lt 2 throws.

Worked examples

Step counts. 1000 sequences, evaluation fraction 5 %: 50 evaluation and 950 training sequences. With batch size 8 that is ⌈950/8⌉=119\lceil 950/8\rceil = 119 steps per epoch; the last batch has 6 sequences. Ten epochs: 1190 steps.

Resuming. If this run is interrupted after three epochs and resumed with trainResume(…, opt, 3, 10), the step counter starts at 3⋅119=3573\cdot 119 = 357; by the schedule over 1190 steps the learning rate there is 2.82⋅10−42.82\cdot 10^{-4}. Had the continuation been started as a new run with three epochs instead, its schedule would already have cooled down to 10−510^{-5} after 357 steps – an entirely different run.

Cutting. Ten ids x0…x9x_0 \dots x_9, L=4L = 4: sections (x0..x3→x1..x4)(x_0..x_3 \to x_1..x_4) and (x4..x7→x5..x8)(x_4..x_7 \to x_5..x_8); a third one starting at x8x_8 would need 13 ids.

How it is checked

  • TrainerTest: a run is interrupted halfway, loaded from the checkpoint (optimiser state restored) and resumed; the result must match the uninterrupted run to 10−910^{-9} – according to the module documentation the deviation is exactly 0. The counter-check without optimiser state must deviate by more than a hundred times that (documented: 2.13⋅10−22.13\cdot 10^{-2}), so that the result can be attributed to the state rather than to chance. In addition: the listener is called for every step and every epoch, the loss falls clearly, the evaluation loss is measured, cooperative cancellation takes effect after a few steps.
  • EncoderTest: two backward passes without reset give the sum of the individual gradients to better than 10−1210^{-12} – the computational rule behind the batches itself.
  • According to the module documentation exactly this comparison produced the finding about the learning-rate schedule: a partial run of "three epochs" ran with different learning rates from the first epoch on. Hence the explicit total in trainResume.

Limits

  • Sequence by sequence. A batch is not computed as one large tensor but as BB separate forward and backward passes. That is simple and free of masking errors, but uses the matrix kernels less well than a real batch axis.
  • Resuming only at epoch boundaries. The continuation's step counter is computed from completed epochs; a checkpoint in the middle of an epoch can be loaded but not resumed bit-identically.
  • Randomness in the recipe. If the loss function draws dropout masks from its own generator, its state must also match when resuming; the trainer does not know it.
  • Evaluation every epoch. With large evaluation sets it costs noticeable time; there is no switch for doing it less often.
  • Pairs of equal length. Input and target sequence must have the same length; tasks with output of a different length do not fit this loop.
