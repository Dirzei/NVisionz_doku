Preference model – Bradley-Terry from pairwise judgements

The computation behind PreferenceModel: how judgements of the form "A is better than B" turn into an evaluation function, why the features are normalised and the weights damped, how the estimation computes and what the confidence measure measures – with pseudocode following the source, a recomputed example, the checks and the limits.

What this is about

The search needs an objective. Sometimes it cannot be written down: in curve extraction from a chart one recognises a good extraction when one sees it, but every formula for it misses – too smooth loses detail, too faithful takes over noise. The module documentation records the experience: six hand-designed objectives put the results the user preferred at ranks 11, 6 and 9 of twelve. A search optimising such an objective keeps getting better – in the sense of the objective.

The way out: ask not "how good is this?" but "which of the two is better?". A pairwise comparison is faster and more reliable for people than a score; a number on a scale varies with the day's form, a comparison hardly at all. From many such judgements the preference model estimates what weight each measurable feature of a result has for the person judging. The result is an evaluation function that can be given to the search as fitness – with care, see Confidence measure.

The Bradley–Terry model

Every result is described by a feature vector x∈Rdx \in \mathbb{R}^d – smoothness, coverage, number of jumps of an extracted curve, for instance. The model assumes a linear utility s(x)=w⋅z(x)s(x) = w \cdot z(x), with the normalised features zz (next section) and a weight vector ww. The probability that AA is preferred to BB is the logistic function of the utility difference:

P(A≻B)=σ(s(A)−s(B))=11+e−(s(A)−s(B)).P(A \succ B) = \sigma\big(s(A) - s(B)\big) = \frac{1}{1 + e^{-(s(A) - s(B))}}.

Equal utility means fifty-fifty; a difference of 2 means 88 %, of 4 already 98 %. This is the model of Bradley and Terry, here with a utility computed from features instead of estimated freely per result – which makes it applicable to results that were never judged.

Estimation. For NN judgements "bkb_k better than vkv_k" with Δk=z(bk)−z(vk)\Delta_k = z(b_k) - z(v_k), the mean log-likelihood with a quadratic damping is maximised:

ℓ(w)=1N∑k=1Nln⁡σ(w⋅Δk)−λ2‖w‖2,∇ℓ(w)=1N∑k=1N(1−σ(w⋅Δk))Δk−λw.\ell(w) = \frac{1}{N} \sum_{k=1}^{N} \ln \sigma(w \cdot \Delta_k) \; - \; \frac{\lambda}{2}\, \lVert w \rVert^2, \qquad \nabla \ell(w) = \frac{1}{N} \sum_{k=1}^{N} \big(1 - \sigma(w \cdot \Delta_k)\big)\, \Delta_k \; - \; \lambda\, w.

The gradient is intuitive: each judgement pulls ww in the direction of its feature difference, the more strongly the less the model already explains it (1−σ1 - \sigma is large when w⋅Δkw \cdot \Delta_k is small or negative). ℓ\ell is concave; with λ>0\lambda > 0 there is exactly one maximum.

Convention in the framework: The L2 damping is not decoration. If all judgements can be separated by a line in feature space – the normal case with few judgements –, ww grows without bound without damping: every larger ww explains the judgements a little more confidently. With fourteen features and few judgements an undamped model would weight individual features arbitrarily high. Usual default according to the class comment: λ=0.05\lambda = 0.05.

Normalising the features

Features have different units and orders of magnitude; without normalisation the feature with the largest numerical span would dominate the estimation, and λ\lambda would damp the features unequally. fit therefore normalises over all 2N2N vectors of the judgements to mean 0 and standard deviation 1:

zi(x)=xi−misi,mi=12N∑allxi,si=12N∑all(xi−mi)2,si<10−9⇒si=1.z_i(x) = \frac{x_i - m_i}{s_i}, \qquad m_i = \frac{1}{2N}\sum_{\text{all}} x_i, \qquad s_i = \sqrt{\frac{1}{2N}\sum_{\text{all}} (x_i - m_i)^2}, \quad s_i < 10^{-9} \Rightarrow s_i = 1.

In the differences Δk\Delta_k, mm cancels; it only determines where s(x)s(x) is zero: a result with exactly average features has utility 0. The weights refer to the normalised features and are therefore comparable with each other: a weight of 2 means that one standard deviation of this feature changes the utility by 2.

The method in the code

The estimation uses plain gradient ascent with a fixed step size: 0.5 in the first half of the steps, 0.15 afterwards. The caller sets the number of steps; there is no convergence check.

Pseudocode – PreferenceModel

// fit(pairs, lambda, steps)
if pairs empty: done                                 model stays as it was
seen ← all better and worse vectors
m, s ← mean and standard deviation per feature over seen   s < 10⁻⁹ → 1
w ← 0;  η ← 0.5
for it ← 0 to steps − 1:
    g ← 0
    for each pair (b, v):
        Δ ← z(b) − z(v)
        g ← g + Δ / (1 + exp(w·Δ))                   1/(1+e^d) = 1 − σ(d)
    w ← w + η · (g / |pairs| − lambda · w)
    if it = ⌊steps/2⌋: η ← 0.3 · η

// score(x)
if never estimated: 0  else w · z(x)

// confidence(x) – a distance, not a confidence value
if never estimated: largest floating-point number
min over all seen vectors q of ‖z(x) − z(q)‖

// accuracy(pairs)
share of pairs with score(b) > score(v)

Confidence measure

As soon as a search optimises against the model, it finds the model's blind spots – exactly as with a hand-written objective. A linear model is particularly prone to this: outside the judged examples the utility keeps growing in the direction of ww without end, although nobody has ever judged there. confidence(x) therefore measures the distance of xx to the nearest judged vector, in normalised units:

c(x)=minqseen⁡‖z(x)−z(q)‖.c(x) = \min_{q\ \text{seen}} \lVert z(x) - z(q) \rVert.

Despite the name, a large value means little confidence – the model is extrapolating. The search should not adopt candidates with large cc but set them aside for judgement. The class prescribes no fixed bound; it depends on the number of features, because distances grow with d\sqrt{d}.

Measured on the digitizer: without a confidence bound an unjudged candidate received twenty times the best utility and was in truth bad.

The loop with the human

The module documentation describes how model and search are meant to work together:

  1. Compute and display results.
  2. Present them in pairs: "A or B better?" – each round costs four looks.
  3. Estimate the weights, check the hit rate.
  4. Search against the model, bounded by confidence().
  5. Set candidates outside the trust region aside for judgement – and start again.

According to the documentation the model becomes reliable at 30 to 50 judgements. The loop was run through once: after 19 judgements the model was right 89 % of the time. In production code it is not yet a built-in route; the model is checked but has no caller outside the probes yet.

How it is checked

EvolveTest, section preference model, with a constructed preference:

  • 40 pairs; the first feature decides (preferred between 0.5 and 1, rejected between 0 and 0.5), the second is random between 0 and 1 for both.
  • Estimated with λ=0.01\lambda = 0.01 and 300 steps. Checked: one weight per feature; the deciding feature gets the larger weight in magnitude; a high value in the first feature is rated better than a low one; the hit rate on its own pairs is above 80 %; the names are kept.
  • Measured: weights 2.711 and −0.403, hit rate 100 %.

The confidence measure is not the subject of a check.

Limits

  • Linear utility. The model can express "more is better" and "less is better" per feature, but no "medium is best" and no interaction of two features. Whoever expects something like that feeds in derived features, such as the distance to a target value.
  • No tie. A judgement "both equally good" cannot be expressed.
  • Hit rate on its own judgements. accuracy on the same pairs used for the estimation overestimates the quality. It is informative on held-back judgements.
  • Normalisation from the judgements. mm and ss come from the judged vectors. If the search's candidates are distributed differently, the model computes on a scale not made for them.
  • Confidence measure without a bound. Which distance is too large is up to the caller; the class only supplies the number. Without this bound the model must not be used as a search objective.
  • Fixed step size, no convergence check. Whether 500 steps suffice is shown only by a comparison with more steps.
  • Choosing features remains the real work: what is not measured as a feature the model cannot learn – even if the person judging pays attention to exactly that.
