The search run – generations, budget and feedback

The loop in EvolveEngine: how a generation proceeds, how evaluation runs in parallel while insertion stays repeatable, when the run ends and what the budget really counts, how the operators learn about their children – with pseudocode following the source, recomputed numbers, the checks and the limits. The archive itself is described on the page MAP-Elites.

What this is about

The archive holds the niches, the operator (Proposer) creates new candidates, the evaluator (Evaluator) computes them. The engine joins the three into a cycle: draw parents from the archive, have children proposed, evaluate, back into the archive. One pass is called a generation; it creates a batch of children that are independent of each other and therefore evaluated in parallel.

The division of labour is strict. The engine knows no domain terms and makes no selection other than the archive's; the operator may propose any nonsense but never evaluates itself; the evaluator alone decides fitness and niche. This makes it possible to measure any operator against any other on the same evaluator – the question "does this method gain anything over random mutation?" becomes a measurement instead of an assumption.

The course of a generation

Pseudocode – EvolveEngine.run(onProgress)

pool ← fixed thread pool with config.threads threads
try:
    if archive.coverage = 0:                         fresh archive
        evaluateAndInsert(evaluator.seeds(), notify = false)
        if archive.coverage = 0: exception "no seed candidate could be evaluated"

    generation ← 0
    while not cancelled and archive.totalInserts < config.budget:
        generation ← generation + 1
        parents ← archive.sampleParents(config.parentsPerJob, config.eliteBias, rnd)
        context ← (evaluator.id, displayName, geneSpec, axes,
                   the config.topExamples best elites, descending)
        children ← proposer.propose(parents, context, config.batchSize)
        if children empty: continue                   no evaluation, no report
        accepted ← evaluateAndInsert(children, notify = true)
        if onProgress ≠ none:
            onProgress(generation, archive.totalInserts, archive.coverage,
                       archive.qdScore, best value or −∞, accepted)
    return archive
finally: pool.shutdownNow()

Pseudocode – evaluateAndInsert(batch, notify)

jobs ← for each child c in batch:
    ( try e ← evaluator.evaluate(c)
      on RuntimeException x: e ← Evaluation.error(classname(x) + ": " + message(x))
      return (c, e) )
results ← pool.invokeAll(jobs)                       waits until all are done
accepted ← 0
for each result in batch order:                     not in completion order
    (c, e) ← result.get()                            ExecutionException: skip
    acc ← archive.insert(c, e)
    if acc: accepted ← accepted + 1
    if notify: proposer.tell(c, e, acc)
return accepted

Source: envisionz-framework-evolve/src/envisionz/evolve/EvolveEngine.java (run, evaluateAndInsert, topElites). The pool is created per run and closed in the finally.

Evaluate in parallel, insert in order

In most applications evaluation is the expensive part – a curve trace, a solver run, a simulation. The children of a batch do not depend on each other; the engine therefore hands them to threads threads at once. Insertion, however, happens only when all are done, in the calling thread and in batch order. That has two consequences:

  • The result does not depend on the number of threads. Which evaluation finishes first is a matter of machine load; the order of insertion is not. Recomputed on the probe's sphere run with 1, 4 and 8 threads: each time best value −0.00465625 and QD score −47.79072117.
  • The operator is never called concurrently. propose and tell run in the engine's thread. Stateful operators such as CMA-ES need no locks.
Convention in the framework: Evaluator.evaluate must be thread-safe and free of side effects – that is part of the contract. Candidate faults are reported by the evaluator as invalid, not as an exception. If it throws a RuntimeException nonetheless, the run continues; the child is recorded as ERROR, rejected and reported as such to the operator.

Budget and termination

The termination condition checks the archive's number of insertion attempts against budget, before every generation. Three things follow:

  1. The budget is not an upper limit. A generation once begun runs to completion.
  2. The seeds count. They are inserted before the loop and raise totalInserts like every child.
  3. A loaded archive counts. ArchiveIO.load inserts the stored elites via insert; a continued run therefore does not start at zero.

If ss insertions happened before the loop (seeds or loaded elites), the operator always delivers full batches of size bb, and s<Bs < B, the run ends after

Convention in the framework: budget is the number of insertion attempts from which no new generation is begun. The class comment of Config additionally says the seeds come "on top"; according to the code they count towards the budget (table above). The figure 404 at budget 400, batch 8 and four seeds results under both readings and therefore does not settle the question; with one, two or three seeds the difference becomes visible.

Cancelling. cancel() sets a volatile flag that the loop reads before every generation. The running generation is still evaluated, inserted and reported; then run returns the archive normally. An interruption of the calling thread (InterruptedException from invokeAll), by contrast, ends the run immediately with that exception.

Context and feedback to the operator

Per generation the operator receives two things: the drawn parents (parentsPerJob of them, with replacement) and a task context (TaskContext) with the evaluator's identifier, display name, gene description and axes, and the topExamples best elites in descending order of fitness. The gene description and the examples are meant for operators that "read" – the numeric operators use the examples as additional population (differential evolution) or as initial knowledge (surrogate).

After insertion the operator receives a tell(child, evaluation, accepted) for every child. The interface default does nothing; learning operators need it:

Operatorwhat it does with the feedback
CmaEsProposercollects fitness values, updates mean, covariance and step size after λ\lambda reports; invalid children enter as −∞-\infty
SurrogateProposeradds point and fitness to the surrogate model, only for finite fitness
MixedProposercounts proposals and acceptances per sub-operator and passes the report on to the sub-operator that proposed the child
Gaussian, differential evolution, structural, sequencenothing – they read the archive anew on every call
Convention in the framework: Seeds are not reported – they do not come from the operator. The report comes after insertion so that accepted is already known, and from the engine's thread, not from the evaluation threads.

Progress

After every generation with children the engine reports a Progress: generation, insertion attempts so far, coverage, QD score, best value and the number of children accepted in this generation. The report comes from the calling thread; a GUI passes it on to its event thread itself. An excerpt from the probe's sphere run (budget 400, batch 8, four seeds):

The best value never falls – the archive guarantees that. The QD score, however, jumps down when a new niche is occupied with poor fitness (generations 10 and 15) and rises afterwards as the elites improve. With negative fitness it is comparable as a measure of progress only between points in time with equal coverage.

When the operator delivers nothing

An operator may deliver fewer children than requested, even none. The engine then counts nothing, reports nothing and immediately begins the next generation. For single generations that is harmless. If the operator fundamentally cannot deliver, however, the loop never ends: the termination condition depends only on insertion attempts, and they no longer change.

Measured with differential evolution as the only operator and a single seed: it needs at least four distinct individuals, never gets enough from an archive with one elite and returns an empty list every time. After two seconds the loop was still running, with 1 886 909 calls to propose, a single evaluation and no progress report; only cancel() ended it.

Convention in the framework: Whoever uses an operator that needs a minimum population (differential evolution: four, surrogate: three observations) mixes in, via MixedProposer, an operator that always delivers – Gaussian mutation is meant for exactly that – or gives the evaluator enough distinct seeds.

Repeatability

With a fixed engine seed, fixed operator seeds and a deterministic evaluator, a run yields the same archive on every repetition: the random sources are used only in the engine's thread, insertion follows batch order, and the iteration order of the archive table depends only on the – therefore also fixed – sequence of insertions. Candidate identifiers are the only exception; they are random but do not influence the search.

How it is checked

Evolveprobe runs the search on the sphere function f=−(x2+y2)f = -(x^2+y^2) with budget 400, batch 8, two parents, eliteBias 0.35, one thread and four seeds:

  • The run reports progress.
  • The best value never gets worse from generation to generation (tolerance 10−1210^{-12}).
  • The budget is reached and exceeded by less than one batch plus the seeds; measured 404.
  • Niches are occupied; the best value lies above −0.5 and not above the maximum 0.
  • The same seed twice gives the same best value (tolerance 10−1210^{-12}).

Limits

  • Endless loop with permanently empty proposals – see above. Neither a maximum number of empty generations nor a report catches this.
  • Budget counts seeds and loaded elites and is exceeded by up to one batch.
  • Lost children. If an evaluation job fails with an Error instead of a RuntimeException (running out of memory, for instance), the child is silently skipped: no insertion, no feedback to the operator.
  • Synchronous generations. The next batch begins only when the slowest candidate of the previous one has finished. If evaluation times scatter widely, threads wait.
  • Progress only with children. Generations without children report nothing – not even that nothing is happening.
  • One archive directory, one writer. ArchiveIO knows no locks; two runs saving into the same directory overwrite each other.
