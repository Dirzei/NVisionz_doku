Storage and evaluation cache – formats and LRU

What lies behind GenomeIO, ArchiveIO and MemoizingEvaluator: the text format of a genome, the structure of a saved archive, what happens when loading and continuing, and how the evaluation cache recognises repetitions and forgets them again – with pseudocode following the source, a real archive file, the checks and the limits.

What this is about

A search run is useful only when its result arrives where it is needed: as a preset in an application's GUI. It is economical only if it can be continued tomorrow where it stood today, and if it does not compute the same expensive evaluation twice. Three small building blocks take care of this:

  • GenomeIO – a genome as a text file, the exchange format between search and GUI;
  • ArchiveIO – a whole archive as a directory, for continued learning across runs and sessions;
  • MemoizingEvaluator – a "genome → evaluation" cache around a deterministic evaluator.

All three make do with java.base; the module thus stays free of third-party libraries and fit for native image.

The genome format

A genome is an ordered map name → string. The file holds it line by line, UTF-8:

# any comment, multi-line allowed
radius=2.5
stufen=4
modus=fein
glatt=true

Reading (load, loadResource): every line is stripped of whitespace at both ends. Empty lines and lines starting with # are skipped. The key is everything before the first equals sign, the value everything after it, both trimmed again. A line without an equals sign or with an empty key aborts with a message including the line number. The order of the file is preserved.

Writing (save): first the comment, each of its lines preceded by #␣, then one line key=value per gene in the order of the map.

Convention in the framework: Deliberately not java.util.Properties: that would lose the order and escape special characters. The file is meant to read like the list of settings it is, in the order of the GUI. With loadResource(class, name) an application can ship presets in its own package.

The archive format

An archive becomes a directory, preferably named after the evaluator's identifier. It contains an axes file and one file per elite, both in the genome format:

FileKeyContent
axes.propertiescountnumber of axes
i.name, i.unit, i.min, i.max, i.binsaxis ii, starting at 0; unit only if set
elite-NNNN.properties_fitnessfitness
_descriptorsdescriptors, comma-separated
_metric.nameone line per additional metric
_id, _gen, _origin, _parentidentifier, generation, origin, parent (only if present)

Pseudocode – ArchiveIO.save(archive, directory) and load(directory)

// save
create directory (including parents)
write axes.properties: count, per axis name, unit (if set), min, max, bins
delete all existing elite-*.properties                the archive might have shrunk
n ← 0
for each elite in archive.elites():                   order of the table
    f ← _fitness, _descriptors, _metric.*, _id, _gen, _origin, [_parent], then the genes
    write f to elite-%04d.properties with n;  n ← n + 1

// load
ax ← read axes.properties;  count ← ax.count (missing: 0)
if count < 1: exception "axes.properties without axes"
archive ← new MapElitesArchive(axes 0 … count−1)
for each file elite-*.properties, sorted by name:
    f ← read file
    genes ← all keys without "_";  metrics ← all _metric.*
    d ← _descriptors split at commas, as numbers
    candidate ← (_id or "geladen", genes, _parent, _origin or SEED, _gen or 0)
    archive.insert(candidate, Evaluation.ok(_fitness or 0, d, metrics))
return archive

Source: envisionz-framework-evolve/src/envisionz/evolve/ArchiveIO.java and GenomeIO.java. In addition exists(directory) (is there an axes.properties?) and describe(directory) ("N Elites in …").

Convention in the framework: When loading, every elite is added via insert, not written directly into the table. The niche is thus recomputed from descriptors and the stored axes, and the archive's counters run along: a loaded archive with seven elites reports seven insertion attempts. An archive directory belongs to one writer; there are no locks.

Continuing on a loaded archive

The engine has a second constructor that takes a pre-filled archive. If it is not empty, the evaluator's seeds are not evaluated; the search picks up where the stored one stopped:

ArchiveIO.save(archive, Path.of("lauf-01"));
MapElitesArchive more = ArchiveIO.load(Path.of("lauf-01"));
new EvolveEngine(evaluator, operator, cfg, more).run(null);

Two things must be kept in mind. First, the loaded elites count towards the budget: measured, a run with budget 100 on an archive with seven elites adds only 96 new evaluations (see Budget and termination). Second, the archive brings its own axes. If the evaluator now delivers a different number of descriptors, the first insertion of a new child fails with an exception; if it delivers the same number with a different meaning, nobody notices.

Learning operators start from scratch when continuing: CMA-ES begins with its initial distribution, the surrogate model reads only the examples of the first context. Whoever wants to give the surrogate model the whole archive feeds it in with observe.

The evaluation cache

Mutation operators produce duplicates: small steps that land on the same value after rounding to four decimal places, structural moves that switch back, moves to the same position. With evaluations taking seconds, every repetition is expensive. MemoizingEvaluator wraps itself around the evaluator as a decorator and remembers the evaluation for every genome.

The key is the text form of the genome: all entries as name=value with a line break, in the order of the map. Two candidates with different identifiers but the same genes therefore hit the same entry – which is precisely the point, because in a search run identical genomes with new identifiers arise all the time.

Eviction is LRU (least recently used): the cache is a LinkedHashMap in access order; every hit moves the entry to the back, and if after an insertion there are more than CC entries, the front one – the one unused for the longest time – drops out. C=max⁡(16,capacity)C = \max(16, \text{capacity}), default 10 000.

Pseudocode – MemoizingEvaluator.evaluate(candidate)

k ← Σ over the genes in order: name + "=" + value + "\n"
locked:
    e ← cache.get(k)                              moves the entry to the back
    if e ≠ none: hits ← hits + 1;  return e
e ← delegate.evaluate(candidate)                 without lock: may run in parallel
locked:
    misses ← misses + 1
    cache.put(k, e)                                above C entries: drop the eldest
return e

Source: envisionz-framework-evolve/src/envisionz/evolve/MemoizingEvaluator.java. Identifier, display name, axes, seeds and gene description are passed through unchanged by the decorator.

Convention in the framework: Wrap only a deterministic evaluator. With an evaluator that scatters, the cache would freeze the first measurement and hide the scatter. Whoever wants to memoise only a part – an expensive preprocessing step that depends on few genes, say – builds that into the evaluator itself; only it knows the structure. The hit rate says something about the search itself: many hits mean that the same candidates are proposed again and again – the diversity of the proposals is waning.

How it is checked

Evolveprobe:

  • Genome file there and back: three genes, among them a value with an inner space and an empty value, come back complete and with their values.
  • Archive there and back: two elites with fitness 5 and 7 saved in a directory; exists finds it, loading returns as many niches, the best value is 7 (tolerance 10−910^{-9}), describe names something, and a non-existent directory does not count as an archive. The files are created in a temporary directory and deleted afterwards.
  • Evaluation cache against a counting evaluator: three evaluations, two of them candidates with equal genes, reach the evaluator exactly twice; both yield the same fitness; one hit, two misses; identifier and axes are passed through.

Limits

  • Values with edge whitespace, line breaks or a leading # do not survive the genome format: whitespace at the ends is cut off, a line break tears the line apart, a key starting with # becomes a comment line. Keys must not contain =; values may.
  • Incomplete elite files. If _fitness is missing, the fitness becomes 0 – a plausible number, not an error message. If _descriptors is missing, loading aborts with a number format error.
  • Numbering not stable. The elite files are numbered in the order of the archive table; the same elite may carry a different number after the next save. When saving, all old files are deleted first; if writing aborts after that, the directory is incomplete.
  • The cache key depends on order. The same genes in a different order give a different key. Measured: two candidates with a=1, b=2 and b=2, a=1 reached the evaluator twice, without a hit. In the search run this does not occur because all operators take over the parent's order.
  • Errors are cached too. An ERROR evaluation lands in the cache like any other; a transient fault of the evaluator then holds permanently for this genome. Measured: after a one-off error the second request returned the same ERROR without a new call.
  • Simultaneous requests for the same new genome both compute; the cache locks only lookup and storage, not the evaluation.
  • Smallest capacity 16. Smaller values are raised to 16.
