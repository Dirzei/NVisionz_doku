Structural genes and sequences – mutation without numbers

The methods behind StructuralGenome, StructuralMutationProposer, SequenceGenome and SequenceMutationProposer: how enumerations, switches and ordered lists are described and changed in a type-appropriate way, with which probabilities which move occurs and why the order of the genes matters for repeatability – with pseudocode following the source, recounted frequencies, the checks and the limits.

What this is about

Not every setting is a number. An evaluation chain has method choices ("threshold global or adaptive"), switches ("noise suppression on/off") and often an order of steps ("smooth first, then threshold" or the other way round). Such genes have no neighbourhood in the sense of "a bit more" or "a bit less"; a Gaussian perturbation or the difference of two vectors makes no sense for them. If one changed them randomly as strings nonetheless, almost only invalid values would result.

That is why they have their own descriptions and their own operators, which produce only valid values: an enumeration switches to another value of its pool, a switch flips, a sequence is rebuilt by one of four elementary moves. The numeric operators leave these genes untouched, the structural and sequence operators the numeric genes; via mixing all of them share the same genome.

Enumerations and switches: StructuralGenome

A structural description consists of

  • enumeration genes – gene name → list of allowed values, e.g. art → [rot, gruen, blau];
  • switch genes – gene names whose value is true or false.

The exact description comes from the application's EvaluatorProvider (structuralGenome()), which knows the value pools. If it is missing, inferFrom(sample) provides a fallback: every gene whose value reads true or false, ignoring case, becomes a switch. The heuristic does not recognise enumerations – the pool cannot be read off a single sample genome.

Convention in the framework: The genes are stored in the order passed in: first the enumerations, then the switches. This is not cosmetic. The operator picks a gene via an index into this list; with a set without fixed order, the same seed would give different candidates and a different archive on every program start. Until September 2026 the class stored the switches as Set.copyOf and had exactly this fault; since then it is an ordered copy.

Structural mutation

Exactly one move per child – structural jumps are big enough. With KK structural genes:

  1. Draw a parent uniformly from the given parents (without parents, from the best examples of the context).
  2. Choose a gene uniformly: probability 1/K1/K per gene.
  3. If it is a switch, it is flipped. If it is an enumeration with pool VV, a value is drawn uniformly from VV without the current one.

A particular other value vv of an enumeration with |V||V| values therefore arises with

P(gene g becomes v)=1K⋅1|V|−1.P(\text{gene } g \text{ becomes } v) = \frac{1}{K} \cdot \frac{1}{|V| - 1}.

In the probe's example with art ∈ {rot, gruen, blau} and the switch schnell, K=2K = 2: every child flips the switch with ½ or changes to one of the two other colour values with ¼ each.

Pseudocode – StructuralMutationProposer.propose(parents, context, n)

pool ← parents, if empty: context.topExamples     both empty → empty list
keys ← [enumeration genes…, switch genes…]          fixed order
for k ← 1 to n:
    p ← pool[rnd.int(|pool|)].candidate
    g ← copy of p.genes
    s ← keys[rnd.int(|keys|)]
    if s is a switch:
        g[s] ← not parseBoolean(g[s])                 missing or unreadable counts as false
    else:
        values ← pool of s
        if |values| < 2: continue                     no child for this move
        repeat new ← values[rnd.int(|values|)] until new ≠ g[s]
        g[s] ← new
    child ← p.child(g, MUTATION)

Source: envisionz-framework-evolve/src/envisionz/evolve/StructuralMutationProposer.java and StructuralGenome.java. The constructor rejects an empty structural description.

Convention in the framework: All other genes – in particular the numeric genes – are taken over unchanged. Typically the operator is mixed in with a small weight next to a numeric operator.

Sequences: SequenceGenome

A sequence gene is a gene whose value is an ordered list from a fixed pool – the order of the filters of an image evaluation, for instance. This opens the search from parameters to structure: the order of the steps carries meaning. Each sequence gene is described by

Encoding in the genome: the elements separated by commas, e.g. schritte=Glätten,Schwelle,Entflecken; the empty list is the empty string. When reading (parse) the value is split at commas, each piece is stripped of whitespace, and empty pieces are dropped; format joins with commas without spaces. Element names therefore must not contain a comma.

Sequence mutation

For each child one sequence gene is chosen uniformly and one move is applied to it. Four moves are available, each with a condition on the current length LL:

The choice is length-dependent, in a particular way: up to four times a move is drawn uniformly from the four; if it is not possible in the current situation, the next attempt follows. If kk of the four moves are possible and q=(4−k)/4q = (4-k)/4, then

P(no child)=q4,P(a particular possible move)=14∑a=03qa=1−q4k.P(\text{no child}) = q^4, \qquad P(\text{a particular possible move}) = \frac{1}{4}\sum_{a=0}^{3} q^a = \frac{1 - q^4}{k}.

Pseudocode – SequenceMutationProposer

// propose(parents, context, n)
pool ← parents, if empty: context.topExamples     both empty → empty list
for k ← 1 to n:
    p ← pool[rnd.int(|pool|)].candidate;  g ← copy of p.genes
    s ← sequence gene, uniform;  seq ← parse(g[s])
    if mutate(seq, gene s): g[s] ← format(seq);  child ← p.child(g, MUTATION)
    else: no child                                      the list becomes shorter than n

// mutate(seq, gene): at most four attempts
repeat 4 times:
    choose one of four moves uniformly:
    swap:    if L ≥ 2: i ≠ j uniform, exchange seq[i], seq[j];  return true
    move:    if L ≥ 2: e ← remove seq[i]; insert e at position 0…L−1;  return true
    insert:  if L < maxLen:
                 free ← elements, without allowRepeat minus those present
                 if free not empty: insert free[random] at position 0…L;  return true
    remove:  if L > minLen: remove seq[random];  return true
return false

Source: envisionz-framework-evolve/src/envisionz/evolve/SequenceMutationProposer.java and SequenceGenome.java. If a move is not possible, the code breaks out of the case and draws again.

Convention in the framework: The length bounds are kept by the moves, not checked afterwards. A sequence already outside the bounds – from a file, say – stays there as long as no suitable move occurs; inserting is blocked at L≥maxLenL \ge \text{maxLen}, removing at L≤minLenL \le \text{minLen}.

Worked example

Gene schritte with pool A, B, C, D, length 2 to 5, repetition allowed; parent sequence A, B, C (L=3L = 3). All four moves are possible, each with ¼:

  • Length of the children: 2 with ¼ (remove), 4 with ¼ (insert), 3 with ½ (swap, move).
  • Unchanged children: moving takes out one element and puts it at one of LL positions of the remaining list; one of them is the old one. With ¼ · ⅓ = 1/12 ≈ 0.083 the child equals the parent. Swapping distinct elements always changes something.

Recounted with the operator over 120 000 children: lengths 2, 3, 4 with 29 793, 60 158 and 30 049 children; unchanged 0.0821. With the parent sequence A, B (L=2=minLenL = 2 = \text{minLen}): 119 533 children instead of 120 000 (expected 1−1/2561 - 1/256), share of inserting 0.3327 (expected ⅓), unchanged 0.1660 (expected ⅓ · ½ = ⅙).

Together with numeric genes

A genome may contain all three kinds: numeric genes, structural genes, sequence genes. Each operator touches only its kind and takes over the rest unchanged – the numeric operators via NumericGenome, the two described here via their descriptions. A child therefore changes in only one kind per move. How strongly each kind is worked on is governed by the weight in the MixedProposer; with adaptive weighting, the kind whose children enter the archive more often gets more moves.

How it is checked

Evolveprobe, section "structural and sequence mutation":

  • Counting: one enumeration and one switch give size 2.
  • Order of the switches: 40 switches in a deliberately shuffled but fixed order come back exactly so. Against the old state with Set.copyOf this check is red.
  • Structural mutation, 300 children: only values from the enumeration, only true/false for the switch, every child differs from its parent, and both genes get their turn.
  • Sequences: format(parse("A,B,C")) gives A,B,C again; over 300 children the length stays between 2 and 5, only A to D occur, and the length actually changes.

Limits

  • Repeatability depends on the caller. The constructor keeps the order it receives. If the caller passes Map.of or Set.of, that order itself differs on every program start: checked with four enumerations and six switches, three starts gave three different orders. For repeatable runs pass a LinkedHashMap or a LinkedHashSet.
  • Unchanged children. Moving to the same position and swapping equal elements (with allowRepeat) return the parent; that costs an evaluation without insight (see worked example).
  • Fewer children than requested. Enumerations with fewer than two values and sequences to which no move applies yield no child.
  • No crossover. Both operators change one parent; sub-sequences of two good parents are not combined.
  • No neighbourhood in enumerations. Every other value is equally likely; a natural order (small, medium, large) is not used by the operator.
  • Expressions as genes (formulas) do not yet have an operator.
  • Sequence genes do not yet have a user outside the probes.
