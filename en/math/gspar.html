Sparse LU – background

The computation behind GSPAR, SparseMatrix and GSPARWorkspace: storage format, Markowitz pivoting with a threshold, fill-in and linked lists, forward and backward substitution, the pseudocode for fast refactorisation and the condition estimate – with pseudocode following the source, worked examples, checks and limits.

What this is about

A flowsheet model of an engine – for example the JT9D model of the eqnparser with 1184 equations – leads in Newton's method to a Jacobian in which every equation depends on only a few unknowns: a compressor map on speed, flow and pressure ratio, a mass balance on the flows at one node. Of the 11842≈1.41184^2 \approx 1.4 million entries only a few thousand are non-zero. The matrix is sparse.

Stored and factored densely it would cost 11 MB of memory and about n3/3≈5.5⋅108n^3/3 \approx 5.5 \cdot 10^8 multiplications – per Newton step. A sparse factorisation stores and computes only with the non-zeros. The difficulty is fill-in: elimination creates non-zeros where AA was zero. How many depends solely on the order in which rows and columns are eliminated. The art of a sparse LU is choosing that order – in such a way that the pivots still stay large enough.

GSPAR is the Java port of the Fortran package GSPAR by Friedrich Grund (WIAS Berlin, about 1994): 27 subroutines, plus the documented corrections to the original (section corrections). The work splits into an expensive preparation that runs once per sparsity structure, and cheap steps repeated with new values in every Newton iteration.

The input is a SparseMatrix in CSR format (compressed sparse row): three arrays instead of a matrix.

Example from the documentation of DLLUGE (0-based):

A=(9002110305020401070805079)A = \left(\begin{matrix} 9 & 0 & 0 & 2 & 1 \\ 1 & 0 & 3 & 0 & 5 \\ 0 & 2 & 0 & 4 & 0 \\ 1 & 0 & 7 & 0 & 8 \\ 0 & 5 & 0 & 7 & 9 \end{matrix}\right)

a  = {9,2,1,  1,3,5,  2,4,  1,7,8,  5,7,9}

The solver in the eqnparser builds the matrix from triplets (i,j,aij)(i, j, a_{ij}) with buildFromTriplets: the triplets are sorted stably by (row, column), duplicate positions are summed. This produces the transfer list itra: for every triplet in sorted order it says either “open the next position with the value of triplet kk” (k≥0k \ge 0) or “add triplet kk to the position opened last” (encoded as −(k+1)-(k+1)). In every Newton iteration transferValues uses it to move the new Jacobian values in O(nnz)O(\text{nnz}) without sorting again.

Pivot choice: Markowitz with a threshold

Eliminating with the pivot arca_{rc} combines every other row that is occupied in column cc with every other occupied column of row rr. If the pivot row has rir_i non-zeros and the pivot column cjc_j, at most

Mij=(ri−1)(cj−1)M_{ij} = (r_i - 1)(c_j - 1)

new non-zeros can appear – the Markowitz count (Markowitz 1957). A pivot with a small Markowitz count keeps fill-in low. But a pivot must also be numerically sound: a small pivot produces large multipliers and rounding errors. The compromise is threshold pivoting: in each column only entries whose magnitude is at least β\beta times the column maximum are admitted,

|aij|≥βmaxk⁡|akj|,0≤β≤1,|a_{ij}| \ge \beta \max_k |a_{kj}|, \qquad 0 \le \beta \le 1,

and among the admitted ones the smallest Markowitz count wins. β=1\beta = 1 is pure partial pivoting (stable, much fill-in), β=0\beta = 0 pure Markowitz choice (little fill-in, no stability guarantee); customary, and used in the eqnparser, is β=0.1\beta = 0.1. With equal Markowitz counts the entry of larger magnitude wins.

Convention in the framework: the enumeration PivotStrategy has four values (in Fortran MPIV 1 to 4, otherwise return code 28). MIN_FILL is the Markowitz choice with threshold β\beta described here, searching all remaining columns in every step – the default. MARKOWITZ takes the smallest Markowitz count without threshold (only magnitudes below apiv are excluded): least fill-in, no protection against small pivots. COLUMN is column pivoting: the columns in their order, in each step the element of largest magnitude. NONE takes the diagonal in natural order; if it is missing or 0, the factorisation ends with code 8. Until 2026-09-28 all four computed like MIN_FILL (finding WT1, fixed). On a 6×66\times 6 arrow matrix (NM1-GS-06) they produce 1, 0, 9 and 20 fill-ins.

Elimination with linked lists

Because new entries appear during elimination, CSR is no good as a working format. GSPAR keeps every non-zero as an element of one large array af (length ma) and links the elements twice: per row via jzei (next element of the same row, column index ascending), per column via izei. The heads of the lists are in iu/il (rows of U and L) and ju/jl (columns). jlu holds the column index of an element; for the pivot it is encoded as a negative number (−(j+1)-(j+1)), for L elements it holds the elimination step. Two counters per row and column – iez and ies – give the Markowitz counts without searching. A fill-in is appended at the end of af and inserted into both lists.

In addition GSPAR stores the pivot as its reciprocal 1/ukk1/u_{kk}: the multipliers of L are then formed by multiplication, and the backward substitution needs no division.

Pseudocode – GSPAR.dllugb (core of factorize)

for k ← 0 to mp−1:
    // 1. find the pivot
    for every open column i ≥ k:
        am ← max |a| over the column list i
        if am = 0:  add 1e−100 to one element up to 3 times, else return code 8   singular
        for every element je of the column with |a_je| ≥ β · am:
            cost ← (ies[i] − 1) · (iez[row(je)] − 1)                   Markowitz count
            keep je if the cost is smaller, on ties if |a| is larger
        compare with the best candidate of the previous columns (same rule)
    // 2. bring the pivot to position (k, k)
    row swap in iu, il, iez, ip, ipi;  column swap in ju, jp, jpi, ies
    decrease the column counters of the pivot row by 1;  mark pivot: jlu ← −(column+1)
    af[pivot] ← 1 / af[pivot]                                            reciprocal
    remove the pivot row from the column lists
    // 3. eliminate
    for every element e of the pivot column (except the pivot), row z:
        af[e] ← af[e] · af[pivot]                                         multiplier l_zk
        move e from the row list of U(z) to the L list of z
        // Schur complement: walk the sorted rows k and z simultaneously
        for every non-pivot element p of pivot row k:
            if row z has an element q in the same column:  af[q] ← af[q] − af[e] · af[p]
            else:  new element at the end of af: −af[e] · af[p]              fill-in
                  insert into row and column list, counters +1
                  if af is full: return code 16
mlu ← number of elements

Source: envisionz-framework-math/src/envisionz/math/linear/gspar/GSPAR.java, dllugb (1:1 port of Fortran lines 2027–2666), preceded by dllugc (working structure from CSR, empty rows or columns → return code 8), followed by dlluga (unit pivots for rows beyond mp) and dllugd (column lists of L and U for the solution).

Forward and backward substitution

With the row and column permutations PP, QQ we have PAQ=LUP A Q = L U. solve(ws, b) computes

Ly=Pb(forward),Uz=y(backward),x=Qz,L y = P b \quad (\text{forward}), \qquad U z = y \quad (\text{backward}), \qquad x = Q z,

where the column permutation does not appear as a separate step: the backward substitution writes each result straight to the position of the original column, which is encoded in the pivot element.

// forward
for i ← 0 to n−1:
    x[i] ← b[ip[i]] − Σ over the L list of i: af[e] · x[step(e)]
// backward; b is used as the result array and zeroed first
b ← 0
for i ← n−1 down to 0:
    s ← Σ over the U list of i, without pivot: af[e] · b[column(e)]
    b[column(pivot)] ← (x[i] − s) · af[pivot]                    af[pivot] = 1/u_ii
x ← b

Source: GSPAR.java, dlsolk. In the original, DLSOLA then contained a block X(I)=B(I) that overwrote the backward substitution; in the port DLSOLA is gone.

Convention in the framework: GSPAR.solve(ws, b) overwrites b (it serves as working array). Anyone needing the same right-hand side several times passes a copy – during the move a comparison probe against LinAlg deviated by 0.086 for exactly this reason. Check NM1-GS-04 pins the contract down.

Refactorisation with the same structure: the pseudocode

In Newton's method only the numerical values of the Jacobian change from iteration to iteration, not its sparsity. The pivot order of the first factorisation is kept, and after factorize GSPAR generates a pseudocode (GSPARPseudoCode.generate, Fortran DLDPCA to DLDPCY): a list of integer instructions describing exactly the arithmetic of the factorisation and of the forward and backward substitution – which elements meet in which scalar product – without searching and without walking lists. The elements are ordered by level: the level of an element is 1 plus the highest level of the elements it is computed from. All instructions of one level are independent of each other (in the original intended for vector computers). Each instruction is a 32-bit word, the upper 16 bits being the instruction type, the lower ones the element count.

For the matrix from section storage format there are 8 levels for the factorisation, 5 for the forward and 4 for the backward substitution (groupsLU/FW/BW in the workspace).

Convention in the framework: the pseudocode path currently does not compute correctly (open item GS1): solveInPlace returns the right-hand side unchanged, and refactorize(ws, apiv) reports “Pivot too small” even with unchanged values and leaves unusable factors. The GSPARSolver in the eqnparser then falls back to a full factorize, the results are correct, the fast refactorisation never takes effect. What is checked and in use is the direct path factorize + solve. The Pseudocodeprobe records today's behaviour as a finding.

Condition estimate

estimateCondition(A, ws) estimates κ1(A)=‖A‖1‖A−1‖1\kappa_1(A) = \|A\|_1 \|A^{-1}\|_1 with the existing factorisation (Fortran DLCOND/DLNORA/DLNORI). ‖A‖1\|A\|_1 is the largest column sum of magnitudes. For ‖A−1‖1\|A^{-1}\|_1 a system with ATA^T is solved whose right-hand side is chosen during the computation from signs ±1\pm 1 so that the solution yy becomes as large as possible; then Az=yA z = y and

‖A−1‖1≈‖z‖1‖y‖1.\|A^{-1}\|_1 \approx \frac{\|z\|_1}{\|y\|_1}.

This is a lower estimate: for the matrix from section storage format it returns 161, the exact value ‖A‖1‖A−1‖1\|A\|_1 \|A^{-1}\|_1 (recomputed densely) is 241.

Convention in the framework: the estimate is scale-independent: the same matrix times 10−310^{-3} also gives 161 (NM1-GS-05). Until 2026-09-28 ‖A‖1\|A\|_1 was bounded below by 1 (anorm = max(anorm, 1.0)), and the same matrix times 10−310^{-3} gave 7013 (finding WT2, fixed).

How it is checked

  • SparseMatrixSelfTest (17 checks): CSR access, set outside the structure throws, triplets yield row starts and ascending columns, value transfer in sorted order; AB16: duplicate triplets (0,0)=5 and (0,0)=6 give 11, triple unordered duplicates, triplets without row grouping.
  • Linearprobe NM1-GS-01 … 04: 1D Laplace n=50n = 50 with xi=i+1x_i = i + 1 to 10−1210^{-12} (measured 2.1⋅10−132.1\cdot 10^{-13}); zero first pivot in [[0,1,1],[1,1,0],[0,0,3]][[0,1,1],[1,1,0],[0,0,3]] to 10−1410^{-14}; sparse random matrix 30×3030\times 30 equal to LinAlg.solve to 10−1310^{-13}; solve modifies the right-hand side.
  • Linearprobe NM1-GS-05 … 09 (2026-09-28): condition estimate for AA, 10−3A10^{-3}A and 103A10^{3}A equal to 10−1210^{-12}; arrow matrix 6×66\times 6 with fill-in per strategy MIN_FILL 1, MARKOWITZ 0, COLUMN 9, NONE 20, all solving to 10−1210^{-12}; NONE with zero first diagonal element → code 8; opCount for the Laplace matrix n=50n = 50 exactly 3⋅49+1=1483 \cdot 49 + 1 = 148.
  • Pseudocodeprobe (13 checks): generate error-free and repeatable, the direct path hits xi=i+1x_i = i + 1 to 10−1210^{-12}, memory and pivot limits report codes 4 and 24; four checks record finding GS1 and will turn red when it is fixed.
  • Counter-probes (gs-pivotkehrwert, gs-vorwaerts-permutation, pc-*) corrupt the pivot reciprocal, the permutation of the forward substitution and the pseudocode; each turns a probe red.

Limits

  • The pivot choice searches all open columns in every step – sufficient for the flowsheet sizes of the eqnparser (up to a few thousand equations), not intended for field problems with 10510^5 unknowns.
  • The memory for fill-in is estimated in allocate at five times the non-zeros; if it does not suffice, the factorisation ends with code 16 without requesting more by itself.
  • The fast refactorisation via the pseudocode currently has no effect (GS1); every new Jacobian is factored in full.
  • MARKOWITZ and NONE do not check the pivot size (apart from apiv or exact 0 respectively); for the Newton solvers MIN_FILL remains the choice.
  • The condition estimate is a lower estimate.
