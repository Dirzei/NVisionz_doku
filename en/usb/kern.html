The core – self-description, control requests, transfer types

A USB device describes itself: in descriptors it sends on request over the control endpoint. They tell which interfaces it has, which class they belong to and through which endpoints the data flow. The core reads this description following chapter 9 of the USB 2.0 specification, checks every number against the rest of the data and hands the classes a finished picture of the device.

What it is about

Between the classes (HID, UVC, CDC, USBTMC, UAC, MSC) and the line to the device lies a thin but strict layer. It builds control requests byte by byte, reads device and configuration descriptors, splits the configuration into interfaces, alternate settings, associations and endpoints, attaches the class descriptors to the place they follow, and reads strings. The line itself is only an interface, UsbTransport; behind it is the transport over usbfs on Linux (Linux via usbfs) and a simulated device in the tests.

The setup packet

Every control request starts with eight bytes: bmRequestType (bit 7 direction, bits 5–6 type: standard, class, vendor; bits 0–4 recipient: device, interface, endpoint), bRequest, then wValue, wIndex and wLength of two bytes each, least significant byte first. The request for the device descriptor of 18 bytes thus reads 80 06 00 01 00 00 12 00: 0x80 means "to the host, standard, device", 0x06 is GET_DESCRIPTOR, wValue carries index 0 in the low and type 1 (device) in the high byte, wIndex is 0, wLength 18=0x12⁡18 = \mathrm{0x12}.

The device may send less than requested, never more. What arrives is valid only up to the reported length.

Descriptors and how they are checked

Every descriptor starts with bLength and bDescriptorType. The device descriptor (table 9-8) has 18 bytes: USB version as a BCD number, class, subclass, protocol, packet size of the control endpoint, vendor and product ID, device version, three string indices and the number of configurations. The packet size of the control endpoint may only be 8, 16, 32 or 64. From USB 3 on it holds an exponent: the value 9 means 29=5122^9 = 512 bytes. Under USB 2, 9 is not a valid value and the descriptor is rejected.

The core reads the configuration in two steps. First it fetches the nine bytes of the header; they contain wTotalLength, the length of the whole block with all interfaces, endpoints and class descriptors. Only then does it request exactly that length. No device needs to know the size of the host's buffer in advance, and no host needs to guess.

Within the block every length only counts once it has been checked against the rest: a bLength of 0 would stall the loop, one that is too large would read past the end. Both are errors of the kind invalid, not runtime errors. An interface association (IAD) groups consecutive interfaces into one function, for example the control and data interface of a serial port. It names the first interface ee and their number nn, so it applies to the interfaces e,…,e+n−1e, \ldots, e + n - 1.

Strings

Names are not in the descriptor but stored as an index to a string descriptor. Index 0 is special: it returns the list of language IDs. The core requests strings in the first reported language and decodes them as UTF-16 with the least significant byte first; an odd length is invalid. If a device reports no language at all, there are no names, but the device remains usable; the profile then says why the names are missing.

An endpoint descriptor (table 9-13) names the address with direction, the type and wMaxPacketSize. For high-speed endpoints this field carries two values: bits 0–10 are the packet size, bits 11–12 the number of additional transactions per microframe. The bytes per microframe are

B=(wmod211)⋅(⌊w/211⌋mod4+1),B = \left(w \bmod 2^{11}\right) \cdot \left( \left\lfloor w / 2^{11} \right\rfloor \bmod 4 + 1 \right),

so for w=0x1400⁡=5120w = \mathrm{0x1400} = 5120 they are 1024⋅3=30721024 \cdot 3 = 3072 bytes. Reading only the lower bits reserves a third of the bandwidth and loses two of three packets.

Classes

Which class an interface speaks is stated in its descriptor as base class (one byte), subclass and protocol; if the device descriptor holds 0x00, the interface decides, 0xEF with an IAD the association. The core translates the base classes following the list of standard classes (0x01 audio, 0x02 communication, 0x03 HID, 0x08 mass storage, 0x0A CDC data, 0x0B smart card, 0x0E video, 0xFE application specific, 0xFF vendor specific and more). A vendor-specific interface is left untouched: vendor commands are not guessed.

The classes themselves sit on top. Their numbers are the same kind of self-description one level deeper: the report descriptor of a HID interface states bit by bit where in a report each field lies; a video interface describes formats and frame sizes; a mass storage device answers SCSI commands with fixed structures in which large numbers carry the most significant byte first. A logical block address above 2322^{32} needs READ(16); a capacity whose last block lies above 2632^{63} cannot be represented by a signed Java long and is rejected.

How it meets the core

The core makes no request the device does not report, and it relies on no answer it has not checked. So that this can be shown without hardware, the simulated device plays the rules of the specification, more strictly than some real devices:

  • An answer is truncated to wLength; a buffer that is too small is an error of the caller.
  • Unknown requests, missing alternate settings and missing descriptors are answered with STALL.
  • GET_CONFIGURATION returns one byte with the value of the selected configuration, GET_STATUS two bytes.
  • Endpoints other than 0 only speak once their interface is claimed; a packet larger than the buffer is babble.
  • Isochronous packets only come from the selected alternate setting.

A class example for bulk transfers: after a block that fills exactly a whole number of full packets, a serial port sends a packet of length 0 so that the other side recognises the end (USB 2.0, 5.8.3). Writing zero bytes, on the other hand, causes no traffic. A disconnected device ends the input stream with −1, like an end of file.

How it is checked

  • Usbprobe: setup packets byte by byte, a configuration with association, alternate settings, isochronous endpoint and class descriptors, two-step reading, strings, broken descriptors and 3000 random sequences that may only produce errors of the kind invalid.
  • Randfallprobe ([ZD-US-01] to [ZD-US-17]): class codes, usage names and status codes following the tables of the specifications, the device descriptor field by field, the packet size under USB 3, the association, the standard requests of the simulated device, devices without configuration or without languages, and the limits of the SCSI structures.
  • Cdcprobe ([ZD-US-18] to [ZD-US-22]): length 0, a single byte, available bytes, disconnected device, closing twice.

Each of these rules has a counter-test that breaks it in the source; all of them turn red.

Limits

  • Simulated devices only. Error paths that only a real device triggers (a device that sends less than announced, or a status error in the middle of an instrument answer) cannot be set up in the simulation and remain unchecked.
  • Reading before writing. Mass storage is only read; output to the device for sound and picture is missing.
  • Vendor protocols stay outside. Converters with their own protocol do not belong to the core.
