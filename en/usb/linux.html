Linux via usbfs – the line to the device without libusb

On Linux the kernel exposes every USB device as a file /dev/bus/usb/BBB/DDD. Whoever opens it talks to the device through a handful of ioctl calls: control requests, bulk and interrupt transfers, isochronous packets, claiming interfaces. The module calls them directly through FFM, without a third-party library. Numbers and structures are recomputed from the kernel header, not copied.

What it is about

The classes in framework-usb (HID, UVC, CDC, USBTMC, UAC, MSC) know only the interface UsbTransport: control request, bulk, interrupt, isochronous, select alternate setting, claim and release an interface. This module is its Linux side. The kernel does the actual bus work: it schedules the transfers, retries on line errors and caches the descriptors. The transport only has to hand over the request in the form the kernel expects. Where a request touches the kernel's own state, it must also use the dedicated call for it.

The ioctl numbers

An ioctl number is not arbitrary. It is built from four fields, as in the kernel macro _IOC(dir, type, nr, size): two bits of direction (1 = kernel writes, 2 = kernel reads, 3 = both), fourteen bits for the size of the structure passed, eight bits of type (for usbfs the letter 'U' = 0x55) and eight bits of sequence number.

The module computes every number this way, from the sizes of the rebuilt structures. If a size is wrong, the number is wrong too, and the kernel rejects the call. The computation therefore also checks the structures.

The structures

Rebuilt are the structures from include/uapi/linux/usbdevice_fs.h for 64 bits (x86_64, aarch64), including the gaps the compiler inserts to align pointers:

usbdevfs_ctrltransfer24header of the control request (bmRequestType, bRequest, wValue, wIndex, wLength), timeout, pointer to the data

usbdevfs_urb56type, endpoint, status, flags, buffer (offset 16), buffer length (24), number of packets (36); followed by one usbdevfs_iso_packet_desc of 12 bytes per packet
usbdevfs_getdriver260interface and driver name (256 bytes, null-terminated)
usbdevfs_disconnect_claim264interface, flags, driver name

Requests the kernel must carry out itself

Three standard requests change state the kernel keeps. Sent as an ordinary control request to the device, kernel and device would disagree afterwards:

  • CLEAR_FEATURE(ENDPOINT_HALT) resets the data toggle of the endpoint on the device; the kernel must reset it as well, otherwise it discards the next packet as a repeat. Hence USBDEVFS_CLEAR_HALT. Only feature 0 addressed to an endpoint counts; any other feature takes the ordinary path.
  • SET_INTERFACE selects an alternate setting and with it new endpoints; the kernel must know them. Hence USBDEVFS_SETINTERFACE.
  • SET_CONFIGURATION likewise, via USBDEVFS_SETCONFIGURATION.

Kernel error numbers become error kinds of framework-usb: EPIPE is a STALL of the device, ETIMEDOUT an expired timeout, ENODEV a disconnected device, EACCES missing permissions (with a hint at a udev rule).

Isochronous transfer

Isochronous endpoints, for instance of a camera or a sound card, deliver one packet per (micro)frame, without retries on errors. usbfs accepts a URB (USB Request Block) for this: a header and, per packet, a description with the expected length. The transport sets up n packets of platz bytes each, submits the URB with USBDEVFS_SUBMITURB and collects it with USBDEVFS_REAPURBNDELAY. If the kernel answers EAGAIN, the URB is still in flight, and the transport asks again after one millisecond.

From submission on, the memory belongs to the kernel. On an error, when the timeout expires and when the thread is interrupted, the URB is therefore first cancelled with USBDEVFS_DISCARDURB and reaped with USBDEVFS_REAPURB. Only then is the memory released. After reaping, each packet stands on its own: a packet with non-zero status or an impossible length gets length −1, the others their real length. If the timeout expires but a packet has arrived anyway, the result counts. Only without any packet does the transport report a timeout.

Interfaces and kernel drivers

Before an endpoint is used, its interface must be claimed (USBDEVFS_CLAIMINTERFACE). If it already belongs to a kernel driver, such as uvcvideo for a built-in camera, the kernel answers EBUSY. The transport then names the driver (USBDEVFS_GETDRIVER) and does not detach it on its own. Only with trenneTreiber(true) does it detach the driver and claim the interface in one step (USBDEVFS_DISCONNECT_CLAIM). On release it reattaches the driver via USBDEVFS_IOCTL with USBDEVFS_CONNECT. The device is thus missing from the system only while it is used here. On close, every interface still claimed is released, and the node is closed exactly once.

How it is tested

Without Linux and without a device, against two stand-ins:

  • Usbfsprobe (45 checks): the 16 ioctl numbers against the values from the header, sizes and offsets of the structures, the mapping of error numbers, the special cases and device discovery via a rebuilt sysfs tree. On Linux, a comparison of the descriptors read via the control path with sysfs and the kernel cache is added for every reachable device.
  • Transportprobe (50 checks): the transport calls the kernel through a narrow seam (Systemaufrufe: open, close, ioctl, read). In the probe a rebuilt kernel sits behind it. It reads the passed structures field by field, as the real kernel reads them, and answers or fails on request. Checked are opening with O_RDWR | O_CLOEXEC, the control header byte by byte, input and output, the special cases, bulk with offset and the URB fields. Also checked are EAGAIN, packet lengths, cancel and reap on error, timeout and interruption, claiming with and without detaching the driver, and release and close.

Each of these rules has a counter-probe that corrupts it in the source; all 23 turn red.

Limits

  • One URB per call. Between two isochron calls no URB is submitted, and the packets of those frames are lost. A gapless stream would need several URBs in flight; that is still open.
  • 64 bits only. The structures, and therefore the numbers, are computed for x86_64 and aarch64.
  • Not tested on real hardware. The rebuilt kernel follows the header. How real devices and real drivers behave will only show in a run on Linux.
  • Permissions. Without write access to the node nothing works; the error message points to a udev rule.
  • The FFM calls themselves (Libc) only run on Linux and are not yet in the native-image metadata.
