Launching kernels and waiting – command buffers, barriers, descriptor sets and where the time goes

What happens between starte and the result: how Vulkan records launches into a command buffer and submits them as a batch, why a barrier has to stand between two kernels, how buffers reach kernels through descriptor sets, and what a measurement on a card says about the cost of a launch – with pseudocode and figures.

What this is about

A kernel on the card is fast; often everything around it is expensive. A kernel over 4,096 values computes in about a microsecond on an integrated graphics unit. Submitting it alone and waiting for the end costs 9 µs on the same device under OpenCL and about 90 µs under Vulkan. Whoever launches many small kernels – a CFD step has a dozen per stage – must above all avoid one thing: waiting for each one separately.

Recording and submitting

Under Vulkan vkCmdDispatch does not compute; it writes a command into a command buffer. Only vkQueueSubmit hands the buffer to the card, and a fence signals when everything is done. The framework's Warteschlange maps this as follows:

starte(k, n):
    if a batch was submitted and not awaited:  abwarten()
    if k's set is stale:  new descriptor set (see below)
    if first launch in the batch:  vkBeginCommandBuffer
    else:  barrier: shader writes → shader reads and writes
    vkCmdBindPipeline(k);  vkCmdBindDescriptorSets(k.set)
    vkCmdPushConstants(k.numbers)                    the numbers are copied now
    vkCmdDispatch(⌈n / group⌉, 1, 1)

fertig():   abschicken();  abwarten()

abschicken():
    barrier: shader writes → reads by the host
    vkEndCommandBuffer;  vkQueueSubmit(buffer, fence)  under the device lock

abwarten():
    wait for the fence (spin or sleep, see below)
    vkResetFences;  vkResetCommandBuffer;  reset used set pools

lies(p, target):  fertig();  copy from the mapped memory
schreibe(p, w):   fertig();  copy into the mapped memory

Source: envisionz-framework-vulkan/src/envisionz/vulkan/Warteschlange.java.

Because the numbers of a launch are copied at recording time, the caller may change arg between two launches of the same kernel – that is how the four stages of Jameson run with four different α in the same batch. Because lies and schreibe call fertig() first, the caller never sees a half-computed buffer.

Barriers between kernels

The card may overlap consecutive dispatches. If the second kernel reads what the first one writes, a barrier (vkCmdPipelineBarrier) must stand in between: all writes of the shader stage become visible before the next shader stage reads. The framework puts one between every two launches – also where it would not be needed. In kernel chains like the CFD step, where almost every kernel depends on the previous one, that costs hardly anything, and it prevents a class of errors that only show up sometimes and only on some cards. Under OpenCL the command queue does the same on its own.

A barrier towards the host (shader writes → host reads) stands at the end of every batch. Only after it and after the fence are the results in the mapped memory reliable to read.

Descriptor sets

A kernel sees its buffers through a descriptor set: binding 0 is this buffer, binding 1 that one. A set used by a recorded, not yet finished batch must not be changed. The framework keeps to a simple rule:

  • Every kernel has a pool of 256 sets.
  • arg(i, buffer) with a different buffer than before marks the current set as stale. The next launch takes a new set from the pool and writes it; the old one stays untouched for the launches already recorded.
  • If the pool is empty, the batch is submitted and awaited automatically; after that the whole pool is available again.

In the CFD step a kernel's buffers never change – each kernel gets its sets once and keeps them. Probe VK-09 switches 600 times within one batch and requires every result to be right; a counter-probe keeps the set after a buffer change and has to turn red.

Waiting: spin or sleep

vkWaitForFences puts the thread to sleep until the driver wakes it. The first measurement on the card suggested that the wake-up comes late. On cards the framework therefore polls the fence itself (vkGetFenceStatus in a loop, at most 50 ms, then sleep after all); on CPU devices it sleeps right away, because spinning there takes the cores away from the driver. Switch with -Denvisionz.vulkan.warten=kreisen|schlafen (spin|sleep) or in the settings.

Where the time goes – measurement

The measuring tool tools\vulkan-messen.cmd computes y = a x + y in double, 1,000 launches, once as a batch and once singly, and breaks down the time. "On the card" is the distance between two timestamps the card itself writes before the first and after the last kernel (vkCmdWriteTimestamp):

Batched, Vulkan is faster than OpenCL. Singly, the card computes for only 12 µs; the large rest of about 80 µs lies between the submission and the signal that the fence is set – in the path through driver and operating system, not in the framework's waiting. Spinning instead of sleeping therefore brings only about 10 %.

Two rules for the framework follow:

  • Wait as rarely as possible. Without CPU boundaries the CFD step submits exactly one batch per step; norm and time step are read only at the end. With this rule the whole step via Vulkan was faster than via OpenCL in seven of eight measured cases.
  • Measure before rebuilding. Whether the completion signal arrives faster through memory than through the fence is measured by the tool as a row of its own: a tiny second kernel writes a number into visible memory, Java reads it in a loop (Warteschlange.abschicken, liesOhneWarten), and it is compared with the fence and with whether the data are already complete at that moment.

The signal through memory arrives 5 to 35 µs earlier than the fence – but the results of the computing kernel are not reliably visible at that moment: in one variant only in 107 of 1000 cases. Without the barrier towards the host, which only the fence completes, Java sees the signal before it sees the data. Most of the waiting time (about 40 µs) also lies before the signal, in the start-up. The framework therefore stays with the fence; the gain comes from the number of waiting points, not from their kind.

Under OpenCL

OpenCL has no recorded command buffers in the Vulkan sense; every launch is enqueued into a command queue that the driver processes in order. A blocking read waits for everything before it. The batch thus forms by itself as long as nobody reads in between. That is why the same rule – read norm and dt only at the end – applies to both back ends.
