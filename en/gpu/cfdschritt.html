The whole explicit CFD step on the graphics unit

Why not only the residual but the whole time step belongs on the device; which 22 kernels run per stage, what crosses the bus per step, how boundaries only the CPU knows still take part, and how the solver chooses the implementation and falls back to the CPU – with pseudocode following the source.

What this is about

An explicit time step of the Euler solver consists of several stages (four with Jameson, three with SSP-RK3), and each stage computes a residual: primitive variables, boundary values, gradients, limiters, fluxes over all faces, sum per cell. The first attempt put only the most expensive part, the fluxes and the sum, on the graphics unit. It was slower than the CPU: gradients, limiters and boundaries stayed on the CPU, and every call sent the state up and the residual down.

Since then the whole step runs on the device. The state goes up once per step and down once; in between everything stays on the card. Measured on an integrated notebook graphics unit, the step became 2.2 to 3.7 times as fast as eight CPU threads.

The interface Schrittkern

The solver (framework-cfd) stays pure JDK and does not know the graphics unit. It knows only the interface envisionz.cfd.loeser.Schrittkern; the implementations live in their own modules and register with the ServiceLoader through META-INF/services:

ImplementationModuleKernels
OpenClSchritt (name opencl)framework-cfd-openclOpenCL C, compiled by the driver
VulkanSchritt (name vulkan)framework-cfd-vulkanthe same text, through the framework's own compiler to SPIR-V

On opening, the solver hands over an Aufgabe (task): the mesh (owner and neighbour per face, faces per cell, normals, face areas, centres, volumes), the method (order, gradient, limiter, Jameson or SSP-RK3, local or global time step, CFL, rotation), the kind of every boundary and exchange arrays for the CPU boundaries. Back comes a Sitzung (session) with schritt(u, zeit, grenze).

Pseudocode – choice and fallback (following Schrittkern.kandidaten and EulerLoeser.schrittBereit)

if not chosen (case file -grafikeinheit:schritt, setting or -Denvisionz.cfd.gpu=schritt):  CPU
if implicit or not Roe or viscous or real gas or turbulence or species or source:
    CPU, remember the reason                            "nur mit Roe-Fluss (hier hllc)" …
candidates ← all implementations on the class path
if -Denvisionz.cfd.schrittkern = name:  candidates ← only those with that name
else:  order by VORRANG = (vulkan, opencl), then the rest
for each k in candidates:
    try:  session ← k.oeffne(task);  done
    catch error e:  reasons ← reasons + (k.name + ": " + e)  no device, no double, switched off …
if no session:  CPU, reason = reasons                  e.g. "vulkan: …; opencl: …"

EulerLoeser.grafikeinheit() shows the reason, and the command line writes it to the log: "Schritt: CPU (nur Euler (ohne Zaehigkeit))" or "Schritt: Grafikeinheit, ganzer Schritt (Vulkan: …)". A solver that silently computes on the CPU although you wanted the card would be a bad surprise.

Since October 2026 VulkanSchritt talks to the device only through the common layer framework-gpu (see The same notions for both). It is registered for Vulkan; with -Denvisionz.cfd.vulkan.rueckende=opencl the same sequence runs via OpenCL. This lets the lean step be compared on both back ends, and the probe demands a result bit-identical to the CPU via OpenCL as well.

Every kernel performs the same operations as the Java code in EulerLoeser, Gradienten, Limiter, Roe and Gas, in the same order. The face kernels compute the flux for inner faces and device boundaries alike; faces computed by the CPU they leave out.

Sequence of a step

Pseudocode – Sitzung.schritt(u, zeit, grenze) (following VulkanSchritt, OpenCL alike)

write u up;  bad ← INT_MAX
launch kopiere                                        u0 ← u
residual(time, withLambda = yes)
launch normquadrate, zeitschritt
if global:  launch minTeil, minEnde(limit), fuelle
early ← SSP-RK3 and there are CPU boundaries        only then does the callback need dt now
if early:  (norm, dt0) ← normAndDt()
if Jameson:
    for α in (1/4, 1/3, 1/2, 1):
        if not the first stage:
            if CPU boundaries and bad():  return nothing
            residual(time, no)
        launch stufe(α), pruefe
else (SSP-RK3):
    launch stufe(1), pruefe;    residual(time + dt0);    launch stufeSsp(2), pruefe
    residual(time + dt0/2);     launch stufeSsp(3), pruefe
if bad():  return nothing                         the solver computes the step on the CPU
if not early:  (norm, dt0) ← normAndDt()             only now: no waiting in mid-step
read u down
return (norm, dt0)

normAndDt():
    read the squares per cell and dt of cell 0
    s ← 0;  for c = 0 … zz−1:  s ← s + quad[c]       in sequence like EulerLoeser.norm
    return (√(s/zz), dt[0])

Under Vulkan starte only records. The first read – here bad() at the end – submits all kernels of the step as one batch and waits once. After that the norm squares, dt and u are readable without further waiting. Under OpenCL starte enqueues, and the first blocking read waits likewise. Formerly norm and dt were read right after the first residual; that stalled the queue in mid-step and cost a second submission of about 100 µs under Vulkan.

Boundaries only the CPU knows

Wall, extrapolation and boundaries with a fixed state (inflow with a fixed ghost) are computed by the device itself. Far field per Riemann invariants, inlet with total quantities, outlet with radial equilibrium, periodic boundaries and the mixing plane need field averages, partner cells or iteration – that stays Java. Instead of rebuilding these boundaries in OpenCL C, the CPU computes them per stage with exactly its own code, through a callback:

residual(t):
    launch primitiv, randwerte
    if CPU boundaries:
        read w down;  callback.randwerte(t)              field averages, boundary values of the CPU boundaries
        pack their boundary values, write up, launch verteile
    if order 2:  launch gradienten, bezugTeil, bezugEnde, begrenzer
    if CPU boundaries:
        if order 2:  launch sammle; read gradient and limiter of the cells involved
        callback.randfluesse(t)                          with flux-conserving mixing plane
        pack their fluxes, write up, launch verteile
    launch flaechen, zellen

That costs two waiting points per stage and is the reason why cases with many such boundaries gain less. The advantage: no second code for boundary conditions, and the probe can still check them bit-identically against the CPU.

No physical state

If the density or internal energy of a cell becomes negative in a stage, the kernel pruefe calls atomic_min(schlecht, c). At the end of the step – or before the next CPU callback, which could do nothing with a broken state – the session reads schlecht. If a cell is there, schritt returns nothing, the state stays unchanged, and the solver computes the same step on the CPU. That produces the same error message with the same cell as without the graphics unit ("Zelle 10 bei (0.35, 0.038, 0.05) nach Schritt 0: … CFL senken oder erste Ordnung"); the probe checks exactly that.

Integrated notebook graphics unit with double in hardware, tools\cfd-gpu-messen.cmd -schrittkern:opencl,vulkan, with one submission per step. Vulkan is faster than OpenCL in seven of eight cases, except on the smallest first-order mesh – there one submission under Vulkan weighs more than the whole computation. The deviation from the CPU was around 10−15 relative for both. For comparison, the measurement before norm and dt were moved to the end (two submissions per step): Vulkan 15.0 instead of 14.3 ms at 80,000 cells second order and 62.0 instead of 55.4 ms at 320,000 – but the CPU also varied by a few percent between the two runs.

How it is checked

Both back ends have a probe with the same cases: wedge Mach 2 first order with local time step, second order with global time step up to an end time (reductions), Barth-Jespersen with velocity as a vector and Green-Gauss, rotating frame, cylinder with far field (CPU boundaries), step with periodic boundaries and mixing plane, the versions of the face kernel, no physical state, restart file (the fluxes come from the device), switched off. The comparison is step by step with the CPU path of the same solver – bit-identical on the CPU emulations. The Vulkan probe also counts the submitted batches (one per step without CPU boundaries) and checks the fallback to OpenCL.
