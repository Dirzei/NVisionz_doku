The path to the graphics unit – FFM, driver library, device, buffer and kernel

How the framework calls a C interface of the graphics driver from pure Java: the three tools of the foreign function and memory interface (FFM), structs byte by byte, and then step by step what OpenCL and what Vulkan need before a kernel computes – with pseudocode following the source and the reasons for each choice.

What this is about

A graphics unit is not addressed like a Java object but through the C interface of its driver. For OpenCL that is the library OpenCL.dll (on Linux libOpenCL.so.1), for Vulkan the loader vulkan-1.dll (libvulkan.so.1). Both are present on every machine with a current graphics driver.

The usual way is to ship a binding library that wraps this interface in Java classes. The framework does not: every such library brings its own native code, its own versions and its own bugs, and it ages faster than the driver. Since Java 22 the JDK itself contains what is needed – the foreign function and memory interface (java.lang.foreign, FFM for short). The "binding" thus shrinks to two classes: Cl with about 25 and Vk with about 50 function handles.

FFM in three moves

Each C function needs three things: its address in the library, a description of its signature, and memory for everything that goes in or comes out as a pointer.

  1. Load the library: SymbolLookup.libraryLookup(name, arena) loads the library and finds symbols by name. If the library is missing an exception is thrown – the framework turns it into "kein OpenCL (OpenCL.dll)" and computes on the CPU.
  2. Build the handle: Linker.nativeLinker().downcallHandle(address, FunctionDescriptor.of(...)) returns a MethodHandle. The descriptor names return value and parameters in C terms: JAVA_INT for cl_int/VkResult, JAVA_LONG for size_t and VkDeviceSize, ADDRESS for every pointer and every handle.
  3. Memory: arena.allocate(bytes, alignment) gives a MemorySegment outside the Java heap; fields are written and read with set/get at fixed byte offsets.

Pseudocode – one handle and one call (following Cl and OpenCl.baue)

lib ← SymbolLookup.libraryLookup("OpenCL.dll")
if lib missing:  throw "kein OpenCL (OpenCL.dll)"
getPlatformIDs ← handle(lib.find("clGetPlatformIDs"),  int ← (int, pointer, pointer))
-- first ask how many, then fetch: the usual pattern of C interfaces
n ← new int memory
rc ← getPlatformIDs(0, NULL, n)
ids ← new memory for n pointers
ok(getPlatformIDs(n, ids, NULL), "clGetPlatformIDs")      rc ≠ 0 → exception with name and code

Source: envisionz-framework-opencl/src/envisionz/opencl/Cl.java, OpenCl.java; for Vulkan Vk.java, Vulkan.java.

If a required function is missing in the library, building the handles stops with its name ("Vulkan ohne vkCmdDispatch"). Optional functions – such as vkEnumerateInstanceVersion, which a version 1.0 loader lacks, or the timestamps – are null, and the caller works around them.

Structs by hand

Most calls take a struct. FFM could describe it through a StructLayout; the framework writes the fields directly at their offsets, with a comment naming the struct. That way the call shows what goes in, and no layout has to be reconciled with the C header. The rules on 64 bit are simple: pointers and 64-bit numbers sit at offsets divisible by 8, 32-bit numbers at offsets divisible by 4, and the total size is rounded up to the largest alignment.

A wrong offset rarely shows as a crash, usually as a wrong value. That is why each of these spots hangs on a probe that compares the result with Java, and on counter-probes that deliberately shift an offset (for instance the push block without std430 alignment).

OpenCL: platform, device, context, program

OpenCL is the older and more convenient interface: the driver compiles the kernel source itself and manages memory and dependencies between launches. The way to the first kernel is short.

Pseudocode – opening the device (OpenCl.oeffne, once per JVM)

if -Denvisionz.opencl=aus:  return null           grund() says so
type ← GPU;  if -Denvisionz.opencl.alle=ja:  type ← all    CPU devices too, for probes
for each platform p (clGetPlatformIDs):
    if p has a device of type:  device ← the first;  leave
if no device:  throw "kein OpenCL-Grafikgeraet"
context ← clCreateContext(device)
return Geraet(device, context, name)

Pseudocode – a kernel computes

prog ← clCreateProgramWithSource(context, source)
rc ← clBuildProgram(prog, options)                     e.g. -cl-opt-disable
if rc ≠ 0:  throw message with the compiler log (clGetProgramBuildInfo)
q ← clCreateCommandQueue(context, device)               one per thread
p ← clCreateBuffer(context, bytes)
clEnqueueWriteBuffer(q, p, blocking, values)
k ← clCreateKernel(prog, "axpy");  clSetKernelArg(k, i, value) for each argument
clEnqueueNDRangeKernel(q, k, global = rounded_up(n, group), local = group)
clEnqueueReadBuffer(q, p, blocking, target)             waits for everything before

The driver knows the order within a queue and itself ensures that a kernel only reads what the previous one wrote. The framework sets the work-group size (64) because the driver's choice is often 1 for odd sizes; the global size is rounded up to a multiple, and every kernel checks if (i < n) itself.

Vulkan: instance, device, memory, pipeline

Vulkan is built for graphics and leaves almost everything to the program: which memory, when to wait, how buffers are bound to a kernel. In return a launch is cheap, and nothing happens behind your back. Computing here means compute: a compute shader in a compute pipeline, launched with vkCmdDispatch.

Pseudocode – opening the device (Vulkan.oeffne, once per JVM)

instance ← vkCreateInstance(API 1.1)
best ← none
for each physical device d:
    rank ← discrete 0, integrated 1, virtual 2, CPU 3 (only with .alle=ja), otherwise rejected
    family ← first queue family with COMPUTE
    if rejected or no family or version < 1.1:  remember the reason;  continue
    if rank better:  best ← d
if none:  throw "kein passendes Vulkan-Geraet: " + reasons
features ← switch on shaderFloat64 and shaderInt64 if present
device ← vkCreateDevice(best, one queue of family, features)
-- memory: visible and coherent for the host is mandatory; device-local +2, cached +1
memoryType ← best type with HOST_VISIBLE | HOST_COHERENT

The choice of memory is the main difference from a graphics application. The framework puts every buffer into memory the host can also see and maps it permanently (vkMapMemory once on creation). Writing and reading are then plain copies into the mapped range, without transfer commands. On an integrated graphics unit this memory is also device-local – there is only one. On a discrete card a device-local buffer with transfers would be faster; this is a deliberate simplification.

Pseudocode – buffer and kernel (Warteschlange.puffer, Warteschlange.kern)

buffer(bytes):
    b ← vkCreateBuffer(bytes, STORAGE_BUFFER)
    req ← vkGetBufferMemoryRequirements(b)            size, allowed memory types
    if memoryType not allowed:  throw
    m ← vkAllocateMemory(req.size, memoryType);  vkBindBufferMemory(b, m)
    mapping ← vkMapMemory(m)  filled with zeros       stays mapped

kernel(description):                                 SPIR-V words, group, parameters
    module ← vkCreateShaderModule(words)
    setLayout ← bindings 0 … p−1, each STORAGE_BUFFER, for COMPUTE
    pipelineLayout ← setLayout + one push range of size description.push
    pipeline ← vkCreateComputePipelines(module, entry = kernel name)
    pool ← vkCreateDescriptorPool(256 sets)           see "Launching kernels"

Source: envisionz-framework-vulkan/src/envisionz/vulkan/Vulkan.java, Warteschlange.java, Kern.java.

Buffers are not passed as pointers as in OpenCL but through descriptor sets: a set says which buffer hangs at which binding. Numbers – n, a, gamma – go along as push constants: a small block (at least 128 bytes) that is copied into the command buffer when recording. The order of the kernel parameters stays the same as in OpenCL C; Kern.arg(i, …) puts a buffer at its binding or a number at its offset in the push block.

A queue belongs to one thread. Several threads share the device but not their buffers and kernels. In Vulkan the device's compute queue is a single one; vkQueueSubmit is therefore called under a device lock. The probes let four (Vulkan) or eight (OpenCL) threads compute at the same time.

Switching off, fallback, native image

All paths to the card are optional. -Denvisionz.opencl=aus and -Denvisionz.vulkan=aus switch off; ….bibliothek=PATH takes another driver library, ….alle=ja admits CPU devices. The emulations on the CPU (for OpenCL a free driver, for Vulkan the software driver from Mesa) are the build environment of the probes: there bit-identical results are mandatory.

The modules using FFM are not in the native image. The computing modules do not depend on them but only on an interface, and find an implementation through the ServiceLoader – or none, then the CPU computes. The JVM needs --enable-native-access=ALL-UNNAMED, otherwise it warns at the first handle.
