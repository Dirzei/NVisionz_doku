Tuning per graphics unit – which form of a kernel runs fastest on this card

A kernel that is fast on one card can be slow on another: work groups, results per thread and tiles in local memory suit one design and not the next. Instead of adjusting the kernels for every card by hand, the framework tries on the computer itself, checks every candidate against the CPU, measures it on the real products and remembers the fastest – per device and driver.

What this is about

The matrix kernel of training on the graphics unit was tuned for an integrated notebook graphics unit: work groups of 16 × 16 threads, 4 × 4 results per thread, tiles of 16 values in k. On a dedicated notebook card from another vendor the simple tiled product ran at 17 to 38 GFLOP/s for the long head of the language model (4 096 × 192 × 8 000), but at 311 GFLOP/s for the square product 1 024³ – the card can do more, the form of the kernel does not fit. Which form fits cannot be predicted; it depends on the number of registers, the size of local memory, the width of subgroups and the driver. So it is measured.

What is tuned

A form of the matrix kernel C = op(A) op(B) has five sizes; it is written as text like t32x8r4x8k16:

SizeMeaningGrid of the tuning
tx × tythreads per work group (columns × rows)16×16, 32×8, 8×32, 16×8, 8×16, 32×4, 64×4, 32×16
rm × rnresults per thread2×2, 2×4, 4×2, 4×4, 4×8, 8×4, 8×8, 2×8, 8×2
rkvalues in k per tile in local memory8, 16, 32

Each work group produces a block of ty·rm × tx·rn results. A thread holds rows ty + ty·i and columns tx + tx·j, so neighbouring threads write neighbouring columns. Summation follows the same order as the previous kernel (k ascending); with 16, 16, 4, 4, 16 it is exactly the previous register kernel.

global(M, N) = ( ⌈N / (tx·rn)⌉ · tx ,  ⌈M / (ty·rm)⌉ · ty )      local = (tx, ty)
local memory = 4 · rk · ((ty·rm + 4) + (tx·rn + 4)) bytes             +4 columns against bank conflicts

In addition come the fixed kernels of the main program – register (the reference), r84, r48, r88 – and, if the driver reports the vendor's extension for matrix engines, their kernels xmx, xmx22, xmx44. They compute in bf16; -Denvisionz.opencl.matrix.bf16=nein leaves them out.

Procedure

tune():
    products ← the matrix products of one training step with their count
    for each form f of the grid with rk = 16:                               coarse
        if f does not fit the device (threads, local memory): skip
        compile, check against the CPU, measure once on the three largest products
    fine ← the six fastest forms, each with rk = 8, 16, 32
           + register, r84, r48, r88 (+ xmx, xmx22, xmx44 with matrix engines)
    for each candidate in fine:                                           fine
        check; on all products three rounds of three launches, median
        performance = Σ floating-point operations / Σ count · time
    choice ← the fastest correct one; but register as long as none beats it by more than 2 %
    remember(device, choice)                                                not on cancel

The products follow exactly the calls in the training step: per layer forward q, k, v, o, gate, up, down, backward the gradients for inputs and weights (21 products), plus three times the head with the vocabulary. The probe compares the list with a trace of the real calls.

The 2 % threshold is deliberate: two equally good kernels differ by a few percent in measurement, and a choice made of noise should not displace the proven default.

Every candidate first computes against the CPU

Before it is measured, every candidate computes six odd-sized products – all four transpose cases, edges in every direction, with and without beta – and is compared with a sum in double. The bound per element is the usual one for a sum of K products in float:

| cij − cijdouble | ≤ 2 K · 2−24 · ( Σk | aik bkj | + | β cijold | )

A different summation order or a fused multiply lies far below; a wrong index or a missing tile lies in the order of the sum itself. For the matrix-engine kernels the comparison is against double from bf16-rounded inputs. A candidate that computes wrongly is listed with place and value and can never be chosen; the probe deliberately spoils one kernel by a thousandth for this.

A form that does not compile or does not launch is listed with the reason ("nicht übersetzt", "nicht lauffähig"); a form that needs more threads or local memory than the device has is not compiled at all.

Remembered per device and driver

The result is stored in <home>/.envisionz/gpu-abstimmung.properties (or -Denvisionz.gpu.abstimmung.datei=PATH) – one file for the user interface and the command line, so training from tools\ uses the same choice the settings measured. The device key contains name, driver version and number of compute units: a new driver is a different device, and the old choice no longer applies until tuned again.

matrix@Graphics card X | 1.2.3 | 16 RE.wahl = t32x8r4x8k16
matrix@Graphics card X | 1.2.3 | 16 RE.wert = 142.3
matrix@Graphics card X | 1.2.3 | 16 RE.bezug = register        (example, not a measurement)

A cancelled run and one without a correct candidate are not remembered. Some devices report their name with "@ clock rate"; the @ separates task and device in the file and is therefore replaced by a space in the key.

Effect

The training step on the graphics unit (GpuSchritt) uses the matrix kernel auto by default: the remembered choice for this device, otherwise register. The run-time line of training shows it with "(abgestimmt)". An explicit kernel always wins (-matrix: in training, -Denvisionz.opencl.matrix=); if a remembered form no longer fits the device, register computes and the line says why. -Denvisionz.gpu.abstimmung=aus ignores every remembered choice.

Operation

  • Settings, area "GPU tuning": choose the task, see device and remembered choice, "Tune" (runs in the background, with progress and "Cancel"), then the list of candidates – the chosen one with a tick, wrong ones with a cross and reason; "Forget" removes the choice for this device.
  • Command line: tools\gpu-abstimmen.cmd lists tasks, devices and remembered choices, -aufgabe:matrix tunes, -vergessen:matrix forgets. Another device with set JAVA_TOOL_OPTIONS=-Denvisionz.opencl.geraet=NAME.
  • Another step form: measured on the S1 form (d 192, ff 768, vocabulary 8 000, 4 096 tokens, 4 layers); -Denvisionz.opencl.matrix.form=D,FF,V,TOKEN,LAYERS measures another.

The settings app knows no task by name: every module reports its own through the ServiceLoader (envisionz.gpu.abstimmung.Abstimmaufgabe). A new task appears there without a change to the app.

Limits

  • So far only the matrix kernel of training is tuned. The kernels of the CFD step follow; there only what does not touch the order of sums may change (work group, layout), because the step is to stay bit-identical to the CPU.
  • For the matrix engines packing happens per product; in training part of it is saved. The measurement is therefore rather too slow for these kernels.
  • Figures from the build container (OpenCL on the CPU) say nothing about a card; tuning belongs on the computer used for training.
