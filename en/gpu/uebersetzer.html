A compiler of our own from OpenCL C to SPIR-V

Why Vulkan kernels in the framework come from the same OpenCL C text as the OpenCL kernels, how the compiler is built (preprocessor, lexer, syntax tree, generator), what a SPIR-V module looks like, and how the three difficult spots are solved: structured control flow, short-circuit operators and buffers as arguments of helper functions – with pseudocode following the source.

What this is about

An OpenCL driver compiles kernel source itself. A Vulkan driver only takes SPIR-V: an intermediate language of 32-bit words in which every value has a number, every computation is an instruction and every branch names an explicit merge point. The usual ways there are third-party compilers – glslang for GLSL, clspv for OpenCL C – with their own build, their own versions and their own native code.

The framework takes another way. The kernels of the CFD step are already written in OpenCL C and checked bit-identically against the CPU. A second set in another language would be a second place for errors to creep in, and one that has to follow every correction. So the framework compiles the subset of OpenCL C its kernels use to SPIR-V itself. Whatever lies outside is rejected with a line number instead of being half compiled. About 1,900 lines of Java, without dependencies.

What a SPIR-V module looks like

A module is a sequence of 32-bit words: five header words (the magic number 0x07230203, version 1.3 for Vulkan 1.1, the generator, the highest assigned id plus one, zero), then instructions. Each instruction starts with a word carrying length and opcode. The order of the sections is prescribed:

OpCapability Shader, Float64                    what the module needs
OpExtInstImport "GLSL.std.450"                  square root, absolute value, NMin, NMax
OpMemoryModel Logical GLSL450
OpEntryPoint GLCompute %kern "axpy" %gid …      entry: name as in the source
OpExecutionMode %kern LocalSize 64 1 1          the work group
OpName …                                        names for the driver's error messages
OpDecorate …                                    bindings, offsets, built-ins, NoContraction
types, constants, global variables              buffers, push block, __local arrays
OpFunction … OpFunctionEnd                      helper functions and the kernel

The generator collects the sections in separate lists and joins them in this order at the end. Types and constants are cached so that each is declared exactly once – SPIR-V requires that for types.

Parameters: buffers as bindings, numbers in the push block

In OpenCL C buffers are pointers. In SPIR-V for Vulkan there are no pointers coming from outside; a buffer is a global variable in the storage class StorageBuffer, a block with one runtime-sized array member, decorated with set 0 and a binding. Numbers live in a common push block with offsets per std430: int aligned to 4, double to 8 bytes.

for each parameter p of the kernel, in order:
    if p is a buffer:
        type ← Block { array[] of double or int }      ArrayStride 8 or 4
        v ← global variable StorageBuffer;  DescriptorSet 0, Binding = next number
        if p const:  NonWritable
    else:
        offset ← round_up(pushSize, size(p.type));  pushSize ← offset + size(p.type)
        member of the push block at offset
in the kernel: load every number once from the push block into a variable of its own –
so the kernel may modify it as in C

The buffer at binding k and the number at offset v are exactly what Kern.arg(i, …) fills on the Java side. The order of the kernel parameters stays the same as under OpenCL, so the same calling code can serve both back ends.

Structured control flow

SPIR-V for Vulkan requires structured branches: before every conditional branch it states where the paths merge again (OpSelectionMerge), and every loop names its exit and its continue block in the header (OpLoopMerge). break jumps to the exit, continue to the continue block. The generator maps the C statements exactly onto this.

Pseudocode – if and loops (following Erzeuger.anweisung, Erzeuger.schleife)

if(cond, then, else):
    c ← expression(cond)
    merge, bThen, bElse ← new blocks   (without else: bElse = merge)
    OpSelectionMerge merge;  OpBranchConditional c, bThen, bElse
    block bThen:  statement(then);  if not terminated: branch merge
    block bElse:  statement(else);  if not terminated: branch merge
    block merge

loop(init; cond; step) body:
    statement(init)
    header, check, body, continue, exit ← new blocks
    branch header
    block header:    OpLoopMerge exit, continue;  branch check
    block check:     c ← expression(cond);  OpBranchConditional c, body, exit
    block body:      (break → exit, continue → continue)  statement(body);  branch continue
    block continue:  expression(step);  branch header
    block exit
do … while: the header jumps straight into the body, the test happens in the continue block

Code after return, break or continue in the same block is dead and not generated – SPIR-V allows no further instruction in a block after a branch.

Short circuit: &&, || and ?:

In C, a && b evaluates the right part only if the left one is true. That is not only speed but often a precondition: i < n && x[i] > 0 reads x[i] only inside the buffer. A plain translation to OpLogicalAnd would compute both sides. The generator therefore really branches and merges the result with OpPhi, which picks a value depending on the block it came from:

and(a, b):
    ca ← expression(a);  fromA ← current block
    right, merge ← new blocks
    OpSelectionMerge merge
    OpBranchConditional ca, right, merge           false: do not compute right at all
    block right:  cb ← expression(b);  fromB ← current block;  branch merge
    block merge:  r ← OpPhi(false from fromA, cb from fromB)
    return r
or(a, b): likewise, except that true branches directly to merge and the phi value from there is true

fromB matters: the right part may branch itself, and then the block from which control reaches merge is no longer right. A counter-probe swaps the predecessor blocks in the OpPhi and has to turn red.

Helper functions and buffers as arguments

The CFD kernels call helper functions that take pointers: read a state from a buffer, write a ghost into a private array, compute a flux. In SPIR-V a pointer carries a storage class as part of its type; a function with "pointer to double" would have to know whether it points to a private array, a __local array or a buffer. Pointers to buffers as function arguments also require the capability VariablePointers, which not every device has.

The generator solves both by specialisation: for each form in which a helper function is called, a separate SPIR-V function is created. An argument that is a private or local array becomes a pointer of the matching storage class. An argument that is a buffer is not passed at all: the version addresses the global variable of that binding directly.

call(f, arguments):
    form ← for each pointer argument: (private, length) | (local, length) | (buffer, binding)
    if (f, form) already generated:  fn ← that version
    else:
        if f is on the call stack:  throw error(line, "recursion")
        fn ← new function;  parameters only for values and array pointers
        in the body: buffer parameter p ↦ global variable of the binding
        remember (f, form) ↦ fn;  generate the body
    OpFunctionCall fn(values, array pointers)

A module contains only the functions its kernel reaches, and each kernel gets a module of its own. The recursion check comes before the cache lookup – otherwise a function calling itself would find its half-generated version and silently form an endless loop. A counter-probe guards this order.

Details that matter

  • Variables in the first block: SPIR-V requires all OpVariables of a function at the start of its first block. The generator collects them in a list of their own and puts them before the code when joining; in C they may still be declared anywhere.
  • Remainder as in C: % becomes OpSRem (sign of the dividend, as in Java), not OpSMod (sign of the divisor). Counter-probe present.
  • Conversion: int to double signed (OpConvertSToF), double to int truncating; mixed arithmetic per the rules of C.
  • signbit reads the sign bit from the upper 32-bit word of the double – a counter-probe takes the lower one.
  • Ids: get_global_id(0) is the built-in GlobalInvocationId, get_local_id LocalInvocationId, get_group_id WorkgroupId.
  • barrier becomes OpControlBarrier with work-group scope and memory semantics for local memory; __local arrays are global variables of storage class Workgroup.
  • No fma: every floating-point operation gets NoContraction (see Bit-identical to the CPU).
