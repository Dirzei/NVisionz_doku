Bit-identical to the CPU – which freedoms a graphics unit has and how to take them away

Why a kernel on the graphics unit can deliver the same bits as the Java code, which four spots must be built with care for it (fma, order of sums, minimum and maximum, division and square root), how reductions still run in parallel, how to measure a deviation properly – and how a wrong measure faked a compiler bug.

What this is about

A probe that asks for "about equal" finds no error smaller than its tolerance – and in a flow solver a small error often grows into a large one over a thousand steps. The framework therefore requires, wherever possible, bit-identical results: the kernel on the device delivers for every cell the same 64 bits as the Java code. Then every difference is a finding, and the probe can narrow it down to the cell.

This is possible because Java and the graphics unit both compute per IEEE 754: addition, subtraction, multiplication, division and square root in double are correctly rounded, the result is the exact value rounded to the nearest representable number. Whoever performs the same operations in the same order gets the same bits. The art lies in taking away every opportunity for the device to deviate.

First freedom: fma

A fused multiply-add computes a⋅b+ca\cdot b + c with a single rounding instead of two:

separate: rd⁡(rd⁡(a⋅b)+c)fma: rd⁡(a⋅b+c)\text{separate: } \operatorname{rd}\big(\operatorname{rd}(a\cdot b) + c\big) \qquad\qquad \text{fma: } \operatorname{rd}(a\cdot b + c)

The fma is more accurate – but different. Java never contracts on its own. C compilers for graphics units like to, since an fma is one instruction instead of two. On each back end exactly one line helps:

  • OpenCL: #pragma OPENCL FP_CONTRACT OFF at the top of the source.
  • Vulkan: SPIR-V knows no pragma but a decoration per result. The builder and the compiler put NoContraction on every floating-point addition, subtraction, multiplication and division. Probe CL-01 counts that none is missing; a counter-probe removes the decoration and has to turn red.

Second freedom: order of sums

Floating-point addition is not associative: (a+b)+c(a+b)+c and a+(b+c)a+(b+c) can differ in the last bit. A parallel sum over many threads inevitably orders the terms differently from a loop. The framework solves this in three ways:

  • Sums per cell are computed by one thread per cell, in exactly the order of the cell's face list – the order in which EulerLoeser sums as well. Only which cell a thread takes is parallel, not the order within it.
  • Sums over the whole mesh (the norm of the residual) are not computed by the device. It puts the squares per cell into a buffer, the CPU fetches them and sums in sequence like EulerLoeser.norm. That costs a transfer of 8 bytes per cell and step – and spares any discussion about the order.
  • Minimum and maximum over the whole mesh (the global time step, the reference values of the limiter) may run in parallel: a maximum does not depend on the order. It is computed in two stages, as shown below.

Pseudocode – sum per cell (kernel zellen)

c ← thread id;  if c ≥ zz:  end
r ← (0, 0, 0, 0, 0)
for q = start[c] … start[c+1] − 1:            the same order as the CPU
    f ← zf[q]
    s ← +1 if c owns f, else −1
    r ← r + s · flux[f]                          component-wise, without fma
res[c] ← r

Pseudocode – maximum in two stages (kernels bezugTeil, bezugEnde)

stage 1: TEILE = 1024 threads, each takes every 1024th cell
i ← id;  m ← 0
for c = i, i + 1024, … < zz:   m ← jmax(m, value(c))
part[i] ← m

stage 2: one work group of ENDE = 256 threads
j ← local id;  m ← 0
for i = j, j + 256, … < 1024:   m ← jmax(m, part[i])
l[j] ← m;  barrier
for h = 128, 64, …, 1:                         tree in local memory
    if j < h:  l[j] ← jmax(l[j], l[j + h])
    barrier
if j = 0:  result ← l[0]

A similar case is the check for a physical state: every thread that finds a cell with non-positive density or internal energy calls atomic_min(schlecht, c). Which thread comes first does not matter – in the end the smallest cell number is there, the same one the CPU loop would have found first.

Third freedom: minimum and maximum

fmin and fmax in OpenCL C – and NMin/NMax in SPIR-V – return the other value when one is NaN and may treat −0 and +0 as equal. Math.max in Java returns NaN if an argument is NaN and considers +0 greater than −0. The kernels therefore never call fmax directly but two small helper functions:

jmax(a, b):
    if isnan(a) or isnan(b):  return a + b      NaN propagates
    if a = 0 and b = 0:  return (signbit(a) ? b : a)    +0 > −0
    return (a ≥ b ? a : b)

jmin(a, b):  likewise, with (signbit(a) ? a : b) and (a ≤ b ? a : b)

The NaN behaviour is no ornament: a NaN in one cell should poison the time step and thereby stand out, not vanish silently through a "minimum".

Fourth freedom: division and square root

OpenCL requires a correctly rounded division and square root for double. With Vulkan the accuracy of OpFDiv and of the square root from GLSL.std.450 is up to the driver; the framework therefore does not rely on it but measures. On the CPU emulation of Vulkan both are correctly rounded – there the Uebersetzerprobe (CL-04) demands bit-identical results; on a card it reports the largest deviation in ULP and allows at most 4. That is why the probes of the CFD step via Vulkan check against a tolerance on a card and bit-identically on the emulation.

The driver's optimisation

Even with all four rules a remainder stays: the driver's optimising compiler may rearrange computations as long as it keeps to the rules of OpenCL – and every driver interprets what exactly the rules allow a little differently. Measured on the whole CFD step on an integrated graphics unit:

OpenCL, 80,000 cells, 2nd orderms per stepagainst CPU
all kernels with -cl-opt-disable37.0bit-identical
all but the face kernel optimised (-Denvisionz.cfd.gpu.optimiert=bitgleich)21.6bit-identical
all optimised (default)16.11.9·10−15 relative

Only the face kernel – reconstruction and Roe flux, the longest kernel – computes differently when optimised, and only by rounding. Since 10−1510^{-15} lies far below any physically relevant accuracy, "all optimised" is the default; the bit-identical path stays reachable with a switch, and the strictest probe takes it explicitly. Under Vulkan the driver always optimises; the deviation there was of the same size.

How to measure a deviation

If not bit-identical, then how far off? The obvious answer – the deviation per value divided by the value – is wrong for fields whose values pass through zero. The framework measures per variable relative to the largest magnitude of that variable, and for the five conserved quantities the three momentum components share one reference:

ev=maxc⁡|ac,v−bc,v|sv,sv=maxc⁡|ac,v|,sρu=sρv=sρw=max⁡(sρu,sρv,sρw)e_v = \frac{\max_c |a_{c,v} - b_{c,v}|}{s_v}, \qquad s_v = \max_c |a_{c,v}|, \qquad s_{\rho u} = s_{\rho v} = s_{\rho w} = \max(s_{\rho u}, s_{\rho v}, s_{\rho w})

and reports maxv⁡ev\max_v e_v. Implemented in Abweichung.bezogen; all probes and the measuring tool use the same place.

A lesson: At first every variable had its own reference. In a two-dimensional case, however, the momentum normal to the plane is only rounding noise around 10−1810^{-18}. A different last bit there gave a "deviation" of 10−2 to 1, and it looked as if the card's optimising compiler computed wrongly. Only the cross-check on our side – all fluxes of every stage equal face by face to the last bit, the step nevertheless "35 % off" – showed that the measure was wrong, not the card. Since then the shared reference for momentum applies.

The tolerance on the card is five orders of magnitude wider than the measured 10−15: it is meant to catch errors, not rounding. The counter-probes break things on purpose – the norm summed backwards, NoContraction left out, the reduction over only half of the group, the deviation measure with its own reference per momentum component – and have to turn red on the emulation.
