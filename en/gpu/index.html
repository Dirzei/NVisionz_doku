The graphics unit from Java – OpenCL and Vulkan without third-party libraries

How the framework drives the graphics unit: no JNI, no binding library, no third-party compiler – only the JDK's foreign function and memory interface (FFM, java.lang.foreign) and the driver that is on the machine anyway. Two back ends – OpenCL and Vulkan compute – run the same kernel source; the CPU stays the yardstick and the fallback. This overview places the parts; the in-depth pages explain every step with pseudocode.

Principles

No third-party code. No JOCL, no LWJGL, no glslang, no clspv. Access is FFM from the JDK; all that is needed is the library the graphics driver ships anyway (OpenCL.dll, vulkan-1.dll). What a library would otherwise provide – function handles, structs, a compiler – lives in a few classes of the framework.
The CPU is the yardstick. Every kernel performs the same operations in the same order as the Java code. On an emulation (OpenCL or Vulkan on the CPU) bit-identical results are required; on a card they are the normal case, with a tolerance only where the hardware may round differently.
No silent failure, but a silent fallback. If the driver is missing, double is missing or the method does not fit (implicit, viscous, turbulence …), the CPU computes – and grafikeinheit() says why. A step that gives no physical state on the device is repeated on the CPU and reported there.
One source. The kernels exist once, in OpenCL C. Vulkan gets them through the framework's own compiler. A correction thus acts on both paths, and no second version can silently drift apart.
Optional and exchangeable. The solver knows only the interface Schrittkern. The implementations live in their own modules and are found by the ServiceLoader. The solver stays pure JDK; if no implementation is present, it computes on the CPU.
Every probe has a red counter-probe. For every important spot there is a deliberately broken case (fma allowed, order swapped, buffers mixed up …), and the responsible probe has to catch it.

The path: FFM instead of a binding library envisionz.opencl · envisionz.vulkan

Calling a C interface from Java means: load the library, build a handle with its signature for each function, lay out structs byte by byte in memory, check return values. For OpenCL that is about 25 functions, for Vulkan about 50. Background and pseudocode: opening the device, buffers, kernels, pipeline →

OpenCl, Vulkan – the device, once per JVM

On the first call opens the library, the device and (for OpenCL) the context or (for Vulkan) instance, logical device and compute queue. Without a device the result is null, and grund() names the cause.

Methods

  • OpenCl.oeffne(), Vulkan.oeffne() → Geraet or null
  • grund(), abgeschaltet()
  • Geraet.programm(quelle, optionen) (OpenCL), Geraet.text()

Switches

  • -Denvisionz.opencl=aus, -Denvisionz.vulkan=aus (off)
  • ….alle=ja: CPU devices too (for the probes)
  • ….bibliothek=PATH: another driver library
  • in the program: Settings, section Graphics unit

Warteschlange, Puffer, Kern – per thread

Both back ends have the same three notions: queue, buffer, kernel. A queue belongs to one thread and owns its buffers and kernels; close() releases everything.

Example – y = a x + y in double on the graphics unit (Vulkan)

String quelle = """
    __kernel void axpy(const int n, const double a, __global const double* x, __global double* y) {
        int i = get_global_id(0);
        if (i < n) y[i] = a * x[i] + y[i];
    }""";
Geraet g = Vulkan.oeffne();                                  // null: Vulkan.grund() says why
Kernbau.Beschreibung b = Uebersetzer.uebersetze(quelle, 64).get("axpy");
try (Warteschlange q = new Warteschlange(g)) {
    Puffer px = q.puffer(8L * n), py = q.puffer(8L * n);
    q.schreibe(px, x);  q.schreibe(py, y);
    Kern k = q.kern(b).arg(0, n).arg(1, 2.5).arg(2, px).arg(3, py);
    q.starte(k, n);                                          // recorded, not yet submitted
    q.lies(py, y);                                           // submits, waits, reads
}

Bit-identical to the CPU

Floating-point arithmetic is not associative, and a graphics unit may do many things differently from Java: contract a·b + c into an fma, reorder sums, form minimum and maximum without regard for NaN and the sign of zero. Bit-identical results only arise if each of these freedoms is explicitly taken away. Background, rules, the deviation measure and a lesson →

Freedom of the deviceOpenCLVulkan (SPIR-V)
fuse a*b+c into an fma#pragma OPENCL FP_CONTRACT OFFNoContraction on every floating-point operation
reorder sumssums per cell in the order of the face list; the CPU sums the norm in sequence
minimum, maximumjmin/jmax like Math.min/Math.max: NaN propagates, +0 > −0
division, square rootdouble rounded per IEEEup to the driver – measured in ULP
driver optimisationselectable per kernel (-Denvisionz.cfd.gpu.optimiert)always; NoContraction keeps it from fma

The compiler OpenCL C → SPIR-V envisionz.vulkan.clc

Vulkan takes no source text but SPIR-V, a binary code of 32-bit words. Instead of shipping a third-party compiler, the framework compiles the subset of OpenCL C it uses itself: preprocessor, lexer, syntax tree, generator – about 1,900 lines of Java. Structure, language subset and pseudocode of the generator →

Uebersetzer.uebersetze(quelle, lokal)

Returns a Kernbau.Beschreibung per __kernel: the SPIR-V words, the work-group size, the parameters (buffers as bindings, numbers as push constants) and the size of the push block. Everything outside the subset is rejected with a line number.

Language

  • macros, also with parameters; int, double, bool
  • if, for, while, do, break, continue, return; &&, ||, ?: with real branches
  • helper functions with value and pointer parameters, private and __local arrays, barrier
  • sqrt, fabs, fmin/fmax, isnan, isinf, signbit, atomic_min/max/add

Checked

All 22 kernels of the CFD step and the two of the residual give valid SPIR-V (the specification's validator as referee); language features over 5,000 values bit-identical to Java.

The whole CFD step on the card envisionz.cfd.opencl · envisionz.cfd.vulkan

Only the residual on the card was slower than the CPU: gradients, limiters and boundaries stayed on the CPU, and every call copied back and forth. Since then the state stays on the device for the whole step; only boundaries the device does not know are computed by the CPU, per stage, with its own code. Launching kernels and waiting

A kernel launch costs microseconds on the card, a submission with waiting dozens. Vulkan records launches into a command buffer and submits them as a batch; that is faster than OpenCL, but the submission itself is more expensive. Command buffers, barriers, descriptor sets, spinning or sleeping →

Which work group, how many results per thread and which tile a kernel needs on a card cannot be predicted.
