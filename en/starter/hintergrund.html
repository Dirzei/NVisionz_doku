How a single-app launcher registers and starts its app

Using the smallest launcher as the example: why it does not search the class path, what can be checked without a window and on which thread the main window is built.

What this is about

A launcher does little, but whatever it gets wrong only shows at delivery. Its path is therefore cut into three parts: registration, configuration and building the window. Only the last part needs a screen.

Registration without searching

The multi-app launcher finds its apps through the ServiceLoader. For a native program, that would mean keeping every entry point in a configuration. The single-app launcher therefore registers its one app explicitly: descriptor and constructor reference stand in one line that the compiler checks.

The registration holds a factory, not a finished instance. Each request yields a new app, because an instance stands for one tab.

Configuration

The configuration names the application name, the log level and the registration. The name gives the working folder in the user directory, .envisionz-hello in the example. The started environment uses exactly the registration it was given and searches for nothing else.

The main window

Swing requires user interfaces to be created on the event thread. The launcher first sets up the environment on the start-up thread and then hands all of the window building to the event thread: main window, first tab and making it visible.

The multi-app launcher

The multi-app launcher registers nothing itself. It finds all apps through the ServiceLoader: every app whose project is on the class path and that brings a registration line appears. The started environment knows exactly these apps, no more and no fewer.

Before the window it looks at the arguments. -messung:<name> runs a measurement without a user interface and exits with its return value. All other arguments without a leading dash are files; this is how the operating system calls an associated program. After start-up the frame opens every file with the app that knows its extension. If several apps know the extension, it opens nothing itself but offers the choice.

The splash screen stays up for at least a fixed time and then hands over to the main window; the two never lie on top of each other.

Measuring the graphics unit

-messung:grafikeinheit checks, in whatever mode the program is currently running (also as a native program), whether the graphics unit computes. On every device found, the kernel yi←axi+yiy_i \leftarrow a\,x_i + y_i runs over 10,007 values. Because addition and multiplication are correctly rounded on both sides and contraction into an fma is switched off, the result must be bit-identical to Java. A device that contracts anyway gets the last bit wrong in many values and turns the measurement red.

Then the whole CFD step runs 20 steps per step kernel against the CPU. Each variable is compared relative to its largest magnitude; the three momenta share one reference, because in 2D the third momentum is zero and its own magnitude is no measure:

d=maxv⁡maxi⁡|uv,iGPU⁡−uv,iCPU⁡|maxi⁡|uv,iCPU⁡|≤10−10.d = \max_v \frac{\max_i |u_{v,i}^{\mathrm{GPU}} - u_{v,i}^{\mathrm{CPU}}|}{\max_i |u_{v,i}^{\mathrm{CPU}}|} \le 10^{-10}.

Limits

  • The window building needs a screen. The probe of the equation-parser launcher therefore runs the whole start-up path only when one is present, with a user directory of its own; without a screen it reports that part as skipped. Line coverage is measured without a screen and so never counts the window building.
  • The load run across all apps (event thread and memory leaks) needs a screen and minutes; it is a tool, not a probe.
