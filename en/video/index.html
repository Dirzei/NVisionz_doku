envisionz-framework-video

Our own MPEG-1/2 decoder, measured against the standard

Function overview for the presentation of the envisionz framework, as of 28 Sep 2026. Bit level and VLC tables, header layers down to the slice, macroblocks, inverse quantisation, IDCT and motion compensation, pictures in display order from streams of any size – plus colour space, levels, chroma siting and aspect ratio for further processing. For each method: purpose, API, use in the framework, applications, examples. The examples are shortened. Many API names are German (e.g. Dekoder = decoder, Bildpuffer = frame buffer, Kopfangaben = header data, Bewegungskompensation = motion compensation); they are shown unchanged.

Principles of the module

No ffmpeg. For the same reason as everywhere in the workspace – and because the yardstick for a decoder measurement is the normative reference software from ISO/IEC TR 13818-5, not ffmpeg.
Display order, not coding order. Two reference pictures are kept; I and P pictures leave delayed, B pictures at once. Whoever ignores this gets judder that looks like a tape fault.
Streamed, not collected. A sliding window, cut only at start codes; a 2.86 GiB program stream fits into no byte[] and does not need to.
A worse picture instead of an abort. Unfitting slices are rejected and counted, missing macroblocks are concealed on request and counted as well; a sequence header above 2048 × 2048 is skipped.
Precise where it matters. The IDCT computes in double precision, far more accurate than IEEE 1180 requires – every rounding enters all subsequent restoration steps.

The decoder envisionz.video.mpeg

Dekoder – elementary stream in, pictures in display order out

Brings together entropy layer, inverse quantisation, IDCT and motion compensation, for MPEG-1 and MPEG-2. Three inputs: a byte[] with a collected list, a byte[] with a sink, an InputStream with a sink. abSequenzkopf skips to the next sequence header – for entering in the middle of a recording; on DVD every VOBU starts with one. Data-partitioned streams get their second partition separately. After the run all header data and counters are available. Background, formulas and pseudocode →

What for

Example – run through a title set and count what was concealed

Dekoder dek = new Dekoder().fehlerverdeckung(true);
try (InputStream ein = Files.newInputStream(Path.of("titel1.m2v"))) {
    dek.dekodieren(ein, bild -> verarbeite(bild.y(), bild.breite(), bild.hoehe()));   // verarbeite: own method
}
System.out.println(dek.kopfangaben().meldung());
System.out.println(dek.bilder() + " pictures, " + dek.verdeckteMakrobloecke() + " macroblocks concealed");
Measured against ffmpeg (decoder Javadoc): I pictures 76.0–76.4 dB, P pictures 69.7–75.0 dB, B pictures 72.9–74.6 dB. The remainder is the ±1 rounding tolerance permitted by IEEE 1180, which accumulates over a group of pictures. A picture comparison against the reference software is still outstanding – it is not available in the workspace.

Header data and extensions envisionz.video.mpeg

Kopfangaben, Bildangaben, Anzeigeangaben, Bildgruppe, Skalierbarkeit …

What the stream says about itself: size, aspect ratio and pixel aspect ratio, frame rate, bit rate and buffer size; per picture type, temporal reference and fields; video format, colour coefficients and transfer characteristic from the display extension; time code of the group of pictures; scalability (data partitioning, SNR, spatial, temporal) detected, not decoded; copyright data and user data. With read damage the time code tells how much is missing.

Layers without decoding envisionz.video.mpeg

Schichtenleser – down to the slice, without coefficient tables

Jumps from start code to start code through sequence, group of pictures, picture and slice. The most important side information is the quantiser scale per slice: how coarsely this macroblock row was rounded – the same information as at macroblock level in coarser resolution, for a hundredth of the effort.

Reconstruction envisionz.video.mpeg

Makroblockleser, Quantisierung, Idct, Bewegungskompensation, Zweifach

The macroblock reader reads per slice addresses (with escape +33), types, motion vectors and coefficients in zigzag or alternate scan. Quantisierung with default and custom matrices, linear and non-linear scale, MPEG-1 special case. Idct separable along the axes in double. Bewegungskompensation fetches full- and half-pel predictions from frames and fields and averages for bidirectional prediction; Zweifach derives the second vector of dual-prime prediction. Bit level envisionz.video.mpeg

Bitleser, Bitschreiber, Doppelleser, Vlc, Abtastfolge

Bitleser with look-ahead, signed reads and start-code detection; Vlc as a lookup table over a fixed bit width. Doppelleser switches between two partitions for data partitioning – nothing is re-encoded, both parts together contain the same bits. Abtastfolge holds zigzag and alternate scan.

Pictures envisionz.video.mpeg · envisionz.video.bild

Bildpuffer, Bild, YuvLeser – Y, Cb, Cr instead of RGB

Bildpuffer is the decoder's output: three int planes 0…255, with 4:2:0 chroma planes half as wide and half as high, plus picture type and temporal reference. Bild is the form for restoration: double planes in the file's value range, deliberately not RGB, because the chroma subsampling is itself a measurement; fields can be extracted. YuvLeser reads raw YUV sequences whose size comes from outside.

Methods

  • Bildpuffer: y(), cb(), cr(), breite(), hoehe(), farbBreite(), art(), zeitbezug()

Colour and geometry envisionz.video.farbe

Farbraum, Pegel, Chromalage, Seitenverhaeltnis

The conversions on which almost every tool chain stumbles. Farbraum: Y'CbCr ↔ RGB after BT.601 or BT.709, level expansion included. Pegel: luma 16…235, chroma 16…240, expand and compress, detect video levels. Chromalage: where the chroma sample sits in 4:2:0 – MPEG-1 in the centre, MPEG-2 on the left. Seitenverhaeltnis: PAL 720 × 576 at 4:3 becomes 768 × 576 square pixels; belongs at the end of the chain. Background, formulas and pseudocode →
