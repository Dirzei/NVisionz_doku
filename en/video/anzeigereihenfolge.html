The decoder – display order, stream and concealment

How Dekoder turns coding order into display order, reads a stream of any size with a sliding window and replaces missing picture parts. Pseudocode after the source, decisions and limits.

Coding order and display order

MPEG knows three picture types. An I picture can be decoded on its own. A P picture is predicted from an earlier I or P picture. A B picture is predicted from an earlier and a later reference picture and never serves as a reference itself. For a B picture to be decoded, the later reference picture must already be there – so it stands before the B pictures that precede it in time. The digit in the name is the temporal reference from the picture header (temporal_reference), i.e. the display position.

The decoder therefore keeps two reference pictures: the newer one (rueckwaerts) and the one before (vorwaerts). A P picture predicts from the newer one, a B picture reads both. When a picture is finished:

  • a B picture goes straight to the sink;
  • an I or P picture first outputs the newer reference picture held so far – it is now certain that no B pictures come before it – and then becomes the newer reference itself, the former newer one becoming the older.

At the end of the stream the reference picture still held is output. Whoever skips this gets a sequence that stutters and jumps back – and may take it for a tape fault.

Pseudocode – Dekoder.bildAbschliessen(art, zeitbezug)

verdecken()                                  replace missing macroblocks, if requested
current.kennzeichnen(type, temporalReference)
current.kodiernummer(count);  count ← count + 1
if type = B:
    sink(current)                            B pictures never serve as reference
else:                                       I or P
    if rueckwaerts ≠ empty: sink(rueckwaerts)       the previous reference picture is now due
    vorwaerts ← rueckwaerts
    rueckwaerts ← current
current ← empty

// abschluss(): finish the open picture, then sink(rueckwaerts) if present

Source: envisionz-framework-video/src/envisionz/video/mpeg/Dekoder.java (bildAbschliessen, abschluss).

The output is I0, B1, B2, P3, B4, B5, P6 – display order. Followed by hand through the source.

Decision in the framework: The output is display order, not coding order, and it is delayed by at most one reference picture. This favours further processing: restoration steps that need neighbouring pictures get the pictures as a viewer sees them. Each Bildpuffer carries its temporal reference and coding number.

A stream that fits in no memory

A Java array holds at most 231−12^{31}-1 elements, just under 2 GiB. The program stream of the sample recording measures 3,069,673,472 bytes, i.e. 2.86 GiB (class comment of Dekoder); it fits in no byte[], and opening failed because of that, not because of decoding. dekodieren(InputStream, senke) therefore slides a window over the stream; the window is in memory, not the recording.

It may be cut only at a start code (the byte sequence 00 00 01). The decoder finds the end of a unit by searching for the next start code; if a window ended in the middle of a slice, this remainder would be read as a complete slice and give a torn picture without any message. So processing goes only up to the last start code in the window; the rest moves to the start of the next. If a full window contains no further start code, it grows to twice the size instead of the decoder standing still.

Pseudocode – Dekoder.dekodieren(ein, senke)

window ← new array of size FENSTER;  fill ← 0
repeat:
    while source not empty and fill < size(window):
        n ← in.read(window, fill, rest);  if n < 0: source empty, leave;  fill ← fill + n
    if fill = 0: stop
    limit ← if source empty then fill else letzterStartcode(window, fill)
    if limit ≤ 0:
        if source not empty:  window ← double(window);  continue     no unit complete
        limit ← fill
    abschnitt(window[0 .. limit))                                   complete units only
    if abort set: stop
    window[0 ..] ← window[limit .. fill);  fill ← fill − limit
abschluss()                                                         output the reference picture still held

// letzterStartcode: search from fill−3 downwards to position 1 for 00 00 01; position 0 does not count

Source: envisionz-framework-video/src/envisionz/video/mpeg/Dekoder.java (dekodieren, letzterStartcode, abschnitt). The reading state is kept in a field between two sections.

Decision in the framework: The window size is 1 MiB (FENSTER = 1 << 20). Position 0 of the window does not count in the start code search – the start code the window begins with is there, and processing up to it would make no progress. An abort ends the run instead of reading the rest of a stream the decoder cannot decode anyway. A sequence header above 2048 × 2048 pixels (the standard allows up to 4095², which would be 384 MB per picture) is skipped and counted as an error mark.

Error concealment

If a slice breaks off or whole sectors of a damaged disc are missing, everything after used to stay black. With fehlerverdeckung(true), at the end of the picture the decoder counts which macroblock positions were never written – it records which ones were occupied. This covers broken-off slices, wholly missing slices (which appear at no break point because they never begin) and a picture of which nothing arrived, with the same calculation. The substitute comes

  • temporally, if a reference picture exists: the same position from the most recently decoded reference picture – the best approximation for a steady camera, and it costs nothing;
  • spatially, if none exists: the nearest occupied macroblock in the same column, searched upwards first, then downwards – clearly worse, but it only affects the very first picture of a recording.

Motion vectors are not guessed: that would be the next step and needs the neighbours' vectors; without evidence that it gets better it would only be more expensive.

Pseudocode – Dekoder.verdecken()

if not concealment or not concealable or no open picture: return
source ← if rueckwaerts ≠ empty then rueckwaerts else vorwaerts
count ← 0
for each macroblock position (row, column) with written[position] = false:
    if source ≠ empty:
        copy block (column, row) from source to current
    else:
        neighbour ← nearest occupied row in this column      up first, then down
        if neighbour < 0: continue
        copy block (column, neighbour) from current to (column, row)
    count ← count + 1
if count > 0:  concealed ← concealed + count;  concealedPictures ← concealedPictures + 1

Source: envisionz-framework-video/src/envisionz/video/mpeg/Dekoder.java (verdecken). Counters: verdeckteMakrobloecke(), verdeckteBilder(), abgewieseneSlices().

Decision in the framework: Concealment happens only on request, and everything concealed is counted. A concealed picture is thus never silently a “good” picture; whoever restores knows which parts are observation and which are substitute.

How it is tested

Dekoderprobe (605 checks according to the module description) secures the building blocks with anchors that can be calculated in closed form; Sequenzkopfgrenzprobe tests the skipping of oversized sequence headers, with a counter-test without the limit that turns red. According to the module description, everything above the building blocks remains untested against a second decoder: assembly of whole pictures, reordering, reference picture handling over a group of pictures, field and dual-prime prediction, scalability, data partitioning and error concealment. Against ffmpeg the pictures are at 69.7 to 76.4 dB (I 76.0–76.4, P 69.7–75.0, B 72.9–74.6); a picture comparison against the normative reference software is outstanding.

Limits

  • The output depends on correctly recognised picture types and start codes; a stream without a sequence header can be decoded only from the next one (abSequenzkopf).
  • A B picture without both reference pictures and a P picture without a forward one cannot be decoded.
  • Concealment is a substitute, not a reconstruction: good with a steady camera, poor with motion.
  • Scalable streams are recognised, not decoded.
