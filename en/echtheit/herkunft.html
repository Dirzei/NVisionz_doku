Provenance record – background

The computation behind Herkunftsspur: where the manifest sits in the file, how boxes and CBOR are read, how a COSE signature is recomputed, what the certificate chain says and how checksums are bound to the image content – with pseudocode following the source, worked bytes, testing and limits.

What this is about

A provenance record is a signed statement embedded in the file about who created or edited it. Unlike the other traces this is not an estimate but plain computation: the signature holds, the hash holds, or not. If no record exists, that says nothing – most files carry none.

Where the manifest sits

FileLocation

loose manifest filestarts directly with a superbox (jumb)

A manifest above 64 MiB is not read.

Boxes and CBOR

JUMBF (ISO/IEC 19566-5) is a nested box structure: per box 4 bytes of length (big-endian), 4 bytes of type, payload. Length 1 means a following 64-bit length, length 0 "to the end". The superbox jumb starts with a description box that holds the label if bit 2 is set there. Depth is limited to 32, and every length is checked against the rest of the input.

CBOR (RFC 8949) encodes values in a head byte: the upper three bits are the major type, the lower five the length or value (24 to 27 mean: 1, 2, 4, 8 following bytes). Examples:

BytesTypeValue
19 03 E8integer, 2 bytes1000
39 03 E7negative number (−1−n-1 - n)−1000
F9 3E 00half precision1.5

Half precision is read for a normal value as (m+1024)⋅2e−25(m + 1024) \cdot 2^{e - 25} (from the literature, RFC 8949, Appendix D). The reader knows no indefinite-length forms, checks every count against the remaining length (at least one byte per element, two for maps) and limits the depth to 64: a length from the file is a claim by the file.

The signature

The active manifest is the last child of the top box, with the parts claim, signature and assertions. The signature is a COSE_Sign1 (RFC 9052) with detached payload: a 4-tuple of protected header, unprotected header, empty payload and signature bytes, optionally with tag 18. What is signed is not the manifest itself but the structure

Sig_structure⁡=["Signature1",protected,empty,claim],\mathrm{Sig\_structure} = [\ \text{"Signature1"},\ \text{protected},\ \text{empty},\ \text{claim}\ ],

in CBOR after RFC 9052, section 4.4. The protected header names the algorithm in entry 1; entry 33 carries the certificate chain (in the protected or unprotected header). Supported algorithms:

COSE labelAlgorithmNote
−7, −35, −36ES256, ES384, ES512signature raw r‖sr \| s, translated to DER
−37, −38, −39PS256, PS384, PS512salt length equals the hash length
−8Ed25519

Raw to DER. Each half is stored as a signed integer: leading zeros dropped, and if the top bit is set, a zero byte in front so that it is not read as negative.

The chain

The first certificate carries the key. For each ii, cic_i must be signed by ci+1c_{i+1}. If a trust anchor is given, the last must equal an anchor or be signed by one:

verify⁡(ci,key⁡(ci+1))∀i,clast∈A∨verify⁡(clast,key⁡(a)),a∈A.\mathrm{verify}(c_i, \mathrm{key}(c_{i+1})) \ \ \forall i, \qquad c_{\text{last}} \in A \ \lor\ \mathrm{verify}(c_{\text{last}}, \mathrm{key}(a)),\ a \in A.

A valid anchor is named, a foreign anchor does not count (EV-64); without an anchor the issuer remains a statement of the file and does not change the verdict. Caveat: what is checked is the cryptographic chain, not the validity period, key usage and revocation (RFC 5280).

Assertions and binding

Each assertion is a box of its own. The claim holds its hash; it is compared against the checksum of the payload without the box header. The algorithm stands with the assertion or in the claim (sha256, sha384, sha512).

The binding to the file is an assertion with the hash of all bytes except the exclusions in which the manifest itself sits, because it cannot contain its own hash:

H=hash⁡(file∖⋃i[si,si+ℓi)).H = \mathrm{hash}\Big(\text{file} \setminus \bigcup_i [s_i,\ s_i + \ell_i)\Big).

The exclusions must lie in ascending order without overlap. A box binding (for MP4 and similar containers) is not recomputed by the trace, which reports this explicitly; it counts neither as an error nor as verified (EV-70).

The verdict

A manifest is good if

signature∧chain∧(no false assertion)∧(binding∉{false,missing})∧(no trap in the file profile).\text{signature} \land \text{chain} \land (\text{no false assertion}) \land (\text{binding} \notin \{\text{false}, \text{missing}\}) \land (\text{no trap in the file profile}).

CaseVerdict
no manifestcannot be evaluated (the normal case, no finding)
manifest damaged or not verifiableconspicuous
condition above violatedconspicuous, with the individual cause
all fulfilledunremarkable, the creator is named

A "trap in the file profile" means structural peculiarities of the file that lead to different readings. Warnings of the profile, by contrast, remain hints (EV-78, EV-79).

Worked example

Sig_structure. Protected header A1 01 26 (algorithm −7), claim "hi":

84                      list, 4 entries
6A 53 69 67 6E 61 74 75 72 65 31   text "Signature1"
43 A1 01 26             bytes, 3: the protected header
40                      bytes, 0: external data, empty
42 68 69                bytes, 2: the claim

Binding. A file of 20 bytes with exclusions (4,6)(4, 6) and (14,2)(14, 2) leaves 12 bytes: bytes 0 to 3, 10 to 13 and 16 to 19.

Half precision. 3E 00: sign 0, exponent e=15e = 15, mantissa m=512m = 512. (512+1024)⋅215−25=1536/1024=1.5(512 + 1024) \cdot 2^{15 - 25} = 1536/1024 = 1.5.

DER. With an rr with the top bit set (32 bytes) and an ss without: header 2, rr with zero byte 33, and header 2, ss 32; content thus 69 bytes. The examples were recomputed with docs/theorie/rechnung/echtheit_herkunft.java.

How it is tested

  • Cryptography (Stufe2probe, manifests built during the test run with its own keys): valid (EV-60, EV-61), over two APP11 segments (EV-62), anchor and foreign anchor (EV-63, EV-64), corrupted signature, wrong checksum, broken chain, wrong binding, one bit in the image (EV-65 to EV-69), box binding (EV-70), PNG, MP4, loose file (EV-71 to EV-73).
  • No finding: JPEG without manifest (EV-74).
  • CBOR and boxes: integers after RFC 8949 (EV-80, EV-81), floating point (EV-82, EV-83), list, map, tag (EV-86, EV-87), truncated, length greater than the input, too deep, bytes after the value, unsupported forms (EV-88 to EV-93), box lengths, superbox (EV-94, EV-95), broken files (EV-96).

Caveat: the manifest in the test is built with the same method of the Sig_structure with which it is verified; an error there would go unnoticed. The bytes in the example therefore come from a separate computation.

Limits

  • A valid record says: this file was signed like this by someone holding the key. It does not say that what is shown is true.
  • Records can be removed; the file is then "cannot be evaluated", no finding.
  • Validity period, key usage and revocation of the certificates are not checked.
  • Box bindings are not recomputed.
  • The signature form with detached payload is supported; other manifest forms count as not verifiable.
