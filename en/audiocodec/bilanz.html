Batch run – the weighted overall balance

How Stapellauf evaluates a codec over a whole collection: a round trip with both methods per file, a balance over the sums of the bytes, why that is a harmonic mean of the individual ratios weighted by raw size and not their ordinary mean. With derivation, pseudocode following the source, a recomputed example, probes and limits.

What it is about

Whether a change to the codec helps is not shown by any single generated test file. A sine can be predicted almost arbitrarily well, noise not at all, and real music lies somewhere in between. Only a collection makes a statement. That requires two things: every file must demonstrably come back bit-exactly, otherwise every ratio is worthless, and the individual results must be combined into one number that says how much space the whole collection needs.

The second half sounds simpler than it is. The obvious mean of the individual ratios answers a different question – “how well is a randomly picked file compressed?” – and lets one second of silence count as much as an hour of orchestra.

The balance as a weighted mean

For file ii let RiR_i be the raw size (PCM in bytes), CiC_i the size of the Rice stream and BiB_i that of the range stream. The individual ratio is vi=Ri/Civ_i = R_i / C_i. The overall balance is

V=∑iRi∑iCiV = \frac{\sum_i R_i}{\sum_i C_i}

Substituting Ci=Ri/viC_i = R_i / v_i and writing gi=Ri/∑jRjg_i = R_i / \sum_j R_j for the file's share of the raw size gives

V=∑iRi∑iRi/vi=(∑igivi)−1V = \frac{\sum_i R_i}{\sum_i R_i / v_i} = \left(\sum_i \frac{g_i}{v_i}\right)^{-1}

– the harmonic mean of the individual ratios, weighted by raw size. Harmonic, because storage requirements add up, not ratios; weighted, because a long file occupies more space. The ordinary mean v=1n∑vi\bar{v} = \frac1n \sum v_i, in contrast, gives every file the same weight and can be far off with files of unequal length, upwards as well as downwards – depending on whether the short files compress well or badly.

The comparison of the two methods is likewise formed over the sums:

D=100⋅∑iBi−∑iCi∑iCi%D = 100 \cdot \frac{\sum_i B_i - \sum_i C_i}{\sum_i C_i} \;\%

Negative means: the range coder needs less space than Rice for the whole collection.

The procedure per file

Pseudocode – Stapellauf.pruefe(name, signal)

try:
    t0 ← clock
    C ← Kodierer(block size, maxLpc, method RICE).kodiere(signal)
    B ← Kodierer(block size, maxLpc, method RANGE).kodiere(signal)
    time ← clock − t0                                     both encodings, no decoding
    bitExact ← signal = decode(C) and signal = decode(B)
    result ← (name, duration, channels, bits, R = raw size, |C|, |B|, bitExact, time)
on exception e:
    result ← failed(name, type and text of e)             all numbers 0
append result to the list;  return result

Pseudocode – bilanz()

tested ← count without error text;  failed ← count with error text
deviating ← count without error text and not bit-exact
ΣR, ΣC, ΣB, ΣT ← sums over all results               failed ones contribute 0
output: counts, playing time ΣT
if ΣR > 0 and ΣC > 0 and ΣB > 0:
    output: ΣR;  ΣC with ΣR/ΣC;  ΣB with ΣR/ΣB;  100·(ΣB − ΣC)/ΣC %

Source: envisionz-framework-audiocodec/src/envisionz/audiocodec/Stapellauf.java and Stapelergebnis.java.

Convention in the framework: A file only counts as bit-exact if both methods return it unchanged. An exception does not abort the batch; it is recorded as a failed result with error text and counted separately; a deviation without exception counts as “deviating”, and any number above zero there is a bug in the codec. The encoding time covers both encodings, not the decoding. Defaults: block size 4096, LPC up to the highest order.

The CSV output (schreibCsv) writes one line per file, columns separated by semicolons, UTF-8, numbers with a decimal point and six decimals: file, duration, channels, bits, the three sizes, both ratios, the difference in percent, bit-exact (ja/nein), encoding time, error text. For a failed file the measurement columns stay empty.

Worked example

The two files of the Stapelprobe, recomputed with Stapellauf (block size 4096): a long, well predictable tone file (220 Hz, amplitude 20,000, 4 s, stereo, 16 bits) and a short noise file (0.1 s, uniform in ±32,000).

The ordinary mean would be (6.9931+0.9965)/2=3.9948(6.9931 + 0.9965)/2 = 3.9948. The weighted harmonic mean: 0.9756/6.9931+0.0244/0.9965=0.1395+0.0245=0.16400.9756 / 6.9931 + 0.0244 / 0.9965 = 0.1395 + 0.0245 = 0.1640, whose reciprocal is 6.098 – the same number as 787,200/129,090787{,}200 / 129{,}090. For this collection the range coder needs D=100⋅(99,996−129,090)/129,090=−22.54D = 100 \cdot (99{,}996 - 129{,}090) / 129{,}090 = -22.54 % less than Rice; that comes almost entirely from the tone file, where the small residuals of an almost perfect prediction hit exactly the strength of the range coder. The noise file is slightly larger than raw with both methods (header and frames).

For comparison, the figures of the module documentation for a real collection: 27 of 27 music tracks (101 minutes) came back bit-exactly, Rice overall 1.88 : 1; there the range coder was 0.1 to 1.5 % larger in 26 tracks.

How it is tested

The Stapelprobe (10 checks) writes the two files of the example as WAV into a temporary directory, reads them back and checks:

  • both files bit-exact; counts 2 tested, 0 failed, 0 deviating;
  • raw and Rice sums are the sums of the individual values, the playing time the sum of the durations (to 10−910^{-9});
  • the anchor: weighted balance and ordinary mean differ by more than 0.5 – computable in closed form with these two very unequal files;
  • the tone compresses more than twice as well as the noise;
  • a failed result entered by hand is counted and not listed as tested;
  • the CSV has a header line and two data lines, and the header names both methods.

Limits

  • Every file is read completely into memory and processed four times (encoded twice, decoded twice).
  • The encoding time is wall-clock time over both encodings, not a measurement per method.
  • The balance says how much space the collection needs. Whoever wants to know how well a typical single file is compressed needs the individual ratios from the CSV.
  • The balance is only as meaningful as the collection: a collection of nothing but noise or nothing but silence shifts it arbitrarily.
