Properties, value table and catalogue – background

What the viewer decides itself, although reading lives in the framework: how types, shapes and filters are named, how the value table shows multidimensional arrays row by row and reads them page by page, what can be handed over as a table, when a file is recognised as HDF4 and how the catalogue builds its levels and column figures.

What this is about

Reading is done with framework-fileformats, read-only. The bridge to tables lives in framework-data. The viewer connects both with the user interface and makes the decisions described here.

Types, shapes and filters

A data type is named from its class and size in bytes: integers as int or uint with the bit count 8⋅size8 \cdot \text{size}, floating-point numbers as float with the bit count, fixed strings with their length, variable ones as string(var), compounds with the number of their members. An attribute with several values carries the count in square brackets after the type.

A shape is written as (n0×n1×…)(n_0 \times n_1 \times \dots), a scalar as ()(), an unlimited maximum extent as ∞\infty. The filter chain is listed in the order of application with arrows in between. A compression ratio

r=values⋅bytes per valuestorage in the filer = \frac{\text{values} \cdot \text{bytes per value}}{\text{storage in the file}}

appears only if there are filters, with two decimals; without filters it says nothing. The maximum shape appears only for extensible data sets.

The value table

An array of rank k≥2k \ge 2 is shown row by row, one row per value, preceded by kk index columns i,j,ki, j, k. The order is that of the file (C order, the last index runs fastest): for the shape (n0,n1)(n_0, n_1) row rr belongs to

i=⌊r/n1⌋,j=r−in1.i = \lfloor r / n_1 \rfloor, \qquad j = r - i\,n_1 .

Only the page of 4096 values containing the requested row is read; a page boundary must neither shift nor skip a value, even when reading in jumps and backwards.

As a table and as CSV

“As table” goes through the bridge in framework-data. A data set becomes a table; a group only if it contains one-dimensional series – otherwise the app reports the reason and disables the CSV output. The table is sent as an event addressed to the chart app. The CSV output of the file tab writes the table last handed over, separated by semicolons.

The extension .hdf is historically used for HDF4 and today also for HDF5. Before opening, the app therefore checks the signature. An HDF4 file is not reported as a broken HDF5 file but as a notice “is an HDF4 file”.

The working directory is read flat, not recursively: it shows the regular files with the extensions .hdf, .h5 and .hdf5, sorted regardless of upper and lower case.

The catalogue

The catalogue has four levels: stocks from a catalogue file, projects in the folder Projects, experiments in the folder experiments, container files in the folder dtfs. Each level can be loaded on its own. A chosen location is either a collection folder (or lies above one), then all entries from it come, or a single folder, then exactly that entry. If the location is no folder at all, the status line says there is nothing there. An experiment without dtfs is marked “without files” in the selection.

For every column of a loaded container the column table shows unit, number of values and the smallest and largest finite value, with six significant digits:

min⁡{xi:xi finite},max⁡{xi:xi finite}.\min\{x_i : x_i \text{ finite}\}, \qquad \max\{x_i : x_i \text{ finite}\}.

Gaps (NaN) and infinities do not count; if there is no finite value the field stays empty.

The CSV card of the catalogue rejects a comma as separator together with a comma as decimal mark, because the file could then no longer be split; if the extension .csv is missing, it is appended.

Limits

  • The viewer only reads. It writes no HDF5 file and changes none.
  • A group becomes a table only with one-dimensional series. The bridge rejects very large data sets as tables; for computing and plotting they remain usable.
  • HDF4 files are recognised but not displayed.
