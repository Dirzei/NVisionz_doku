Text from PDF and glyphs onto the page – background

How PdfText rebuilds lines, words and columns from placed glyphs, how font encodings and CID widths work, and how PdfSeitenmaler puts the outlines of embedded fonts onto the page.

What this is about: a PDF has no running text

A PDF does not contain “this paragraph” but a sequence of instructions: set these character codes in this font, at this size, at this position. Words, lines and paragraphs do not exist; a space is often just a gap. Extraction therefore has three tasks: interpret the text operators while tracking the position, translate the codes into characters through the font encoding, and rebuild lines and words from the placed pieces. The page painter needs the same data, except that it turns the pieces not into text but into outlines.

Text operators and matrices

The content stream consists of operands followed by an operator. For text the important ones are Tf (font and size), Td, TD, T*, Tm (position), Tc (character spacing), Tw (word spacing), Tz (horizontal scaling), Tj, ', " and TJ (show strings). Two matrices run along: the text matrix TmT_m for the current position and the line matrix TlmT_{lm} as the anchor of the line start. Td and TD shift relative to the anchor, T* goes down by the leading TLT_L. Keeping only one matrix gives wrong positions in multi-line text.

After a string is shown, TmT_m advances by the width of the characters. For a character with code cc, width wcw_c in thousandths, font size ss, character spacing TcT_c, word spacing TwT_w (only for the single-byte code 32) and scaling h=Tz/100h = T_z/100:

tx=∑c(wc/1000⋅s+Tc+[c=32]Tw)ht_x = \sum_c \bigl( w_c/1000 \cdot s + T_c + [c=32]\,T_w \bigr)\, h

In a TJ array, numbers nn between the strings shift back in thousandths of the text height (negative: forward): d=−n/1000⋅s⋅hd = -n/1000 \cdot s \cdot h. That is kerning – and, for large values, a word gap that arises without a space character.

From codes to characters

What is in the string are codes of this font, not Unicode. The encoding lies in three layers, applied in this order (PdfFontEncoding.of):

  1. The base encoding: Standard, WinAnsi, MacRoman – or, if the dictionary names none, the built-in encoding of the embedded Type 1 program. If the PDF explicitly names a base encoding, it applies; only silence means “take the font's own”.
  2. /Differences: a sequence of numbers and glyph names that redefines individual codes. They are written last.
  3. The glyph name is translated into a Unicode character. Ligatures (fi, fl, ffi) are resolved into ordinary letters so that a search for “flow” finds the word. Extension pieces of large brackets from formula typesetting (braceex and relatives) stay empty on purpose; growing brackets are reduced to their base form.

Treating the bytes as Latin-1 gives correct plain ASCII and fails exactly where umlauts occur: WinAnsi puts typographic characters at 128–159 where Latin-1 has control characters. If /Widths is missing for one of the fourteen standard fonts, their fixed widths apply (PdfStandardbreiten), otherwise 500.

CID fonts (Type 0). Here the code is a multi-byte glyph number (two bytes under Identity-H) and says nothing about the character. The way back is in /ToUnicode, a table of code ranges to Unicode (PdfToUnicode); the widths come from the /W array of the descendant font (PdfCidBreiten). Without /ToUnicode the text cannot be recovered without the font program; the module reports it in warnings() and does not guess.

Lines, words, columns

Each placed piece is recorded as a Fragment (text, x, y, size, font, width, space width). Lines arise from them: sort by yy descending (PDF counts from the bottom), fragments whose baselines are within lineTolerance (3.0 points) belong together, within a line sort by xx. A space is inserted between two fragments if the gap exceeds

gap=xnext−(x+width)>f⋅wspace,f=0.60\text{gap} = x_{\text{next}} - (x + \text{width}) \;>\; f \cdot w_{\text{space}}, \qquad f = 0{.}60

The reference is the space width of the respective font, not the font size: a space is 250 to 600 thousandths of an em wide depending on the font. Example: at 10 point, Helvetica (space 278) has the threshold 0.6⋅2.78≈1.70{.}6 \cdot 2{.}78 \approx 1{.}7 point, Courier (600) the threshold 0.6⋅6=3.60{.}6 \cdot 6 = 3{.}6 point. A kerning gap of about 0.8 point stays below the threshold in both; a real word gap lies above it. No space is added if one of the two fragments already ends or begins with one.

Pseudocode – PdfText.extract (core)

// evaluating the content stream (Engine)
tm, tlm ← identity matrix;  Tc, Tw, TL ← 0;  h ← 1
for each operator with operands:
    select operator:
        Tf:         set font → encoding, ToUnicode if any, CID widths
        Td, TD, T*: tlm ← translate(tlm);  tm ← tlm
        Tm:         tm ← tlm ← matrix
        Tc, Tw, Tz, TL: remember value
        Tj, ', ":   show(string)
        TJ:         for each element: string → show;  number n → tm ← translate(−n/1000·s·h) · tm

show(bytes):                                             single-byte font
    m ← tm · ctm;  (x, y) ← (m[4], m[5])
    for each byte c:  text += decode(c);  width += (width(c)/1000·s + Tc + [c=32]·Tw)·h
    skala ← hypot(tm[0], tm[1])
    Fragment(text, x, y, size, font, width·skala, spaceWidth·skala)
    tm ← translate(width, 0) · tm                        text space: the matrix scales itself
                                                         CID: codes of 1–2 bytes, width from /W, ToUnicode

// lines and columns
if detectColumns and at least 8 fragments and width ≥ 4·minGap:
    count the covering fragments per strip (200);  occupied ← count > max(1, peak/10)
    gaps of width ≥ columnGapFactor · mean size → columns
    columns narrower than 6·size are added to the left neighbour column
    lines that span the gutter (headings) stay outside the column split
    every fragment without a column → nearest column             none is lost
    column by column: toLines
else toLines(fragments)

Source: envisionz-framework-pdf/src/envisionz/pdf/PdfText.java (Engine.show, Engine.showCid, toLines, joinLine, toLinesByColumn), PdfFontEncoding.java, PdfToUnicode.java, PdfCidBreiten.java.

Decision in the framework: the width of the fragment in world coordinates and the advance of the text matrix are two different numbers: the matrix advances by the width in text space (it scales itself), the fragment needs the width in world coordinates, because line assembly computes with xx values taken from the matrix. The font size is not necessarily in Tf: many typesetters write 1 there and scale through the matrix. Using only the number from Tf gives widths that are off by the scale factor, and every kerning point becomes a word gap (“An Ov er vie w”). Column detection reads tables column by column; to read row by row, set detectColumns = false.

Glyphs onto the page: PdfSeitenmaler

The painter runs the same operators and paints into a Graphics2D: each glyph as an outline of the embedded font, plus paths, fills, images, form objects, dashing and the text rendering modes. It needs only Shape and fill and is therefore suitable for native-image compilation. The outline readers are hand-written: TrueType (tables glyf and cmap formats 0, 4, 6, 12), CFF with Type 2 charstrings and Type 1 with eexec encryption.

The mapping of a glyph from font space onto the image is the chain of page mapping (scale, y downwards), text matrix times CTM, and scaling from em units to points:

image=page(scale)⋅(Tm⋅CTM⁡)⋅diag⁡(shE,sE)\text{image} = \text{page}(\text{scale}) \cdot (T_m \cdot \mathrm{CTM}) \cdot \mathrm{diag}\!\left(\frac{s\,h}{E},\ \frac{s}{E}\right)

with EE = units per em of the font (1000 for Type 1/CFF, usually 1000 or 2048 for TrueType). For Type 3 fonts the FontMatrix replaces 1/E1/E; the glyph is a content stream of its own, which a sub-run executes (nesting at most 4). The text modes: 0 fill, 1 stroke, 2 both, 3 and 7 invisible – invisible glyphs are counted, not painted.

Substitute font. If no font is embedded (or it does not know the code), the painter paints the character with a Java font – stretched to the measured advance: stretch=wtarget/wsubstitute\text{stretch} = w_{\text{target}} / w_{\text{substitute}}. The advance is measured, not the ink; for a vertical bar the ink is about one point wide, the advance three, and with the ink width the bar became a beam. Every substituted glyph is counted and reported by name (meldungen(), ersetzteGlyphen()): a substitute font that is not reported looks like the real one. sichtbareGlyphen answers whether a page is typeset or scanned.

    if text mode 3 or 7:  unsichtbar++;  return

How it is checked

  • Round trip with the own writer (PdfSmokeTest): PdfWriter produces files with exactly known content. On a file of 64 lines of tables, umlauts and code spans, 64 of 64 lines came back, 63 character-identical; the one difference was the character →, which lies outside WinAnsi and is deliberately written as a visible ? by the writer. A third-party tool (pypdfium2) reads the same files correctly.
  • Foreign file: a reference book of 1014 pages (19.7 MB, seven fonts per page) is read in 1.5 s, 29 673 lines; spot checks agree character for character with pypdfium2. The book exposed ligatures, word gaps and kerning that the round trip could never have shown, because the writer sets no ligatures and no matrix scaling.
  • Texkodierungprobe, Cmapprobe, Cidbreitenprobe, Standardbreitenprobe: encodings, ToUnicode, /W and standard widths. PdfSmokeTest part 6b guards the column assignment against loss of fragments (test piece via PdfWriter.table, right-aligned value columns, two data rows).
  • Umrissprobe: outlines against a computed bounding box. TrueType, quadratic curve with control point at 1000: apex 14⋅0+12⋅1000+14⋅0=500\tfrac14\cdot0+\tfrac12\cdot1000+\tfrac14\cdot0 = 500. CFF, cubic curve with control points at 750: apex 3t(1−t)⋅7503t(1-t)\cdot 750 at t=12t=\tfrac12 times two points, =562.5= 562{.}5.
  • Seitenmalprobe, Textschichtprobe, Type1probe, Type3malprobe: pages in memory, rasterised at scale 4; the target colours of individual points are computed from the page (an image with four differently coloured quarters shows mirroring and rotation, a single-colour square does not).

Limits

  • CID fonts without /ToUnicode stay unreadable and are reported; predefined character collections (Adobe-Japan1 and relatives) are not implemented.
  • Column detection cannot tell text columns from table columns; tables are read column by column as long as detectColumns is set.
  • The standard widths suffice for line and word building, not for pixel-accurate setting of embedded fonts without /Widths.
  • The painter draws outlines, not hinted rasterised characters; the substitute font is only an approximation of the real one.
