Document, filters and encryption – background

How PdfDocument reads a PDF file without a cross-reference table, how PdfFilters unpacks streams and undoes prediction, and how PdfEntschluesselung forms the file key.

What this is about: a file made of numbered objects

A PDF file is a collection of numbered objects of the form 12 0 obj … endobj. An object is a number, a name, a string, an array, a dictionary – or a stream: a dictionary followed by binary data between stream and endstream. The root node (/Root, the catalog) leads through the page tree to the pages; content, fonts and images hang from it as further objects. At the end of the file are the keyword trailer with /Root and a table (xref) giving the byte offset of every number.

Ordinary readers go from back to front: startxref → table → offset → object. That breaks as soon as a single offset is wrong – for instance because someone sent the file through a text editor. Since PDF 1.5 the table can itself be a compressed stream, and many objects are bundled in object streams without an offset of their own.

The lexer: bytes, three traps

PDF mixes text and binary data. Any character-set conversion while reading would corrupt the binary parts, so PdfLexer works on byte[] with a moving cursor. Three peculiarities of the syntax are the classic stumbling blocks:

  1. Nested parentheses. (a (b) c) is one string with the content a (b) c. The lexer counts openings and closings; a character escaped with a backslash does not count.
  2. #-escapes in names. /FICL#3AEnfocus means FICL:Enfocus; #3A is the byte with hexadecimal value 3A.
  3. /Length as a reference. If a stream says /Length 42 0 R, the length is not yet known while parsing. The lexer resolves the reference if it can; if the length is wrong or missing, it searches for the keyword endstream.

The result is a PdfObject – a sealed interface with nine record types (null, boolean, number, string, name, array, dictionary, stream, reference). Sealed means a switch over the types is checked by the compiler for completeness; if a tenth type is added, the compiler reports every place that does not handle it.

Decision in the framework: arrays and dictionaries may be nested at most 512 levels deep (PdfLexer.TIEFE_MAX). Deeper input is rejected with an exception instead of crashing with a StackOverflowError. The page tree is traversed to depth 64 and each node is visited only once, so that a cycle in /Kids ends.

Search the file instead of trusting the xref

PdfDocument does not read the cross-reference table. Instead it searches the file for every pattern number number obj and remembers the offset after obj. The module names three reasons: it survives wrong offsets (the most common defect in the wild); it needs no /Prev chains of incremental updates, because the last occurrence of a number wins anyway; and it is considerably shorter than supporting classic table and xref stream together. The price is one full pass over the file.

Pseudocode – PdfDocument.scanObjects and load

// 1. find objects
for i ← 0 to length−4:
    if data[i..i+2] ≠ "obj": continue
    if data[i+3] is a regular character: continue        "object", "objstm" …
    // backwards: whitespace, generation, whitespace, number
    gen ← digit run before i;  num ← digit run before that
    if either is empty or a regular character precedes: continue
    offsets[num] ← i + 3                                 later occurrences overwrite
    generationen[num] ← gen

// 2. trailer: xref stream first, then all "trailer" dictionaries from the back
trailer ← { Root, Info, Encrypt from objects with /Type /XRef }
for each occurrence of "trailer", from the end of the file:
    for each key of the dictionary: add it if not yet present

// 3. encryption (if /Encrypt), 4. unpack object streams

    plain ← PdfFilters.decode(stream)
    read N pairs (object number, offset); object i starts at First + offset[i]

// 5. pages

Source: envisionz-framework-pdf/src/envisionz/pdf/PdfDocument.java (scanObjects, readTrailer, expandObjectStreams, collectPages). A defective object stream is skipped; the remaining objects stay usable.

Decision in the framework: objects found individually take precedence over those from an object stream, because they come from a possibly newer version of the file. If a page has no resources, they are inherited from the parent node (PdfDocument.resources); looking at the page alone finds no fonts and no images in some files.

Stream filters and prediction

The bytes of a stream are usually packed. The dictionary names the chain in /Filter; unpacking happens in the stated order. Implemented are FlateDecode (zlib, via java.util.zip.Inflater), LZWDecode, ASCIIHexDecode, ASCII85Decode and RunLengthDecode. An image filter (DCT, CCITT, JBIG2, JPX) ends the chain: it delivers not a byte array but an image, and belongs to PdfImages (see Scans: images and decoders).

Two robustness measures for Flate: leading whitespace before the zlib data is skipped, and a truncated stream delivers what was unpacked up to the error instead of an exception. If the zlib header is unreadable, a second attempt is made without a header.

Prediction

Flate and LZW often get an upstream predictor: before packing, each byte is replaced by a prediction from its neighbours and only the difference is stored. Smooth image rows then contain many small values and pack better. When reading, the difference has to be added back – without this step the unpacked data has the right length but the wrong content, an error that is hard to find.

With xx for the stored byte, aa for the byte to the left (one pixel width back, bpp=max⁡(1,colours⁡⋅depth⁡/8)bpp = \max(1,\,\mathrm{colours}\cdot\mathrm{depth}/8)), bb for the byte above and cc for the one above left, the PNG types are, all modulo 256:

TypeNameInverse
0Nonev=xv = x
1Subv=x+av = x + a
2Upv=x+bv = x + b
3Averagev=x+⌊(a+b)/2⌋v = x + \lfloor (a+b)/2 \rfloor
4Paethv=x+Paeth⁡(a,b,c)v = x + \mathrm{Paeth}(a,b,c)

Paeth forms p=a+b−cp = a + b - c and picks, among a,b,ca, b, c, the value closest to pp; on a tie the order is aa, then bb, then cc. With the PNG types each row is preceded by a filter byte, so a row is columns⁡⋅colours⁡⋅depth⁡/8+1\mathrm{columns}\cdot\mathrm{colours}\cdot\mathrm{depth}/8 + 1 bytes long. Predictor 2 is the TIFF difference: only type “Sub” for the whole row.

Example (by hand). Three bytes in a row of type “Up”. The row above is 10, 20, 30; the differences 1, 2, 3 were stored. Back: 10+1,20+2,30+3=11,22,3310+1,\ 20+2,\ 30+3 = 11, 22, 33. With type “Sub” and bpp=1bpp = 1 and the bytes 5, 1, 1 the result is 5, 6, 7.

Encryption: the standard security handler

Many PDFs are encrypted without anyone knowing a password: they carry only an owner password against printing or copying, and the user password is empty. The reader must still be able to open them. PdfEntschluesselung implements the standard security handler of all revisions.

R2 to R4: MD5 and RC4 or AES-128

The password is padded to 32 bytes (a fixed padding pattern PAD). The file key is the MD5 of the padded password, the /O entry (at most 32 bytes), the permissions /P as four bytes (least significant first), the first file /ID and – from R4, if the metadata is not encrypted – four bytes 0xFF. From R3 the hash is formed 50 more times over the first nn bytes; nn is the key length in bytes. Whether the password is right is shown by the /U entry: the reader encrypts the padding pattern (R2) or MD5(PAD‖ID) with 20 RC4 passes (R3, R4) and compares.

If the password does not fit as a user password, it is tried as an owner password: from it the user password can be recomputed from /O (for R3/R4 by 20 RC4 passes with modified keys, backwards), and the check starts over with that.

Each object gets its own key: MD5 over the file key, object number (3 bytes) and generation (2 bytes, least significant first), for AES additionally the four bytes “sAlT”; the first min⁡(n+5,16)\min(n+5,\,16) bytes are used. At 40 bits (n=5n=5) that is 10 bytes, at 128 bits 16 bytes. AES works in CBC mode; the first 16 bytes of the data are the initial value (IV).

R5 and R6: AES-256

Here the file key is not derived but stored in /UE or /OE, encrypted with AES-256. The key for that comes from a hash over the password, an 8-byte salt from /U or /O (bytes 32–39 for the check, bytes 40–47 for the key) and, for the owner password, the first 48 bytes of /U. If the check hash equals the first 32 bytes of the entry, the password is right. R5 simply uses SHA-256 as the hash. R6 (ISO 32000-2, algorithm 2.B) repeats at least 64 rounds: 64 copies of password‖K‖extra are encrypted with AES-128-CBC (key and IV from K); the sum of the first 16 bytes modulo 3 selects SHA-256, -384 or -512 for the next K; from round 63 the loop ends as soon as the last byte is ≤\le round − 32.

Pseudocode – PdfEntschluesselung.aus (R2–R4, abridged)

for each candidate pw in [given password]:           empty if none given
    k ← MD5(auffüllen(pw) ‖ O[0..31] ‖ P (4 bytes LE) ‖ ID0 [‖ FFFFFFFF])
    if R ≥ 3:  repeat 50 times: k ← MD5(k[0..n−1])
    k ← k[0..n−1]
    if benutzerPasst(k):  return k                    as user password
    // as owner password
    h ← MD5(auffüllen(pw));  if R ≥ 3: 50 times h ← MD5(h[0..n−1])
    benutzer ← O;  R=2: RC4(h, O)   |   R≥3: for i ← 19 down to 0: benutzer ← RC4(h xor i, benutzer)
    k ← as above, but with benutzer[0..31] instead of auffüllen(pw)
    if benutzerPasst(k): return k
else PdfPasswortException (passwortGegeben: wrong or not given at all)

// per object
RC4:    RC4( MD5(k ‖ num₃ ‖ gen₂)[0..min(n+5,16)−1], data )
AES128: as RC4, with “sAlT” appended;  CBC, IV = first 16 bytes
AES256: CBC with the file key itself, IV = first 16 bytes

Source: envisionz-framework-pdf/src/envisionz/pdf/PdfEntschluesselung.java (schluessel24, dateischluessel, benutzerPasst, schluessel56, hash, objektschluessel, rc4). RC4 is hand-written; MD5, SHA-2 and AES come from the JDK.

Decision in the framework: the permissions in /P are not enforced; the module only reads. Not decrypted are the /Encrypt dictionary itself, xref streams and strings inside an object stream (they are encrypted with the stream, not individually). A single string that cannot be decrypted stays as it was instead of making the document unusable.

How it is checked

  • Verschluesselungsprobe: five files that the third-party tool qpdf generated from the same unencrypted template – RC4 with 40 and 128 bits (R2, R3), AES-128 (R4), AES-256 (R5, R6), with empty user password, with user and with owner password. Each must deliver the template's text (checks the streams) and, in the info dictionary, its /Creator (checks the strings, which are decrypted separately). Also known test vectors for RC4 and for R6 (ISO 32000-2, algorithms 2.B and 2.A) and the rejection of wrong passwords.
  • Grenzfallprobe: 200 000 opening parentheses are rejected instead of ending in a StackOverflowError.
  • Xrefstromprobe checks that the catalog is also found without the trailer keyword, even when it lies in an object stream. PdfSmokeTest builds a complete mini PDF in memory, including a stream with /Length as a reference, and reads it back.

Limits

  • The search reads the file once completely; at file sizes around 20 MB this is immaterial (module figure: about 2 s for the 16 833 objects of a 19.7 MB book), for many gigabytes an xref reader would be more economical.
  • The TIFF predictor is implemented only for 8 bits per component.
  • Security handlers other than the standard one (/Filter /Standard) and revisions other than R2–R6 are rejected with a message.
  • A stream filter the module does not know is passed through – the bytes are then not unpacked.
