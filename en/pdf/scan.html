Images from scanned PDFs: fax, JBIG2 and JPEG 2000 – background

How PdfImages turns image streams into images and assembles scanned strips by their position, and what CcittDecoder, Jbig2Decoder, MQDecoder and Jpx compute.

What this is about: pages that consist only of images

A scanned technical manual has no text but one or many images per page. They are stored losslessly and heavily compressed, because they are mostly two-colour originals: CCITT Group 3/4 (fax), JBIG2 or, in newer files, JPEG 2000. The JDK can do none of the three. All three are hand-written here; javax.imageio reads JPEG (DCT), and Flate and LZW are stream filters that deliver raw pixels.

PdfImages.extract resolves width, height, bit depth (1 to 16), colour space (grey, RGB, CMYK, palette, ICC, DeviceN, Separation) and filter for each image object and delivers a BufferedImage. A filter that no decoder serves is recorded in unsupportedFilter; the image is then missing, not silently delivered empty.

Strips by position, not by order

Scanners often store a page as many narrow strips (here 2040 × 63 points, 80 of them on two pages). The order in the resource dictionary is arbitrary. PdfImages.composePage therefore assembles the strips by their placement in the content stream: PdfContentPlacement follows the operators q, Q, cm and Do with the transformation matrix and delivers for each image name, xx, yy, width and height. On a page where the dictionary order was wrong, the heading ended up in the middle of the table; grid detection found 13 rows and 0 columns. Sorted by position: 63 rows and 15 columns. The image looked table-like at first glance, only detection failed – an error that is easily misread as a threshold problem.

CCITT Group 3 and 4

A two-colour image consists of runs: so many white points, then so many black, alternating. Group 3 (one-dimensional) writes each image row as a sequence of run lengths, each with a fixed Huffman code from two tables (terminating and make-up codes for white and black). Group 4 (two-dimensional) saves further: it codes each row relative to the previous one, the reference row. Only the changing elements are stored – the places where the colour changes.

With a0a_0 as the last set position of the current row, a1a_1 as the next change of the current row (sought), b1b_1 as the first change of the reference row to the right of a0a_0 to the opposite colour and b2b_2 as the following change, there are three modes:

Example (by hand). Width 10, reference row: white 0–2, black 3–6, white 7–9, so changes at 3 and 7. Current row: black 4–6, changes at 4 and 7. Start: a0=−1a_0 = -1, colour white. b1=3b_1 = 3 (the first change to black right of a0a_0); a1=4=b1+1a_1 = 4 = b_1 + 1: VR(1), code 011. Now a0=4a_0 = 4, colour black; b1=7b_1 = 7, a1=7a_1 = 7: V(0), code 1. Finally a0=7a_0 = 7, white; the reference row has no change to the right of it, b1=b_1 = end of row =a1= a_1: V(0), code 1. Together 01111.

The search for b1b_1 starts each step behind the previous find instead of at the start of the row; for a JBIG2 collective image many thousand points wide, a quadratic search would be untenable. With damaged data the partial row is completed, not aborted.

JBIG2: arithmetic coding with context

JBIG2 compresses two-colour pages better than fax because it rounds no symbol up to whole bits. The MQ coder (the same as in JPEG 2000) maps the whole message onto an interval and reaches fractions of a bit per image point when the point is well predictable. Two building blocks:

  1. The state machine. For each context there is a state from a fixed table of 47 entries: the estimated probability QeQ_e of the less probable symbol, the next state after the probable symbol (NMPS), after the improbable one (NLPS) and a switch bit that swaps which symbol counts as probable. The decoder learns as it goes, without statistics being sent along. An interval of size AA is shortened by QeQ_e; if the code value CC lies in the lower part (Chi<QeC_{hi} < Q_e), it generally belongs to the less probable symbol, otherwise to the more probable one; if the sub-interval of the more probable one becomes too small, the two exchange roles (conditional exchange). If AA falls below 2152^{15}, it is doubled and bits are shifted in from the stream (renormalisation). The byte 0xFF introduces a marker; if a byte above 0x8F follows, ones are supplied, otherwise only seven instead of eight bits.
  2. The context. In the generic region, the context of a point comes from its already decoded neighbours to the left and in the rows above; template 0 has 16 neighbours, hence 216=655362^{16} = 65\,536 contexts (new int[1 << 16]), plus four movable “adaptive pixels”. A black point in a white neighbourhood is improbable and costs many bits, a white one few.

In addition come the region types that occur in practice in scanned manuals. Symbol dictionary and text region: recurring letter shapes are coded once and then merely placed (symbol number plus position within a strip); when placing, the reference corner (REFCORNER) decides whether the width is added to SS before or after placing. Refinement: a symbol or region is re-coded against a reference image. Huffman tables (standard and custom), halftone regions and the MMR variant of the generic region, which like the halftone regions uses the fax decoder.

Source: envisionz-framework-pdf/src/envisionz/pdf/jbig2/MQDecoder.java (decode, byteIn), Jbig2Decoder.java (generic region, segment headers), Symbolwoerterbuch.java, Textbereich.java, Verfeinerung.java, Huffmantafel.java, Halbton.java.

Decision in the framework: the colour extension of JBIG2 is not provided for in PDF and is reported, not decoded. State table and contexts are taken from the standard; a single wrong next state shows up as an image that turns to noise after a few rows. The segment headers use the short or long form of the reference count and a reference width of 1, 2 or 4 bytes depending on the segment number (up to 256, up to 65 536, above).

JPEG 2000: wavelets and bit planes

JPEG 2000 decomposes each component of an image (possibly in tiles) with a wavelet transform into subbands of growing resolution: a coarse low-pass image LL and, per level, three bands HL, LH, HH with the details. Each subband is divided into code blocks, and each block is compressed bit plane by bit plane with the MQ coder (EBCOT). The decoder reverses this: read packets, decode blocks, compute the wavelet back, transform components back, bring to bit depth.

Block decoder (EBCOT, Tier 1)

From the highest bit plane downward, three passes per plane, scanned in stripes of four rows, column by column within them: significance (points that are not yet significant but have a significant neighbour), refinement (points that were already significant) and clean-up (all others, with a run-length mode for entirely empty columns). The first plane has only the clean-up pass. 19 contexts: 0–8 zero coding by number and position of significant neighbours (depending on the subband orientation), 9–13 sign, 14–16 refinement, 17 run length, 18 uniform. Six code-style switches of the standard are implemented (bypass, reset, termination per pass, vertically causal, predictable termination, segmentation symbols).

Values are held internally at double resolution with midpoint: if a point becomes significant on plane pp, its magnitude is 3⋅2p3\cdot 2^p (midpoint between 2p2^p and 2p+12^{p+1}, times two); each refinement on plane qq halves the interval. Whoever has all planes down to 0 gets the magnitude back exactly with >>1>> 1.

The inverse wavelet transform

From LL and the three high bands of the next resolution, the LL band of the next larger resolution arises: the values are interleaved (even/even from LL, odd/even from HL, even/odd from LH, odd/odd from HH – computed in the reference grid, not in the array), then transformed back row by row, then column by column. Two filters:

The integer 5/3 filter (lossless), with YY for the coefficients and XX for the values; the border is continued symmetrically without duplicating the edge value:

X2n=Y2n−⌊Y2n−1+Y2n+1+24⌋,X2n+1=Y2n+1+⌊X2n+X2n+22⌋X_{2n} = Y_{2n} - \Big\lfloor \frac{Y_{2n-1} + Y_{2n+1} + 2}{4} \Big\rfloor, \qquad X_{2n+1} = Y_{2n+1} + \Big\lfloor \frac{X_{2n} + X_{2n+2}}{2} \Big\rfloor

The 9/7 filter (floating point) with four lifting steps and scaling: first even positions times KK, odd ones divided by KK; then in turn at the even positions xi←xi−δ(xi−1+xi+1)x_i \leftarrow x_i - \delta\,(x_{i-1}+x_{i+1}), at the odd ones with γ\gamma, even with β\beta, odd with α\alpha:

α=−1.586134342,β=−0.052980119,γ=0.882911076,δ=0.443506852,K=1.230174105\alpha = -1{.}586134342,\ \beta = -0{.}052980119,\ \gamma = 0{.}882911076,\ \delta = 0{.}443506852,\ K = 1{.}230174105

Main header, tile headers, resolutions, subbands, precincts, code blocks and tag trees are in Codestrom and Kachel; the JP2 container (colour specification, palette, channel definition) in Jp2.

Decision in the framework: Jpx.dekodiere(bytes, reduzieren) omits the topmost wavelet levels (reduzieren = 1: half resolution); Jpx.aufbau reads only the header. A JPEG 2000 image of 8192 × 8192 points is rejected without allocating hundreds of megabytes, and a stream that ends in the middle of a packet returns in at most five seconds (before, the decoder counted missing bit planes up to over two billion).

How it is checked

  • Jbig2probe: ITU-T T.88 Annex H.2: 32 bytes of input, coded bit by bit in one context, give 30 bytes; the decoder must turn the 30 back into the 32. An own MQ encoder after Annex E is itself bound to this sequence. Also neighbourhoods of templates 0 to 3, adaptive pixels and the segment-header forms. Konformitaetsprobe uses ITU conformance data and third-party files from SerenityOS, where the reference decoder jbig2dec reads differently.
  • Jpxprobe: eleven code streams of the ITU conformance data against size and CRC of their reference images per component, all required exact in class 1, among them three with the 9/7 filter, several layers, tiles, POC, ROI and code-style switches. The same code stream in the JP2 container must give the same. The remaining 12 code streams and nine JP2 files of the conformance data were measured once and passed.
  • Fax: the probe checks that the height of each strip equals the declared one and no strip is more than 70 % dark. “An image was produced” and “the right image was produced” are different statements: an error in vertical modes with offset 2 (000011 and 000010) produced strips with 6, 5, 23 or 63 rows instead of a uniform 63, one was 98.2 % dark.
  • Grenzfallprobe: malicious inputs for Jpx (see above).

Limits

  • The JBIG2 colour extension and JPEG 2000 parts other than Part 1 are not implemented; pixel and tile limits protect against malicious files.
  • Fax and JBIG2 deliver bitmaps with one bit per point; colour and grey levels come from the image dictionary (PdfImages), not from the decoder.
