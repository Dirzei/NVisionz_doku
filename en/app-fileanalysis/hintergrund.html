Reading, interpreting and recognising – background

How the file analysis computes: how it is ensured that a loaded file is never overwritten, why it reads page by page, how it interprets bytes, recognises formats and colours regions, how the record grid and the search work, how elements come out of documents, when a PDF page counts as a scan, how text recognition places its boxes, how the analysis time is measured and how an analysis chain runs.

What this is about

For any file the app answers two questions: What is it? and What is in it? The format readers, the text structure recognition and the decoders for PDF, PostScript and JPEG 2000 come from framework-fileformats and framework-pdf, the line recogniser from framework-ocr. The app connects them and makes decisions of its own on the way: what is read and how much, which view a file gets, which colour means what and what it may write at all. This page describes those decisions.

Read-only

The view has no write path, not even a disabled one. Each page of the byte view is read through a channel opened only with the option READ and closed at once; the file is therefore not held open and not locked for the program that produces it. This is secured not by a promise but by a probe that searches the source of the byte view for every write call (write and append option, write, delete, random file access, output stream) and requires the text area to be explicitly non-editable.

Besides that there are write paths of a tool, which run only on request and never edit the file being read. How they protect against overwriting differs:

  • Recognised text is written only into a new file: the option CREATE_NEW makes the write fail if the file already exists.
  • Anonymise places the copy as name-anonym.ext next to the file and writes nothing if it already exists. On the command line the tool aborts when target and source are the same file; the source stays byte for byte the same.
  • Extracts from PDF and PPTX and the saved analysis chain go into the file (for PDF images: the folder) chosen in the file dialog. Since 12 November 2026 the same two-stage protection applies: if a target is the loaded file, it is always refused, with a message in the panel – for images every single target file is checked before the first byte is written. If a target already exists, a confirmation appears in the panel below the footer (or below the buttons of the chain card), not a pop-up; only triggering the same action with the same target again within ten seconds replaces the file. Without that consent the write core opens with CREATE_NEW, so an existing file makes the write fail.

Page by page, not whole

The byte view never reads the whole file, only what it shows. With GG the file size and vv the offset of the first line shown, it reads

n=min⁡(1024,G−v)bytes from v,page ⌊v1024⌋+1ofmax⁡(1,⌈G1024⌉).n = \min(1024,\ G - v) \ \text{bytes from } v, \qquad \text{page } \Big\lfloor \frac{v}{1024} \Big\rfloor + 1 \ \text{of} \ \max\Big(1, \Big\lceil \frac{G}{1024} \Big\rceil\Big).

Behind the end and for a negative offset nothing comes back, without an error. For G=5000G = 5000 and v=4096v = 4096 these are 904 bytes on page 5 of 5. A jump rounds the target offset zz down to the start of its 16-byte line, v=16⌊min⁡(z,G−1)/16⌋v = 16 \lfloor \min(z, G-1) / 16 \rfloor, because a hex view whose lines do not start at round addresses cannot be counted by eye.

The other tabs read just as sparingly: the inspection (text or binary, signature) and the format recognition look at the first 4096 bytes; the line view reads at most 4⋅220+14 \cdot 2^{20} + 1 bytes – the one byte more only says whether there was more, and then the beginning is recognised and the view says so. Inspection, record grid and recognition run in the background, not on the event thread.

Coming back. Each tab keeps the results of the last six analyses; the most recently used stays, the oldest drops out. The key is not the path alone but the file state (path,G,tmodified)(\text{path}, G, t_{\text{modified}}): if size or time stamp changes, it is a different file and is computed again. A checksum would be safer but would cost exactly the reading that is to be saved.

Interpreting bytes

A line of the byte view has a fixed layout: eight hex digits of address, two spaces, sixteen bytes of three characters each with one extra space after the eighth, one space, sixteen characters of plain text (printable are the values 32 to 126, everything else shows as a dot). From this follows which byte jj lies under the caret in column ss, with k=s−10k = s - 10:

j={⌊k/3⌋,0≤k<24,7,k=24,min⁡(15,8+⌊(k−25)/3⌋),24<k,s<60,min⁡(15,s−60),s≥60(plain text).j = \begin{cases} \lfloor k/3 \rfloor, & 0 \le k \lt 24,\\ 7, & k = 24,\\ \min\big(15,\ 8 + \lfloor (k-25)/3 \rfloor\big), & 24 \lt k,\ s \lt60,\\ \min(15,\ s - 60), & s \ge 60 \ \text{(plain text)}. \end{cases}

The space behind a byte still belongs to it, the middle gap to the eighth. The Interpret card follows this caret; if it is in no data line (for example in a record line), the start of the page applies.

From this position up to eight bytes are read and interpreted twice, once little endian, once big endian, one below the other: byte (unsigned), from two bytes short, from four int and float, from eight long and double. If bytes are missing, the interpretation is missing instead of being padded with zeros. The bytes 00 00 00 00 00 00 f0 3f give the double 1.0 little endian and a subnormal number around 3.04⋅10−3193.04 \cdot 10^{-319} big endian; magnitudes like these show which interpretation is right. Floating-point numbers with |x|<10−4|x| \lt 10^{-4} or |x|≥109|x| \ge 10^{9} are shown in exponent notation, NaN and infinity written out, because they are the most frequent sign of a wrong interpretation.

Recognising: text, format, group

Text or binary. From the first n=min⁡(G,4096)n = \min(G, 4096) bytes the inspection counts the zero bytes n0n_0 and the printable bytes dd (line feed, carriage return, tab, 32 to 126 and from 160). The file counts as text if

n>0,n0=0,p=⌊100dn⌋≥85.n > 0, \qquad n_0 = 0, \qquad p = \Big\lfloor \frac{100\, d}{n} \Big\rfloor \ge 85 .

Alongside stand a byte order mark, the line endings, whether the bytes are valid UTF-8, and the number of distinct byte values. The result decides which tab opens when another app hands a file to the file analysis: the content, not the extension. Measurement files are often called .dat or .bin and are text; a .txt sometimes is not. If the inspection fails, the file counts as binary, because the byte view copes with everything and the line view does not. If you pick a file in the working folder yourself, the tab in front stays.

Format. The data tab asks the format recognition for the format: it compares the start of the file (up to 4096 bytes) with the signatures, opens ZIP, compound and HDF5 containers to determine the sub-type, and finally checks cases without a signature (a shifted HDF5 header, STL). By the format the app chooses the path: PDF, PostScript, JPEG 2000 and PPTX have branches of their own, raster images go to the image reader, everything else to a data source with outline and tables. If you force a reader (“Open file as …”), the app says when the recognition found something else.

Groups. The 55 formats of the toolkit sit in seven groups of the rail: containers, databases, measurement data, meshes and fields, images, packing, other (including “unknown”). Each format stands in exactly one group. This is checked two ways – the sum of the group sizes and the set without duplicates must both give the number of formats – because a grouping that forgets a format makes it unreachable without anything crashing.

Colouring bytes and lines

Bytes. In the byte view exactly two things are coloured: the first byte of each record green (see record grid) and the search hit jumped to with a yellow background. Everything else stays without colour so that colour means something. Switched off, the same text is inserted in one piece, for example for copying it out.

Lines. In the line view each line gets the colour of the rule that claims it, and the other way round from what one expects: what is recognised is pale, what is unknown stands out. The hue says what is claimed (header line, count field, marker or assignment, record or value block), the strength how certain. The colour is not set fixed but mixed into the background gg of the view:

c=(1−a)g+at,a={0.34unknown,0.22confirmed or assumed,0.15only measured,c = (1 - a)\, g + a\, t, \qquad a = \begin{cases} 0.34 & \text{unknown},\\ 0.22 & \text{confirmed or assumed},\\ 0.15 & \text{only measured}, \end{cases}(1)

rounded per colour channel. For recognised regions every second block gets 0.0450.045 more, so that two neighbouring value blocks do not look like one – their boundary is exactly where a format description has to start a loop. On a dark background, that is at a brightness

Y=0.299R+0.587G+0.114B255<0.5,Y = \frac{0.299\, R + 0.587\, G + 0.114\, B}{255} \lt 0.5,

the hue is first mixed 35 % with white and the share aa multiplied by 1.25; otherwise a medium-dark hue on a dark background would give hardly any distance. So the hue stays the same in both themes, the brightness follows the theme, and there is no second colour table. A probe measures in both themes that unknown lies further from the background than confirmed, and confirmed further than merely measured.

Record grid

Fortran writes an unformatted file as a sequence of records: before each record its length LL as a 4-byte number, behind it the same number once more. The app first determines the byte order from the first record – little endian, otherwise big endian – if 0<L≤G−80 \lt L \le G - 8 holds and the trailing marker at 4+L4 + L carries the same value. Then it walks the chain:

s0=0,record i:payload from si+4,length Li,si+1=si+8+Li,s_0 = 0, \qquad \text{record } i:\ \text{payload from } s_i + 4,\ \text{length } L_i, \qquad s_{i+1} = s_i + 8 + L_i ,

as long as si+8+Li≤Gs_i + 8 + L_i \le G and the trailing marker equals LiL_i. If leading and trailing marker disagree, the grid stops there: a half-invented record division would be worse than none, because it looks as if it were right. At most 4096 records are computed; above the page stand the records that fall on it. With three records of 8 bytes each the payloads lie at 4, 20 and 36.

Searching

Text or byte sequence. The input counts as a byte sequence if – after an optional 0x and without the separators space, colon, underscore and hyphen – it consists of at least two hex digits and either carries 0x, contains separators or has an even number of digits. An odd number is padded with a leading zero. Otherwise the input is searched for as UTF-8 text. This is a heuristic (cafe is both); therefore the location line says what was actually searched for.

Block by block with overlap. For a pattern of length mm the search reads blocks of size B=max⁡(4096,4m)B = \max(4096,\ 4m) and advances by

s←s+b−(m−1),s \leftarrow s + b - (m - 1),

where bb is the number of bytes read. Without the overlap of m−1m-1 bytes it would not find an occurrence that reaches across a block boundary. With m=6m = 6 the second block starts at 4091; a hit at 4094 lies across the boundary 4096 and is found.

Next. Search starts at the position shown, Next at the byte behind the last hit, as long as that lies on the page. If nothing more is found up to the end, the search starts from the beginning and says so in the same message that names the hit.

Elements from documents

PDF. What the selected node of the outline means is fixed by a scope: the root stands for the whole document, “Seite nn” for the page with number n−1n-1, the group “Seiten” for nothing – it means the same set as the root, and two menu items doing the same thing invite mistakes. The text goes into one file, explicitly in UTF-8 (an “ä” stands there as C3 A4); the images go as PNG into a folder, named after page or document, running number and name of the image. An image that could not be converted is named with its filter instead of being skipped.

PPTX. You choose a shape of the slide. An embedded image comes out unchanged, the app determines the extension from the bytes (PNG, JPEG, otherwise .bin instead of a guessed one); a table becomes CSV with quotes doubled; otherwise the text of the shape. Charts and SmartArt have nothing to give out.

JPEG 2000. The file is recognised by its content, even under a wrong extension, and converted completely into an image with the decoder from framework-pdf. A bare code stream carries no colour information: with several components the app shows the first three as red, green, blue (with two, the first as grey) and says that this is an assumption; with four it names the frequent CMYK case. A JP2 file carries its colour space; an attached colour profile is named.

Scales. Pages and slides are drawn as images; the image size follows the size of the page in points (1pt⁡=1/721\,\mathrm{pt} = 1/72 inch):

w=round⁡(b⋅m),mPDF⁡=1.5,mPS⁡=10872=1.5,mslide⁡=1.25pixels per point.w = \operatorname{round}(b \cdot m), \qquad m_{\mathrm{PDF}} = 1.5, \quad m_{\mathrm{PS}} = \frac{108}{72} = 1.5, \quad m_{\mathrm{slide}} = 1.25 \ \text{pixels per point}.

An A4 page of 595.28595.28 points becomes 893 pixels wide, a PostScript page of 100×50100 \times 50 points 150×75150 \times 75. For a PDF page the visible area applies (including one inherited from the page tree) and the rotation by multiples of 90°. In slides a font size gg is drawn with the font scale σ\sigma of the autofit, max⁡(6,round⁡(gσm))\max\big(6, \operatorname{round}(g\, \sigma\, m)\big) pixels, so that an overfull box does not run out of its frame at the bottom.

Zoom. The mouse wheel changes the scale by the factor 1.15 per notch, limited to 0.05 to 20. A typeset PDF page and a slide are then redrawn at the new scale instead of enlarging pixels; the outlines of the type stay sharp. A PostScript page, a photo and a scan are not redrawn.

Scanned or typeset

A PDF page counts as scanned if it carries no visible text; then its images are composed into the page at their positions, and exactly that is shown. If it carries visible text, it is typeset, even if a full-page image lies beneath (a letterhead, say): then the glyphs are drawn as outlines from the embedded font in their fill colour, together with lines, areas and images. In short:

scanned⟺visible glyphs=0∧images present.\text{scanned} \iff \text{visible glyphs} = 0 \ \wedge\ \text{images present}.

Invisible text (rendering mode 3, the recognition layer of a scan) does not count; a scan with text recognition stays a scan. A scanned image is not redrawn when zooming – it cannot become sharper than it is – but it is rotated like a typeset page. The typeset page says explicitly that it is not the whole page: it names how many glyphs came with the original font and how many with a substitute, how many lines, areas and images are painted, and that gradients, patterns and transparency are missing.

Text recognition

The Recognise text card reads the image shown – photo, screenshot, scanned page, PostScript page or slide image – with the line recogniser from framework-ocr: the whole page, with deskewing and columns. It runs only on request and in the background; for text the recogniser with stride 2 is preselected. The result is blocks of lines of pieces; in the text, pieces are separated by spaces, lines by line breaks and blocks by an empty line, uncertain pieces with an orange background.

Boxes. The boxes of the pieces read are carried back from the deskewed image into the one shown and stored in pixels of the original: if the image shown is drawn at scale β\beta (a PDF page, say, at 1.5) and the view shows at effective scale mm, a corner satisfies

u=xβ,X=x0+um.u = \frac{x}{\beta}, \qquad X = x_0 + u\, m .

So the boxes stay right when zooming, even when a PDF page is redrawn in the process; a new image clears them. Certain pieces are outlined in blue, uncertain ones have an orange background; the boxes can be switched off. The app writes the recognised text only into a new file (above).

Measuring the analysis time

To decide whether a persistent store for analysis results pays off, the app measures in real use how long its three background analyses take (bytes, lines, data); hits in the cache do not count. Per analysis it appends a line to a measurement file in the user folder (.envisionz/fileanalysis-messung.csv): time, session, view, key, size, duration in ms. The key contains no file name; it is the first 8 bytes (16 hex digits) of the SHA-256 over path, size and modification time. The measurement is switched on only when the app builds its window, it stops at a measurement file over 2 MiB, and a write error never disturbs the analysis. An analysis that fails is measured too.

The evaluation (cmd.fileanalysis.Analysedauer) counts nn analyses with durations did_i, of which nsn_{\mathrm{s}} have di>5sd_i > 5\,\mathrm{s}, and names median and maximum. A store pays off if slow analyses occur regularly and a file analysed slowly is looked at again:

nsn≥0.10∧∃k:|sessions⁡(k)|>1,maxi∈k⁡di>5s.\frac{n_{\mathrm{s}}}{n} \ge 0.10 \ \wedge\ \exists\, k:\ \big|\mathrm{sessions}(k)\big| > 1,\ \max_{i \in k} d_i > 5\,\mathrm{s} .

Return 10 means fulfilled, 0 not fulfilled, 1 no measurement data, 2 file not readable. Ten analyses with two slow ones but no file looked at again do not fulfil the condition.

Analysis chains

The Analysis chain card splits the recognition of the line view into steps. Each step needs and supplies ingredients:

Stepneedssupplies
Split lineslinesmarkers, signatures
Measure print controllinescontrol
Form blocksmarkers, signaturesblocks, wraps, header lines
Measure column gridblocks, markersgrid
Wrapped recordswrapswraps
Header linesheader linesheader lines

If a step lacks an ingredient, it is not executed but reports which one is missing – and the chain runs on, so that you see it whole and not only up to the first stumbling point. Only a run of the whole chain recolours the line view; “up to the selected step” is an intermediate state and shows only the messages.

A chain is saved as a plain properties file with the extension .kette: number of steps, for each step its key and its settings – no file name and no path. For a chain applies to a family of files, say all outputs of one computing program, not to the one file it was made on. An unknown step, for example from a newer version, is skipped on loading and reported instead of aborting the load.

Limits

  • The confirmation before replacing is tied to the target, not to the file's time stamp: whoever confirms it replaces the file as it is then. And the protection recognises the loaded file only as that file – a copy of it elsewhere is an ordinary target.
  • The cache recognises a changed file by size and time stamp; leaving both unchanged deceives it.
  • Text or binary is decided on the first 4096 bytes; a file that becomes binary only later counts as text.
  • The search runs only forwards, and only the hit jumped to is coloured.
  • The drawn pages and slides are evaluations, not complete renderings; what is missing is in the findings. PostScript is evaluated, not fully interpreted.
  • Text recognition reads one page at a time; the search does not find recognised text.
