envisionz-app-pdfdigitizer

Turning tables from PDF pages and scans into numbers

Overview of the app, as of 29 September 2026. The app reads tables from PDF files and scanned pages and writes them as CSV or into a database. It shows which cells were read with doubt instead of feigning certainty.

16source files in 3 packages
2detection paths for the grid: rules and white space
3independent confidence checks per cell
6tool cards in the bar
> 200checks in ten probes
9help pages, German and English

What the app is for

A lot of technical data exists only in print: performance tables in old manuals, measurement records as PDF, scanned data sheets. Retyping is tedious and error-prone. The app is the sister of the image digitizer but does something different: that one reads curves from plots with calibrated axes, this one reads cells from tables.

The path: open a PDF, detect the table grid, read the characters in the cells, check and correct the result, export. The checking step is the real core. With performance data a misread digit is more dangerous than an empty cell, and a recogniser that is wrong rarely says so itself.

What it can do

Load and view a page

The “Page” card opens PDF files, a card of its own PostScript and EPS. The working directory appears as a tree and is read only on request.

  • Scanned pages often consist of many narrow image strips. The app assembles them into one page image in the order of the page content.
  • Typeset pages without a raster image, or with visible text, show the text layer. Nothing is recognised there; the existing text is written out with “Save page text”. Rasterising it and recognising it again would only add errors.
  • The grid lies as an overlay on the unchanged image. When zooming, the pixels of the base image remain the coordinates for grid, cells and selection; only the display is redrawn finer for typeset pages and PostScript.
  • The “Password” card asks for the user password when a file requires one. The password is kept nowhere.

Detect the grid

The “Grid” card finds rows and columns. Given a selection in the image it works only there, because the blocks of a page look different.

  • Rules: projection of the ink onto straight lines, robust against a degree or two of skew. What counts is the longest contiguous dark run per row, not the sum: a line of text has many dark pixels but no long run, a rule few pixels but a very long run.
  • Rows between grouping rules: if a table draws a rule only every few rows, the app splits the bands into text rows by horizontal ink projection. The vertical rules are masked out while doing so.
  • White space: without drawn rules, free vertical gutters form the columns. What is counted is how many text rows have ink in a strip; a heading spanning several columns therefore does not clog a gutter. A word gap is narrower than the minimum gutter even when it lines up in every row.
  • Automatic: rules first, white space if no column or row is found. That also catches tables with a single rule at top and bottom. Both paths can be forced.

Learn the characters

The “Characters” card trains a recogniser on the typeface of the scan itself.

  • A manual is set in a typeface that resembles no system font. On a sample scan an untrained recogniser read nearly every 6 as an 8 while reporting 0 percent unsure; a network trained on system fonts scored 100 percent on its own training data and was no better.
  • The app collects all characters on the page and clusters them. Equal characters look nearly equal within one print, so about as many groups remain as there are character classes. One labels groups instead of thousands of single characters; each decision carries hundreds of samples.
  • Each group shows six examples and its spread. A large spread hints at two classes in one group. The card reports characters without examples, since a class without training data is never recognised. Rare classes are oversampled up to eightfold during training.
  • Model library: a folder of trained models is ranked by how well each fits the scan and pre-fills the labels. Nothing is ever chosen automatically: “very likely” appears only above 0.98 agreement, suggestions only from 0.80 per character, and a single unsuitable model can read a whole scan confidently wrong.

Read, check, correct

The “Read” card reads all cells and shows the table before anything is exported.

  • Three checks, independent of each other: the recogniser's own threshold (a “?” when unsure), the shape against the column type (an “8G.8” in a number column is suspicious) and the outlier along the column. Unsure cells are shaded.
  • Column types text, number and mixed (a number with a leading footnote marker such as “(1) 86.8”). The type can be changed per column, and the checks then run again without re-reading.
  • Gaps that narrow digits simulate in number columns (“31 .5”) are closed; in text columns they stay.
  • Cells are editable. A corrected cell no longer counts as unsure, because someone has looked at it.
  • Without a trained model the app asks first and quotes the measurement “6 read as 8”. Reading all pages into one file with the page number as first column requires a model; nobody checks every cell there.

Data and formats

  • Reading: PDF (also encrypted with a user password), PostScript and EPS. Raster images such as embedded image strips, fax-coded ones included, come through framework-pdf.
  • CSV: semicolon as separator, because the values carry decimal points. Three kinds: values only, unsure cells marked in the text, or a separate file with the marks. “Values only” discards which values were guessed and therefore warns when unsure cells exist.
  • Database (H2): with many pages the tables sit side by side and can be queried. Each value column gets a companion column …_UNSICHER (“unsure”); the value stays typed (number) and the information is kept. A column is typed as number only if every value converts; mixed columns stay text.
  • Models: .ennet, the model format of the framework module neural.

What it is built on

  • framework-pdf: PDF structure, image strips to pages, text layer, password, PostScript interpreter.
  • framework-neural: the character recogniser, its training and the model library.
  • framework-data: writing into the H2 database.
  • framework-swing: user interface, tool bar with cards, background runner.
  • framework-core and framework-api: registration as an app, saving of the state.

Grid detection, cell checking and clustering are code of the app itself. The layout follows the image digitizer: working directory, tool bar with cards, page view; each card is at most 360 pixels wide.

Status and limits

The whole path is built: page, grid (rules and white space), learning characters, reading with checking and correction, export as CSV or H2, multi-page export and password. On a sample scan, all numbers checked were correct after training on the typeface of the scan. Grid detection is tested on drawn tables with a known result; detection without rules has so far not been tried on a real scan.

None of the three checks catches systematic confusions: if every 6 is read as 8, the column stays uniform and nothing stands out. Only a model trained on that typeface helps. “0 percent unsure” therefore does not mean “0 percent wrong”. On scanned pages zooming does not sharpen the image, because an image in the file does not get sharper.
