envisionz-app-hello

The smallest complete app: a note pad as a template for new applications

Overview of the app, as of 29 September 2026. “Hello Note” is a note pad with a title and multi-line content. Its real purpose is to show how an app comes to life inside the framework.

3source files (HelloApp, HelloPanel, Msg)
1dependency: framework-api
2language bundles, German and English
49checks in 2 probes
6counter-tests in the note probe, all red

What the app is for

Anyone who wants to write a new application for the framework first needs an example that is complete and yet can be read in a quarter of an hour. That is app-hello: a note pad with a title field and a text field. It has no technical calculation and no data layer, but it has every element an app needs inside the framework – descriptor, view, saving and restoring state, and cleaning up on close.

The app has deliberately stayed small. It is meant to remain the simplest possible template: no Swing framework module, no data layer, only the framework’s interface.

What it can do

Create, write and keep a note

Creating a note opens a tab with a title and content. The tab title follows the title field with every keystroke; when empty it reads “Untitled”. When the workspace is saved, the app records title, content and the time of creation; when the workspace is opened, it restores all three.

What the template demonstrates

Every element of the app interface appears once, in the order of an app’s life cycle:

Registration and descriptor

  • a constructor without parameters, so the ServiceLoader can find the app
  • a descriptor with id, name, “New …” menu text, Fugue icon, file extensions (none here) and accelerator (ALT N)
  • an entry in META-INF/services/envisionz.api.App

View and state

  • createView returns the view; onShown puts the focus in the title field
  • captureState writes title, content and creation time into the tab state; the app id doubles as the tab type in the workspace file
  • restoreState reads them back and sets the tab title
  • dispose cleans up and writes a log line

Rules for anyone copying the template

Keep the parameterless constructor and the service entry. Keep the state in the view, not in the app class: the app class knows no Swing. If the view was never built, captureState returns nothing.

Bilingual from the start

All interface texts live in two language bundles (German, English) and are looked up through Msg. A missing key returns the key itself rather than an exception, so that a gap becomes visible and nothing crashes.

Data and formats

The app reads and writes no files of its own. Its only persistent data is the tab state inside the workspace file: title, content and creation time of each note.

What it builds on

  • framework-api – the interface between framework and application: App, AppView, AppContext and the tab state used for saving. It is the only dependency; an example without further modules is the stated goal.

The app is started by the multi launcher or by its own single launcher (see launchers). The single launcher also serves as an example of how one app becomes a standalone program, up to a GraalVM native image.

Status and limits

The app is complete and stable and has intentionally not grown. It is documented in its source; it has no help page because there is nothing to operate except a title and a text field.

For an example app the testing is unusually careful, because others copy from the template and an error here multiplies. The language probe (18 checks) compares both bundles directly from their files and finds missing keys as well as identical, that is untranslated, ones. The note probe (31 checks) runs registration, descriptor, saving, restoring and closing with a stand-in context, so that here too only framework-api is needed. The shared probes for controls and state come on top; both controls of the view can be addressed unambiguously.

Deliberately absent: file formats, technical calculation, data storage. Anyone who needs those will find them in the other applications.
