GIF — comparison against the 1989 specification and against Pillow

As of: 2026-09-06
Our implementation: envisionz.fileformats.gif.GifDatei with Giflzw, Gifbild, read-only, no third-party library
Specification: Graphics Interchange Format, Version 89a (CompuServe, 1990) — public; references give block names
Compared against: Pillow 12.2.0 (Python)
Test bench: envisionz.fileformats.gif.Gifprobe — 245 checks, nine foreign anchors, twelve counter-tests

The reference implementation. Pillow is the image library of the Python ecosystem: a thin Python layer over its own C code. It is the 2010 fork of the original Python Imaging Library by Fredrik Lundh (Secret Labs), started by Jeffrey "Alex" Clark and maintained today by the python-pillow team. Nearly everything that opens an image in Python — from matplotlib to Django's image fields — passes through it. It is therefore the most widely used implementation in its field, but the reference implementation of no format at all: it reimplements other people's formats. For this format it uses its own C code, no third-party library.

Why this one. Because GIF does have a proper specification (89a from CompuServe) but no living reference implementation: every implementation is a reimplementation. Pillow has its own C code for GIF, so it is a genuine second reader and not a second wrapper around the same code — which is exactly what makes the comparison meaningful. The LZW decoder and the interlacing can thus be held against an independent implementation rather than only against our own writer.

Feature comparison

GIF is the oldest format in this collection that is still produced daily — ratified in 1987, extended in 1989 with timing and transparency, unchanged since. It is also the first image in this series, which raises a question the other twenty-three did not: what a reader should deliver when the result is not a table.

What was measured

Eight foreign anchors, seven of them written by Pillow 12.2.0 and one built by hand. For an image format the measurement differs from a table format's: there are no "values" to compare one by one but tens of thousands of pixels. The measurement therefore has two stages.

First the sum, then the place

The colour sum over all pixels, computed by Pillow and recomputed by us, catches every colour error and every lost pixel — a wrong palette, a truncated stream, a forgotten row. It does not catch a permuted order: with interlaced rows they are the same pixels, only elsewhere, and the sum stays exactly equal.

The probe therefore additionally checks individual places — in a way that can be recomputed. All anchors are computed images: the colour index at (x, y) is a formula such as (x·7 + y·3) % 256, and the palette is ((i·7)%256, (i·13)%256, (i·29)%256). So nothing is checked against transcribed numbers but against a rule; the foreign anchors only supply the bytes it should come out of.

Three counter-tests that stayed green — and why that was a finding about the probe

A set of checks is worth something only once it goes red the moment one breaks the reader. Of ten interventions only seven went red at first. Three stayed green, and all three concerned the same thing: compositing several frames.

The cause was not the reader but the fixture. Pillow's animation folge has four frames that are all as large as the canvas and all at (0,0), all with the same control block. As long as that holds, it is entirely irrelevant whether a reader honours a frame's corner, knows the transparent index and assigns the control block to the right frame — the same thing comes out every time. Three real bugs would have gone unnoticed.

Pillow does not write such files readily: it decides at write time whether to store partial frames and whether to use transparency. So the eighth anchor was built by hand — five frames on a 24 × 24 canvas, four of them partial at four different corners, each a checkerboard with a transparent half, four different delays, and the fifth frame without a control block. The five sums still come from Pillow: it read the finished file. Since then all ten counter-tests are red.

What is hard about the format

The same LZW, packed two different ways. GIF and TIFF use the same algorithm, and a decoder for one is useless for the other: GIF packs its codes least significant bit first, TIFF most significant; and TIFF grows the code width one position earlier — the famous early change. Both differences sit in the same loop, and neither shows up at once. The wrong bit direction yields well-formed codes that mean nothing; the wrong growth rule yields an image that starts cleanly at the top and falls apart after a few hundred pixels.

Interlaced rows are the ideal silent error. If the bit is set, the rows come in four passes: every eighth from 0, then every eighth from 4, then every fourth from 2, then every second from 1. Take them in sequence and you get an image with the same pixels, the same colour sum and the same size — only striped. No exception, no message, and with a photograph it looks like a photograph at first glance. It is exactly the case for which a checksum does not suffice.

The code stream lies in sub-blocks, and the boundaries are not code boundaries. At most 255 bytes per block, each with a length byte in front. An LZW code may cross a block boundary. Decode the blocks separately and you lose a few bits at every boundary — the image is wrong from the first block end, that is after about 255 bytes, which for a small image never shows and for a large one shows at once.

A frame is not the image. Every GIF has at least one frame, and that one need not be as large as the canvas. In an animation the later ones are often only the changed region, to keep the file small, and a transparent index leaves what lies beneath. Whoever takes the first frame's indices for the image gets a fragment from every such file — and this trap kept three counter-tests green during this work, see section 2.2.

What is good: the block structure. Every block states its kind in one byte, every extension its length in sub-blocks. A reader that does not know an extension can skip it without knowing its layout — it only counts length bytes. That is why GIF could be extended in 1989 with timing and transparency without breaking the readers of 1987, and why our reader handles a GIF87a and a GIF89a with the same code. For a format of that age it is a remarkably forward-looking arrangement.

Our open gaps — this is the work

Deliberate decisions — nothing to do

I15 (decided) — No route through the general format detection

Datenquellen.oeffne rejects a GIF and points at GifDatei.lies — a good message, but a rejection nonetheless. The reason is honest: an image is not a table, and a Datenquelle is a table view. A view with one row per pixel (x, y, red, green, blue) would be possible; for an image of 4000 × 3000 that would be twelve million rows, and whether that is a good idea depends on what for. The same situation as VTK (V9) and HDF4 (H8), only for a more fundamental reason.

Decided by the owner on 2026-09-06. The item stood as a gap in five image formats with identical wording (BMP B1, GIF I15, PNG P1, TIFF T24, WebP W20). It is not one: a Datenquelle is a table view, and an image is not a table. A view with one row per pixel (x, y, red, green, blue) would be possible — at 4000x3000 that is twelve million rows, and what it would buy does not answer the question "what is in this file" but a different one. The readers exist and are named in the rejection message; that is the information the user needs. VTK (V9) and HDF4 (H8) are different: their content really is tabular, and there the view is being built.

I6 (decided) — An LZW decoder of our own

There is already one in the house: envisionz.pdf.PdfFilters reads PDF's and TIFF's. It is not usable here — different bit direction, different growth rule, different initial width; three differences in the same loop. A shared decoder with switches would be the tidier home, but it would have to touch framework-pdf, and that is an existing module. The GIF decoder therefore sits in Giflzw, with the cross-reference in the class comment. If the owner wants it, merging is a manageable step — and the right moment would be when TIFF (BF26) arrives and there are three callers.

I16 (decided) — Writing

Pillow writes GIF and supplied seven of the eight foreign anchors. This module reads. The eighth anchor was built by hand because Pillow would not write it (section 2.2) — that is test equipment, not an output path.

I13 (property) — Disposal method 3 — closed on 2026-09-06

Closed. "Restore to previous": before drawing, the frame's rectangle is copied and afterwards written back. Only the rectangle — everything beside it stays, even when the frame is smaller than the canvas.

The anchor is deliberately built so that one can see it. The third frame does not cover the whole canvas: if it did, the restore would be invisible and a counter-test omitting it would stay green. As it is, position (2,2) — which lay inside the green patch and lies outside the blue one — must be red again. Pillow reads red there too.

I5 (property) — Plain text blocks — closed on 2026-09-06

Closed as reading out, not as display. Block 0x01 has a fixed header of twelve bytes — corner, field size, cell size, foreground and background colour — followed by the text in sub-blocks. All of it is read and exposed through GifDatei.Klartext. Skip the header and its twelve bytes are read as text; that is what the counter-test hangs on.

It is not drawn, and that is a decision. The format says nothing about the typeface — not its name, not its shape — it only says how large a cell should be. Whoever paints letters from that invents them. Pillow does not read the block either; the difference is that here what is inside is stated.

Properties of the format

I1 (property) — Two versions, one reader

GIF87a and GIF89a differ only in which extension blocks may occur. Because every block knows its length, the same code reads both. The anchor alt87a is the same bytes as klein with a changed magic, and both must come out pixel-identical — they do.

I7 (property) — The code width grows differently from TIFF

See section 3. The anchor gross is just large enough for the dictionary to overflow repeatedly; the check runs across the whole image and expressly the last row, because with a too-early increase it is precisely the end that is wrong.

I8 (property) — The code that refers to itself

It arises when the same character occurs three times in a row — with a single-colour image, therefore, immediately. A decoder without that branch stops right at the start and delivers a handful of pixels instead of 4096. The anchor einfarbig checks exactly that.

I9 (property) — Sub-blocks are not code boundaries

See section 3.

I10 (property) — Interlaced rows

See section 3 — the ideal silent error, and the reason this probe does not stop at the colour sum. Pillow writes interlacing of its own accord above a certain image size; three of the eight anchors are therefore interlaced without having been asked for.

I11 (property) — A frame is not the image

See sections 3 and 2.2.

I12 (property) — The transparent index

It leaves what lies beneath — that is the whole basis for an animation storing only partial frames. See 2.2: without an anchor containing genuinely transparent pixels, the counter-test for it stayed green.

I3 (property) — A control block applies to exactly one frame

It stands before the frame it refers to and does not carry on. A reader that does not reset it gives a frame without its own control block the delay and transparent index of the previous one. The eighth anchor therefore expressly has a fifth frame without a control block.

Findings against the reference implementation

I2 (open there) — Six conditions without a statement about the file

A missing colour table, an unknown extension, an unknown block marker, a missing trailer, a frame reaching past the canvas, and a sub-block claiming more bytes than are there. We name all six in the findings, with the offset; Pillow reads on silently or throws a Python exception. That is not a bug in Pillow — it is an imaging library, not a file-inspection tool, and for its purpose reading on silently is the right choice. It is the difference between displaying an image and being able to say what is in the file.

I4 (open there) — Comment blocks are carried only partly

Pillow puts the first comment block into info["comment"]; several are not carried as a list. We collect all of them. The difference is small and rare in practice — it stands here because a file carrying its provenance in several comments is exactly the one where you want to read them. No bug in Pillow was found in this measurement.

I14 (open there) — A truncated stream

If the file ends in the middle of a frame we read as far as possible and report how many pixels are missing; the rest stays at the background value. Pillow in this case either delivers an image without a hint or throws, depending on where the truncation is. Both are defensible; the number of missing pixels is the piece of information a search starts with.

The Java implementation — where this reader stands among its own kind

Why against javax.imageio in particular. Every other comparison in this module measures against a tool in a different language — Pillow, astropy, pyarrow, meshio. That is good against misunderstandings of the format and says nothing about where this reader stands among its own kind. javax.imageio is the Java implementation it actually competes with in the field: it sits on every machine this module runs on, and it costs no foreign library — the module's rule stays untouched. It is measured on every run, not once: Bildvergleichsprobe, 80 checks now that JPEG is included. And the reader measured against here really is pure Java: com.sun.imageio.plugins.gif.GIFImageReader has not a single native method. Measured on 2026-09-06, because adding JPEG revealed that this does not hold there — the JDK's JPEG reader is a JNI wrapper around libjpeg 6b. For this format, then, the comparison really is one among its own kind.

8 anchors, all 8 pixel-identical. Interlacing, the old 87a version, comment blocks, an animation and one with sub-rectangles — no differing pixel against javax.imageio.

The comparison uses our canvas after the first frame and not the frame itself: for an animation ImageIO returns the first image on the canvas, and with a sub-rectangle those are two different things.

And a trap that is half the yield of the measurement. BufferedImage.getRGB() returns not the pixel from the file but its conversion to sRGB. For greyscale, ImageIO stores the values in a linear grey space and getRGB applies the sRGB curve on top: the raw value 0x25 becomes 0x6A — to three digits exactly (37/255)^(1/2.4) in sRGB encoding. The first run therefore reported differences on every greyscale image, in PNG and in BMP, that is on two independent readers of ours with the same symptom. It looked like a real bug and was none. The comparison goes through the raster. With TYPE_USHORT_GRAY the raster carries the raw 16-bit value while our punkte() is the view scaled to eight bits — whoever shifts there instead of rounding is off by one, and takes that for a bug too.
