PowerPoint .pptx — comparison against specification and python-pptx

As of: 2026-09-05
Our implementation: envisionz.fileformats.pptx.PptxQuelle, read-only, no third-party library
Specification: ECMA-376 (Office Open XML), part 1, PresentationML — public; references give part names and XML elements
Compared against: python-pptx 1.0.2
Test bench: envisionz.fileformats.pptx.Pptxprobe — 143 checks, one foreign anchor, thirteen own fixtures

The reference implementation. python-pptx is a pure Python library by Steve Canny. It is an independent reimplementation of Office Open XML — the format developed by Microsoft and standardised as ECMA-376 / ISO 29500 — with no Microsoft involvement. In the Python world it is the standard library for .pptx.

Why this one. Because Microsoft Office does not fit into a test bench as a reference, and python-pptx is the standard library in the Python world. The comparison has a peculiarity here: python-pptx also writes, so presentations can be produced that a second implementation considers correct, instead of only reading existing ones.

The purpose of this reader differs from every other format here: it is not about measurement data but about text from slides — what is in this presentation, in what order, on which slide. It is cut accordingly.

What was measured

The foreign anchor Pptxanker.zwoelf() — a presentation of twelve slides produced by PowerPoint — through both readers. Same slide numbers, same order, same texts. We additionally hand out three tables python-pptx does not have: a slide directory with part path, layout name, title, shape count, table count and character count per slide, plus the paragraphs and table cells as tables of their own.

The thirteen own fixtures from Pptxschreiber could not be cross-measured, and the reason is important enough to write down: python-pptx rejects them because the main part's content type in them is application/xml instead of the ECMA-376 presentation type. That is not a bug in python-pptx and not one in our reader either — it is a property of the fixtures: they are cut to what our reader is meant to check and do not bring the full container header.

The rows about broken relationships, missing parts and unreadable layouts in section 1 are therefore evidenced on one side only: measured on our reader, not on python-pptx. A tick in the comparison column would be a guess there, which is why it says no with item Y5 rather than a tick and a good feeling.

What is hard about the format

The slide order is stated in two places, and only one counts. presentation.xml lists identifiers; which part is behind them is stated only in ppt/_rels/presentation.xml.rels. The file names slide1.xml, slide2.xml, … do not say it — they are often in a different order, because PowerPoint keeps the names when reordering. Sorting by name yields a presentation with the same slides in the wrong order.

A paragraph falls apart into runs. "Point A of 11" may appear as four runs because one word is bold and another is not. Handing out the runs individually yields text fragments; joining them requires knowing where a paragraph ends.

What the reader sees is not what the viewer sees. A placeholder empty on the slide shows the layout's text. A text box may sit behind an image. And a field (a:fld) carries a cached value that may differ from what PowerPoint computes on opening. For a full-text search across slides that is the difference between a hit and a miss.

What is good: as with .xlsx — ZIP and XML. A .pptx can be unpacked and read with the naked eye.

Our open gaps — this is the work

Deliberate decisions — nothing to do

Y2 (decided) — Runs are joined

A paragraph comes out as one text, not as its runs. The formatting is lost — it is the reason runs exist — but for a search across slide texts a paragraph is the unit one searches for. python-pptx offers both; we chose.

Y3 (decided) — The cached field value

An a:fld carries the value PowerPoint last computed. We hand it out and compute nothing — the same decision as with the Excel formulas and the MDF conversions: a cached value comes from the producer, a self-computed one from us.

Y9 (decided) — Writing

python-pptx writes and is built for it. This module reads.

Properties of the format

Y5 (property) — The cross-measurement — closed on 2026-09-07

The gap was not in the reader but in the evidence: four rows of the table concern broken containers, and the own fixtures were not presentations to python-pptx at all. Now Pptxschreiber writes five fixtures with a complete container — [Content_Types].xml with all overrides, master, layout, theme — and python-pptx opens them. They are intact except at exactly one place; only so can the other side's answer to that one place be obtained.

What came out. (1) A relationship that does not exist: python-pptx raises KeyError: no relationship with key 'rId9' on open — the whole file is lost, but the message names the relationship. (2) A part not in the container: KeyError: no relationship with key 'rId1' — and rId1 is in the relationship file. It reports the relationship it discarded itself rather than the missing part; following the message searches in the wrong place. (3) An unreadable layout: XMLSyntaxError on open — a single broken layout costs the whole presentation, although no slide content lives in a layout. (4) An unreadable indentation: the file opens, the first two paragraphs arrive, then a ValueError in the middle of iterating — the most unpleasant of the four answers, because it comes after the data.

And the cross-measurement found a defect of ours right away. In cases 1 and 2 we raised "PPTX: keine einzige Folie war lesbar" — which said that nothing was readable, not why. The reasons were already in the findings at that point; they were simply lost with the exception, because afterwards nobody holds a source to query them. For a file with a single slide our message was thus the worse of the two. Now the exception carries the findings along.

Y6 (property) — Notes slides and masters — closed on 2026-09-07

The text of the notes slides was already read; the earlier text of this item was outdated in that respect. New is the master and the layout: their text now stands in a table of its own, vorlagen, with kind, part path, name, placeholder, paragraph, level and text.

A table of its own, because both are true. A layout contains "Click to edit Master title style". Whoever counts that as slide text turns every presentation into a document full of prompts — the test explicitly checks that no slide text contains that string. Whoever leaves it out loses, for a slide with an empty placeholder, exactly the information about what stands there in the talk. So: kept separate and assigned by name (item Y7).

Measured in passing: the master of the anchor presentation carries no name. Instead of an empty field its part path stands there — a name that does not exist would be worse than a path.

Y7 (property) — Placeholder text from the layout — closed on 2026-09-07

The new table platzhalter carries, per slide, every placeholder — including the empty one — with four pieces of information: whether the slide fills it, what stands on the slide, what the template provides in its place, and where that template text comes from: layout or master.

The empty placeholder is the whole point. The paragraph list carries only paragraphs with text; an empty placeholder does not appear in it. A slide whose title someone did not fill in therefore looks, in a text output, like a slide without a title — and in the talk it is one with the prompt on it.

Measured, not assumed: python-pptx shows both sides — slide.shapes with empty text and slide_layout.placeholders with the template text — but it does not connect them. Whoever wants the association makes it himself, via placeholder_format.idx. That is why the row stands at yes/partial and not yes/yes.

Y8 (property) — Everything that is not text — closed on 2026-09-07

Three tables for three different questions. formen says what lies where: kind (text, image, chart, table, SmartArt, shape), position, size and rotation in EMU, the placeholder, the size of an embedded image — and where the position comes from: the slide, the layout, the master, or nowhere. It comes from Folienplan, which already reads it together with the placeholder inheritance; a second reader beside it would be a second truth. laeufe says how the text looks: font, size, bold, italic, underline, colour. bewegung says what moves: transition and timing per slide.

Three places where a reader goes quietly wrong. (1) The font size is in hundredths of a point: sz="1800" is eighteen. Taking the number as it stands builds a font of 1800 points — and in a table a number looks like a number. (2) A theme name is not a colour. <a:schemeClr val="tx1"/> means: look up in the master's colour map what tx1 means, and fetch that colour from the theme — two steps, and both can lead nowhere. (3) The transition's name is in the child, not on the element: <p:transition><p:fade/></p:transition>. Searching p:transition for a name finds none and reports "no transition".

Where we go further than the reference: for a theme colour python-pptx yields the name (ACCENT_1) and leaves the lookup to the caller; we take the two steps and name both — the colour 4472C4 and its origin Thema accent1. Everything else about the formatting matches python-pptx character for character, measured on the same file.

What explicitly is not there: the shape geometry of a:prstGeom — nearly two hundred predefined shapes, each a parametric path — and the line breaking. The break is not in the file; it depends on box width, font metrics, insets and normAutofit. Neither is negligence but a named limit, and Folienplan reports it for every shape carrying text.

Y10 (property) — The preview image — the only real picture of the slide

A PPTX almost always carries docProps/thumbnail.jpeg: the picture the producer made of the first slide when it last saved. It is the only image in the whole file that shows a slide as it looks — with theme colours, fonts and shape geometry. This workspace's layout plan, by contrast, says where things are; that is a different statement. Since 2026-09-07 the preview is shown, and shown first in the slide list.

Three things go with it, and they stand on the view and not only here. First: the producer rendered it, not this reader. Second: it is almost always the first slide only. Third — and this is the dangerous one — it is as old as the last save. Change a PPTX with a tool that does not refresh the preview and you have a file whose picture shows a different state than its content. Showing such an image without comment would be worse than showing none.

Which image format is actually inside is decided by the first bytes, not by the extension: Bilder.ausBytes asks Formaterkennung.erkenne(byte[]). That is not a precautionary ritual — PowerPoint writes thumbnail.jpeg, LibreOffice thumbnail.png, and the relationship type names no extension at all. The probe therefore deliberately stores a PNG under the name thumbnail.jpeg and demands that PNG be reported.

Why the reference column says no: python-pptx maps the package through its relationships and knows the part, but does not hand it out as an image — it has no image reader at all. That is not a weakness but a different scope; it is mentioned because the column would otherwise read as an omission.

Y1 (property) — The order lives in the relationships

See section 3. Both implementations take the route via presentation.xml and the .rels; we additionally hand out the slide order as a table of its own, with the part path alongside — so one can see that slide7.xml is in third place and does not take it for a reading error.

The Java implementation — where this reader stands among its own kind

Why this section. Every other comparison in this module measures against a tool in a different language. That is good against misunderstandings of the format and says nothing about where this reader stands among its own kind. What matters is the distinction between a pure reimplementation in Java and a wrapper around a C library: only the reimplementation solves the same task under the same conditions.

A pure Java reimplementation exists: Apache POI, module XSLF, in the same poi-ooxml jar as XSSF and with the same dependencies. No JNI. Not measured — the same situation as with XLSX. No serious alternative to POI is known for PPTX.

On scope: POI reads a presentation completely, with shapes, formatting and images; this reader reads the text. That is item Y8, and in comparison with POI it becomes what it is — not an oversight but a different task.
