Apache Arrow IPC — comparison against specification and pyarrow

As of: 2026-09-06
Our implementation: envisionz.fileformats.arrow.ArrowQuelle with Arrowtyp and Flach — including an own FlatBuffers reader, read-only
Specification: Apache Arrow Columnar Format and IPC File Format, public; references give FlatBuffers structures
Compared against: pyarrow 25.0.1
Test bench: envisionz.fileformats.arrow.Arrowprobe — 147 checks, fourteen foreign anchors, ten own fixtures

The reference implementation. pyarrow is the official Python implementation of Apache Arrow, maintained by the Apache Software Foundation. Arrow was announced in 2016 out of a coalition of several analytics projects — the initial code came from Apache Drill, with Wes McKinney prominently involved. It is therefore the reference implementation of the format and, through pandas, Dask and Spark, also its most widely used reader.

Why this one. Because pyarrow is the official implementation of the format. A difference is therefore ours. The comparison has a second task here: Arrow describes its buffers via FlatBuffers, and a reader that counts buffers per field tree differently delivers plausible wrong data — which only shows up against the official implementation.

What was measured

Eighteen fixtures — eight foreign anchors from Arrowanker (produced by pyarrow) and ten deliberately damaged ones from Arrowschreiber — through both readers. Seven of the eight anchors agree completely: all integer widths at their limits, date and timestamp, mixed types, nulls, two record batches and a list.

The eighth diverges, and that is a gap of ours: gepackt.arrow carries a zstd-compressed record batch. pyarrow reads it; we report "a record batch is compressed (method 1 — 0 means LZ4, 1 means zstd); this reader does not decompress it and skips it" and return zero rows.

That gap became cheap on 2026-09-05. On the same day, BF34 and BF33 produced an LZ4 and a zstd reader in framework-compress — exactly the two methods Arrow uses here. Only the wiring is missing. See A12.

Among the ten damaged fixtures both readers reject nine. On the tenth — ohneAnfangskennung, a file without the leading ARROW1 magic — pyarrow reads it completely anyway, because it starts from the end of the file. We reject it. Both are defensible; whoever wants to rescue a truncated file is better served by pyarrow, whoever wants to know whether a file is intact by us.

What is hard about the format

The number of buffers is not in the message but in the field tree. A record batch enumerates its buffers, but which belongs to which column follows only from how many buffers each type needs: an integer column two (validity and values), a string column three (validity, offsets, bytes), a list likewise three plus those of its child. Walking the field tree in a different order than the writer accesses valid buffers of the wrong column.

Booleans and validity are bit fields, not byte fields. Eight rows in one byte, least significant bit first. Reading them byte-wise yields one value for the first eight rows and zeros for the rest — and the first eight look right.

The offset buffer has one entry more than the column has rows. With n rows there are n+1 offsets, because the end of the last string has to be recorded somewhere. Reading n loses the last row; taking n+1 as the row count invents one.

What is good: Arrow describes itself completely, and in a language (FlatBuffers) one can read without a code generator — the vtable is in the message. The reader here therefore brings its own FlatBuffers reader, in about two hundred lines.

Properties of the format

A12 (property) — Compressed record batches — closed on 2026-09-06

Closed. BodyCompression allows LZ4 frame and zstd; both are decompressed, via envisionz.compress.lz4.Lz4 (BF34) and envisionz.compress.zstd.Zstd (BF33). What matters about the format: the body is not compressed as a whole, each buffer is compressed on its own, preceded by eight bytes of uncompressed length. The offsets in the FlatBuffer point at the compressed layout, so a new body is built and the offsets are rewritten.

How it was accepted. Not by numbers coming out — wrong ones would too. Arrowanker.gepackt() (zstd) and Arrowanker.gepacktLz4() (LZ4, produced with pyarrow 25.0.1 on 2026-09-06) carry the same content as the uncompressed anchor gemischt(); the probe compares column by column against it. Two mutations go red: not skipping the eight length bytes (eleven failures) and not rewriting the offsets (eight).

One residue remains, and it is named: a buffer may carry the length -1 — "this one is not compressed". The branch is built but not measured: pyarrow 25.0.1 never writes it, not even for a one-byte value or for random bytes. That mutation stays green and is therefore not counted — the same situation as the body alignment, and it is documented at the spot in the source.

A7 (property) — The stream format — closed on 2026-09-06

Closed. Arrow exists as a file with a footer and as a stream without one. The stream is now read: recognised by the continuation marker 0xFFFFFFFF at the start instead of by a signature, then message after message — schema, dictionaries, record batches — until a length of zero says it is over. A file that begins with ARROW1 and does not end with it is read the same way and the case is named; before it was rejected.

What is worth knowing: one has to move from length to length, and every figure comes from the file itself. A length that no longer fits ends the reading with a finding — truncation is stated, not guessed. Detection checks three things, not one: the marker, a schema length divisible by eight, and a root offset pointing into the schema. With the marker alone, every file starting with four FF bytes would be an Arrow stream.

A8 (property) — The four smaller types — closed on 2026-09-06

Closed. Half precision (IEEE binary16, subnormals included), time of day in four units, duration and interval. LargeUtf8/LargeBinary were already there. A duration stays a number in its unit, with the unit in the field description — converted, −2500 milliseconds would have become −2 seconds, and rounding is not visible in a number. An interval becomes text in ISO 8601 notation, because a month has no fixed length in days.

And in doing so a real bug was found in code that had stood for months. The default of the time unit is MILLISECOND in the format, not SECOND or DAY. A FlatBuffer omits every field whose value equals the default — so for a date64 the unit is missing entirely. Assume days, and 2026-09-06 becomes the year 5331045, and since a date64 takes eight bytes and a date32 four, every row after it is displaced too. Both look like dates. The anchor vorgabewerte holds the case.

A9 (property) — Decimals — closed on 2026-09-06

Closed. Decimal128 and Decimal256, with precision and scale from the type. What comes out is text, not a floating-point number: a decimal is exact, a double is not — and with monetary amounts in particular nobody notices the difference until it counts. The number is little-endian two's complement; it is reversed and turned into its digits via BigInteger/BigDecimal.

A10 (property) — Nested types — closed on 2026-09-06

Closed. List, large list, fixed-size list, struct, map and union — dense as well as sparse. They come out as text: [1, 2, 3], {a=1, b=x}, {k1=1, k2=2}. That is a presentation, not an interpretation, and it is more honest than the alternatives: for a table view a list is not a cell, and whoever gives out the first value or the length instead delivers a number that looks like a value. Nesting is shown nested.

Two traps in the union, both measured. Since format version 5 it carries no validity buffer — look for one and the type ids are read as a bitmap, turning 07 09 into "the first three rows are valid, the next are not". And the type ids are freely chosen: the anchor auswahl uses 7 and 9 instead of 0 and 1, because equating them with the child's index reads correctly every file whose writer started at zero, and the next one wrongly.

A11 (property) — Dictionary-encoded columns — closed on 2026-09-06

Closed. The dictionaries sit in their own messages before the record batches; the record batch holds only indices. They are read first and resolved on access, deltas (isDelta) appended rather than replacing. Two things are worth knowing: the column's type describes the values, not the indices — and a dictionary-encoded column therefore occupies two buffers, not three, even when its values are strings. Count three and everything after it is misassigned.

The anchor woerterbuch deliberately uses eight-bit indices in one column and thirty-two in the other: with a single width a counter-test that hard-wires the width would stay green.

A1 (property) — FlatBuffers without a code generator

The metadata is a FlatBuffer: a root offset, a vtable per object, fields as offsets within it. Absent fields appear as zero in the vtable and mean "default" — not "null". Missing that distinction reads the number 0 as a value for every unset field. Both implementations get it right; we with an own reader, pyarrow with generated code.

A2 (property) — Two ways of writing the message length

Since Arrow 0.15 the marker 0xFFFFFFFF precedes every message length; before that the length stood alone. Both occur. We read both and report the older one ("this is the older form and is read"), so that it is clear what one is dealing with.

A3 (property) — Bit fields

See section 3. The anchor mitNullen measures it with a column in which three of five values are missing — with eight rows the boundary would fall exactly on the byte boundary and an error would not show.

A4 (property) — The offset buffer with n+1 entries

See section 3.

A5 (property) — Buffers belong to the field tree, not the column

See section 3. Our reader checks the buffer count against the schema and reports a mismatch ("a record batch names N buffers, the schema needs M; reading follows the schema") — the only place where an ordering error can be noticed at all.

Findings against the reference implementation

A6 (open there) — Four conditions without a message

An unknown metadata version, a block pointing nowhere, a block that is not a record message, and a buffer count that does not match the schema. We name all four; pyarrow aborts on the middle two with a FlatBuffers message that does not name the place, and reads on for the outer two.

The Java implementation — where this reader stands among its own kind

Why this section. Every other comparison in this module measures against a tool in a different language. That is good against misunderstandings of the format and says nothing about where this reader stands among its own kind. What matters is the distinction between a pure reimplementation in Java and a wrapper around a C library: only the reimplementation solves the same task under the same conditions.

A pure Java reimplementation exists: apache/arrow-java, module arrow-vector, with ArrowFileReader and ArrowStreamReader. The project's JNI parts (arrow-dataset, arrow-gandiva, arrow-c-data) are separate modules and not needed for the IPC format. Not measured — the default memory management arrow-memory-netty pulls in Netty, and Arrow requires JVM flags such as --add-opens; a measurement would mean several jars and a launch line of its own.

That is not an aside but the difference in scope: this reader gets by with the JDK and reads the same files. The counter-argument is just as honest — Arrow-Java covers far more than what is read here.
