STL — comparison against specification and meshio

As of: 2026-09-05
Our implementation: envisionz.fileformats.stl.StlQuelle, read-only, no third-party library
Specification: The STL description is public domain and one page long; references give byte ranges and keywords
Compared against: meshio 5.3.5 (Python)
Test bench: envisionz.fileformats.Stlprobe — 25 checks

The reference implementation. meshio is a pure Python library by Nico Schloemer, essentially a single-developer project with community contributions. It reads and writes over thirty mesh formats and is therefore the reference implementation of none of them — it is the common denominator. In the scientific Python world it is the usual tool for converting between mesh formats.

Why this one. Because STL is so simple that it needs no reference implementation — and that is exactly the trap: the text form has no magic number, and the binary form begins with 80 arbitrary bytes. A second reader on the same files is therefore worth more than any specification. meshio is the most widespread one.

Feature comparison

STL is the simplest format in this collection: a list of triangles with a normal, and nothing else. No node numbers, no edges, no colours, no units — the same corner appears in the file as often as triangles touch it.

What was measured

Two fixtures, produced by meshio: the same mesh of two triangles, once binary and once as ASCII. Both read by envisionz.fileformats.stl.StlQuelle. Equal — two triangles, the same normals, the same twelve coordinates, the same attribute field.

The shapes differ: meshio returns four points and two triangles, we return two rows of thirteen columns — normal, three corners, attribute. Both are correct and describe the same file; meshio merges the duplicated corners into points, we do not. See T6.

meshio's binary fixture header begins with This file wa… — that is, not with solid. The difficult case, a binary file with solid in the header, is therefore not measured here but covered by our own probe (Stlprobe, item BF3). This is stated because otherwise a row in the table would look better evidenced than it is.

What is hard about the format

The form is stated nowhere. An ASCII file starts with solid; a binary file has eighty bytes of header into which the writer may put whatever it likes — and many binary writers put solid there too, having taken the word from the ASCII form. Deciding by the word reads a binary file as ASCII and finds zero triangles.

The way out is computing instead of guessing: a binary STL has exactly 84 + 50 × n bytes, and n is in bytes 80 to 83. If both agree, it is binary — regardless of what stands in the header. That is a check that cannot err, and it costs four bytes.

The normal is usually wrong. It is in the file but is set to 0 0 0 by many writers, and where it is present it sometimes contradicts the right-hand rule of the vertex order. A reader that passes it through does the right thing; one that corrects it has already made a decision.

What is good: there is nothing to understand. Fifty bytes, twelve floats and two bytes of remainder. No format in this collection can be read completely in fewer lines.

The items

The Note column names the kind in front of the identifier. Only the gaps are work.

Our open gaps — this is the work

T6 (decided) — Corners are not merged into points

A cube has eight corners and twelve triangles; an STL contains thirty-six corners. meshio merges them and yields eight points; we yield the thirty-six as they stand.

Merging means rounding. Two corners are the same point if their coordinates agree — but in an STL they are 32-bit floats, and two triangles touching the same corner do not always have exactly the same bits there. Merging requires a tolerance; and a tolerance is a decision about the geometry, not about the format. It belongs one layer up.

T3 (decided) — The normal is passed through

See section 3. We hand it out as it stands — including 0 0 0. Whoever needs it can compute it from the corners and then knows that they did.

T7 (decided) — Writing

meshio writes. This module reads.

Properties of the format

T5 (property) — Several solid blocks — closed on 2026-09-06, and the item was wrong

The item claimed something false about us. It said: "we read the first block and hand out one table." Measured against a file with two blocks of one and two triangles: all three come out. The ASCII reader runs over the whole file and collects every facet regardless of which solid it sits in — it never dropped anything. Whoever writes down an item without measuring it sometimes writes down a gap that does not exist; that is the harmless case, but it costs the same attention as a real one.

The real gap was a different one and is closed: what was lost is the separation. An assembly of three parts was indistinguishable from a single part. The table now carries a fourteenth column block with the name of the solid the triangle came from, and with more than one block a finding says so. The binary form has no blocks — there the header text stands. The column is appended at the end so that every access by column number stays where it was.

The comparison therefore reverses: meshio merges all blocks and loses their separation — exactly what we did before and no longer do. The row therefore reads yes/partial rather than partial/yes.

Two mutations go red: not carrying the block name (three failures) and not reporting the blocks (two). A file with one block deliberately reports nothing — otherwise every ordinary STL would carry a line that says nothing.

T1 (property) — The form is computed

See section 3. We compute 84 + 50 × n against the file size; meshio checks whether the header starts with solid and falls back to the size computation on mismatch. Both get there with ordinary files; with a binary file carrying solid in the header, the size route is the safer one.

T2 (property) — The two bytes nobody uses

Every binary triangle ends with two bytes of "attribute byte count". The description says it is zero; some tools store a colour there, in two mutually incompatible encodings. We hand out the two bytes as a column and do not interpret them — what is in there is known only to whoever knows the writer.

T4 (property) — Eighty bytes in which anything may stand

The binary header often carries the tool's name, sometimes units, sometimes nothing. We carry it; meshio discards it. When asking which program a foreign STL came from, it is the only answer the file gives.

The Java implementation — where this reader stands among its own kind

Why this section. Every other comparison in this module measures against a tool in a different language. That is good against misunderstandings of the format and says nothing about where this reader stands among its own kind. What matters is the distinction between a pure reimplementation in Java and a wrapper around a C library: only the reimplementation solves the same task under the same conditions.

Several pure Java implementations exist — the format is simple enough: DrPlantabyte/STL-Parser-for-Java, the older org.j3d.loaders.stl.STLFileReader and a parser generated from a Kaitai Struct description. None of them is a maintained Maven artefact; currency is moderate. Not measured.

With a format this simple the interesting question is not whether somebody reads the triangles but what they do with the edge cases — with several solid blocks (item T5), with an ASCII file of binary size, and with the two bytes nobody uses. That is exactly where implementations differ, and exactly where this document is written.
