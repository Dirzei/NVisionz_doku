Understanding unknown text formats – background

How Strukturleser recovers the writing routine from a text file without a description: character set and round trip, line signatures, column grid, block kinds, count fields, wrapped records and the rule tree that covers the whole file.

The problem: the trace of a small program

A numeric file from a simulation program is not free text. It is the output of a short write loop, typically

WRITE(u,*) n
DO i = 1, n
   WRITE(u,'(5F10.4)') (x(i,j), j=1,5)
END DO

The program has a few lines, the file millions. Inferring a short grammar from a long trace is something other than “understanding text” and orders of magnitude simpler, because the grammar is small. The method works in layers; each answers one question and hands a result to the next: bytes become lines (layer 0), lines become signatures (1), signature sequences become blocks, count fields and wraps (2), names follow (3), and the acceptance test is the round trip (4).

Layer 0: character set, byte order mark, line ends

First the reader determines what is there at all, in a way that turns the lines back into the same bytes. Adding the round trip only at the end means discovering that the needed facts were lost on input.

  • Byte order mark. EF BB BF is UTF-8, FF FE UTF-16 little endian, FE FF big endian. The mark is removed and obeyed: it states the character set. Read as UTF-8 instead, ASCII in UTF-16 is valid UTF-8 with a zero byte after every character; every line from the second on then starts with a NUL, and no signature is right.
  • Character set. Without a mark, UTF-8 first, checked strictly. If that fails, ISO-8859-1: every one of the 256 byte values is a character there, no byte is lost and the round trip stays possible. Windows-1252 would look more correct and is not – five byte values are unassigned there.
  • Line ends per line. The separator (LF, CRLF, CR or none at the end) is kept per line, not as a property of the file. Only then does a file with mixed ends survive the way there and back, and that very case reveals a file assembled from parts.

Each line's byte range is computed from the character set: “ß” takes two bytes in UTF-8, every basic-plane character two in UTF-16. Counting characters instead of bytes gives ranges that are off only for files with umlauts.

Layer 1: the line signature

Each line is replaced by its shape: one character per token. Z integer, R decimal, E number with exponent, W word, T quoted string, = assignment, , separator, ( ) brackets, ? other character; _ stands for an empty line, # for a comment. A file of hundreds of megabytes becomes a sequence over about twenty symbols in which typically five to twenty distinct signatures occur.

Why Z, R and E stay apart. A Fortran FORMAT statement makes exactly this distinction, and count fields are always integers. Throwing all numbers into one symbol loses the most common blueprint (“write n, then n records”). The sign, on the other hand, belongs to the data, not to the shape.

The number rules of Fortran output. Three notations are valid Fortran output and no number for an ordinary number parser:

  • 1.2340D+05: D as the exponent letter of double precision.
  • 1.2345-100: with a three-digit exponent there is no room for the E in the field Ew.d, and the standard drops it. The digit count decides: exactly three means exponent, fewer means the next number starts there (1.0-20 is two numbers, -1.0-2.0-3.0 three).
  • E output always writes a decimal point. A sign with three digits after an integer is therefore no swallowed exponent: 5-100 from 2I4 is the numbers 5 and −100, not 5·10−100.

Formally: a number has the shape [±] digits [. digits] [(E|D)[±]digits]; if a mantissa with a point is immediately followed by ±ddd with exactly three digits, that belongs to the number as its exponent.

Strings and comments. Inside quotes a doubled character counts as one in the text (the same rule as RFC 4180); an unclosed string ends at the end of the line instead of discarding it. A comment character is not universal – #, !, C in column 1, *, // – so the prefixes are given and none is assumed. Without them no line is a comment; the signature list then shows which character is a candidate.

The column grid: measured over all lines

Whether a file is in fixed columns cannot be seen from one line: a negative number takes one more place, a three-digit exponent too. So it is measured over all lines of a block. The tokens of all lines are merged into column ranges – two tokens belong to the same column when their spans overlap; that brings the left-aligned heading NLRT at 2..6 and the right-aligned number 0.8000 at 2..8 together. A block has a grid if

  1. every token of every line falls into exactly one range and no range is used twice in a line, and
  2. a line missing ranges has gaps only inside. A hole between filled cells is an empty cell – evidence for a table. A line that simply stops early is the short last line of a wrapped record and occupies nothing.

A grid from one line would be the single measurement dressed up as statistics; at least two are required. If the columns disagree there is no grid – an “approximate” one would look like a measurement and be an estimate.

Three block kinds, named rather than guessed

Engineering code writes tables in three ways. The decision rests only on the ratio of words to numbers per column over the whole block and on the line immediately before it:

KindLayoutRecognition rule
Cross tablehead xname yname y₁ … yₙ, below xᵢ fᵢ₁ … fᵢₙhead: w ≥ 1 words, then z ≥ 1 numbers, and z = s − 1 (s columns per line)
Header and recordname₁ … nameₛ / value₁ … valueₛhead: exactly s words, no number
Row seriesper line nameᵢ value₁ … valueₙcolumn 1 always a word, all others always numbers

All lines must have the same number of tokens; if no kind fits, the block stays unnamed. An unnamed block is information, a wrong name would be a claim.

Layer 2: the count field – the loop read backwards

Every integer g ≥ 1 in a line before a block of L lines with m values each is tested against four claims:

  1. g = L: “g lines follow”;
  2. g = L·m: “g values follow” (the wrapped record);
  3. with several integers g₁…gₖ: P = ∏gᵢ = L or P = L·m (the structured grid nx ny nz);
  4. L·m = k·P with 2 ≤ k ≤ 8: P records of k values each.

The fourth form is the most frequent in practice: PLOT3D writes nx ny nz and then three coordinates per point, a Q file five quantities. The head number counts points, not values. The bound k ≤ 8 is deliberate: allow enough multiples and some number always fits. An exact match (1 before 2) beats a derived one: “four lines” says more than “four pairs”. The claim is falsifiable and costs one pass; if it holds, the loop has been found. The finding carries a blueprint with placeholders (#1*#2*3) into which a draft later inserts names.

The wrapped record and carriage control

WRITE(u,'(5E15.7)') (a(i),i=1,17) gives three lines of five and one of two. In the head of a file the line means everything, in the numeric part nothing – there the line break is layout, and the file is a stream of tokens. The tell-tale sign: in a stretch of purely numeric lines nearly all lines carry v values, and at a regular distance a there is a shorter one with r < v values, the last at the end of the stretch. A record then has (a − 1)·v + r values; a is the number of lines per record.

Carriage control is not a guess. Formatted Fortran output reserves column 1 for the printer: blank one line on, 0 a blank line before, 1 new page, + overprint. If at least 20 non-empty lines carry these characters in column 1 at a rate of at least 95 %, the file counts as a print file, and the 0 and 1 mark record starts. That holds even where each record begins with a name and the search for purely numeric lines misses it. Equal distances and equal shape of consecutive records are still required.

The rule tree: every byte belongs to exactly one leaf

The findings overlap; they are combined by strength: count field with block, wrapped record, block, and last the header line as a guess. The leaves of the tree tile the byte range [0, size) without gaps or overlaps; what no rule claims becomes an UNBEKANNT (unknown) leaf and is not left out. Coverage is thus not an estimate but a sum, and every view – colouring, outline, format description, skeleton, round trip – is only a rendering of the same tree.

Two files from the same writer

For one file there are always several grammars that produce it. With two files the question nearly answers itself: literally equal lines were written by the routine (skeleton), equal signature with different text is data, a different signature is the interesting rest. Line n is compared with line n, without alignment; two outputs of the same routine differ in their numbers, not in their order, and an alignment would invent matches.

What follows

  • The assumption of the whole method is that a loop did the writing. For nested, self-describing texts (HTML, XML, JSON) the line signature carries no signal; a dedicated reader is the right tool there.
  • All findings are hypotheses with evidence, not certainties. Whether six numbers per line are six columns or two triples no file says; the finding reads “structure recognised, meaning unknown”.
  • Because layer 0 writes back byte-identically, every later layer can be measured by the round trip – the round trip is a locating test (see format description and matching).

How it is tested

Textstrukturprobe (layers 0–4, seven line-end cases, three Fortran traps), Blockartprobe, Kettenprobe, Baumbauprobe and TheorieFBprobe in package text (ids [TD22-FB-T1] to [TD22-FB-T13]): each rule on this page with a case that separates it, among them 5-100 as two integers, a cross table with an empty column, the bound k ≤ 8, the thresholds of 20 lines and 95 %, a UTF-16 file with a mark and the gap-free tiling of the rule tree. Counter-probes td22fb-*.

Limits

  • UTF-16 is recognised only with a mark; without one a UTF-16 file reads as UTF-8 with zero bytes, and the zero bytes appear in the finding.
  • Comments without a leading character are not recognised, only reported as unassigned.
  • Two files are compared line by line; if a loop runs a different number of times, only the common beginning is reliable from there on.
  • Repeat counts of Fortran list-directed input (4*1.5) are not expanded; they appear as number, star, number.
