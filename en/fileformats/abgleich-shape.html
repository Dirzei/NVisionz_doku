ESRI Shapefile — comparison against specification, pyshp and shapely

As of: 2026-09-26
Our implementation: envisionz.fileformats.shape.ShapeQuelle, read-only, no third-party library
Specification: ESRI Shapefile Technical Description (July 1998); references give byte offsets and shape types
Compared against: pyshp 3.1.6 and shapely 2.1.2 (Python)
Test bench: envisionz.fileformats.shape.Shapeprobe — 73 checks; Bezugssystemprobe — 76 checks against pyproj/PROJ (SH3)

The reference implementation. pyshp is a pure Python library started by Joel Lawhead, for years the usual tool for reading and writing shapefiles without GDAL. shapely is the Python binding to GEOS, the geometry library behind PostGIS and QGIS.

Why this one. pyshp writes the fixtures; the expected text of the shapes comes from shapely, translating pyshp's GeoJSON view into WKT. So neither the file nor the expected value comes from this reader. GDAL was not available.

Feature comparison

A shapefile set is three to five files sharing a stem: the shapes (.shp), their index (.shx), their attributes (.dbf), often also the encoding (.cpg) and the projection (.prj). The occasion was item SK18: until 2026-09-25 only the .dbf was read.

What was measured

Seven sets, written by pyshp (docs/shape/erzeuge.py): points with a null shape and UTF-8 attributes, single- and two-part lines, polygons with a hole and with a hole placed after a foreign outer ring, a multipoint, PointZ with and without M, PolyLineM and a multipatch. The pyshp and shapely output is in docs/shape/auskunft.txt verbatim. Equal for every shape shapely can represent. Z, M and multipatch cannot reach shapely through pyshp's GeoJSON; there the numbers come from pyshp and the notation follows ISO 19125.

What is hard about the format

Two byte orders in one file. Code, file length, record number and record length are big endian, everything else little endian — and the lengths count 16-bit words, not bytes.

A polygon is a list of rings, not of polygons. Which rings belong together is told only by orientation (outer clockwise) and position. The description demands no order; a hole may follow a different outer ring.

.shp and .shx share the same header. They are told apart by the first entry: record number 1 in the .shp, offset 50 in the .shx.

Deliberate decisions

SH4 (decided) — Deleted .dbf records are read along

The .dbf only marks; the shape in the .shp stays. Assignment is by position — skipping deleted records shifts every following shape onto foreign attributes. GDAL omits such features; we read them and report the count.

SH8 (decided) — Writing

pyshp writes. This module reads.

Properties of the format

SH1 (property) — Detection by header, ahead of dBASE

Formaterkennung checks the code, five zero words, the version and a shape type of the description. It runs before the dBASE check because that one is only plausible.

SH2 (property) — The .shx is checked, not needed

The .shp is read sequentially. A mismatching index is a finding; a missing one too, but no obstacle. pyshp reads through the index when present.

SH5 (property) — "No data" becomes NaN, not -10³⁹

pyshp returns None, we return NaN (or an empty cell). Passed through, -10³⁹ would be a measurement silently carried into calculations; a mutation without this mapping turns four checks red.

SH6 (property) — Multipatch as in GDAL

The multipatch has no WKT counterpart. Strips and fans fall apart into triangles, rings become polygons with holes by their kind — the result is a MULTIPOLYGON Z. pyshp refuses a GeoJSON view of it.

SH7 (property) — Holes by position, not by order

A counter-clockwise ring belongs to the outer ring that contains its first point. The obvious shortcut "to the preceding ring" would give a different result than shapely on the second fixture; the probe checks both.

SH3 (property) — The reference system is interpreted, four projections converted

Bezugssystem reads the .prj in both dialects — as ArcGIS writes it and as GDAL writes it — into one model: datum, ellipsoid, prime meridian, units, projection, parameters, EPSG (from AUTHORITY, otherwise inferred from the name and marked so). Transverse Mercator (sixth-order Krüger series), Mercator on ellipsoid and sphere, Lambert conformal conic with one and two parallels and geographic systems are converted; the punkte table then gets laenge and breite. No datum shift — its parameters or grids are nowhere in the .prj. Other projections are named, not computed, and a finding says so. Measured on fifteen EPSG codes against PROJ 9.5.1: lon/lat to 1e-8 degrees, x/y to one millimetre. Two traps: GDAL writes Pseudo-Mercator (3857) as Mercator_1SP on WGS 84 and stores the sphere only in EXTENSION["PROJ4",…] — without it the map is off by up to 40 km; and for NTF Paris the prime meridian is in degrees, the parameters in grads.

The Java implementation — where this reader stands among its own kind

GeoTools (gt-shapefile) is the Java reference: a pure reimplementation, maintained, with JTS as its geometry model. This reader is deliberately smaller — it hands out tables and WKT instead of a geometry model. Not measured.
