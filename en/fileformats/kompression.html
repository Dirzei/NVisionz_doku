Compression in image formats – background

What stands behind the image readers: LZW in GIF, TIFF and PDF, PackBits, the row filters and Adam7 of PNG and the cosine transform of JPEG – as the decoders implement them.

What this is about: writing points down sparingly

An image of w×hw \times h points at 3 bytes per point needs 3wh3wh bytes; an area of 1000 × 1000 points is three megabytes. Image formats store it smaller, in two fundamentally different ways. Lossless (GIF, PNG, TIFF, WebP lossless) exploit repetition and predictability: every byte can be recovered from the data. Lossy (JPEG, WebP lossy) throw away what the eye hardly sees and are reversible only up to a tolerance. The reader has to get both right; in both there are places where a decoder silently delivers an image that looks like an image and is not correct. The following sections name them. The decoders are own implementations without javax.imageio; unpacking (LZW, Deflate) comes from framework-compress.

LZW: a dictionary that arises while reading

Lempel-Ziv-Welch replaces recurring byte sequences by codes of a table that encoder and decoder build simultaneously: no table is sent. The table starts with the single characters (codes 00 to 2b−12^{b}-1 for bb bits per character), then a clear code 2b2^b (reset the table) and an end code 2b+12^b+1; new entries from 2b+22^b+2. Each code read outputs a sequence and adds to the table the previous output plus the first character of the current one. The code width grows with the table up to at most 12 bits.

Example (by hand). ABABABA is encoded with A=65A = 65, B=66B = 66, clear code 256, end code 257. The encoder outputs 256, 65, 66, 258, 260, 257, building 258 = AB, 259 = BA, 260 = ABA on the way. Decoder: 65 gives A; 66 gives B and enters 258 = AB; 258 gives AB and enters 259 = BA; then comes 260, which is not yet in the table (the next free one is 260). That is the self-reference: the entry is the previous output plus its first character, AB + A = ABA. Output: A B AB ABA = ABABABA.

GIF, TIFF and PDF all use the same method and differ in three things:

Bit order of the codesleast significant bit firstmost significant firstmost significant first

The core in Lzw.entpacke has switches for this (lsbZuerst, frueh, anfangsbits), and the width grows as soon as next+early≥2width\text{next} + \text{early} \ge 2^{\text{width}} holds. The strictness with broken streams also differs per format and has been kept deliberately: GIF accepts as self-reference only exactly the next code and otherwise aborts, PDF skips a code that is not in the table, TIFF stops there quietly.

PackBits: runs

Besides LZW, TIFF knows the simplest run-length method. A byte nn, read signed, decides: n≥0n \ge 0: copy the following n+1n+1 bytes unchanged; −127≤n≤−1-127 \le n \le -1: repeat the following byte 1−n1-n times; n=−128n = -128: do nothing. Example: 02 41 42 43 FD 58 gives 41 42 43 and then four times 58 (1−(−3)=41 - (-3) = 4), so ABCXXXX. It is read as byte, not as 0 to 255: whoever reads unsigned takes 253 for a count of 254.

PNG: Deflate, row filters, Adam7

The eight bytes at the start of a PNG file are a test track: 89 drops out if someone cuts off the top bit, 0D 0A is destroyed if a program rewrites line endings, 1A ends output under MS-DOS, the last 0A catches the opposite direction. In addition, each chunk carries its own CRC-32; a PNG file can thus say which part of it is damaged.

The image data stands as a zlib stream (Deflate) from own code (envisionz.compress.deflate.Zlib, explicitly not java.util.zip.Inflater). Before packing, each row is preceded by a filter byte that says how it was computed against its neighbours: 0 None, 1 Sub, 2 Up, 3 Average, 4 Paeth. The inverse is the same as the PDF predictor (table on the page Document, filters and encryption), with aa left, bb above, cc above left:

v=x+{0NoneaSubbUp⌊(a+b)/2⌋AveragePaeth⁡(a,b,c)Paeth(mod256)v = x + \begin{cases} 0 & \text{None}\\ a & \text{Sub}\\ b & \text{Up}\\ \lfloor (a+b)/2 \rfloor & \text{Average}\\ \mathrm{Paeth}(a,b,c) & \text{Paeth} \end{cases} \pmod{256}

Three places where a reader goes silently wrong, and all yield an image that looks like an image:

  1. Average rounds down. Whoever rounds commercially gets an image that is right at the top and drifts downward, because the errors add up from row to row. Paeth on a tie: aa, then bb, then cc.
  2. The filter distance below eight bits is 1 byte, not one pixel: the filters work on bytes that contain several points (Pngkopf.filterabstand).
  3. Adam7: seven passes, each a small image of its own with its own filter bytes and row length. Whoever reads them as one sequence of rows gets an image of tiles.

Pseudocode – PngDatei, inverse of one pass

for y ← 0 to höhe−1:
    if stream ended: finding “ended after y rows”, rest black;  return
    f ← next byte                                 filter 0 to 4; larger: finding, row taken unfiltered
    zeile ← the next zeilenbytes bytes
    for i ← 0 to zeilenbytes−1:
        a ← (i ≥ abstand) ? ziel[y][i−abstand] : 0
        b ← (y > 0) ? ziel[y−1][i] : 0
        c ← (y > 0 and i ≥ abstand) ? ziel[y−1][i−abstand] : 0
        ziel[y][i] ← (x + { 0 | a | b | (a+b) >> 1 | paeth(a,b,c) }[f]) mod 256

Adam7: seven passes, each as above with own width, height and own filter bytes;
       a point (x, y) of pass p lies in the image at (xAnfang_p + x·xSchritt_p, yAnfang_p + y·ySchritt_p)

JPEG: cosine transform and colour

A lossy JPEG divides each component into blocks of 8 × 8 points, transforms each block with the two-dimensional cosine transform and divides the 64 coefficients by values of a quantisation table; this is where information is lost. The coefficients are ordered in zigzag sequence (low frequencies first, many zeros at the end) and Huffman coded; the first (DC component) as a difference to the DC component of the previous block. The decoder reverses this: read Huffman, multiply by the table, bring from zigzag into the 8 × 8 arrangement, transform back.

The inverse transform for a block with coefficients F(u,v)F(u,v), with C(0)=1/2C(0) = 1/\sqrt2 and otherwise C=1C = 1:

f(x,y)=14∑u=07∑v=07C(u)C(v)F(u,v)cos⁡(2x+1)uπ16cos⁡(2y+1)vπ16f(x,y) = \frac14 \sum_{u=0}^{7}\sum_{v=0}^{7} C(u)\,C(v)\,F(u,v)\,\cos\frac{(2x+1)u\pi}{16}\,\cos\frac{(2y+1)v\pi}{16}

The decoder computes it separably: first all rows (sum over uu, result divided by 2), then all columns (sum over vv, again divided by 2), with a precomputed cosine table cos⁡((2x+1)uπ/16)\cos((2x+1)u\pi/16) and in floating point. Then it rounds, shifts by the midpoint 2t−12^{t-1} (at depth tt = 8 bits that is +128) and limits to 00 to 2t−12^t-1. From luminance YY and the colour differences CbC_b, CrC_r (each shifted by the midpoint) follows, according to T.871:

R=Y+1.402Cr,G=Y−0.344136Cb−0.714136Cr,B=Y+1.772CbR = Y + 1{.}402\,C_r, \quad G = Y - 0{.}344136\,C_b - 0{.}714136\,C_r, \quad B = Y + 1{.}772\,C_b

The colour components are usually stored at half resolution and are brought to full resolution before this computation. Besides the basic method with Huffman tables, the reader handles progressive JPEG (coefficients in several passes), arithmetic coding (SOF9, an entropy coder other than Huffman), the hierarchical method (image in resolution levels; when doubling, the old values stay at the even positions, between them stands the rounded-down mean of the neighbours, at the border the value is repeated), lossless JPEG (SOF3), restart markers and EXIF.

Decision in the framework: the quantisation table stands in the file in zigzag order and is read in this order; whoever applies it in natural order swaps the divisors and gets a falsified image. Jpegleser delivers the coefficients already dequantised, 64 per block in natural order. The inverse transform is the straightforwardly computed floating-point version with a precomputed cosine table; against libjpeg the bound of the probe applies (see below).

How it is checked

  • Lossless: what went in must come out. Gifprobe, Pngprobe, Tiffprobe, Bmpprobe check against anchors – files from third-party tools, stored as bytes.
  • JPEG (Jpegprobe): “equal” does not exist for a lossy method, hence several questions. (1) Is it still the image? The originals are formulas; the own loss must not be larger than that of libjpeg on the same file – a fixed bound would be wrong, because the loss depends on quality and image, not on the decoder (at quality 10 libjpeg alone loses 28 counts). (2) Does it agree with libjpeg? Nine points per anchor taken from libjpeg may deviate by at most three counts. Also Progressivprobe, Hierarchischprobe, Jpegvarianteprobe.
  • Bildvergleichsprobe measures the readers against javax.imageio, the implementation against which they compete in the field, without a third-party library. Pitfall there: BufferedImage.getRGB does not deliver the point of the file but its conversion to sRGB; a grey value 0x25 becomes 0x6A in a linear grey space.

Limits

  • Lossy formats are reproducible only up to the tolerance of the probe; for JPEG, two decoders do not deliver the same points but points within a few counts.
  • The inverse transform is a floating-point method without an integer fast version; it can be recomputed but is not designed for speed.
  • The LZW table is limited to 4096 entries (12 bits); a stream that demands more aborts or ends quietly depending on the format.
  • WebP (VP8 and VP8L) has methods of its own and is not described here.
