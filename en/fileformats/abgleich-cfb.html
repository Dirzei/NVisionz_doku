Compound File — comparison against MS-CFB and olefile

As of: 2026-09-07
Our implementation: envisionz.fileformats.cfb.Cfbdatei and CfbQuelle, read-only, no third-party library
Specification: [MS-CFB] Compound File Binary File Format — published by Microsoft and freely available; references give section and field offset
Compared against: olefile 0.47
Test bench: envisionz.fileformats.cfb.Cfbprobe — 27 checks; envisionz.fileformats.Compoundprobe — 9 checks on detection

The reference implementation. olefile by Philippe Lagadec is a pure Python implementation of MS-CFB, grown out of the Python Imaging Library's OleFileIO. In the Python world it is the library everything else that touches old Office files builds on — from python-oletools to virus scanners.

Why this one. Because the comparison here runs the other way round. For CFB there is no tool that writes a fixture: olefile only reads, and Office does not fit into a test bench. So the test is inverted — the file this bench builds itself is handed to olefile. If it passes there, it is a real compound file and not merely something the reader happens to accept.

Coverage, computed from the rows below: of 26 features we have 23 present, 0 partial and 3 absent; the reference implementation has 16 / 2 / 8.

The Note column points into section 5 of this document — not into the workspace item list. The word in front says what kind of thing it is: gap is something we lack and that is open; decided is something we deliberately do not do; property is a trait of the format affecting both implementations; open there is a gap of the reference product. Only the gaps are work — they are collected in section 5.1 and appear as one item in OFFENE-PUNKTE.md.

A file system inside a file. A compound file has storages and streams instead of directories and files, an allocation table instead of a FAT — it is a FAT — and a red-black tree as its directory. Everything Microsoft stored before OOXML lives in one: .ppt, .doc, .xls, .msg, .msi, plus Thumbs.db and most old installer packages.

What is read here, and what is not. The container is read: storages, streams, sizes, timestamps, location. What is inside a stream — the PowerPoint records, the Word text, the Excel cells — is not interpreted; that would need a record reader per application. This is the same cut as in ZipQuelle, and CfbQuelle states it as a finding on every open. A view that shows a directory tree and leaves open that the content stays unread lets the user believe they are seeing the presentation.

How this was measured. On 2026-09-07 the fixture produced by Cfbprobe.baue (7680 bytes, one large stream of 5000 bytes and a small one of 11 bytes in the mini stream) was written out and handed to olefile 0.47. Result: isOleFile says yes, the sector size is 512, the mini sector 64, the mini stream cutoff 4096; the directory names exactly Kopf (11 bytes) and PowerPoint Document (5000 bytes); the large stream comes back byte for byte identical; and the root's modification time reads 2026-06-15 12:00:00 there — the same one this reader derives from the FILETIME field. That pins down the time arithmetic too, not only the structure.

The items

Our open gaps

Deliberate decisions

CF3 (decided) — Colour and state bits stay out

The directory is a red-black tree and every entry carries its colour. A reader does not need it: it walks the tree, it does not rebalance it. olefile does not read it either. The row is listed anyway so that nobody takes it for forgotten.

CF6 (decided) — The record streams are not interpreted

PowerPoint Document, WordDocument, Workbook are each a binary format of their own with their own specification ([MS-PPT], [MS-DOC], [MS-XLS] — well over a thousand pages together). Reading them here would not be one more item but three more formats. The cut sits at the container deliberately, and CfbQuelle emits it as a finding on every open — not as a footnote in the documentation but where the user is looking.

CF7 (decided) — No writing

A CFB writer would have to keep the FAT, the MiniFAT, the DIFAT and a balanced red-black tree correct at once. The bench builds its fixture by hand — and that this fixture is a real compound file is stated not by our own reader but by olefile.

Properties of the format

CF1 (property) — The creation time — closed on 2026-09-23

Every directory entry carries two FILETIME fields: 0x64 creation, 0x6C modification. Since 2026-09-23 both are read (Cfbeintrag.erzeugt, column erzeugt) with the same conversion; Cfbprobe pins it on an entry with different times.

CF2 (property) — The class id CLSID — closed on 2026-09-23

At 0x50 each entry carries a 16-byte GUID. Since 2026-09-23 it is output in the usual form (first three fields little-endian, MS-DTYP 2.3.4.2; all zeros give empty), column clsid. Cfbprobe checks it against PowerPoint's id.

CF4 (property) — Damaged files: report instead of crash

Four places in this format can be bent so that a naively written reader runs forever instead of failing: a FAT chain pointing at itself, a DIFAT in a circle, a directory tree with a back reference, and a mini stream ending before the stream. All four are checks in Cfbprobe, and all four end here with a finding and a partial answer rather than an endless loop. None of the four is caught cleanly by the reference product: two of them it survives silently and answers wrongly (CF8, CF9), and where it does notice the damage it refuses the whole file rather than returning the part that was readable.

CF5 (property) — The extension does not decide, the directory tree does

A .ppt file may be a Word file, and a file with no extension at all may be either — the container is the same. Detection therefore goes by the name of the leading stream: PowerPoint Document → PPT, WordDocument → DOC, Workbook or Book → XLS. If none is found it stays Compound File (application undetermined) — explicitly not PPT on suspicion. And a hit for the same string somewhere in the data does not count: the search is in the directory. Compoundprobe tests exactly these five cases.

Findings on the reference product

CF8 (BUG there) — A looping FAT chain silently yields wrong data in olefile

olefile reads a stream by its size, not by its chain: it fetches as many sectors as the size demands, following the FAT entries without noticing that it visits the same number more than once. If an entry points at itself, that sector simply comes out repeatedly. The result has the right length, looks like data, and is wrong from that point on — the nastiest of all outcomes, because nothing hints at it. This reader breaks the chain on the second visit, reports X and returns the shorter but correct part. It is the one row in the table where we do more than the reference, and it is worth having.

How to reproduce — Write out the fixture from Cfbprobe.baue (7680 bytes). The FAT sits in sector 0, i.e. from file offset 512; its entry 9 points at 10. Set that entry to 9 — struct.pack_into('<I', d, 512 + 4*9, 9) — and open the file with olefile 0.47. Expected: a message, or a shorter stream. Observed on 2026-09-07 with olefile 0.47 under Python 3.12: openstream('PowerPoint Document').read() returns 5000 bytes with no message whatsoever; from byte 3072 — the stream's seventh sector — the sixth sector appears again, and again after that. Cfbdatei on the same file returns fewer than 5000 bytes plus the finding that the chain runs in a circle.

CF9 (BUG there) — A mini stream that is too short becomes an empty stream in olefile

The mini stream hangs off the root entry and carries its size there. If that size says 0 while the directory still lists a small stream of 11 bytes, the file contradicts itself. olefile returns zero bytes without comment — exactly what a genuinely empty stream returns too. An empty stream and a broken file thus become indistinguishable from the outside. This reader also returns what is there, but says that the mini stream ends before the stream.

How to reproduce — The same fixture. Read the directory sector from the header (offset 0x30), set the size field at 0x78 of the root entry to 0, and open the file with olefile 0.47. Expected: a message, or at least a difference from an empty stream. Observed on 2026-09-07: listdir() still names Kopf, and openstream('Kopf').read() returns b'' with no message, although the directory entry states 11 bytes.
