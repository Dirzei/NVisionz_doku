Ensight Gold — comparison against the manual and against VTK

As of: 2026-09-05
Our implementation: envisionz.fileformats.ensight.EnsightQuelle with Ensightfall, Ensightart, read-only, no third-party library
Specification: EnSight User Manual, appendix C "EnSight Gold Casefile Format" — public; references give section names
Compared against: VTK 9.7 (vtkEnSightGoldReader, vtkEnSightWriter)
Test bench: envisionz.fileformats.ensight.Ensightprobe — 144 checks, one foreign anchor, twenty-three own fixtures

The reference implementation. VTK by Kitware is the de facto core of scientific visualisation and the foundation of ParaView. Here, however, it is explicitly not the owner of the format: EnSight Gold belongs to CEI (Computational Engineering International), part of Ansys since 2017. vtkEnSightGoldReader and vtkEnSightWriter are an independent reimplementation of a vendor format — the most widely used one, but a reimplementation nonetheless.

Why this one. Because the vendor tool is not freely obtainable and VTK's reader is the most widespread reimplementation. More important still: VTK also ships a writer. That makes it possible to produce files a second implementation considers correct — the sharpest comparison available for a multi-file assembly, because it exercises the neighbouring-file rule as well.

Feature comparison

Ensight Gold is this workspace's first reader that touches more than one file. The .case file carries not one number — it only names names. Geometry and variables live beside it, and resolving them means opening files the user did not name. That is why this format has a route of its own, Datenquellen.oeffneVerbund(Path), and a strict rule by which the names are resolved: names only, no path, same folder only (Nachbardatei).

What was measured

One foreign anchor, and it is the best available for this format: an Ensight Gold output written by VTK itself, read through EnsightQuelle. Plus seventeen own fixtures from Ensightschreiber, twelve of which are deliberately broken — references upwards, absolute paths, references to folders, missing sections, too few coordinates. The second group is unusually large here, and for a reason: with a format whose case file contains file names, "what happens with a malicious name" is not an edge question.

The VTK file set

vtkEnSightWriter produces three files: fall.0.case, fall.0.00000.geo and fall.0.00000_n.t. Our reader opens the set through the case file and yields three tables:

TableContent
dateien2 rows: geometry fall.0.00000.geo (828 bytes, found), nodal variable t_n → fall.0.00000_n.t (260 bytes, found)
knoten4 records, columns knoten x y z t_n — the variable stands as its own column beside the coordinates
tria36 entries element platz knoten — two triangles of three nodes each

The numbers agree with what was written in. Two observations are noteworthy. First, the node tags start at zero: vtkEnSightWriter writes node id given with tags 0…3, while the connectivity counts one-based. Precisely that separation — tags are not indices — is the format's second trap, and the foreign anchor happens to contain it in pure form. Second, there are four nodes, not five: VTK writes only the points used by a cell. A reader taking the node count from another source would be off by one here.

The finding our reader emits for it is the title line of the geometry file: "Written by VTK EnSight Writer No Title was Spec…". That is not a report of a defect but the provenance, and it is there for every file. For a file from a foreign hand that is the first thing one wants to know.

The twelve malicious names

Ensightschreiber builds case files pointing at ../geheim.geo, at /etc/passwd, at unterordner/netz.geo, at a folder and at a symlink. All twelve are rejected, and the rejection names the reason, not merely the fact. That is where this reader differs from a converter: vtkEnSightGoldReader resolves paths as the operating system understands them. For a tool a user starts on their own files that is right. For a reader opening an uploaded file it is the wrong default — and that is why it is not a row in the feature table here but a class of its own (Nachbardatei) with seventeen checks on it.

The N2 rows therefore stand at ● for us and ● for VTK. That is expressly not a bug in VTK — it is a different purpose, and the rows are listed here because a reader of this document must know the difference before using one in place of the other.

What is hard about the format

The case file names names, and names are dangerous. Ensight is the only format in this collection where reading one file entails opening others whose names are in the first. Everything one has to know about path resolution becomes a format question here.

node id given is in the header, not with the data. If set, the tags follow the node count first and the coordinates after. Whoever skips the header line reads the tags as x values — and gets a mesh that looks like a row. The information sits dozens of lines before the place where it takes effect.

The node tags are not the connectivity indices. Connectivity counts nodes in the order of the coordinates, one-based. The tags from node id given may start at zero, jump or appear in any order. In the foreign anchor exactly that is the case: tags 0…3, connectivity 1…4. Whoever takes the tag as an index is wrong for every file whose numbering is not accidentally 1…n.

Binary or ASCII is decided by the geometry file, not the case file. The first eighty bytes say C Binary or Fortran Binary — or they are already the title, and then it is ASCII. The case file says nothing about it.

The element name does not say how many nodes follow. tria3, quad4, hexa20 — the number in the name is a convention, not a rule; nsided has none at all. The mapping is in a table in the manual. An unknown type stops our reading of the file rather than continuing with a guessed count — because a wrong node count shifts everything that follows and never announces itself.

What is good: the separation of description and data. The case file is readable text and fits on one screen; one sees at a glance what a dataset consists of without reading a single number. And because the geometry sits in its own file, a time series can have a hundred variable files beside one geometry. That is frugal, and was so before frugality was a topic.

The items

Our open gaps — this is the work

Deliberate decisions — nothing to do

N13 (decided) — Writing

VTK writes Ensight Gold and supplied this document's foreign anchor. This module reads. Ensightschreiber in the test bench builds file sets — twelve of them with malicious references — it is test equipment, not an output path.

N4 (decided) — The file set is carried as a table

The dateien table names role, name, whether it was found and how large it is, per file. With a format whose case file points at neighbours, the first question is never "which values" but "which files". VTK does not answer it because a converter does not ask it.

N1 (property) — All time steps — closed on 2026-09-06

Closed. The case is read across all steps: one column per variable and step, named after the variable and the number from the case file (druck#5, druck#7, druck#9). Nothing is rearranged — the table stays the table of nodes respectively elements; what is added are columns. Which step belongs to which time stands in the new table zeitschritte, and it exists only when there is more than one: for a steady computation it would be a single row that says nothing.

One case stays named, and it is not a gap but a statement about the file: if the geometry pattern itself carries a wildcard, the mesh depends on the step. The geometry of the first step is then read, and the variables of the later steps stand on that mesh. That is right as long as the mesh does not move, and it is stated so one knows.

N5 (property) — Fortran Binary — closed on 2026-09-06

Closed. The third variant, with Fortran record marks around every record: four bytes of length before, the same four bytes after. The reader now holds a current record and takes its values from it; when it is empty the next one begins.

The trailing length is not decoration, and it is checked. It allows reading backwards — and it is the only place where a reader can notice that it has miscounted. Skip it and you are four bytes off from then on, reading numbers that look like numbers.

The variant is recognised in the first eighty bytes — at two places: with Fortran Binary the signature already sits inside a record and is therefore four bytes further along. Look only at the first and a Fortran file passes for text.

N8 (property) — Several parts — closed on 2026-09-06

Closed, and a real bug found along the way. Previously the coordinates of the second part were written over those of the first while the element blocks accumulated — so the second part's connectivity pointed at the first part's nodes. That produced a geometry that looked like a geometry. Now the nodes are appended, each keeps its part number, and each part's connectivity is shifted by that part's node offset: a connection counts within its part from one.

Both tables — knoten and every element table — now carry a teil column. And without numbers in the file (node id assign) numbering runs across all parts rather than restarting in each: otherwise the number 1 would exist several times and two different nodes would look alike.

N9 (property) — nsided and nfaced — closed on 2026-09-06

Closed. Polygons and polyhedra with a node count varying from element to element. nsided: first the element count, then each element's node count, then all connectivity. nfaced: first the element count, then each element's face count, then each face's node count, then all connectivity — two length lists, not one. Skip the second and the node counts are read as connectivity.

An element's nodes come out in one run, face after face; how many faces there were stands in a column beside it. Enumerating the faces separately would introduce a third table level that the format does not have.

N10 (property) — Structured blocks — closed on 2026-09-06

Closed. block [iblanked] with i × j × k and the coordinates component-wise. The points go into the same node table as those of an unstructured part — with their part number — and the dimensions stand in the new table bloecke, together with the number of blanked points from iblank.

Two modifiers stay named and unread: range and with_ghost change the block's layout, and skipping them means reading the coordinates in the wrong place. The reader says so and stops rather than guessing.

N11 (property) — Element variables — closed on 2026-09-06

Closed. A scalar per element file is built like a nodal variable, except that beneath each part there is not coordinates but an element type — and beneath that as many values as that part has elements of that type. The values are kept per element type; the type's table then gains a column.

If a type appears that the geometry does not know, that is stated and not guessed. Without its element count one does not know how many values to skip, and from there nothing is right any more.

N12 (property) — Materials — closed on 2026-09-06

Closed. The case file's MATERIAL section is read: numbers and names sit there in two lines and belong together pairwise; they form the new table stoffe. The file behind material per element carries one number per element and is built like an element variable — it is read as one and becomes a column on the element tables.

The shared gap from 5.4 therefore no longer stands: VTK reads materials only partly, this reader reads them.

Properties of the format

N6 (property) — node id given takes effect far from where it stands

See section 3. And the tags are not indices — the foreign anchor numbers 0…3 while the connectivity counts from one.

N7 (property) — Component-wise coordinates

All x first, then all y, then all z — not as triples. The same trap as in Exodus (E4) and PLOT3D.

Findings against the reference implementation

N2 (open there) — References are resolved as the operating system understands them

See 2.2. vtkEnSightGoldReader follows a ../ and an absolute path in the case file. That is not a bug: VTK is a tool a user starts on their own files, and there it is the expected behaviour. The item stands here because with a reader opening foreign files it would be the opposite, and because this difference is documented nowhere else. Whoever replaces one implementation by the other has to know it.

N3 (open there) — A missing file ends in an exception

If a file named in the case file is missing, we name it in the dateien table with "found: no" and read on as far as possible. VTK aborts. With a set of a hundred files of which one is missing, the difference between "exactly this one is missing" and "does not work" is the difference between five minutes and an afternoon.

The Java implementation — where this reader stands among its own kind

Why this section. Every other comparison in this module measures against a tool in a different language. That is good against misunderstandings of the format and says nothing about where this reader stands among its own kind. What matters is the distinction between a pure reimplementation in Java and a wrapper around the original C library: only the reimplementation solves the same task under the same conditions as this reader; a wrapper calls the original.

No Java implementation found. There is pure Python (ensight-reader), C++ with a MATLAB binding (Ensight4Matlab) and the C++ reader in VTK — the latter again only as a JNI wrapper from Java. No JVM implementation surfaced during the research.

How solid this is. Researched on 2026-09-06 via web and GitHub search; Maven Central's search API was blocked at the time, so a systematic artefact search was not possible. "Nothing found" is therefore not the same as "nothing exists" — a little-visible or in-house implementation would not be discoverable this way. What stands here is the state of an honest search and not a claim of completeness.
