Conventions over containers and numeric arrays: CGNS, Exodus, MATLAB, NumPy – background

Why CGNS and Exodus are not byte formats of their own but rules over HDF5 and netCDF, how MATLAB and NumPy store a numeric array, and where a reader silently delivers a transposed matrix.

The problem: order in memory

A multidimensional array is stored in a file as a linear sequence. Which axis runs fastest is the one question all four formats depend on. In C order (row-major) the last axis runs fastest, in Fortran order (column-major) the first. For an array of shape (n0, …, nd−1) the element (i0, …, id−1) lies at position

$$ p_C = \sum_{k=0}^{d-1} i_k \prod_{j>k} n_j , \qquad p_F = \sum_{k=0}^{d-1} i_k \prod_{jBoth formulas give the same set of positions, only assigned differently. Whoever uses the wrong one gets the transposed matrix for a square array – it looks like a matrix, and no checksum notices.

CGNS: nodes with name, label and “ data”

CGNS from version 3 is HDF5 with a rule on top: every node is a group with the attributes name, label and type, its values are in the dataset " data" – with a leading space. The meaning is carried by the label (CGNSBase_t, Zone_t, GridCoordinates_t, FlowSolution_t, Elements_t). It is written in Fortran order, so the HDF5 shape is the reversed CGNS shape: a 3 × 2 grid appears as 2 × 3.

The zone size is, in the CGNS view, an array (axes × 3): per axis vertices, cells, boundary vertices. In the file it is transposed; row 0 holds the vertex counts of all axes:

Dz,a=Ca,z,Ka−1=Za,D_{z,a} = C_{a,z}, \qquad K_a - 1 = Z_a ,

with D the array in the file, C the CGNS view, Ka and Za the vertex and cell counts of axis a (for structured zones).

The second relation checks the transposition: if it is wrong, “vertices minus one” no longer holds either. Vertex and element numbers are one-based and stay so.

Exodus II: names over netCDF

Exodus is a convention over netCDF. The coordinates are stored per dimension: coord has the shape (num_dim, num_nodes), first all x, then all y, then all z; some writers create coordx, coordy, coordz instead. The x value of node j is therefore at j, the y value at n + j, not at 2j + 1. The connectivities connect1, connect2 … count nodes one-based; the block ids in eb_prop1 are not the running numbers. Variable names are stored as a character grid (count × 33) padded with zero bytes.

MATLAB level 5: tags in two sizes

A MAT file of level 5 has a 128-byte header (116 bytes of text, 8 bytes subsystem offset, version 0x0100, byte-order mark “IM” or “MI”), followed by data elements. Each starts with a tag of type and byte count. It comes in two sizes, and the short one is recognisable only by the upper two bytes of the first word:

w1=216b+t(1≤b≤4),otherwisew1=t,w2=b,w_1 = 2^{16} b + t \quad (1 \le b \le 4), \qquad \text{otherwise} \quad w_1 = t,\; w_2 = b ,

with t the element type and b the byte count.

If the upper part of w1 is non-zero, it is the short form: content in the second word, the element is eight bytes long. Otherwise the byte count follows as the second word, and the element is padded to a multiple of eight – except miCOMPRESSED: a compressed element is not padded, the next one starts right behind it. Measured on a file with three compressed variables: elements at 128, 180 and 236, file length 281.

Element types (miINT8 … miUTF32) and matrix classes (mxDOUBLE …) both count from one; a 6 is miUINT32 and mxDOUBLE. The values of a matrix are stored column by column.

MATLAB 7.3: HDF5 behind a user block

Level 7.3 is HDF5 with a 512-byte user block carrying the same description text as the level-5 header; without it the file cannot be told apart from any HDF5 file. Each variable is a dataset, its attribute MATLAB_class names the class (double, char, logical, …). Because MATLAB writes column-major and the HDF5 shape describes the C view, the shape appears reversed:

(n0,…,nd−1)=(md−1,…,m0),(n_0, \ldots, n_{d-1}) = (m_{d-1}, \ldots, m_0) ,

with n the MATLAB shape and m the HDF5 shape.

A MATLAB matrix 2 × 3 is stored as an HDF5 dataset 3 × 2; the characters of a char variable are 16-bit codes, a logical is one byte. If “MATLAB” is missing from the user block, the file is still read under the convention and that is reported.

A cell is a dataset of object references into the group #refs#. Its elements are resolved and delivered as text of their content; until 2026-10-19 the cursor aborted at the first value.

NumPy: a Python literal as header

An .npy starts with \x93NUMPY, two bytes of version and the header length: two bytes in version 1, four bytes (unsigned) in versions 2 and 3. The header is a Python dictionary with descr, fortran_order and shape, padded with spaces and a newline so that the data start at a multiple of 64. It is parsed, not executed. The size of the data follows as

N=∏knk,B=N⋅w,N = \prod_{k} n_k , \qquad B = N \cdot w ,

with w the width of one value. All three numbers are claims of the file: a negative axis length, a product above 263 (65 5364 = 264 would wrap to zero in 64 bits and make an empty file look valid) and a header length beyond the file size are rejected before anything is allocated.

An array with more than two axes is delivered in long form: one row per value with the indices and the value. The rows run in C order; with fortran_order: True the reader first computes the indices from the running number and from them, with pF, the position in the file.

Text of type U takes four bytes per character, and every character is a number from the file. Anything that is not a valid Unicode code point (above U+10FFFF) is returned as the replacement character U+FFFD; until 2026-10-25 the cursor aborted there with an exception.

What follows

  • Assumptions: the convention holds for the whole file; a CGNS node without " data" or an Exodus file without coord is reported, not completed.
  • A shape is never just taken over: for a Fortran writer on top of HDF5 (CGNS, MATLAB 7.3) it is reversed, for NumPy fortran_order decides, for MATLAB 5 it is always column-major.
  • The sharpest test of an ordering is an array with different axis lengths and values that reveal their position (12 i + 4 j + k); a square array with smooth values tests nothing.
  • Header values are claims of the file: lengths, axes and counts are checked against the rest of the file.

How it is tested

CGNS against three files from pyCGNS, Exodus against a file from meshio, MATLAB level 5 against ten files from scipy (plus own big-endian files), MATLAB 7.3 against a file from h5py 3.16 with user block, NumPy against files from NumPy itself and against hand-built headers for the edge cases. The recomputation is in docs/theorie/rechnung/fileformats_wissenschaft.py.

Limits

  • CGNS in the old ADF version is named, not read.
  • MATLAB: objects (mxOBJECT) are read as structures; in level 7.3 structs appear as separate datasets with path, cells only one level deep (a cell inside a cell stays text without content).
  • NumPy: object arrays (|O) contain Python pickle and are rejected.
