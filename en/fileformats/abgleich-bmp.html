BMP — comparison against the documented Windows structures and against Pillow

As of: 2026-09-06
Our implementation: envisionz.fileformats.bmp.BmpDatei with Bmpkopf, read-only, no third-party library
Specification: Microsoft Windows GDI, Bitmap Storage, and the structures BITMAPFILEHEADER, BITMAPCOREHEADER, BITMAPINFOHEADER, BITMAPV4HEADER, BITMAPV5HEADER — publicly documented; references give structure and field names
Compared against: Pillow 12.2.0 (Python)
Test bench: envisionz.fileformats.bmp.Bmpprobe — 389 checks, fourteen foreign anchors, two computed fixtures, twelve counter-tests

The reference implementation. Pillow is the image library of the Python ecosystem: a thin Python layer over its own C code. It is the 2010 fork of the original Python Imaging Library by Fredrik Lundh (Secret Labs), started by Jeffrey "Alex" Clark and maintained today by the python-pillow team. Nearly everything that opens an image in Python — from matplotlib to Django's image fields — passes through it. It is therefore the most widely used implementation in its field, but the reference implementation of no format at all: it reimplements other people's formats. For this format it uses its own C code, no third-party library.

Why this one. Because for BMP there is no reference implementation to measure against. The format is a sequence of C structures from the Windows programming interface; whoever reads it reads a description of structures, not a norm. Among the freely available implementations Pillow is by far the most used and covers the header variants and run lengths broadly — so it is not the truth, but the most solid second opinion obtainable without Windows. That is precisely why every difference here is recorded as a finding, not as an error on either side, until it is settled against the structure documentation.

Feature comparison

BMP has no specification in the sense the other formats in this collection have. There is no document with numbered paragraphs to point at — there are documented C structures from the Windows programming interface, and the file format is what comes out when you write them one after another into a file. Everything characteristic of this format is therefore a property of a 1990 memory layout rather than a design decision: rows run bottom-up because OS/2's coordinates started there; colours are stored blue-green-red because that is what a COLORREF looks like in little-endian memory; rows are padded to four bytes because a 32-bit access would otherwise be unaligned.

That makes BMP the simplest format in this series and at the same time the one with the most silent traps. There is nothing to decompress and nothing to decode; there are only half a dozen places where a reader accidentally delivers something plausible that is wrong.

What was measured

Eleven foreign anchors: five were written by Pillow 12.2.0, six were built by hand and read back by Pillow — so the target values come from there in all eleven cases. What had to be built by hand is what Pillow does not write: the 12-byte header, the negative height, four bits, sixteen bits and the two run-length images. Pillow always writes a BMP uncompressed and with eight, twenty-four or thirty-two bits; the arguments bits=4 and compression=1 are accepted and ignored (measured, see B19).

Why the colour sum alone does not suffice here

For every anchor the probe checks three things: the colour sum over all pixels, the first row and the last. The reason is the format's main trap. A BMP is stored bottom-up; a reader that overlooks this delivers a vertically mirrored image — with the same colour sum, the same colours, the same size and without any message. Only comparing the first row against the last uncovers it. The same holds for the BGR/RGB mix-up: on a grey image it is invisible because all three channels are equal. That is why both colourful and grey anchors are in the list.

Two fixtures manage without a foreign anchor, and the reason is itself a finding: BI_BITFIELDS with an express 5-6-5 and BI_ALPHABITFIELDS with four masks. Pillow does not read the second compression at all (B15) — there is nobody to read it back. The probe therefore builds both files itself, byte by byte from a rule, and checks against that same rule rather than against transcribed numbers: with eight bits per mask a pixel must come out unchanged, and the same 16-bit word must give something different without masks than with them. This is the only place in this comparison without an outside cross-check, and it is marked as such.

Two counter-tests that stayed green — and why that was a finding about the probe

A set of checks is worth something only once it goes red the moment one breaks the reader. Of twelve interventions only eight went red at first. Two stayed green: "skip the delta in the run-length stream" and "do not pad absolute runs to an even byte count".

The cause was not the reader but the fixture. The anchor rle8 consists exclusively of encoded runs — four pixels of one index, four of another, end of line, end of bitmap. A stream in that shape uses neither the delta nor the absolute run. The two corresponding branches in the reader were covered by not a single fixture; they stood there unproven, and the counter-tests could not go red at all.

The house rule says a counter-test that stays green is discarded or the probe is sharpened. Here the second was right, because both branches are genuine parts of the format and not an invention. So an eleventh anchor was added: rlesprung, 8 × 4, built by hand and read back by Pillow. Its bottom row contains an absolute run of three pixels — three bytes and one pad byte — its second row a delta of three to the right whose skipped pixels stay on the background, and above that two ordinary rows. Since then all twelve counter-tests are red.

What is hard about the format

Bottom-up. The first row in the file is the bottom row of the image, as long as the height is positive. Only a negative height — which cannot occur in the 12-byte header, whose dimensions are unsigned — flips it. Overlook it and you get a mirrored image with the same checksum. With a pattern that has no clear top, and that is most patterns in a test bench, it never shows.

Blue, green, red. Both in the palette and at 24 and 32 bits the channels are stored in that order. Swap them and the colour sum stays numerically identical — the same three numbers, only assigned differently. And on a grey image the error is entirely invisible. A test bench comparing only a sum over a grey image says nothing about this mix-up.

The row padding aligns every row, not the file. Every row occupies a multiple of four bytes. For three pixels at 24 bits that is nine useful bytes and twelve occupied. Forget the padding and you read shifted from the second row on — and the image is then not broken but sheared: it looks like an image, only skewed. That is exactly why the anchor b1 is 17 wide and vierbit is 7; at even widths the padding coincides by accident.

A zero that means "all". biClrUsed = 0 does not mean "no palette" but "as many entries as fit the bit depth" — at eight bits, 256. Take the zero literally and you skip the palette, compute the data start 1024 bytes too early and thereby mistake the palette for image data. The result is not a crash but an image of gradients that at first glance looks like a test pattern.

Sixteen bits are 5-5-5. Without masks the three channels take five bits each and the top bit stays unused. The 5-6-5 split familiar from elsewhere occurs in BMP only when stated expressly through BI_BITFIELDS. Read maskless data as 5-6-5 and the image is not wrong enough to notice: red and blue sit one bit off, green is too bright — it looks like a different colour rendering, not like a bug.

The header kind is stated nowhere — only its length. There is no "version" field. The first word of the info header is its length in bytes, and that alone tells whether a BITMAPCOREHEADER (12) or a BITMAPV5HEADER (124) follows and where the colour masks sit. An unknown value leaves only two ways: reject, or read on as a 40-byte header and say so.

What is good: that there is nothing to decompress. An uncompressed BMP is the only widespread image file in which one can work out the pixel at a given place with paper and pencil. For a test bench that is no small advantage — for every error the question "what is really in the file" can be answered without having to believe a second reader. That is precisely why six of the eleven anchors could be built by hand.

The items

Our open gaps — this is the work

Deliberate decisions — nothing to do

B1 (decided) — No route through the general format detection

Datenquellen.oeffne rejects a BMP and points at BmpDatei.lies. The reason is the same as with GIF (I15): an image is not a table, and a Datenquelle is a table view. The detection itself knows BMP and names it; only opening it as a data source is missing. The same situation as VTK (V9), HDF4 (H8) and GIF (I15).

Decided by the owner on 2026-09-06. The item stood as a gap in five image formats with identical wording (BMP B1, GIF I15, PNG P1, TIFF T24, WebP W20). It is not one: a Datenquelle is a table view, and an image is not a table. A view with one row per pixel (x, y, red, green, blue) would be possible — at 4000x3000 that is twelve million rows, and what it would buy does not answer the question "what is in this file" but a different one. The readers exist and are named in the rejection message; that is the information the user needs. VTK (V9) and HDF4 (H8) are different: their content really is tabular, and there the view is being built.

B5 (decided) — Widen by rounding, not by bit replication

A five-bit value stands for the fraction v / 31; on eight bits that is v · 255 / 31, and how you make that an integer decides the result. Three ways are in circulation. Shifting alone (v << 3) is wrong: 31 becomes 248, the brightest white would not be white. Bit replication (v << 3 | v >> 2) hits the ends and is the trick quoted everywhere — but it is off by one at four of the thirty-two values (too dark at 3 and 7, too bright at 24 and 28). We round to nearest, written in integers as (v · 255 + 15) / 31. It is the only one of the three that lands on the right number everywhere, and the probe recomputes this in closed form over all 32 values — against the formula, not against a reference product.

B6 (decided) — Alpha is carried but not counted in the sum

The reader returns one int per pixel in ARGB form; alpha comes from the fourth mask where one exists and is otherwise full. The probe's colour sum counts only red, green and blue. That is deliberate: Pillow delivers alpha differently depending on mode (RGB or RGBA), and a sum that depends on the reference product's operating mode checks nothing. Alpha is checked at individual places instead.

B3 (decided) — Writing

Pillow writes BMP and supplied five of the eleven foreign anchors. This module reads. The six hand-built anchors are test equipment, not an output path — they arise in the test bench from a few lines and sit as packed bytes in Bmpanker.

B2 (property) — Embedded JPEG and PNG — closed on 2026-09-06

Closed. Compression methods 4 and 5 are not compression: where the pixels would be there is a complete file, with its own signature, header and dimensions. The work is therefore handing on to PngDatei respectively JpegDatei — both sit in the same series and cost no third-party library.

The one question this raised: which dimensions apply when the envelope and its content disagree. Those of the inner image apply, because the BMP is only the envelope; the disagreement is reported. A dedicated anchor covers it, whose header says 12 × 9 while its PNG is 8 × 6 — without it a counter-test that fetches the pixels with the wrong row width would stay green, because with equal dimensions both computations coincide.

One remainder is named: that the length field biSizeImage is honoured is not measured — the counter-test of always reading to the end of the file stays green, because neither the PNG nor the JPEG reader minds bytes after the end of the image. The line stands in the code anyway, because the format calls for it.

B4 (property) — Colour space and ICC profile — closed on 2026-09-06

Closed, as far as a reading module can take it. The 108-byte header carries a colour-space tag, nine endpoint coordinates in 2.30 fixed point and three gamma values in 16.16 fixed point; the 124-byte one adds the rendering intent and the offset and length of an embedded ICC profile. All of it is now read and exposed through Bmpkopf, and the three cases — calibrated, embedded profile, link to a profile file — are named.

Nothing is converted, and that is a decision, not a remainder. A colour transform needs a target — which screen, which profile, which intent — and file inspection does not know that. Whoever applies the values hands out numbers that differ from those in the file and still calls them "the pixels". So the pixels come out unconverted; whoever wants to convert them now has the endpoints and the gamma values in hand. Pillow likewise only carries the ICC profile in info and does not convert either.

The test measures both together: the values must come out and the pixels must remain untouched. Whoever converts here is caught.

Properties of the format

B7 (property) — Bottom-up

See section 3 — the main trap. Two anchors therefore stand side by side: b24 bottom-up and obenunten top-down, both with first and last row checked individually. The 12-byte header carries its dimensions unsigned; a negative height cannot exist there, and we report it if one does.

B8 (property) — Rows padded to four bytes

See section 3. Two anchors are deliberately of odd width: b1 with 17 pixels at one bit and vierbit with seven at four bits — there the row ends in the middle of a byte and before the padding.

B9 (property) — Blue, green, red

See section 3. The anchor grau is in the list to show where this mix-up does not show.

B10 (property) — Three or four bytes per palette entry

The 12-byte header carries three-byte RGBTRIPLEs, all larger ones four-byte RGBQUADs. Always take four and the 12-byte case reads a palette a third too long and lands on the wrong data start; always take three and the reverse. The anchor kern12 covers exactly that — it is the intervention with the most failures of all (119).

B11 (property) — The zero that means "all"

See section 3. Bmpkopf.farben() resolves it so that no caller has to interpret it a second time.

B12 (property) — Sixteen bits are 5-5-5

See section 3. The anchor sechzehn is a computed image: the red channel at (x, y) is (x·7) % 32, green (y·11+3) % 32, blue (x·5 + y·9) % 32. It is checked against that rule and not against transcribed numbers.

B13 (property) — The header kind is only in its length

See section 3. We know 12, 40, 52, 56, 64, 108 and 124; anything else is reported and read on as a 40-byte header, because the image content is usually unaffected.

B14 (property) — Delta and absolute run

Besides the encoded run the run-length stream knows three special cases with a leading zero byte: end of line, end of bitmap and delta (00 02 dx dy). Anything above that is an absolute run of n pixels whose bytes are padded to an even count. Forget the pad byte and the rest of the row shifts by one; skip the delta and everything following shifts left. Both branches were covered by no fixture until 6 September 2026 — see 2.2.

Findings against the reference implementation

B15 (open there) — BI_ALPHABITFIELDS (6) is not read

This compression comes from OS/2 and differs from BI_BITFIELDS only in that four masks follow instead of three. Pillow 12.2.0 rejects it with OSError: Unsupported BMP compression (6); we read it. The compression is rare, but it occurs, and the effort is one extra mask. Because nobody reads it back here, there can be no foreign anchor for this compression. The probe therefore builds the fixture itself, byte by byte from a rule, and checks against that same rule: with eight bits per mask a pixel must come out unchanged, and the alpha must be carried, not invented.

B16 (open there) — Four conditions as an exception instead of a finding

Truncated image data, a palette cut short, a run-length stream without an end-of-bitmap, and an unknown header length. In all four cases we read as far as possible, report the place and leave the rest black. Pillow throws (image file is truncated, Unsupported BMP header type) and delivers nothing. That is not a bug in Pillow — it is an imaging library, not a file-inspection tool, and half an image is no usable result for its purpose. For the question "what happened to this file" it is the difference between an answer and none.

B17 (open there) — Unknown header length

See B16. Listed separately because there is a way to read on that Pillow does not take: the first sixteen bytes of every info header from the 40-byte one upwards are laid out identically. An unknown length — say from a writer that invented a header — therefore does not cost the image but only the extra fields.

B18 (open there) — A wrong file size in the header

bfSize is meant to state the length of the file. Many writers put nonsense there. We read by the actual length and report the discrepancy as a finding; Pillow reads on silently without mentioning it. Not a bug, but that field is the only place where a BMP can say of its own accord that it is incomplete — and then you want to see it.

B19 (open there) — bits and compression on writing are accepted and ignored

Image.save(..., "BMP", bits=4) and compression=1 raise nothing and change nothing: the file comes out eight-bit and uncompressed. Measured on a 4 × 4 P image — the file is 1094 bytes in all four cases, compression 0, depth 8. A silently ignored argument is more unpleasant than a rejected one, because the caller believes he got what he asked for. That is why six of the eleven anchors had to be built by hand.

The Java implementation — where this reader stands among its own kind

Why against javax.imageio in particular. Every other comparison in this module measures against a tool in a different language — Pillow, astropy, pyarrow, meshio. That is good against misunderstandings of the format and says nothing about where this reader stands among its own kind. javax.imageio is the Java implementation it actually competes with in the field: it sits on every machine this module runs on, and it costs no foreign library — the module's rule stays untouched. It is measured on every run, not once: Bildvergleichsprobe, 80 checks now that JPEG is included. And the reader measured against here really is pure Java: com.sun.imageio.plugins.bmp.BMPImageReader has not a single native method. Measured on 2026-09-06, because adding JPEG revealed that this does not hold there — the JDK's JPEG reader is a JNI wrapper around libjpeg 6b. For this format, then, the comparison really is one among its own kind.

11 anchors, all 11 pixel-identical. One, four, eight, sixteen, twenty-four and thirty-two bits, both run-length variants with delta markers, the old 12-byte core header and the bottom-up variant — not a single differing pixel against javax.imageio.

And a trap that is half the yield of the measurement. BufferedImage.getRGB() returns not the pixel from the file but its conversion to sRGB. For greyscale, ImageIO stores the values in a linear grey space and getRGB applies the sRGB curve on top: the raw value 0x25 becomes 0x6A — to three digits exactly (37/255)^(1/2.4) in sRGB encoding. The first run therefore reported differences on every greyscale image, in PNG and in BMP, that is on two independent readers of ours with the same symptom. It looked like a real bug and was none. The comparison goes through the raster. With TYPE_USHORT_GRAY the raster carries the raw 16-bit value while our punkte() is the view scaled to eight bits — whoever shifts there instead of rounding is off by one, and takes that for a bug too.
