HDF4 — comparison against the specification and against pyhdf

As of: 2026-09-27
Our implementation: envisionz.fileformats.hdf5.hdf4.Hdf4File with Hdf4Dataset, Hdf4Vdata, Hdf4Tag, Hdf4Sonderart, read-only, no third-party library
Specification: HDF Specification and Developer's Guide (The HDF Group), chapter "File Format" — public; references give tag numbers
Compared against: pyhdf 0.11.7 (Python, linked against the HDF Group's HDF4 library)
Test bench: envisionz.fileformats.hdf5.hdf4.Hdf4probe — 251 checks; plus hdf4_muster.hdf in the Referenzdateiprobe

The reference implementation. pyhdf is a Python wrapper around the HDF4 library — a binding to the reference implementation, whose code originally came from NCSA and is maintained today by the HDF Group. The original author abandoned the project; it lives on under community maintenance and is the only common HDF4 binding for Python.

Why this one. Because pyhdf talks to the HDF4 library and so reaches the reference itself. There is effectively no alternative: HDF4 is a format on its way out, and apart from the owner's library and this wrapper around it there is nothing in the freely available space that reads it completely.

Feature comparison

HDF4 and HDF5 share nothing but three letters. Where HDF5 has a superblock, B-trees and named objects, HDF4 has a plain linked list of data descriptor blocks: a count, the offset of the next block, and twelve-byte entries of tag, ref, offset and length. Names exist only where an element brings one. The format is simpler than HDF5 and therefore harder to interpret: the structure is there, the meaning is in a table of tag numbers.

What was measured

Two foreign anchors, written by pyhdf and thus by the HDF Group's own HDF4 library: sd.hdf (3320 bytes) with two scientific data sets and vd.hdf (396 bytes) with one Vdata table. Both read through Hdf4File. This makes it one of the better fixtures in this collection: the files come from the reference library.

The numbers are right

sd.hdf dataset 2float32[3][4], values 0, 1.5, 3.0, 4.5, 6.0, 7.5, …[3, 4] float32, values equal value for value

The inventory our reader emits for sd.hdf is more precise than what pyhdf says about the file: 200 entries in one DD block, broken down by library version, values, Vdata rows, Vdata headers, Vgroups, number types, dimensions and data groups. For a file behaving unexpectedly this list is where every search starts — and it is the reason why a file that gets "does not work" from an HDF4 reader still yields an account here.

And the names are missing

The measurement uncovered exactly one gap, and it sits in an unexpected place: neither dataset has a name. beschriftung() returns null, einheit() returns null — although the file contains "temperatur", "kanal" and "einheit: K".

The reason is a piece of format history. HDF4 has the tag SDL for a dataset's label — and pyhdf does not use it. Instead it creates one Vgroup of class Var0.0 per dataset carrying the name, and the attributes as a Vdata beside it. Both are the newer route preferred by the SD interface, and both are in the specification. Our reader reads SDL/SDU/SDF and does not look into the Vgroups.

What is remarkable: the information is already read. For the same file Hdf4Inspect shows the Vgroups "temperatur (Var0.0) — 8 member(s)" and "kanal (Var0.0) — 6 member(s)" and the Vdata "einheit — 1 row(s)". What is missing is only the link: from the Vgroup to the dataset it describes. The gap is therefore not reading work but an assignment — and precisely for that reason it stands as an item of its own (H4) and not as "HDF4 can do more than we read".

One small side matter is noticeable: beschriftung() and einheit() return null and not the empty string. For a caller that is the difference between "has no name" and an exception three lines later. The point is noted under H4.

What is hard about the format

The meaning is in a table of numbers. A DD entry is tag, ref, offset, length — twelve bytes without a word. What an element is, is said by the tag number alone, and the mapping is in the developer's guide. A reader without that table sees a well-formed file about which it can say nothing. We carry 35 tags with names and name unknown ones by number — the number is then still information one can look up in the manual.

Two gigabytes, and strictly so. Offsets and lengths are signed 32-bit numbers. The format cannot describe larger files. A negative offset is therefore a format error and not a large file — a reader interpreting it unsigned "to handle large files too" reads on at a random place. That is a place where generosity does harm.

The same thing twice, historically grown. A name may be in SDL or in a Vgroup; an attribute in SDU or in a Vdata. Both are correct, both occur, and which one you meet depends on which interface wrote the file — the old DFSD or the newer SD interface. Section 2.2 is exactly this case in pure form: our anchors use the one route, pyhdf the other.

The chain may point in a circle. The "next block" offset is a number in the file; nothing stops it pointing at an earlier block. We bound the number of blocks and report it. Without that bound a reader on a damaged file reads until memory runs out.

What is good: self-description without an index. There are no B-trees, no heaps, no fractal structures — a linked list, and everything is in it. Whoever has the tag table can read an HDF4 file with a hex editor. With HDF5 that is hopeless and was a deliberate advance; with HDF4 it is the reason thirty-year-old satellite holdings are still accessible today.

Our open gaps — this is the work

Since 2026-09-27 nothing is left here — H6 stands under 5.3.

Deliberate decisions — nothing to do

H2 (decided) — A negative offset is an error

See section 3. Offsets are signed and the file cannot exceed two gigabytes. Interpreting one unsigned "to handle large files too" would turn a reported format error into silent reading on at the wrong place.

H9 (decided) — Writing

pyhdf writes HDF4 and supplied this document's foreign anchors. This module reads. Hdf4Schreiber in the test bench builds fixtures — including ones with cyclic chains and negative offsets — it is test equipment, not an output path.

Properties of the format

H6 (property) — Raster images — closed on 2026-09-27

Hdf4Bild reads all three generations: the GR interface (one Vgroup RI0.0 per image with a name, dimension record ID, data RI, palette LUT with LD, attributes as Vdatas of class RIATTR0.0C — always named RIATTR0.0N, the attribute name is the field name), the raster image groups RIG of the old DFR8/DF24 interface, which GR writes in addition for 8-bit images with one or three components (the same image then appears twice in the inventory and is listed once), and the HDF 3.0 tags (ID8, RI8/CI8, IP8) when no group covers them. Interlace by pixel, line and plane is reordered to pixel; compression as a special element (RLE, deflate) like any other element, plus the old RLE from the dimension record (compression tag 11) — a different method from the new one: a run counts c & 0x7F times, not + 3. IMCOMP and JPEG are named. uchar8, as DFR8 writes it, is computed as an unsigned byte. Through Datenquellen.oeffne each image becomes a table with the axes zeile and spalte and one column per component, the palette a table <bild>.palette with rot, gruen, blau; file attributes appear as findings. Measured on two files written by the HDF4 library 4.2.14 itself — the libdf bundled with pyhdf 0.11.7, via ctypes (pyhdf itself has no GR interface): Hdf4anker.grBilder() (eight images: 8-bit with palette, three components, 16-bit, passed line-interlaced, RLE, deflate, floating point, little-endian) and Hdf4anker.r8Bilder() (DFR8 uncompressed and RLE, DF24 in all three interlaces); build script and the library's account in test/proben/h6_gr.py, h6_auskunft.txt. Three variants derived per the specification: groups set to the null tag (then RI8/CI8 carry), tief16 with representation 4 and swapped bytes, a dimension record with IMCOMP.

H10 (open there) — The GR interface forgets little-endian byte order

Measured on klein16 in Hdf4anker.grBilder(): GRcreate with DFNT_INT16 | DFNT_LITEND. The HDF4 library 4.2.14 stores the bytes little-endian (e8 03 for 1000) but writes the default representation into the number type (01 16 10 00, representation 0) — and itself reads back −6141 instead of 1000 with GRreadimage. We follow the file as the library does and return the same numbers; the writer's intent is nowhere in the file. Whether the GR interface admits DFNT_LITEND at all has not been checked — hence fremd and not fremdfehler.

H3 (property) — Special forms — compressed, chunked, external: closed on 2026-09-25

The three special forms found in real holdings are now read, following the header layouts of the HDF4 library (hcomp.c, hchunks.c, hextelt.c): compressed with the methods none, RLE and deflate (an ordinary zlib stream, inflated with our own Zlib); chunked, also with compressed chunks — the chunk table is a Vdata with fields origin, chk_tag, chk_ref, edge chunks are stored full size; external in a side file next to the HDF file. Measured on Hdf4anker.sonderformen() (pyhdf 0.11 over the HDF4 library, chunked via SDsetchunk) and on the existing hdf4_muster.hdf, whose deflate dataset used to be rejected and now shows the values hdp names. Still named: szip, N-bit, skipping Huffman, linked Vdata, buffered, compressed raster. Found and fixed on the way: with linked blocks the first block has the length of the original element, not the block length (hblocks.c). The reader always advanced by the block length; the chunk table, whose first row sat alone in the first block, then yielded only zeros.

H4 (property) — Names and attributes from the Vgroups — closed on 2026-09-07

HDF4 has the tag SDL for a dataset's label. The HDF Group's own HDF4 library does not use it when writing through the SD interface. It creates one Vgroup of class Var0.0 per dataset: it carries the name, names the Dim0.0 Vgroups of the axes and holds the attributes as Vdatas of class Attr0.0 beside it. Both are in the specification, and both are the newer route.

A reader that knows only the old tags does not stand out doing so. The values are right, the dimensions are right, the type is right — only the label is missing, and a missing label looks like a file without a label. That is exactly why this item stood here and not in a defect list.

The old tags come first. If an SDL is there, it holds. Preferring the new route skips a statement somebody wrote down. And units is the unit, another attribute name is not: the anchor deliberately carries a dataset with the attribute einheit="Pa" — to a German-speaking reader that sounds like a unit and is none. Choosing by sound gets it wrong for every file with a self-chosen attribute name.

Done along with it: beschriftung() and einheit() now return the empty string instead of null. null is the same value as "not read" and forces every caller into a check he forgets.

Four mutation checks, all red — the fourth only after a new anchor. "Every Vgroup is an axis" stayed green at first: in sd.hdf a Var0.0 Vgroup names nothing but Dim0.0 Vgroups. Instead of discarding the mutation, an anchor was added — sd2.hdf, extended by an ordinary Vgroup through pyhdf's V interface and thus written by the library again. After that it is red. A mutation check that stays green does not measure the reader but the reach of the anchor.

H5 (property) — Vdata values — closed on 2026-09-07

Hdf4Vdata.werte() unpacks the rows by the field descriptions: one list per row, one value per field. The reference values are pyhdf 0.11.7's on the same file — [[0.0, 1013.0], [0.5, 1012.5], [1.0, 1011.75]].

Every field carries its own offset, and it need not follow on seamlessly. Summing the field widths reads past the mark from the second field onwards for every Vdata with padding — and the numbers that come out are numbers. The anchor does not cover this trap, and that is stated here so it does not vanish into what is covered: pyhdf writes the fields contiguously, zeit at 0 and druck at 8. The row is therefore evidenced on one side only.

Two smaller finds while building: a character field is one string, not n characters — reading it row-wise turns "Kelvin" into six values. And a Vdata with zero rows is legal: the SD interface creates one such marker per dataset (SDSVar). Its descriptor is there, offset and length are -1. Until 2026-09-07 access to it threw "Zugriff ausserhalb der Datei: Versatz -1, Laenge -1" — a message that sounds like a broken file and describes an intact one.

H7 (property) — Annotations — closed on 2026-09-07

The earlier text of this item was wrong. It said "we read the short ones and skip the long ones"; Hdf4Annotation.alle has always read all four tags — FID, FD, DIL and DIA — and the long file annotation (FD) was even tested. Untested was only the long object annotation (DIA).

It is tested now: the same four-byte reference in front, the same branch in the reader, 87 characters of text.

Why there is no foreign anchor for it. pyhdf 0.11.7 has no AN interface — the module is missing from the package, and the lower-level hdfext layer offers no AN… function either. A file with a long object annotation therefore cannot be produced with the reference product available here. The test case rests on our own writer, and the foreign column of those two rows stands at - rather than yes — not measured is not the same as cannot.

H8 (property) — The route through the format detection — closed on 2026-09-07

Datenquellen.oeffne(Path) now yields tables for HDF4 instead of a message: Langform.ueberHdf4. One table per scientific dataset, with its axes and a value column; one table per Vdata, with a row axis and one column per field.

It came after H4, and that was the point. Without the names from the Var0.0 Vgroups the tables would be called datensatz2 and datensatz4 — a table whose name is a serial number does not answer the question "what is in this file". The message that stood here before was better than that.

Not every Vdata is a table. The SD interface also stores its dimension values, its attributes and its dataset markers as Vdatas. Emitting them appends eight tables nobody wrote to a file with three datasets — and what they say already stands elsewhere: the dimensions as axes, the attributes as properties. They are therefore left out, and that they are left out is stated as a finding.

A dataset in a special form this reader does not resolve — szip, N-bit, buffered or compressed raster data — gets no table with invented numbers but a finding naming the special form in plain words. Compressed (none, RLE, deflate), chunked and external are read since 2026-09-25 (H3).

Until then the Langformprobe recorded that this view does not exist, and it fell over when the gap was closed. That is the right direction: a test that records a gap must fall over when the gap is closed.

H1 (property) — The chain may point in a circle

See section 3. We bound the number of DD blocks and report reaching the bound; pyhdf relies on the C library. A fixture for it is built by Hdf4Schreiber, because such a file cannot be obtained anywhere else.

The Java implementation — where this reader stands among its own kind

Why this section. Every other comparison in this module measures against a tool in a different language. That is good against misunderstandings of the format and says nothing about where this reader stands among its own kind. What matters is the distinction between a pure reimplementation in Java and a wrapper around the original C library: only the reimplementation solves the same task under the same conditions as this reader; a wrapper calls the original.

A pure Java reimplementation does exist, and it is a surprise: netcdf-java has read HDF4 and HDF-EOS2 since version 4.0.09 explicitly as a "100% Java library" without the C library. The HDF Group's official Java products by contrast are JNI wrappers around the C library — their own documentation says so.

There is therefore a genuine Java reference for HDF4, and it is already on the machine (netcdfAll-5.10.0.jar). A measurement against it is the next sensible step for this document — it is still outstanding and is not claimed here.

How solid this is. Researched on 2026-09-06 via web and GitHub search; Maven Central's search API was blocked at the time, so a systematic artefact search was not possible. "Nothing found" is therefore not the same as "nothing exists" — a little-visible or in-house implementation would not be discoverable this way. What stands here is the state of an honest search and not a claim of completeness.
