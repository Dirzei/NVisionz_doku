PLOT3D — comparison against the NASA manual and against VTK

As of: 2026-09-07
Our implementation: envisionz.fileformats.plot3d.Plot3dQuelle with Bauart, read-only, no third-party library
Specification: PLOT3D User's Manual (NASA TM 101067), appendix "Grid and solution file formats" — public; references give record orders
Compared against: VTK 9.7 (vtkMultiBlockPLOT3DReader, including SetQFileName, SetFunctionFileName and SetTwoDimensionalGeometry)
Test bench: envisionz.fileformats.Plot3dprobe — 120 checks, one foreign anchor and five fixtures measured against VTK 9.7, ten counter-tests

The reference implementation. VTK by Kitware is the de facto core of scientific visualisation. For PLOT3D it is an independent reimplementation: the format goes back to 1982 and the work of Pieter Buning at the NASA Ames Research Center. Kitware's own source comments record that PLOT3D files are often not unambiguously classifiable at the byte level — the same observation that forces sixteen variants on this reader too.

Why this one. Because for PLOT3D there is no authoritative implementation and there cannot be one: the files carry no statement of which of the sixteen variants they are. Kitware's reader records this in its own source comments, and that honesty is exactly what makes it a usable reference — it describes the same problem this reader has to solve.

Feature comparison

PLOT3D is the only format in this collection with no identification at all. No magic at the start, no header record, no version. Precision, byte order, block count, Fortran record markers and IBLANK are stated nowhere — they follow solely from which combination fits the file size. A reader assuming a default here reads nonsense for every other file and notices only when the coordinates look obviously wrong.

What was measured

One foreign anchor: einblock.xyz, written by VTK itself, 108 bytes for a grid of eight points. It was read through vtkMultiBlockPLOT3DReader and through our reader.

The result, and why it is not what it looks like

VTK reads the file and finds eight points. Our reader via the general route Datenquellen.oeffne(Path) rejects it. At first glance that looks like our gap. It is one, but a different one than it looks like.

Datenquellen.oeffne(Path) recognises a format by its first bytes. PLOT3D has no first bytes that mean anything — the file begins with a number, and any number is allowed. There is no way to distinguish a PLOT3D file from an arbitrary heap of bytes short of computing through the file size. That is exactly what Plot3dQuelle.oeffne(Path) does — the named route by which this format is to be opened and by which Plot3dprobe opens it. The general route refuses because format detection must not be allowed to guess.

VTK has the same problem and solves it differently: vtkMultiBlockPLOT3DReader is explicitly selected and told the variant through switches (SetBinaryFile, SetMultiGrid, SetHasByteCount, SetDoublePrecision). Set them wrong and you get numbers without a warning. Our reader computes them and reports when several fit. Row P4 therefore stands at ● for us and – for the reference: VTK has no general route by which the format could be opened without prior knowledge.

What the variant computation actually achieves

For einblock.xyz — eight points, one block — several variants fit the file size. Our reader reports that and takes the first. That is honest and still a statement one has to check: for tiny grids the file size is too little information. For a grid of ordinary size — a hundred thousand points — exactly one combination fits, and then the computation is not merely a hint but a proof.

What is hard about the format

There is nothing to recognise. No format in this collection is so defenceless against confusion. A 108-byte .xyz file may be a PLOT3D grid, a point-cloud text file or a leftover. All a reader has is the file size and arithmetic.

The coordinates are stored one after another, not side by side. All x of a block first, then all y, then all z. Reading them point-wise gives a grid that looks like a tangle — the same trap as in Exodus and Ensight, but here without a dimension name to give it away.

Fortran record markers are data that are not data. A Fortran program brackets every record in two four-byte lengths. A C program does not. Both write files with the same extension. Whoever takes the markers for payload reads the first coordinate as a record length — and gets a number of order 10⁻⁴⁰.

IBLANK is invisible until it is missing. If present, an integer follows the coordinates for every point; if absent, the next block follows. The difference is a four-byte shift per point, and the file stays exactly as large under both readings if the block count is guessed correspondingly differently. That is why the variant computation must try all combinations and not take the first that fits.

What is good: the block structure itself. A cuboid of points with ni × nj × nk is the simplest conceivable description of a structured grid, and the indices run exactly as the manual says. Once the variant is settled, reading is trivial. The whole difficulty sits in the first twenty bytes that do not exist.

Properties of the format

P2 (property) — Two axes — closed on 2026-09-07

PLOT3D has a two-dimensional form: two numbers in the block dimensions, two coordinates per point, and in the solution four flow quantities instead of five. It is read; since 2026-09-07 the number of axes is part of the variant and is computed along with everything else.

There is no k column and no z column. VTK delivers a two-dimensional file as a grid with nk = 1 and z = 0 — that is its view, because its data structure is always three-dimensional, and for a viewer that is right. For a file-inspection tool it is not: a column of zeroes is a statement about the file that the file does not make. Whoever wants to know what is in the file should not have to guess whether the zero is there or invented.

The price is recorded in P6: the number of possible variants has risen from thirty-two to a hundred and ninety-two, and that makes detection more ambiguous.

P3 (property) — Solutions and functions — closed on 2026-09-07

A grid .xyz usually has a solution .q beside it and sometimes a function file .f. Both are read. The solution delivers per point density, one momentum per axis and energy; the function file any number of quantities f1, f2, … A grid without the solution on it was exactly half of what PLOT3D files exist for.

Three traps, and all three are silent. First: a solution file has two records per block — first four properties (Mach number, angle of attack, Reynolds number, time), then the quantities. Skip the first and you read the flow shifted by sixteen or thirty-two bytes. Second: the four properties stand in the same width as the quantities — at double precision therefore eight bytes each. At single precision the difference never shows, and that is exactly why an anchor at double precision is there. Third: a function file has one number more in the block header, saying how many quantities follow; miss it and you read the next block's dimensions shifted by one place — and get numbers that look like dimensions.

And the quantities stand one after another, not side by side — first all densities of the block, then all x-momenta. The same trap as with the coordinates, and it is more dangerous here: a wrongly read coordinate gives a tangle one can see; a wrongly read density gives a number that looks like a density.

The names are the manual's, and they are conservative: the momentum is ρu and not u. Read them as velocities and in any flow with varying density you get something else — and the result still looks like a velocity. VTK calls them Density, Momentum and StagnationEnergy and means the same numbers; every expected value in this probe is its.

P6 (property) — The price of completeness: a hundred and ninety-two variants

Until 2026-09-06 there were thirty-two possible variants; since P2 and P3 there are a hundred and ninety-two. That is not a gain in convenience but one in ambiguity: the more forms are allowed, the more often two fit the same file size. A grid of two by two by one is 88 bytes — and the same 88 bytes also work out as a two-dimensional C solution.

Against that stand two rules, in this order. First: a verified interpretation beats an unverified one. In Fortran unformatted the length of every record stands before and after it, and both must agree — the file confirms the reading. In C binary nothing of the kind is there; the only check is that the size works out. Second, and only then: the file extension may decide between equally well verified readings.

The order is the point. Put the extension above the check and you read a flawless Fortran grid as a derived C solution merely because someone renamed the file — and in fluid dynamics files are renamed constantly. Conversely there is exactly one case where the extension really decides: when all fitting readings are unverified. A C-binary grid of seven by one by three, 264 bytes, is a three-dimensional grid as .xyz and a two-dimensional solution as .q — the same bytes, and nothing in them says which is right. The file name is then the only thing left.

And because that is so, the reader says it: for every variant without record markers there is a finding stating that the only check was the file size and nothing in the file confirms the reading. That is the most honest statement this format permits.

P4 (property) — No route through the general format detection — settled on 2026-09-06

The item stands in substance and is nevertheless no longer a gap. A PLOT3D file carries no magic: it starts with a bare block count, which is an ordinary number. Formaterkennung therefore fundamentally cannot recognise it — and should not: whoever infers a format from a leading number recognises every numeric file as PLOT3D. That is a property of the format, not an omission of the reader.

What was really missing was the message, and that is built. Until now Datenquellen.oeffne(datei) ended with "for unknown there is no reader here" — a dead end although the route existed. Now it names it: that there are formats without magic, that PLOT3D is one, and that Datenquellen.oeffne(datei, Format.PLOT3D) works. The probe measures both — that detection really does fail (otherwise it would be checking a message nobody sees) and that the named route actually carries (otherwise the message would be a false trail).

P1 (property) — No identification — the variant has to be computed

See sections 2 and 3. The difference between the two implementations is not whether they handle the format but who determines the variant: with VTK the user via switches, with us the arithmetic via the file size. Both routes can go wrong, but only one notices: a file to which no combination fits we reject; a VTK reader with wrongly set switches delivers numbers. That several variants can fit we report — that is the honest limit of the method and is worked through in section 2.2.

The Java implementation — where this reader stands among its own kind

Why this section. Every other comparison in this module measures against a tool in a different language. That is good against misunderstandings of the format and says nothing about where this reader stands among its own kind. What matters is the distinction between a pure reimplementation in Java and a wrapper around the original C library: only the reimplementation solves the same task under the same conditions as this reader; a wrapper calls the original.

No Java implementation found. The known readers are Fortran and C++; the C++ reader vtkPLOT3DReader is reachable from Java only through the JNI wrapper of the VTK wrappers. That fits the finding in section 2: the format carries no magic, and whoever wants to read it must either know the variant or compute it — which is what this reader does.

How solid this is. Researched on 2026-09-06 via web and GitHub search; Maven Central's search API was blocked at the time, so a systematic artefact search was not possible. "Nothing found" is therefore not the same as "nothing exists" — a little-visible or in-house implementation would not be discoverable this way. What stands here is the state of an honest search and not a claim of completeness.
