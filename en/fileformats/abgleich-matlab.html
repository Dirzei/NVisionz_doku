MATLAB .mat — comparison against the format document and against scipy

As of: 2026-09-05
Our implementation: envisionz.fileformats.matlab.MatQuelle with Matelement, Matart, read-only, no third-party library
Specification: MAT-File Format (MathWorks), chapter "Level 5 MAT-File Format" — public; references give field and element names
Compared against: scipy 1.17.1 (scipy.io.loadmat/savemat)
Test bench: envisionz.fileformats.matlab.Matprobe — 254 checks, ten foreign anchors, eleven counter-tests

The reference implementation. scipy is scientific Python's collection of numerical methods, carried by an open community. scipy.io.loadmat is an independent reimplementation — no MathWorks code in it and no binding to a MATLAB library. scipy draws and documents its own boundary: versions 4, 6 and 7 through 7.2 are read, 7.3 explicitly is not, because that is an HDF5 file and scipy ships no HDF5 reader.

Why this one. Because the norm belongs to MathWorks and its implementation is not freely obtainable. scipy is the most widespread independent reimplementation and states its boundary explicitly instead of hiding it — which is what makes it usable as a reference: one knows where it stops. A difference between two reimplementations is a finding here, not a verdict.

Feature comparison

A .mat is two different files under one extension: level 5 is a byte format of its own with a 128-byte header and a sequence of data elements; version 7.3 is plain HDF5 with a convention over it. This reader reads level 5. A 7.3 file is recognised and named — it goes through this toolkit's HDF5 route, and the message says so.

What was measured

Nineteen fixtures, in both directions. Ten foreign anchors from scipy 1.17.1 through our reader and nine of our own from Matschreiber through scipy. The reverse direction paid off here as in no other format of this collection: it found a bug that none of the ten anchors would have exposed.

The bug only the reverse direction showed

All ten scipy anchors read; every value agreed. In the reverse direction scipy then rejected two of our nine own files, precisely the two compressed ones: OSError: could not read bytes.

The first suspicion had to be our writer — and it was, but not only. The cause: a miCOMPRESSED element is not padded to eight bytes. Every other one is. That is nowhere stated this plainly in a format document, and it can be measured against a file written by scipy: three compressed variables sit at offsets 128, 180 and 236, and the file is 281 bytes long — not even divisible by eight.

The same bug was in our reader. And it would not have surfaced: of the ten anchors only one has a compressed element at all, and it has exactly one variable. The four-byte overshoot then lands past end of file, the loop stops anyway, and the result is right. Only with two compressed variables does the jump land in the middle of the next element — and what stands there is a valid number.

Both places are corrected, with the date and the measured reason in the source. A tenth foreign anchor was added — a scipy file with three compressed variables — and a counter-test that puts the padding back has gone red since. Without the reverse direction the bug would eventually have shown up in a file from a foreign hand as "reads nonsense", and nobody would have known where.

Our nine through scipy

scipy reads the six healthy ones and delivers the same numbers — including the two in big-endian byte order, which scipy returns as >f8 and >i4. That is the only measurement able to check this half of our reader at all: an MI file arises on a machine with that byte order, and there is none here. Without our own writer it would stay unmeasured — and it is exactly the half one has least in mind.

scipy rejects the three sick ones: ValueError: Unknown mat file type, version 0, 1 for the wrong endian indicator, OSError: could not read bytes for an element reaching past end of file, and TypeError: Expecting miMATRIX type here, got 524293 for a short tag claiming more than four bytes. The first message is as good as ours; the other two are Python errors from the inside — the number 524293 is a raw tag word and no statement about the file. That is not a bug in scipy but the difference between a library for computing and a reader for looking.

What is hard about the format

The tag comes in two sizes, and that is stated nowhere. The usual one is eight bytes. For elements of up to four bytes there is a short form of four bytes, recognisable only by the top two bytes of the first word being non-zero. No field says which form is present. Overlook it and you are permanently off from the first short element on — and short elements are the normal case: every matrix's dimensions and every name of up to four characters are stored that way. The counter-test for it crashes the probe after nineteen checks.

Everything is column-major. MATLAB comes from Fortran: a matrix is stored column by column. With a square matrix a mix-up goes unnoticed — you get the transpose, and that looks like a matrix. That is why the anchor nichtquadratisch is a 2 × 3 and not a 2 × 2. The same holds for mxCHAR: an ['ab'; 'cd'] is stored as a c b d.

Two number spaces that look alike. The element type (miINT8 … miMATRIX) and the array class (mxDOUBLE, mxCHAR, …) both count from one, both reach into the twenties, and both appear as a bare number. A 6 is miUINT32 as an element type and mxDOUBLE as a class. That is why the two tables sit separately in Matart, with different prefixes.

Almost everything is compressed — and the exception to the padding rule sits exactly there. Since version 7 MATLAB writes every variable as miCOMPRESSED. Whoever does not inflate it sees a file full of unknown elements and not one variable. And whoever inflates it but rounds up to eight as with every other element reads wrong from the second variable on. See section 2.1 — that is the bug made and found during this work.

What is good: the endian indicator. Two characters at the end of the header, IM or MI, read as a 16-bit number — a self-description trick that needs nothing else and cannot be misunderstood: if 0x4D49 comes out, the file was written big-endian. In PLOT3D the byte order has to be computed from the file size, in Gmsh from a check value, in FITS there is no choice at all. Here it simply stands there, in two characters.

The items

The Note column names the kind in front of the identifier. Only the gaps are work.

Our open gaps — this is the work

Deliberate decisions — nothing to do

L11 (decided) — A matrix becomes a table like a NumPy array

One axis gives wert, two give s0, s1, …, three or more the long form with i0, i1, … . The same rule as in NpyQuelle and FitsQuelle — not out of convenience, but so that a user touching three formats does not have to learn three rules. The row stands at – for the reference: scipy returns a numpy array and forms no tables.

L15 (decided) — Same-named variables get #2 and a finding

Two variables may carry the same name; the format does not forbid it. Merging them or swallowing the second would be the quieter and the wrong answer. scipy keeps the last one — the row stands at – there because that is not comparable behaviour but the consequence of returning a dictionary.

L18 (decided) — Writing

scipy writes .mat and supplied this document's ten foreign anchors. This module reads. Matschreiber in the test bench builds fixtures — above all the big-endian ones that could not be obtained anywhere else — it is test equipment, not an output path.

Properties of the format

L13 (property) — Structures, cell arrays and objects — closed on 2026-09-07

Closed. mxSTRUCT, mxCELL and mxOBJECT are unfolded, recursively. In real MATLAB holdings the structure is the usual packaging: a measurement comes as daten.zeit, daten.kanal, daten.werte and not as three variables. This was therefore the gap that hit most often.

What a structure looks like in the file. After the name comes one miINT32 with the field-name length — a fixed width to which all names are padded. Then a miINT8 with all names in sequence, each in that width. And then field count times element count complete matrices, element-wise outside, field-wise inside: with two elements and three fields the three fields of the first element come first, then the three of the second. For an object the class name precedes all that.

And how it becomes tables. A structure is not a table but a collection — it is unfolded. From daten with the fields zeit and werte come the variables daten.zeit and daten.werte; if the structure has more than one element the number is added (daten(2).zeit); a cell array gives z(1), z(2) … That is exactly the notation MATLAB itself uses — whoever knows the file knows the names here too.

The trap is the name slot. A field of a structure carries no name of its own: the name slot in the element is empty, because the name stands in the structure's field-name list. Miss that and you get variables called unbenannt1, unbenannt2 … with the association gone. The anchor verbundTief is therefore nested — the field kanal is itself a cell array — and the mutation "drop the passed-through name" turns five checks red and makes the test abort.

Two anchors from scipy 1.15.3: one with a structure and a cell array side by side, one with a nested measurement (daten.zeit, daten.kanal(1), daten.werte). Plus a cell array with three unlike elements — a number series, a single number, a string — because unlike is the point of a cell array.

L14 (property) — Sparse matrices — closed on 2026-09-07

Closed, and with an explicit decision. mxSPARSE is stored as three arrays: ir gives each value its row number, jc gives for each column the value at which it starts, and pr are the values. That is the common CSC scheme.

The decision that was open: output all positions with the zeros in between, or only the occupied ones? It is only the occupied ones, in long form with the columns zeile, spalte, wert. The reason is not convenience: a sparse matrix is stored sparsely precisely because its full form does not fit in memory. A 100000 x 100000 with a thousand values would have ten billion rows — and 99.99999 per cent of them would be a message about nothing.

jc has one entry more than there are columns — the last is the total number of occupied positions. Counting it gives one column too many; omitting it loses the last. And the column number must come from the starts and not from a counter: the anchor duennGross (5 x 4 with four values) deliberately has an empty second column, that is two equal starts in a row. Whoever counts instead of looking up shifts everything by one column from there — and the values themselves stay right.

L12 (property) — Complex matrices — closed on 2026-09-07

Closed. A complex matrix carries real and imaginary part as two value sections in sequence — not interleaved but one after the other at full length. Both are read. Before, only the real part stood here with a finding attached; in vibration measurement, from which part of this workspace comes, a complex transfer function is the normal case and not a special one.

What comes out is text: 3.0-4.0i. That is the same decision as in the FITS reader for column types C and M, and deliberately so: whoever touches both formats should not have to learn two notations. The alternative — two columns per value — would turn a 2 x 3 into one with six columns, and the shape of the matrix is the information one least wants to lose.

The anchor komplexGross is chosen so that any confusion shows: a pure real part (5+0i), an imaginary part larger in magnitude than the real one (0.5−1.5i), a negative number without imaginary part (−2+0i) and a pair of two equal ones (7+7i). The mutation "do not read the second value section" turns eight checks red.

L16 (property) — Version 7.3 — closed on 2026-09-07

Closed. A .mat from version 7.3 on is HDF5, and this toolkit's HDF5 route already read it — but as HDF5. MatQuelle now reads it with the MATLAB convention on top. Three things are added, and all three change the result and not merely the labelling.

First: the HDF5 signature is not at the start of the file. A 7.3 has a 512-byte "user block" carrying the same description text as the header of a level-5 file — the HDF5 signature begins only behind it. Whoever looks only at zero takes every 7.3 for a broken level 5. That is exactly what this reader did until today, and its message about it was especially misleading: it said a 7.3 carries the HDF5 signature.

Second: MATLAB_class. An attribute on every dataset says what it is — char, logical, double, int32 … Without it a string comes out as a column of numeric codes: 77, 101, 115 … instead of "Messreihe". The mutation for it turns six checks red. Third: the axes are reversed. MATLAB stores column-major, HDF5 row-major; on writing the axis order is turned around. A 3 x 4 sits in the file as 4 x 3 — miss that and you get the transposed matrix, which on a square one looks like the right one. The anchor is therefore not square.

The anchor comes from hdf5storage 0.2.2 and not from scipy — scipy does not write 7.3. This is the only item in this collection for which a second foreign writing tool was needed, and it stands here because an anchor one has built oneself confirms one's own understanding instead of testing it.

L17 (property) — Windowed access — closed on 2026-09-07, with a named limit

Closed for version 7.3. A 7.3 is no longer read whole into memory: the HDF5 dataset stays in the file, and the cursor fetches blocks of a thousand values when it needs them. A measurement series of a few hundred megabytes passes through — the same capability scipy has via h5py.

Not possible in level 5 with compressed elements, and that is not negligence but a property of zlib. Since version 7 MATLAB writes every variable as miCOMPRESSED, that is as a zlib stream. A zlib stream cannot be entered in the middle: to read the millionth byte, the 999999 before it must pass through the decoder. Windowed access there would not be a shortcut but the same work with more bookkeeping. For uncompressed level-5 elements it would be possible; it is not built, because an uncompressed level-5 file is in memory as a whole anyway — it is read whole, and for it that is the only way to find the element headers.

The row for level 5 therefore stays at ⛔, and at the reference product too: scipy cannot do it there either, and for the same reason.

L1 (property) — The endian indicator

See section 3. IM or MI, read as a 16-bit number. The cleanest route a format can take for this question.

L2 (property) — Big-endian really does occur

And here it can only be measured with our own writer — see 2.3. Of this probe's twenty-two checks in that section, thirteen concern only this half of the reader.

L3 (property) — The tag in two sizes

See section 3. This module's sharpest counter-test: it crashes the probe after nineteen of 254 checks.

L4 (property) — miCOMPRESSED is not padded

See 2.1 and 3. The exception to a rule that otherwise holds without exception — and it goes unnoticed in a file with a single compressed variable. That both implementations get it right today is why this row stands under property and not under gap; that ours got it wrong until 2026-09-05 stands in 2.1.

L5 (property) — Almost everything is compressed

Since version 7 MATLAB writes every variable as miCOMPRESSED. Whoever does not inflate sees an empty file full of unknown elements.

L7 (property) — The class sits in the lowest byte of the flags word

Above it the flags for complex, global and logical. The counter-test shifting the byte by eight bits goes red six times.

L8 (property) — Column-major storage

See section 3. The second sharpest counter-test: twenty failures.

L9 (property) — Eight integer classes, and half of them are unsigned

The anchor typen carries, in every unsigned class, a value that would come out negative as a signed number: 200 as uint8, 60000 as uint16, 4 · 10⁹ as uint32. Three counter-tests, three red checks.

L10 (property) — Characters are stored column-major too

An ['ab'; 'cd'] is stored as a c b d. Whoever reads the characters in sequence gets acbd.

Findings against the reference implementation

L6 (open there) — Two broken files without a statement about the file

An element reaching past end of file is answered by scipy with OSError: could not read bytes; a short tag claiming more than four bytes with TypeError: Expecting miMATRIX type here, got 524293. The number 524293 is a raw tag word. In both cases we name the offset and what was expected there. For the wrong endian indicator, by contrast, scipy's message is as good as ours, and that is stated here expressly. No bug in scipy was found in this measurement — on the contrary: scipy uncovered a bug of ours (see 2.1), and it deserves the mention.

The Java implementation — where this reader stands among its own kind

Why this section. Every other comparison in this module measures against a tool in a different language. That is good against misunderstandings of the format and says nothing about where this reader stands among its own kind. What matters is the distinction between a pure reimplementation in Java and a wrapper around a C library: only the reimplementation solves the same task under the same conditions.

A pure Java reimplementation exists for level 5: HebiRobotics/MFL (100% Java, core module without external dependencies), successor to matfilerw and JMatIO. Not measured — the jar is not present yet. It would be the most obvious outstanding measurement for this document, since MFL and this reader solve exactly the same task.

For version 7.3 the same holds as for us: MFL and matfilerw exclude it explicitly. A 7.3 file is HDF5 with MATLAB's own conventions, and as things stand nobody interprets those in Java — whoever wants to read them takes an HDF5 library and writes the conventions themselves. Item L16 describes exactly this situation, and it is therefore not a peculiarity of this reader but the state of Java as a whole.

How solid this is. Researched on 2026-09-06 via web and GitHub search; Maven Central's search API was blocked, so a systematic artefact search was not possible. Where it says "not measured" below, it says so explicitly — a named library is not yet a measured one.
