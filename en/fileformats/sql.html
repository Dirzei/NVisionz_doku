SQL over every data source – background

How a SELECT query is evaluated over dBASE, SQLite, Parquet and the other formats: operator precedence, three-valued logic with NULL, LIKE, integer arithmetic as in SQLite, aggregation and skipping row groups.

What this is about: a query language without a database

Every readable format offers the same view: tables of fields and a cursor over the records. On top of that, envisionz.fileformats.sql evaluates a subset of SQL – SELECT with WHERE, GROUP BY, HAVING, ORDER BY, LIMIT – without touching the file. For SQLite this explicitly does not mean the built-in engine: reading uses the own reader, evaluation the own code. Because results are compared with those of SQLite, its rules apply, including where they surprise.

Precedence

The parser is recursive descent with one level per precedence, from weak to strong:

OR≺AND≺NOT≺comparison, LIKE, IN, BETWEEN, IS NULL≺+,−≺×,/,%≺sign.\text{OR} \ \prec\ \text{AND} \ \prec\ \text{NOT} \ \prec\ \text{comparison, LIKE, IN, BETWEEN, IS NULL} \ \prec\ +,\,- \ \prec\ \times,\,/,\,\% \ \prec\ \text{sign} .

So a OR b AND c equals a OR (b AND c), and NOT a AND b equals (NOT a) AND b. A precedence error produces no error message but rows – just the wrong ones; it is therefore tested on the tree, not on the result.

Three truth values

SQL knows true (T), false (F) and unknown (U). Every comparison with NULL is U, even NULL = NULL. The connectives follow Kleene's strong logic:

In short: p∧q=min⁡(p,q)p \wedge q = \min(p, q), p∨q=max⁡(p,q)p \vee q = \max(p, q), ¬p=1−p\neg p = 1 - p with F = 0, U = ½, T = 1. WHERE keeps only rows with T. Hence NOT (value > 0) does not bring back a row whose value is NULL: ¬U=U\neg U = U. Whoever counts NULL comparisons as false gets too many or too few rows on every table with gaps.

LIKE

% matches any number of characters (including none), _ exactly one. Case is ignored only in the ASCII range, as in SQLite: 'ABC' LIKE 'abc' is true, 'ä' LIKE 'Ä' is not. Several % in a row act as one. Matching is greedy with two pointers: only the last % and the text position belonging to it are remembered; when a character does not match, the pattern pointer jumps back behind that %, and the % swallows one more character. A later % makes every earlier jump-back point unnecessary – what it has found before it cannot be improved by another split. The match therefore ends after at most

(|t|+1)(|m|+1)(|t| + 1)\,(|m| + 1)

steps for text t and pattern m, without recursion. Until 2026-10-25 every continuation was tried recursively at each %; 30 times %a against 40 times a and one b practically never finished.

Arithmetic as in SQLite

Two integers give an integer: 7 / 2 is 3, truncated towards zero, −7/2=−3-7 / 2 = -3; the remainder has the sign of the dividend, −7mod2=−1-7 \bmod 2 = -1. As soon as a floating-point number is involved, the computation is floating: 5.0 / 2 is 2.5. An overflow (including −263/−1-2^{63} / -1) becomes a floating-point number instead of silently wrapping; division by zero gives NULL.

Aggregation

A query aggregates if it has GROUP BY or if an aggregate – COUNT, SUM, AVG, MIN, MAX – appears anywhere in the selection or in HAVING. “Anywhere” means in every subexpression, including the bounds of BETWEEN, the list of IN and the pattern of LIKE: SELECT 5 BETWEEN MIN(w) AND MAX(w) is one row, not one per record. COUNT(*) counts all rows, COUNT(column) only those without NULL; SUM, AVG, MIN, MAX skip NULL.

Skipping row groups

From a WHERE condition made of AND-joined comparisons of a column with a number, or a BETWEEN two numbers (other parts are passed over), a preselection is derived: one range per column. A reader with statistics per block (Parquet: smallest and largest value per row group) may skip blocks whose range cannot meet the condition. This is an offer, not a condition: WHERE is still evaluated on every row delivered, and LIMIT counts after skipping.

What follows

  • Assumptions. One table, one query; no joins, subqueries or window functions – they are rejected by name.
  • The same query over dBASE, SQLite and Parquet gives the same result; this is the strongest test of the evaluator.
  • Without ORDER BY, GROUP BY and DISTINCT the query streams and stops at LIMIT; with one of the three the selection is held in memory.
  • An aggregate may stand anywhere in an expression; whether the query aggregates does not depend on where.

How it is tested

  • Sqlprobe (parsing, precedence on the tree, three-valued logic, arithmetic, aggregation, ordering, three formats, one result) and sql.Auswerterprobe with expectations from the SQLite documentation.
  • TheorieFDprobe tests aggregates in BETWEEN, IN, LIKE and HAVING as well as the LIKE rules; counter-probes shift precedence, NULL comparison, AND with false, integer division and the aggregate search.
  • TheorieG2probe times LIKE with 30 times %a against a limit of three seconds and compares 20,000 random cases with a table computation (dynamic programming); the counter-probe puts the recursive backtracking back.
  • sql.TheorieG2probe runs 59 queries whose results SQLite computed on the same table: groups over two columns, LIMIT a, b and OFFSET, aliases, negated predicates, pre-selection with swapped sides, aggregates in HAVING under NOT, IS NULL, functions and arithmetic, SUBSTR with negative arguments, number notations, syntax errors.

Limits

  • No joins of several tables, no subqueries, no UNION, no window functions, nothing that writes.
  • LIKE has no ESCAPE clause; % and _ cannot be escaped in the pattern.
  • The preselection uses only comparisons and BETWEEN with numbers; OR, NOT and texts remain without preselection.
  • Where the subset deliberately differs from SQLite: ORDER BY sorts only by selected columns (otherwise the query is rejected with a reason instead of silently sorting wrong), OFFSET without LIMIT is accepted, DISTINCT inside an aggregate function is rejected. The postfix form x NOT NULL counts, as in SQLite, as x IS NOT NULL.
