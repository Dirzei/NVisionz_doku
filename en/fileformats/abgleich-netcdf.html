netCDF — comparison against the specification and against netCDF4-python

As of: 2026-09-05
Our implementation: envisionz.fileformats.hdf5.netcdf.Netcdf3Reader for the classic container and NetcdfFile/Hdf5Backed for netCDF-4, read-only, no third-party library
Specification: NetCDF Classic Format Specification (Unidata) and NetCDF-4 / HDF5 File Format — both public; references give header fields and attribute names
Compared against: netCDF4 1.7.4 (Python, linked against Unidata's C library)
Test bench: envisionz.fileformats.hdf5.Netcdf4probe — 53 checks, five foreign anchors; the classic container additionally in Leserprobe

The reference implementation. netCDF4-python is the binding to netcdf-c and is maintained under the umbrella of Unidata (UCAR) — that is, by the owner of the format itself, started by Jeff Whitaker. In climate and geoscience it is the standard route to netCDF files. This measures against the reference implementation, not against a reimplementation.

Why this one. Because netCDF4-python is maintained by the owner itself. One cannot get closer to the norm without being the norm. Every deviation is therefore unambiguously attributable — it is ours.

Feature comparison

"netCDF" is one name for two entirely different byte formats. The classic container (magic CDF) is a standalone, old, very frugal format with a header at the start of the file. netCDF-4 is a convention over HDF5 — the same construction as CGNS. Both carry the .nc extension, both are read by the same library, and they have as much in common as a filing cabinet and a database.

What was measured

Seven fixtures in both directions: two classic files written by netCDF4-python through our reader, and five anchors from Netcdf4anker through both. This makes this format one of the few in this collection whose cross-measurement runs in both directions and across both containers.

The classic files written by netCDF4-python

klassisch.nc (344 bytes, NETCDF3_CLASSIC) and gross.nc (356 bytes, NETCDF3_64BIT_OFFSET) carry the same data: an unlimited dimension zeit, a dimension ort of length four, a double variable temperatur(zeit, ort) with three written records, an integer variable ort and a char variable name. Our reader reads both identically: one table zeit_ort with columns zeit, ort, temperatur and the values 0,0 / 0,1.5 / 0,3.0 …

That the two versions yield the same is the real value of this measurement. Between version 1 and 2 lies only the width of the data offsets — four versus eight bytes — at exactly one place in the header. A reader confusing them still reads the header correctly and is then four bytes off at every variable. In small files that shows up as obvious nonsense; in large ones as a series of numbers shifted by half a cell.

Both times our reader emits the same two findings, and both are honest: the char variable name is skipped (D3), and the classic container has no windowed access (D7).

The five netCDF-4 anchors

Two observations from this are worth recording. First namensgleich.nc: two variable groups over the same dimension set would yield the same table name. We append #2 and report it. A silently merged table would be the worse answer — it would look right. Second reinesHdf5.nc: an HDF5 file without the netCDF attributes is read by us because the substrate can open it; netCDF4-python reads it too but carries the dimensions only partly. The difference is small and is noted in D4.

The finding for reinesHdf5.nc — "HDF5 can do windows: numeric columns are read in blocks of 65536 values, not whole. String columns however whole" — is at the same time the most precise statement about the difference between the two containers this reader makes. Over HDF5 windowed access exists; over the classic container it does not.

What is hard about the format

The interleaved record variables. Variables whose first dimension is the unlimited one do not lie contiguously: all quantities of the first time step first, then all of the second. The stride between two records of one variable is the sum of the record sizes of all record variables. Overlook that and the first variable reads right and every following one reads as a mixture.

And the exception to it. If there is exactly one record variable, its record is not padded to four bytes. A special rule for a special case, a subordinate clause in the specification. Overlook it and everything from the second time step on reads wrong — while the first is right, which lengthens the search by hours. That is the nastiest single sentence in this whole collection of documents.

Two byte formats, one name, one extension. An .nc may be CDF\x01, CDF\x02, CDF\x05 or HDF5. The first four bytes say so — that is the friendly part. The unfriendly one: same library, same API, same tools, and beneath them formats with nothing in common. A reader needs two separate implementations, and one of them can do windowed access and the other cannot. That is a property of the containers, not of the implementation.

What is good: the classic header. Everything is at the start of the file: dimensions, attributes, variables, types and the start offset of each variable's data. After a few hundred bytes a reader knows the whole inventory and can jump to any variable without scanning the file. For a format from the eighties that is a remarkably modern arrangement — and the reason older weather and ocean holdings are almost all in it and still readable.

The items

The Note column names the kind in front of the identifier. Only the gaps are work.

Our open gaps — this is the work

D3 (property) — char variables — closed on 2026-09-07

Closed. In netCDF strings are traditionally char arrays with a length axis as their last axis — station names, units, identifiers. They are now carried as text columns. Whoever wants to know which station number three is, finds it here.

The last axis is not a data axis. A variable name(station, namelen) is not a table of station × namelen letters but a column of station names. Whoever treats the length axis as a data axis gets a table of single characters — formally right and practically useless. The mutation that leaves it in makes the test crash: the text variable then lands in a table with one axis too many.

And it goes into the table of its remaining axes, not into one of its own. Otherwise name and height of the same station would stand in two tables, with the association only through the row number. The anchor therefore carries two text variables and one numeric variable on the same axis; all three stand in the table station.

The padding falls away. netCDF pads shorter names to the full width — with spaces or null bytes — and the padding is not part of the name. The names in the anchor are four, seven and five characters long at a width of eight so that this shows; the mutation that leaves the padding turns six checks red. Written by netCDF4-python 1.7.4 in NETCDF3_CLASSIC format.

Deliberate decisions — nothing to do

D5 (decided) — Two dimension sets, one table name

The table view groups variables by their dimensions: everything over (time, station) becomes one table, everything over (time, depth) another. The name comes from the dimensions, and so it can repeat if two groups use the same dimension names — in netCDF-4 that is allowed, because there dimensions belong to a group.

The name is then extended by the group path, not numbered. A trailing number (points, points2) would be shorter and say nothing; the path says which group is meant, and that is exactly the question someone has who sees two tables of the same name. It is not a gap: there is no case in which a variable would be unreachable.

D7 (decided) — Windowed access — for numbers, not for strings

Both containers deliver windows: netCDF-4 in blocks of 65536 values, the classic one directly via the offset. That is the property that makes a file of twenty gigabytes openable at all — what is asked for is read, not the file.

It does not apply to string columns, and that is decided, not forgotten. A char variable with a length dimension (D3) is assembled as a whole column, because its records only come into being when it is split: the length dimension is not a data dimension, and a block of 65536 bytes almost never lands on a record boundary. Windowed access would have to buffer the remainder and would then no longer be windowed access but a buffer with extra steps. At the sizes at which name columns occur — stations, identifiers, units — that is no loss.

D8 (decided) — Writing

This module reads. netCDF4-python writes, and all seven fixtures came about that way — five written by it, two built by hand and read back by it. A writer here would be a discipline of its own: the classic format requires a header computation over offsets one only knows once all variables are fixed, and netCDF-4 would require an HDF5 writer.

Properties of the format

D6 (property) — Compound types — closed on 2026-09-06

Closed together with LF1, because it was the same cause in the same place: the Langform table view took only the numeric members of a compound and reported the string members as skipped — "the compound member /messreihe.kennung has type string[8] and is skipped". They are now carried as text columns via readMemberString. See docs/hdf5 LF1 for the measurement and the mutations.

Item D3 (char variables in the classic container) stays open: that is a different read path — netCDF-3 has no HDF5 types — and the same cause does not apply there.

D1 (property) — Interleaved record variables

See section 3. Both implementations handle it; it stands here because it is the place a third would fail.

D2 (property) — Exactly one record variable is not padded

See section 3. The special rule easily overlooked, whose effect starts only at the second time step. Both implementations observe it.

Findings against the reference implementation

D4 (open there) — Plain HDF5 is carried only partly

An HDF5 file without the netCDF marker attributes (_Netcdf4Dimid and relatives) opens in netCDF4-python, but it carries the dimensions only partly: datasets without an assigned dimension appear with substitute dimension names. Our reader takes the same route through the HDF5 substrate and carries the shape as it stands in the dataset. The difference is small, it is not a bug in netCDF4-python — the file simply is not a netCDF file — and it is recorded here because in a comparison of two outputs it would otherwise look like our error. No genuine bug in netCDF4-python was found in this measurement.

The Java implementation — where this reader stands among its own kind

Why this section. Every other comparison in this module measures against a tool in a different language. That is good against misunderstandings of the format and says nothing about where this reader stands among its own kind — and that is the question a Java developer asks first. The distinction that matters is between a pure reimplementation in Java and a wrapper around the original C library: only the reimplementation solves the same task under the same conditions as this reader; a wrapper calls the original.

Measured on 2026-09-06 against netcdf-java 5.10.0 — Unidata's Java implementation, that is by the format's own owner, and for the classic container as for netCDF-4 a pure Java reimplementation. Only for writing netCDF-4 does it reach for the C library (via JNA, not JNI); not for reading.

The measurement ran through the HDF5 path (netCDF-4 is HDF5) on five files: all dataset paths, shapes and values agree, without a single divergence. Details in the HDF5 document, section 7 — it is the same run.

The scope is noteworthy: netcdf-java is a large project (GRIB, BUFR, HDF4, Zarr, THREDDS) and reads HDF4 in pure Java as well — among the Java implementations in this collection that is the only one touching HDF4 without a C library.

This measurement lives outside the module, in javavergleich/Javavergleich.java, because envisionz-framework-fileformats has the rule "no foreign libraries" — and it still holds. Only the result goes into the module, with date and version. The single exception is javax.imageio for the image formats: that sits in the JDK and therefore measures along as a permanent probe.
