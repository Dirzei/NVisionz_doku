LMDB data.mdb — comparison against specification and py-lmdb

As of: 2026-09-07
Our implementation: envisionz.fileformats.lmdb.LmdbQuelle, read-only, no third-party library
Specification: LMDB's layout is not published as a document — references give structure names from mdb.c, the Symas implementation
Compared against: py-lmdb 2.3.0 on libmdb
Test bench: envisionz.fileformats.Lmdbprobe — 65 checks, four self-built variants, one anchor written by LMDB itself, five counter-tests

The reference implementation. py-lmdb by David Wilson and Nic Watson is a pure binding to liblmdb — and that is the thing itself: LMDB grew out of OpenLDAP development in 2009 as a replacement for Berkeley DB, written by Howard Chu (Symas). No standard exists outside that code; the implementation is the format definition.

Why this one. Because with LMDB the implementation is the format. No specification exists outside the code, so there is nothing to measure against but the code. py-lmdb passes exactly that code through.

Feature comparison

LMDB is a key-value store, not a table format: one file, one B+ tree, key and value as raw bytes. What is inside is known to the application, not to the file. The table view here is therefore flat and honest: two columns, SCHLUESSEL and WERT, both as bytes.

What was measured

An environment created with py-lmdb 2.3.0: fifty entries in the main database and two in a named sub-database unter, written in two transactions. Read with envisionz.fileformats.lmdb.LmdbQuelle.

Read, values equal — both tables with the right entries. Plus three findings that together describe the file's situation: "meta page 1 is current (transaction 3); page 0 holds the previous state (transaction 2)", "lock.mdb (the lock file) lies alongside. It is not opened and not written; this reader enters itself into no reader table." and "the main database holds 1 named sub-database; its entries are at the same time entries of the main database."

The third finding is the most important and the easiest to overlook: a named sub-database is itself an entry of the main database. Iterating the main database shows its name as a key and its root page as the value — and counts it. Fifty plus one is the right number here, not fifty.

What is hard about the format

There is no format description. LMDB is defined by mdb.c, a file of some ten thousand lines of C. Everything here is derived from that source and from files — the weakest evidence in this entire collection, and the header says so.

The file does not state its layout. Whether page numbers are four or eight bytes wide, and in which byte order they are stored, depends on the machine that wrote it and is stated nowhere in the file. It must be inferred from the first bytes — and this module's test bench produces all four combinations itself, because no real LMDB on a single machine can produce more than one.

Two meta pages, and the newer one wins. Page 0 and page 1 each carry a complete state; which one applies is decided by the higher transaction number. Always taking page 0 reads, depending on chance, the state of the day before yesterday — and the file is perfectly fine.

What is good: the layout is small. One meta page, three page types, one B+ tree. Once the variant is determined, an LMDB file can be read completely without ever having to guess.

The items

The Note column names the kind in front of the identifier. Only the gaps are work.

Our open gaps — this is the work

L2 (decided) — Only the local variant is measured against a foreign implementation

The reader handles all four combinations of word width and byte order, and Lmdbschreiber produces all four — but the measurement against py-lmdb could only hit the one this machine writes. The other three are covered by our own probe and are not measured against a foreign implementation. That is not a gap in the reader but one in the evidence, and it can only be closed with files from other machines.

Deliberate decisions — nothing to do

L3 (decided) — The lock file stays closed

LMDB normally requires a reader to register itself in a reader table inside lock.mdb. We do not — and we do not even open the file. That is this module's read-only principle at its sharpest: a file we want to read is not touched by our wanting to read it. The consequence is that a concurrently writing process does not see us and could reuse pages we are reading. For a tool looking at a file at rest that is the right trade; for a concurrent user it would be wrong. Which is why it is in the findings.

L5 (decided) — Writing, transactions, locking

Out of scope, explicitly. LMDB is a database; this module reads files.

Properties of the format

L7 (property) — Several values per key — closed on 2026-09-07

With MDB_DUPSORT a key may carry several values, and they now come out one at a time. An entry of the database is a pair, and a key with three hundred values is three hundred entries — that is how LMDB counts, and the anchor proves it: mdb_stat reports 306, and this reader delivers 306. Before, it was six.

That was this reader's one gap that yielded silently wrong numbers, and it has exactly the shape one fears: no exception, no finding, no crooked byte — only a number that is far too small and looks like a number. Whoever carries it into an evaluation never notices.

Two forms, and both occur in the same file. For few values LMDB puts them as a sub-page into the same node: a whole page in miniature, with its own header and its own node pointers — and the pointers are relative to the start of the sub-page, not of the page. Relate them to the surrounding page and you read at a place that happens to contain bytes too. For many values LMDB creates a tree of its own and writes its description into the node; then the node additionally carries F_SUBDATA — the same bit as a named sub-database (L4), and only together with F_DUPDATA does it mean something different.

And in both forms the value is the key. The values stand in the sub-page and in the sub-tree as keys with a data length of zero — LMDB sorts them, and sorting goes by the key. Read the data there and you get nothing but empty values, and exactly as many as you expected.

Plus the third form: with MDB_DUPFIXED all values are the same length, and the sub-page carries them packed without node headers — the same layout as a P_LEAF2 leaf, with the length in the pad field. Read it like an ordinary sub-page and you look for node pointers where payload stands.

L8 (property) — The free list — closed on 2026-09-07

FREE_DBI is database zero and lists which pages a completed transaction has released: the key is its number, the value a list of page numbers. freiliste() walks it.

The first number of the list is its length and not a page number. Count it in and you report a page as free that may not exist at all — and at the same time count one real page short. The anchor shows it on two entries: transaction 3 released pages 4 and 3, transaction 4 pages 6 and 5. Both values begin with a two.

Why this matters to anyone: the bytes of deleted entries still stand on those pages. LMDB overwrites nothing on deletion; it hangs the page into the list and reuses it on the next write. Until that happens, everything is still there. The same situation as with SQLite and its free list — only here nobody has lifted it yet.

Nothing is lifted here, and that is deliberate. This method says where the remnants lie; interpreting them is a discipline of its own (with SQLite it is called SqliteReste, and it is three times as long as the reader itself). It begins with knowing where to look — and that is now available.

L1 (property) — The newer meta page wins

See section 3. In the findings we name both transaction numbers, not only the current one — when asking why a file shows an older state than expected, the second number is the answer.

L4 (property) — A sub-database is an entry

See section 2. Both implementations get it right; we additionally say so, because otherwise the entry count is off by the number of sub-databases and nobody knows why.

Findings against the reference implementation

L6 (open there) — Four conditions libmdb does not report

A format version other than 1, a file length that is not a multiple of the page size, a missing second meta page, and two sub-databases with the same name. libmdb reads on silently in the first three cases or refuses without saying why; in the fourth one of the two silently wins. None of the four makes the file unreadable — each of them changes what the result means.

The Java implementation — where this reader stands among its own kind

Why this section. Every other comparison in this module measures against a tool in a different language. That is good against misunderstandings of the format and says nothing about where this reader stands among its own kind. What matters is the distinction between a pure reimplementation in Java and a wrapper around the original C library: only the reimplementation solves the same task under the same conditions as this reader; a wrapper calls the original.

Java access exists, but exclusively as a wrapper and not as a reimplementation — and in this collection that is the clearest result of its kind. lmdbjava embeds unmodified liblmdb through JNR-FFI and ships the native libraries inside the JAR; the older lmdbjni is genuine JNI; LWJGL likewise offers only bindings.

A pure Java reader for the LMDB file format — one that reads the B-tree pages itself — was not found. As things stand, this reader is therefore the only implementation in Java that opens an LMDB file without the C library. That also explains why the comparison in this document runs against py-lmdb and not against something from the JVM world.

How solid this is. Researched on 2026-09-06 via web and GitHub search; Maven Central's search API was blocked at the time, so a systematic artefact search was not possible. "Nothing found" is therefore not the same as "nothing exists" — a little-visible or in-house implementation would not be discoverable this way. What stands here is the state of an honest search and not a claim of completeness.
