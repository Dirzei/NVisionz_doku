Excel workbooks .xlsx — comparison against specification and openpyxl

As of: 2026-09-07
Our implementation: envisionz.fileformats.xlsx.XlsxQuelle, read-only, no third-party library — the ZIP container comes from framework-compress
Specification: ECMA-376 (Office Open XML), part 1 — public; references give part names and XML elements
Compared against: openpyxl 3.1.5 (Python)
Test bench: envisionz.fileformats.Xlsxprobe — 117 checks, four anchors, six counter-tests

The reference implementation. openpyxl comes from Eric Gazoni and Charlie Clark and is maintained by volunteers. It was created expressly out of the lack of a library that could write Office Open XML from Python, initially modelled on PHPExcel. It is an independent reimplementation of the format standardised as ECMA-376 / ISO 29500 and today the default engine pandas uses for .xlsx.

Why this one. Because Excel does not fit into a test bench as a reference, and openpyxl is the engine pandas uses as well — whatever opens an .xlsx in Python mostly opens it with this. The 1900 leap-year bug, the cell formats and the relationship files are places where two reimplementations easily diverge; those are exactly the ones recorded here.

Feature comparison

An .xlsx is a ZIP container of XML parts that find each other through relationship files. None of it sits at a fixed location: which part is the first sheet is stated in xl/_rels/workbook.xml.rels, and that this file exists is stated in _rels/.rels.

What was measured

The anchor Xlsxanker.x1() — a workbook produced by Excel with two sheets: Messung with the columns name, wert, datum, ja over five rows, including a row with three empty cells, and Zweites with a single row and no header. Read with XlsxQuelle and with openpyxl 3.1.5.

Values equal, shape different. openpyxl returns six rows by four columns, the first row holding the texts name, wert, datum, ja. We return five rows with the column names name, wert, datum, ja and report why: "sheet 'Messung': the first row is taken as a header row, because it contains only text and the second does not."

For the second sheet the same rule does not apply — its first row is text and there is no second — and we hand out the columns as A, B, C. That too is measured and not asserted: the rule is a heuristic, and a heuristic that always fires is none.

The date comes out as a date in both (2026-09-04 and 2000-01-01), the boolean as a boolean, the three empty cells as empty and not as zero.

What is hard about the format

Nothing sits at a fixed location. The path to the first sheet runs _rels/.rels → xl/workbook.xml → xl/_rels/workbook.xml.rels → xl/worksheets/sheet1.xml, and every step can differ. Hard-wiring xl/worksheets/sheet1.xml reads the right sheet for most files and the wrong one for some — and the wrong one is the file produced by a foreign tool.

Skipped cells are the normal case. A row with the cells A1 and D1 has four columns, not two. Counting cells in sequence instead of reading their reference shifts the values to the left — and the table looks complete afterwards.

A date is a number with a format. The cell holds 45900; that this is a date is stated in styles.xml, through a reference to a number format that in turn may be a number or a pattern. Reading only the cell yields a number — correct and useless.

And then the 1900 bug. Excel believes 1900 was a leap year, because Lotus 1-2-3 did. Day 60 is the non-existent 29 February 1900; all dates before it are off by one, all after it are right. A reader that computes strictly is one day out for every date before 1 March 1900 — rare, but exactly the case somebody looks at.

What is good: it is ZIP and XML. One can unpack an .xlsx and look inside, and repair a broken one without a dedicated tool. For a format from that house, unusually open.

The items

Our open gaps — this is the work

Deliberate decisions — nothing to do

X5 (decided) — The header row rule

If the first row contains only text and the second does not, the first is taken as a header row and supplies the column names; otherwise the columns are called A, B, C. That is a heuristic, it is stated in the findings, and it can be switched off with XlsxQuelle.ohneKopfzeile(...).

Why guess at all? Because a table view needs column names and .xlsx has none. openpyxl does not need them — it hands out rows and cells and leaves the interpretation to the caller. Both ways are right; one only has to know which one is in front of one, otherwise one compares five rows with six and looks for the error in the reading.

X3 (decided) — The computed value, not the formula

See X8. A formula value coming from Excel is a measurement; a formula we computed ourselves would be a source of error with the appearance of a measurement. The same decision as with the MDF formulas, for the same reason.

X10 (decided) — Writing

openpyxl writes. This module reads.

Properties of the format

X8 (property) — The formula text — closed on 2026-09-07

formeln(sheet) delivers the formula text per cell exactly as it stands in the file — without a leading equals sign, because there is none there. The value stays where it was: in the table. Both are needed and they are different things: the value says what came out, the formula says how. A formula value from Excel is a measurement; a formula we computed ourselves would be a source of error (X3).

The real work is the shared formulas. If the same formula stands a hundred times in a column, Excel writes it once: the master cell carries <f t="shared" ref="C2:C101" si="0">A2*B2</f>, all the others only <f t="shared" si="0"/> — without text. Take the text as it stands and ninety-nine cells give nothing; take the master formula unchanged and you get A2*B2 a hundred times. The right thing is to translate it by the distance between the two cells.

Five places where a translator goes silently wrong. First: the dollar sign anchors — in A$2 the row stays, in $A2 the column, in $A$2 both. Skip it and a sum over a fixed range becomes one that travels along, and the result is still a number. Second: a function name looks like a reference — LOG10 is three letters and a number, exactly like C15; what has a ( behind it is a name. Third: inside quotes nothing is translated — IF(A1>0,"B2","C3") has one reference and two texts. Fourth: a quoted sheet name must not be touched — 'Sheet A1'!B2 contains two things that look like a reference, and only the second is one. Fifth: what runs past the edge is no longer a reference — Excel has 16384 columns and 1048576 rows.

All five stand in one formula of the anchor fallen, and all five expected values are openpyxl 3.1.5's, which reads the same file and computes the same translation.

X9 (property) — Merged cells — closed on 2026-09-07

verbundeneBereiche(sheet) delivers the ranges like A7:C7. A merged cell carries its value only in the top-left corner; the others are genuinely empty in the file.

They are not filled, but they are reported. Writing the value into every cell of the range would be convenient and would be an invention — nothing stands there. Leaving it out and saying nothing would be right and unhelpful, because whoever sees the gap takes it for forgotten. The finding names the ranges and says the sentence that matters: merged, not forgotten. The same attitude as with the invented z in PLOT3D (P2) and the guessed gamma in PNG (P2).

What is still missing and meant to be: cell styles beyond date detection, charts, images, pivot tables. Those are display questions and not data — a number stays the same number whether it is bold or not. Merged cells were the one part of this item where that is not true: there the formatting changes what stands in the table.

X7 (property) — Hidden sheets — closed on 2026-09-06

Closed. The data was never the problem: a hidden sheet was read and offered like any other. What was withheld was the state, so a workbook with a hidden sheet looked like one without. It now stands on the sheet node and as a finding.

workbook.xml knows three states, and the latter two are distinguished: a missing attribute or visible means visible, hidden means hidden, veryHidden means deeply hidden. The difference is no subtlety — a hidden sheet is unhidden from the sheet tab bar in two clicks, a veryHidden one only through VBA. Whoever names both the same loses exactly the information one looks for: with the second form, somebody took trouble.

They are all still offered. A reader that withholds a sheet because a workbook wanted to withhold it makes a decision that is not its to make — its job is to say what is in the file.

X1 (property) — The path through the relationships

See section 3. Both implementations take it; we additionally report when a sheet has no relationship and the path had to be guessed.

X2 (property) — The cell reference is the column number

See section 3. A to Z, then AA — a base-26 numbering without a zero, which makes it one of the few cases in which the obvious conversion is wrong.

Findings against the reference implementation

X12 (BUG there) — One formula falling off the sheet makes the whole workbook unreadable

If a shared formula translates a reference past the left or top edge, openpyxl raises a TranslatorError: Formula out of range while opening — out of load_workbook, that is, before anything has been read. The workbook is thereby entirely unreadable, including every sheet that has nothing to do with it.

Excel writes #REF! in such a case, and that is exactly what our reader delivers: A7*2, translated two columns to the left, becomes #REF!*2. This is not a matter of taste — a reference falling off the sheet is an error, and the error belongs in the cell and not in the file.

The way out in openpyxl is data_only=True: then the formulas are not interpreted at all and the file opens. Whoever needs the formulas does not have that way out.

How to reproduce — Build a workbook in which a shared formula falls off the sheet to the left: master cell C7 with <f t="shared" ref="C7:C8" si="8">A7*2</f>, dependent cell A8 with <f t="shared" si="8"/>. Then openpyxl.load_workbook(file). Expected: the workbook opens and A8 carries a formula containing #REF! — that is how Excel writes it. Observed with openpyxl 3.1.5 under Python 3.10: openpyxl.formula.translate.TranslatorError: Formula out of range, raised from load_workbook; no sheet of the workbook is reachable. With data_only=True the same file opens without complaint.

X13 (open there) — openpyxl does not evaluate formulas

A workbook written by openpyxl has an empty <v/> in every formula cell — there is no computed value, because openpyxl computes none. Whoever reads such a workbook with a program that takes the value (which is the usual thing, see X3) gets nothing but empty cells. That is not a bug but a deliberate limit of the tool — it stands here because it describes the measurement situation: the anchors for the formulas had to be completed by hand with their values, or there would have been nothing to compare.

The same holds for shared formulas: openpyxl reads them correctly and translates them cleanly, but it writes every formula individually. The branch that is the normal case in an Excel file never occurs in a file written by openpyxl. Whoever checks a reader only against workbooks written by openpyxl never checks it on a shared formula.

X4 (open there) — The 1900 bug and the 1904 epoch

Excel knows two epochs — 1900 (Windows) and 1904 (old Mac Excel) — and the choice is in workbook.xml. On top comes the 1900 leap year bug. We compute both epochs and the bug; openpyxl computes the 1904 epoch too but handles the leap year bug only partially, because it relies on Python's datetime, which does not know 29 February 1900. For dates after 1900 that is irrelevant; for those before it is not.

X6 (open there) — Two broken relationships without a message

A sheet without a relationship entry, and a sheet pointing at a part that is not in the container. In the first case we guess the usual path and report it, in the second we skip the sheet and report it. openpyxl aborts in the second case with a message that does not name the sheet. With a workbook of thirty sheets that is the difference between information and a search.

The Java implementation — where this reader stands among its own kind

Why this section. Every other comparison in this module measures against a tool in a different language. That is good against misunderstandings of the format and says nothing about where this reader stands among its own kind. What matters is the distinction between a pure reimplementation in Java and a wrapper around a C library: only the reimplementation solves the same task under the same conditions.

A pure Java reimplementation exists, and it is the reference outright: Apache POI, module poi-ooxml/XSSF. No JNI. Not measured — the binary distribution is not present yet; it is several jars (poi, poi-ooxml-lite, XMLBeans, commons-compress, SparseBitSet, log4j-api).

Worth noting for a later measurement: XSSF reads through DOM by default and is memory-hungry; the event-based SAX route is the fast one. This reader takes the streaming route from the outset — a measurement would therefore have to be careful which POI route it compares, otherwise it measures the mode and not the reader.

How solid this is. Researched on 2026-09-06 via web and GitHub search; Maven Central's search API was blocked, so a systematic artefact search was not possible. Where it says "not measured" below, it says so explicitly — a named library is not yet a measured one.
