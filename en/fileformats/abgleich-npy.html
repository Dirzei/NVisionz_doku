NumPy .npy and .npz — comparison against specification and numpy

As of: 2026-09-05
Our implementation: envisionz.fileformats.npy.NpyQuelle, read-only, no third-party library
Specification: NEP 1 — a simple file format for NumPy arrays, public; references give header fields
Compared against: numpy 2.4.4 (Python)
Test bench: envisionz.fileformats.Npyprobe — 59 checks

The reference implementation. numpy is the array library of scientific Python, carried by an open community. For this format it is not one reference among several but the owner: .npy is numpy's own format, implemented in numpy.lib.format and documented there — the documentation calls itself more current than the original NEP 1 proposal and is therefore the authoritative source.

Why this one. Because numpy owns the format. There is no second opinion here and no leeway: what numpy writes is the definition. The comparison is therefore strictly one-sided — every deviation is ours, and the reference column only says which parts of the format numpy actually uses.

Feature comparison

.npy is the smallest binary format in this collection: six bytes of magic, two bytes of version, a header length and then a Python dictionary as text, followed by the raw bytes. That is where its single trap comes from — the header is Python source, not a data format.

What was measured

Seven fixtures from Npyanker — six .npy covering all read types and orders, plus one .npz with two entries — through envisionz.fileformats.npy.NpyQuelle and through numpy 2.4.4. No divergence. Type, shape, byte order and values agree in all seven cases, including the big-endian >i2 and the empty string in S3.

That is to be expected with this format and is still a statement: everything a reader needs to know is in the header, and the header is readable text. The differences are not in reading but in the breadth of the type list — and there numpy is far ahead, because .npy simply stores every numpy type there is.

What is hard about the format

The header is Python source. {'descr': '<i4', 'fortran_order': False, 'shape': (2, 3), } is a Python literal, not JSON: single quotes, capitalised True/False, a trailing comma and a one-element tuple written (3,). Approaching it with a JSON parser fails on each of those four points separately.

Fortran order is no detail. With shape (2, 3) the values are laid out row-wise in one case and column-wise in the other; both times there are six numbers of the same type, and both times the result looks like a matrix. Missing the flag yields the transposed matrix — and with a square one that only shows when somebody reads the numbers.

What is good: the format has no version trap. The three versions differ only in the width of the length field and the encoding of the header; nothing that follows depends on it.

The items

The Note column names the kind in front of the identifier. Only the gaps are work.

Our open gaps — this is the work

N4 (property) — Compound types — closed on 2026-09-07

Closed. A descr may carry a list of named fields instead of a type code — exactly what a compound dataset is in HDF5, and the natural form for a table: one column per field, one row per entry. Until today such a file was rejected entirely; among this reader's gaps it was the only one that made a whole file unreadable rather than just one column.

The offsets are nowhere written. The header names fields and type codes and no offsets — they follow from the widths, in order, without padding. numpy packs a structured array tightly unless explicitly told otherwise. Whoever aligns here like a C compiler reads wrong from the second field on.

And the byte order stands per field. For a simple array it holds for the whole file; here every code carries its own. The anchor verbundgemischt therefore has a >i8 between two < fields — read the order once for the file and you are orders of magnitude off there. Plus an unsigned byte with the value 250 (signed it would be −6).

A sub-array is the second trap, and it needed an anchor of its own. ('v', '<f8', (3,)) are three floats in one place; they get three columns v[0], v[1], v[2], because a column with three values is not a column. But the shape itself carries a comma — split the field tuple at every comma instead of only at the top-level ones and you get four pieces instead of three. With (3,) that works by accident: the mutation for it stayed green on three anchors. Only the fourth (verbundmatrix) has the shape (2, 3) — a comma between two numbers — and there the wrong split yields two values instead of six.

The same anchor has a second job: its sub-array stands before another field. Advance the offset by one field width instead of the whole sub-array width and you read the following field twenty bytes too early — and in the other anchors the sub-array stands last, where nothing follows. Four anchors from numpy 2.2.6, three mutations, all red.

Deliberate decisions — nothing to do

N5 (decided) — How an array becomes a table

A two-dimensional array (2, 3) becomes two rows with the columns s0, s1, s2; a one-dimensional one becomes a single column wert. With three or more axes the leading ones are folded into a running index. That is an interpretation, not a format requirement — numpy simply hands back the array and leaves the shape to the caller. A table view has to decide, and the decision is stated here so that nobody mistakes it for a property of the format.

N6 (decided) — Objects are not unpickled

A .npy with descr: '|O' carries a Python pickle. numpy reads it only with allow_pickle=True and warns explicitly, because a pickle executes arbitrary code while being read. We do not read it at all — not for reasons of effort, but because a format reader that executes foreign code has stopped being a format reader.

Properties of the format

N3 (property) — Five data types — closed on 2026-09-06

Four built, one was already there. U (fixed-length Unicode) was already read — the row stood at no wrongly. New are f2, c8/c16, M8 and m8.

Where the values go was settled on 2026-09-06 — "a number where possible, text where not", because the toolkit has neither a type for a complex number nor one for a duration. So: f2 as KOMMAZAHL (conversion to double is lossless), c8/c16 as TEXT 1.5+2.5i (as a float the imaginary part would vanish unnoticed), M8 as ZEITPUNKT (that type exists), m8 as GANZZAHL in its own unit — a duration is not a point in time, and 90 seconds are not a date in 1970. The unit stands in the column's format type.

Two things are still rejected, and rightly so. An M8 without a unit — without it the number is meaningless, and guessing one would mean inventing a date. And units finer than a nanosecond (ps, fs, as) — they no longer fit into a point in time, and delivering them rounded would be worse than rejecting them.

Seven new foreign anchors from NumPy 2.2.6 (n7 to n13), with values where an error looks like a value: 65504 is the largest binary16, NaT read as a number is a date in the year minus 292 million, and the same number under M8[D] is a different date than under M8[s]. Four mutations go red — exponent bias, offset of the imaginary part, confused time unit, unrecognised NaT.

N1 (property) — The order flag

See section 3. Both implementations get it right; the anchors n1/n3 measure both cases side by side so that a mix-up cannot slip through.

Findings against the reference implementation

N2 (open there) — Silence about leftovers

If there are more bytes behind the values than shape and descr account for, our reader reports it ("there are N more bytes behind the values that the format does not provide for"); numpy skips them. The same for a .npz entry that is not a NumPy array. That is not a bug in numpy — it reads what is described — but it is the difference between "the file was fine" and "I know that it was fine".

The Java implementation — where this reader stands among its own kind

Why this section. Every other comparison in this module measures against a tool in a different language. That is good against misunderstandings of the format and says nothing about where this reader stands among its own kind. What matters is the distinction between a pure reimplementation in Java and a wrapper around a C library: only the reimplementation solves the same task under the same conditions.

Two pure JVM implementations exist, both small: GreenDelta/npy (org.openlca:npy, pure Java 11 without dependencies, but only version 0.0.1 and described by the project itself as thinly tested) and JetBrains-Research/npy (Kotlin/JVM, without structured types, complex numbers and unsigned types). Neither measured.

The second entry is telling for this document: the JetBrains implementation cannot do precisely what was added here on 2026-09-06 with item N3 — complex numbers and structured types. Whoever needs both has little choice in Java today.
