SQLite — comparison against the specification and the SQLite library itself

As of: 2026-09-07
Our implementation: envisionz.fileformats.sqlite — SqliteQuelle, SqliteSeiten, SqliteSatz, SqliteTabelle, Varint, SqliteReste, read-only
Specification: SQLite Database File Format, public and unusually complete; references give header offsets and page types
Compared against: SQLite 3 through Python's sqlite3 2.6.0 — the reference implementation itself
Test bench: Sqliteprobe 138, OhneRowidprobe 28, Resteprobe 22 — 188 checks in total, four anchors written by SQLite itself, seven counter-tests

The reference implementation. SQLite is at once the owner and the reference implementation of the format, begun in August 2000 by D. Richard Hipp, developed at Hwaci, code and documentation in the public domain. It is the most widely deployed database engine in existence. The measurement went through Python's bundled sqlite3 module, which does nothing but call that C library.

Why this one. Because SQLite itself is the reference. The file format is normatively documented — the documentation says of itself that it defines the format of all releases since 3.0.0 — and the library beside it is exactly that documentation in executable form. One cannot get closer to a truth than that.

Feature comparison

This comparison has a peculiarity: the reference is not a second implementation but the implementation. What SQLite does is the format — the specification describes a library, not the other way round. A finding against it would not be a finding but a misunderstanding on our part. Section 5.4 is therefore empty here, and that is not restraint.

What was measured

Six databases, created with Python's sqlite3 and read with our reader: basic types including NULL and an empty blob; a WITHOUT ROWID table with a composite key; thirty records of 5000 characters each, forcing overflow pages; all serial types at their limits (2⁶², 1e308, a 300-character text, bytes 0…19, negative zero); fifty records with an index of their own; and two hundred records of which half were deleted again, to produce a free list.

All six read, values equal. The WITHOUT ROWID table comes out with the correct column order, the 5000-character texts completely across the overflow chain, and the hundred surviving records of the free-list database in the right number.

One tiny thing diverged: the negative zero. SQLite stores it as -0.0, our reader prints 0. That is not a divergence in reading — the raw state on the Wert carries the eight bytes unchanged — but one of presentation. It is listed anyway, because in a value-by-value comparison it would show up and cost half an hour of looking in the wrong place.

What is hard about the format

The page count in the header is not always valid. Byte 28 names the number of pages — but only if byte 92 matches the change counter in byte 24. If it does not, the number comes from an older SQLite version that did not maintain it, and the file length applies. Missing this reads too little or too much from old files.

The record header describes itself — with varints. Every serial type is a variable-length integer, and from it follows the byte count of the value: even from 12 means blob, odd from 13 means text, and the length is (n−12)/2 respectively (n−13)/2. Reading the varint one byte off yields a serial type that exists, with a length that exists — and from there the whole record is shifted.

INTEGER PRIMARY KEY is not a field. A column declared that way is not in the record; its value is the B-tree entry's rowid. A reader that doggedly matches the creation SQL's columns against the record's values is off by one from that column on — and the shift looks like a type error, not a counting error.

WITHOUT ROWID inverts three things. Such tables live in an index B-tree (page types 2 and 10), the key sits at the front of the record instead of at its declared place, and there is no rowid. Failing to separate that reads the columns in the wrong order — with nothing but valid values.

What is good: SQLite's format description is the best in this entire collection. It is complete, public, with byte offsets, and it is maintained. With no other format here was so little measuring and so much looking-up needed.

The items

Our open gaps — this is the work

Deliberate decisions — nothing to do

S15 (decided) — A view is named, not executed

A view is a stored query and has no pages — its root page is zero. Offering it as a table would mean executing it, and that would require an SQL engine: expressions, joins, ordering, grouping. That is a module of its own and not one line, and it would also be a different promise — this reader says what is in the file, and in the file stands the query and not its result.

The creation text is fully available; whoever wants to evaluate the view has it. The same holds for a trigger: it is behaviour, not data.

S8 (decided) — Companion files are noticed and not touched

Journal, WAL and -shm are found and named in the findings — nothing is created, cleaned up or replayed. That is the core of this module's read-only principle: a reader that repairs has already lost. The SQLite library necessarily does otherwise; it is not a reading interface but a database.

S13 (decided) — SQL — only as much as needed

We evaluate the creation SQL to obtain column names and types, and there is a separate SQL layer above it (Sqlprobe, 116 checks, item DB10) over all data sources. What there is not, is SQL execution inside the file: no triggers, no views, no functions. A format reader that executes SQL is a database.

S14 (decided) — Writing

No write path, no repair, no migration on open — measured by Nurlesenprobe over 24 patterns and by Datenprobe.nurLesend() byte for byte before and after a complete run.

Properties of the format

S11 (property) — The WAL is applied — closed on 2026-09-07

In WAL mode SQLite writes changed pages not into the main file but appends them to a companion file; only a checkpoint enters them. So if a -wal lies alongside, the main file shows an older state — silently: it is complete in itself, every page is right, every checksum works out, only the newest records are missing. A reader that skips the WAL delivers flawless, stale data, and that is the most unpleasant way to be wrong.

The anchor shows it in a number: the same main file delivers five records alone and nine with its WAL — one changed, one deleted, five added. The expected value is SQLite's own, which reads both cases. And the WAL in question is 568 bytes and contains one frame.

Four rules, and each one is a possible silent error. First: the same page stands in it more than once. Changed three times, it stands three times in the WAL, and only the last one counts — read from the front and take the first hit and you get the second-oldest state, which is worse than none. Second: the salt. After a checkpoint SQLite starts over and changes the two salt values in the header; the old frames remain physically in place, because the file is not truncated. Third: the checksum runs cumulatively — a frame's builds on the previous one's, so one damaged frame invalidates all that follow. A WAL is a chain, not a collection. Fourth: only a frame with a database size other than zero closes a change; frames after it belong to one that never finished.

The salt is the one check that catches its case on its own, and that is not obvious: the cumulative checksum does not cover it. It runs over the first eight bytes of the frame header — page number and database size — and then over the page; the salt values stand at bytes 8 to 15 and are left out. So a frame with a foreign salt has a flawless checksum. The counter-test for it is a hand-rewritten WAL, and SQLite reads the same file and shows the old state.

And a magic number that says the opposite of its name. The WAL header starts with 377f0682 or 377f0683, and the number also says in which word order the checksum is computed. The even number means little-endian order: in SQLite the field is called bigEndCksum and is computed as magic & 1, so the even magic sets it to zero. Whoever infers the value from the name has it exactly backwards — and then discards every frame without anyone noticing: the file opens, the data is intact, and it is the day before yesterday's. Measured, not read.

Finally: the database can be shorter in the WAL than in the main file. A DELETE with VACUUM shortens it, and the main file stays long at first. The commit frame names the valid page count, and that takes precedence.

S10 (property) — The pointer maps — closed on 2026-09-07

auto_vacuum tidies a file on deletion: free pages at the end are truncated, and for that occupied pages must be moved from the end to the front. Whoever moves a page must rewrite every reference to it — and for that must know who points at it. That is exactly what the pointer maps hold: for every page its type and its parent, five bytes per entry.

They are recognisable only from the header. Bytes 52 to 55 name the largest root page; if that is zero, there are no pointer maps. If it is anything else, page 2 is not a data page, and neither is any further map. Miss that and you find, in the middle of an otherwise intact file, pages whose page type does not exist.

And the map does not describe itself. Between two maps lie exactly as many ordinary pages as entries fit into one map; the map itself appears in no computation. Count it in and you shift by one page per map — and only from the second one on. At a page size of 4096 that is 819 pages before the error first shows; at the anchor's 512 bytes it is 102. That is why the anchor is small and still checks the second map: by the fact that it does not occur.

For reading an intact file all of that is irrelevant — the trees carry their references themselves, and the maps are skipped. It counts exactly where the trees are broken: for an orphaned page the pointer map is the only place that still says where it belongs. bisZurWurzel delivers the chain from a page up to the root node of its tree — and thereby the answer to the question which table a found remnant belongs to (DB6). Without it a remnant is a find without provenance.

S12 (property) — Views, triggers, virtual tables — closed on 2026-09-07

schemaobjekte() names everything in sqlite_schema that is not an ordinary table: views, triggers and virtual tables, each with name, affiliation and creation text. Named, not offered — why is in S15. The difference to the earlier state is nevertheless the essential one: a database with five views used to look like one without.

A virtual table stands there as table and has root page zero. In the entry itself it is recognisable only from the creation text — CREATE VIRTUAL TABLE … USING fts5(…). Its data lies in shadow tables: suche creates suche_data, suche_idx, suche_content, suche_docsize and suche_config. Those all stand there as ordinary tables and are individually readable.

How they belong together is said by the name alone, and so schattentabellen(name) is a conjecture and not a lookup: there is no reference in the file from the virtual table to its shadows. It stands here nonetheless, because without it five tables stand around with no discernible purpose — and because a conjecture that is named as one is worth more than silence.

S9 (property) — UTF-16 as text encoding — closed on 2026-09-06

Closed, and again there was nothing to build. Byte 56 may say 2 (UTF-16LE) or 3 (UTF-16BE), and SqliteKopf.kodierung() has been handing the right charset to the cursor since it was built. The item stood open with the reason "cheap to close but no fixture" — and that is exactly what it was: not a gap but a gap in the evidence. Sqliteschreiber writes UTF-8 because that is what it was taught; an own writer cannot measure this place.

Sqliteanker now carries two databases produced with the sqlite3 module via PRAGMA encoding. They contain umlauts — and that is the point: with pure ASCII, UTF-16LE would have a zero at every second byte and a wrong reading would show up at once. With umlauts a character comes out that looks like a character. Two mutations go red: reading UTF-16LE as UTF-8 (three failures) and swapping the byte order (two).

Noticed in passing and fixed along the way: the mutation at first took down the whole probe instead of producing a red line — and a probe without a closing line counts as not run. The section now has a clamp, as other places in the workspace already do.

S1 (property) — The conditional page count

See section 3. We report both cases in the findings; the library resolves them silently, because it can.

S2 (property) — WITHOUT ROWID inverts the record shape

See section 3. The item has its own probe in this workspace (OhneRowidprobe, 28 checks), because it was wrong on the first attempt.

S3 (property) — Overflow is a chain, not a field

A value that does not fit on a page sits partly in the cell and for the rest in a chain of overflow pages whose first four bytes point to the next. How much stays in the cell depends on the page size and the reserved space — a formula one cannot guess.

S5 (property) — Varints, and big-endian at that

SQLite stores its variable-length integers big-endian, up to nine bytes, where the ninth contributes all eight bits. That is the opposite direction from Parquet and Protobuf. Bringing the design over from there reads valid numbers — the wrong ones.

S6 (property) — The key that is not there

See section 3, INTEGER PRIMARY KEY.

S7 (property) — Column names live in SQL, not in a list

The only place the column names appear is the CREATE TABLE text in sqlite_schema — that is, source code, with quotes in three flavours, comments, line breaks and table constraints that look like columns. We parse it and report when the result is uncertain. That report is not a weakness but the only honest answer at a place where guessing is required.

S4 (property) — Deleted data is still there

The free list, free blocks inside a page and orphaned pages still carry the bytes of deleted records. SqliteReste (item DB6, Resteprobe, 22 checks) makes them visible. The library does not — it has no reason to; for a forensic look it is the subject.

Findings against the reference implementation

None, and here that is a statement about the situation, not about diligence. The reference is the implementation that defines the format. Where we diverge from it, the error is ours; where it does something other than the format description says, the description is out of date. A finding would be misaddressed either way.

The Java implementation — where this reader stands among its own kind

Why this section. Every other comparison in this module measures against a tool in a different language. That is good against misunderstandings of the format and says nothing about where this reader stands among its own kind. What matters is the distinction between a pure reimplementation in Java and a wrapper around a C library: only the reimplementation solves the same task under the same conditions.

The Java default here is a wrapper, not a reimplementation. xerial/sqlite-jdbc, the de-facto standard library, ships precompiled sqlitejdbc.dll/.so/.dylib inside the jar and unpacks them on load — it therefore measures the C library and not a Java implementation.

There are two pure-JVM routes, both with a catch. SQLJet is a genuine Java reimplementation but without SQL — only low-level B-tree access; the project appears dormant. roastedroot/sqlite4j translates the SQLite C source to WebAssembly and from there to JVM bytecode — neither JNI nor a reimplementation but a third route. Neither measured.

That places this reader: it reads the pages itself, without C and without Wasm, and brings with SqliteReste and the SQL layer things that none of the three Java routes in this comparison has.
