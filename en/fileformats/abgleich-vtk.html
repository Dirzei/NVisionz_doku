VTK Legacy — comparison against the format description and against VTK itself

As of: 2026-09-05
Our implementation: envisionz.fileformats.vtk.Vtkleser with Vtkdatei, Vtkfeld, Datensatzart, read-only, no third-party library
Specification: VTK File Formats (Kitware, appendix to the VTK User's Guide) — public; references give keywords
Compared against: VTK 9.7 (Kitware, C++/Python) and meshio 5.3.5
Test bench: envisionz.fileformats.vtk.Vtkprobe — 89 checks

The reference implementation. VTK was started in 1993 by Will Schroeder, Ken Martin and Bill Lorensen; the three founded Kitware in 1998, which maintains VTK to this day. It is the de facto core of scientific visualisation and the foundation of ParaView. For this format Kitware is not a reference product but the owner: the VTK legacy format is VTK's own, documented by Kitware. Alongside it, meshio served as an independent second reading.

Why this one. Because Kitware owns the format. A difference from VTK is therefore always our error. meshio stands beside it as a second, independent reading, and that is not decoration: where owner and independent reader diverge lies a place the documentation does not state clearly enough — and this format has several of those.

The one finding, and it is ours

The measurement uncovered exactly one real gap, and it is sharp: version 5.1 rebuilt the cell section. Up to 4.2 a flat list followed CELLS n size, in which each cell begins with its node count. Since 5.1 there are two named sub-lists, OFFSETS and CONNECTIVITY, each with its own type. Our reader knows only the old form and reports, at the right place, "line 9: expected a number, found 'OFFSETS'".

The finding weighs more than it first appears: VTK 9.7 writes 5.1 by default, and so does meshio. Every file created fresh today is therefore unreadable to this reader as soon as it contains cells. That all five 4.2 anchors pass is reassuring for legacy holdings and for nothing else. See V6.

The counter-check is noteworthy: strukt.vtk also carries the header line # vtk DataFile Version 5.1 and is read without complaint. The version number is therefore not the obstacle — the reader checks it and lets it through. It is the cell section alone. The gap is thus exactly one place wide, not one format version.

The side finding

poly42.vtk is read, the points are right — but zellzahl() stays zero although the POLYGONS section contains two triangles. The reader reads VERTICES, LINES, POLYGONS and TRIANGLE_STRIPS into the same branch as CELLS but counts only what stood under CELLS. With UNSTRUCTURED_GRID that goes unnoticed, with POLYDATA it does not. See V5.

What is hard about the format

Text and bytes in one stream. With BINARY, raw big-endian bytes stand among the header lines. A reader that first decodes the file into a string and then splits it has already destroyed the data at that moment. That is why this reader works on the byte array and not on a String — no subtlety, but the precondition for the binary branch working at all.

Mixed line endings. This workspace's writers mix \n literals with %n and on Windows produce files with CRLF and LF side by side — 1581 to 5 in one measured sample. Whoever commits to one line ending reads a \r as part of a number. That is not a hypothetical case; it is the reason this reader exists.

The format changed under the same name. "VTK Legacy" sounds like something settled. Version 5.1 rebuilt the cell section, and the header line does say so — but a reader that merely reads the version and lets it through notices only at the first keyword it did not expect. See section 2.1.

What is good: the line orientation. Almost everything sits in named sections with a leading count. A reader knows before every block how many numbers follow and can report an unknown marker with a line number rather than guessing. Few binary formats permit so precise an error message — that our reader can say "line 9" is a merit of the format, not of the reader.

The items

The Note column names the kind in front of the identifier. Only the gaps are work.

Our open gaps — this is the work

V7 (property) — FIELD as a dataset kind — closed on 2026-09-07

Closed — and the measurement immediately produced a correction. It said here that the dataset kind is called DATASET FIELD. That is wrong: VTK 9.7.0 does not read such a file. vtkDataObjectReader then reports "Field reader cannot read datasets" and returns zero arrays. Correct is FIELD <name> <n> without the word DATASET — and the arrays follow immediately, with no POINT_DATA or CELL_DATA before them, because there is nothing for them to hang on.

That is the value of measuring against a foreign tool: the gap had been described since it was recorded with a spelling that does not exist. Whoever had closed it from that description would have built a reader that reads exactly the files it is not about.

Both spellings are read nonetheless. The second costs nothing, it appears in several descriptions in circulation, and rejecting a file one understands helps nobody. The test measures both and demands the same numbers.

In the long-form view such a file yields no punkte and no zellen table, because there are neither points nor cells. The arrays are grouped by their length: arrays of different length do not belong in the same table because they would have no common axis. An array with three components gives three columns.

Deliberate decisions — nothing to do

V10 (decided) — Writing

VTK writes the format it invented. This module reads. Vtkschreiber in the test bench builds fixtures — including broken ones that cannot be obtained anywhere else — it is test equipment, not an output path.

V8 (decided) — LOOKUP_TABLE is read and discarded

The line after SCALARS names a colour table. The workspace had three partial readers of the same format: one checked the line, one skipped it unconditionally, one read it and threw it away. This reader reads it and explicitly discards it — colours are not measurements. What matters is not which of the three readings was chosen but that there is only one left.

Properties of the format

V9 (property) — Route through the general format detection — built on 2026-09-06

Decided and built. Datenquellen.oeffne now opens a VTK Legacy file as a Langform view with two tables: punkte (axis over the point count, columns x, y, z and every field on the points) and zellen (axis over the cell count, columns from the fields on the cells). Just as the Ensight and Exodus routes already did.

Why yes here and no for the image formats. The same question stood in eight items with identical wording. For BMP, GIF, PNG, TIFF and WebP the answer is no — a Datenquelle is a table view, and an image is not a table. For VTK the content really is tabular: a point field with values on it. And detection can find it, since # vtk DataFile Version stands in every file — unlike PLOT3D (P4), where there is no magic.

A field with several components — a velocity vector, a stress tensor — is split into one column per component (name_1 to name_n). Carrying only the first would be exactly the error item G10 describes for Gmsh. A field whose length does not match the axis is reported and skipped rather than padded or truncated.

Measured against the foreign anchor from meshio, text and binary, because only it carries point and cell data: only on it can one show that the view keeps the two sides apart. Two mutations go red — not separating point and cell fields (two failures) and reading the coordinates without stride three (one). The zellen table is not created when there are no fields on the cells: a table of nothing but cell numbers would be no information.

V6 (property) — The cell section of version 5.1 — closed on 2026-09-06

Closed. Since 5.1, CELLS <numOffsets> <numConnectivity> is followed by two named sub-lists OFFSETS and CONNECTIVITY instead of the flat list. The two numbers therefore mean something different than before, and the cell count is numOffsets - 1: the offset list carries the end of the last cell as well. The distinction is made on the version number in the header, not on whether the next line reads OFFSETS — with BINARY there are raw bytes there, and looking ahead would mean looking into numbers.

The anchor is foreign, and that is the point. Vtkanker carries two files produced with meshio 5.3.5, text and binary. This is exactly where the in-house workshop failed: Vtkschreiber knew only the old variant, all own probes were green, and yet every freshly written file with cells was unreadable. A writer that comes from the same understanding as the reader cannot find this error — it confirms it. Acceptance is not only on the cell count but on the fields after the cell section: whoever mislengths the sub-lists reads from the wrong place from there on. Two mutations go red.

V5 (property) — Cell count for POLYDATA — closed on 2026-09-06

Closed. Counting now happens for every connectivity section, not only CELLS: POLYDATA carries its cells under VERTICES, LINES, POLYGONS and TRIANGLE_STRIPS, and the sum is the cell count. For UNSTRUCTURED_GRID nothing changes, since only CELLS occurs there. The probe measures a polygon mesh built from three different sections — four cells, none of them under CELLS.

V1 (property) — The version number says less than it promises

See section 2.1. The same version 5.1 is read for STRUCTURED_POINTS and not for UNSTRUCTURED_GRID — the version affects one section only. A reader checking the version number and rejecting files by it would be stricter than necessary; one that merely reads it is too lax. We read it, check it and fail only at the place that really differs — with a line number.

See section 3. The reason this reader works on bytes.

Findings against the reference implementation

V4 (open there) — An unknown marker without a location

When VTK meets a keyword it does not know it reports that without a line number; meshio answers with a Python exception from the inside. Our reader names the line and the word and says explicitly that it does not guess. That is no superiority in reading — in the one case where it really mattered it was our file that went unread (V6) — but the difference between an error message and a debugging session. No bug in VTK has been found here; with the format's originator that would have been surprising.

The Java implementation — where this reader stands among its own kind

Why this section. Every other comparison in this module measures against a tool in a different language. That is good against misunderstandings of the format and says nothing about where this reader stands among its own kind. What matters is the distinction between a pure reimplementation in Java and a wrapper around a C library: only the reimplementation solves the same task under the same conditions.

No pure Java implementation. VTK itself is C++; the VTK Java wrappers are a JNI wrapper around the C++ library and need its native files. The research found no standalone Java reader for VTK Legacy.

That gives finding V6 its weight: the cell form of version 5.1 was unreadable to this reader, and in Java there was no other one to fall back on. Since 2026-09-06 it is read, and since V9 there is a data-source view on top.

How solid this is. Researched on 2026-09-06 via web and GitHub search; Maven Central's search API was blocked, so a systematic artefact search was not possible. Where it says "not measured" below, it says so explicitly — a named library is not yet a measured one.
