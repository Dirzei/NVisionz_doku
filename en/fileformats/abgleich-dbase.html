dBASE .dbf — comparison against specification and dbfread

As of: 2026-09-05
Our implementation: envisionz.fileformats.dbase — DbaseQuelle, DbaseKopf, DbaseFeld, Memodatei, Sprachtreiber, read-only
Specification: The xBase format descriptions (dBASE III/IV/V, FoxPro, Visual FoxPro) — public and in several versions; references give header bytes and field codes
Compared against: dbfread 2.0.7 (Python)
Test bench: Datenprobe (dBASE core), Memoprobe 37, Indexprobe 40

The reference implementation. dbfread is a small, pure Python library by Ole Martin Bjoerndalen, read-only. It is an independent reimplementation of a historical vendor format: dBASE came from Ashton-Tate, passed through Borland, and there is no active owner with a library of its own any more. There is therefore no reference to measure against — only several independent readings of the same legacy.

Why this one. Because there is nothing better. dBASE has no owner any more and no norm; what circulates are several partly contradictory descriptions and a handful of independent readers. dbfread is the tidiest of them and covers the common variants. Every difference here is explicitly a finding and not an assignment of blame — there is no authority that could decide.

What was measured

Two fixtures, built by hand from the format description and not derived from either reader: a .dbf of version 0x03 with field types C, N, L, D over three records — including an empty N field, an indeterminate L (?) and an empty date — and a .dbf with no records at all.

Both readers agree, including in the three delicate cells: the empty N is empty and not zero, the ? in the L field is empty and not false, and the date made of eight spaces is empty and not 1 January 1900. Our reader additionally reports that byte 29 names no language driver — the character encoding is therefore not stated, and with a file containing umlauts that is the single most important piece of information.

The rows about memo, index and Visual FoxPro fields are not measured on these two files but derived from both implementations' source; the corresponding fixtures live in the module's test bench (Memoschreiber, Indexschreiber) and not in this measurement run.

What is hard about the format

Numbers are stored as text. An empty N field is a row of spaces, not zero. Turning it into 0 falsifies every sum — downwards, evenly, inconspicuously. An overflowed field is written by dBASE as *****; that is not a value either.

The header lies about the record count. Many tools append records without updating the counter. Believing it means not reading the appended records — and noticing nothing, because the file is otherwise fine.

Deleted means marked. Byte 0 of each record is *, the data stays there unchanged. For an analysis they are to be skipped; for a forensic look they are often the interesting part. A reader that does not offer them at all decides that for the caller.

What is good: after forty years dBASE is still readable in a hex editor. Header, field list, records — fixed lengths, no pointers, no directory. There is no second data format of this reach in which a damaged file could be rescued by hand so easily.

The items

The Note column names the kind in front of the identifier. Only the gaps are work.

Our open gaps — this is the work

D11 (decided) — Writing

Neither we nor dbfread write. For us that is a guarantee resting on four levels and measured; for dbfread it is the library's scope. The row stands in the table as no/no so that nobody mistakes the empty cell for an oversight.

Reclassified on 2026-09-06. The item stood as a gap although its own title already said "explicitly not a gap here" — and although all twenty-six other formats in this collection list "writing" as a deliberate decision. It was the sole outlier. Being read-only is this module's scope, not unfinished work; such an item in the gap list presents the guarantee as an omission and invites breaking it.

D2 (decided) — Deleted records are offered, not forced

Skipped by default, readable via mitGeloeschten(). Both paths are needed: for an analysis deleted records are noise, for a forensic look they are the subject. dbfread has the same through DBF(..., raw=False) and the deleted view.

D3 (decided) — The raw state stays alongside the value

A Wert carries the interpretation and the bytes it came from. With dBASE that is no luxury: a date 00000000, a number with leading spaces, a text field with padding — a reader that only interprets loses information exactly when it matters.

D5 (property) — General and picture fields — closed on 2026-09-06

Closed, as naming rather than unwrapping. G and P point into the companion file like a memo field but carry an embedded OLE object respectively an image. The value stays the whole block — nothing is cut away — but what is inside it is now stated: Olekunde reads the OLE 1.0 frame (version, kind, class name, topic, item, payload), recognises the image inside and names offset and length of the payload within the block. The field type moved from GANZZAHL to BYTES along the way: the block number sits in the record, what comes out is the content.

Why naming and not unwrapping. A module that only reads must throw nothing away. The OLE frame carries the class name — PBrush, Word.Document.8, METAFILEPICT — and that is often the only clue about which program wrote the object. Whoever hands out only the payload delivers an image and loses the provenance. Whoever names the offset gives both.

Recognised are BMP, PNG, JPEG, GIF, both Windows metafile signatures (the placeable D7 CD C6 9A and the plain 01 00 09 00), the enhanced metafile and an OLE 2 compound document — plus the case without a frame, where the image sits directly in the block. The lengths in the OLE frame are stored least significant byte first; read the other way round the class name is not found and the whole thing looks like raw bytes. That is what the counter-test hangs on.

dbfread still does what it did: raw bytes without information. The difference therefore no longer stands in the list of gaps but in the feature table.

Properties of the format

D7 (property) — Autoincrement and timestamp — closed on 2026-09-06

Closed, but not as expected. The item said the Visual FoxPro codes + and @ were missing. They were not — they had been in the reader since it was built, + as an integer like I, @ as a timestamp like T. What was missing was the measurement: no probe had ever touched a binary field code.

And the measurement immediately found a bug the item had not claimed at all: I and + were read unsigned. −1234 came out as 4294966062. The format description says signed, dbfread reads it that way, and no probe had ever put a negative number into an I field. That is the more unpleasant of the two cases: a gap that is not one can be checked away — an implementation nobody measures looks exactly like a correct one.

All six binary codes are now measured — I, +, B, Y, T, @ — on a fixture of raw bytes (Dbaseschreiber.rohSatz), because little-endian numbers pushed through a character encoding are no longer measurable. The Julian day and the milliseconds are computed by hand and not read back from the reader.

D8 (property) — The FoxPro numbers are the other way round

In the .dbf everything is little-endian, in the .fpt next to it big-endian — the same file, two byte orders. On top of that the block number in the record is sometimes ten ASCII digits and sometimes four bytes of binary, and the field type does not say which. Getting both right at once is the actual work on memo fields.

D6 (property) — Varchar needs the null-flag column

A V field in Visual FoxPro carries its real length in the last byte of the field — unless the field is flagged as empty, and that is stored in a hidden _NullFlags column. Reading only the length byte mistakes an empty cell for a full one.

Findings against the reference implementation

D1 (open there) — Five conditions dbfread does not report

Record count versus file length, missing 0x1A, truncated final record, missing language driver, memo file read with flavour and block size. None of these makes a file unreadable; each of them changes how far the result can be trusted. dbfread reads past them silently.

D4 (open there) — Memo fields without a companion file

If no .dbt/.fpt lies alongside, our reader yields the block number and reports it. dbfread yields nothing without ignore_missing_memofile=True, and with that flag an empty string. An empty string looks as if there were nothing to fetch; a block number says that there is something, and where.

D9 (open there) — The message instead of the void

See D4 — the same thing from the table's point of view: a column that is empty everywhere looks like a column without content.

D10 (open there) — Index files

.ndx and .cdx are read by us (Indexprobe, 40 checks) — not to search faster, but to see what indexes a data set brings along. dbfread does not read them. For an analysis that is irrelevant; for the question "does this .cdx belong to this .dbf?" it is the whole answer.

The Java implementation — where this reader stands among its own kind

Why this section. Every other comparison in this module measures against a tool in a different language. That is good against misunderstandings of the format and says nothing about where this reader stands among its own kind — and that is the question a Java developer asks first. The distinction that matters is between a pure reimplementation in Java and a wrapper around the original C library: only the reimplementation solves the same task under the same conditions as this reader; a wrapper calls the original.

Measured on 2026-09-06 against javadbf 1.14.1 — a pure Java reimplementation (100% Java, no external dependencies), the most widespread Java implementation for .dbf. The same fixture through both readers: text, number, date and logical, each column once empty.

The values agree, the representation differs — and that is not a divergence but a design decision. We return 12.5 as a number, javadbf 12.50 as a BigDecimal with scale; we return 2026-09-06 as a LocalDate, javadbf a java.util.Date with a time zone — for a dBASE date that has none.

A genuine finding against javadbf, and of the kind that matters. An empty date field occurs in two forms: eight blanks or eight zeros. javadbf 1.14.1 handles the blanks correctly and returns null — from 00000000 it produces 30 November of the year 2. An invented date that looks like a date: it goes unnoticed in an analysis and sorts to the front. We return LEER for both forms. To reproduce: a .dbf with three D fields and the record 20260906 / 00000000 / eight blanks, then new DBFReader(...).nextRecord().

This finding stands here and not under 5.4: that section is about dbfread, this comparison's reference implementation. javadbf is a different tool, and the count of upstream findings is meant to say what stands against dbfread.

This measurement lives outside the module, in javavergleich/Javavergleich.java, because envisionz-framework-fileformats has the rule "no foreign libraries" — and it still holds. Only the result goes into the module, with date and version. The single exception is javax.imageio for the image formats: that sits in the JDK and therefore measures along as a permanent probe.
