ASAM MDF 4 — comparison against specification and asammdf

As of: 2026-09-27
Our implementation: envisionz.fileformats.mdf (classes MdfQuelle, Mdftyp, Umrechnung), read-only, no third-party library
Specification: ASAM MDF 4.2 — references give block and field names, not paragraph numbers (see section 4 for why)
Compared against: asammdf 8.8.26 and 8.8.27 (Python, with C acceleration)
Test bench: envisionz.fileformats.mdf.Mdfprobe — 426 checks (2026-09-27), sixteen foreign anchors, plus the own fixtures from Mdfschreiber

The reference implementation. asammdf is a fast Python reader and editor by Daniel Hrisca with community contributions. It is an independent third-party implementation: the standard is set by ASAM e.V., whose documents sit behind a membership. In automotive measurement asammdf is the dominant open-source library for MDF — and therefore the only reference reachable without a vendor tool.

Why this one. Because the ASAM documents sit behind a membership and asammdf is the only open-source implementation that reads MDF 4 completely enough to serve as a yardstick. That is exactly why the references in this document are given as block and field names rather than paragraph numbers: the names can be looked up in the file itself, whereas an invented paragraph number looks just like a checked one.

Coverage, computed from the rows below: of 68 features we have 62 present, 0 partial and 6 absent; the reference implementation has 53 / 8 / 7.

Five measured differences

The following five are not inferred from source code but measured by running the same file through both readers. The fixtures come from Mdfschreiber and Mdfanker and live in the module's test bench; the values below are the output of the two runs.

The VLSD group inside an unsorted stream

Fixture Mdfschreiber.vlsdGruppe(): a data group with record IDs in which the records of the payload group (ID 1, three cycles: 11, 22, 33) are interleaved with those of a VLSD group (ID 2).

Us: three records — 11, 22, 33 — plus the finding "channel group Gruppe1_2 is a VLSD group (cg_flags bit 0): it only carries variable-length values for another channel and is not a table". asammdf 8.8.26: one record — 11. The other two are missing, with nothing reported.

This is the most unpleasant of the five: the output looks complete and is not.

The channel reaching past the record

Fixture Mdfschreiber.krummerSatz(): cg_data_bytes says 4 bytes per record, the channels require 8.

Us: the overhanging channel yields LEER (empty), plus the finding "channel group krumm declares 4 bytes per record but its channels need 8; the overhanging channels yield empty". asammdf: the channel yields [0, 0] — zeros that look like measurements.

The invalidation bit — two views, not a bug

Fixture Mdfanker.ungueltig(): five cycles, two of them with the invalidation bit set.

Us: five rows; the invalid values are empty, the time axis stays complete. asammdf: three values and three timestamps — the invalid cycles disappear along with their time.

Neither is wrong here. asammdf delivers signals, and a signal has no point where there is no valid value. We deliver a table, and a table with vanished rows could no longer be joined against another quantity. Anyone using both tools side by side must know this difference — otherwise they compare series of different lengths and look for the error in the wrong place.

Text in UTF-16

Fixture Mdfschreiber.texte(): the same text Gruen in all four encodings — cn_data_type 6 through 9.

Us: Gruen four times. asammdf: likewise for STRING_SBC and STRING_UTF8, but for STRING_UTF16LE and STRING_UTF16BE the raw bytes — b'G\x00r\x00u\x00e\x00n' with dtype |S12. The characters are there, undecoded.

The algebraic conversion

Fixture produced by asammdf: a channel with cc_type 3 and the formula 2*X+3 over raw values 1, 2, 3.

asammdf: 5, 7, 9 — it evaluates the formula. Us: 1, 2, 3 plus the finding "channel alg.Alg has conversion type algebraic; it is named, not computed — the raw value is returned unchanged". This is a decision, not an oversight; it is recorded as note MD9.

How this was measured

Sixteen fixtures — eight foreign anchors from Mdfanker (produced by asammdf 8.8.26) and eight of our own from Mdfschreiber — were written out as .mf4 and run through both readers: through envisionz.fileformats.mdf.MdfQuelle and through asammdf 8.8.26 on Python 3.11. Table count, column names, data types, record count and the values themselves were compared.

Since 2026-09-25 seven more foreign anchors, written by asammdf 8.8.27: CANopen date and time, complex numbers, MIME data, a structure, an array, two events and a virtual channel. Each was read back by asammdf itself before being embedded; where a byte was set by hand (MIME), the anchor and the item say so.

Both directions count. That we read everything asammdf writes is one half; that asammdf reads everything we build for our own tests is the other. Only together do they mean something: a reader that only understands its own files is not a reader of the format but of its writer.

Where a row could not be measured against a file, it rests on both implementations' source — for asammdf on asammdf/blocks/v4_blocks.py, mdf_v4.py and v4_constants.py of version 8.8.26. Such rows are identifiable by their item.

Why no specification paragraph numbers appear here

In the HDF5 comparison next door the reference column carries II.A or III.G — sections of the HDF5 File Format Specification, which is freely available. That does not hold for ASAM MDF: the specification sits behind an ASAM membership.

A paragraph number from memory would be a reference nobody can look up, and yet it would look as if it had been checked. So what stands here is the block and field name — cn_data_type, dz_zip_type, cg_flags. These names are the same in every MDF file, every tool and every implementation; anyone wanting to check them finds them in the file itself, without a membership.

The items

Four different kinds of thing were in one column until 2026-09-05 and could not be told apart. They are now separated, and the Note column names the kind in front of the identifier.

Our open gaps — this is the work

These and only these are open items. They appear as one entry AB-MDF4 in OFFENE-PUNKTE.md; the detail lives here, so that the item list stays an index and does not become a second document.

Since 2026-09-27 nothing is left here — MD14, MD16 and MD18 (2026-09-26) and MD19 (2026-09-27) stand under 5.3; their anchors are our own because no foreign writer produces the construct.

Deliberate decisions — nothing to do

Nothing is missing here; something was decided. Anyone wanting to reverse one of these finds the reason below, and the condition under which it would fall.

MD9 (decided) — Formula and bitfield are named, not guessed

cc_type 3 carries a formula as text, cc_type 11 a bitfield table. Both could be evaluated; we do not. The reason is not effort but the absence of an anchor: evaluating a formula without a fixture to measure the result against is a source of error disguised as a measurement — it yields a number, and nobody can tell whether it is right. asammdf evaluates both (measured: 2*X+3 over 1, 2, 3 gives 5, 7, 9). The day a fixture with documented expected values exists is the day this item falls.

MD10 (decided) — A version number that is too new

We keep reading by the 4.10 rules and report it. asammdf aborts on an unknown version. Both are defensible; we chose to keep reading with a warning, because a measurement series that is ninety-nine percent readable is worth more than an error message.

MD11 (decided) — The unfinished file

id_unfin_flags says the writer was interrupted: cycle counts and lengths may be too small. We read and report it verbatim. asammdf also reads and partially repairs the cycle count — which yields more data at the cost of the warning.

MD20 (decided) — Bus protocols

asammdf can decompose CAN, LIN and FlexRay recordings into named signals using a database file. That is not a format gap but a domain layer on top, and it does not belong in a format reader: it needs a second file the format knows nothing about.

MD21 (decided) — Writing

This module does not write — not as a gap but as a guarantee resting on four levels and measured (Nurlesenprobe). asammdf writes and converts.

Properties of the format — affecting both

MD14 (property) — The guard block ##GD (MDF 4.3) — closed on 2026-09-26 with an own anchor

Read since 2026-09-26: MdfQuelle.bewacht resolves a ##GD on every chain (data and channel groups, channels, texts, hierarchies, attachments, events). If gd_version requires at most 4.20, the guarded block is read as if it stood there itself; otherwise the reader stops at this point and says so in a finding. Measured only on the own anchor Mdfschreiber.waechter(430) and (410) — a foreign anchor is still missing.

Until 2026-09-25 this read "gap data block, MDF 4.2, carries ranges without records". That was wrong. ##GD arrives with MDF 4.3 and is a guard: it stands in a chain in place of a block that a reader of an older version cannot know, and it names two things — gd_addr, the guarded block, and gd_version, the minimum version one must understand to follow it. An older reader is meant to stop there instead of interpreting a block whose layout it does not know. asammdf 8.8.27 has a GuardBlock class (asammdf/blocks/v4_blocks.py) but uses it nowhere when reading; we have none. No foreign writer produces one — asammdf does not write it, and the vendor tools that might are not available here. The row is therefore derived from source and not measured.

MD16 (property) — Maximum length cn_type 5 — closed on 2026-09-26 with an own anchor

Evaluated since 2026-09-26: cn_data points to the length channel of the same channel group; per record only as many bytes are taken as it states. Own anchor Mdfschreiber.hoechstlaenge() with padding bytes that are not zeros ("AbcXXXXX" → "Abc"). If the length channel lies elsewhere, the full length is read and that is reported.

The virtual data channel (cn_type 6) is measured since 2026-09-25: anchor Mdfanker.virtuell() from asammdf 8.8.27, a channel with no bits in the record and linear conversion 10 + 2.5 · n, yields 10, 12.5, 15, 17.5 in both readers, and the neighbouring channel is untouched. What remains is cn_type 5: the channel carries the maximum length, the actual length sits in a second channel referenced by cn_data. We recognise and report it; it is not evaluated. asammdf does not write one — so there is no foreign anchor, and a self-built one only measures our own reader.

MD18 (property) — Channel hierarchies ##CH — closed on 2026-09-26 with an own anchor

Read since 2026-09-26: each hierarchy is a node under Kanalhierarchien with its kind (group, function, structure, map list, input, output and local variables, calibration definition and reference), comment, sub-hierarchies and, per element, the channel (or channel group); the channel itself carries its path as hierarchie, several separated by semicolons. Own anchor Mdfschreiber.hierarchie().

Events are read since 2026-09-25: ##EV appears in the outline tree under Ereignisse with kind, cause, range, reference, time (ev_sync_base_value · ev_sync_factor, twelve digits), scopes, attachments and comment — measured on anchor Mdfanker.ereignis() (asammdf 8.8.27: a marker at 1.5 s, a trigger at 1.0 s; asammdf reads the same two). What remains is ##CH: we count and name the hierarchies but do not order the channels by them. asammdf has no class for it and writes none — a foreign anchor is missing.

MD19 (property) — Sample reduction ##SR — closed on 2026-09-27 with an own anchor

##SR carries precomputed reductions over windows of fixed length. The levels hang as a chain on cg_sr_first; the body holds sr_cycle_count, sr_interval, sr_sync_type (time, angle, distance, record index) and sr_flags (bit 0: invalidation bytes follow). A reduction record is three sections in the group's record layout — mean, minimum, maximum — followed, with bit 0, by the invalidation bytes that apply to all three. Each level becomes a table of its own <gruppe>.verdichtungN with the columns <kanal>.mittel, .min, .max per channel: a reduction has different rows (windows instead of records) than its group and therefore does not belong beside it as a column. In the outline tree it sits under its channel group with window, reference, cycle count and data block; zyklen, zeitkanal (the mean of the time channel), einheit and umrechnung know the level. Virtual and VLSD channels have no interpretable value in a reduction record and yield empty. Whether a record ID precedes a reduction record is decided by the data length — only if it adds up exactly with one; nothing is guessed. Named, not read: the column storage ##RV/##RI of MDF 4.2 — how the three sections lie there cannot be established without a fixture. No foreign writer produces ##SR — asammdf 8.8.27 has no class for it and does not read it (it does read the group of the same fixture correctly: eight records, Temp with the three invalid ones left out). The anchor is therefore our own: Mdfschreiber.verdichtung(false) with two levels (0.2 s with invalidation bytes, as a ##DL of two ##RD; 0.8 s without) and verdichtung(true) with the second level as ##RV. The expected values stand in the writer's table and are computed in closed form, not from the reader. What the time channel holds in a reduction record is chosen freely by the anchor; the ASAM description of it sits behind the membership and has not been checked here.

MD12 (property) — Source information — closed on 2026-09-07

##SI is now evaluated instead of merely taken as text. Two bytes answer the first question one asks of a measurement file: si_type says whether the value comes from an ECU, from a bus, from I/O, from a tool or from a user; si_bus_type says which bus — CAN, LIN, MOST, FlexRay, K-Line, Ethernet, USB. A channel from a CAN bus and a channel from an ECU often carry the same name and do not mean the same thing.

The one flag one must not overlook. Bit 0 of si_flags means simulated. A file from a test-bench run and one from a simulation look otherwise identical — same channels, same units, same time axis. Skip that bit and you later compare measurement against computation without noticing. It therefore stands in the same line as the source kind and not in a side column: Werkzeug, SIMULIERT — modell/druck.

The anchor, and the one hand-set byte. asammdf 8.8.26 wrote it: two channels with their own sources, one from the CAN bus, one from a tool. The simulated flag, however, asammdf did not carry over on save — the object holds it, the written file does not. It was therefore set afterwards in a single byte, and that the file is still valid is stated not by this reader but by asammdf: the same version reads it back and reports flags == 1. Without that return path the line would be worthless — a hand-set byte the reader is measured against measures only the reader.

MD22 (property) — Attachments named instead of merely counted — closed on 2026-09-07

##AT is now read: file name, content type, original size, block size, MD5 checksum and comment stand in the outline tree under Anhänge. Counted means: the user knows something is there, not what. MDF 4 carries foreign files along — the DBC or A2L file that turns raw values into named quantities in the first place, a photo of the test setup, a log.

Bit 0 of at_flags decides everything else: does the file lie in the block, or is only its path there? In the second case the file is not in the measurement file, and the path points at a machine that may no longer exist. A reader that does not say so lets the user believe they have the DBC file for the measurement — and they have the name of a DBC file. The finding therefore states both numbers: how many attachments there are and how many of them actually lie here.

Nothing is extracted, and that is not a leftover. An attachment may be a gigabyte, and on opening a file nobody wants to read a gigabyte. What is needed on opening stands complete in the header: what lies there, how large, compressed or not, and with which checksum. Handing out the bytes is a separate call and belongs to the moment somebody wants them.

MD5 (property) — CANopen date and time as timestamps — closed on 2026-09-25

Both data types now come back as timestamps, no longer as raw bytes. CANOPEN_DATE (7 bytes): milliseconds u16, minute 6 bits, hour 5 bits with DST in bit 7, day 5 bits with the weekday in bits 5–7, month 6 bits, year 7 bits — years 0 to 69 count as 20xx, 70 to 99 as 19xx. CANOPEN_TIME (6 bytes): milliseconds since midnight in 28 bits, plus days since 1984-01-01. The bit layout follows ihedvall/mdflib, the implementation from the standard body's circle. Measured on anchor Mdfanker.canopen(): 2024-03-05 09:07:30.250, 1999-07-01, 1984-01-01, 2024-01-01 12:34:56.789 and 2025-01-25 23:59:59.999 agree in both readers. The second date does not — see MD23.

MD7 (property) — Structures and arrays are decomposed — closed on 2026-09-25

cn_composition is now evaluated. If it points at a ##CN chain the channel is a structure, and each member becomes its own column parent.child with its own data type and conversion. If it points at ##CA it is an array, and each element becomes a column name[i][j] — in the order ca_flags states (bit 6: inverse layout, last index first). At most 4096 elements are expanded; a larger array stays raw bytes and is reported, because a table with a hundred thousand columns helps nobody. Measured on Mdfanker.struktur() (paar.x, paar.y: (1, 1.5), (2, 2.5), (3, 3.5)) and Mdfanker.feld() (2 × 3 floats per record). Arrays with axes from other channels, dynamic sizes and ca_storage 1 and 2 (elements in their own groups) are recognised and reported, not expanded.

MD15 (property) — Complex numbers and MIME data — closed on 2026-09-25

Complex numbers (cn_data_type 15, 16) come back as text 1.0+2.0i: two floats of equal width, real part first, in the data type's byte order. A table column has no complex type; the text is lossless and stays readable. asammdf returns complex128 with the same values — measured on anchor Mdfanker.komplex(): 1+2i, −0.5+0.25i, 3−4i. MIME data (11, 12) stays bytes, and rightly so: what it holds is a foreign file. What is new is that the finding names the content type, which MDF keeps in the channel's unit — image/png. asammdf returns the same bytes as a uint8 array. The anchor was written by asammdf with one byte set by hand (data type 10 → 11, because asammdf always writes byte arrays as 10); that the file is valid afterwards is stated by asammdf, which reads it back and reports data_type == 11.

Neither gap nor decision, but places where the format itself is hard. They are listed because a third implementation will fail exactly there.

MD1 (property) — Transposed compression — the case you do not notice

With dz_zip_type == 1 the bytes were rearranged column-wise before deflating, so that the most significant byte of all records sits together. Forgetting to undo this yields data of the right length in which every number is wrong — no exception, no length mismatch, just wrong values. Both implementations handle it. It is listed anyway, because it is the place where a third implementation is most likely to fail; and because it was measured that asammdf writes this way by default: the anchors a_gepackt and a_listeGepackt both carry dz_zip_type = 1. Anyone testing against asammdf files therefore always tests this place, whether they mean to or not.

MD3 (property) — Byte order lives on the channel, not on the file

Two channels of the same record may have different byte orders — UINT_BE next to REAL_LE. Deciding the order once for the whole file reads the second channel wrong, and silently so: 258 becomes 513. Measured on Mdfschreiber.grossEndig(); both implementations are correct.

MD6 (property) — The invalidation bit — table versus signal

See section 2.3. Not a bug on either side, but two views of the same file. Anyone using both tools side by side gets series of different lengths and must not mistake that for a read error.

MD8 (property) — The channel beyond the record boundary

See section 2.2. The difference is not the number but the report: empty with a reason versus 0 without. A zero is a valid measurement, an empty value is not — which is why one case can be evaluated and the other cannot.

MD13 (property) — Report rather than guess — and what it costs

In eight places this reader reports something where asammdf silently carries on: a block of the wrong kind in a chain, an over-deep nesting, an unknown data type, a duplicate channel name. This is the module's consistent line — an empty finding list is a statement, not silence. The price is a findings list that must be read; the return is that a silent deviation does not pass as a measurement.

MD17 (property) — The half-open range boundary

min <= x < max, and this is measured, not inferred: for the adjacent ranges (0,10) and (10,20) asammdf returns the second range for x = 10 and the default for x = 20. Under the other reading every value on a boundary slides into the wrong range — an error that only occurs at boundaries and therefore slips through a spot-check comparison.

Findings against the reference implementation

No cause for satisfaction, but a warning for anyone using both tools side by side: at these places the results differ, and the difference is not visible from there.

MD2 (BUG there) — asammdf loses two of three records when a VLSD group is interleaved

See section 2.1 — measured on Mdfschreiber.vlsdGruppe(). Three records are in the file, asammdf 8.8.26 delivers one. We deliver three and report the VLSD group for what it is.

How to reproduce — An MDF 4 file with one data group, dg_rec_id_size = 1, containing two channel groups: ID 1 the payload group with three cycles (uint16 values 11, 22, 33), ID 2 a VLSD group (cg_flags bit 0) with two records. The records are interleaved: 1, 2, 1, 2, 1. Then MDF(file).get('Wert'). Expected: three values. Observed with 8.8.26 on Python 3.11: one value, 11. The file is produced by envisionz.fileformats.mdf.Mdfschreiber.vlsdGruppe().

MD4 (open there) — UTF-16 stays undecoded in asammdf

See section 2.4. The bytes are all there; they are simply not turned back into characters. For a tool that plots signals this hardly shows — for a table view with text columns it does.

MD23 (BUG there) — asammdf reads and writes hour and day in the CANopen date with four bits instead of five

Measured on anchor Mdfanker.canopen(), record 1: written with hour 21, day 28, weekday 7. asammdf places the weekday from bit 4 of the day byte instead of bit 5 and masks hour and day with 0x0F on reading — hour 5 and day 12 come back. So asammdf's own file does not survive the round trip as soon as an hour or day of 16 or more occurs. By mdflib's bit layout the written byte holds day 12 with weekday 4; we therefore read 2025-12-12 21:59:59.999 — that is what the bytes say, and the fault lies with the writer, not the interpretation.

How to reproduce — from asammdf import MDF, Signal; write a CANOPEN_DATE channel with the date 2025-12-28 21:59:59.999 (hour 21, day 28) and read it back with the same version. Expected: hour 21, day 28. Observed with 8.8.27: hour 5, day 12. Cause in asammdf/blocks/mdf_v4.py: day_of_week << 4 on writing (lines 3426 and 4469), hour & 0xF and day & 0xF on reading (lines 8925 f.) — weekday one bit too low, masks 0x0F instead of 0x1F.

MD24 (BUG there) — asammdf lists a wrong offset in an array's channel list

Measured on anchor Mdfanker.feld() (2 × 3 floats, offset 8): asammdf lists the elements as channels of their own and gives offset 24 for feld[1][0] — the same place as feld[0][2]; 32 would be correct. The values asammdf reads are nevertheless right. The error sits only in the list — anyone building their own accesses from it reads the wrong element.

How to reproduce — The file md7_feld.mf4 from Mdfanker.feld(): one channel feld, REAL_LE 64 bits, offset 8, cn_composition pointing to ##CA with ca_type 0, ca_storage 0, sizes 2 × 3, ca_byte_offset_base 8. Open MDF(file) and print the group's channel list (mdf.groups[0].channels, each name and byte_offset). Expected for feld[1][0]: offset 8 + 3 · 8 = 32. Observed with 8.8.27: 24, the same as feld[0][2]. MDF(file).get('feld') on the other hand returns the correct values.

What is hard about the format itself

The link count lives in the block, not in the standard. A ##CN has at least eight links, more with attachments and defaults. Looking for the body at a fixed offset reads nonsense in every file that has an attachment — and it will be the file a customer sends, not the one you developed with.

The same eight characters for two formats. MDF 3 and MDF 4 both start with MDF . They are distinguished by the number at offset 28 (330 versus 410), not by the text. A reader checking the text takes an MDF 3 file for an MDF 4 file and then reports a block error instead of a format error — the message is not wrong, but it sends you down the wrong path.

The raw value is not the measurement. The record almost never holds the physical quantity but a uint16 from the control unit. Twelve conversion types sit between them, and two of those are little languages in their own right. A reader that skips the conversion delivers numbers that look like measurements and are orders of magnitude off.

Compressed does not only mean deflate. See MD1. This is the one place in the format where a mistake produces neither an exception nor a length mismatch.

What is good about the format: the block tags are readable (##CG appears in plain text in the file), every length precedes what it measures, and the links are absolute file offsets rather than relative jumps. A damaged MDF file can be traced by hand with a hex editor and patience — which is true of very few binary formats.

The Java implementation — where this reader stands among its own kind

Why this section. Every other comparison in this module measures against a tool in a different language. That is good against misunderstandings of the format and says nothing about where this reader stands among its own kind. What matters is the distinction between a pure reimplementation in Java and a wrapper around a C library: only the reimplementation solves the same task under the same conditions.

A pure Java reimplementation exists: R1tschY/mdf4j ("Reading channels using pure Java", lazy loading, Apache-2.0), on Maven Central as 0.2.0, supporting MDF 4.00 to 4.20. It is a young, small project — before a measurement one would have to check it against real files oneself. Not measured.

Beside it again org.eclipse.mdm.openatfx.mdf with its heavy tree and a possible JNI wrapper around the C++ library ihedvall/mdflib. The situation is therefore the same as with MDF 3: in Java there is something, but nothing established.
