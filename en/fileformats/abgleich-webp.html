WebP — comparison against Google's specification and against Pillow

As of: 2026-09-07
Our implementation: envisionz.fileformats.webp.WebpDatei with Vp8l, Vp8lbits, Vp8lhuffman for the lossless and Vp8, Vp8bereich, Vp8tafeln for the lossy branch, plus Webpbild and Webpstueck, read-only, no third-party library
Specification: WebP Container Specification and WebP Lossless Bitstream Specification (Google) for the container and the lossless branch, RFC 6386 for VP8 — all three public; references give chunk names and sections
Compared against: Pillow 12.2.0 and 12.3.0 (Python, via libwebp); for the colour profile additionally ImageCms (lcms2)
Test bench: envisionz.fileformats.webp.Webpprobe — 6429 checks, twenty-eight anchors, thirty-six counter-tests; plus Vp8probe — 148 checks, nineteen foreign anchors, thirty-one counter-tests

The reference implementation. The measurement went through Pillow, but it measured against libwebp. Pillow's WebP plugin is a pure binding: it hands everything to the C module around libwebp and has no decoder of its own. libwebp is Google's C library, created as part of the Make the Web Faster initiative, and it is explicitly the reference implementation of the WebP specification. Whatever reads or writes WebP — browsers, image tools, Python — ends up using it.

Why this one. Because for WebP the reference product is the reference implementation. That changes the meaning of the whole comparison: it does not measure two opinions against each other but our own against the only one. A difference here would always be our error, never a finding against the other side — and it is therefore no accident that this is the only one of the five image formats with no finding against the reference product. A second, independent reference for VP8L effectively does not exist; everything that reads WebP uses libwebp.

Feature comparison

"WebP" is not a format. It is a RIFF container holding two entirely different image formats: VP8L, lossless, a self-contained method; and VP8, lossy, the still frame of a video format. The two have nothing in common but the container — not the bit reader, not the coding, not the colour representation.

Until 2026-09-06 this toolkit read the lossless branch completely and the lossy branch not at all. That was not a half-measure but a named boundary, and it stood in this document as a gap. Since then it is both. A lossy image with alpha therefore needs two decoders side by side: the colours from VP8, the alpha from VP8L.

And the two are tested differently. VP8L is lossless — a correct reader must hit every byte. VP8 is lossy but integer and completely specified: there too a correct reader must hit every pixel, bit-exactly, down to the rounding in the loop filter. That is the difference from JPEG, where two correct readers may produce different numbers. The test therefore demands a checksum over the whole image here, not a bound.

What was measured

Twenty-two foreign anchors: seventeen were written by Pillow 12.2.0 via libwebp, five were built by hand and read back by Pillow. The lossless branch is thereby measured completely — all four transforms, eleven of the fourteen predictors, the colour cache, several Huffman groups, the single-symbol code and the distance map.

The detour through a second implementation

VP8L is the most intricate method in this collection: a bit reader, Huffman codes over Huffman codes, back references over pixels, a colour cache and four transforms applied in reverse. Such a chain has the unpleasant property that every error makes everything after it unreadable — you do not get a wrong pixel, you get an exception three hundred bits later.

The decoder was therefore built twice: first as a throwaway in Python, into which one could look with print at any point, and only then in Java. The Python version ran against 120 randomly generated images before a line of Java existed; the Java version was green on its first run. The detour found three errors, none of which is stated — or stated clearly enough — in the specification:

Twenty-one counter-tests, three of them sharpened afterwards

Of twenty-one interventions eighteen went red at once. The three green ones all concerned the same thing: a branch no anchor touched. The Select predictor, the half-difference predictor, the colour cache, the single-symbol code, the top-right neighbour, alpha filters 2 and 3, and the scale field in the VP8 frame header — none of these occurred in the first fourteen anchors, because libwebp's encoder always picks the same few paths for ordinary images.

The matching images were found by search: the Python throwaway was rebuilt to record which predictors, which colour cache and which code form occur in a file; then a few hundred generated images ran through seven encoder effort levels until every missing branch had a file. That is how the anchors waehlen, farbcache, einsymbol, praedvielfalt and obenrechts came about — each one makes exactly one counter-test red. Filters 2 and 3 occurred in no generated file; they had to be built by hand.

A counter-test that stayed green — and the bug behind it

The intervention "drop the alpha plane when compositing" stayed green although three animation anchors were in place and one of them expressly carries a semi-transparent frame. The reason: all three are lossless. With VP8L every pixel carries its alpha already and the separate plane is empty there — the branch that inserts it was never entered.

So a twenty-eighth anchor was added: the same two frames, written lossily. Colour and alpha then lie in two chunks — the second frame carries an ALPH of ten bytes and a VP8 of sixty. And the new anchor immediately exposed a real bug that had nothing to do with the intervention: the first canvas came out entirely transparent.

Because Vp8 delivers its pixels as pure RGB with an alpha of zero — a VP8 stream knows nothing of alpha, and rightly so. On a still it does not show, because the alpha stands separately beside it and the probe measures both apart. Only on a canvas does it become a computation: transparent pixels laid on top of each other give nothing. A frame without ALPH is opaque and not transparent — and that had to be written down first.

While searching, a second place of the same family turned up: a frame's alpha plane was read only when its VP8 could not be read. A lossy frame with an alpha plane therefore lost it precisely when everything worked. Both are now counter-tests of their own.

The lossy branch: first in Python, then in Java

The same route as with VP8L, and for the same reason: a defect in VP8 does not crash, it produces an image. The reimplementation was written in Python first and measured against 128 images — 1 × 1 to 128 × 96, every quality level, one to four segments, filter strengths 0 to 100, sharpness 0 to 7, simple and strong filter, all seven methods of cwebp. The comparison went against dwebp -pgm, that is against the YUV planes before any colour conversion, and additionally against Pillow's RGB. 128 of 128 equal, pixel by pixel in both cases. Only then came the Java version, and it was green on its first run.

A single error in the reimplementation, instructive enough to stand here: the four above-right samples of a macroblock belong in rows 3, 7 and 11 of the scratch buffer. In libwebp this reads as {@code top_right[BPS]} on a {@code uint32} pointer — the pointer steps in groups of four, so the line looks like "row 1". Done wrong, only the last column of every macroblock is off: twelve of 391 pixels on a 23 × 17 image, and on a smooth gradient nothing at all. An anchor of noise found it. The same lesson as with VP8L: smooth anchors test nothing.

Thirty-one counter-tests, three of them sharpened afterwards

Twenty-eight went red at once. Three stayed green, and as with VP8L the answer was not "another anchor" but first calculate under which condition the intervention yields a different number. Two conditions could be met and brought three new anchors: the lower bound of the Y2 AC step only bites at quality 100 on a gentle gradient; the sharpness cap on the interior filter limit only matters with fine structure; and an empty macroblock wrongly filtered internally only shows on hard steps. All three counter-tests went red afterwards.

The third could not be saved, and that was the most useful result of the whole round. The intervention served 255 instead of zero past the end of a partition. The calculation showed: across 144 valid files nothing is ever read there, so no value there can change anything. That settled the counter-test — but not the insight: if nothing is ever read there, a read beyond it is a sign of a truncated file. Before, such a file was silently read to the end and an image delivered. Now it is named, and there is a new counter-test for it, and it is red.

What is hard about the format

Two bit directions in the same file. VP8L's bit reader delivers bits from the least significant end of each byte; numeric fields assemble them from the bottom, but Huffman codes from the top. It sounds contradictory and is not — the reader delivers a sequence of bits, and how one turns them into a number is a second question. Confuse the two and you get a bit stream that reads for a few hundred more bits and then yields nonsense.

A Huffman code with exactly one symbol consumes no bit. There is nothing to distinguish, so nothing is read. The specification does not say this clearly; the implementation does. And it happens often: every uniform area, every channel constant over a whole image leads to it.

The "top right" neighbour at the right edge is the first pixel of the same row. The buffer is contiguous, and the authoritative implementation simply reaches one element further — which at x = width-1 lands exactly there. It looks like an oversight and is part of the definition. Fall back to the upper neighbour instead and you get one wrong column; with smooth images it does not show.

The distance map is why VP8L packs smaller than PNG. A back reference with code 2 does not mean "two pixels back" but "the same place one row up". For patterns repeating row-wise that costs a small code, while a method with a plain pixel distance would have to count the whole image width. The anchor streifen is 80 × 60 and the file is 52 bytes.

Four transforms, backwards. They stand in the file in the order in which they were applied when packing, and must be undone from the back when reading. The colour-indexing transform changes the width along the way: the decoded image is narrower than the picture, and only undoing it restores the width. Reverse the order and every image with two transforms comes out as something colourful with no relation to the picture.

What is good: that the container and the image format are cleanly separated. A reader that cannot do VP8 need not stay silent — it reads the container, states the size, counts the chunks and delivers the alpha plane. With GIF or JPEG there is no such separation: there one can do either everything or nothing. That this reader no longer needs the separation does not make it less right — it is what made the intermediate state usable at all.

The items

The Note column names the kind in front of the identifier. Only the gaps are work.

Our open gaps — this is the work

Deliberate decisions — nothing to do

W20 (decided) — No route through the general format detection

Datenquellen.oeffne rejects a WebP and points at WebpDatei.lies. The same reason as with GIF (I15), BMP (B1), PNG (P1) and TIFF (T24): an image is not a table. With WebP the same wrinkle as with TIFF applies: a file can contain several images.

Decided on 2026-09-06. The item stood as a gap in five image formats with identical wording (BMP B1, GIF I15, PNG P1, TIFF T24, WebP W20). It is not one: a Datenquelle is a table view, and an image is not a table. A view with one row per pixel (x, y, red, green, blue) would be possible — at 4000x3000 that is twelve million rows, and what it would buy does not answer the question "what is in this file" but a different one. The readers exist and are named in the rejection message; that is the information the user needs. VTK (V9) and HDF4 (H8) are different: their content really is tabular, and there the view is being built.

W7 (decided) — Two bit directions, two classes

The bit reader ({@code Vp8lbits}) and the Huffman code ({@code Vp8lhuffman}) stand apart although both are only a few lines. The reason is the risk of confusion: the same bit stream is assembled bottom-up in one place and top-down in the other, and a reader that has both in one class will sooner or later write one rule where the other belongs. Both carry the difference in their class comment.

W17 (decided) — The size is read twice

The container reader takes width and height from the frame header itself, although {@code Vp8} delivers them too — three bytes behind the start code, without a decoder. The reason is the alpha plane: it lies in the ALPH chunk, needs width and height, and should still come out when something is wrong with the VP8 stream. The top two bits of each size word are a scale and are masked out — libwebp always writes zero there, so a missing mask shows on no foreign file. The probe therefore sets them by hand.

W26 (decided) — Triangular upsampling, as libwebp does

How a subsampled chroma component returns to full size is in no document. libwebp's method was adopted: over the two diagonals of a square of four chroma values, weights 9:3:3:1 — the same idea as libjpeg's for 4:2:0, written differently. Not because it is prettier but because it is the most widespread: whoever else looks at this image sees it this way. And only then can one check bit-exactly against a foreign reader.

W28 (decided) — Inter frames are not read

Everything that makes VP8 a video format — motion compensation, reference frames, the golden and altref frames — is absent here and is meant to be. A WebP still is always a key frame, and every frame of an animation must be one too. A frame that is not one is rejected by name rather than half-read: on its own it could not be displayed at all, because it describes only the difference to a frame that is nowhere.

W21 (decided) — Writing

Pillow writes WebP via libwebp and supplied seventeen of the twenty-two foreign anchors. This module reads. The five hand-built anchors are test equipment, not an output path — for the three alpha planes the filtered plane was even encoded by Pillow; only the container around it was built.

Properties of the format

W5 (property) — The animation on the canvas — closed on 2026-09-07

leinwaende() delivers one canvas per frame, each as large as the VP8X says. A frame is usually smaller than the canvas and sits at an offset; whoever displays it on its own sees a fragment. Only here does it become an image.

Four places where a reader goes silently wrong. First: the corners stand as half pixels — a frame can only begin at an even position. Second: the blend flag says the opposite of its name — bit 1 set means not to blend. Third: the background colour is BGRA as bytes and already ARGB as a little-endian number; take the four bytes individually and assemble them "correctly" and you swap red and blue. Fourth: a frame without ALPH is opaque and not transparent — see 2.6.

It is measured against five anchors, and four of them exist only because libwebp never writes certain forms: it always stores the changed sub-rectangle instead of disposing, and it picks the blend flag itself. Two anchors are therefore rewritten by hand from a file Pillow wrote — for one of them a single byte —, and Pillow reads both back and supplies the expected values. One byte of difference and the whole canvas is a different one.

W29 (property) — Disposal: the specification and libwebp say different things

The specification says: the canvas starts with the background colour from ANIM, and disposal 1 fills the frame's rectangle with it again. libwebp — and therefore every viewer using it, which is practically every one — starts with transparent black instead and disposes there too, treating the colour as a mere suggestion. The specification itself permits this: it says a viewer with its own idea of a background may ignore the value.

Both are available, and the choice is stated. leinwaende() follows libwebp, because that is what a viewer shows; leinwaendeAufHintergrund() follows the wording. The difference is measurable only on a file carrying disposal and a set background colour — and because libwebp never writes disposal, such a file exists only if one builds it by hand. That is exactly what the anchor folgeEntsorgt is for.

This is not a bug on either side but a place where a specification permits two readings and the widespread implementation has made one of them the habit. Whoever checks only against libwebp mistakes its reading for the format.

W4 (property) — Colour profile and side data — closed on 2026-09-07

All three side chunks are interpreted. ICCP: the profile header with class, colour space, connection space, version, platform, rendering intent, creation time and creator, plus the desc and cprt tags as text. EXIF: the whole directory, field by field, with names. XMP : the text. The raw bytes remain available beside them.

The EXIF is not read here but by the TIFF reader. An EXIF chunk is a complete TIFF stream without an image — header, directory chain, fields, and no pixels. TiffDatei.lies rightly rejects such a thing: ImageWidth and ImageLength are mandatory in an image file. So on 2026-09-07 the field reading was extracted as Tiffverzeichnis (item T26); TiffDatei.nebenkette delivers the same directories without claiming an image stands behind them. One reader instead of two — and the same work waits in JPEG (APP1) and in PNG.

The sub-directory does not hang in the chain. ExifIFD and GPSInfo stand as an offset on a field, not as the next link. Whoever follows only the chain sees a camera image's maker, model and orientation — and nothing of exposure time, aperture, sensitivity or focal length, because those all live in the sub-directory. Both are followed.

Three byte orders in one file. The RIFF container is little-endian, the ICC profile is always big-endian, and the EXIF stream says so itself in its first two characters — II or MM. A reader that carries over the container's order reads a profile size of one and a half billion; one that carries over the profile's reads the EXIF backwards. Every chunk brings its own.

Still nothing is applied — the colours come out as they stand in the file. Building colour management from the profile is a discipline of its own; Pillow does not do it either. The difference to the earlier state is nevertheless the essential one: before, the bytes lay there; now it says what is in them. The same situation as PNG (P2) and BMP (B4).

W1 (property) — RIFF alone says nothing

The four characters RIFF also begin every WAV and every AVI file. Only the four characters at offset eight say what is inside. The detection therefore checks both, and the variant additionally says whether the image is lossless (VP8L), lossy (VP8 ) or extended (VP8X) — with this format that is not a detail but the question of whether the pixels come out at all.

W2 (property) — The pad byte

If a chunk's length is odd, one byte follows that does not count. Forget it and you are one byte off from the first odd-length chunk on and read the rest of the file as nonsense. With a simple image of one chunk it never shows — hence an anchor with five chunks, at least one of them odd.

W3 (property) — The extended header

VP8X carries the canvas size and five flags: ICC profile, alpha, EXIF, XMP and animation. The size there is authoritative and need not match the first image — with an animation it almost never does.

W6 (property) — Half pixels

A frame's corner is stored as half the number: a frame can only begin at an even position. Fail to double it and every frame lands at half the distance — at (0,0) it does not show, at the second frame it does.

W8 (property) — A code with one symbol

See section 3. The anchor einfarbig covers the simple form, einsymbol the fully coded one — and the second was added only when a counter-test stayed green.

W9 (property) — The colour cache first, then the meta Huffman

The order is the first place where a reader following the specification goes wrong. Read the meta Huffman first and the bit stream is off by one to five bits from there, and the next Huffman tree is nonsense — the message then reads "code longer than 15 bits" and points at a place that has nothing to do with the error.

W10 (property) — The distance map

See section 3. Codes up to 120 are not pixel distances but an offset of up to eight to the left and up to seven rows up, encoded as (rows << 4) | (8 - columns).

W11 (property) — The colour cache

The most recently written pixels stand in an array addressed by a hash of their colour: (0x1e35a7bd · colour) >>> (32 − bits). The factor is part of the definition; a different one yields an image that is right over long stretches and wrong at the repetitions.

W12 (property) — Fourteen predictors

Eleven of them occur in the anchors. The missing 3 and 9 both reach for the top right neighbour, whose edge case is covered via predictors 5 and 10. The most interesting is the thirteenth: it computes the half difference and divides towards zero rather than rounding down — for negative differences that is a different value.

W13 (property) — Top right at the right edge

See sections 3 and 2.1. The anchor obenrechts was sought specifically for this; 97 of its 527 pixels depend on it.

W14 (property) — The colour table bundles pixels

With at most 2, 4 or 16 colours, 8, 4 or 2 pixels stand in one byte, and the decoded image width is correspondingly smaller than the real one. On top of that the table is stored as differences: every entry is the difference to the previous one. Two traps in one transform.

W18 (property) — Alpha is lossless even when the colours are not

For a lossy image with alpha, the alpha plane lies in the ALPH chunk and is stored losslessly there — either byte by byte or as a headerless VP8L stream whose green channel carries the values. That is why this reader delivers the shape of a cut-out pixel-exactly without knowing a single colour value. For a file-inspection tool it is the most useful property of the whole format.

W19 (property) — The alpha plane's first row

It has no upper neighbour and is therefore unfiltered horizontally for every filter — including "vertical" and "gradient". Overlook it and you get exactly one wrong row, and at the top edge that barely shows.

W16 (property) — VP8 is the still frame of a video format

This is not an aside but the reason this branch fits into a toolkit for file formats at all. A key frame knows no motion compensation, no reference frame and no sequence; what remains is a still-image method. Everything else in VP8 falls away — not as a gap, but because it cannot occur in an image file. What remains is substantial nonetheless: a range decoder, macroblocks, fourteen prediction modes, two transforms and a loop filter in two flavours.

W22 (property) — A row reads from partition row mod count

The coefficients lie in one to eight partitions, and a macroblock row reads not in sequence but from partition {@code row mod count}. With four partitions every fourth row reads from the same one. Whoever works through them in order gets noise from the second row on. The catch when testing: cwebp always writes a single partition, in all 128 files measured. The whole branch would have stayed a promise had a small program of our own against libwebp's C interface not produced three anchors with two, four and eight partitions.

W23 (property) — The Y2 block

In a macroblock with 16 × 16 prediction the sixteen DC terms of the Y blocks stand not with their blocks but together in a block of their own, transformed once more — with a Walsh-Hadamard instead of a cosine transform. Its quantisation steps are deliberately bent: the DC step is doubled, the AC step stretched by 155/100 and floored at eight. All three look like fine-tuning and are not. The floor of eight only bites at very fine quantisation; it needed an anchor of its own.

W24 (property) — Above-right is not where one expects it

The subblocks at the right edge of a macroblock need four above-right samples that belong to the neighbour that has not been read yet. Taken instead are the four samples from the row above — and they must be copied into rows 3, 7 and 11 of the scratch buffer. In libwebp this reads as {@code top_right[BPS]} on a {@code uint32} pointer and therefore looks like row 1. Done wrong, only the last column of every macroblock is off: on a 23 × 17 image twelve of 391 pixels, on a smooth gradient nothing at all. It was the only error in building this reader, and it was found only because one anchor was noise.

W25 (property) — The loop filter is part of the image

It is not post-processing one could leave out: the filtered image is the result. Two flavours, four to six samples per edge, an outer and an inner threshold, plus special handling for hard edges. Three details one cannot guess: the clamp is not symmetric — minus 16 to 15, not to 16; the edge between two macroblocks gets four counts more headroom than the interior edges; and a macroblock without coefficients is not filtered internally at all, because no block boundary arose there. The last two needed anchors of their own.

W27 (property) — Where nothing is ever read, truncation shows

Across 144 valid files from libwebp the range decoder never once reaches past the end of its partition — the counter is zero without exception. That makes a read beyond it a usable sign of a truncated file. This was found by a counter-test that stayed green: it served 255 instead of zero past the end, and no anchor noticed. The counter-test could not be saved — the test could. Before, a truncated file was silently read to the end and an image delivered.

Findings against the reference implementation

W30 (BUG there) — Pillow reports a colour profile's creation date one month early

ImageCmsProfile.profile.creation_date returns the month minus one. A profile whose header names 25 December 2026 comes out as 25 November 2026. And a profile from January does not come out at all but raises ValueError: month must be in 1..12, because the month falls to zero. A profile from January is therefore unreadable through that property.

The cause lies visibly at the boundary to lcms2: its struct tm counts the month from zero as C does, and the conversion to datetime does not adjust. The field in the profile header itself counts from one — it is a dateTimeNumber of six unsigned sixteen-bit values, and there a nine stands for September. Our reader takes the number as it stands.

How to reproduce — Build an sRGB profile: b = bytearray(ImageCms.ImageCmsProfile(ImageCms.createProfile('sRGB')).tobytes()). Set the twelve date bytes: b[24:36] = struct.pack('>6H', 2026, 12, 25, 13, 14, 15). Then read ImageCms.ImageCmsProfile(io.BytesIO(bytes(b))).profile.creation_date. Expected: 2026-12-25 13:14:15. Observed with Pillow 12.3.0: 2026-11-25 13:14:15. With struct.pack('>6H', 2026, 1, 3, 0, 0, 0) — that is January — the same call raises ValueError: month must be in 1..12.

W31 (BUG there) — An EXIF rational written as a tuple becomes two SHORTs

Whoever writes an exposure time as ifd[33434] = (1, 250) — the obvious thing — gets field type 3 (SHORT) with count 2 in the file. In the EXIF specification ExposureTime is a RATIONAL, that is type 5 with count 1. Pillow reads its own file back correctly because it makes the same guess on reading; every other reader gets two numbers where a fraction should stand, and an exposure time of 1 instead of 0.004.

The correct form is ifd[33434] = IFDRational(1, 250); then type 5 stands in the file. The difference is invisible anywhere as long as one writes and reads with the same tool — and that is exactly what makes it dangerous. That Pillow has a type table it shows elsewhere: for XResolution it warns tag 282 had too many entries: 2, expected 1. Inside the ExifIFD that check does not apply.

How to reproduce — Save an image with EXIF: ex = Image.Exif(); ifd = ex.get_ifd(0x8769); ifd[33434] = (1, 250), then im.save('x.webp', exif=ex). Cut the EXIF chunk out of the file and look at the sub-directory's fields. Expected per the EXIF specification: ExposureTime, type 5 (RATIONAL), count 1, value 1/250. Observed with Pillow 12.3.0: type 3 (SHORT), count 2, values 1 and 250. With IFDRational(1, 250) instead of the tuple, type 5 stands there.

W15 (open there) — Five conditions without a statement about the file

A wrong length in the RIFF header, a chunk reaching past the end of the file, a frame reaching past the canvas, a VP8 without a key frame, and a VP8X announcing an alpha plane that is not there. We report all five and read on as far as possible; Pillow throws in these cases or reads on silently. That is not a bug in Pillow — it is an imaging library, not a file-inspection tool. No bug in libwebp or Pillow was found in this measurement; among the image formats in this collection that is the exception and speaks for the implementation.

The Java implementation — where this reader stands among its own kind

Why this section. Every other comparison in this module measures against a tool in a different language. That is good against misunderstandings of the format and says nothing about where this reader stands among its own kind. What matters is the distinction between a pure reimplementation in Java and a wrapper around a C library: only the reimplementation solves the same task under the same conditions.

No pure Java implementation in the JDK and none established beside it. javax.imageio reads PNG, JPEG, GIF, BMP and TIFF, but no WebP — this is the only one of this module's six image readers for which the JDK has no counterpart. The common Java routes (webp-imageio and relatives) are JNI wrappers around Google's libwebp.

This document therefore stands differently from its four neighbours: there a Java comparison sat in the JDK, here there is none. For the lossless branch this reader is, as things stand, the only implementation in pure Java.
