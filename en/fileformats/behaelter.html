Container formats: ZIP, Compound File and Office packages – background

How a ZIP directory is read from the back, how a Compound File stores its data streams in sectors and chains, and how a PPTX makes a slide from both.

What this is about: a file that contains a file system

Many formats are containers: they hold several named parts, each of which could be a file in its own right. A workbook (XLSX), a presentation (PPTX), a NumPy bundle (NPZ), a Java archive and the old Office files (PPT, DOC, XLS) are all containers, in just two designs: ZIP (the new ones) and Compound File (CFB, the old ones). A reader for the format must first be able to read the container, then the directory, then the parts; and it must know in which part the sought content stands. Both container readers are hand-written here (ZIP in framework-compress, CFB in fileformats).

ZIP: the directory is at the back

A ZIP archive consists of local headers with the (usually deflate-packed) data, followed by a central directory and at the end the end of central directory (EOCD, signature PK 05 06, value 0x06054b50). The EOCD gives count, size and offset of the central directory; each entry there (0x02014b50) gives name, method, packed and unpacked size, CRC-32 and the offset of the local header (0x04034b50). The reader therefore goes from back to front.

More than 65 535 entries or sizes over 4 GB do not fit the 16- and 32-bit fields; then those fields hold 0xFFFF or 0xFFFFFFFF, and the true values lie in the Zip64 end record and in the extra field with ID 1. An empty archive has no local header, only the EOCD (PK 05 06); that was a boundary case of detection. The checksum CRC-32 is compared on unpacking.

ZipQuelle turns the container into a data source: the table of contents as a table, one row per entry with name, method, both sizes, checksum and time. That is the question one has of an unknown ZIP; nothing is unpacked in the process.

Pseudocode – Zipdatei.oeffne (abridged)

suchweite ← min(size, 22 + 65535)
ende ← last occurrence of 0x06054b50 in the last suchweite bytes      from the back
anzahl, verzeichnisGröße, verzeichnisVersatz ← fields of the EOCD
if anzahl = 0xFFFF or size = 0xFFFFFFFF or offset = 0xFFFFFFFF:
    read Zip64 locator (0x07064b50) → Zip64 end record (0x06064b50);  take the values there
for each entry from verzeichnisVersatz:                                signature 0x02014b50
    name, methode, gepackt, ungepackt, crc, versatzLokalerKopf
    if a field = 0xFFFFFFFF: read extra field 1 (Zip64)
if number of entries ≠ anzahl: finding

Source: envisionz-framework-compress/src/envisionz/compress/zip/Zipdatei.java (oeffne, zip64), envisionz-framework-fileformats/src/envisionz/fileformats/zip/ZipQuelle.java.

Compound File: a file system made of sectors

The old Office format is a Compound File (also OLE2): a small file system inside a file. It has a 512-byte header (signature D0 CF 11 E0 A1 B1 1A E1), followed by sectors of equal size 2s2^{s} bytes (sector shift ss in the header: 9 for 512 bytes, 12 for 4096). Sector nn begins at (n+1)⋅sector size(n+1)\cdot\text{sector size}, because the header counts as sector −1. What belongs to which data stream is told by the FAT (allocation table): an array with one entry per sector that names the next sector of the stream. Special values: 0xFFFFFFFE end of chain, 0xFFFFFFFF free, 0xFFFFFFFD sector of the FAT itself, 0xFFFFFFFC sector of the DIFAT.

Example: a stream begins at sector 5; fat[5] = 6, fat[6] = 9, fat[9] = 0xFFFFFFFE. The stream therefore lies in sectors 5, 6 and 9, in this order, and begins at bytes 3072, 3584 and 5120 (at 512 bytes). A sector holds 512/4=128512/4 = 128 FAT entries; the 109 FAT sectors that fit in the header address 109⋅128⋅512=7143424109 \cdot 128 \cdot 512 = 7\,143\,424 bytes. For larger files the DIFAT (directory of FAT sectors) continues in a chain of its own; its last entry in each case points to the next DIFAT sector.

The directory entries (128 bytes each) themselves lie in a sector chain; the first is the root, the others form a tree of storages (folders) and streams. Small streams are uneconomical in 512-byte sectors; streams below the mini-stream cutoff (from the header, 4096 bytes in the usual case) lie in the mini stream: a data stream of the root that is divided into mini sectors (shift from the header, 64 bytes in the usual case) and has its own table (MiniFAT). A reader that can do only the big path fails on real Office files at once, because their header streams are almost all small.

Pseudocode – Cfbdatei.oeffne and bytes

kopf ← 512 bytes;  check signature
sg ← 2^sector shift;  msg ← 2^mini shift;  grenze ← mini-stream cutoff
fatOrte ← the first up to 109 entries in the header (until FREI or ENDE)
difat ← first DIFAT sector
while difat is not ENDE/FREI and guard counter:                   cycle → finding, stop
    fatOrte += all entries except the last;  difat ← last entry
fat[] ← the entries of all FAT sectors
minifat[] ← kette(fat, first MiniFAT sector)
eintraege ← kette(fat, first directory sector), 128 bytes each
ministrom ← bytes of the root  (from kette)

bytes(e):
    if e is not a stream: exception;   if size = 0: empty
    if size < grenze:  ausMinistrom(e)                via minifat and ministrom
    else kette(fat, startsektor, size)

kette(fat, start, größe):
    s ← start;  besucht ← {}
    while s is not ENDE/FREI/FAT/DIFAT and counter < |fat| + 16:
        if s already visited: finding “runs in a circle”, stop
        append sector s;  if größe reached: stop
        s ← fat[s]
    cut to größe;  if too short: finding

Source: envisionz-framework-fileformats/src/envisionz/fileformats/cfb/Cfbdatei.java (baue, kette, sektor, bytes, ausMinistrom). From the names of the streams, Formaterkennung derives the format: PowerPoint Document means PPT, WordDocument DOC, Workbook or Book XLS.

Decision in the framework: broken containers are named, neither repaired nor passed over: a sector chain in a circle, a DIFAT in a circle, a version that prescribes a different sector size (version 3: 512, version 4: 4096), a header that names more FAT sectors than were found – each ends up in befunde(). A counter guard and a visited set keep a cyclic chain from halting the reader.

PPTX: a package of parts and relationships

A PPTX is a ZIP with XML inside, exactly like a workbook. The substructure (Zipdatei and a streaming XML reader) is the same as for XLSX; the rules differ. Parts refer to each other not by file names but through relationships (_rels/*.rels). Four places where a reader goes silently wrong:

  1. The slide number is not in the file name. The order is in ppt/presentation.xml as a list of references that point through ppt/_rels/presentation.xml.rels to files. Anyone who counts slide1.xml, slide2.xml, … has the wrong order from ten slides on (slide10 comes alphabetically before slide2), and if someone moved slides it is wrong altogether.
  2. Layouts and masters also carry text (“Click to edit Master title style”). Only the parts the slide list points to are read; from the layout only its name is taken.
  3. A paragraph splits into runs. A format change in the middle of a word makes Messreihe two runs (<a:r>). Text is assembled per paragraph (<a:p>), and <a:br> becomes a line break.
  4. The title is not the first text but the shape with the placeholder title or ctrTitle.

The position of each shape is in EMU (English Metric Units): position x,yx, y and size as whole numbers; the data fields of Folienplan are named x, y, breite, hoehe “in EMU”. In addition come rotation, fill, line and theme, so that a slide can be redrawn.

Source: envisionz-framework-fileformats/src/envisionz/fileformats/pptx/PptxQuelle.java (oeffne, beziehungen, layoutteil), pptx/lage/Folienplan.java.

How it is checked

  • Cfbprobe: the test file is built in the probe – a complete, rule-conforming Compound File from nothing (header, allocation table, directory, mini stream) – so that every value can be held against a known target. There is deliberately one large and one small stream so that both paths (FAT and MiniFAT) are taken. The writer stays in the probe because the module is read-only.
  • Compoundprobe: the three known streams lead to PPT, DOC and XLS; a Compound File without a known stream leads to OLE2.
  • Pptxprobe: a genuine PPTX from a third-party tool (python-pptx 1.0.2) with twelve slides whose order was reversed after writing (slide 1 lies in slide12.xml), so that the slide-number trap is in the anchor; plus a self-built paragraph of three runs with a line break and a field. Zipquellenprobe: among others the empty archive.

Limits

  • The table of contents of a ZIP is read, not unpacked; the caller opens contents as files of their own.
  • For PPT, DOC and XLS the module reads the container and names the streams but does not read their content (see overview).
  • Nothing follows from the container itself about the validity of the parts: a ZIP with the right directory structure can contain XML that the PPTX reader rejects.
