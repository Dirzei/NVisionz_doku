HDF5 — comparison against specification, h5py and jHDF

As of: 2026-09-25 (Merkmalstabellen vom 2026-08-26, Runde 46; siebter Nachtrag 2026-09-25)
Our implementation: envisionz.fileformats.hdf5 — 34 core classes plus 10 in the envisionz.fileformats.hdf5.netcdf package, read-only, no third-party library
Specification: HDF5 File Format Specification Version 4.0 by The HDF Group — freely available, which is why section numbers appear here
Compared against: h5py 3.16 / HDF5 2.0 (measured)
And against: jHDF — feature column from the 0.5.11 changelog, values measured against 0.13.0 on 2026-09-06
Test bench: Leserprobe 120, Entpackerprobe 70, Netcdf4probe 53, Hdf4probe 113, Langformprobe 172, Nachtrag7probe 73 — 601 checks in total

The reference implementation. h5py is a pure binding to the HDF5 C library, started by Andrew Collette and maintained by a community. Measuring against h5py therefore does not measure against a second opinion but against the reference implementation: library and format both come from the HDF Group, the non-profit successor to the HDF work at NCSA.

The second reference implementation. jHDF by James Mudd is a pure Java reader for HDF5, built explicitly from the format specification and without HDF Group code — not a wrapper around the C library but a reimplementation under the same conditions as this one. Reading is broadly covered, writing only in limited cases; what it cannot do, it reports. Its column in this document comes from the change log, not from a measurement of our own — as the header also states, and as should be kept in mind when reading the table.

Why this one. Because h5py talks to the HDF Group's C library and is therefore the reference itself: format and library come from the same place. jHDF stands beside it as a second reference for a specific reason — it too is a pure reimplementation in Java, that is, the implementation solving the same task under the same conditions as this one.

How this was measured

Two kinds of measurement underlie this comparison. The large one is the run over The HDF Group's 460 official test files (section 2.1); it dates from 2026-08-26 and underpins the feature tables above. The small one was added on 2026-09-05, when this document was brought into the common form: four own test files and five netCDF-4 anchors, each through both readers.

The 2026-09-05 run in detail. probe_grundlagen.h5, probe_gepackt.h5, probe_messreihe.h5, probe_verbund.h5 from envisionz-app-hdf5reader/proben and the five anchors from Netcdf4anker were run through envisionz.fileformats.hdf5 and through h5py 3.16; the netCDF-4 anchors additionally through netCDF4 1.7.4. Dataset paths, types, shapes and values were compared. Exactly one kind of divergence came out — and it sits not in the HDF5 reader but in the table view above it: see LF1.

With the netCDF-4 anchors one difference stands out that is none: netCDF4 1.7.4 shows two variables in gruppen.nc, h5py four datasets. The reason is that netCDF treats the dimension variables (i, j) as axes rather than variables — same file, two views. Our reader carries them as axis columns and thereby arrives at the same two tables as netCDF4. Anyone placing such numbers side by side without knowing the views finds a bug where there is none.

What is hard about the format

This assessment comes from building this reader and checking it against 460 official test files. Every point below either caused a bug in this module or surfaced during that comparison — it is not a literature review.

The sheer number of variants

Four superblock versions, five layout versions, five chunk index kinds, three ways to store groups, three for attributes, two B-tree generations, three encodings of dataspace selection — and the combinations multiply.

A reader that handles 95 % of files may still fail on the next one. This module's bugs sat almost exclusively in rare corners: layout version 1 with chunks, shared messages version 1, filtered array indexes. All correctly specified, all rare, all undetected until the reference files.

For a format meant to carry data across decades this is the wrong direction: every new variant increases the chance that a future reader will not know it.

Missing self-description at decisive points

Repeatedly a number that is needed is not stated but must be derived:

  • How many members a multi file has is stated nowhere — one counts the distinct values in the mapping table. - How far an unlimited virtual dataset extends is not in the dataset but follows from how many source files happen to be present. - The width of the size field in filtered array entries follows a rule ("one byte more than needed, at most eight") instead of simply being stated.

A value that must be computed is a value that two readers can compute differently.

Checksums where they are least needed

The newer structures — B-tree v2, fractal heap, array indexes, object header v2 — all carry a Jenkins checksum. The older ones — superblock v0 and v1, B-tree v1, symbol tables, local heap, object header v1 — carry none at all.

Precisely the old files, which have been sitting longest and are most likely to have accumulated bit rot, are unprotected. And the raw data always is, unless fletcher32 is explicitly enabled.

No referential integrity across file boundaries

External links, externally stored raw data and virtual datasets point at other files. If one is missing, the library silently returns fill values — no message, no marker in the data model.

A dataset that is half measurements and half zeros looks exactly like one that genuinely contains zeros. This module therefore has missingSources() and prefers to refuse when the extent cannot be determined — a workaround for a format problem.

Filter plugins defeat readability

A file can become unreadable to every conforming reader through a foreign filter. Bitshuffle, blosc, zstd and BitGroom are binary extensions loaded at run time; without the filter the data is gone. In the 460 official test files this affects twelve datasets.

For a format that advertises long-term archiving this is a fundamental contradiction: the file describes itself, but its payload can only be decompressed by one particular software installation.

Valid files that look destroyed

h5clear_mdc_image.h5 is perfectly valid — but its root header lives in the metadata cache image, and at the address named by the superblock there are nothing but zeros. Anyone who has not implemented chapter III.J will consider the file destroyed. That a performance mechanism can undermine the file's basic structure is a design flaw.

Rounding is not specified

With the scaleoffset filter for floating point, whether one computes the inverse in single or double precision decides the last bit. The specification says nothing about it; it had to be determined empirically. Two conforming readers can therefore return different numbers — for a scientific data format, not a trifle.

The tree is a graph

Groups may carry hard links to their own ancestors; the reference count even says so. This module's tree traversal promptly ran into a stack overflow. That was our own bug — but the word "tree" throughout the documentation invites it.

Addresses right up against the numeric range

The multi driver places its members at 0x1999999999999999, 0x3333… through 0x7FFFFFFFFFFFFFFD. The test "address less than start plus size" overflows into negative territory there. A layout that deliberately runs to the edge of the numeric range is an invitation to overflow.

What is good about it

The core is soundly built: the chunk indexes cover the range from one block to billions with structures suited to each, fractal heaps scale cleanly from ten to millions of entries, and factoring out shared messages saves substantially when many datasets are alike.

Above all, the format specification is complete enough that an independent reader can be built from it — by no means a given with binary formats. The 641 expected-output files make the result verifiable. That is exactly why this module reads 413 of 460 official files without a single line of foreign code.

The criticism aims at one thing: the format has grown for over thirty years and has thrown away almost nothing along the way. The burden of that growth falls on the readers.

Not provided

Writing, in any form. Hdf5Source is the module's only opening point and opens exclusively with READ; ReadOnlyAudit scans the source at build time for write access; a tripwire compares size and timestamp on close.

The items

The Note column names the kind in front of the identifier. Only the gaps are work; they are listed individually in OFFENE-PUNKTE.md. Everything listed here announces itself by name when reading — none of it silently returns wrong values.

Our open gaps — this is the work

Since 2026-09-25 nothing is left here. All six gaps carried the same block: without a file to check the result against, nothing gets built — an unpacker that returns plausible-looking wrong numbers is worse than none. The files now exist (NACHTRAG7-README.md in envisionz-app-hdf5reader/proben/referenz/), written by HDF5 2.0 itself; the six items stand under 5.3.

Deliberate decisions — nothing to do

H1 (decided) — The subfiling driver

A virtual file driver from HDF5 1.14 for parallel I/O: the logical file is split into "subfiles" whose count and stripe size live in a companion file, not in the format. Unlike Family and Multi, the split is therefore nowhere in the HDF5 file itself — it is a matter for the runtime and not part of the format specification. Affects 2 of the 460 files.

H2 (decided) — Filter plugins

bitshuffle, blosc, zstd, dynlib*, myfilter, BitGroom, Granular BitRound: application-specific extensions loaded at runtime. A format reader fundamentally cannot know them — the algorithm lives in a foreign library, not in the file. Affects 12 datasets in 6 files. That one of them is called zstd, and that this workspace has been able to read zstd since 2026-09-05, changes nothing: the HDF5 filter identifier does not say which flavour of zstd is meant.

H3 (decided) — Writing

Not a gap but a guarantee resting on four levels and measured: channel opened read-only, no writing method, Nurlesenprobe searches the source, and size and modification time are remembered on open and compared on close. h5py and jHDF write.

Properties and closed items

C3b (property) — The szip filter — closed on 2026-09-25

Own decoder Hdf5Szip for the adaptive entropy coding of CCSDS 121.0-B, inside the frame HDF5 puts in front (4-byte size). The format specification does not describe szip; measured against g7_szip.h5, written by HDF5 2.0.0 with libaec 1.1.4: seven datasets, 19 compressed chunks, byte-identical. They cover all four block kinds (82 second extension, 282 zero-block runs, 250 uncompressed, 1330 split blocks), both byte orders, with and without preprocessing, 8, 16, 32 and 64 bits. Two places are not in the standard but in the implementation and were checked against libaec (sz_compat.c): at 32 and 64 bits the values are split into bytes and interleaved by position before packing, and a scanline that does not divide into blocks is padded with its last value. The counter-check reads the same chunk as a 16-bit stream and gets different bytes.

C5 (property) — Complex data type (class 11) — closed on 2026-09-25

Read following H5Odtype.c: bit 0 homogeneous, bits 1–2 form (only rectangular is described), then the floating-point type of one part. Hdf5Dataset.readComplex() returns real and imaginary parts alternately, readString() the number as text 1.0+2.0i; readDouble() reports that the series is not numeric instead of silently dropping one part. Measured on g7_komplex.h5 (64-bit little-endian, 32-bit big-endian, 2 × 2). h5py writes complex128 as a compound by default — class 11 only arises through the COMPLEX_IEEE_* types.

C1b (property) — Virtual datasets with shared names — closed on 2026-09-25

From library low bound 2.0 HDF5 writes the mapping heap block in version 1: one flag byte per entry, and a name that already occurred is given as the number of the earlier entry (H5Dvirtual.c). Measured on g7_vds_geteilt.h5: four mappings, three from the same source, one from the file itself; each of the hundred cells as h5py. Found and fixed on the way: hyperslab selection version 3 was read wrongly. After the flags comes one byte of encoding width; four were read — none of the older files carried version 3, which only arises from low bound 1.12. Unlimited is the maximum of the respective width.

C6b (property) — Reference encoding from HDF5 1.12 — closed on 2026-09-25

New class Hdf5Reference. Each element carries its own kind and flags — one dataset mixes object, region and attribute references; an object reference into the same file has its target in the element, everything else lives in the global heap (H5Tref.c, H5Rint.c). readReferences() returns the object per element, readRegions() the regions, the new readAttributeReferences() the attributes; a reference into another file is named, not followed. Silently wrong until then: kind 2 was read as an old object reference, the first eight bytes 02 00 08 b3 … as an address. Measured on g7_verweis2.h5, written via H5Rcreate_* — h5py 3.16 does not know this kind, hence partial in the h5py column.

C7c (property) — Fractal heap with filters on the blocks — closed on 2026-09-25

If the heap header carries a filter pipeline, every direct block is compressed as a whole — signature and header included (H5HFcache.c). Indirect-block entries then also give the compressed size and filter mask; for the root direct block both sit in the heap header. Decompression uses the same pipeline as datasets, after which the blocks live in memory; the checksum is computed on the decompressed block. Measured on g7_heapfilter.h5: a group with 40 entries in dense storage and deflate on the group creation property list; the FHDB signature does not occur in the file.

D9 (property) — Free space index, complete — closed on 2026-09-25

With fs_persist the addresses of up to thirteen free-space managers stand in the file space message. Hdf5FileInfo.freeSections() reads each manager's FSHD header and its FSSE section list — grouped by size, count, size and address in the narrowest widths that hold the maxima from the header (H5FScache.c). Measured on g7_freiraum.h5: six sections, 6183 bytes in total, the same and in the same order as H5Fget_free_sections. Fixed on the way: file space message version 0 was read like version 1. Managers belonging to a fractal heap are counted, not listed.

FB1 (property) — The row stood the wrong way round — corrected on 2026-09-06

The row was called "third-party libraries required" and stood at partial for all three. Both were wrong. First the direction: in this table ✔ means "present", that is something good — with a row of that name ✔ would have meant "needs some", making the one row in the document that must be read the other way round precisely the one not marked as such. It is now called "works without a third-party library", and ✔ means the same as everywhere else.

Second the values. For us it now reads yes: this reader needs none, and that is not a claim but measured — the probe compiles it against an empty classpath. For h5py no: it talks to the HDF Group's C library, that is its entire nature. For jHDF no, and this was measured on 2026-09-06: jhdf-0.13.0.jar alone on the classpath throws NoClassDefFoundError: org/slf4j/LoggerFactory, and with slf4j behind it org/apache/commons/lang3/concurrent/LazyInitializer. It is a pure Java reimplementation, but not one without dependencies.

The finding is small and instructive: a table row whose name inverts the meaning of the ticks will sooner or later be filled in wrongly — here it had been, since day one, in all three columns.

LF1 (property) — String columns in the Langform view — closed on 2026-09-06

Closed, and the gap was smaller than the item said. A standalone string dataset was already carried as a text column. What was skipped were only the string members of a compound — on the grounds that readMemberDouble cannot interpret them. True, and the wrong question: the HDF5 reader underneath has always had readMemberString. The gap sat in the view, not in the reader, and exactly one branch was missing.

For a measurement series with a name column that is the column one misses first — and the compound is the usual packaging in real holdings. The probe measures not only that the column is there but that each string belongs to the right row: readMemberString cuts the column out of the compound's raw block, and whoever is off by the member offset gets letters — and letters look like letters. Two mutations go red.

Fixed along the way: the first mutation made the section crash with IndexOutOfBounds instead of turning it red. Section clamp added, access to the column list guarded. And this document's section numbering is aligned with the other twenty-eight — 5.3 here used to be the upstream findings, everywhere else the properties.

Findings against the reference implementation

None. In the four own test files and the five netCDF-4 anchors, h5py 3.16 produced nothing that diverges from our reader with h5py in the wrong. That is no surprise: h5py sits on The HDF Group's library, and that library is the specification in executable form. A finding against it would be a finding against the standard.

For jHDF nothing can be said here, because it could not be measured.

The Java implementation — where this reader stands among its own kind

Why this section. Every other comparison in this module measures against a tool in a different language. That is good against misunderstandings of the format and says nothing about where this reader stands among its own kind — and that is the question a Java developer asks first. The distinction that matters is between a pure reimplementation in Java and a wrapper around the original C library: only the reimplementation solves the same task under the same conditions as this reader; a wrapper calls the original.

Measured on 2026-09-06 against netcdf-java 5.10.0 (ucar.nc2) — a pure Java reimplementation: Unidata's reader has its own HDF5 access (ucar.nc2.iosp.hdf5) and does not need the C library for reading. Five test files from envisionz-app-hdf5reader/proben; compared were the set of dataset paths, their shapes and the values of all numeric datasets.

Result: not a single divergence in the values. probe_container.h5 7 of 7 numeric datasets equal, probe_gepackt.h5 4 of 4, probe_grundlagen.h5 9 of 9, probe_messreihe.h5 6 of 6. Paths and shapes agree too — including the group nesting /tief/eins/zwei/drei/wert and the compressed datasets.

A single difference, and it is in our favour: in probe_verbund.h5 we carry the dataset /punkte_leer, netcdf-java does not. It is an empty dataset — we name it, the reference omits it. A dataset that exists deserves to be named; whether it carries values is a second question.

And measured against jHDF 0.13.0 on 2026-09-06 — that was the one unmeasured place in this collection. Five test files through both readers, comparing dataset paths, shapes and all numeric values. Result: 24 numeric datasets equal, none different, and the path sets agree in all five files. In probe_verbund.h5 jHDF also finds the empty dataset /punkte_leer that netcdf-java omits — of the two Java implementations, jHDF is the closer to ours.

A finding one only makes by measuring. jHDF does not read the two compressed datasets in probe_gepackt.h5 — it throws NoClassDefFoundError: com/ning/compress/lzf/LZFException. The remarkable part is that one of those datasets is gzip-compressed and has nothing to do with LZF: jHDF's FilterManager touches the LZF classes in its static initialiser, and when that jar is missing the entire filter chain fails — the second dataset then reports only "Could not initialize class io.jhdf.filter.FilterManager". The dependency is therefore not optional per filter but all or nothing.

That is not a criticism of the reimplementation but an operational fact: whoever uses jHDF needs slf4j-api, commons-lang3 and compress-lzf on the classpath, otherwise reading breaks at the first compressed place — and in real holdings almost everything is compressed. This reader needs none of them; see item FB1.

This measurement lives outside the module, in javavergleich/Javavergleich.java, because envisionz-framework-fileformats has the rule "no foreign libraries" — and it still holds. Only the result goes into the module, with date and version. The single exception is javax.imageio for the image formats: that sits in the JDK and therefore measures along as a permanent probe.
