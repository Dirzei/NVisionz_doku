CGNS — comparison against SIDS and against h5py

As of: 2026-09-06
Our implementation: envisionz.fileformats.cgns.CgnsDatei with Cgnsknoten, read-only, on our own HDF5 reader, no third-party library
Specification: CGNS Standard Interface Data Structures (SIDS) and CGNS/HDF5 mapping — both public; references give node labels and dataset names
Compared against: h5py 3.16 (Python) — not a CGNS reader but the container beneath it; see section 2
Test bench: envisionz.fileformats.cgns.Cgnsprobe — 63 checks, four foreign anchors

The reference implementation. h5py is a pure binding to the HDF Group's HDF5 C library, started by Andrew Collette. For CGNS it is explicitly not a CGNS reader but the container underneath: a CGNS file in its HDF5 flavour is an HDF5 file with rules inside it. What is measured is therefore the layer on which both sides must see the same thing — and that is exactly where a differing reading of the rules shows up.

Why this one. Because a CGNS reader would be the wrong level of reference. The CGNS library already interprets the rules, and where two interpreters agree one can no longer see whether both are right. With h5py the container is read raw: node names, data types, shapes, Fortran ordering. What CGNS makes of that is then ours alone — and an error in the interpretation shows up instead of being mirrored back.

Feature comparison

CGNS is not a byte format. Since version 3 it is a convention over HDF5 — exactly the relation netCDF-4 has to HDF5 and Exodus has to netCDF. The substrate was therefore already there; what is added here are rules about names, labels and axis order. And that is precisely where the traps are, because a misread CGNS file is a well-formed HDF5 file with transposed numbers.

What was measured

First a limitation, and it is the most important sentence in this document: For CGNS no second CGNS reader is available in this workspace. The reference implementation (the CGNS/MLL in C, plus pyCGNS or h5pyd) cannot be built here. The comparison is therefore against h5py, and h5py reads the container, not the format. Every ● in the h5py column above therefore does not mean "h5py cannot do it" but "h5py knows nothing about it, because it is not a CGNS reader". That is no statement about h5py's quality but about the limit of this measurement.

What can nevertheless be measured that way is the most valuable part of the container relationship: whether our numbers are the same as those in the HDF5 dataset — and whether the transposition CGNS requires actually happens. That is exactly what was checked.

The three anchors, through both paths

The three fixtures from Cgnsanker — strukturiert.cgns, unstrukturiert.cgns, zweizonen.cgns — were read once through CgnsDatei and once through h5py. h5py opens all three without complaint and finds the same groups, the same attributes and the same datasets; the numbers in " data" agree with ours value for value.

The transposition one sees only by comparison

In strukturiert.cgns CoordinateX is an HDF5 dataset of shape 3 x 2. CGNS means by that a grid with i = 2 and j = 3, not the other way round: the axes are in Fortran order in the file. Our reader transposes; h5py returns the shape as it stands. Whoever reads a CGNS file through h5py and takes the shape as given gets a grid rotated by ninety degrees that nevertheless looks plausible.

That is the kind of error this document exists for: it throws nothing, it reports nothing, and it is only noticed when somebody plots the result.

What is hard about the format

The name with the space. A node's data lives in the HDF5 dataset " data" — with a leading space. Likewise " format" and " hdf5version". Whoever searches for "data" finds nothing and reports an empty file; whoever knows about the space but not that the three space-prefixed names are not child nodes carries bookkeeping as payload. Both are one-character mistakes with entirely different consequences.

Everything is Fortran. The dataset shapes, the zone size, the node tags. The zone size is the nastiest case: SIDS describes one row [nodes, cells, boundary] per axis, but the file holds the transposed form, so row 0 holds the node counts of all axes. For a cubic grid — same number on every axis — the difference is invisible. That is exactly why Cgnsprobe uses a grid whose axes have different lengths.

Meaning is in the label, not the name. A node is called whatever the solver called it; what it is is stated by label: Zone_t, GridCoordinates_t, FlowSolution_t. A reader searching by name works exactly as long as the sample files come from one and the same tool.

What is good: CGNS lying on HDF5 is a gift. The container is checked, self-describing and openable with existing tools — every CGNS file can be inspected with h5dump, without a CGNS library. Few domain formats permit that.

Our open gaps — this is the work

Deliberate decisions — nothing to do

C1 (decided) — ADF is not read

Version 2 and earlier live in the in-house ADF container, an entirely different byte format. It is recognised and named — the message says this is ADF, instead of claiming a broken HDF5 file. Building a second container reader so that twenty-year-old files work is not worth the effort; conversion with adf2hdf has shipped with CGNS itself since version 3.

C9 (decided) — Writing

This module reads. h5py writes HDF5 — but even h5py does not write CGNS, only the container; the row stands at partial, not ●.

C5 (property) — Boundary conditions — closed on 2026-09-06

Closed. ZoneBC_t and every BC_t beneath it are laid out as a table of their own, <zone>_rand: one row per boundary condition with name, type, location and range. The value of the BC_t node is the type (BCWall, BCInflow), not its GridLocation child — confuse the two and every row reads "Vertex".

One row per boundary condition, not per point. Enumerating the points would turn two corners into thousands of rows and lose exactly the information that matters: which boundary is what.

The trap measured along the way: a PointRange sits in the HDF5 file as [IndexDimension][2] — one pair per axis — while the CGNS view is [2][IndexDimension]. Split the array linearly in half and 1,1,1 .. 1,2,1 becomes 1,1,1 .. 2,1,1: the same numbers, a different meaning, and both look like a range.

C6 (property) — Zone connectivity — closed on 2026-09-06

Closed. ZoneGridConnectivity_t becomes the table <zone>_verbindungen: name, neighbouring zone, kind (one-to-one or general), the range on this side, the range on the other side and the transform. The transform is the actual content — it says which way round one zone's axes lie in the other's: 1,2,3 means aligned, -2,1,3 rotated by ninety degrees.

And the second measured trap: beneath a connection sits PointRangeDonor as well as PointRange, and pyCGNS writes the donor first. Searching with startsWith swaps the two sides of the connection — and yields two ranges that both look like ranges. So the search matches the name exactly.

C7 (property) — Time steps — closed on 2026-09-06

Closed, and without rearranging the tables. BaseIterativeData_t carries the time values, ZoneIterativeData_t carries the solution names in FlowSolutionPointers in the same order. Together they give the mapping, and it now stands as a property on the zone table: zeit.Loesung#1 = 0.0. The solutions remain columns side by side — what was missing was not the arrangement but the information about which belongs to when.

The third trap: FlowSolutionPointers is an array of fixed-width characters (32), not a list of strings. Take the width from the wrong axis and with two names the width becomes two — yielding Lo and es.

C8 (property) — Windowed access — closed on 2026-09-06

Closed. A column is no longer read whole on first access but block by block through CgnsDatei.daten(node, from, howMany); the HDF5 reader beneath could always do this, CGNS simply did not use it. On a grid with millions of points that was not an inaccuracy but an order of magnitude: touch one coordinate and it sat in memory in full for the rest of the session.

The window is measured directly at the reader and not through the long form. The reason is a counter-test that stayed green: on an anchor of six values, "read whole" and "read in a block of 65536" deliver the same thing. A counter-test that stays green measures the anchor's reach, not the reader. So the test asks the reader directly: a window must return exactly its length and exactly the values at that place, and must not grow longer at the end.

Properties of the format

C3 (property) — The names with the space

See section 3. " data", " format", " hdf5version". No reader can guess this; it is in the CGNS/HDF5 mapping and nowhere else.

C4 (property) — Fortran order in three places

See sections 2.2 and 3. Dataset shapes, zone size, node tags. All three can be got wrong independently, and none of the three throws.

Findings against the reference implementation

C2 (open there) — h5py does not know CGNS — and that is not a criticism

Every row above carrying a ● in the h5py column goes back to the same circumstance: h5py is an HDF5 reader and makes no statement about CGNS. They stand here nevertheless because they make the limit of the measurement visible: for this format only the container could be cross-read, not the interpretation. Should a CGNS library ever become available in this workspace, this section is the first to re-measure. No bug in h5py has been found here.

The Java implementation — where this reader stands among its own kind

Why this section. Every other comparison in this module measures against a tool in a different language. That is good against misunderstandings of the format and says nothing about where this reader stands among its own kind. What matters is the distinction between a pure reimplementation in Java and a wrapper around the original C library: only the reimplementation solves the same task under the same conditions as this reader; a wrapper calls the original.

No Java implementation found. The reference library is C and Fortran; the official bindings cover Python (pyCGNS) and MATLAB (cgns4m), not Java. The only Java route that exists today runs through the JNI wrapper vtkCGNSReader in the VTK Java wrappers — that is, through the C++ library and not through a reimplementation.

A partial route would be possible: a CGNS/HDF5 file can be opened at node level in pure Java with jHDF or netcdf-java — the container is HDF5. The SIDS semantics, that is what a Zone_t or a GridCoordinates_t means, would have to be written on top. That is exactly what this reader does.

How solid this is. Researched on 2026-09-06 via web and GitHub search; Maven Central's search API was blocked at the time, so a systematic artefact search was not possible. "Nothing found" is therefore not the same as "nothing exists" — a little-visible or in-house implementation would not be discoverable this way. What stands here is the state of an honest search and not a claim of completeness.
