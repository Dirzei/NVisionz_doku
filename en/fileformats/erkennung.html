Format detection by magic bytes – background

How Formaterkennung determines the format of a file from its first 4096 bytes: signatures, structure checks for formats without a signature, looking inside containers, and the order that decides accuracy.

What this is about: the extension says nothing

A file daten.bin can be an MDF 4 measurement, a renamed SQLite database or text. The extension is a convention of the file system, not part of the file; it is missing, gets changed or lies. Almost every file format, on the other hand, begins with a fixed byte sequence, a signature (magic bytes), by which it identifies itself. The module therefore always detects by content. Detection is the precondition for Datenquellen.oeffne(pfad) choosing the right reader without a format argument (see the overview), and for wrongly named files to stand out.

The table covers 55 formats, including some for which the module has no reader at all (PDF, PostScript, Tecplot binary, Java class file, zstd, LZ4): detection should also be able to say what a file is that it cannot read.

Signatures and why one is not enough

The simplest signature is a fixed beginning. Well-chosen beginnings contain bytes that do not occur in text or that reveal transmission errors. The PNG signature 89 50 4E 47 0D 0A 1A 0A begins with a byte above 127 (reveals a 7-bit transfer), names the format as text (PNG), contains carriage return and line feed (reveals a line-ending conversion) and the Ctrl-Z 1A (stops old text viewers). HDF5 uses the same pattern with 89 48 44 46 0D 0A 1A 0A.

Not every signature is that long. Three examples from the table of how more than the beginning becomes necessary:

  • BMP has only the two characters BM, and “BM” is quite possible as the start of text (“BMW-Kennzahlen …” would otherwise be an image). Therefore the length of the description header from byte 14 is also read; it must be one of seven known numbers (12, 40, 52, 56, 64, 108 or 124). A random four-byte sequence hits one of them with a probability of 7/2327/2^{32}.
  • WebP lives in a RIFF container, and RIFF also carries WAV and AVI. The four characters RIFF alone say nothing; only the four characters at position 8 (WEBP) decide.
  • JPEG 2000: the signature box of a JP2 file is twelve bytes long; a bare code stream begins with FF 4F (SOC), which by the standard must be followed by FF 51 (SIZ) – only the four bytes together count, two alone would be too little.

Formats without a signature: structure as proof

Some formats carry no signature but have a header with rules that together hold only for a genuine file. The more independent conditions hold at once, the rarer a chance match:

  • dBASE: first byte one of 15 known version marks (for example 0x03, 0x30, 0x83), month 1 to 12 and day 1 to 31 in the date, header length L≥33L \ge 33 with (L−1)mod32=0(L-1) \bmod 32 = 0 (32 bytes per field plus preamble), record length >0> 0 and – if the header was read long enough – the terminator byte 0x0D at position L−1L-1. Example: a header with one field has L=32+32+1=65L = 32 + 32 + 1 = 65; (65−1)mod32=0(65-1) \bmod 32 = 0, fits.
  • Shapefile: code 9994 (big endian), five zero words, version 1000 (little endian) and one of the 14 valid geometry types. Checked before dBASE, because the Shapefile header is fixed and the dBASE check only plausible.
  • STEP: ISO-10303-21; (whitespace may precede); IGES has no signature but a fixed form: 80 characters in the first line, column 73 is S, columns 74 to 80 carry the number 1.
  • UFF: a line -1, then the number of the dataset (at most five digits, 1 to 99999, optionally with b for binary); Arrow stream: no signature, but the continuation marker 0xFFFFFFFF, behind it the length of the first message and, in the FlatBuffer, the signature ARROW at offset 12 – without the second condition every file with four 0xFF bytes at the start would be an Arrow stream.

Pseudocode – Formaterkennung.erkenne(Pfad) and erkenne(byte[])

erkenne(pfad):
    kopf ← the first min(4096, size) bytes
    f ← erkenne(kopf)
    if f = ZIP:    return imBehaelter(pfad)                  look at the central directory
    if f = OLE2:   return imCompound(pfad)                   open the directory tree
    if f = HDF5:   return imHdf5(pfad)                       e.g. CGNS, netCDF-4, Exodus
    if f = NETCDF_CLASSIC and istExodus(pfad): return EXODUS
    if f ≠ UNBEKANNT: return f
    if the HDF5 signature stands at offset 512, 1024, 2048 … (up to 8 MiB): return imHdf5
    if binary or text STL: return STL
    return UNBEKANNT

erkenne(kopf):                                        top to bottom, the first match wins
    HDF5 | HDF4 | netCDF ("CDF" + 1, 2 or 5) | SQLite | PAR1 | TDSm | "MDF     " (→ version)
    | $MeshFormat | "# vtk DataFile Version" | VTU (VTKFile and UnstructuredGrid in the head)
    | NumPy | ARROW1 | Arrow stream | ORC | Avro | OLE2 | PK 03 04 | PK 05 06 (empty archive)
    | gzip | zstd | LZ4 | SIMPLE | <?xml | Tecplot | %PDF- | bzip2 | XZ | PNG | JPEG | JPEG 2000 | GIF | BMP (with header length) | WebP
    | TIFF (II*\0 or MM\0*) | Java class | MATLAB | %!PS | LMDB | Ensight | UFF | STEP | IGES | Shape | dBASE (plausible)
    otherwise UNBEKANNT

Looking inside: same shell, different content

XLSX, PPTX, NPZ, ODS, DOCX and JAR are outwardly the same ZIP container and differ only in content. Anyone who stops at PK calls a workbook “ZIP” – correct, but useless. imBehaelter therefore reads the directory: an entry xl/workbook.xml means XLSX, ppt/presentation.xml PPTX, an entry with the extension .npy NPZ, otherwise it stays ZIP. An empty archive does not begin with PK 03 04 (it has no local header at all) but with the end of the central directory PK 05 06; without that line it counted as unknown.

For a Compound File (old Office files) the directory tree is really opened instead of searching the start of the file for names. The name hunt read names that happen to stand in the start and would have said the wrong thing for an Excel workbook with an embedded Word object. The tree says it correctly: an entry PowerPoint Document means PPT, WordDocument DOC, Workbook or Book XLS. HDF5 files are opened because several formats lie only one layer above: if the root group carries the label Root Node of HDF5 File, it is CGNS (no other HDF5 file writes that); if it carries _NCProperties or a dataset has CLASS = DIMENSION_SCALE, it is netCDF-4, and Exodus is netCDF with fixed names – again one layer more. An HDF5 file may also begin behind a preamble; therefore offsets 512, 1024, 2048 … up to 8 MiB are searched.

Binary STL has no signature at all but a length rule: 80 bytes of header, a counter nn (4 bytes, little endian) and nn triangles of 50 bytes each. The file is STL if n>0n > 0 and 84+50n=file size84 + 50\,n = \text{file size}. Example: 12 triangles (a cube) make 684 bytes. Textual STL begins with solid.

Decision in the framework: the factory Datenquellen.oeffne is a switch over the formats that the compiler checks for completeness, deliberately not a ServiceLoader: a new format without a branch is a compile error, not a runtime error. The start of the file is only read (READ), never written. VTK legacy deliberately does not check the version number behind the signature: it has grown since 1.0, and no version takes anything away from another.

File profile: when no signature fits

For files that carry no signature or match no format, Dateikunde.untersuche adds a description from the content: size, share of printable characters, null bytes, suitability as UTF-8, byte order mark, line endings, Fortran record marks (fortranSatzmarke) and the tools of the hex view (lese, suche, satzraster). It returns a Befund with kurz() and erkannt(). With it unknown files can be classified and wrongly named files found.

How it is checked

  • Boeswilligprobe: the seed is the module's genuine files (anchors) produced by third-party tools, as bytes in the source. From each, truncations and a fixed number of random mutants arise (default 8 per seed, key 0; about 7000 runs, two minutes); reading goes through the same path as in the file analysis. Required: no crash, no hang, no memory demand above the limit. Every seed must itself be readable, otherwise the rest measures nothing.
  • Sauberabweisungsprobe: for the formats whose readers have been converted to it (among others Gmsh, Arrow, TDMS, TIFF, BMP) it requires zero “unclean” rejections – that is, no foreign runtime exception such as ArrayIndexOutOfBounds instead of the format's own message.
  • The reader probes of the individual formats (for example Pngprobe, Mdfprobe, Shapeprobe) call detection as part of their chain.

Limits

  • A signature covers only the beginning. A file with a valid header and a destroyed rest is detected as that format; whether it is readable is decided only by the reader (lesbar(pfad)) and its befunde().
  • At most the first 4096 bytes are read; signatures that stand further back need a search of their own (HDF5 with preamble up to 8 MiB).
  • Text formats without a signature (Ensight, UFF, IGES) are detected by form rules that make chance matches harder, not impossible.
  • The table is finite: a format that is not entered is UNBEKANNT; the file profile then only describes it.
