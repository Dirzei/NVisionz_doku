FITS — comparison against Standard 4.0 and against astropy

As of: 2026-09-05
Our implementation: envisionz.fileformats.fits.FitsQuelle with Fitskarte, Fitskopf, Fitsspalte, read-only, no third-party library
Specification: Definition of the Flexible Image Transport System (FITS), version 4.0 (IAU FITS Working Group) — freely available; references give section numbers
Compared against: astropy 8.0.1 (Python) — the FITS community's reference implementation
Test bench: envisionz.fileformats.fits.Fitsprobe — 247 checks, seven foreign anchors, ten counter-tests

The reference implementation. astropy is the shared library of the astronomical community. Its astropy.io.fits part descends from PyFITS, developed at the Space Telescope Science Institute — the institute that operates Hubble. PyFITS is now retired and archived with an explicit note that all of it lives on in astropy. astropy is therefore the de facto reference of the FITS world without owning the standard: that belongs to the IAU FITS Working Group, since 1988.

Why this one. Because astropy stands as close to the standard as a library can without setting it: it comes from the institute that operates Hubble and is the tool with which the field actually reads its files. Whoever reads FITS differently from astropy reads differently from astronomy — a sharper argument than any paragraph number.

Feature comparison

FITS was ratified in 1981 and since then never changed, only extended. A file from 1985 can be read today, and that is no accident but the declared intent: once FITS, always FITS. There are few formats of which that is true — and it is the reason a FITS reader is worth having, although the format comes from a field this workspace has nothing to do with.

What was measured

Nineteen fixtures, in both directions. Seven foreign anchors from astropy 8.0.1 through our reader, and twelve of our own from Fitsschreiber through astropy. That is the full arrangement this workspace requires for a comparison: that we read what the other product writes is one half; that it reads what we build for our checks is the other.

Our twelve through astropy

That is not a bug in astropy — the files are broken, and astropy never promised to describe them. It is the difference between an error message and a debugging session.

fremdeArt is the most interesting of the four, because both sides do something defensible and different. astropy hands through the bytes of an unknown extension; we name it and leave it uninterpreted. Whoever needs the bytes is better off with astropy; whoever wants to know what is in the file, with us. The row stands under T15 and not under "bug".

Ten counter-tests, ten times red

A set of checks is worth something only once it goes red the moment one breaks the reader. Ten interventions, one line each, each measured separately:

Interventionfailures

And one of them found a real bug in our reader. The counter-test "forget PCOUNT" stayed almost green at first: only the computation itself went red, while the file haufen.fits with two units across a three-thousand-byte heap still read. The cause was a check drawn too wide: the reader asked hat("XTENSION") — and that searches the whole header. If the wrong computation landed it in the middle of the heap's zeros, it picked up the cards of the next, real header while searching on, found XTENSION there and took the header for valid. It looked valid and began in the wrong place.

The standard is unambiguous here: SIMPLE resp. XTENSION must be the first card. The reader now carries Fitskopf.ersterSchluessel() and checks exactly that; the counter-test has gone red twice since, and two new checks hold the case down. Without the counter-test the bug would not have surfaced — the checks were green and all nineteen fixtures read correctly.

What is hard about the format

The eighty-character card. FITS comes from the age of the punched card, and a punched card had eighty columns. That is no anecdote but the rule of computation: there are no line endings. A reader reading the file line by line finds a single 2880-byte line — or, with binary data behind it, none at all.

PCOUNT sits outside the axes. The data length is |BITPIX|/8 · NAXIS1 · … · NAXISn, plus PCOUNT, then rounded up. For a binary table with variable-length fields, PCOUNT is the heap behind it, and it can be much larger than the rows. Whoever forgets it looks for the next unit too early — and finds either none or, worse, an XTENSION that happens to sit in the data. That second outcome really did occur once during this work (section 2.3).

A negative BITPIX is a type, not a width. -32 means "four bytes IEEE floating point", not "minus thirty-two bits". Whoever takes the absolute value and forgets the type reads floats as integers and gets values of order 10⁹ — which in astronomy look like count rates and therefore go unnoticed.

BZERO is the detour to unsigned numbers. FITS has no unsigned integers. The usual route to a detector's 16-bit raw data is therefore BITPIX = 16 with BZERO = 32768. Whoever skips the scaling gets negative values for the bright half of an image — the dark half is right, and the image looks like an image with an exposure fault.

20A is one column, 4E are four values. In a binary table's TFORM the number before the letter is a repeat count — except for A, where it is a character count. A reader applying the rule uniformly turns a name field into twenty one-character columns. The foreign anchor bintabelle.fits deliberately contains both cases side by side.

What is good: that there is only one byte order. Big-endian, everywhere, with no field that could announce anything else. That is one of the few places in this whole collection of documents where a reader has nothing to decide — and it is remarkable because FITS is older than almost every other format here and the question was just as open then. It was answered and left alone.

Our open gaps — this is the work

Deliberate decisions — nothing to do

T16 (decided) — Same-named units get #2 and a finding

Two extensions may carry the same EXTNAME; the standard does not forbid it. Merging them would be the quieter and the wrong answer — the table would look right and have twice as many rows. The row stands at – for the reference because astropy carries units by number and the question does not arise there.

T9 (decided) — An image becomes a table like a NumPy array

One axis gives a column wert, two axes give s0, s1, …, three or more give the long form with index columns i0, i1, … . That is the same rule as in NpyQuelle — not out of convenience, but so that a user touching both formats does not have to learn two rules. The row stands at – for the reference: astropy returns a numpy array and forms no tables.

T18 (decided) — Writing

astropy writes FITS and supplied this document's seven foreign anchors. This module reads. Fitsschreiber in the test bench builds fixtures — including the four broken ones astropy does not write — it is test equipment, not an output path.

Properties of the format

T12 (property) — Compressed images — closed on 2026-09-07

Closed. Since version 4.0 an image may lie tile-compressed inside a BINTABLE. The table then carries ZIMAGE = T, and its header cards describe not the table but the image inside it: ZBITPIX instead of BITPIX, ZNAXISn instead of NAXISn, plus ZTILEn and ZCMPTYPE. Every row is a tile. In real archives this is the normal case and not the exception — raw data is stored this way almost throughout. Built are RICE_1, GZIP_1 and GZIP_2; eight anchors from astropy 6.1.7, all equal number for number.

This item depended on T14. A tile does not sit in the row but in the heap — the row carries only a pointer. As long as the heap was unresolved there was nothing to fetch here. This is the only case in this collection where one gap held up another, and both were closed on the same day.

Rice, in three sentences. Not the values are written but the differences to the left neighbour; those are small and centred on zero. Negative differences are folded (0, −1, 1, −2, 2, … becomes 0, 1, 2, 3, 4, …) so they carry no leading ones. And every number is split: the lower fs bits stand unchanged, the upper part as a run of zeros with a one at the end. fs is chosen afresh for each block of BLOCKSIZE values and precedes it.

And everything hangs on BYTEPIX. It fixes two numbers: how wide fs itself is written (3, 4 or 5 bits) and how large it may become (6, 14 or 25). Whoever takes the four-byte values on a two-byte image reads the first blocks correctly — until the first arrives whose fs fits in four bits and looks different in five (44 checks red). Dropping the folding turns 3 red; reading a byte as signed, where FITS has no sign, turns 9 red.

The three traps outside the coder. First GZIP_2: before packing it groups all most-significant bytes, then all second ones — the same idea as TIFF's floating-point predictor. Forgetting to undo it yields numbers with swapped byte halves, and those look like noise rather than an error (17 red). Second the edge tile: it is smaller than ZTILEn and occupies only as many points as it has in the packed data. Computing with the full size shifts every image row right of the first edge — on all anchors whose tiles span the full image width the mutation for it stays green; only the anchor kachelRand (23 x 17 in tiles of 9 x 5) turns it red. Third the fallback: a tile that could not be packed profitably sits in GZIP_COMPRESSED_DATA or UNCOMPRESSED_DATA, and in its original form — for a floating-point image as IEEE numbers and not as quantised integers. Missing that gets exactly those tiles wrong that the writer found difficult (6 red).

One mutation found a fault in the TEST and not in the reader. The mutation "skip the fallback" stayed green at first — not because the reader survived it but because the comparison function nahe reported nothing on a NaN: every comparison with NaN is false, including "greater than". A whole vanished tile therefore turned nothing red. The function now checks for NaN explicitly.

What is named and not decoded: PLIO_1 (IRAF's list coding for masks), HCOMPRESS_1 (a wavelet transform with its own coder) and floating-point images with dithering (ZQUANTIZ = SUBTRACTIVE_DITHER_1 and relatives). In all three cases no numbers come out, plus a finding naming the method — an image of zeros would be the worse answer, because zeros look like a measurement. Two anchors check exactly that. Dithering is the most interesting of the three: it is laid down in the convention, and without it the values would be off by up to half a quantisation step — that is, by so little that the image would look right.

Two mutations stay green, and both for the same reason: there is no foreign tool against which the place could be measured. The first concerns the default for ZTILEn (first axis whole, every further one at 1). astropy 6.1.7 always writes ZTILEn and refuses to open a file without them at all — so there is neither a foreign anchor nor a foreign reference value. The reader applies the default and says so in a finding; an own fixture measures that finding. The second is a safety net: a ZSCALE of zero on a packed tile is not applied. No writer producing that is known; the line exists because scaling by zero would turn every image into zeros. Both places are therefore unmeasured, and that stands here rather than being kept quiet.

T14 (property) — The heap is resolved — closed on 2026-09-07

Closed. A column with TFORM P or Q carries no value but count and offset into the heap behind the table. Before, 2@0 stood there — the pointer, honestly displayed, but only the pointer. Now it is resolved: PCOUNT and THEAP say where the heap begins, the pointer width (P four bytes, Q eight) says how to read it, and the values come out in the same shape as from a fixed-length column.

The trap is THEAP. The heap does not necessarily begin directly behind the rows — THEAP may shift it, and its default is NAXIS1 × NAXIS2. Whoever forgets the default reads at the wrong place for every file without THEAP; whoever sets it and ignores THEAP for every file with one. An empty field (count zero) now gives an empty text rather than 0@21. Reference values from astropy 6.1.7.

T11 (property) — World coordinates are computed — closed on 2026-09-07

Closed. CRVAL, CRPIX, CDELT, CTYPE and the rotation matrix no longer stand in the tree merely as cards but are computed. Fitswcs reads the three spellings of the matrix — CD, PC times CDELT, and the old rotation CROTA2 —, always performs the linear transformation and the spherical projection for TAN (gnomonic, almost every exposure), SIN (orthographic, radio interferometry) and CAR (plate carrée). Every other projection is named and not computed, rather than inventing a number that looks like a coordinate.

CRPIX is one-based. The reference point 3.0 means the third pixel, not the fourth. That is the place where a reader lands exactly one pixel width off — and a sky coordinate that is one pixel width wrong looks like a correct one. The mutation for it turns 32 checks red.

And two anchors that exist only because mutations stayed green. The narrow SIN anchor measures six by five pixels of one thousandth of a degree each; over such a postage stamp the gnomonic and orthographic projections agree to ten digits, and the mutation "compute SIN like TAN" stays green on it. It measures not the reader but the anchor's reach. The second anchor (wcsSinWeit) has twenty by twenty pixels of half a degree each — there the two projections differ by 0.035 degrees in the corner, and the same mutation goes red. Likewise for the CD anchor: it carried no CDELT, so the mutation "apply CD and CDELT" could find nothing; the second (wcsCdCdelt) carries a CDELT of 7 beside it, which the standard says to ignore, and turns it red.

Five mutations, all red: zero-based CRPIX (32), SIN computed gnomonically (6), CD times CDELT (4), LONPOLE default 0 instead of 180 (25), and swapped arguments in the native angle (22). Reference values throughout from astropy 6.1.7, to seven decimal places.

T17 (property) — Windowed access — closed on 2026-09-07

Closed. The file is no longer read whole into memory on opening. Fitsbytes lays a 64 KiB window over the channel and slides it; the header names each unit's data offset, and that suffices to jump to an arbitrary place. For an exposure of 4096 × 4096 points in double precision, 134 megabytes previously stood in memory even when only one row was needed.

T10 (property) — BLANK and TNULL — closed on 2026-09-06

Closed. An integer image may mark a value as "nothing here" via BLANK, an integer column via TNULL<i>n</i>. Both are now recognised and yield Wert.LEER instead of a number. Before, a −32768 stood in the analysis as a measurement and pulled every mean.

The sharp point is not that something comes out empty but what it is compared against: the raw value, before BSCALE/BZERO respectively TSCAL/TZERO. Whoever scales first and compares afterwards no longer finds the marker. And both apply only to integer types — with floating point NaN is the marker, and a TNULL on an E column is reported, not applied.

Two anchors, and the second exists only because one mutation stayed green. The first (fehlendeWerte) has BSCALE 1 and BZERO 0 — scaling there is the identity, and the mutation "scale first, compare afterwards" stays green on it. So it measures nothing. The second (fehlendeWerteSkaliert) carries BSCALE 2, BZERO 100 and TSCAL 3, TZERO 7; on it the same mutation goes red. Both produced with astropy 6.1.7.

T1 (property) — Eighty characters, no line endings

See section 3. The punched card of 1981 is still there, and it is why a line-oriented reader finds nothing.

T2 (property) — The doubled quote

'O''Brien'. Whoever stops at the first closing one reads O and takes the rest for a comment — and because the result is a well-formed string, it goes unnoticed. The foreign anchor hochkomma.fits contains exactly this case, and the counter-test for it goes red.

T3 (property) — With a duplicate keyword the first one holds

No arbitrariness but the standard. A reader taking the last one reads something different from the rest of the world for every subsequently amended file — and quietly at that.

T4 (property) — SIMPLE and XTENSION must come first

See 2.3. This rule is not formalism: it is the only safeguard against a reader believing it has found a header in the middle of the data. That is exactly where our reader was caught out and corrected on 2026-09-05.

T6 (property) — PCOUNT counts towards the data length

See sections 3 and 2.3. Both implementations observe it; the row stands here because it is the place where a third would fail — and where the second nearly did.

T7 (property) — Negative BITPIX means floating point

See section 3.

T8 (property) — BZERO is the detour to unsigned numbers

See section 3. The foreign anchor unsigned.fits measures it: without the scaling, 40000 and 50000 would come out negative.

T13 (property) — 20A is one column, 4E are four values

See section 3. The counter-test for it — applying the rule uniformly — goes red with twenty-three failures and is thus the second sharpest of this probe.

Findings against the reference implementation

T5 (open there) — Seven conditions without a statement about the file

A BITPIX that does not exist (KeyError: 12); a truncated file (TypeError: buffer is too small); a file length not a multiple of 2880; SIMPLE = F; GCOUNT ≠ 1; a column sum unequal to NAXIS1. We name all of them in the findings, with the place; astropy answers the first two with a Python exception from the inside and does not report the rest. For ohneEnde astropy's message is as good as ours and is expressly noted. This is not a bug — astropy is a library for computing with sky data, not a tool for examining files. It is the difference between an error message and a debugging session.

T15 (open there) — An unknown extension is handed through

See 2.2. astropy reads an XTENSION = 'FOOBAR ' as NonstandardExtHDU and hands out the bytes; we name it in the findings and leave the data uninterpreted. Both are defensible and different: whoever needs the bytes is better off with astropy; whoever wants to know what is in the file, with us. No bug in astropy was found in this measurement — with the reference implementation of a format unchanged for forty years that would have been surprising.

The Java implementation — where this reader stands among its own kind

Why this section. Every other comparison in this module measures against a tool in a different language. That is good against misunderstandings of the format and says nothing about where this reader stands among its own kind — and that is the question a Java developer asks first. The distinction that matters is between a pure reimplementation in Java and a wrapper around the original C library: only the reimplementation solves the same task under the same conditions as this reader; a wrapper calls the original.

Measured on 2026-09-06 against nom-tam-fits 1.22.2 — explicitly a 100% pure Java reimplementation, with no mandatory dependencies, and the established Java library in the FITS community. All nine anchors from Fitsanker through both readers.

Both read every one of the nine files, including the two new anchors for BLANK and TNULL, the ASCII table, the heap pointers and the doubled apostrophe. The image dimensions agree — bild 3×4, unsigned 2×3, fehlendeWerte 2×3, hochkomma 4.

What cannot be compared directly, and why: nom-tam-fits counts units (HDUs), we count tables. A FITS file with an empty primary header and one binary table has two units and yields one table for us — both numbers are right and mean different things. Holding them against each other measures one's own confusion.

This measurement lives outside the module, in javavergleich/Javavergleich.java, because envisionz-framework-fileformats has the rule "no foreign libraries" — and it still holds. Only the result goes into the module, with date and version. The single exception is javax.imageio for the image formats: that sits in the JDK and therefore measures along as a permanent probe.
