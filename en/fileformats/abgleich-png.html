PNG — comparison against RFC 2083 / W3C PNG and against Pillow

As of: 2026-09-07
Our implementation: envisionz.fileformats.png.PngDatei with Pngkopf, Pngstueck, Pngtext, read-only, no third-party library
Specification: PNG (Portable Network Graphics) Specification, RFC 2083 (1997) and the third W3C edition — public; references give section and chunk names
Compared against: Pillow 12.2.0 and 12.3.0 (Python); for the ancillary chunks javax.imageio (JDK)
Test bench: envisionz.fileformats.png.Pngprobe — 1807 checks, twenty-one anchors, twenty-six counter-tests

The reference implementation. Pillow is the image library of the Python ecosystem, the 2010 fork of the original Python Imaging Library by Fredrik Lundh, started by Jeffrey "Alex" Clark and maintained today by the python-pillow team. It is the most widely used implementation in its field and at the same time the reference implementation of no format at all. For PNG it has its own chunk parser and uses foreign code only for the data stream itself — zlib, not libpng.

Why this one. Because PNG has a strict, freely available specification but no reference implementation that owns it — libpng is the most widespread but not normative. For PNG Pillow specifically does not use libpng but its own chunk reader with zlib underneath. That makes it a truly independent second reader: the filters, Adam7 and the colour types were built twice from the same specification, and wherever the two diverge is a place the specification does not state clearly enough.

Feature comparison

Of all the formats in this collection PNG is the only one designed against transmission damage and not merely against misunderstanding. It arose in 1995 as an answer to GIF's patent situation, and the people who designed it clearly had a precise idea of what happens to a file travelling the networks of 1995: it goes through a channel that strips the top bit; a program rewrites line endings; someone types TYPE image.png and the screen falls apart. There is something in the file against all three.

For this test bench PNG is therefore a special case. With every other format the question "is this file intact" is a guess; here it is answerable, because every chunk carries its own CRC-32 and thereby says which part of the file is damaged. That is exactly the piece of information a search starts from — and the reference product does not give it on an ordinary read (P22).

What was measured

Twenty-one anchors: ten were written by Pillow, eleven were built by hand and read back by a foreign reader. For each of them the probe checks five numbers — colour sum, alpha sum, first row, last row and the dimensions.

For the four most recent anchors the cross-reader changed, and that says something about the reference product: of the seven ancillary chunks Pillow carries only cHRM and gAMA in its info and is silent about the other five. So it cannot supply expected values for them at all. They therefore come from javax.imageio, the JDK's PNG reader, which exposes all seven field by field through its metadata tree. That is the one foreign library allowed to run as a permanent fixture — it is inside the JDK, pure Java, and brings nothing that would be missing under native-image.

The alpha sum is there because PNG knows four different ways to make a pixel transparent and three of them are invisible in the colour sum. And the individual rows are there because a wrong Adam7 split delivers the same pixels in other places — with the same colour sum.

What Pillow does not write

Eight anchors had to be built by hand, and the list of what Pillow never writes is the reason: interlaced (Adam7), two bits, truecolour at sixteen bits, more than one IDAT below 64 KBytes, a colour key — and which of the five row filters it picks it decides itself. That is not a weakness: a writer picks the simplest form that fits. For a reader it means that precisely the branches in which it goes silently wrong never occur in foreign files.

Two counter-tests that stayed green — and what came of it

Of seventeen interventions fifteen went red at first. The two green ones were instructive, in two different ways.

The first was a gap in the fixture. The intervention "the filter distance without its lower bound of one" could not go red because all three anchors below eight bits used filter 0. The filter distance there is one and not one pixel — the filters work on bytes containing two or eight pixels. Without a single filtered anchor below eight bits that branch stood unproven. So a seventeenth anchor was added: vierbitfilter, eight pixels at four bits over five rows with filters 0 to 4. Afterwards: 117 failures.

The second was a gap in my thinking. The intervention "break Paeth strictly instead of taking left on a tie" — pa < pb && pa < pc instead of pa <= pb && pa <= pc — stayed green although the probe checked seven Paeth cases. Working it out: a tie between a and b is impossible when a ≠ b. pa = |b−c| and pb = |a−c| are equal only if a = b or c = (a+b)/2 — and in the second case pc = |a+b−2c| = 0, so c wins anyway. My seven cases therefore could not see the difference.

The break becomes visible only where pa = pc < pb: there the correct computation takes a, the strict one falls through and takes c. One such case is a = 0, b = 3, c = 2 — p = 1, pa = 1, pb = 2, pc = 1. Four new cases now check exactly this break and its mirror image (pb = pc < pa), and an eighteenth counter-test attacks the second comparison line. Both are red. The lesson is recorded because it generalises: a probe with seven cases is not the same as a probe that can see the difference.

A third counter-test that stayed green

The intervention "the denominator zero stays zero" stayed green although the probe checked all three delays of the animated PNG. The reason is the same as in 2.2 and yet a different one: Pillow does not write a denominator of zero. All three frames of the anchor stand at x/1000, and there the special rule has no effect. The branch was described, computed and unproven.

So a twenty-first anchor was added: the same file with 7/0 on the second frame, rewritten by hand with a recomputed checksum. The expected value is foreign all the same — Pillow does not write the file, but it reads it and reports 70 milliseconds for that frame. The special rule is therefore not our interpretation but a measured one. Afterwards: red.

That is now three times the same pattern, and it is worth saying once: a counter-test that stays green does not measure the reader but the reach of the anchors. It is therefore not a nuisance but the only finding of its kind a test bench produces by itself. The right answer to it is never to discard the intervention but always to build an anchor that can see it.

What is hard about the format

The five row filters, and that the errors accumulate. Before every row stands a byte saying how it is computed against its neighbours. All five reach into already unfiltered neighbours — the row above is itself the result of another filter. A reader rounding average to nearest instead of down is off by one in the first row, by more in the tenth and noticeably at the bottom edge; the image is right at the top and drifts downwards. That is exactly why one anchor is 60 × 40: over forty rows the drift shows, over three it does not.

Paeth and the order of its comparisons. It takes from left, above and upper-left whichever lies closest to a + b − c; on a tie a beats b beats c. That is what the specification says and it is not a matter of taste. The case is not rare — in flat areas a tie is the normal case — and it is at the same time the case a probe most easily misses, because it does not arise from any arbitrary triple of numbers (see 2.2).

Adam7 is not a row order but seven images. Each pass is its own small image with its own filter bytes and its own row length, and whoever takes one of its rows for an image row gets an image of tiles. On top of that: a pass containing no pixels is skipped entirely — it then has no filter bytes either. For an image of 3 × 3 that is three of the seven. Read a filter byte for an empty pass anyway and everything after it shifts by exactly one byte.

The filter distance is one below eight bits. It is the number of whole bytes per pixel, floored at one — not one pixel. On an image with one bit per pixel the filters therefore work on bytes containing eight pixels. It feels wrong and it is right; round up or drop the floor and you get stripes. The branch is especially easy to leave unchecked because on such short rows a writer almost always picks filter 0 — see 2.2.

Four ways to transparency, three of them invisible. A separate channel (colour types 4 and 6), an alpha list for the palette, a colour key for greyscale and one for truecolour. The last three live in tRNS — the same chunk, with three entirely different contents depending on colour type: one byte per palette entry, one sixteen-bit value, three sixteen-bit values. And all three are invisible in the colour sum, because the pixel's colour stays what it was.

What is good — and better than anything else here: the self-description. Every chunk states its length, carries its own CRC-32 and says, in the case of its four letters, whether a reader may skip it. A reader that does not know a chunk type therefore does not have to guess — the file tells it. That is why PNG has been unchanged since 1997 and could still be extended, and it is why this reader can say which chunk of a damaged file is damaged. No other format in this collection can do that.

Our open gaps — this is the work

Deliberate decisions — nothing to do

P1 (decided) — No route through the general format detection

Datenquellen.oeffne rejects a PNG and points at PngDatei.lies. The reason is the same as with GIF (I15) and BMP (B1): an image is not a table. The detection itself knows PNG and checks all eight signature bytes; only opening it as a Datenquelle is missing. The same situation as VTK (V9) and HDF4 (H8).

Decided on 2026-09-06. The item stood as a gap in five image formats with identical wording (BMP B1, GIF I15, PNG P1, TIFF T24, WebP W20). It is not one: a Datenquelle is a table view, and an image is not a table. A view with one row per pixel (x, y, red, green, blue) would be possible — at 4000x3000 that is twelve million rows, and what it would buy does not answer the question "what is in this file" but a different one. The readers exist and are named in the rejection message; that is the information the user needs. VTK (V9) and HDF4 (H8) are different: their content really is tabular, and there the view is being built.

P6 (decided) — Our own deflate and our own CRC-32

java.util.zip.Inflater is in every Java runtime and would be one line. Used instead are envisionz.compress.deflate.Zlib and envisionz.compress.pruef.Crc32 from framework-compress — our own code, measured against zlib, and therefore usable under native-image without extras. That is the house rule ("no third-party libraries where our own implementation is feasible"), and here it costs nothing: the deflate reader was already there for ZIP and gzip. PNG is the first caller to use it across one stream in several chunks.

P7 (decided) — Sixteen bits are carried in full and not silently rounded

punkte() delivers eight-bit ARGB — the view one works with. At a bit depth of sixteen, punkte16() additionally delivers the full samples, and at eight bits it deliberately returns null instead of extrapolated values. The null is the decision: a number we invented would look exactly like one that stands in the file. The way from sixteen to eight is rounded ((v·255+32767)/65535) and not the high byte — the difference is at most one and, see P17 and P18, exactly the point at which the reference product makes two different mistakes.

P9 (decided) — A broken stream is a finding, not a failure

If the deflate stream cannot be unpacked the image stays black — but the header, the dimensions, the chunk list and the statement of which chunk violates its checksum are there. For a viewer an exception would be right; for a file-inspection tool it is the wrong answer to the question "what happened to this file". We abort only where nothing can be said at all: no IHDR, no signature, a combination of bit depth and colour type that does not exist.

P8 (decided) — Alpha is carried but the colour sum counts only RGB

As with BMP (B6): the probe's colour sum counts red, green and blue, and alpha is summed separately. With PNG that matters even more, because there are four ways to transparency and three of them leave the colour alone. A combined sum would have swallowed three errors.

P3 (decided) — Writing

Pillow writes PNG and supplied nine of the seventeen foreign anchors. This module reads. The eight hand-built anchors are test equipment, not an output path; the probe has its own small builder for chunks and CRC-32, and it sits expressly under test/.

Properties of the format

P4 (property) — APNG — animated PNG — closed on 2026-09-07

The chunks acTL, fcTL and fdAT put several frames into one PNG. They are not in the specification but a later extension — properly marked as ancillary, so the earlier behaviour (skip them and deliver the main image) was not wrong but exactly what the specification prescribes for a reader that does not know them. Since 2026-09-07 the reader assembles the animation: bewegt(), durchlaeufe() and teilbilder(), and every frame carries the whole canvas as it looks at its point in time.

Four places where a reader goes silently wrong. First: the first four bytes of an fdAT are the sequence number and are not part of the image data — pack them along and you get a deflate stream with four foreign bytes in front, which will not unpack. Second: an fcTL closes the previous frame and opens the next; close only at the end of the file and you keep just the last one. Third: the main image is the first frame only if an fcTL stands before the IDAT — if it stands after, the main image is a fallback for readers without APNG and does not belong to the animation. Fourth: a frame is usually smaller than the canvas and sits at an offset; index the canvas with the frame's width and you write diagonally.

And two numbers where zero does not mean zero. The loop count in acTL: zero means endless, not "not at all" — take it as a counter and an endless animation plays not once. And the denominator of the delay in fcTL: zero means one hundred — divide blindly and you divide by zero; take the denominator unchecked and you get a delay of infinity. Both special rules are measured; the second cost an anchor of its own (see 2.3), because no writer writes it.

The canvas work itself is the same as with GIF in different words: three disposal operations after a frame (leave it, clear to transparent, restore the previous canvas) and two blend operations while drawing (replace or blend over). Disposal 2 is the expensive one — it requires remembering the canvas beforehand, and a reader that does not fails only at the third frame.

P2 (property) — Colour space — read, and applied on request — closed on 2026-09-07

gAMA, sRGB, cHRM and iCCP are all four read: the four chromaticities as numbers, the ICC profile with its name and decompressed. And gAMA is applied on request — punkteMitGamma(2.2) converts the pixels to a named screen gamma, punkte() delivers them unchanged.

The split into two methods is the decision, not an intermediate step. punkte() delivers what stands in the file; for file inspection that is right — whoever wants to know what is in a file does not want to see the result of a conversion. A default that converts sometimes would be the worst of all answers, because then the meaning of the numbers would depend on whether the file carries a gAMA. The same split as with orientation in the TIFF reader (T10), for the same reason. Without gAMA the pixels come out unchanged and not with a guessed gamma — a guessed value would shift every image that carries none, and that would be an error without a message.

What is deliberately missing is the full ICC transform. The profile is available decompressed; building colour management from it is a discipline of its own and not one line. Pillow does not do it either — it carries the profile in info and does not convert of its own accord. The same situation as BMP (B4). The difference to the earlier state is nevertheless the essential one: before, cHRM and iCCP were skipped; now they are there, and whoever needs them has them.

P5 (property) — The five ancillary chunks — closed on 2026-09-07

sBIT, bKGD, hIST, sPLT and tIME are interpreted and available as bedeutsameBits(), hintergrund(), haeufigkeit(), vorschlagstafeln() and aenderungszeit(). sBIT is the most useful: it says that an image with sixteen bits may carry only twelve real ones — information one wants with measurement data and cannot reliably recover from the numbers themselves.

Two of the five take their length from the colour type, not from the chunk. bKGD is one byte with a palette (an index into it), two with greyscale and six with truecolour. Read three sixteen-bit values always and on a palette image you read five bytes that do not belong — and get a background colour that looks like a colour. And hIST exists only with a palette; it counts its entries. That is why a second anchor with a palette stands beside the truecolour one: the same chunk name, a different meaning.

And sPLT has two entry widths. An entry is six bytes at a depth of eight and ten at sixteen — four samples plus a two-byte frequency. The depth stands in the chunk itself, after the name, and has nothing to do with the image's bit depth. Assume a fixed width and on every other image you get a palette of shifted numbers that still look like colours. sPLT may also occur more than once, with different names; that is why it is a list and not a field.

The measurement was against javax.imageio and not against Pillow — see section 2. Of the seven chunks Pillow knows only two; for the other five there is no expected value there to copy. The JDK reader exposes all seven field by field through its metadata tree. The interpretation is thereby measured against a foreign reader; its creation is not: the bytes are inserted by hand, because no available writer writes sBIT, hIST and sPLT.

P10 (property) — The eight signature bytes are a check

89 50 4E 47 0D 0A 1A 0A. The 0x89 fails if the top bit is stripped; 0D 0A breaks if a program rewrites line endings, and the final 0A catches the reverse; the 1A ends output under MS-DOS so that TYPE image.png does not wreck the screen. Check only for "PNG" and you throw away five of the eight statements. The probe alters each of the eight bytes individually and demands a rejection.

P11 (property) — Every chunk carries its checksum

Four bytes of CRC-32 over type and data, on every chunk. That is the property distinguishing PNG from everything else in this collection: a PNG can say which part of it is damaged. Our reader verifies every checksum, reports the bad ones with chunk type and offset, and reads on. See P22 for what the reference product does with it.

P12 (property) — Upper and lower case in the chunk type

In each of the four bytes, bit 5 carries a statement, and because that very bit is what separates upper from lower case, they can be read: first byte lower case means ancillary (may be skipped), second lower case means private, third lower case is reserved, fourth lower case means safe to copy. That is why a PNG reader need not guess at an unknown chunk type — and why an unknown critical chunk is something different from an unknown ancillary one: for the former the specification says expressly that a reader may not then claim to have read the image correctly.

P13 (property) — The five row filters

See section 3. Two anchors cover them: filter with five rows at eight bits and vierbitfilter with five rows at four bits. Both are computed images; they are checked against the rule and not against transcribed numbers.

P14 (property) — Adam7

See section 3. The anchor is 17 × 11, and that is deliberate: at an edge length divisible by eight all seven passes are the same size and a wrong rounding of the pass size does not show. One place belonging to exactly one pass is checked for each, and then the whole image against the rule.

P15 (property) — The filter distance below eight bits

See section 3 and 2.2. Until 6 September 2026 the branch was covered by no fixture, because all three anchors below eight bits used filter 0.

P16 (property) — Fifteen of twenty-five

Five bit depths and five colour types do not give twenty-five combinations but fifteen. A palette does not exist at sixteen bits — an index into a table of 65536 entries would be larger than any table; truecolour does not exist below eight bits — that is what the palette is for. The probe counts it in closed form instead of believing it.

P19 (property) — Four ways to transparency

See section 3. Three of them live in tRNS — the same chunk, with three entirely different contents depending on colour type. That is where a reader can mistake an alpha list for a colour key; the difference cannot be told reliably from the chunk's length but only from the colour type in the header.

P20 (property) — Several IDATs are one stream

The boundaries between IDAT chunks are not boundaries in the deflate stream. Unpack the chunks separately and you get no further than the first. Pillow writes more than one only above 64 KBytes — a small image therefore never has more than one, and the branch stays unchecked in foreign files. The anchor mehridat forces four chunks on an image of 24 × 16.

Findings against the reference implementation

P17 (BUG there) — Sixteen to eight bits: Pillow clamps at 255 instead of scaling

Pillow reads a sixteen-bit greyscale image correctly — the raw samples come out unchanged. But as soon as the image is brought to eight bits (convert("L") or convert("RGB")), every value above 255 is set to 255 instead of being scaled into the eight-bit range. 1000 becomes 255, 20000 becomes 255, 45000 becomes 255. A sixteen-bit image is then almost entirely white. That is not a rounding difference and not a matter of taste — it is a bug, and it is silent: there is no message, and the result looks like an overexposed image. Measured on Pillow 12.2.0.

How to reproduce — Build a sixteen-bit greyscale image and read it back: im = Image.frombytes("I;16", (3,2), struct.pack("<6H", 1000, 20000, 45000, 300, 60000, 7)), save as PNG, reopen with Image.open. Expected: list(r.getdata()) returns the six values — it does. Then list(r.convert("L").getdata()). Expected: the six values scaled to eight bits, i.e. 4, 78, 175, 1, 233, 0. Observed with Pillow 12.2.0 under Python 3.13: 255, 255, 255, 255, 255, 7 — every value above 255 is clamped instead of scaled. Without a message. The same with convert("RGB").

P18 (open there) — Truecolour at sixteen bits is read using only the high byte

Pillow has no mode for truecolour at sixteen bits. Such a PNG is delivered as an ordinary eight-bit image, by truncation: 20000 becomes 78, 40007 becomes 156 — the high byte. Unlike P17 this is not a bug but a missing mode, and the conversion is at most one away from our rounded one. It stands here because it means Pillow is not usable as a cross-check for this anchor: it cannot deliver the full values at all. So the check runs against the rule the image was built from, plus Pillow's eight-bit values with a tolerance of one.

P22 (open there) — Five conditions without a statement about the file

A wrong checksum goes unnoticed on an ordinary read — load() delivers the image without a hint; only the separate verify() call finds it, and that then aborts instead of saying the image is otherwise intact. A missing IEND is not noticed. An unknown critical chunk is silently skipped, although the specification expressly demands the opposite. A truncated file and a corrupted data byte lead to an OSError without saying which chunk is affected. We report all five with chunk type and offset and read on. That is not a bug in Pillow — it is an imaging library, not a file-inspection tool. It is the difference between displaying an image and being able to say what is in the file — and with PNG that difference is larger than with any other format here, because PNG brings the information along by itself.

P23 (open there) — A text keyword survives only once

If two tEXt chunks with the same keyword occur — which the specification expressly allows — Pillow keeps only the last. With two comments the second remains, the first is gone, and there is no hint that there ever were two. We collect all of them in file order. The same finding as with GIF (I4), in the same place of the same tool — there it concerned comment blocks. A file carrying its provenance in several text chunks is exactly the one where you want to read them.

P21 (open there) — What Pillow never writes

Interlaced (Adam7), two bits, truecolour at sixteen bits, more than one IDAT below 64 KBytes, a colour key — and which of the five row filters it picks it decides itself. Eight of the seventeen anchors therefore had to be built by hand. That is no reproach: a writer picks the simplest form that fits, and Pillow's choice is sensible every time. It stands here because it describes the measurement situation: whoever checks a PNG reader only against files written by Pillow checks roughly half the format.

The Java implementation — where this reader stands among its own kind

Why against javax.imageio in particular. Every other comparison in this module measures against a tool in a different language — Pillow, astropy, pyarrow, meshio. That is good against misunderstandings of the format and says nothing about where this reader stands among its own kind. javax.imageio is the Java implementation it actually competes with in the field: it sits on every machine this module runs on, and it costs no foreign library — the module's rule stays untouched. It is measured on every run, not once: Bildvergleichsprobe, 80 checks now that JPEG is included. And the reader measured against here really is pure Java: com.sun.imageio.plugins.png.PNGImageReader has not a single native method. Measured on 2026-09-06, because adding JPEG revealed that this does not hold there — the JDK's JPEG reader is a JNI wrapper around libjpeg 6b. For this format, then, the comparison really is one among its own kind.

17 anchors, 16 pixel-identical. Colour in eight and sixteen bits, palette with and without transparency, one, two and four bits, greyscale, RGBA, interlacing, several IDAT blocks, colour key — all pixel for pixel identical with javax.imageio.

The one difference is graudeckung — grey with alpha. For that ImageIO returns no grey-space image but TYPE_4BYTE_ABGR, and the sRGB conversion from above applies again. No finding, the same trap in different packaging.

And a trap that is half the yield of the measurement. BufferedImage.getRGB() returns not the pixel from the file but its conversion to sRGB. For greyscale, ImageIO stores the values in a linear grey space and getRGB applies the sRGB curve on top: the raw value 0x25 becomes 0x6A — to three digits exactly (37/255)^(1/2.4) in sRGB encoding. The first run therefore reported differences on every greyscale image, in PNG and in BMP, that is on two independent readers of ours with the same symptom. It looked like a real bug and was none. The comparison goes through the raster. With TYPE_USHORT_GRAY the raster carries the raw 16-bit value while our punkte() is the view scaled to eight bits — whoever shifts there instead of rounding is off by one, and takes that for a bug too.
