The long form – fields as tables

How multidimensional fields in HDF5, netCDF, CGNS, Exodus, VTK, Gmsh and HDF4 become tables that can be queried with SQL: axes as columns, one table per axis combination, C versus Fortran order and block-wise reading.

The problem

Scientific containers have a richer model than a table: groups, and in them fields with any number of axes. That model stays where it is. The long form is a view beside it: a field temperatur(zeit, ort) with three times and two places becomes a table of six rows with the columns zeit, ort, temperatur. Then SELECT zeit, temperatur FROM zeit_ort WHERE ort = 10 works over a netCDF file just as over a dBASE table.

Row number and axis positions

A field with axes of lengths n₀ … nd−1 has N = ∏ nₖ rows. Row r belongs to the axis positions

ik=⌊rsk⌋modnk,i_k = \left\lfloor \frac{r}{s_k} \right\rfloor \bmod n_k,

with strides sk. In C order (HDF5, netCDF) the last axis runs fastest:

sd−1=1,sk=sk+1nk+1.s_{d-1} = 1,\qquad s_k = s_{k+1}\,n_{k+1}.

In Fortran order (CGNS) the first runs fastest: s₀ = 1, sk = sk−1 nk−1. The rows thus follow the storage of the file exactly, and row r is value r without conversion. Treating both orders alike gives, for a 3 × 2 grid, the value of (1,0) at position (0,1) – a grid that looks plausible and is transposed. If an axis has values (a coordinate variable), the value is in the column, otherwise the index.

One table per axis combination

temperatur(zeit, ort) and hoehe(ort) have different row counts. Putting them side by side would repeat the height three times and claim three measurements where there was one. So there is one table per axis combination, named after its axes; every variable on the same axes becomes another value column. If two combinations give the same name, the second is called name#2 and that is reported – overwriting would be a silent loss.

How much the formats know determines the construction: netCDF knows named axes, often with values (table per combination); CGNS knows zones, nodes and cells (table per zone, a second one for cell-centred values, element groups as (element, platz, knoten)); plain HDF5 knows no axes (table per group and shape, axes i, j, k – inventing a name would be a guess).

A netCDF character variable name(n, length) is split into n strings along its last axis; the padding at the end (spaces and null bytes) is not part of the string and is dropped – also when the variable holds a single string only.

Memory: reading in blocks

With HDF5 the cursor fetches B = 65 536 values per column and access, starting at block ⌊r/B⌋·B. Reading N rows sequentially takes ⌈N/B⌉ accesses per column, and a column nobody reads is never loaded. netCDF and CGNS offer no partial access; there a column is read completely on first access, and that is reported.

What follows

  • The long form computes nothing: no means, no interpolation, no unit conversion. The unit is attached to the column as information.
  • What cannot be mapped (more than two billion rows, a type without numeric counterpart, a compound in a multi-axis field) is skipped and named.
  • Row order is that of the file; a query needs ORDER BY only if another order is wanted.

How it is tested

Langformprobe on foreign anchors (netCDF-4, classic netCDF, HDF5, CGNS, Exodus, VTK, Gmsh) and TheorieFBprobe in package langform: a 2 × 3 field in C and in Fortran order row by row against the formula, 65 541 rows across the block boundary with exactly two accesses, combinations with equal names. Counter-probes td22fb-langform-*.

Limits

  • At most 2³¹ − 1 rows per table.
  • netCDF and CGNS keep a column that has been read entirely in memory.
  • Variables on the same axes in a different order give different tables.
