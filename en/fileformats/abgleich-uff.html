Universal File Format (UFF) — comparison against specification and pyuff

As of: 2026-09-07
Our implementation: envisionz.fileformats.uff.UffQuelle with Uffart, read-only, no third-party library
Specification: The SDRC/IDEAS dataset descriptions — public but scattered; references give dataset numbers and line positions
Compared against: pyuff 2.5.6 (Python)
Test bench: envisionz.fileformats.uff.Uffprobe — 140 checks, five foreign anchors, sixteen own fixtures, eight counter-tests

The reference implementation. pyuff is a Python module from the ladisk group (modal-analysis research; grown out of the OpenModal project). It is an independent reimplementation: the Universal File Format came from SDRC and lived on in I-DEAS, today at Siemens; there is no active owner with a Python library of its own. In experimental modal analysis pyuff is the common tool.

Why this one. Because there is no active owner any more and pyuff is the common tool in experimental modal analysis. UFF is a column-fixed text format from the punched-card era; for such a format a second reader that reads the same real files correctly is worth more than any description of the record types.

Feature comparison

UFF is a text format with fixed column positions — a file of datasets, each framed by a line reading -1. That is exactly where its trap lies: it looks like something one can split on whitespace, and it is not.

Twenty fixtures, seven divergences

Four foreign anchors from Uffanker and sixteen of our own from Uffschreiber were run through both readers. On the four foreign anchors and on five of the sixteen own ones both agree. On the rest pyuff does not read the dataset — and not with a statement of what is wrong, but with the message Error when reading data-set(s).

Measured fairly: pyuff offers two ways — read_sets() without an argument reads everything, read_sets(i) reads one dataset. Both were tried. For fremderDatensatz the second way helps: the dataset 58 behind the unknown 2412 can be read individually, only the bulk call fails. For the other six the individual call fails as well.

Fortran numbers without a separator

Fixture Uffschreiber.fortranZahlen(). The number line reads 1.00000E+00-2.00000E+00. These are two numbers: the second is negative, and its minus sign doubles as the separator. Fortran writes like this when the format fills the columns.

Us: we split by column width, as the format prescribes, and read both numbers. pyuff: Error when reading data-set(s). — the dataset stays unread.

Of the ways to fail here, pyuff's is the better one: splitting on whitespace and not failing turns two numbers into one, and that again looks like a number. An error is better than a plausible wrong value. The file still does not get read.

An unknown dataset takes the bulk call down with it

Fixture Uffschreiber.fremderDatensatz(): a dataset 2412 (elements), followed by an ordinary 58.

Us: the 2412 is counted, listed in the dataset directory as not interpreted and named in the findings; the 58 behind it is read. pyuff: read_sets() over the whole file fails; read_sets(1) returns the 58. Anyone using the bulk call — and that is the usual one — loses a file of which part is perfectly readable.

Five more where pyuff does not read even individually

ohneNamen (empty ID lines — permitted by the format), gleicherName (two datasets with the same name — likewise permitted), ungleichUndKomplex (uneven abscissa and complex values, three numbers per point), zuVieleZahlen and zuWenigZahlen (the declared point count does not match the numbers).

We read all five and, for the last two, report what does not add up: "dataset zuviel declares 2 points, the numbers hold 4; the declared count wins". pyuff returns the same message for all five: Error when reading data-set(s).

For the first two this is a loss for no reason: the files are fine. For the last two the file is contradictory, and there an error message is defensible — but it should say which contradiction.

How this was measured

Twenty fixtures written out as .uff and run through envisionz.fileformats.uff.UffQuelle and pyuff 2.5.6 on Python 3.11, each in its own process with a time limit. For pyuff both call paths were tried — the bulk call and the per-dataset call — so that a failure is not attributed to the wrong one.

The sixteen own fixtures are built from the format description and not derived from the reader. Even so: where a divergence hangs on a self-written fixture alone, it proves nothing about the format but shows two different readings. For fortranZahlen the reading is documented — the fixed column layout is part of the dataset description; for ohneNamen and gleicherName likewise, since both are explicitly allowed there.

Our open gaps — this is the work

U10 (decided) — The dataset directory as a table of its own

Alongside the functions this reader exposes a table saetze: for each dataset its running number, its type, the type's name, the line count and whether it was interpreted. That is not a format requirement but a decision — and the answer to the question that always comes first with an unfamiliar UFF file: what is actually in there? pyuff has something similar in get_set_types(), but without saying which of them were interpreted.

U12 (decided) — Writing

pyuff writes UFF. This module does not write — as a guarantee resting on four levels and measured.

Properties of the format — affecting both

U14 (property) — Dataset 2429 — groups — closed on 2026-09-07

2429 collects nodes and elements into groups — "all nodes of the flange", "the elements of the weld". For a measurement series that is irrelevant; for a mesh someone works on, the groups are the structure by which he looks at it at all. Both sides are now read: the headers (number, name, entry count) and the entries (type, type name, tag).

Three traps in fifteen lines. (1) The eighth number of the header counts entries, not lines: each line holds four pairs, and the last line is shorter. Reading it as a line count runs into the next group for every group with more than four entries. (2) The name line is a whole line in format 20A2 — forty columns, spaces included — and it may be empty. Splitting it into words turns "obere Schaufel" into "obere"; discarding it as a blank line shifts the whole remainder of the dataset. (3) The tag is a node, element or load case number, depending on the type in front of it. All three numbering ranges start at one — a mix-up does not show.

Four mutation checks, all red: the eighth number as a line count (10 failures), the name line split into words (1), blank lines skipped everywhere (6), the pair read the other way round (9). The anchor carries all three cases in one file: a group of six entries mixing nodes and elements, one with an empty name, one without entries.

The anchor is hand-built and read back by pyuff 2.5.3 — hand-built because pyuff cannot write a 2429 at all (item U15), read back because the reference values must be foreign. For the third group pyuff yields nothing (item U16); that it arrives is therefore not a comparison but a surplus.

U9 (property) — Five further dataset types — closed on 2026-09-07

Now read are 2412 (elements), 82 (line traces), 55 and 2414 (results) and 2420 (coordinate systems) — plus, as before, 58, 15, 151, 164 and 2411. Each type becomes a table; 55 and 2414 share one, with the type as a column beside, because they are the same data in two spellings. All expected values are pyuff 2.5.3's, which reads the same file.

Four traps, and all four are shifts of exactly one line.

First, dataset 2412: the orientation line. An element carries six key numbers, then its nodes — unless it is a rod or beam: then between them stands a line with three orientation numbers. Miss it and you read a rod's nodes as 0,0 instead of 1,2, and everything after is shifted. Which types belong is not a range but a list: 11, 21, 22, 23 and 24. The 25 does not belong, although it lies right beside — that is measured (pyuff carries exactly these five) and not inferred.

Second, the same dataset: the node list may wrap. A hexahedron with twenty nodes does not fit into eighty columns. So it is read by the node count from the header and not by lines. That is at the same time a difference to pyuff, which reads line-wise: on a wrapped element its reader breaks, ours does not. The price is the opposite case — a writer that pads the line with zeroes is read wrongly by us and rightly by pyuff. Both occur; the specification is on our side.

Third, results 55 and 2414: how many numbers per node stand there is in the header — and with complex data it is twice as many, because the number in the header counts quantities and not numbers. Six values fit in a line, twelve do not, and a reader assuming one line per node falls over exactly where it gets interesting. How many key lines precede the values also depends on the analysis type; so the first line carrying a single whole number is sought — that is the first node number.

And the 2414 names the location: dataset_location says whether the values sit at the nodes, at the elements or at the element nodes. In the latter two the first number per record is not a node number, and a reader taking it for one assigns the results to the wrong places. This reader says so as a finding and reads the numbers anyway — they are there.

Fourth, coordinate systems 2420: four lines per system, not three. The first three are the rotation, the fourth the translation. Three is the number one expects — a rotation matrix has three rows — and taking it makes you read the first system's translation as the second's key line.

The element types get a name along the way: 91 becomes "thin triangle (3)". The list is of the common types and expressly not complete — there are over two hundred. A number without a name is no information.

U11 (property) — The binary dataset 58b — closed on 2026-09-07

A dataset 58 may carry its numbers in binary; the ID line then reads 58b and names, in its fourth field, how many ASCII lines follow, and in its fifth, how many bytes come after. It is read.

After that the file can no longer be read line by line, and that is the real point. Anything can stand in those bytes, including 0x0A. Read the file as lines and you split in the middle of a floating-point number — and then read the whole rest shifted by an indeterminate number of bytes. The error does not stop at the binary dataset; it makes the file unreadable. So the bytes are read first and the blocks are cut out before anything is interpreted as a line.

The ordinate type gives the width, and nothing else does. Four values occur: 2 real single, 4 real double, 5 complex single, 6 complex double. The byte count in the ID line says how much is there but not how it is divided — it is therefore no usable cross-check. It is still checked that it works out; a remainder is a finding.

And the byte order stands per dataset, not per file: the second number of the ID line, 1 for little and 2 for big. It is there because UFF comes from a time when both were usual. Read it once and take it for the whole file and, on a file assembled from two sources, half the curves are wrong — and the wrong numbers look like numbers.

U5 (property) — Two flags, four cases, three numbers per point

Line 7 of dataset 58 carries two independent flags: whether the abscissa is even and whether the ordinate is complex. That yields four cases with one, two or three numbers per point. Implementing only the two common ones — even-real and even-complex — reads the other two offset by one point per point, and the curve looks like noise rather than like an error.

Findings against the reference implementation

U15 (BUG there) — pyuff cannot write four of its own datasets

prepare_2412 builds a data structure that write_sets silently discards. The preparation returns a dictionary with string keys (element_nums, fe_descriptor, …); but the writer _write2412 iterates over the keys and skips every one that is not an integer. What comes out is an empty dataset — two lines, -1 and 2412, and nothing in between. Without any message. The reader _extract2412 expects exactly the integer-keyed structure the writer wants; those two match each other, and the preparation matches neither.

prepare_58 with binary=1 leaves the file seven bytes long. A write_sets([d], mode='overwrite') with a binary dataset 58 produces a file of seven bytes — the closing separator line and nothing else. The dataset is gone. Again without a message. A hand-built 58b, on the other hand, is read flawlessly.

prepare_2414 and prepare_2420 demand shapes their description does not name. prepare_2414 raises Error writing data-set #2414 unless the analysis type is five — for any other type the writer has no branch. And prepare_2420 wants the transform as four rows by three columns; give it three by four — the shape one expects of a rotation matrix with translation — and it raises Error writing data-set #2420. Neither is a silent error; they only cost time.

prepare_2429 and _write2429 disagree about the shape (measured on 2026-09-07 while closing U14). prepare_2429 yields {'type': 2429, 'groups': [...]}; _write2429 reads dset['group_number'] from it and does not find the key. Out comes Exception('Error writing data-set #2429'). A dataset 2429 cannot be written with pyuff along the intended path. The reader _extract2429, on the other hand, expects exactly the groups form — preparation and reader match each other, the writer matches neither.

Feeding _write2429 a single group by hand brings out the second defect: the last, non-full line writes the wrong entries. The loop takes entity_type_code[i * 4] instead of entity_type_code[full * 4 + i]. With six entries the last line reads 1 101 5 105 — the first entry again and the fifth, while the sixth is missing. Same with ten. The file is formally valid afterwards and wrong in content, and the stated count still matches.

And a third: prepare_group writes active_dof_set_no_for_group into three fields. 'active_temperature_set_no_for_group': active_dof_set_no_for_group, and the same line again for active_contact_set_no_for_group. Measured: with dof=9, temperature=3, contact=4 out come 9, 9, 9.

The 2412 is the worst: it writes a file that looks like a file and does not contain the dataset. Whoever passes on a mesh with it passes on a mesh without elements. The 2429 is the second worst — not because it fails, but because it does not fail when fed by hand.

How to reproduce — With pyuff 2.5.3 under Python 3.10: d = pyuff.prepare_2412(...) as above, then pyuff.UFF('e.uff').write_sets([d], mode='overwrite'). Expected: a file with two elements. Observed: the file contains dataset 2412 with zero elements, and read_sets(0) returns {}. Without a warning. With a hand-built dictionary {'type': 2412, 11: [ … ]} — key as an integer — the same library writes and reads the elements flawlessly.

U16 (BUG there) — pyuff loses an empty group at the end of the file

A group without entries is legal: header and name line, nothing else — two lines. But _extract2429 runs while lineIndex < len(split_data) - 2, and an empty group at the end lies exactly within that two-line margin. It drops out. Without a message, and the remaining groups arrive correctly — only one is missing, and one is not told.

It is the position, not the emptiness. The same empty group in the middle of the file is read. That is exactly what makes the defect unpleasant: looking for it with a file whose empty group sits in the middle will not find it.

How to reproduce — Build three files with the same dataset 2429, each with the header in format 8I10 and the name line in format 20A2: (a) groups A (two entries), leer (zero entries), C (one entry) in that order; (b) the same three but with leer last; (c) only A and C. Then read each with pyuff.UFF(file).read_sets(0)['groups'] and count the group numbers. Expected: (a) three, (b) three, (c) two. Observed with pyuff 2.5.3 on Python 3.10: (a) three — [(1,'A',2), (2,'leer',0), (3,'C',1)] —, (b) two — [(1,'A',2), (3,'C',1)] —, (c) two. The cause is the line while lineIndex < len(split_data) - 2 in pyuff/datasets/dataset_2429.py, function _extract2429.

U1 (open there) — Text before the first dataset

Some tools write a header line above the file before the first -1 frame begins. We skip it and name it in the findings; pyuff does not cope with it.

U2 (open there) — Missing closing separator

A truncated or hand-spliced file ends without the final -1. We read the last dataset anyway and report it; pyuff returns zero datasets.

U3 (BUG there) — An unknown dataset makes the bulk call fail

See 2.2. The file is fine, only one of its dataset types is unknown to pyuff — and read_sets() over the whole file aborts instead of skipping the unknown type. Through the per-dataset call the rest is reachable; anyone using the bulk call will not notice.

How to reproduce — A UFF file with two datasets: first a dataset 2412 (elements) of two lines, then an ordinary dataset 58 named dahinter. Then pyuff.UFF(file).read_sets(). Expected: the 58 comes back, the 2412 is skipped or reported as unknown. Observed with 2.5.6 on Python 3.11: Exception: Error when reading data-set(s). for the whole file; read_sets(1) on the other hand returns the 58 cleanly. The file is produced by envisionz.fileformats.uff.Uffschreiber.fremderDatensatz().

U4 (open there) — Dataset 58 without a name in the ID lines

The ID lines may be empty. We then form the table name from response node and direction — knoten21_richtung2 — so that the table is addressable at all. pyuff does not read the dataset.

U6 (BUG there) — Fortran numbers without a separator stay unread

See 2.1. 1.00000E+00-2.00000E+00 are two numbers at fixed column width. pyuff does not read the dataset. This is the most consequential of the divergences, because files written that way come from every Fortran tool — and in this corner that is most of them.

How to reproduce — A UFF file with one dataset 58 whose number lines are in Fortran fixed format: two values immediately adjacent without a space, the second negative, i.e. 1.00000E+00-2.00000E+00, and with D instead of E as the exponent letter. Then pyuff.UFF(file).read_sets(0). Expected: two numbers per line. Observed with 2.5.6 on Python 3.11: Exception: Error when reading data-set(s). The file is produced by envisionz.fileformats.uff.Uffschreiber.fortranZahlen().

U7 (open there) — Contradictory point count

If line 7 declares a point count that does not match the numbers, we read as far as we can and report both counts. pyuff does not read the dataset. An error is defensible here — the file is contradictory — only the message does not say which contradiction.

U8 (open there) — Two datasets with the same name

Permitted by the format and common in measurement files — the same measuring point in two runs. We turn it into two tables and tell them apart; pyuff reads neither.

What is hard about the format

It looks like text and is column-based. The numbers sit in fixed fields; splitting on whitespace works for most files and not for the Fortran-written ones. That is the one place where a UFF reader can go silently wrong — and it hits precisely the files from the oldest and most widespread family of tools.

It is not a format but a family. More than a hundred dataset types, each with its own line layout, and the fewest of them are ever needed. No reader can do all of them; the only question is whether it names the others or keeps quiet about them.

What is good: you can open a UFF file in a text editor and see what is in it. In an argument about which reader is right, that is worth more than it sounds.

The Java implementation — where this reader stands among its own kind

Why this section. Every other comparison in this module measures against a tool in a different language. That is good against misunderstandings of the format and says nothing about where this reader stands among its own kind. What matters is the distinction between a pure reimplementation in Java and a wrapper around the original C library: only the reimplementation solves the same task under the same conditions as this reader; a wrapper calls the original.

No complete Java reader found. jCAE contains a UNV writer in pure Java (org.jcae.mesh.xmldata.MeshExporter.UNV); whether a reader sits there too could not be established, and the project has been very quiet for years. For dataset 58, the measurement side, there is Python (pyuff) and C++ (unvpp), but no discoverable Java counterpart.

How solid this is. Researched on 2026-09-06 via web and GitHub search; Maven Central's search API was blocked at the time, so a systematic artefact search was not possible. "Nothing found" is therefore not the same as "nothing exists" — a little-visible or in-house implementation would not be discoverable this way. What stands here is the state of an honest search and not a claim of completeness.
