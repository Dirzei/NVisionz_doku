PNG, GIF and BMP – background

What the three readers must know beyond compression: checksums per chunk, compositing animated images, gamma, interlacing, disposal, row padding and stretching short colour values to eight bits.

What this is about: an image is more than its points

How the points are packed – Deflate with row filters, LZW, run lengths – is described on the page Compression. This page covers the rest: where a point belongs, which colour a stored number means and what happens to the canvas after a frame. Errors at these places throw no exception; they deliver an image that looks like an image – shifted, mirrored, too dark or with a remnant of the previous frame.

PNG: chunks with their own checksum, gamma

A PNG file is a sequence of chunks. Each carries a CRC-32 (polynomial 0x04C11DB7, reflected, initial value and final inversion 232−12^{32}-1) over the four type bytes and the data, not over the length field. This gives a property no other format of this collection has: a bit error can be attributed to one chunk. The reader still reads a chunk with a wrong checksum and reports it; the statement is the finding, not the reason to stop.

Gamma. gAMA holds the file's encoding exponent gg: the stored value VV arose from the light LL as V=LgV = L^{g}, usually g=1/2.2≈0.45455g = 1/2.2 \approx 0.45455. A screen shows a value V'V' as L'=V'γsL' = V'^{\gamma_s}. For L'=LL' = L to come out,

V'=V1/(gγs)V' = V^{1/(g\,\gamma_s)}(1)

must hold. With g=1/2.2g = 1/2.2 and γs=2.2\gamma_s = 2.2 the exponent is one and nothing changes; a linear file (g=1g = 1) is brightened on the same screen with 1/2.21/2.2 – the middle value 128 becomes 186.

Until 2026-10-19 the code used the exponent gγsg\,\gamma_s instead of its reciprocal. In the normal case this does not show (both are one); a linear file came out darker instead of brighter. Corrected while writing this page.

APNG: frames on a canvas

An animated PNG describes each frame with fcTL: rectangle, duration as a fraction z/nz/n seconds (n=0n = 0 means n=100n = 100), disposal and blend mode. The duration is thus 1000z/n1000\,z/n ms.

Blending (blend_op 1). The new frame with coverage aoa_o lies over a point with coverage aua_u. The result has its own coverage, and the colour is divided by it:

a=ao+au(1−ao),c=coao+cuau(1−ao)aa = a_o + a_u\,(1 - a_o), \qquad c = \frac{c_o\,a_o + c_u\,a_u\,(1 - a_o)}{a}(2)

Dividing by aoa_o instead of aa, or dropping the result coverage, gives too dark colours at half-transparent places. Half red over half blue gives a=0.75a = 0.75 and red to blue as 2 : 1. With blend_op 0 the frame replaces the point including its coverage.

Disposal (dispose_op). After display, the frame's rectangle is: 0 left as is, 1 set to transparent black, 2 restored to the state before the frame. This applies to the next frame, not to the one shown.

GIF: sub-blocks, interlacing, disposal

Sub-blocks. A frame's LZW stream stands in blocks of at most 255 bytes, each preceded by its length, a zero closes. Block boundaries are not code boundaries: a 9-bit code may run across two blocks. The reader therefore joins the blocks into one stream first; the same stream in blocks of 255 or of one byte gives the same image.

Interlacing. With the bit set the rows stand in four passes: every eighth from 0, every eighth from 4, every fourth from 2, every second from 1. The passes cover each row exactly once, since they split the row numbers by their residues modulo 8: {0},{4},{2,6},{1,3,5,7}\{0\}, \{4\}, \{2, 6\}, \{1, 3, 5, 7\}. The row stored as the kk-th in the file is

yk=sp+(k−Kp)dp,(s,d)∈{(0,8),(4,8),(2,4),(1,2)}y_k = s_p + (k - K_p)\,d_p,\quad (s, d) \in \{(0,8), (4,8), (2,4), (1,2)\}(3)

with KpK_p the number of rows in the passes before pp. For ten rows the order stored is 0, 8, 4, 2, 6, 1, 3, 5, 7, 9.

Transparent index. The control block before a frame can declare one colour index transparent; at those places the canvas stays as it is.

Disposal. 1 means leave, 2 restore the rectangle to the background, 3 restore the state before the frame – each only within the rectangle.

What "background" means for 2 is a choice. The wording of GIF89a fills the rectangle opaquely with the background colour of the screen descriptor. Browsers make it transparent, and animations from the web are built for that. The reader offers both: transparent (00000000\mathtt{00000000}, default) or background colour (FF\mathtt{FF} before the colour from the global table; without a table or with an index outside it, opaque black). The choice is made in the settings under Appearance, or for one run with the start option -Denvisionz.gif.entsorgung=durchsichtig|hintergrundfarbe, which takes precedence over the setting.

BMP: rows, direction, short colour values, run lengths

Row padding. Every row starts at a position divisible by four. With ww points of bb bits a row occupies

Z=4⌈wb32⌉ bytes.Z = 4 \left\lceil \frac{w\,b}{32} \right\rceil \text{ bytes.}(4)

Three points of 24 bits are 9 payload bytes and 12 occupied; 33 points of 1 bit are 8 bytes. Forgetting the padding gives a sheared image.

Direction. With a positive height the first row of the file is the bottom row of the image, with a negative one the top. The colour sum is the same in both cases; only the position reveals the error.

Short colour values. A component of bb bits stands for v/(2b−1)v/(2^b-1). Brought to eight bits this is 255v/(2b−1)255\,v/(2^b-1), rounded:

v8=⌊255v+⌊(2b−1)/2⌋2b−1⌋v_8 = \left\lfloor \frac{255\,v + \lfloor (2^b-1)/2 \rfloor}{2^b-1} \right\rfloor(5)

Plain shifting turns 31 (five bits) into 248 instead of 255; the common bit replication is off by one at four of 32 places for five bits (3 gives 24 instead of 25). From eight bits on the top eight are taken.

Run lengths (RLE8). Two bytes per instruction: (n,c)(n, c) with n>0n > 0 repeats cc; (0,0)(0, 0) ends the row, (0,1)(0, 1) the image, (0,2,dx,dy)(0, 2, dx, dy) jumps – the skipped points remain unwritten –, (0,n)(0, n) with n≥3n \ge 3 starts nn unpacked points, padded to an even number of bytes.

What follows

  • The dangerous errors of these formats change no sum: direction, interlacing and channel order only swap places. That is why the probes check individual positions, not only sums.
  • Animated images have a state. A frame cannot be interpreted without the frames before it; the canvas after frame kk depends on all earlier disposals.
  • The blend formula (2) is the same "over" operation as in WebP and in image editing; computed in integers it is at most one step from the floating-point version.
  • The gamma conversion (1) is an offer (punkteMitGamma); punkte() delivers the values of the file. Without gAMA nothing is computed.

How it is checked

The probes png.TheorieFCprobe, gif.TheorieFCprobe and bmp.TheorieFCprobe build their files themselves – including animated PNG with half-transparent frames, GIF with one-byte sub-blocks and BMP with a jump and an unpacked run – and compute the expected values from the formulas on this page: blending in floating point with at most one step of distance, gamma over all five sample values, the stretch for all values from 1 to 7 bits. Next to them stand the foreign anchors from Pillow in Pngprobe, Gifprobe and Bmpprobe.

Limits

  • GIF disposal 2 makes the rectangle transparent by default, as browsers do; the background colour following the 1989 wording can be chosen in the settings. Which reading a file means is not stated in it.
  • Colour profiles (iCCP, BMP colour space) are read and reported but not applied.
  • APNG frames outside the canvas are clipped, not rejected.
