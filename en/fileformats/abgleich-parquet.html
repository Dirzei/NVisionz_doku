Apache Parquet — comparison against specification and pyarrow

As of: 2026-09-27
Our implementation: envisionz.fileformats.parquet.ParquetQuelle, read-only, no third-party library — including an own Thrift reader
Specification: Apache Parquet Format (parquet-format), public; references give Thrift structures and field names
Compared against: pyarrow 25.0.1 (parquet-cpp)
Test bench: envisionz.fileformats.Parquetprobe — 309 checks, with seven foreign anchors for nested types; parquet.Deltaprobe 71

The reference implementation. pyarrow is the official Python implementation of Apache Arrow and, since the merge with parquet-cpp, carries its Parquet side as well: the standalone project is archived and has been absorbed into apache/arrow. Parquet itself is a separate Apache Software Foundation project. This measures against the foundation's own C++ implementation of the format it publishes.

Why this one. Because the Apache Software Foundation's C++ implementation is at the same time the publisher's implementation. For a format with this many encoding paths — RLE hybrid, dictionary, definition and repetition levels — a second opinion is worthless; one needs the one everybody else aligns to.

Feature comparison

Parquet is a columnar table format with a Thrift-encoded directory at the end of the file. Of the formats compared here it is the one with the most layers: file → row group → column chunk → page → encoding → compression, and each layer offers choices.

What was measured

Seven foreign anchors from Parquetanker, produced by parquet-cpp-arrow 25.0.1 and read both ways: all six primitive types side by side, missing values via definition levels, a dictionary-encoded column, twenty rows across several pages, twelve rows of text, FIXED_LEN_BYTE_ARRAY next to raw BYTE_ARRAY, and two hundred rows across several row groups. No divergence — types, column names, row counts and values agree in all seven cases.

With a format of this depth that is not a given, and it is also not a complete statement: the seven anchors hit the paths pyarrow takes by default. What pyarrow writes only on request — delta encodings, nested types, Brotli — is marked no in the tables and is not measured but derived from both implementations' source. An anchor for it is missing, and saying so is the more honest answer than a tick.

What is hard about the format

Three places where a Parquet reader fails — and none of them is where one looks for it.

First: Thrift. The directory is encoded in the compact protocol, with zigzag varints and field numbers as deltas to the previous field. Failing to implement that fully reads the structure wrongly at the first place a field is absent — and absent fields are the norm in Thrift, because unchanged defaults are not written at all.

Second: the definition levels. Whether a value is missing is not stored with the value but in a separate, RLE-hybrid encoded stream in front of it. Skipping it yields a column that is too short — and then every following row shifts by one. The result is numbers that all really exist, wrongly assigned.

Third: the RLE hybrid. The same stream alternates between run lengths and bit-packed blocks, and which is current is stated in a zigzag header. The bit width comes from outside — for levels from the nesting depth, for dictionaries from the page's first byte. Getting the width wrong reads perfectly valid indices into a perfectly valid dictionary and yields nothing but wrong words.

What is good: the directory is at the end and describes everything. Whoever can read the last eight bytes knows how large the directory is, and whoever can read the directory knows everything else — without touching a single data page. For gigabyte-sized files that is the whole difference.

The items

The Note column names the kind in front of the identifier. Only the gaps are work.

Our open gaps — this is the work

Since 2026-09-25 nothing is left here — P12 stands under 5.3.

Deliberate decisions — nothing to do

P18 (decided) — Skipping belongs in the SQL layer

Statistics, page index and Bloom filter are now there (P15, P17) — they are not used for skipping, and that is not a leftover but the interface. A Datenquelle has tables and cursors; it has no predicate one could hand it. Without a question there is nothing to skip: "read all rows, but skip some" is not an instruction but a bug. The predicate belongs to the SQL layer (item DB10), and so does the skipping — together with everything attached to it: which row numbers a skipped page consumes, what becomes of LIMIT, and what happens when the statistics lie. What belonged here is the information, and it stands there as two entirely ordinary tables.

P16 (decided) — No decryption

Recognised yes, decrypted no — and that is not a half measure but this reader's boundary, drawn where it belongs. Parquet Modular Encryption encrypts footer and pages individually with AES-GCM; the keys come from a key store that the file does not and cannot contain — otherwise it would not be encrypted. A reader wishing to decrypt would therefore need not cryptography but key management: where the key comes from, who may hand it out, how long it stays in memory. That is not a format matter, and it would be the first place in this workspace where a file no longer speaks for itself. What was missing was the information, and that is now there (P9).

Properties of the format

P12 (property) — Nested types — closed on 2026-09-25 (one level) and on 2026-09-27 (any depth)

Repetition levels are now read, and a leaf's levels come from its path in the schema (Blattpfad): each optional or repeated group above raises the maximum definition level. A struct becomes one column per leaf (s.a, s.b); if the struct is missing, both are. A list becomes a text column in square brackets, and the three cases stay distinguishable: list missing, list empty ([]), element missing ([null, 7]). A map yields keys and values as two lists of equal length (m.key, m.value). The column name drops the wrapping — l.list.element becomes l. Measured against pyarrow 25.0.1 with data pages of version 1 and 2 and on 3000 rows whose lists run across page boundaries. Lists within lists (repetition level above 1) are rejected by name — hence partial. Found and fixed on the way: for version 2 data pages is_compressed was not read. pyarrow stores a page uncompressed when compression does not pay off, and that page was then decoded as a Snappy stream.

Addendum 2026-09-27 — across several levels. A repetition level above 1 is no longer rejected but assembled as nested lists: Blattpfad.stufen() gives per level the definition level at which that level's list is present but empty; below it the list is missing (or the element of the level above), above it the list carries an element, and a slot's repetition level says at which level a new element starts. The result is a text in nested brackets ([[1, 2], [3]], [[null, 4], null, []]). Found and fixed on the way: in a list of structs the column was named ls.element.a instead of ls.a — element counted as wrapping only when it was a leaf; now always in the three-level form (the repeated group has exactly one child). Measured on three files from pyarrow 25.0.1 (Parquetanker.verschachteltTiefV1/V2/Lang, build script test/proben/p12_tief.py): list<list<int32>>, three levels, list<struct>, struct<…, list>, struct<struct>, map<string, list>, map<string, struct>, list<map>, with data pages of version 1 and 2 and 2000 rows across small pages; the expected rows are pyarrow's own read-back (to_pylist), projected onto one column per leaf (p12_soll.py). The old anchor verschachteltTief, until then "rejected by name", now yields what pyarrow reads. Deliberately left: the per-leaf column only knows value or empty — whether a struct is missing or just its field cannot be seen there (pyarrow distinguishes None and {'a': None}); hence the one partial row.

P20 (property) — BIT_PACKED — closed for levels on 2026-09-23

Deprecated since Parquet 2.0, used only for levels, and the only encoding that packs most significant bit first, with no length prefix. Since 2026-09-23 definition levels in it are read (Spaltenwerte.bitGepacktMsb); the anchor is the worked example of the specification (0 to 7, width 3), because no current writer produces it (Bitpackprobe). As an encoding of values it stays rejected — there would be nothing to measure it against.

P14 (property) — Six of seven, and the gap says its name

Closed on 2026-09-07. Read now are all seven: uncompressed, Snappy, gzip, LZO, Brotli, LZ4 (both variants) and zstd — all from framework-compress, without a third-party library. LZO arrived the same evening with BF37; pyarrow cannot write it at all. Closing it exposed a contradiction, and it was in this document: since 2026-09-05 it claimed zstd and LZ4 were present. The source said otherwise — Packung.ZSTD and LZ4_RAW stood at no, and Spaltenwerte.entpacke had no branch for them at all. The source was right. The mix-up is easy to explain and therefore worth recording: on that day zstd and LZ4 arrived in framework-compress — they were never wired into the Parquet reader. "The house can do it" and "this reader uses it" are two statements, and the second does not follow from the first. New alongside: LZ4 in the Hadoop frame, the superseded variant with two four-byte numbers in front — most significant byte first, the only place in a Parquet file where a number is stored that way. Three foreign anchors from pyarrow 25.0.1 carrying the same content in three compressions; that way the anchor measures the decompression and nothing else.

P13 (property) — The differences are smaller than the numbers

Closed on 2026-09-07. A measurement series rises; its numbers need 32 or 64 bits, its differences often three. All four delta encodings are now read. The five places where it silently goes wrong: first, a block's minimum delta is signed and is added to every value — omitting it turns a falling series into a rising one; second, the first value sits in the header and is not a difference, but counts; third, the bit widths of all miniblocks are present, including the empty ones in the last block, but their data is not — counting bytes through reads past the end; fourth, the bit width may be 64, and (1L << 64) - 1 is 0 in Java, not -1; fifth, in DELTA_BYTE_ARRAY the common prefix refers to the previous value, and a single wrong one spoils all that follow. Measured against four anchors from pyarrow 25.0.1 with column_encoding and dictionaries switched off — among them Long.MIN_VALUE beside Long.MAX_VALUE (bit width 64), a falling series, an empty string in the middle of the prefix chain, and -0.0, whose single set bit sits in the last byte stream.

P15 (property) — What the file says without reading the data

Closed on 2026-09-07. For every column of every row group there are minimum, maximum, null count and optionally distinct count; plus, in separate blocks outside the footer, the page index made of ColumnIndex (per-page bounds) and OffsetIndex (per-page location, size and first row). Both are now readable, as two ordinary tables spaltenstatistik and seiten. Three traps, and all three cost rows silently: first, there are four Thrift fields for two numbers — fields 1 and 2 are deprecated and were compared signed for byte arrays, which is wrong for UTF-8 as soon as a character above 0x7F occurs; the new pair (5 and 6) beats them. Second, the booleans in null_pages are stored as a whole byte using the field-header numbers: 1 means true, two means false — checking "not zero" declares every page empty. Third, the lists min_values/max_values carry an empty byte string for an empty page, not an omitted entry; skipping them shifts every following page by one. Measured against three anchors from pyarrow 25.0.1, one with an empty page in the middle of a column — on a column with a single page the wrong interpretation looks right too.

P17 (property) — The question statistics cannot answer

Closed on 2026-09-07. For a sorted column the range between minimum and maximum says a lot; for an identifier it says nothing, because everything lies between the smallest and the largest string. The Bloom filter answers "does this one value perhaps occur here?" — with a reliable no or a non-committal maybe. Parquet uses the split-block filter: a block is 32 bytes and fits in a cache line, the upper half of the hash picks the block, the lower half picks exactly one bit per word. The hash is xxHash64 with seed 0, rebuilt here from the specification — it is prescribed, a third-party library was out of the question, and a different hash would not be different but wrong. Cross-checked against the published values (xxHash64("") = ef46db3751d8e999, xxHash64("abc") = 44bc2cf5ad770999) and against a file from DuckDB 1.5.5: of 100 present values none is denied, of 1000 foreign ones 9 are falsely affirmed. The block number comes from a multiplication, not a modulo — with a single-block filter the wrong arithmetic looks right too, hence a second anchor with four blocks.

P9 (property) — Encrypted is information, corrupt is a false trail

Closed on 2026-09-07. An encrypted file carries PARE instead of PAR1 at both ends — four bytes, in the same place. A reader that knows only PAR1 reports a corrupt file, and then somebody checks disk, wire and writer while the file was fine all along. The reader now says what is the case. Closing it exposed a second defect, and that one was ours: the magic check existed in two places — once in Parquetkopf for a file in memory, once copied into ParquetQuelle.oeffne for the channel route. The new detection sat in the one; the other was the one being called. The probe noticed, not the reading. A copied check is not a second check but the same one, ageing separately from now on — there is only one of it now. pyarrow 25.0.1 reports the case just as clearly (Could not read encrypted metadata, no decryption found in reader's properties). Decryption itself is a decision and stands as P16 in 5.2.

P10 (property) — Four time reckonings in one format

Closed on 2026-09-07. DATE is days since 1970-01-01 in an INT32; TIME_MILLIS/TIME_MICROS a time since midnight; TIMESTAMP_MILLIS/TIMESTAMP_MICROS an instant since the epoch; and INT96 the old Impala timestamp: twelve bytes, least significant first, eight bytes nanoseconds of the day, then four bytes Julian day. 1970-01-01 is Julian day 2440588; failing to subtract it lands you in 4713 BC. Three traps, none of which announces itself: a negative day count read unsigned becomes the year 5881580; the day part of an instant goes wrong for negative values if computed with / instead of Math.floorDiv; and pyarrow 25 no longer sets a ConvertedType for TIME at all, only the new LogicalType in Thrift field 10 — a reader that reads just the old field 6 sees no meaning in a fresh file and hands out the bare number 51785123. Measured against two anchors from pyarrow 25.0.1: typen with date, time, instant and the date 1969-12-31, and int96, written with use_deprecated_int96_timestamps=True, carrying a value before the epoch.

P11 (property) — An amount short by two digits looks like an amount

Closed on 2026-09-07. DECIMAL stores a fixed-point number as INT32, INT64, BYTE_ARRAY or FIXED_LEN_BYTE_ARRAY; precision and scale are separate Thrift fields (7 and 8) beside the meaning, not inside it. For the byte-array forms the number is most significant byte first and signed — exactly what new BigInteger(byte[]) does, and exactly the opposite of everything else in Parquet, where least significant comes first. The real decision lies elsewhere, though: a double carries fifteen digits. From DECIMAL(30,2) holding 12345678901234.56 it would silently make 1.234567890123456E13 — the last digits gone, without a word. So a column with more than fifteen digits of precision comes out as text (BigDecimal.toPlainString) and not as a number: better a text that is right than a number that computes and is wrong. Measured against typen from pyarrow 25.0.1 with decimal128(10,2) and decimal128(30,2).

P1 (property) — Thrift compact protocol

See section 3. The reader here brings an own Thrift reader — not out of sportsmanship, but because the alternative would have been a third-party library and Parquet uses only a tiny slice of Thrift.

P2 (property) — The dictionary is a page like any other

The dictionary page sits before the data pages of the same column chunk and carries its values PLAIN encoded. The data pages then carry indices into it, bit-packed with a width stated in the page's first byte. Mistaking the dictionary page for a data page reads the values twice — once as words and once as indices.

P3 (property) — Missing values are stored elsewhere

See section 3, second point. Both implementations get it right; anchor f2 measures it with a column in which two of five values are missing.

P4 (property) — Five compressions, and none is described in the file

The column chunk names a number — 1 means Snappy, 2 gzip, 6 zstd. What those algorithms do is nowhere in Parquet; a reader has to bring them along. That is why a Parquet reader became possible in this workspace only once framework-compress had them — and why the last three (gzip, LZ4, zstd) arrived on 2026-09-05 together with BF30, BF34 and BF33.

Findings against the reference implementation

P21 (BUG there) — fastparquet writes a header that does not belong there

fastparquet 2026.5.0 compresses its LZO pages with python-lzo's lzo.compress — which prepends its own header: one byte 0xF0 and four bytes of uncompressed length, most significant byte first. That header does not belong in a Parquet page; there the raw LZO1X block begins, as hadoop-lzo writes it. fastparquet cannot notice: it reads back with the same library, which eats its own header again. For any other reader the page is unreadable — and the error shows not at the header but two hundred bytes later as "back-reference of 1770 bytes, only 223 emitted". Our reader skips the header, but only when it is confirmed: the length inside must match the size the page states anyway. Nothing is guessed.

How to reproduce — With fastparquet 2026.5.0 and python-lzo: fastparquet.write('x.parquet', df, compression='LZO', write_index=False) for a 200-row DataFrame. Then inspect the first data page by hand: it begins with f0 00 00 06 4f, python-lzo's header, instead of the first command byte of an LZO1X block. pyarrow 25.0.1 cannot read the file at all (LZO is missing there entirely); fastparquet itself reads it without complaint. The file is held as a foreign anchor in the test bench: envisionz.fileformats.Parquetanker.packungLzo().

P19 (open there) — A switch that is a wish

WRITE_BLOOM_FILTER true in DuckDB 1.5.5 does not always produce a Bloom filter. DuckDB builds it from the column's dictionary; if it picks PLAIN for a column — with few rows, or with very many distinct values — no filter is created, and the file nowhere states that the wish went unfulfilled. Measured: the same column with 20 rows yields no filter, with 40 one; with 2000 distinct values none again. This is not a defect — a Bloom filter is an acceleration, not a promise — but relying on it when writing and building on it when reading means relying on something that is not there. A reader should therefore always check whether a filter is present rather than assume it.

How to reproduce — With DuckDB 1.5.5 on Python 3.10 issue the same statement twice, differing only in row count: COPY (SELECT ('w'||(i%5))::VARCHAR AS name, (i%7)::INTEGER AS id FROM range(N) t(i)) TO 'b.parquet' (FORMAT parquet, COMPRESSION uncompressed, WRITE_BLOOM_FILTER true, ROW_GROUP_SIZE N) for N = 20 and N = 40. Expected: a Bloom filter both times. Observed: at N = 20 bloom_filter_offset is unset in both columns and the encoding is PLAIN; at N = 40 it is present (offsets 334 and 381, 47 bytes each) and the encoding is PLAIN_DICTIONARY. With SELECT ('k'||i) FROM range(2000) — 2000 distinct values — it is absent again. The N = 40 file is held as a foreign anchor in the test bench: envisionz.fileformats.Parquetanker.bloom().

P8 (open there) — Naming rather than guessing

For an unknown encoding, an unknown compression and a too-new format version our reader names the column and the reason and leaves it empty; pyarrow aborts in the first two cases with a message that does not name the column, and reads on in the third. Neither is wrong — but with a file of two hundred columns, "column preis_netto uses encoding DELTA_BINARY_PACKED" is information and "unsupported encoding" is a search task.

The Java implementation — where this reader stands among its own kind

Why this section. Every other comparison in this module measures against a tool in a different language. That is good against misunderstandings of the format and says nothing about where this reader stands among its own kind. What matters is the distinction between a pure reimplementation in Java and a wrapper around a C library: only the reimplementation solves the same task under the same conditions.

A pure Java reimplementation exists: apache/parquet-java (formerly parquet-mr), including encodings and compression. Not measured, and the reason is the dependency tree: parquet-java pulls in Hadoop transitively and imports Hadoop types right into its core classes. To avoid that one takes strategicblue/parquet-floor, which reimplements the needed Hadoop classes and does without Hadoop.

For this document that is a useful classification: the established Java implementation of Parquet is not to be had without a data ecosystem behind it. A reader that opens a Parquet file with the JDK alone is therefore not a matter of course.

How solid this is. Researched on 2026-09-06 via web and GitHub search; Maven Central's search API was blocked, so a systematic artefact search was not possible. Where it says "not measured" below, it says so explicitly — a named library is not yet a measured one.
