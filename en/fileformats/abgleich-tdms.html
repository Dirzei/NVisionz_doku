NI TDMS — comparison against specification and npTDMS

As of: 2026-09-27
Our implementation: envisionz.fileformats.tdms.TdmsQuelle with Tdmstyp, read-only, no third-party library
Specification: The NI TDMS File Format (National Instruments, public) — references give field and flag names
Compared against: npTDMS 1.11.0 (Python)
Test bench: envisionz.fileformats.Tdmsprobe — 144 checks (2026-09-27), eight foreign anchors, fixtures from Tdmsschreiber

The reference implementation. npTDMS is a pure Python module by Adam Reeve built on numpy, following Floris van Vugt's earlier pyTDMS. It is an independent reimplementation: TDMS belongs to National Instruments, and npTDMS needs no NI library. That is possible because NI publishes the internal structure of the format itself. In the Python world npTDMS is the usual tool for TDMS.

Why this one. Because the vendor tool LabVIEW is not freely obtainable, but National Instruments publishes the internal structure itself — and npTDMS builds on exactly that. It is therefore an independent reimplementation of the same description this reader was built from. Two independent readings of the same description are the most usable comparison a vendor format allows.

Feature comparison

The most striking result of this comparison is that there is none. Eight fixtures through both readers, and in every single case the same values, the same types, the same grouping into groups and channels. That is itself a statement: TDMS is a format one can read correctly, because it carries its own description. The differences are not in reading but in what is offered afterwards.

What was measured — and why nothing diverged

Eight fixtures from Tdmsanker, run through envisionz.fileformats.tdms.TdmsQuelle and through npTDMS 1.11.0: a plain value channel, two groups, booleans, strings including an empty one, all numeric types side by side, three segments with continuation, properties, timestamps at three epochs. All eight: same values, same types, same grouping.

The reason lies in the format. TDMS describes every channel in the segment in which it occurs, with type, value count and — for strings — length fields. There is no place where a reader must know something the file does not state. That is exactly where it differs from MDF, where the formula as text, the bitfield table and the CANopen timestamps demand interpretation.

Agreement is still not proof. It shows that both readers take the same eight paths — not that both know every path. What none of the eight anchors touches is marked no or partial in section 1, and those rows are derived from source and not measured.

The one place where TDMS is dangerous

A segment need not describe its channels. If the kTocMetaData bit is absent, the previous segment's object list and raw data description remain in force; if the raw data index is 0xFFFFFFFF, it remains in force for that one object. A reader that reads each segment on its own takes whatever description happens to be there — and gets numbers that look plausible and are wrong.

Both implementations carry this state. Ours additionally names every place where the description was carried forward, in the findings — with a file of a hundred segments that is the difference between "it worked" and "I know why it worked".

Our open gaps — this is the work

T4 (property) — The index file is used — closed on 2026-09-07

Closed. Beside a .tdms there is often a .tdms_index with the same metadata without the raw data. Whoever reads it finds all channels without touching the large file — at several gigabytes that is the difference between a second and a minute. It is now used when it is there.

Two counters run side by side, and that is the whole trick. The index file's lead-ins carry the main file's numbers: next segment offset and raw data offset are the same there. A segment is therefore only 28 + rawDataOffset bytes long in the index file, while the same segment occupies 28 + nextOffset in the main file. Confuse the two and you read the values at the wrong place — while the channel list stays right and the numbers look like numbers. The anchor therefore has two segments whose second carries values shifted by 100; the mutation turns three checks red.

A broken index file is no reason to give up. It is a shortcut, not a source: everything in it is also in the main file. The reader therefore falls back to the main file on any error and says so. A .tdms_index goes stale easily because it is maintained separately on writing. In addition it is measured that without the index file the same result comes out — otherwise it would not be shown that it is only a shortcut.

T7 (property) — Complex numbers — closed on 2026-09-07

Closed. Types 0x08000C and 0x10000D carry real and imaginary part as a pair. They are emitted as text — 3.0-4.0i — the same notation as in this module's FITS and MATLAB readers. Deliberately the same: whoever touches several formats should not have to learn three notations.

The type code carries the width. 0x08000C — the upper byte is the number of bytes, the lower one the ordinal. Whoever looks only at the lower one takes a complex single (0x0C = 12) for something else; whoever sets the width to four instead of eight reads every second value at the wrong place. The mutation for it makes the test abort.

T8 (property) — DAQmx raw data — closed on 2026-09-07

Closed. Raw data of type 0xFFFFFFFF comes straight from a measurement card: counter readings instead of volts, and several channels of the same card lie side by side in one buffer. A channel's value then does not stand contiguously but one every width bytes. For LabVIEW recordings without post-processing this is the normal case; among this reader's gaps it was the most consequential. Until today such a file was rejected.

The marker stands where a length would. The raw data index otherwise begins with its own length; here stands 0x00001269 (format changing scaler) or 0x0000126A (digital line scaler). A reader taking it for a length jumps 4713 bytes further. And the number is 0x00001269 and not 0x69120000: the four bytes in the file are 69 12 00 00, read least-significant-first like everything else. NI's description shows them as a byte sequence — copy them down as a number and they come out reversed.

Two traps, both quiet. First: a DAQmx scaler does not number its data types like the rest of the format — there 3 is an int32, here an int16. Take one table for the other and every value is read at the wrong width, with the numbers staying in range (mutation: abort). Second: a channel's offset within the buffer stands in the index and not in the object order. Take it from the order and the second channel gets the first one's values (mutation: four red).

And the block size is computed differently. For ordinary channels it is the sum over the channels; for DAQmx the sum over the buffers — several channels share one. Summing over the channels gives a block size several times too large, the raw data length no longer divides, and all channels vanish silently. That is exactly what happened once while building it.

The anchor is an own fixture and measured nonetheless. npTDMS does not write DAQmx data — it comes from a measurement card, not from a program. The file here is hand-built; npTDMS 1.11.0 read it and returned 0.6, 0.7, 0.8, 0.9 and -1, -2, -3, -4. This test's reference values are its own, the bytes are ours, and both stand here rather than being blurred together.

T10 (property) — Scaling is computed — closed on 2026-09-07

Closed for Linear, Polynomial and Table. The scaling stands not in the raw data and not in the raw data index but in the channel's properties: NI_Number_Of_Scales says how many there are, and each carries a name of the form NI_Scale[i]_Scale_Type with its coefficients beside it. The channel thus contains counter readings, and what they mean stands next to them as text.

Scalings can stand on each other. NI_Scale[i]_..._Input_Source says where one takes its input from: 0xFFFFFFFF means "from the raw data", any other number means "from the scaling with that index". First counts into volts, then volts into newtons. Apply them in the wrong order, or only the first, and you get numbers in a unit that does not exist.

And one property switches everything off. NI_Scaling_Status set to "scaled" means the values in the file are already scaled. Compute again and you scale twice — and the result looks like a measurement.

The polynomial is evaluated by Horner, from the back. Computing forwards with Math.pow gives rounding errors in the third digit at degree six with large counter readings — and those look like measurement noise. Two mutations: take only the first coefficient (three red), and swap slope and intercept (eight red). The anchors are chosen so the two cases cannot coincide: from 0,1,2,3 come 10, 12.5, 15, 17.5 linearly and 1, 6, 17, 34 polynomially.

Not computed are thermocouple, RTD, strain gauge, thermistor and the combinations (Add, Subtract). They are named: if one stands on a channel, a finding says so and the values stay raw counts. They differ from the three built ones not in structure but in the curve — each brings its own table of physical constants, and those are not to be copied but measured. A foreign anchor for them can be produced with npTDMS; the work is outstanding and is not claimed here.

T5 (property) — Extended floating point numbers — read since 2026-09-27, with an own anchor; closed with a known limit

Addendum 2026-09-27 — read, and on what grounds. The width does not come from the TDMS description but from two places at NI: the LabVIEW help Flattened Data says "LabVIEW stores flattened extended-precision, floating-point numbers as 16-byte quantities", and the NI forum (Convert binary bytes to Labview Extended Precision type) describes the x87 layout stored with six padding bytes after it. Accordingly the reader takes sixteen bytes, eighty used: little-endian mantissa (8 bytes, explicit integer bit), sign and exponent (2), six padding bytes; big-endian sign and exponent, mantissa, padding. Conversion to double rounds to nearest, ties to even, including into the subnormal range; beyond the range becomes infinite, 0x7FFF is infinity or not-a-number. A channel of this type carries a finding that values are rounded. Applies to type 11 and 0x1B, to channels and to properties. The anchor is our own, the values are not: Tdmsschreiber stores the ten payload bytes that numpy.longdouble 2.4.4 yields on x86-64, and the expected values are float() of the same numbers — the FPU's rounding, not this reader's (test/proben/t5_x87.py, 14 values including a tie, subnormals, x87 subnormals, ±infinity, plus a NaN; the sixteen bytes are stated in the writer itself, not taken from Tdmstyp). Measured in both byte orders, interleaved beside a double, as a property and with a unit. The caveat remains: this proves we read what we take the layout to be — not that LabVIEW writes exactly this. FSharp.Data.Tdms, for instance, reads ten bytes. A genuine file from LabVIEW is still the missing evidence; hence both rows stand at partial on our side: read, but not measured on a LabVIEW file.

Closed 2026-09-27, with a known limit. A real LabVIEW file with type 11 or 0x1B cannot be obtained: no LabVIEW installation is available, and eight public TDMS files (npTDMS test data, go-tdms, NREL TITANIC) do not contain the type; npTDMS itself does not read it. The sixteen-byte storage width therefore remains supported by the LabVIEW help and the NI forum, not by a file. Should one turn up, a single run of the reader over it suffices.

Re-stated on 2026-09-07 with the real reason. It said here that Java has no 80-bit type and that a conversion to double would lose digits. That is true and beside the point: a conversion that loses digits would still beat nothing, and it could be reported.

The real reason is that the width is not established. NI's format description lists tdsTypeExtendedFloat (11) and tdsTypeExtendedFloatWithUnit (0x1B) in its type enumeration and gives a byte count for no type at all. The x87 layout from which LabVIEW's EXT comes occupies ten, twelve or sixteen bytes depending on the machine. And npTDMS 1.11.0 records the size None for this type — it does not know it either.

There is therefore neither a writer nor a reader against which an implementation could be measured. A built and unmeasured implementation would be worse in this workspace than a named gap: it would look like a capability. The type is therefore named — it carries the width −2 in the reader, "not known" — a channel of this type does not abort the reading, and its values stay empty. The item would close with one real file from LabVIEW; it is missing.

T9 (decided) — Table instead of series — and what that costs

npTDMS returns each channel as its own series; we turn a group into a table with the channels as columns. If the channels have different lengths — which TDMS explicitly permits — the table is as long as the longest, and the shorter ones give LEER at the end, with a finding. Measured on Tdmsanker.typen(): npTDMS gives 3, 3, 2, 2 values, we give four columns over three rows with two empty cells. Neither is wrong; anyone using both must know it. "Not measured" is something other than "measured zero", and a table can express the difference, a series cannot.

T11 (decided) — Writing and exporting

npTDMS writes TDMS and exports to pandas and HDF5. This module does not write — as a guarantee resting on four levels and measured. Exporting elsewhere does not belong in a format reader but in a layer above it.

Properties of the format — affecting both

T1 (property) — A segment does not necessarily describe itself

See section 3. Three continuation paths — missing kTocMetaData, missing kTocNewObjList, raw data index 0xFFFFFFFF — and all three look harmless on their own. Both implementations get it right.

T2 (property) — The truncated file is the normal case

An offset of 0xFFFFFFFFFFFFFFFF means the writer was interrupted. For a measurement that ran overnight and was switched off in the morning this is a regular occurrence. Both keep reading to the end of the file; we additionally report it. A reader that aborts here loses the whole night because of the last segment.

T6 (property) — The time epoch is 1904

TDMS counts seconds since 1 January 1904, in 64 bits, with another 64 bits of fraction. Assuming the Unix epoch is off by sixty-six years — visible in a year number, but not in a time difference. Both implementations get it right; the anchor Tdmsanker.zeiten() checks all three cases.

T3 (property) — Report rather than guess

A segment reaching past the end of the file, and raw data that does not divide evenly into blocks: both implementations keep reading, ours names it. The difference is not the number but whether one knows afterwards that something was missing.

What is good about the format

TDMS is the most readable of the binary formats compared here, and the comparison shows it: eight fixtures, not a single divergence. Every channel carries its type, every string its length, every segment its flags. There is no version number from which field layouts must be inferred, and no formula as text.

The price is the continuation across segments: describing itself in every segment would be expensive, so a segment may omit it. That is the one place where a TDMS reader goes silently wrong — and it is one place, not four as with MDF.

The Java implementation — where this reader stands among its own kind

Why this section. Every other comparison in this module measures against a tool in a different language. That is good against misunderstandings of the format and says nothing about where this reader stands among its own kind. What matters is the distinction between a pure reimplementation in Java and a wrapper around a C library: only the reimplementation solves the same task under the same conditions.

Practically no Java implementation. The research found exactly one project, AnnaGregusova/TDMSReader (pure Java, but with no stars, no forks and not findable on Maven Central); the GitHub topic tdms lists not one Java project among fourteen, and NI's own overview of third-party tools names C, MATLAB and Excel but no Java. Not measured.

The usual Java route would therefore be a self-built wrapper around NI's TDM C library. For this document that means: there is no Java reference to measure against — the comparison against npTDMS is not the second-best choice but the only one.

How solid this is. Researched on 2026-09-06 via web and GitHub search; Maven Central's search API was blocked, so a systematic artefact search was not possible. Where it says "not measured" below, it says so explicitly — a named library is not yet a measured one.
