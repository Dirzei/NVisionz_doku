Exodus II — comparison against the specification and against meshio

As of: 2026-09-05
Our implementation: envisionz.fileformats.exodus.ExodusDatei with Exodusblock, read-only, on our own netCDF reader, no third-party library
Specification: EXODUS II: A Finite Element Data Model (Sandia SAND92-2137) — public; references give variable and dimension names
Compared against: meshio 5.3.5 (Python), plus netCDF4 1.7.4 as container reader
Test bench: envisionz.fileformats.exodus.Exodusprobe — 103 checks, two foreign anchors

The reference implementation. meshio is a pure Python library by Nico Schloemer that reads over thirty mesh formats and is the reference implementation of none of them. Alongside it ran netCDF4-python as the container reader — the binding to netcdf-c from Unidata (UCAR), the owner of the container. The comparison therefore has two levels: meshio's interpretation, and the raw view of the container through its own reference implementation.

Why this one. Because Exodus is not a byte format of its own but a naming convention over netCDF. Hence two levels: meshio interprets the convention, netCDF4-python shows the container raw. The second level is the more important one — it says what is actually in the file, not what a second interpretation makes of it.

Feature comparison

Exodus is not a byte format of its own but a convention over netCDF — the same relation netCDF-4 has to HDF5 and CGNS has to HDF5. And because netCDF itself comes in two entirely different containers (classic and netCDF-4/HDF5), Exodus files exist in both forms, with the same extension and no hint of which one is at hand. Our reader states the form as a finding.

What was measured

Two fixtures, in both directions: our anchor Exodusanker/netz.exo through ExodusDatei and through netCDF4, and a file written by meshio itself through ExodusDatei. The second direction is the more important one: it does not check whether we find our own file again but whether we read a foreign one.

The file written by meshio

meshio.write("netz.e", …, file_format="exodus") produces an Exodus file in the netCDF-4 container — 22,036 bytes for five nodes and two triangles, because HDF5 brings a superblock, B-trees and object headers where classic netCDF gets by with a few hundred bytes. Our reader opens it, reports "Bauform: netCDF-4 (HDF5)" and yields two tables: knoten with five records and columns knoten x y z, and block1 with six element platz knoten entries. The coordinates agree value for value with those written in.

That is the case this reader was built for, and it works out. What is remarkable is not that it works but where it nearly did not: meshio creates a separate dimension dim_nod_var00 for each nodal field, which happens to have the same length as num_nodes. A reader searching for the values by dimension name does not find them in a meshio file. Our reader goes by variable name and recomputes the length — see E7. That decision predates this measurement and was confirmed by it.

Our anchor through netCDF4

Our reader reads Exodusanker/netz.exo as four tables (nodes, one element block, nodal and element fields). netCDF4 opens the same file and finds nine variables with the same numbers. netCDF4 — like h5py for CGNS — makes no statement about Exodus: it sees variables, not blocks. The interpretation is exactly what this module contributes.

What is hard about the format

Everything hangs on names. num_nodes, coord, connect1, eb_prop1, time_whole, vals_nod_var1. Not one of them is derivable from the file; they are in the Sandia report and nowhere else. That makes the reader short and the file unreadable without the document. Whoever inspects an Exodus file with ncdump sees variables whose meaning must be guessed.

The coordinates are stored dimension-wise. coord has shape (num_dim, num_nodes) — all x first, then all y. Whoever assumes (num_nodes, num_dim) gets half the x values as y values for a planar mesh. The mesh then still looks like a mesh, just in the wrong place. The same trap sits in Ensight and in PLOT3D; it is the Fortran legacy of the whole family.

The field names are a character array, not a string array. name_nod_var is (count, name length) single characters padded with NUL. Whoever does not assemble them has fields without names — and vals_nod_var1 tells nobody what was measured.

Two containers, one extension. An .e may be classic netCDF or HDF5. Both occur in the wild, meshio writes the second, older solvers write the first. A reader that handles only one container fails on half the files — and the message then points at the header, not at the container.

What is good: Exodus lying on netCDF. Dimensions, types and attributes are self-describing; the convention only has to say what the names mean. A format that leaves its structure to a checked substrate and contributes only rules is the exact opposite of PLOT3D — and one notices that at once when reading.

Our open gaps — this is the work

Deliberate decisions — nothing to do

E12 (decided) — Writing

meshio writes Exodus and converts between thirty mesh formats. This module reads.

E5 (decided) — Node tags stay one-based

connect<i>N</i> counts from one. We pass the tags on as they stand and call the column knoten, not index. Whoever needs them as an array index should do that visibly. Silently shifting by one would be more convenient and would put every comparison against foreign output off by one.

E8 (property) — Node sets — closed on 2026-09-06

Closed. node_ns<i>i</i> carries the node numbers, ns_prop1 the ids, ns_names the names, dist_fact_ns<i>i</i> the distribution factors. Each set becomes its own table knotenmenge<id> — one row per node of the set, not per set: a set is a list, and its length is not its information.

E9 (property) — Side sets — closed on 2026-09-06

Closed. elem_ss<i>i</i> and side_ss<i>i</i> stand in pairs: per entry one element and one local side number on that element. Both come out as the table seitenmenge<id>, with the distribution factors beside them. Concatenate the two arrays instead of pairing them and you get four elements instead of two faces — and all four look like elements.

What is expressly not done here, and why that closes the gap rather than moving it: resolving the local side number into nodes — "side 3 of a HEX8 is nodes 2, 3, 7, 6" — needs a table per element type from the Sandia report, and that table is not in the file. Write it from memory and get it wrong, and you deliver faces that look like faces and lie elsewhere. So the pair is handed out as it stands; that is complete, checkable and exactly what the file says. The note stands as a property on the table.

E10 (property) — Attributes and records — closed on 2026-09-06

Closed. attrib<i>N</i> becomes the table block<i>N</i>_attribute with one column per attribute and the names from attrib_name<i>N</i>; the QA records become the table qa with the four columns program, version, date, time, the info lines the table info.

Two traps, both measured. attrib<i>N</i> has the shape (elements, attributes) — the attribute runs fastest; swap the axes and the second element's thickness is read as the first one's width, and both are numbers. And qa_records is (count, 4, length): four strings per record, not one.

E11 (property) — Windowed access — closed on 2026-09-06

Closed, and one layer deeper. The window now sits in NetcdfData and therefore in both forms: netCDF-4 hands it to the HDF5 reader, the classic container computes the address itself. Exodus uses it for coordinates, connectivity, nodal and element variables. That also closes point D7 of the netCDF document — it was the same gap.

The trap with the coordinates: Exodus often stores them in one variable coord of shape (num_dim, num_nodes). The window for the y axis must therefore be shifted by a whole axis. Miss that and you read x instead of y — and x is a coordinate too.

Properties of the format

E1 (property) — Two containers under one extension

See section 3. Both implementations handle both containers; our reader additionally reports which one it was. For a file from a foreign hand that is the first useful piece of information, because size and read speed differ by orders of magnitude.

E4 (property) — Dimension-wise coordinates

See section 3. The same trap in Ensight and PLOT3D.

E6 (property) — Names as a character array

See section 3. Both implementations assemble them; that is no achievement but the minimum condition for the fields having names at all.

E7 (property) — The value dimension sometimes carries a foreign name

See section 2.1. meshio creates dim_nod_var00; the specification does not fix this, and it is no bug of meshio's either — the dimension may be called anything. A reader therefore must not rely on the dimension name. We go by the variable name.

Findings against the reference implementation

E2 (open there) — Four conditions without a message

The container form, an announced but missing block, a block sum unequal to num_elem, a missing value variable for an announced field. We name all four in the findings; meshio reads on silently or throws a Python exception from the inside. That is no bug of meshio's — the files are contradictory in all four cases, and meshio never promised to describe them. It is the difference between a library that converts and a reader that gives an account.

E3 (open there) — api_version and version are skipped

The two header attributes say which library version produced the file. We carry them; meshio skips them. For a file behaving unexpectedly that is the piece of information a search starts with.

The Java implementation — where this reader stands among its own kind

Why this section. Every other comparison in this module measures against a tool in a different language. That is good against misunderstandings of the format and says nothing about where this reader stands among its own kind. What matters is the distinction between a pure reimplementation in Java and a wrapper around the original C library: only the reimplementation solves the same task under the same conditions as this reader; a wrapper calls the original.

No Java implementation found. SEACAS, the format's home at Sandia National Laboratories, offers C, C++, Fortran and Python — no Java. The Java route through VTK (vtkExodusIIReader) is again a JNI wrapper.

The container on the other hand is fully readable in Java: Exodus II sits in netCDF, and netcdf-java reads netCDF-3 as well as netCDF-4 in pure Java. What is missing is the Exodus semantics — element blocks, node and side sets, the naming conventions of the variables. That is the work this reader does, and in Java it is done nowhere else.

How solid this is. Researched on 2026-09-06 via web and GitHub search; Maven Central's search API was blocked at the time, so a systematic artefact search was not possible. "Nothing found" is therefore not the same as "nothing exists" — a little-visible or in-house implementation would not be discoverable this way. What stands here is the state of an honest search and not a claim of completeness.
