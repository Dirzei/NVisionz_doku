HDF5, netCDF and HDF4 – background

How an HDF5 reader gets from the superblock through object headers, B-trees and chunks to the numbers, which rules carry the weight (datatype from bit fields, checksums, filter pipeline), and how netCDF and HDF4 differ.

The problem: a file system for numeric arrays

HDF5 is not a table format but a container: groups form a tree, the leaves are multidimensional datasets with datatype, shape and attributes. What a reader has to get right is not in one place but spread over a web of addresses: the superblock points to the root group, its object header to a link table or a B-tree, that to further object headers, and only the object header of a dataset names type, shape, layout and filters. netCDF-4 is a convention on top of HDF5, netCDF-3 a separate and much simpler byte format, HDF4 a third format that shares only the name with HDF5.

All three are read here read-only and without third-party libraries; decompression uses our own framework-compress.

The reading path through an HDF5 file

The superblock and the base address

The signature 89 48 44 46 0D 0A 1A 0A need not be at the start of the file: a user block may precede an HDF5 file (a MAT file of level 7.3 keeps its description text there). The specification fixes the possible locations: 0 and then every power of two from 512. The reader therefore searches at

a0=0,ak=512⋅2k−1(k≥1),a_0 = 0, \qquad a_{k} = 512 \cdot 2^{k-1} \quad (k \ge 1),

i.e. 0, 512, 1024, 2048, … up to the end of the file. Where the superblock is found lies the base address; all addresses in the file are relative to it. Stopping at 1024 or searching in steps of 512 misses some files or reads at a wrong place.

The width of all addresses (size of offsets) and lengths (size of lengths) is stated in the superblock, usually 8 bytes. An address with all bits set means “undefined”.

Shared messages and the cache image

From superblock 2 on, the superblock extension carries two items without which some files cannot be read. The shared object header message table (SOHM) names one fractal heap per index holding messages that are identical in many objects – the same dataspace, the same type, often attributes too. A message with bit 1 of its flags set is then not content but an eight-byte heap ID. Its top bits say where the object lives: managed in the heap, huge in its own tree, or tiny inside the ID itself; a tiny object does not exist in the heap at all. Up to the list cutoff (default 50) the index is a list SMLI, above it a version 2 B-tree.

The metadata cache image (message 0x18) stores the library cache as one block MDCI on close; the places the metadata come from stay empty in the file. An entry consists of a 14-byte prefix (type, flags, ring, age, number of children, of dirty children and of parents, LRU rank), address and length, the addresses of the p dependency parents and the n bytes themselves, together

ℓ=14+O+L+pO+n\ell = 14 + O + L + p\,O + n

with O and L the widths of offsets and lengths. Skipping the parents shifts everything from the first entry with parents on – and leaves only zeros where the root object header should be. A read that starts in an entry and reaches beyond it is served from the entry; otherwise the stale state of the file would come out.

Until 2026-10-25 such a file was unreadable (“object header version 0”), shared attributes silently disappeared, so did attributes with a named (shared) type, and a list index always reported itself empty.

A broken attribute – say a type or space block whose length runs past the message – costs only itself: it is skipped, the other attributes of the node remain, and the file names node, attribute number and reason in its findings. Until 2026-10-25 such an attribute aborted reading all attributes of the node. For attributes stored densely in a fractal heap there is no safe way to read on past a broken one; there the list stays empty, now with a finding.

Datatypes from bit fields

A datatype message starts with four bytes: version in the high nibble, class in the low one, then 24 class bits, then four bytes of element size. What the class bits mean depends on the class. For floating-point numbers HDF5 describes the number completely by its fields: position and width of exponent and mantissa, position of the sign, bias. The value of a normal pattern is

x=(−1)s(1+m2M)2e−b,x = (-1)^{s}\left(1 + \frac{m}{2^{M}}\right) 2^{\,e - b},

for e = 0 (subnormal) x = (−1)s (m/2M) 21−b, with all exponent bits set infinity or NaN. The same path therefore reads IEEE binary16 (5 exponent bits, 10 mantissa bits, b = 15) and bfloat16 (8 and 7, b = 127): the same bit pattern means something different in each, 16.0 is 0x4C00 and 0x4180 respectively. For 32 and 64 bits with IEEE layout the reader reads directly.

The byte order is given by two bits together: bit 0 and bit 6 of the class bits (00 little, 01 big, 11 VAX, 10 reserved). Reading a VAX order as big-endian would give plausible wrong numbers; the reader reports it.

Compounds. Each member has a name, an offset within the element and its own type. In type versions 1 and 2 the name is padded to a multiple of eight and the offset is four bytes wide. In version 3 the offset is as wide as needed to hold the total size S of the compound; the library computes

w(S)=⌊⌊log2⁡S⌋8⌋+1,w(S) = \left\lfloor \frac{\lfloor \log_2 S \rfloor}{8} \right\rfloor + 1 ,

i.e. one byte up to S = 255, two up to 65 535, three up to 224 − 1, otherwise four.

Until 2026-10-19 the reader read a fixed single byte here. A compound of 256 bytes or more shifted everything after it, and in the end the dataset was reported as missing – it is now checked against a 312-byte compound written by the HDF5 library.

As text a compound appears with its field names, each field read at its offset in its own type: {a=1.0, b=2}, for attributes as for datasets. Until 2026-10-25 it fell through to the numeric path and gave NaN. 64-bit integers come out exactly as text, unsigned ones also above 263 (264 − 2 is 18446744073709551614); before, they went through double and were rounded beyond 253, above 263 to 9 223 372 036 854 775 807.

Array types carry their shape in the type; the element count is the product of the dimensions and a claim of the file. More than 231 − 1 elements per value are rejected instead of truncating the number (65 536 × 65 536 silently gave zero before). Enumerations carry base type, names and values; in versions 1 and 2 each name is padded to eight bytes. Time and bitfield are read as unsigned integers, opaque as bytes.

Timestamps. Version 2 object headers carry four times in the header, older ones a message: the new one (0x12) with version, three reserved bytes and seconds since 1970, the old one (0x0E) without a header as 14 digits YYYYMMDDhhmmss in UTC and two reserved bytes. Until 2026-10-25 the reader skipped four bytes before the digits and reported every old time as “none”.

Checksums: lookup3 for metadata, Fletcher-32 for chunks

From superblock 2 on, all newer metadata blocks (object headers v2, B-tree v2, fractal heap, chunk indices) carry a 32-bit checksum after Jenkins’ lookup3 (hashlittle, initial value 0): three registers, mixed 12 bytes at a time, the rest padded and finally mixed. The empty input gives 0xdeadbeef, the sentence “Four score and seven years ago” 0x17770551.

The data itself may additionally carry the fletcher32 filter. It appends four bytes to every chunk, computed after Fletcher over 16-bit words in big-endian order:

s1←s1+wi,s2←s2+s1,s←(smod216)+⌊s/216⌋,F=216s2+s1.s_1 \leftarrow s_1 + w_i, \qquad s_2 \leftarrow s_2 + s_1, \qquad s \leftarrow (s \bmod 2^{16}) + \lfloor s / 2^{16}\rfloor , \qquad F = 2^{16} s_2 + s_1 .

The sums are folded after at most 360 words – that keeps them within 32 bits; since folding does not change the residue modulo 65 535, the moment of folding does not matter as long as nothing overflows. An odd last byte counts as the high byte of a word. F is stored little-endian; older libraries stored the bytes of each half swapped, so this form is also accepted when reading.

Until 2026-10-19 the checksum was only cut off, never checked: a damaged chunk came out with wrong values although the file carries a checksum for exactly that purpose. Like all other checks it can be switched off with verifyChecksums(false).

Chunks and the filter pipeline

A dataset with chunked layout falls into chunks of equal shape; the chunk index (B-tree v1, B-tree v2, fixed array, extensible array, single chunk, implicit) gives per chunk the address, stored size and a filter mask: a set bit i means filter i was skipped for this chunk. On reading the filters run in reverse order of the pipeline message:

d=f1−1(f2−1(⋯fn−1(c))),d = f_1^{-1}\bigl(f_2^{-1}(\cdots f_n^{-1}(c))\bigr) ,

with c the stored chunk and d the data.

deflate (own zlib with Adler-32 check), shuffle, fletcher32, LZF, LZ4, szip, n-bit and scale-offset are read; an unknown filter is reported with number and name.

A chunk that was never written is not in the index; in its place the fill value of the fill value message applies – also when only a slice is read. Until 2026-10-25 the slice returned zeros there, and the long form (which reads HDF5 block by block) passed them on as measured values. A contiguous dataset that was never written occupies 0 bytes, as with H5Dget_storage_size.

The profile (Hdf5Inspect) asks the filter pipeline what it can decode instead of keeping its own list; szip, n-bit, scale-offset, LZ4 and external raw data were listed as “not supported” there until 2026-10-25.

External links and split files

An HDF5 file can point to other files: external links, sources of virtual datasets and the members of the multi/split driver, where metadata and raw data live in separate files (%s-m.h5, %s-r.h5). All three names come from the file. They are therefore opened under the same rule (Hdf5Verweise, default: same folder only); a name with .. is not attached.

The same rule applies to external raw data (message 0x07, the values of a dataset in other files): a name such as ../draussen.bin is rejected instead of reading a file outside the folder. What the raw data file does not cover stays fill value.

Soft links may point in a circle. They are resolved over at most 32 levels per thread, counted across the recursion (a link to a link resolves the target again through the path); beyond that the reader reports “link chain too deep or circular”. Until 2026-10-25 the count only held within one call, and two links pointing at each other ended in a stack overflow.

netCDF-3: a header and interleaved records

netCDF-3 (CDF-1, CDF-2 with 64-bit offsets, CDF-5 with 64-bit counts and unsigned types) is a simple big-endian format: a header with dimensions, attributes and variables, followed by the data. Fixed-size variables lie contiguously. Variables on the unlimited dimension lie interleaved: record r of variable v starts at

bv+r⋅R,R=∑uzu,b_v + r \cdot R, \qquad R = \sum_{u} z_u ,

with bv = begin of the variable and the sum over all record variables u; their record size zu = vsize is padded to four bytes. The exception: if there is exactly one record variable its record is not padded, and R is the true record size. The length of the unlimited dimension is numrecs in the header; in streaming mode it is 0xFFFFFFFF and follows from the file size.

Missing values and unpacking after the CF conventions

For netCDF-3 and netCDF-4 reading follows the same order: first compare the stored number with _FillValue, missing_value and valid_min/max, then unpack

y=sx+o,y = s\,x + o ,

with s = scale_factor and o = add_offset, in the type of the scale factor: if it is float, the arithmetic is single precision (0.1 · 1 + 1000 gives 1000.0999755859375, not 1000.1). Without _FillValue the default fill value of the type applies: −127, −32 767, −2 147 483 647 and −9 223 372 036 854 775 806 for the signed, 255, 65 535, 4 294 967 295 and 18 446 744 073 709 551 614 for the unsigned integers, 9.969 209 968 386 869 · 1036 for floating point. The expected values come from netCDF4-python itself.

For 64-bit integers the fill value is compared exactly, as an integer and not as a floating-point number. Between −263-2^{63} and −263+1024-2^{63} + 1024 there is no other double; −9 223 372 036 854 775 806 and −263-2^{63} (Long.MIN_VALUE) are the same number as double, likewise 264−22^{64} - 2 and 264−12^{64} - 1. Until 2026-10-25 a real value −263-2^{63} therefore counted as a gap, and an own _FillValue of −263+1-2^{63} + 1 hit it as well. Now the reader reads the values and the _FillValue of such variables exactly (netCDF-4 over HDF5 as well as CDF-5) and compares them there; as with netCDF4-python, exactly the fill value becomes a gap.

HDF4: data descriptors instead of an address tree

HDF4 is a different format. The file is a chain of DD blocks (data descriptors): per entry tag (16 bits), reference (16 bits), offset and length (32 bits each, hence at most 2 GB). What belongs together is given by Vgroups (tag 1965) as lists of tag/reference pairs; scientific datasets, Vdata tables and raster images are such groups. Raster images of the old format are run-length encoded: a control byte with the high bit set repeats the next byte (c & 0x7F) times, otherwise (c & 0x7F) literal bytes follow – without the “+3” of other RLE schemes.

The number type (tag 106) names a class besides kind and width, and the class gives the byte order: 1 is the HDF default (most significant byte first), 4 is Intel for integers and IEEE in the same order for floating point (least significant byte first), 2 is VAX for integers (also least significant first). The HDF4 library writes a dataset of type DFNT_LITEND|DFNT_INT16 with class 4 and the values as they are in memory. Until 2026-10-25 the reader read every dataset most significant byte first: 1, −2, 300 silently became 256, −257, 11 265.

In Vdata tables and attributes uchar8 is text like char8, one byte per character, and uint64 is read without sign: up to 263 − 1 exactly as an integer, above that as a floating-point number as for the datasets, as attribute text exactly. Until 2026-10-25 uchar8 had width 0 there (the field came out empty), and 264 − 2 came out as −2.

Special elements state their size in the header: a linked one the total length, a compressed one the unpacked length, a chunked one axes and element size. At most the decompression limit is allocated; an external element opens its file under the rule for external links.

What follows

  • Assumptions: the file follows the published specification; where the library deviates or writes more than described (the swapped Fletcher storage, the width of the compound offset), the reader follows the library, because the library writes the files.
  • Every number from the file is a claim: addresses, element counts and chunk sizes are checked against the file before memory is allocated.
  • Checksums are checked, not just skipped. A reader that does not check a checksum that is present is worse for measurement data than one that knows none – it looks as if it had checked.
  • Floating-point numbers of other layouts (16 bit, subnormal values) come out right through the fields of the message; a fixed assumption about the layout would silently misread one of the two 16-bit kinds.

How it is tested

Against foreign files: 36 reference files of the HDF Group library with h5dump, netCDF-4 files from Unidata’s library, an HDF4 file of the HDF4 library, and in TheorieFAprobe a fletcher32 file, a 312-byte compound, a split-driver file pair (all from h5py 3.16 on HDF5 2.0) and a netCDF-3 file from netCDF4-python 1.7.5. The Fletcher sums stored by the library agree with our own computation. The recomputation is in docs/theorie/rechnung/fileformats_hdf5.py.

The TheorieG1probe of each package takes further anchors from the libraries (h5py 3.16 on HDF5 2.0, netCDF4, the HDF4 library): old and new layouts, shared messages with a cache image, virtual datasets, external raw data, containers and MATLAB 7.3. What the libraries do not write – layout messages of version 1, the old modification time, the version 0 file space message – is produced as a deliberately rewritten copy in the temporary folder, with the checksum recomputed. The anchors are generated by docs/theorie/rechnung/fileformats_g1_anker.py.

Limits

  • VAX datatypes and reserved byte orders are reported, not read; integers with bit offset and precision smaller than the element size are read as whole elements.
  • The extensible array with paged data blocks is reported, not read.
  • HDF4: compressed special elements are read uncompressed, with RLE and with deflate; N-bit, Huffman and szip are named, not unpacked.
  • A virtual dataset that shares a dataset name with an earlier entry is not tested against any file of the library; it is read according to the specification.
  • The Fletcher check does not distinguish the two storage forms; a sum that happens to match in the swapped form counts as correct (probability 2−32).
