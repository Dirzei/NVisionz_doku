Gmsh .msh — comparison against specification and meshio

As of: 2026-09-05
Our implementation: envisionz.fileformats.gmsh.GmshDatei with Gmshart, read-only, no third-party library
Specification: Gmsh reference manual, section "File formats" — public; references give section names and field orders
Compared against: meshio 5.3.5 (Python)
Test bench: envisionz.fileformats.gmsh.Gmshprobe — 152 checks, four foreign anchors, sixteen own fixtures

The reference implementation. meshio is a pure Python library by Nico Schloemer, essentially a single-developer project with community contributions. It reads and writes over thirty mesh formats and is therefore the reference implementation of none of them — it is the common denominator. In the scientific Python world it is the usual tool for converting between mesh formats.

Why this one. Because Gmsh itself is the owner, but its format has four variants that differ in more than details. meshio reads all four and is the usual route to them in the scientific Python world — making it the practically obtainable second reading. That it is not a reference implementation is stated here explicitly: a difference is a finding, not a verdict.

Feature comparison

.msh exists in two formats sharing one extension: version 2.2 and version 4.1 share a header and after that almost nothing. Each of the two additionally exists as text and as binary. Four variants, then, and a reader has to handle all four, because all four occur in the wild.

What was measured

Twenty fixtures — four foreign anchors from Gmshanker (produced by Gmsh itself, all four variants) and sixteen of our own from Gmshschreiber — through envisionz.fileformats.gmsh.GmshDatei and through meshio 5.3.5. The four foreign anchors read the same in both. Among our own, two cases diverge, and one of them is a bug in meshio which I first took for ours.

The case that looked like our bug

Our fixture Gmshschreiber.binaer22() is rejected by meshio — the identically named foreign fixture Gmshanker.binaer22() is not. The first suspicion had to be that our writer builds an invalid file, and that our probe therefore measures against a wrong fixture.

It is not. The difference between the two files are the node tags: the foreign fixture numbers 1…6, ours 10, 20, 30, 40, 50. meshio's binary path explicitly requires data["index"] == range(1, num_nodes + 1) and throws otherwise. Gmsh permits arbitrary positive node tags — that is precisely why the tag is in the file at all; if it were fixed, it would not need storing.

And meshio is inconsistent with itself about it: it reads the same node tags 10, 20, 30, 40, 50 in the ASCII form of the same version 2.2 without complaint. So it is not a deliberate restriction but a check that exists in only one of the two paths. See G5.

Four broken files, four different messages

abschnittOhneEnde, knotenZuKurz, kopfZuKurz, leer and pruefzahlFalsch are answered by meshio with ValueError: invalid literal for int(), unmatched data, IndexError: list index out of range, need at least one array to concatenate and a file-type error. All five are Python messages from the inside, not statements about the file.

Our reader answers the same cases with sentences naming the place. That is no superiority in reading — neither reads the file — but the difference between an error message and a debugging session.

What is hard about the format

Two formats, one extension. 2.2 and 4.1 differ in everything that follows the header: 2.2 counts nodes and elements individually, 4.1 in blocks by geometric entity. A reader that handles only one fails on half of all files — and the error message then points at the node section, not at the version.

The check value is the only statement about byte order. In binary 2.2 a 1 follows the header as four bytes. If it reads as 16777216, the file is big-endian. There is no second place stating this — skipping the check value reads everything after it in the wrong order, and coordinates then look like numbers of order 10⁻³⁰⁰.

Node tags are not indices. They may have gaps and appear in any order; elements refer to them by tag, not by position. Taking them as an index into an array reads the wrong coordinates for every file from which a node was deleted — and the mesh afterwards still looks like a mesh.

What is good: the sections are named and bracketed. $Nodes … $EndNodes. A reader that does not know a section can skip it without knowing its layout — and that is exactly what both implementations do. There are few binary formats in which the unknown is so cheap to step over.

Properties of the format

G1 (property) — Four variants under one extension

See section 3. This module's test bench produces all four and measures image against image: the same geometry in ASCII 2.2, binary 2.2, ASCII 4.1 and binary 4.1 must yield the same nodes and elements. That is the only check that reliably catches a mix-up of the variants.

G2 (property) — The check value

See section 3.

G4 (property) — Unknown sections are cheap

$Name … $EndName. Both implementations skip what they do not know; we additionally report what was skipped. With a file from a foreign tool that list is the first useful piece of information.

G6 (property) — Parametric nodes — closed on 2026-09-07

A node block of version 4.1 may carry parameter values alongside the coordinates: where on the geometry the node sits. That is a different thing from its coordinates — refining the mesh should put the new node on the curve, not on the chord between two old ones. How many numbers follow is nowhere stated per node; it follows from the dimension of the entity in the block header: one on a curve, two on a surface, none on a point. Assuming a fixed count shifts the reader at the first change from a curve to a surface — and the next number looks like a coordinate. Measured against a file from Gmsh 4.15.2 carrying all three cases in one file, and beside it the same file without parameters: on one file alone every interpretation looks right.

G7 (property) — All element types — closed on 2026-09-07

The table is now complete: 117 types with name and node count. It is not copied but taken from Gmsh 4.15.2 itself — for every number the program's own answer about name and node count. Seven types have zero nodes (34, 35, 69, 133 to 136); anyone typing such a table by hand takes that for a typo and writes down a number.

G8 (property) — $Entities — closed on 2026-09-07

The section is read and carried: per entity the dimension, the tag, the bounding box, the physical groups and the bounding entities. Every node then knows which entity it belongs to — and thereby which element lies on which surface. A point carries three numbers, every other entity six. Reading six everywhere shifts the reader by three numbers at the very first point, and the next number looks like a group number.

G9 (property) — $Periodic — closed on 2026-09-07

Periodic boundaries — which node corresponds to which. In turbomachinery the normal case: one blade passage is meshed and then rotated around. Both notations are read, and they do not look alike: version 4.1 writes a number of values before the affine map — zero or sixteen — while version 2.2 writes the word Affine instead, and where no map is present the line begins straight away with the number of node pairs. A reader that knows only one form trips over a word where it expects a number — and does so with an exception in the middle of reading, not with a finding. The number in front is moreover a count and not a flag: reading it as "yes or no" and then expecting a fixed sixteen numbers shifts the reader by sixteen numbers at every mapping without a map.

G10 (property) — All components of a result field — closed on 2026-09-07

$NodeData and $ElementData carry computed results on the mesh. Until now one value per node was carried per field — the first component — and reported as such. That was honest and still useless: the x direction alone is not a magnitude. Now all components are there; the count is in the file and is not guessed. The old view remains and still yields the first component — for a scalar it is complete. The finding is thereby gone, and that is the point: it was never the goal, it was the admission. Reference values from meshio 5.3.5 reading the same file.

Findings against the reference implementation

G5 (BUG there) — meshio requires node tags 1…n in the binary path — but not in the ASCII path

See 2.1. _gmsh22._read_nodes checks data["index"] == range(1, num_nodes + 1) in the binary branch and raises ReadError for any other numbering. The ASCII branch of the same function does not check it. Gmsh permits arbitrary positive node tags; meshes with gaps in the numbering arise from every deletion and every merge. An everyday case is therefore affected, and the message (meshio._exceptions.ReadError with no text) does not say what is wrong.

How to reproduce — Two Gmsh files with the same mesh — five nodes tagged 10, 20, 30, 40, 50, two triangles and one line — one as $MeshFormat 2.2 0 8 (ASCII), the other as 2.2 1 8 (binary). Then read both with meshio.read(file, file_format="gmsh"). Expected: five nodes both times. Observed with 5.3.5 on Python 3.11: the ASCII form is read, the binary form raises meshio._exceptions.ReadError with no message text. The cause is the line if not (data["index"] == range(1, num_nodes + 1)).all(): raise ReadError() in meshio/gmsh/_gmsh22.py. Renumbering the nodes 1…5 makes the binary form readable too. The files are produced by envisionz.fileformats.gmsh.Gmshschreiber.text22() and .binaer22().

G12 (BUG there) — meshio does not read a file with parametric nodes at all

Not "skips the values" but aborts the whole file. meshio/gmsh/_gmsh41.py line 167: if parametric != 0: raise ReadError("parametric nodes not implemented"). The flag sits in the header of every node block; a single parametric block suffices and the mesh is unreadable — including the nodes, elements and groups standing beside it that have nothing to do with the parameters. Gmsh writes parametric nodes as soon as the geometry is written along; the file therefore arises from the usual setting, not a special one. The earlier text of this comparison said "we skip them with a message; so does meshio" — remeasuring on 2026-09-07 showed that to be wrong.

How to reproduce — With Gmsh 4.15.2 mesh a rectangle and write it with Mesh.SaveParametric = 1 as p41.msh (version 4.1, ASCII); write the same geometry a second time without that setting as p41np.msh. Then read both with meshio.read(file). Expected: twelve nodes both times. Observed with meshio 5.3.5 on Python 3.10: p41np.msh is read (point_data contains gmsh:dim_tags, cell_sets the three physical groups), p41.msh aborts with meshio._exceptions.ReadError: parametric nodes not implemented. The two files differ only in the flag in the block header and in the parameter columns. Both are held as foreign anchors in the test bench: envisionz.fileformats.gmsh.Gmshanker.entitaeten() and .ohneParameter().

G3 (open there) — Five conditions without a message

Big-endian, a float width other than eight, a section without $End, an unknown element type and a truncated element entry. We name all five in the findings; meshio reports nothing in the first two cases and answers the rest with a Python exception from the inside.

The Java implementation — where this reader stands among its own kind

Why this section. Every other comparison in this module measures against a tool in a different language. That is good against misunderstandings of the format and says nothing about where this reader stands among its own kind. What matters is the distinction between a pure reimplementation in Java and a wrapper around the original C library: only the reimplementation solves the same task under the same conditions as this reader; a wrapper calls the original.

No Java implementation found. The official Gmsh API covers C, C++, Python, Julia and Fortran; for Java there was a 2011 mailing-list proposal to build a SWIG wrapper and nothing maintained since. The existing standalone readers are Python (gmshparser) or Rust (mshio).

How solid this is. Researched on 2026-09-06 via web and GitHub search; Maven Central's search API was blocked at the time, so a systematic artefact search was not possible. "Nothing found" is therefore not the same as "nothing exists" — a little-visible or in-house implementation would not be discoverable this way. What stands here is the state of an honest search and not a claim of completeness.
