Reading database files – background

How SQLite, LMDB and dBASE lay records out on pages and in fields, and the arithmetic rules at which a reader goes silently wrong: varint and serial type, the boundary between the local part and the overflow chain, pointer maps, the WAL checksum, the valid meta page, Julian day and currency.

What this is about: records in pages

All three formats store a table in blocks of fixed size – SQLite and LMDB in pages of UU bytes (512 to 65536), dBASE in fixed-length records behind a header. From a few numbers in the header a reader has to work out where a record starts, how long it is and where its remainder lies. The rules are in the format descriptions; the files are written by programs that have computed them this way for decades. A reader that shifts a rule by one reads short records correctly and long ones as nonsense – and the long ones are rarely in a test. The limits below are therefore worked out and tested with records on both sides of every boundary. Reading only: no journal is created, no lock file touched.

SQLite: varint and serial type

Integers without fixed width are stored as a varint: most significant group first, seven bits per byte, the top bit saying “another one follows”. After eight such bytes the ninth contributes all eight bits – exactly 8⋅7+8=648 \cdot 7 + 8 = 64 bits fit, and a varint is at most nine bytes long:

v=∑i=0k−1(bimod128)27(k−1−i)(k≤8),v9=v8⋅28+b8.v = \sum_{i=0}^{k-1} (b_i \bmod 128)\, 2^{7(k-1-i)} \quad (k \le 8), \qquad v_9 = v_8 \cdot 2^8 + b_8 .

A reader that also takes seven bits from the ninth byte loses the lowest bit of numbers from 2562^{56} on; nine times FF then gives a large positive number instead of −1-1.

The jump at 5 is where a reader using the rule of thumb “type = byte count” slips by one byte and reads every following column wrongly.

SQLite: local part and overflow chain

A record that does not fit on its page keeps a beginning there; the rest lies in a chain of overflow pages, each with four bytes of next pointer and U−4U-4 bytes of payload (UU is the usable page size, the page size minus the reserved space). How much stays local is not “as much as fits” but exactly defined:

X={U−35table leaf⌊64(U−12)255⌋−23index pageM=⌊32(U−12)255⌋−23X = \begin{cases} U - 35 & \text{table leaf} \\ \left\lfloor \frac{64\,(U-12)}{255} \right\rfloor - 23 & \text{index page} \end{cases} \qquad M = \left\lfloor \frac{32\,(U-12)}{255} \right\rfloor - 23 P≤X:all local;else K=M+(P−M)mod(U−4),local={KK≤XMotherwise.P \le X:\ \text{all local}; \qquad \text{else } K = M + (P - M) \bmod (U-4), \quad \text{local} = \begin{cases} K & K \le X \\ M & \text{otherwise.} \end{cases}

Why this form. If KK bytes stay local, the rest P−KP-K is a whole multiple of U−4U-4: then all overflow pages are full, the last one too. If that is impossible because KK would exceed XX, the minimum MM stays – then the last overflow page is only partly filled. The two limits ensure that a table page holds at least four records and an index page at least four keys.

Worked out. For U=512U = 512: X=477X = 477 (table), X=102X = 102 (index), M=39M = 39. For U=1024U = 1024: 989989, 230230, 103103. For U=4096U = 4096: 40614061, 10021002, 489489. A 300-byte record is therefore entirely local in a table with U=512U = 512, but already in an overflow chain in an index of the same file – a reader that uses the table limit for the index reads the pointer there as text.

SQLite: pointer maps

With auto_vacuum, SQLite keeps a five-byte entry for every page from 3 on: type (root, free, first or further overflow page, b-tree page) and parent page. A map page holds J=⌊U/5⌋J = \lfloor U/5 \rfloor entries. Page 2 is the first map, and each map describes the JJ pages that follow it; then comes the next map. The maps therefore lie at

s is a map⟺s≥2∧(s−2)mod(J+1)=0,map(s)=2+⌊s−3J+1⌋(J+1).s \text{ is a map} \iff s \ge 2 \ \wedge\ (s-2) \bmod (J+1) = 0, \qquad \text{map}(s) = 2 + \left\lfloor \frac{s-3}{J+1} \right\rfloor (J+1) .

For U=1024U = 1024, J=204J = 204; maps lie at 2, 207, 412, 617, … The spacing is J+1J + 1, not JJ: the map itself counts. A reader that misses this is off from the second map on and reports data pages as maps.

SQLite: the write-ahead log checksum

A WAL is a sequence of frames, each with one page and a running checksum of two 32-bit numbers (s0,s1)(s_0, s_1) carried over all previous frames. For each pair of words x0,x1x_0, x_1 (byte order after the header magic):

s0←(s0+x0+s1)mod232,s1←(s1+x1+s0)mod232.s_0 \leftarrow (s_0 + x_0 + s_1) \bmod 2^{32}, \qquad s_1 \leftarrow (s_1 + x_1 + s_0) \bmod 2^{32} .

The new s0s_0 enters s1s_1 immediately – that interlocks the two halves. A frame is valid only if its sum matches and its salt equals the header’s; the first invalid frame ends the log, even if a later one looks correct on its own. The sum is meant to find half-written frames, not deliberate changes.

LMDB: which meta page holds

LMDB never writes into used pages. Each transaction allocates new pages and finally rewrites one of the two meta pages (page 0 and 1) alternately. The valid one is therefore the meta page with the higher transaction number, compared unsigned; the other holds the previous state. A reader that always takes page 0 reads the second-to-last state by chance – and never notices, because that one is consistent too.

The page size has no field of its own; it sits in a padding field of the free list. Byte order and word width are recognised from the magic 0xBEEFC0DE, which differs in both directions and sits at different offsets for 4- and 8-byte words.

dBASE: header, record and binary fields

A dBASE header has 32 bytes, then a 32-byte descriptor per field and a terminator byte 0D; every record starts with a deletion byte (* = deleted) followed by the sum of the field lengths. With nn fields of lengths ℓi\ell_i:

header length=32+32n+1,record length=1+∑i=1nℓi.\text{header length} = 32 + 32\,n + 1, \qquad \text{record length} = 1 + \sum_{i=1}^{n} \ell_i .

Records are read according to the file length, not the record count in the header – many tools append records without updating the counter.

Numbers in N and F fields are text. Binary are I (four bytes, least significant first, signed), B (IEEE double), Y (currency: an eight-byte integer with four fixed decimals, value =z/104= z / 10^4) and T (timestamp: four bytes Julian day, four bytes milliseconds since midnight). The Julian day counts from 1 January 4713 BC; day 2440588 is 1 January 1970, so

date=1970-01-01+(JD−2440588)days.\text{date} = 1970\text{-}01\text{-}01 + (\text{JD} - 2440588)\ \text{days}.

Example: JD 2440588 with 43,200,500 ms is 1970-01-01 12:00:00.5; JD 2460602 is 18 October 2024. The currency −12345678-12\,345\,678 is −1234.5678-1234.5678.

Which character set applies to text is given by a byte in the header, the language driver. The mapping follows the Visual FoxPro table: 0x01 code page 437, 0x02 850, 0x03 Windows-1252, 0x64 852 (Eastern Europe), 0x65 866, 0x66 865, 0x67 861, 0x7B 932, 0xC8 to 0xCC the Windows pages 1250, 1251, 1254, 1253, 1257. Between 0x08 and 0x1B the national OEM pages alternate row by row with their “starred” variant, which means 850: 0x0F German 437, 0x10 German* 850, 0x13 Japanese Shift-JIS, 0x17 Norwegian 865. For 0x68 (Kamenický) and 0x69 (Mazovia) the JDK has no character table; there a lossless substitute applies instead of a wrong table.

What follows

  • Assumptions. The files follow the format description; the usable page size is stated correctly in the header; for LMDB no transaction is half written (the lock file is not read).
  • The overflow limit differs for tables and indexes; a WITHOUT ROWID record of a quarter to half a page is already in the chain in the index.
  • The WAL checksum makes truncated frames visible, not deliberate changes – a reader that follows a valid-looking frame behind an invalid one shows a state SQLite would never have shown.
  • Two meta pages mean two states in one file; the previous one is reported as such, not discarded.
  • dBASE binary fields are least significant first, block numbers in FoxPro memo files most significant first – the same file knows both orders.

How it is tested

  • sqlite.TheorieFDprobe writes tables and WITHOUT ROWID indexes at 512, 1024 and 4096 bytes page size with the independently built Sqliteschreiber, with records on both sides of XX, around K=XK = X and far beyond, and reads them back byte for byte; plus the serial types and the position of the pointer maps.
  • Varintprobe, Walprobe, Sqlitekopfprobe, Sqliteprobe, OhneRowidprobe, Lmdbprobe, Lmdbkopfprobe, Dbasekernprobe, Memoprobe test the existing code; TheorieFDprobe adds timestamps, currency and language drivers.
  • Each load-bearing formula has a counter-probe that shifts it by one; all turn red.

Limits

  • LMDB with multiple values per key (F_DUPDATA) is reported raw, not resolved.
  • A WAL is evaluated, not applied: the file itself stays as it is.
  • dBASE index files are read in index order; they are not used for searching.
