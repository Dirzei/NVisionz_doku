ASAM MDF 3 — comparison against specification and asammdf

As of: 2026-09-05
Our implementation: envisionz.fileformats.mdf.Mdf3Quelle with Mdf3typ and Mdf3umrechnung, read-only, no third-party library
Specification: ASAM MDF 3.3 — references give block and field names, not paragraph numbers (see section 4)
Compared against: asammdf 8.8.26 (Python)
Test bench: envisionz.fileformats.mdf.Mdf3probe — 133 checks, six foreign anchors, fifteen own fixtures

The reference implementation. asammdf is a fast Python reader and editor by Daniel Hrisca with community contributions. It is an independent third-party implementation: the standard is set by ASAM e.V., whose documents sit behind a membership. In automotive measurement asammdf is the dominant open-source library for MDF — and therefore the only reference reachable without a vendor tool.

Why this one. Because MDF 3 is in the same position as MDF 4 — norm behind a membership, one dominant open-source implementation — and because asammdf reads both versions. That the same reference stands for both is an advantage: a difference between the two comparisons is then really a difference of the formats and not one of the tools.

Feature comparison

MDF 3 is not the older version of MDF 4 but a different format in the same family: the same eight MDF characters in the header, but no ## blocks, fixed block lengths instead of link counts, and an entirely separate list of conversion types. A reader for one cannot read the other.

Six measured differences

Twenty-one fixtures — six foreign anchors from asammdf, fifteen of our own from Mdf3schreiber — were run through both readers. Six cases diverged. Five of them concern damaged or unusual files; that is not a coincidence but the point: on healthy files two decent readers almost always agree.

The cyclic reference — asammdf hangs

Fixture Mdf3schreiber.ringverweis(): a data group whose link to the next points back at itself.

Us: MdfException saying "the chain of data groups is cyclic: the block at offset 272 appears a second time". asammdf 8.8.26: does not return within twenty seconds; the run was aborted.

Of all the ways to fail on a damaged file, hanging is the most expensive: an error message costs a minute, a hung batch run overnight costs the night.

Three record-ID bytes — asammdf reads garbage

Fixture Mdf3schreiber.dreiKennungsbytes(): dg_rec_id_size is 3. Only 0, 1 and 2 are allowed.

Us: named — "the data group at offset 272 declares 3 record-ID bytes per record; only 0, 1 or 2 are allowed". asammdf: reads without complaint and yields zeit = 3.47e-310, druck = 2.60e-259, zaehler = 0 — the numbers you get when reading floating-point values off by one byte.

A human notices numbers like these. In an average over ten thousand records nobody notices them.

The unknown data type — asammdf drops the channel

Fixture Mdf3schreiber.unbekannterTyp(): channel zeit carries data type 77, which does not exist.

Us: the channel stays in the table as a byte array, plus the finding "channel zeit has unknown data type 77; it is carried as a byte array". asammdf: returns two channels instead of three — zeit is missing, with nothing reported.

A missing channel is worse than an unreadable one: someone who does not know the file misses nothing.

The value range table — asammdf misreads its own file

Fixture Mdf3schreiber.umrechnungen(), channel bereich: cc_type 12 with ranges 0 to 5 → "tief", 5 to 10 → "hoch", default "weg". Raw values 0, 3, 5, 8.

Us: tief, tief, hoch, hoch. asammdf: tief, tief, tief, tief.

This difference could be ours, because our fixture is written by us — a reader that matches its own writer proves nothing. So it was measured independently: asammdf wrote an MDF 3 file with the same conversion itself and then read it back. Again tief, tief, tief, tief — contradicting the very range it reports having parsed, lower_0 = 5.0, upper_0 = 10.0, text_0 = 'hoch'. So asammdf here does not even agree with itself.

Along the way it emerged that writing also loses default_upper: 5.0 going in, 0.0 coming back.

The formula — again a decision, not an oversight

The same fixture channel formel: cc_type 10 with the text 2 * X1 + 1 over raw values 0, 3, 5, 8.

asammdf: 1, 7, 11, 17 — it evaluates the formula, and correctly. Us: 0, 3, 5, 8 plus the finding "channel formel uses a formula as text; this reader does not evaluate it and returns the raw value". The same decision as for MDF 4 and for the same reason — see M10.

The message that sends you down the wrong path

Fixture Mdf3schreiber.zuKurz(): a file of 18 bytes.

Us: "not an MDF file: it is only 18 bytes long, the identification alone needs 64". asammdf: "is not a supported MDF file; 3.3 file version" — it names a version number it cannot have read from 18 bytes, sending you to look for a version problem.

Both report an error. Only one of the two messages leads to the cause. That is exactly why in this module the length check comes before reading — with MDF 4 that was already the lesson.

How this was measured

Twenty-one fixtures from Mdf3anker and Mdf3schreiber were written out as files and run through both readers — through envisionz.fileformats.mdf.Mdf3Quelle and through asammdf 8.8.26 on Python 3.11. Each fixture ran in its own process with a time limit; without that, the cyclic reference would have taken the whole measurement down with it.

Where a difference rests on a self-written fixture, it was verified independently — see 2.4. A reader that matches its own writer proves nothing about the format.

Why no specification paragraph numbers appear here

As for MDF 4: the ASAM specification sits behind a membership. A paragraph number from memory would be a reference nobody can look up and that would still look as if it had been checked. So block and field names stand here instead.

The items

The Note column names the kind in front of the identifier. Only the gaps are work; they are listed individually in OFFENE-PUNKTE.md.

Our open gaps — this is the work

Deliberate decisions — nothing to do

M10 (decided) — The formula is named, not computed

cc_type 10 carries a formula as text. asammdf evaluates it, correctly in the measured case. We do not, for the same reason as with MDF 4: evaluating a formula without a fixture carrying documented expected values is a source of error disguised as a measurement — it yields a number, and nobody can tell whether it is right. The raw value comes back, the formula is quoted verbatim in the findings, and anyone wanting to evaluate it can do so outside.

M12 (decided) — Bus protocols

As with MDF 4: a domain layer on top of the format that needs a second file the format knows nothing about. It does not belong in a format reader.

M13 (decided) — Writing

This module does not write — as a guarantee resting on four levels and measured.

Properties of the format — affecting both

M5 (property) — Source information — closed on 2026-09-07

CEBLOCK says where a channel comes from. It now stands as a table of its own, quellen: per channel the type, its plain-language name, description, identification, number and address. The reference values are asammdf 8.8.26's on the same file — it writes such a block for every channel.

Two layouts under one id. A CEBLOCK carries at the same place either a control unit (type 2: module number, address, 80-character description, 32-character identification) or a CAN source (type 19: message id, channel index, 36-character message name, 36-character sender name). The fields sit at different offsets and have different lengths — a reader that knows only one layout reads text from numbers and numbers from text in the other.

M6 (property) — Channel dependencies — closed on 2026-09-07

CDBLOCK says that several channels together form an array. The grouping now stands in the table felder: the leading channel, the type (vector, matrix), the number of parts and the dimension sizes. The columns still stay separate — that is a decision, not a gap: a table column containing "vector" is useless to SQL. What was missing was the information, not the shape.

The sizes stand behind the links, and thus at a place that depends on the number of dependent channels: three links per part. Looking for them at a fixed offset reads a link as a size for every array with a different part count — a number that looks like a size.

M7 (property) — Program and trigger blocks — closed on 2026-09-07

PRBLOCK carries the measurement program's text; it now stands at Mdf3Quelle.programmtext(). It is not a TXBLOCK: own id, no link, text directly up to the end of the block. Reading it through the text function returns null and makes the file look like one without a program text.

TRBLOCK stands as the table ausloeser — and three numbers per trigger, not one: instant, pre time, post time. Taking only the instant tells you when something happened, not which excerpt is in the file because of it. Plus the comment from the TXBLOCK beside it.

M8 (property) — Sample reduction — closed on 2026-09-07

SRBLOCK carries precomputed reductions over time windows. They stand as the table stichproben: per level the channel group, the number of reduced records, the window length and the offset of the data block. They hang as a chain, one level per window length — reading only the first shows, of a file with tenth-second and second windows, only the tenth.

asammdf's MDF 3 implementation does not know the block; the foreign column therefore says no, and the fixture is our own, built onto an asammdf body.

M9 (property) — The code page — closed on 2026-09-07

hd_code_page names the code page of the texts, and it is now applied: twenty-four Windows code pages are mapped, an unknown number yields a finding and not silently ISO-8859-1.

The case at issue is the silent one: for German umlauts from a 1252 file, 1252 and ISO-8859-1 agree at exactly the places where it would show. For Cyrillic or Japanese channel names they do not — and every byte is a valid character in ISO-8859-1, so there is no place where it breaks.

M11 (property) — Date and time as conversion types — closed on 2026-09-07

cc_type 132 and 133 are not a calculation but an interpretation of bytes: seven for a date, six for a time span. All other types take the raw value and compute with it; these two say how the channel's bytes are to be read. Reading them as a number yields a number.

Three traps in thirteen bytes. The milliseconds of type 132 include the seconds — 0 to 59999, not 0 to 999. The day carries the weekday in its top three bits, the hour the DST flag in bit 7; taking both bytes whole gives the 41st day and the 141st hour. And the year is two digits without a century.

This interpretation is not cross-measured, and that is stated here. asammdf 8.8.26's MDF 3 implementation does not know the two types, and there is no fixture from the reference product for them. It follows the specification and is tested against our own fixture whose reference values are computed, not read off. More is not to be had at this point — not measured is not the same as guessed, and neither is the same as confirmed.

Done along with it: the column's field type now says TEXT. Were it GANZZAHL, the column description would say something other than the value — and a caller trusting the description would get an exception instead of a date.

MDF3.1 (property) — The same eight characters for two formats

Formerly: M31.

MDF 3 and MDF 4 both start with MDF . They are told apart by the number at offset 28 — 330 versus 410 — not by the text. A reader checking the text takes one for the other and then reports a block error instead of a format error. Both implementations get it right; it is listed because a third almost certainly will not.

MDF3.2 (property) — Byte order lives in the file header — but only for six types

Formerly: M32.

Unlike MDF 4, MDF 3 has a byte order for the file, and it applies to data types 0 through 3. Types 9 through 16 carry it themselves and override the file setting. Implementing only one of the two reads half the file wrong.

MDF3.3 (property) — The name is stored twice, at different lengths

Formerly: M33.

The channel field holds 32 characters; a longer name additionally sits in a text block. The short form is then truncated and still valid. Reading only the field yields names that are right until two channels agree in their first 31 characters. Both implementations take the long one.

MDF3.4 (property) — Report rather than guess — and what it costs

Formerly: M34.

In five places this reader reports something where asammdf silently carries on: a declared count that does not match the chain length; a data block that is too short; an unknown conversion type; a value table declaring more entries than it holds; an illegal record-ID size. The price is a findings list that has to be read.

MDF3.5 (property) — With two ID bytes the record ID appears before AND after

Formerly: M35.

With dg_rec_id_size = 2 the same ID appears before and after the record. Reading only the leading one and taking the trailing one as payload shifts every following record by one — and the values look plausible until the first floating-point channel.

Findings against the reference implementation

M14 (BUG there) — A channel dependency on the master channel makes the file unreadable for asammdf

A CDBLOCK on the master channel of a channel group — naming two other channels as parts of a vector and not itself — suffices, and asammdf 8.8.26 no longer reads the whole group: ValueError: record is None. Affected are also the channels that have nothing to do with the dependency.

It is the position, not the block. The same block on the second channel is read without complaint. That is exactly what makes the defect unpleasant: looking for it with a file whose dependency sits on a data channel will not find it.

How to reproduce — Take an MDF 3 file from asammdf with a channel group of three channels — time (master), druck, zaehler. Append a CDBLOCK at the end of the file: id CD, block length 8 + 2*12 + 6, dependency type 1, part count 2, then twice the triple (data group, channel group, channel) for druck and zaehler, then three uint16 sizes 2, 0, 0. Point the link at offset 16 of the first CNBLOCK to that block. Then MDF(file).get("zaehler"). Expected: five values. Observed with asammdf 8.8.26 on Python 3.10: ValueError: record is None from blocks/mdf_v3.py, function get_master. Putting the same link on the second CNBLOCK instead makes the file readable. Both files are held as foreign anchors in the test bench: Mdf3anker.cdAmZeitkanal() and Mdf3anker.bloecke().

M1 (BUG there) — The cyclic reference makes asammdf hang

See 2.1. Measured with a twenty-second time limit; the process was then aborted. A damaged file may make a reader abort, but not stall.

How to reproduce — Build an MDF 3 file in which the first data group's dg_dg_next link points back at the data group itself (here: offset 272). Then asammdf.MDF(file). Expected: an error message. Observed with 8.8.26 on Python 3.11: the call does not return within twenty seconds and was aborted. The file is produced by envisionz.fileformats.mdf.Mdf3schreiber.ringverweis().

M2 (BUG there) — Illegal record-ID sizes turn into numbers

See 2.2. dg_rec_id_size = 3 yields floating-point values on the order of 10⁻³¹⁰ from asammdf instead of a message.

How to reproduce — An MDF 3 file with dg_rec_id_size = 3 in the DGBLOCK (only 0, 1 and 2 are allowed), otherwise an ordinary group with channels zeit (DOUBLE), druck (DOUBLE), zaehler (INT). Then read the three channels. Expected: a message about the illegal record-ID size. Observed with 8.8.26: no warning, and zeit = 3.47e-310, druck = 2.60e-259, zaehler = 0. The file is produced by Mdf3schreiber.dreiKennungsbytes().

M3 (BUG there) — A channel with an unknown data type disappears

See 2.3. Three channels in the file, two in the output, no message.

How to reproduce — An MDF 3 file with three channels, one of which carries data type 77 in its CNBLOCK (only 0, 1, 2, 3, 7, 8 and 9 through 16 exist). Then query the channel list. Expected: three channels, the third marked somehow. Observed with 8.8.26: two channels, no message. The file is produced by Mdf3schreiber.unbekannterTyp().

M4 (BUG there) — The value range table is applied wrongly

See 2.4 — verified on a file asammdf wrote itself, where the result contradicts the range boundary asammdf itself reports having parsed.

How to reproduce — Reproducible without any foreign file — asammdf alone suffices. Using ChannelConversion(conversion_type=12, ref_param_nr=3, default_lower=0.0, default_upper=5.0, default_addr=b'tief', lower_0=5.0, upper_0=10.0, text_0=b'hoch', lower_1=0.0, upper_1=0.0, text_1=b'weg'), write a signal with raw values 0, 3, 5, 8 as MDF 3.30 and read it back. Expected from the parsed table (lower_0 = 5.0, upper_0 = 10.0, text_0 = 'hoch'): tief, tief, hoch, hoch. Observed with 8.8.26 on Python 3.11: tief, tief, tief, tief. Side finding: default_upper comes back as 0.0 instead of 5.0.

What is hard about the format itself

Fixed block lengths without a link count. Unlike MDF 4, an MDF 3 block does not say how many links it carries — the length is there, and what is inside must be known from the version number. A field added in 3.30 is absent in a 3.00 file, and both files look the same.

The time axis is a channel with a flag, not a concept of its own. Not looking for it yields a table without time; looking for it wrongly yields two.

What is good about the format: it is small. Ten block types, fourteen data types, twelve conversions — that can be read completely and checked completely. That is no longer true of MDF 4, and it is why MDF 3 will not disappear from test benches any time soon.

The Java implementation — where this reader stands among its own kind

Why this section. Every other comparison in this module measures against a tool in a different language. That is good against misunderstandings of the format and says nothing about where this reader stands among its own kind. What matters is the distinction between a pure reimplementation in Java and a wrapper around a C library: only the reimplementation solves the same task under the same conditions.

No maintained Java project found. wollekuel/jmdflib is pure Java against specification 3.1.1 but without a published release, with a long self-documented list of gaps and no discernible licence. More usable would be org.eclipse.mdm.openatfx.mdf, which reads MDF3 and MDF4 — but only through an ASAM ODS session, with a CORBA ORB and OpenATFX in tow. Not measured, and hardly suited to a lean measurement.

How solid this is. Researched on 2026-09-06 via web and GitHub search; Maven Central's search API was blocked, so a systematic artefact search was not possible. Where it says "not measured" below, it says so explicitly — a named library is not yet a measured one.
