Host, workspace and rail – background

How the frame is built in a fixed order, how a workspace is restored from saved tabs or rebuilt after a language change, and how the vertical toolbar with its cards replaces the settings window.

Start-up in a fixed order

A Swing program has many things that must exist before the first window and depend on each other: the language, the icon size, the look and feel, the log, the list of apps. If they are set up in the wrong order the error does not show as a crash but as a cosmetic fault – a menu in English although German is set, or icons of the wrong size. FrameworkBootstrap.start() therefore fixes the order in one place:

StepWhatWhy here
0Preparation for the GraalVM executableThere java.home is not set, but Swing's font configuration needs it; without the fix every look and feel fails during font set-up. No effect on the normal JVM.
1Determine the working directoryEverything else (settings, log) lives below it.
1bLoad operating settings, apply language and icon sizeThe language must be in place before the user interface is built, the icon size before the first icon is loaded.
1cFrame settings (database defaults, diagnostics, start folder per app)A file chooser should already stand in the remembered folder at the first click.
2, 2b, 2cLog, handler for uncaught exceptions, diagnosis of the old AWT event modelWithout a console window System.err goes nowhere; from here on every exception leaves a trace in <working directory>/logs/<appName>-0.log.
3, 3bLook and feel, then interface and font scalingA new look and feel resets the default font; scaling must follow it and is noted for later changes.
4Build the app catalogOnly after the language: the app classes with their (possibly localised) descriptor texts are then loaded only once the language is set.

For the look and feel (step 3) a fallback chain applies: the theme stored in theme.properties; if the file is missing, the default theme (Arc); if the FlatLaf libraries are missing altogether, the system look and feel. The result of start() is the SwingHost, which holds catalog, bus, services, persistence and log and offers each app its own AppContext.

Source: envisionz-framework-swing/src/envisionz/swing/FrameworkBootstrap.java (start, comments 0 to 4).

Decision in the framework: Language and icon size before the user interface is built, log before anything that can fail, app catalog after the language. The order is part of the contract of start(); whoever moves a step changes how the apps look.

Saving, restoring and rebuilding the workspace

The workspace consists of the open tabs. The TabManager holds them together with the app instances; two routes rebuild them from saved state, and both use the same contract of captureState() and restoreState() (life cycle of the app).

Loading

SwingHost.loadWorkspace(file) reads the file through the PersistenceManager (session storage) before it closes anything: if the file is unreadable or has an unknown version, the current workspace is left untouched. Only then are all tabs closed and the saved tabs opened in file order. If a single tab fails – for example because its app is missing from the class path – this is logged and the next one is opened; the session then returns incomplete rather than not at all. Finally the saved active tab is selected, provided the index is in the valid range.

loadWorkspace(file):
    state ← persistence.load(file)                        throws before anything is closed
    tabManager.closeAllTabs()
    for each tab in state.tabs:
        try  app ← catalog.newInstance(tab.appId);  tabManager.openTab(app, tab)
        catch exception → log, continue with the next
    if 0 ≤ state.activeTab < number of open tabs:  tabManager.select(state.activeTab)

saveWorkspace(file):
    if no TabManager: throw IllegalStateException
    state.activeTab ← tabManager.selectedIndex
    for each open app:  t ← app.captureState();  if t ≠ null: state.tabs.append(t)
    persistence.save(state, file)

openTab(app, saved):
    view ← app.createView(contextFor(app));  create tab, select it
    if saved ≠ null: try app.restoreState(saved); set title  catch → log
    view.onShown()

Source: envisionz-framework-swing/src/envisionz/swing/host/SwingHost.java (saveWorkspace, loadWorkspace), …/tabs/TabManager.java (openTab).

Rebuild after a language change

A user interface built with German texts is not relabelled but rebuilt: this is simpler and more dependable than updating every component individually. TabManager.rebuildAll() first captures the state of every app, plus title and whether the tab is detached, and notes the selection. Only when everything is saved are the old instances closed without a prompt (canClose is skipped because the state is preserved; dispose() and cleaning up the working directory still run). Then a fresh instance is created per entry with openTab(fresh, state), the title is restored, a detached tab is detached again, and the selection is reset if its index is still valid. Errors in one app are logged per step and affect only that app.

Source: envisionz-framework-swing/src/envisionz/swing/tabs/TabManager.java (rebuildAll, disposeQuietly).

Decision in the framework: Whatever is not stored through captureState() is lost on a language change – a rebuild makes this gap visible, a file save only at the next start. An app that stores its state completely survives both. In addition, a FocusAppEvent request from one app brings another to the front (focusOrOpen): if the app is already open its tab is selected, otherwise a new one is opened. For this the host subscribes to the bus when the TabManager is first set and switches to the event thread, so that a data event following immediately reaches the freshly opened app.

Rail and cards instead of a settings window

In the apps, settings are not in a dialog but are cards in a vertical toolbar (rail). The reason is practical: a modal dialog covers the work area and stops every automatic test, whereas a card next to the diagram shows the change immediately. ContentSidebar implements this with three parts: a toolbar of toggle buttons (icon only, label as tooltip), a JSplitPane whose left side is a CardLayout with the cards, and the work area on the right.

  • addCard(key, panel, icon, label) adds the card to the CardLayout under the key, creates a toggle button in a ButtonGroup and names the card after the key if it carries no name yet (so a test can find it).
  • showCard(key) shows the card, selects the button and opens the bar if it was collapsed. Unknown keys do nothing.
  • setSidebarVisible(b) sets the divider to the card width or to 0; if the bar is set to “always visible”, it stays open.

The width limit of 360 px

A card must never become so wide that it displaces the diagram. Kartenbreite.GRENZE is 360 pixels, TEXTBREITE 320, the default for wrapped text. Three helpers keep cards to it:

umbruch(text, width = 320):
    if text empty: return text
    if text already "<html>…" and contains "width": return text        already has a width, do not guess
    content ← (text already HTML) ? body : escape(text)                 & < > replaced
    return "<html><table width='width'><tr><td>" + content + "…"

umbrichWennBreiter(button, width):
    if preferredWidth(button) ≤ width: return
    button.text ← umbruch(button.text, max(80, width − 34))             34 px allowance for icon and border

gedeckelt(content, width = 360):
    container with BorderLayout whose preferred and minimum width are min(own width, width)

Source: envisionz-framework-swing/src/envisionz/swing/layout/Kartenbreite.java, …/module/layout/ContentSidebar.java (addCard, showCard, setSidebarVisible).

Why HTML with a table: a JLabel with plain text never wraps and demands the width of its longest line; HTML with a fixed table width wraps. Long labels thus grow in height instead of width. gedeckelt limits the same for a whole container through its preferred and minimum width.

How it is checked

  • Rahmenprobe checks host, menu, toolbar and actions, among them that saveWorkspace without a registered TabManager refuses with a reason that names it.
  • Beendenprobe checks the path on exit: the prompt through canClose(), dispose() and cleaning up the working directory.
  • Bausteinprobe (77 checks) and Baumprobe (76) run headless with -Djava.awt.headless=true; what cannot be carried out on a machine counts as “not feasible”, not as failed.
  • Kartenbreite, ContentSidebar and rebuildAll do not appear in the probes of this module; their behaviour is shown by the apps in use, not by a measurement of its own.

Limits

  • The rebuild after a language change is only as complete as the captureState() of the respective app. State that lives only in components is lost.
  • loadWorkspace closes the existing workspace as soon as the file has been read; a tab whose app is missing is skipped without asking the user (a log entry only).
  • Kartenbreite acts through the preferred (and, for gedeckelt, the minimum) width. The width of the bar itself is set by the caller with new ContentSidebar(content, width); the constant GRENZE is a convention the caller has to keep, not an enforcement.
  • The order of the start-up steps is fixed; use without a log or without a look and feel is not intended.
