Probes, counter-probes and coverage

How the workspace is tested and how to tell whether a check is worth anything: probes as classes with main, a collecting runner, counter-probes that must catch deliberately corrupted code, the measurement of the lines that ran, and corrupted files against every reader.

What this is about

A green probe only says that it found nothing. Whether it could have found something, it does not say. The test bench therefore answers three questions separately: does the probe pass (collecting run)? Does it turn red when the code is wrong (counter-probe)? Which lines did it run at all (line coverage)?

Probes and the collecting run

A probe is a class with main that counts checks and ends with a non-zero return code if one failed. No external test framework is needed. Pruefung collects the verdicts: wahr (true), gleich (equal), nahe (close within a tolerance), gescheitert (failed), and uebersprungen (skipped) for a probe whose fixture is missing. Skipped counts neither as checked nor as a failure. It does appear with its reason in the collected report, because staying silently green would claim a coverage that does not exist.

The collecting runner builds the class paths from the modules' project files, compiles every probe directory and runs everything that has main, headless and with a fixed locale. A probe whose fixture is missing is reported as pending, not silently skipped. Probes find their files via the location of their class, never relative to the working directory.

Whoever tests an application gives it a Testkontext instead of a window. Its event bus delivers immediately and on the same thread, to every subscriber whose type the event is, not only to the exact same type. Its log collects the messages with level and name prefix, so that an error message becomes a verdict.

Zustandsabgleich counts the controls on a settings card that carry state. A composite component of the workspace, such as a font field made of a text field and two check boxes, counts as one setting. It does not descend into its internals. Labels, panels, separators and scroll panes carry nothing.

Counter-probes

Every probe needs at least one counter-probe. A case names a file, a text alt (old) that must occur in it exactly once, its replacement neu (new), the responsible probe and optionally a text that must appear in its red output. The tool corrupts a copy, compiles it into its own directory that comes before the built state on the class path, and runs the probe. Before that the probe runs once uncorrupted; if it is already red, a red result says nothing.

VerdictMeaning
ROT (red)correct: the probe catches the corruption, with the expected text
GRUEN (green)finding: the corruption goes unnoticed, the probe is blind at this spot
ANDERS (different)finding: red, but without the expected text, i.e. caught by another check
FEHLER (error)cannot be judged: alt is missing or occurs more than once, the corruption does not compile, the build is stale, the probe is already red uncorrupted, or the time ran out

The expected text matters. Without it a corruption could be caught by chance by an entirely different check, while the intended check has long stopped checking anything.

Cases run in groups: one probe of a module with its baseline run and its cases. Within a group the cases stay sequential, because a probe may write fixed files. The groups are distributed over tracks:

Trackwhen
PARALLELthe normal case, on all threads but one
EINE (one)modules with windows, focus, clipboard, sound or network: one after another on a thread of their own alongside
KOPFLOS (headless)a group of such a module whose probe reaches neither sound nor network and prints the same lines without a screen as with one: it runs headless on the parallel threads
ALLEIN (alone)graphics unit and camera, only after everything else

Groups start ordered by their computing time in the last run, longest first. That way the run does not end with a long group that started last. If a probe run next to others exceeds the time limit, it is repeated once on its own. A case that was red last time and whose inputs have not changed is not run again. Its inputs are the fields of the case, the sources of the module and its dependencies, the Java version and the tool itself; their fingerprint is SHA-256.

Line coverage and probe coverage

Probe coverage reads only the source tree. It counts which classes a probe mentions by name: in the same package, through an import or fully qualified. The number is an upper bound. Only the converse is reliable: a class no probe mentions is certainly untested.

Line coverage measures which lines actually ran during the probes, and at every branch whether both ways were taken. To do so the compiled classes are copied into a directory of their own and extended with counting calls using the JDK's ClassFile interface: one after each line marker, and one each for “taken” and “not taken” at every conditional jump. The built state stays untouched. Every probe JVM stores its hit markers when it ends. With ZZ the measurable lines of a module and G⊆ZG \subseteq Z the lines that ran, the coverage is

d=|G||Z|.d = \frac{|G|}{|Z|}.

A line that ran is not yet checked; whether its result is checked is shown by the counter-probes. Extended classes run slower, so probes with time limits quadruple them under the measurement.

Coarser and older is the class coverage. A runtime agent changes no class; it only records which of the workspace's classes were loaded and from where. It leaves out the runtime's own classes and nameless constructs such as lambda carriers.

Corrupted files against readers

A reader receives a file it did not write. Every number in it (count, length, image size, depth) is a claim of the file. Boeswillig derives deterministic variants from a readable seed: truncations, 16-, 32- and 64-bit extreme values in both byte orders, flipped bits, self-references and runs of 0xFF. The same seed yields the same variants, so that a finding is reproducible.

Each variant is read on a thread of its own and judged:

Verdictwhen
GELESEN (read)the reader ran through
ABGEWIESEN (rejected)an I/O exception or an exception of the workspace's own
UNSAUBER (unclean)a foreign runtime exception: no crash, but no message either
ABSTURZ (crash)an Error, more than 5 s, or more than max⁡(256MB⁡,256n)\max(256\,\mathrm{MB},\, 256\, n) allocated for a file of nn bytes

The report counts the reasons per verdict, the most frequent first and with the first example. ABSTURZ is red in every probe.

Limits

  • Line coverage runs headless. Code that only runs with a window stays uncovered in the measurement, even if a probe checks it with a screen.
  • A probe that starts a JVM of its own is measured there only if it passes on the measurement's storage directory.
  • A counter-probe corrupts source code. A check that works on the source text itself cannot be corrupted this way; there the behaviour is measured.
  • None of the numbers says whether a probe checks the right thing. Expected values are computed from formulas, not copied from the old state.
