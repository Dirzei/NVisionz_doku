App contract, session state and hardened XML – background

How an app is found, built, saved and cleaned up, what shape its saved state has, and why every XML file in the framework is read through the same hardened factory.

Discovery through ServiceLoader

The main window knows no app by name. It still has to know which apps are on the class path, which file extensions they open and which menu entry they get. The framework uses the mechanism the JDK already provides: each app library ships a text file META-INF/services/envisionz.api.App that holds the fully qualified class name of its App implementation. ServiceLoader.load(App.class) reads all such files on the class path and returns one instance per line.

Two properties of this procedure are what the contract builds on:

  • The host needs no configuration. An app is added by putting its module on the class path and removed by taking it out. The host stays unchanged.
  • Instances are created before anything is shown. This is why an app's constructor may only set fields – no user interface, no file access – and why descriptor() must be cheap. Both are duties stated in the Javadoc of App.

The metadata lives in a record AppDescriptor: identifier, display name, menu text, icon, file extensions, accelerator key. The identifier is the key under which the host finds the app again – in the menu, when opening a file and when restoring a saved session.

The life cycle of an instance

An App instance is one open tab, not the app type. If the user opens two files with the same app, two instances run side by side, each with its own state and its own working directory. The contract fixes the order of calls:

  1. Constructor – fields only, no Swing, no file access.
  2. descriptor() – at discovery time, immutable metadata.
  3. createView(AppContext) – exactly once per instance. The user interface is built here. Everything the app needs from the framework is in the AppContext it receives: log, event bus, service registry, a working directory of its own, setting the tab title, closing the tab. The app never touches a host class or a static singleton; whoever supplies the context (multi-app host, standalone starter, test) decides what the app can do.
  4. restoreState(PersistableTab) – after createView, when a saved state exists.
  5. captureState() – before the session is written; may return null if the app has nothing to save.
  6. dispose() – on closing: close connections, stop worker threads, cancel timers.

The interface appears only in step 3 for a practical reason: discovery runs at start-up for all apps, including those the user never opens. If the constructor were expensive, every program start would pay for all 21 apps.

Pseudocode – registering and opening (host, after the source of AppRegistry and TabManager)

// start-up: once
for each instance app of ServiceLoader.load(App):
    desc ← app.descriptor()
    cls ← app.getClass()
    catalog[desc.id] ← (desc, factory = () → cls.noArgConstructor().new())
                                              same id: the later one replaces the earlier

// opening a tab: per tab
app ← catalog[id].factory()                   fresh instance, never the one from start-up
ctx ← Context(Log(id), Bus, Services, workDir, Title, Close)
view ← app.createView(ctx)
tab ← view.component()
if saved state ≠ null:
    try app.restoreState(state)  catch exception → log, tab stays open
view.onShown()

Source: envisionz-framework-core/src/envisionz/core/registry/AppRegistry.java (discover, newInstance) and envisionz-framework-swing/src/envisionz/swing/tabs/TabManager.java (openTab); the contract itself is in envisionz-framework-api/src/envisionz/api/App.java. The host side is described under app catalog and host.

Decision in the framework: The instance created at discovery serves only to read descriptor() and to remember the class. Each tab gets its own fresh instance through getDeclaredConstructor().newInstance() – which is why every app needs a no-argument constructor. The standalone starters register their app through register(descriptor, supplier) instead, without reflection.

The descriptor is a value

Two guarantees in the compact constructor of the record keep it dependable: id, displayName and menuLabel must not be null, and the extension list is copied with List.copyOf (a null list becomes empty). Without the copy an app could keep filling its list after construction and change the host's menu afterwards with nothing in sight to explain it. As a side effect, List.of("csv") and an ArrayList with the same content are equal after copying – whoever puts descriptors in a set or searches with contains relies on that. Display name and menu text are looked up in a resource bundle on every call (envisionz.api.apps, keys <id>.name and <id>.menu); if the key or the bundle is missing, the text stored in the record applies. Extensions are written without a leading dot and in lower case.

The saved session state

On exit – or at any time on request – the framework should record which tabs were open and what was set in them, and rebuild everything at the next start. The model for this is deliberately simple: strings in ordered tables, no object graphs.

TypeContent
PersistableStateformat version ("1.0"), time of saving (ISO string), list of tabs in display order, index of the active tab
PersistableTabapp identifier, title, flat properties key → value, named sections
PersistableTab.Sectionproperties of the section and a list of repeated entries, each again key → value

An app writes its settings with tab.set(key, value), structures them with tab.section(name) and adds repetitions – such as the rows of a table – with section.addItem(). Reading uses get(key, default): if a key is missing because the file comes from an older version, the app's default stays.

Decision in the framework: No reflection, no annotations, no JAXB. The model is a flat structure of strings, so that the GraalVM native image needs no reflection configuration for persistence and format changes are possible without changing the model code. All tables are LinkedHashMap: insertion order is kept and appears like that in the file, so two saved states can be compared line by line. section(name) returns the same section on the second call; PersistableState.tabs(), by contrast, is intentionally the live list the host fills while loading.

The implementation of writing and reading (StAX, path relativisation, temporary file) is not in this module but in framework-core. The file has the form

<envisionz-state version="1.0" savedAt="…">
  <tabs>
    <tab type="<app id>" title="…">
      <properties>  <property key="…">value</property>  …  </properties>
      <section name="…">
        <properties> … </properties>
        <items>  <item> <property key="…">…</property> … </item>  …  </items>
      </section>
    </tab>
  </tabs>
  <activeTab>0</activeTab>
</envisionz-state>

Source: envisionz-framework-api/src/envisionz/api/persistence/PersistableState.java, PersistableTab.java; shape of the file after the class comment of PersistableState.

Events and services as interfaces

The context hands two intermediaries to the apps that exist in this module only as interfaces. EventBus has publish(event) and subscribe(class, listener); the result of subscribe is a handle for unsubscribing. Any object can be an event, usually a record – for example FocusAppEvent(appId), with which an app asks the host to bring another one to the front. ServiceRegistry manages at most one implementation per interface type: register, get (as an Optional), unregister. The guarantees – who determines the recipients, in which order delivery happens – belong to the implementation and are therefore on the framework-core page.

Hardened XML readers

An ordinary XML factory does two things on the file's say-so that nobody wants here:

  • External entities. A declaration of the form <!ENTITY x SYSTEM "file:///…"> makes the parser read a foreign file and put its content into the document. A diagram definition that is passed on could fetch an arbitrary file of the recipient into a title when opened.
  • Nested entities (“billion laughs”). Ten levels of ten references each inflate a few hundred bytes to gigabytes.

The framework's files never need either – they carry no DOCTYPE declaration. SichereXml therefore forbids the declaration altogether. That closes both routes with one measure; the further settings are the second safeguard in case another parser sits behind DocumentBuilderFactory.newInstance().

domFabrik():
    f ← new DocumentBuilderFactory
    f.secureProcessing ← on
    f.DOCTYPE declaration ← forbidden                 the actual barrier
    f.external general entities ← off;  f.external parameter entities ← off
    f.load external DTD ← off;  f.XInclude ← off;  f.expand entity references ← off
    try ACCESS_EXTERNAL_DTD ← "";  ACCESS_EXTERNAL_SCHEMA ← ""
    catch IllegalArgumentException → nothing   parser does not know the attribute; the switches above hold
    return f

staxFabrik():  SUPPORT_DTD ← false;  IS_SUPPORTING_EXTERNAL_ENTITIES ← false

Source: envisionz-framework-api/src/envisionz/api/xml/SichereXml.java (domFabrik, domLeser, staxFabrik).

Decision in the framework: SichereXml is the place where XML factories come from. New readers call it instead of building a factory themselves; a probe searches the workspace source for unhardened DocumentBuilderFactory.newInstance() calls.

How it is checked

  • Vertragsprobe (70 checks) measures the quiet spots of the module: the copy of the extension list, equality of two descriptors, that section(name) returns the same section on the second call, insertion order, the initial value of the active tab and the ISO format of the timestamp. Nine deliberate falsifications of the production code – such as dropping List.copyOf, replacing LinkedHashMap by TreeMap, making the tab list static – each turned the probe red.
  • SichereXmlprobe (12 checks) reads an ordinary document, rejects an external entity pointing at a secret file and a “billion laughs” document, and checks the same for the StAX factory. As a counter-test, the unhardened factory reads the same secret file – otherwise the probe would be blind.
  • Descriptor comparison reads the descriptors of all apps from the source and checks them against each other: duplicate identifier, duplicate accelerator, duplicate icon, form of the extensions. No probe inside one module can do that, because a collision arises only between two apps that know nothing of each other.
  • EventBus and ServiceRegistry are deliberately not tested here: a probe would have to write an implementation itself and then test that – which measures nothing. The module that implements them tests their guarantees.

Limits

  • The state consists of strings only. Numbers, truth values and lists are converted by the app itself; object graphs with references cannot be stored.
  • The interface knows no format migration: PersistableState.CURRENT_VERSION is "1.0"; what the reader does with a foreign version is described in framework-core.
  • A collision of identifiers is not reported at run time: with the same identifier the app found later replaces the earlier one. Only the descriptor-comparison tool catches that.
  • SichereXml forbids DOCTYPE completely. Files that carry a DTD cannot be read with it.
