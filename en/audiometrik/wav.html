Signals and WAV – representation, quantisation, file layout

The computation behind Audiosignal, Ganzsignal, Wavleser, Wavschreiber and Wavformat: how a sample is converted between file, integer and floating point, how a RIFF/WAVE file is laid out, what “bit-exact” means, pseudocode following the source, how it is tested and where the limits are.

What this is about

A digital audio signal is a sequence of numbers: one sample per channel at fixed time intervals, at 48 kHz that is 48,000 values per second and channel. In a file these values are stored as integers of fixed word length (8, 16, 24 or 32 bit) or as floating-point numbers (32 or 64 bit). The measurement chain, on the other hand, wants to compute with a single representation independent of the file, so that a signal-to-noise ratio does not depend on whether the reference is a 16-bit file and the test signal a 24-bit file.

The module therefore keeps two forms side by side:

  • Audiosignal – one double array per channel in the range −1…+1. All measures, the alignment and the spectra work on it.
  • Ganzsignal – one int array per channel with the raw values of the file and the word length. This is the form in which a lossless encoder sees its input, and the only one in which “bit-exact” can be taken literally.

Wavleser and Wavschreiber mediate between both and the file. They read and write RIFF/WAVE directly, without a third-party library and without javax.sound.

Integer and floating point

An integer with bb bits in two's complement covers the values −2b−1-2^{b-1} to 2b−1−12^{b-1}-1. The conversion to the range −1…+1 divides by the power of two V=2b−1V = 2^{b-1}:

x=kV,V=2b−1,k∈{−V,…,V−1}x = \frac{k}{V}, \qquad V = 2^{b-1}, \qquad k \in \{-V, \dots, V-1\}

The range is therefore asymmetric: −1 is exactly representable, +1 is not. The largest positive value is 1−1/V1 - 1/V, for 16 bit 32767/32768≈0.9999732767/32768 \approx 0.99997. The opposite direction rounds to the nearest integer and clamps to the representable range:

k=min⁡(V−1,max⁡(−V,round⁡(x⋅V)))k = \min\left(V-1,\ \max\left(-V,\ \operatorname{round}(x \cdot V)\right)\right)

As long as nothing is clamped, the error of a round trip is at most half a quantisation step:

|x−k/V|≤12V=2−b|x - k/V| \le \frac{1}{2V} = 2^{-b}

For 16 bit that is about 1.5⋅10−51.5 \cdot 10^{-5}, for 24 bit about 6⋅10−86 \cdot 10^{-8}. This is exactly the bound that Wavprobe checks.

Convention in the framework: reader, writer and Ganzsignal.alsAudiosignal() all use the same power of two 2b−12^{b-1}. The writer does not scale by 2b−1−12^{b-1}-1. The source code notes that mixing both factors produces a systematic level error of about one quantisation step. The price of the uniform power of two: +1.0 is clamped to V−1V-1 on writing and comes back as 1−1/V1 - 1/V.

The 8-bit peculiarity

WAV stores 8-bit values, as the only word length, unsigned with the zero point at 128. The reader subtracts 128 before dividing by 128; the writer adds 128. From 16 bit upwards the values are signed and stored with the least significant byte first (little endian).

Floating point

With IEEE floating point (format type 3) nothing is scaled: the value in the file is the value in the Audiosignal. 32 bit are read via Float.intBitsToFloat, 64 bit via Double.longBitsToDouble, both little endian. Values outside −1…+1 are preserved – a floating-point file may exceed full scale without anything being cut off. When writing with 32 bit, only the rounding from double to float is lost.

The layout of a WAV file

A WAV file is a RIFF container: a header consisting of the tag RIFF, the remaining length and the tag WAVE, followed by a sequence of chunks. Each chunk starts with four characters of type and four bytes of length; the length counts only the content. Chunks of odd length are padded to even length with one byte. For reading, two chunks matter: fmt describes the format, data contains the samples. Everything else – metadata, markers, extra information from recording software – is skipped.

With WAVE_FORMAT_EXTENSIBLE (type 0xFFFE) the chunk must be at least 40 bytes long; the actual type – PCM or floating point – is then found in the first two bytes of the format GUID at offset 24. In data the values follow interleaved by channel: first the first value of all channels, then the second, and so on. Such a set of one value per channel is called a frame; its size is returned by Wavformat.bytesJeRahmen().

Convention in the framework: the writer always produces the lean 44-byte header with a 16-byte fmt chunk, also for floating point and for more than two channels – no extensible header, no fact chunk. The reader, on the other hand, accepts everything that is PCM or IEEE floating point, including the extensible form. A NaN in the signal is written as 0.

The integer path and “bit-exact”

For a lossless encoder the floating-point signal is not sufficient as proof. The conversion k→k/V→round⁡(x⋅V)k \to k/V \to \operatorname{round}(x \cdot V) is exactly invertible for every word length up to 32 bit, because a double has a 53-bit mantissa and division by a power of two only changes the exponent. But a comparison in floating point needs a tolerance, and the tolerance decides what counts as equal. Ganzsignal avoids this: it keeps the raw values as int, and gleicht(andere) compares channel count, length, sample rate, word length and every single value for equality – without a tolerance.

  • Wavleser.liesGanz(path) reads PCM only; a floating-point file is rejected with an exception instead of being rounded silently.
  • Wavschreiber.schreibGanz(path, ganzsignal) writes the values back without any conversion (for 8 bit with the offset 128).
  • ersterUnterschied(andere) returns the index of the first differing frame, for debugging an encoder.
  • rohgroesseBytes() = length · channels · bits/8 is the reference size for the compression ratio.

Source: envisionz-framework-audiometrik/src/envisionz/audiometrik/Ganzsignal.java.

Convention in the framework: Audiosignal and Ganzsignal take over the arrays passed in without copying, and kanal(i) returns the array itself. With audio data every silent copy matters; whoever still writes into an array after handing it over changes the signal as well. The transforming methods (verschoben, ausschnitt, skaliert, aufLaenge), in contrast, return new signals – except in the neutral case (offset 0, same length, whole range), where they return the signal itself.

Transformations: mono, shift, excerpt

The measurement chain needs four simple transformations, all in Audiosignal:

  • alsMono() – arithmetic mean over the channels, mi=1C∑cxc,im_i = \frac{1}{C}\sum_c x_{c,i}. With it the alignment estimates the offset once for all channels.
  • verschoben(v) – yi=xi−vy_i = x_{i-v} where 0≤i−v<n0 \le i - v < n, otherwise 0. Positive vv shifts backwards; the length stays the same, zeros appear at the vacated edge.
  • aufLaenge(n) – cuts off or pads with zeros.
  • ausschnitt(von, bis) – half-open interval [von,bis)[\text{von}, \text{bis}); the bounds are clipped to the signal, an empty excerpt is an error.

In addition spitzenwert() = largest magnitude over all channels, to which the silence threshold of the measures refers, and dauerSekunden() = length / rate for the bit rate.

Worked example

A mono signal of two values, 0.25 and −0.25, at 48 kHz written as 16-bit PCM (Wavschreiber.alsBytes(signal, 16, false)). The 48 bytes of the file in hexadecimal:

52 49 46 46  28 00 00 00  57 41 56 45       "RIFF", 40 = 36 + 4, "WAVE"
66 6D 74 20  10 00 00 00                    "fmt ", 16
01 00  01 00  80 BB 00 00  00 77 01 00      PCM, 1 channel, 48000, 96000 bytes/s
02 00  10 00                                2 bytes per frame, 16 bit
64 61 74 61  04 00 00 00                    "data", 4 bytes
00 20  00 E0                                +8192, −8192

0.25 · 32768 = 8192 = 0x2000, least significant byte first: 00 20. −8192 in two's complement is 0xE000: 00 E0. Read back, 8192 / 32768 gives exactly 0.25 again – both values are exactly representable in 16 bit, the round-trip error is zero.

How it is tested

Wavprobe generates a stereo signal (left 32 periods with amplitude 0.8, right 64 periods with 0.4 and phase π/3, 4096 values each, 48 kHz), writes it to a temporary directory and reads it back – 19 checks:

  • For 8, 16, 24 and 32 bit PCM: sample rate, channel count and length are preserved, and the largest error stays below half a quantisation step 0.5/2b−10.5 / 2^{b-1} (with the factor 1+10−91 + 10^{-9} as rounding slack). The bound is known in closed form and does not come from an earlier run.
  • 32-bit floating point: deviation below 10−710^{-7} – only the rounding to float.
  • The profile (liesFormat) of a 16-bit file reports 16 bit, PCM and 4 bytes per frame.

The probe removes its directory afterwards. The test data are generated, not shipped.

Limits

  • The whole file is read into memory with Files.readAllBytes; positions and lengths are int. Files above 2 GB cannot be read this way.
  • Supported are PCM with 8, 16, 24 and 32 bit and floating point with 32 and 64 bit. Other format types (such as compressed WAV variants) are rejected with an exception, as is 64-bit PCM.
  • With the extensible form, the valid-bits field is read but not used: the container width is what counts. A 20-bit recording in 24-bit containers is treated as 24 bit. The channel mask is not evaluated.
  • A truncated file is not rejected: if a chunk is longer than the file, the rest counts as content. An incomplete last frame is dropped.
  • For floating point, the writer does not check the word length. Only 32 and 64 bit are intended; for any other value it writes 8 bytes per sample into an array that is too small and fails with an index-out-of-bounds exception.
  • The WAV classes duplicate those in framework-audio; merging them is an open point.
